Глава 12. Очереди и стеки: Queue, Stack, PriorityQueue

Три коллекции «взять крайний»: Queue (первым пришёл — первым вышел), Stack (последним пришёл — первым вышел) и PriorityQueue (первым выходит самый важный). Полный API, поведение на пустой коллекции, разница между «посмотреть» и «забрать», кольцевой буфер внутри Queue и разбор обхода дерева очередью и стеком.

основная глава

Общее у всех трёх: доступа по индексу нет. Вы не спрашиваете «что лежит под номером 3», вы спрашиваете «что следующее». Это делает их удобными для обработки по порядку: задачи, обход графа, буферы, планировщики.

КоллекцияКто выходит первымДобавитьЗабрать Посмотреть
Queue<T>тот, кто пришёл раньше всех (FIFO) EnqueueDequeuePeek
Stack<T>тот, кто пришёл последним (LIFO) PushPopPeek
PriorityQueue<TElement, TPriority>самый важный (минимальный приоритет)EnqueueDequeue Peek

Запомнить сразу: Peek только смотрит — элемент остаётся в коллекции и Count не меняется. Dequeue/Pop забирают — элемент удаляется и возвращается вам. Дальше это показано выводом, а не словами.

Queue<T>: Peek смотрит, Dequeue забирает

var q = new Queue<string>();
q.Enqueue("первый");
q.Enqueue("второй");
q.Enqueue("третий");

Console.WriteLine(q.Count + " " + q.Peek() + " " + q.Count);   // 3 первый 3 — Peek НЕ удаляет
Console.WriteLine(q.Dequeue() + " " + q.Count);                // первый 2 — Dequeue удалил
Console.WriteLine(q.Contains("третий"));                       // True
Console.WriteLine(string.Join(",", q.ToArray()));              // второй,третий

«Без сдвига элементов» — а что с пустотой?

Резонный вопрос: Dequeue забрал элемент из начала — в массиве осталась пустая ячейка. Кто её уберёт? Никто, и именно поэтому очередь быстрая: пустота не убирается, а переиспользуется. Внутри Queue<T> обычный массив и два индекса, которые ходят по кругу:

  • head — индекс первого элемента: отсюда читают Dequeue и Peek;
  • tail — индекс, куда ляжет следующий: сюда пишет Enqueue;
  • size — сколько ячеек занято (это и есть Count). Он же отличает пустую очередь от полной: в обоих случаях head == tail, и без счётчика их не различить.

Оба индекса двигаются только вперёд, а дойдя до конца массива — прыгают в начало: tail = (tail + 1) % array.Length. Поэтому «конец» очереди может оказаться левее её «начала»: массив считается круглым. Вот настоящее состояние внутренностей Queue<string>, снятое рефлексией по приватным полям в .NET 8 (· — пустая ячейка):

ДействиеМассив в памятиheadtailsize Что видит код
new Queue<string>()[] (0)00 0пусто
Enqueue(a) ×4[a, b, c, d] (4)00 4a, b, c, d — tail обежал круг
Dequeue() → a[·, b, c, d] (4)1 03b, c, d — ячейку обнулили, остальное не сдвинулось
Dequeue() → b[·, ·, c, d] (4)2 02c, d

Enqueue(g): 5-й элемент при длине 4 [c, d, e, f, g, ·, ·, ·] (8)055 c, d, e, f, g — буфер вырос

Смотрите на пятую строку: e легло в ячейку 0 — ту самую, которую только что освободило Dequeue. Ничего не сдвигалось, пустота просто ушла под следующий элемент. Это и есть кольцевой буфер: массив один, а очередь «едет» по нему по кругу.

Когда всё-таки происходит копирование: только при росте. Если size == array.Length и приходит ещё один элемент, создаётся массив вдвое больше, элементы копируются в логическом порядке (начиная с head), head становится 0, tail — size. Это O(n), но случается логарифмически редко — в этом и смысл «амортизированно O(1)». Рост удвоением — тот же приём, что у List<T> (глава 7).

Две детали, которые видно на том же дампе
  • Ячейка обнуляется при Dequeue. В строке 3 на месте a стоит ·, а не a: иначе очередь держала бы ссылку на уже отданный объект и не давала сборщику мусора его собрать.
  • Массив не сжимается сам. После всплеска очередь продолжает держать большой буфер: в том же прогоне 9 элементов жили в массиве на 16, и только TrimExcess() сжал его до 9 (и вернул head в 0). Разобрали 100 000 сообщений и очередь больше не нужна — вызовите TrimExcess().
Как посмотреть внутрь самому

Поля приватные, но рефлексией их видно — годится только для экспериментов:

var t = typeof(Queue<string>);
var flags = BindingFlags.NonPublic | BindingFlags.Instance;
object? Field(string n) => t.GetField(n, flags)!.GetValue(q);

var arr = (string[])Field("_array")!;
Console.WriteLine(string.Join(",", arr.Select(x => x ?? "·"))
    + " head=" + Field("_head") + " tail=" + Field("_tail") + " size=" + Field("_size"));

Имена полей — внутренняя деталь реализации: в другой версии .NET они могут называться иначе. Для понимания это не важно, важно что head, tail и size есть всегда.

Пустая очередь: исключение или Try*

Peek и Dequeue на пустой коллекции бросают исключение, и текст у него общий для обычной и приоритетной очереди:

var empty = new Queue<string>();
Console.WriteLine(empty.TryPeek(out _) + " " + empty.TryDequeue(out _));   // False False

try { empty.Dequeue(); }
catch (Exception e) { Console.WriteLine(e.GetType().Name + ": " + e.Message); }

Вывод

False False
InvalidOperationException: Queue empty.

Поэтому обработку в цикле пишут через TryDequeue — цикл закончится сам, когда очередь опустеет, и проверка Count > 0 не нужна:

while (q.TryDequeue(out var item))
    Console.WriteLine("обрабатываю: " + item);     // ровно столько итераций, сколько элементов

Stack<T>: Push, Pop, Peek

Стек — та же идея, но с другого конца: Push кладёт наверх, Pop снимает верхний, Peek смотрит верхний, не снимая.

var stack = new Stack<int>();
stack.Push(1);
stack.Push(2);
stack.Push(3);

Console.WriteLine(stack.Count + " " + stack.Peek() + " " + stack.Count);   // 3 3 3 — Peek не снимает
Console.WriteLine(stack.Pop() + " " + stack.Count);                        // 3 2 — Pop снял
Console.WriteLine(stack.Contains(1));                                      // True
Console.WriteLine(string.Join(",", stack.ToArray()));                      // 2,1 — сверху вниз

Вывод

3 3 3
3 2
True
2,1

Обратите внимание на ToArray: у стека перечисление идёт сверху вниз, то есть в порядке «как будут сниматься». Это же касается foreach.

Что выбрать: FIFO или LIFO

Разница видна на одних и тех же данных: обойти дерево очередью и стеком — значит получить разный порядок. Прежде чем смотреть на код, разберём, что в нём происходит и зачем нужна каждая строка.

Данные: дерево, записанное словарём

Дерево в примере — это связи «узел → его дети». Держать их удобно словарём (глава 10): ключ — имя узла, значение — массив детей, у листьев массив пустой. Ничего специфически «словарного» тут не происходит, это просто способ хранить граф в коде:

var tree = new Dictionary<string, string[]>
{
    ["A"] = new[] { "B", "C" }, ["B"] = new[] { "D" },
    ["C"] = new[] { "E" },      ["D"] = Array.Empty<string>(),
    ["E"] = Array.Empty<string>(),
};

// A
// ├── B
// │   └── D
// └── C
//     └── E

tree["A"] — это ["B", "C"], то есть «у A два ребёнка». Оба обхода делают одно и то же: берут узел, записывают его в ответ и кладут в коллекцию его детей. Разница только в том, какая это коллекция.

Код: два одинаковых цикла, одна разница

  • var bfsOrder = new List<string>() — «тетрадка» для порядка посещения. К обходу она отношения не имеет: это место, куда складываем ответ, чтобы в конце напечатать и сравнить два порядка. Не нужен результат — не нужен и List.
  • var q = new Queue<string>() — очередь; в ней лежат узлы, которые уже найдены, но ещё не посещены.
  • q.Enqueue("A") — начинаем с корня.
  • while (q.TryDequeue(out var node)) — «пока очередь не пуста, взять следующий узел». TryDequeue вернёт false, когда элементов нет, поэтому цикл закончится сам и Count > 0 проверять не нужно.
  • bfsOrder.Add(node) — отметили узел посещённым (в графе с циклами здесь была бы ещё проверка «не посещали ли уже»).
  • foreach (var child in tree[node]) q.Enqueue(child) — дети встают в очередь в конец, то есть будут обработаны после всех, кто пришёл раньше.
  • Второй блок отличается двумя словами: Stack вместо Queue и Push/TryPop вместо Enqueue/TryDequeue. Дети ложатся наверх, поэтому обрабатываются сразу, а не после всех.
// очередь: обход «в ширину» — уровень за уровнем
var bfsOrder = new List<string>();       // тетрадка для ответа, к обходу не относится
var q = new Queue<string>();
q.Enqueue("A");                            // стартуем с корня
while (q.TryDequeue(out var node))         // пока в очереди есть узлы
{
    bfsOrder.Add(node);                    // посетили узел
    foreach (var child in tree[node])      // а его детей — в конец очереди
        q.Enqueue(child);
}

// стек: обход «в глубину» — до самого низа, потом сосед
var dfsOrder = new List<string>();
var stack = new Stack<string>();
stack.Push("A");
while (stack.TryPop(out var node))
{
    dfsOrder.Add(node);
    foreach (var child in tree[node])
        stack.Push(child);                 // дети ложатся наверх — их возьмут сразу
}

Console.WriteLine(string.Join(" ", bfsOrder));
Console.WriteLine(string.Join(" ", dfsOrder));

Вывод

A B C D E
A C E B D

Что происходит на каждом шаге

Тот же прогон, но с состоянием коллекции. У очереди смотрим «кто в ней стоит», у стека — «кто наверху» (снимают правого):

Что из этого вынести

  • Данные одни и те же, порядок разный. Коллекция и есть правило порядка: очередь отдаёт того, кто пришёл раньше, стек — того, кто пришёл последним.
  • A B C D E — это уровни дерева: корень, затем его дети (B, C), затем внуки (D, E). Так работает BFS — поиск кратчайшего пути в невзвешенном графе, «волной» от источника.
  • A C E B D — это ветка до конца, потом соседняя: спустились A → C → E, вернулись и пошли в B → D. Так работает DFS: парсеры, обход дерева каталогов, топологическая сортировка.
  • Почему не A B D C E? Потому что дети легли в стек в порядке B, C — и C оказался сверху, поэтому его сняли первым. Стек переворачивает порядок детей. Нужно «по алфавиту» — кладите их наоборот: foreach (var child in tree[node].Reverse()), и получится A B D C E.
  • В настоящем обходе графа, где есть циклы, дополнительно хранят посещённые узлы (HashSet, глава 11), иначе обход зациклится. В дереве из примера циклов нет, поэтому проверка не нужна.
Очередь ≠ List<T> с RemoveAt(0)

Соблазн сделать очередь из списка велик, но list.RemoveAt(0) сдвигает все оставшиеся элементы — O(n) на каждое извлечение, то есть O(n²) на обработку n элементов. Очередь на кольцевом буфере делает то же за O(1).

PriorityQueue<TElement, TPriority>: приоритет вместо порядка

С .NET 6 в BCL есть приоритетная очередь: при добавлении указываются элемент и его приоритет, а извлекается всегда минимальный приоритет.

var pq = new PriorityQueue<string, int>();
pq.Enqueue("низкий", 5);
pq.Enqueue("критичный", 1);
pq.Enqueue("средний", 3);

Console.WriteLine(pq.Count + " " + pq.Peek() + " " + pq.Count);          // Peek не забирает
Console.WriteLine(pq.TryPeek(out var e, out var p) + " " + e + "/" + p);
Console.WriteLine(pq.TryDequeue(out var d, out var dp) + " " + d + "/" + dp);

pq.Enqueue("ещё-средний", 3);
Console.WriteLine(string.Join(", ", pq.UnorderedItems.Select(i => i.Element + "(" + i.Priority + ")")));

Вывод

3 критичный 3
True критичный/1
True критичный/1
средний(3), низкий(5), ещё-средний(3)

UnorderedItems — не порядок извлечения, а внутреннее представление кучи, и имя это честно говорит. Настоящий порядок видно только при извлечении.

Два поведения, которые чаще всего удивляют:

// 1. Максимум вместо минимума — обратный компаратор (глава 9)
var maxHeap = new PriorityQueue<string, int>(Comparer<int>.Create((a, b) => b.CompareTo(a)));
maxHeap.Enqueue("a", 1); maxHeap.Enqueue("c", 3); maxHeap.Enqueue("b", 2);
while (maxHeap.TryDequeue(out var el, out _)) Console.Write(el + " ");

// 2. Равные приоритеты: порядок НЕ гарантирован — это куча, а не стабильная сортировка
var same = new PriorityQueue<string, int>();
same.Enqueue("первый", 1); same.Enqueue("второй", 1); same.Enqueue("третий", 1);
var order = new List<string>();
while (same.TryDequeue(out var el, out _)) order.Add(el);

Console.WriteLine();
Console.WriteLine(string.Join(",", order));

Вывод

c b a
первый,третий,второй

первый,третий,второй — не случайность и не баг: при равных приоритетах куча не обязана сохранять порядок вставки. Нужна стабильность — делайте приоритет составным: (int Priority, long Sequence), где Sequence — счётчик добавления.

Итог: какую коллекцию под какую задачу

Теперь разобраны все три — Queue, Stack и PriorityQueue, — так что таблицу выбора можно читать без забегания вперёд:

ЗадачаЧемПочему
Обработать задачи в порядке поступленияQueueСправедливо: кто раньше пришёл, тот раньше обслужен
Обход в ширину (BFS), «уровни»QueueСоседи обрабатываются раньше их детей
Отмена последнего действия (undo)StackОтменяется то, что сделано последним
Обход в глубину (DFS), парсер скобокStackВложенность: закрываем то, что открыто последним
Сначала самое важноеPriorityQueueПорядок задаётся приоритетом, а не временем прихода

Как это устроено и где применять

  • Queue — кольцевой буфер (разобран выше): массив плюс head/tail, O(1) на Enqueue и Dequeue. Stack — массив плюс указатель на верхушку: Push и Pop тоже O(1). У обоих поиск значения (Contains) — O(n), память — как у массива, с запасом на рост.
  • PriorityQueue — двоичная куча в массиве: добавление и извлечение O(log n), просмотр минимума O(1), полный перебор — O(n) в произвольном порядке.
  • Где пригодится приоритет: планировщик задач (сначала критичные), ограничитель частоты (сначала те, у кого кончается квота), алгоритм Дейкстры (сначала ближайшая вершина), обработка таймаутов (сначала тот, кто истекает раньше). Обычно приоритетом служит DateTime или TimeSpan — они сравнимы (глава 9).

Очередь и несколько потоков

Queue, Stack и PriorityQueue не потокобезопасны: одновременные Enqueue и Dequeue из разных потоков могут испортить внутренний указатель — без исключения, просто «поехавшими» данными. Варианты по назначению:

Что нужноЧем
Очередь между потоками без ожиданияConcurrentQueue<T>, ConcurrentStack<T> — TryDequeue/TryPop вместо Dequeue/Pop
Очередь с ожиданием (производитель ждёт, пока потребитель заберёт) Channel<T> — глава 26 .NET-книги
Очередь в одном потокеОбычные Queue/Stack — самый быстрый вариант

Обёртка «Queue + lock» работает, но это ровно то, что уже сделано внутри ConcurrentQueue; а блокирующее ожидание элемента лучше не писать руками, а взять Channel с ReadAllAsync.

Почему глав про List и SortedList нет, а про LinkedList есть

В части II коллекции разобраны не «по одной на каждую», а по тому, где чаще ошибаются: словари (глава 10), множества (глава 11), очереди и стеки (эта глава), связный список (глава 13).

  • List<T> — глава 7: внутри массив, Capacity и EnsureCapacity, рост удвоением, скрытая аллокация в foreach, какой интерфейс возвращать из метода. Отдельная глава была бы пересказом этого плюс Add/RemoveAt.
  • SortedList<TKey, TValue> — глава 10, таблица рядом с SortedDictionary: API у них одинаковый, разница только во внутренней структуре (два массива против дерева), поэтому это сравнение на полстраницы, а не глава.
  • LinkedList<T> — вынесен в отдельную главу 13: он устроен принципиально иначе (узлы вместо массива), и про него спрашивают на собеседованиях — почему перебор медленнее, где O(1) реально помогает, как устроен LRU-кэш.

Ловушки

  • Peek не удаляет, Dequeue/Pop удаляют. Классическая ошибка: посмотреть Peek и удивиться, что в цикле элемент обрабатывается дважды.
  • Исключение на пустой коллекции. Dequeue/Pop/Peek бросают InvalidOperationException; в цикле обработки — TryDequeue/ TryPop.
  • Проверка Count вместо TryDequeue. while (q.Count > 0) q.Dequeue() работает, но в многопоточном коде между проверкой и извлечением элемент может исчезнуть — исключение. TryDequeue атомарен по смыслу.
  • Изменение очереди во время foreach — InvalidOperationException (глава 14). Забирать элементы нужно через цикл с TryDequeue.
  • ToArray у стека — сверху вниз, а не снизу вверх: перечисление Stack<T> идёт в порядке извлечения.
  • Равные приоритеты в PriorityQueue идут в произвольном порядке — не полагайтесь на «порядок добавления».
  • Список вместо очереди — RemoveAt(0) даёт O(n²) на всю обработку.
★ Что запомнить из главы
  • Peek смотрит, Dequeue/Pop забирают — Count после Peek не меняется.
  • Queue — FIFO (Enqueue/Dequeue/Peek), Stack — LIFO (Push/Pop/Peek); оба O(1) на краях и O(n) на Contains.
  • Пустая коллекция: InvalidOperationException («Queue empty.» / «Stack empty.») либо Try*-варианты с false.
  • PriorityQueue отдаёт минимальный приоритет; максимум — обратным компаратором; равные приоритеты не стабильны; UnorderedItems — не порядок извлечения.
  • Очередь — это Queue, а не List: RemoveAt(0) превращает обработку в O(n²).
  • Между потоками — ConcurrentQueue/Channel, а не Queue с lock.
