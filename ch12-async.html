Глава 12. Асинхронность: async/await и Task

Главный инструмент серверной разработки на .NET: как обслуживать много запросов малым числом потоков и не превратить это в «стоп-кран».

Как работает async/await

Компилятор превращает метод с async в машину состояний. В точке await метод не блокирует поток: он сохраняет своё состояние и возвращает управление вызывающему (поток уходит обслуживать другие запросы). Когда операция завершится, продолжение выполнится — возможно, на другом потоке.

Где разобрано внутреннее устройство

Во что именно разворачивается async (поля стейт-машины, MoveNext, AsyncTaskMethodBuilder), почему Task — это обещание, а не поток, когда ValueTask экономит аллокацию и какие у него ограничения, а также что делает ConfigureAwait(false) — в C#-книге, глава 9. Здесь — прикладная сторона: как писать асинхронный код сервиса.

public async Task<UserDto> GetUserAsync(int id, CancellationToken ct)
{
    var user = await _repo.GetByIdAsync(id, ct); // поток освобождён на время I/O
    return user;                                  // продолжение после завершения
}

Правило №1: async до конца

Если метод асинхронный — он должен быть таким на всём пути, от эндпоинта до последнего слоя. Смешивание async и синхронного ожидания — причина «голодания» пула из главы 9.

«Не до конца» — это когда где-то в глубине асинхронный результат достают синхронно:

✘ async не до конца: синхронное ожидание внутри

public Order Get(int id)
{
    // .Result блокирует поток, пока не придёт ответ из базы
    return _repo.FindAsync(id).Result;
}

// то же самое, другая запись
public Order Get2(int id) => _repo.FindAsync(id).GetAwaiter().GetResult();

Что происходит: поток пула стоит и ждёт базу. Под нагрузкой свободные потоки кончаются, новые запросы встают в очередь — задержка растёт, начинаются таймауты.

✔ async до конца: ожидание не занимает поток

public async Task<Order> GetAsync(int id, CancellationToken ct)
{
    var order = await _repo.FindAsync(id, ct);   // поток освобождён на время запроса
    return order;
}

// и выше по стеку — тоже await, до самого эндпоинта
app.MapGet("/orders/{id:int}", async (int id, OrderService svc, CancellationToken ct) =>
    Results.Ok(await svc.GetAsync(id, ct)));
Как проверить, что путь «до конца»

Пройдите от эндпоинта вниз: если хотя бы на одном слое есть .Result, .Wait(), GetAwaiter().GetResult() или синхронный вызов БД — путь порван именно там. Лечится изменением сигнатуры на async Task<T> по всей цепочке.

Что полезно знать

ТемаКоротко
TaskЗадача без результата: «сделай и скажи, когда закончишь» — async Task
Task<T>Задача с результатом типа T: «сделай и верни значение» — async Task<Order>
async voidТолько для UI-событий. В серверном коде — нет: исключения не поймать.
ValueTaskЭкономит аллокацию, когда результат часто готов сразу (например, кэш). Обычно хватает Task.
ConfigureAwait(false)В библиотеках — чтобы не возвращаться в исходный контекст. В ASP.NET Core своего контекста нет, поэтому там менее критично.
Не нужен Task.Run «чтобы стало асинхронно»

На сервере оборачивание кода в Task.Run не ускоряет его, а просто переносит работу на другой поток пула + добавляет аллокацию. Async оправдан там, где есть настоящее ожидание ввода-вывода.

Отмена операций: CancellationToken

CancellationToken — это структура-флаг: «работу пора прекратить». Сам токен ничего не отменяет — он лишь сообщает об отмене, а код должен это заметить и завершиться. Такая отмена называется кооперативной: никого нельзя убить снаружи, можно только попросить.

Кто создаёт токен

ГдеКто создаётКогда срабатывает
ASP.NET Core, обработчик запросафреймворк — у каждого запроса свой токен клиент отключился; сервер останавливается (SIGTERM)
Фоновая задача (BackgroundService)хост — токен остановки приложения StopAsync / завершение процесса
Свой таймаутвы: new CancellationTokenSource(TimeSpan) или CancelAfterистекло время
Объединениевы: CreateLinkedTokenSource(ct, cts.Token) сработает любой из двух

Токен — не «магическая» переменная. Это обычный параметр метода; ct — просто общепринятое сокращение от cancellationToken. Имя может быть любым, но менять его без причины не стоит: ct узнаётся с первого взгляда.

Как он передаётся

Токен идёт по цепочке вызовов: контроллер → сервис → репозиторий → EF Core / Npgsql / HttpClient. Каждый слой передаёт его дальше, а не создаёт свой:

[HttpGet("/orders/{id:guid}")]
public async Task<IActionResult> Get(Guid id, CancellationToken ct)   // ← токен дал фреймворк
{
    var order = await _service.GetAsync(id, ct);                     // передали в сервис
    return order is null ? NotFound() : Ok(order);
}

public Task<Order?> GetAsync(Guid id, CancellationToken ct) =>
    _db.Orders.AsNoTracking().FirstOrDefaultAsync(o => o.Id == id, ct);   // и в EF Core

// наружу (HTTP-зависимость) — тоже с токеном
var response = await _client.GetAsync(url, ct);
  • Не храните токен в DI (singleton/scoped на всё приложение): токен относится к конкретной операции, а не к сервису.
  • Не используйте CancellationToken.None в публичном API «по умолчанию, если не передали» — так отмену молча теряют все вызывающие. Лучше требовать параметр (или помечать ct = default только для удобства тестов).
  • Проверяйте в длинных циклах: ct.ThrowIfCancellationRequested() на каждой итерации — иначе «отмена» заметится только после завершения всей работы.

Что происходит при отмене

  • Операция, поддерживающая отмену (EF Core, Npgsql, HttpClient, Task.Delay), прерывается и бросает OperationCanceledException (для задач — TaskCanceledException).
  • await пробрасывает это исключение в ваш код; задача переходит в состояние Canceled.
  • Это не ошибка сервиса: в ASP.NET Core, если клиент отключился, писать 500 некому — такие исключения обычно не логируют как ошибку.
  • Поток при этом не «убивается»: он просто перестаёт ждать и возвращается в пул (гл. 9).
// свой таймаут поверх клиентского токена: сработает то, что раньше
using var cts = CancellationTokenSource.CreateLinkedTokenSource(ct);
cts.CancelAfter(TimeSpan.FromSeconds(2));      // «не дольше 2 секунд»

try
{
    return await _client.GetStringAsync(url, cts.Token);
}
catch (OperationCanceledException) when (!ct.IsCancellationRequested)
{
    // отменил таймаут, а не клиент → это ошибка зависимости, её можно повторить (гл. 27)
    throw new TimeoutException("зависимость не ответила за 2 с");
}
Две тонкости, на которых ошибаются
  • IsCancellationRequested против ThrowIfCancellationRequested: первое — «спросить флаг» (когда нужно аккуратно завершиться), второе — «бросить исключение» (когда можно прерваться).
  • CancellationTokenSource нужно освобождать (using), но не раньше, чем закончатся операции, которые им пользуются. И отменённый источник повторно не используют — создают новый.
  • Отмена ≠ немедленная остановка: код может ещё какое-то время доигрывать текущую порцию (например, коммит транзакции). Поэтому в обработчиках отмену проверяют на границах шагов, а не посреди критической секции.
★ Что запомнить из главы

async/await позволяет не занимать поток во время ввода-вывода — это основа высокой пропускной способности. Держите путь асинхронным от начала до конца и пробрасывайте отмену. Как запускать несколько операций сразу и как это ограничивать — в главе 13.
