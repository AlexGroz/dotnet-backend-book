Глава 5. Версии строк: почему UPDATE «создаёт» строку

Почему UPDATE в PostgreSQL не меняет строку на месте — и откуда из этого берутся версии строк, MVCC (глава 21), VACUUM и раздувание таблиц (глава 23).

Три термина, которые встретятся дальше
ТерминОдной фразойПодробно
MVCCБаза хранит несколько версий одной строки, поэтому читатели не блокируют писателейглава 21
VACUUMОчистка мёртвых версий, которые больше никому не видныглава 23
Bloat (раздувание)Рост таблицы из-за мёртвых версий и «дырок» в страницахглава 23

Задача: читатели не должны ждать писателей

Представь, что один клиент читает длинный отчёт, а другой в это время меняет строку. Как быть? Можно запретить чтение на время записи — но это убило бы пропускную способность. PostgreSQL решает это иначе: хранит несколько версий одной строки.

Что происходит при UPDATE

СУБД не меняет строку на месте. Вместо этого:

  1. старая строка помечается как «мёртвая» (версия, которую видеть больше не нужно);
  2. создаётся новая версия строки с новыми значениями.
Было:   [ строка id=5, сумма=100 ]        ← версия 1 (актуальная)
UPDATE orders SET amount = 200 WHERE id = 5;
Стало:  [ строка id=5, сумма=100 ]  мёртвая версия (ждёт VACUUM)
        [ строка id=5, сумма=200 ]  ← новая версия (актуальная)

DELETE работает похоже: строка просто помечается мёртвой, физически она останется на диске, пока её не уберёт VACUUM.

Как СУБД понимает, какую версию видит читатель

У каждой версии есть служебные метки — идентификаторы транзакций:

  • xmin — «кто создал» эту версию;
  • xmax — «кто её удалил/заменил» (пусто, если ещё жива).

Правила видимости простые: читатель видит ту версию, которая была создана до начала его работы и ещё не удалена. Поэтому каждый читатель видит свой согласованный «снимок», и никому не приходится ждать.

Цена этого решения

За удобство платим тремя вещами:

  • Раздувание (bloat): мёртвые версии занимают место, таблица «толстеет».
  • Нужен VACUUM: кто-то должен убирать мёртвые версии (иначе таблица только растёт).
  • Долгие транзакции мешают: пока транзакция «держит» старый снимок, старые версии нельзя удалять.

Почему на запись таблица может «распухнуть»

Если по таблице часто выполняют UPDATE, версии копятся быстрее, чем их успевает убирать VACUUM. Таблица занимает всё больше места, а запросы читают всё больше страниц — то есть тормозят. Именно поэтому при миграции из Oracle важно настроить autovacuum (глава 23).

Ещё одно следствие: ctid нестабилен

Мы помним (глава 4), что адрес строки ctid меняется при UPDATE — именно потому, что строка физически переезжает на новое место. Поэтому ctid нельзя использовать как ключ.

★ Что запомнить

UPDATE не меняет строку, а создаёт новую версию, оставляя старую «мёртвой». Благодаря этому читатели и писатели не мешают друг другу. Обратная сторона — «раздувание» таблиц и необходимость VACUUM; долгие транзакции мешают очистке.
