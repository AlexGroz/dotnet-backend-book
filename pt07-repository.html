Глава 7. Репозиторий и Unit of Work: когда нужны, а когда мешают

Самый спорный паттерн в .NET-сообществе: без него не обходится ни один «энтерпрайз»-шаблон, но поверх EF Core он часто не даёт ничего, кроме лишнего слоя.

основная глава

Разминка: идея на десяти строках

Бизнес-логике нужно «достать заказ по id», не зная, откуда он берётся: из базы, кэша или тестового списка. Репозиторий — это «коллекция» с таким интерфейсом.

public sealed record Order(int Id, decimal Total);   // просто данные

public interface IOrderRepository
{
    Order? Find(int id);              // «найди по id»
    void Save(Order order);           // «сохрани»
}

// Реализация для тестов: словарь в памяти, никакой базы
public sealed class InMemoryOrders : IOrderRepository
{
    private readonly Dictionary<int, Order> _items = new();

    public Order? Find(int id) => _items.GetValueOrDefault(id);
    public void Save(Order order) => _items[order.Id] = order;
}

// Бизнес-логика не знает ни про базу, ни про EF Core
static decimal Total(IOrderRepository repo, int id) => repo.Find(id)?.Total ?? 0m;

var repo = new InMemoryOrders();
repo.Save(new Order(1, 500m));
Console.WriteLine(Total(repo, 1));    // 500

Ровно так же выглядит работа с базой — только внутри реализации будет SQL или EF Core. Дальше разберём, зачем это нужно и где репозиторий превращается в лишний слой.

Идея: «коллекция» вместо SQL и одна транзакция на работу

  • Репозиторий — интерфейс, который выглядит как коллекция объектов домена: GetById, Add, Remove, Find.... Бизнес-код не знает, что внутри EF Core, Dapper или два разных источника данных.
  • Unit of Work — «единица работы»: набор изменений, которые применяются вместе, одной транзакцией. В EF Core эту роль играет DbContext.
public interface IOrderRepository
{
    Task<Order?> GetAsync(Guid id, CancellationToken ct);
    Task<IReadOnlyList<Order>> GetOverdueAsync(DateTime now, CancellationToken ct);
    void Add(Order order);
    void Remove(Order order);
}

public interface IUnitOfWork
{
    Task<int> SaveChangesAsync(CancellationToken ct);   // одна транзакция на все изменения
}
// Реализация на EF Core: здесь и только здесь живут запросы
public sealed class EfOrderRepository(AppDbContext db) : IOrderRepository
{
    public Task<Order?> GetAsync(Guid id, CancellationToken ct) =>
        db.Orders.FirstOrDefaultAsync(o => o.Id == id, ct);

    public async Task<IReadOnlyList<Order>> GetOverdueAsync(DateTime now, CancellationToken ct) =>
        await db.Orders.Where(o => o.DueAt < now && o.Status != OrderStatus.Paid)
                       .AsNoTracking()
                       .ToListAsync(ct);

    public void Add(Order order) => db.Orders.Add(order);
    public void Remove(Order order) => db.Orders.Remove(order);
}

public sealed class EfUnitOfWork(AppDbContext db) : IUnitOfWork
{
    public Task<int> SaveChangesAsync(CancellationToken ct) => db.SaveChangesAsync(ct);
}

Сервис теперь работает с доменом, а не с SQL:

public sealed class PayOrderHandler(IOrderRepository orders, IUnitOfWork uow)
{
    public async Task HandleAsync(Guid id, CancellationToken ct)
    {
        var order = await orders.GetAsync(id, ct) ?? throw new NotFoundException(id);
        order.MarkAsPaid();                 // бизнес-правило внутри сущности
        await uow.SaveChangesAsync(ct);     // одна транзакция, одна точка сохранения
    }
}
В интерфейсе нет кода — откуда берётся работа?

IOrderRepository — только обещание («есть метод GetAsync»). Тело метода живёт в реализации EfOrderRepository, где написан запрос через EF Core. Обработчик об этом классе не знает — он видит только интерфейс.

Связывает их контейнер при старте приложения:

builder.Services.AddScoped<IOrderRepository, EfOrderRepository>();  // «на интерфейс — вот эта реализация»
builder.Services.AddScoped<IUnitOfWork, EfUnitOfWork>();
builder.Services.AddScoped<PayOrderHandler>();

Когда приходит запрос, контейнер создаёт PayOrderHandler и подставляет в него настоящий EfOrderRepository. Поэтому строка await orders.GetAsync(id, ct) в итоге выполняет SQL — просто обработчик об этом не знает. Механика — «Backend на .NET», глава 15.

Что значит «работает с доменом, а не с SQL»

Раньше в сервисе было бы db.Orders.Where(o => o.Id == id) — сервис знал бы про EF Core, таблицу и колонки. Теперь он знает только про домен: «есть заказы, у них есть MarkAsPaid(), изменения сохраняются одним SaveChangesAsync». Как это уйдёт в базу — вопрос реализации репозитория.

Кстати, ?? throw new NotFoundException(id) — идиома «получить или упасть»: если репозиторий вернул null, бросаем исключение (подробно — C#-книга, глава 9).

Неприятная правда про EF Core

DbContext уже реализует оба паттерна:

  • отслеживает изменения и сохраняет их одной транзакцией — это Unit of Work;
  • DbSet<T> ведёт себя как коллекция сущностей — это репозиторий.

Поэтому «репозиторий поверх EF Core» часто превращается в тонкую прослойку, которая просто пробрасывает вызовы, и в худшем случае — в утечку IQueryable:

// ✘ антипаттерн: репозиторий отдаёт IQueryable — значит, всё равно «течёт» ORM
public interface IRepository<T>
{
    IQueryable<T> Query();               // вызывающий может собрать любой SQL и сломать план
    Task<T?> GetAsync(int id);
    Task AddAsync(T entity);
    Task RemoveAsync(T entity);
    … ещё 15 методов «на всякий случай»
}

Что может сделать вызывающий — и почему ломается план

var bad = repo.Query()
    .Where(o => o.CreatedAt.Year == 2026)   // ← функция по колонке
    .OrderBy(o => o.Total)
    .Take(20)
    .ToList();

// в SQL уйдёт: date_part('year', created_at) = 2026
// → индекс по created_at не применим → Seq Scan по всей таблице
// и репозиторий об этом не узнает: запрос собрал вызывающий
Почему это плохо
  • IQueryable «протекает» наружу: бизнес-код снова собирает LINQ, то есть ORM никуда не спрятан.
  • Универсальный IRepository<T> с десятком методов обслуживает всех и не выражает доменные запросы — вместо GetOverdueAsync появляется Query().Where(...) в сервисе.
  • Появляется «репозиторий ради репозитория»: tests всё равно требуют EF InMemory или базу, а преимущество не достигнуто.

Когда репозиторий оправдан

  • Несколько источников данных. Заказ — в PostgreSQL, документы — в S3, справочник — во внешнем API. Домену нужен один интерфейс, а не три клиента.
  • Домен не должен знать про ORM. Если сущности и правила живут отдельно от EF (clean/hexagonal-архитектура), репозиторий — граница между слоями.
  • Сложные доменные запросы. GetOverdueAsync с понятным именем читается и тестируется лучше, чем запрос на 20 строк в сервисе.
  • Командное соглашение. Если вся команда договорилась «в сервисах нет DbContext», репозиторий обеспечивает это правило.
Компромисс, который работает

Делать не универсальный IRepository<T>, а репозиторий на агрегат с доменными методами (IOrderRepository.GetOverdueAsync), без IQueryable наружу и с возвратом IReadOnlyList. А Unit of Work — просто DbContext.SaveChangesAsync, обёрнутый только если домену нужна независимость от EF.

Как это выглядит в DI

builder.Services.AddScoped<IOrderRepository, EfOrderRepository>();
builder.Services.AddScoped<IUnitOfWork, EfUnitOfWork>();
builder.Services.AddScoped<PayOrderHandler>();

// ВАЖНО: DbContext тоже scoped — иначе получатся «разные транзакции» и гонки.
builder.Services.AddDbContext<AppDbContext>(o => o.UseNpgsql(cs));

Если репозиторий и Unit of Work регистрируются как singleton или создают свой DbContext — изменения перестают быть атомарными: одна часть работы сохранится, другая нет (об этом — глава 23 .NET-раздела и глава 4 конспектов про транзакции).

Ловушка, на которую легко попасть: Service Locator

Иногда «репозиторий» превращают в способ достать что угодно из контейнера:

// ✘ Service Locator: зависимости скрыты, тесты и чтение кода страдают
public sealed class OrderService(IServiceProvider sp)
{
    public async Task PayAsync(Guid id, CancellationToken ct)
    {
        var repo = sp.GetRequiredService<IOrderRepository>();   // зависимость «из воздуха»
        …
    }
}

Правильно — внедрять зависимости через конструктор. Тогда видно, что нужно сервису, и тест может подставить реализации напрямую.

Статистика: насколько часто

Оценка: ~50 % проектов и ~10 % от всех применений паттернов.

  • Факт: DbContext — это готовый Unit of Work, а DbSet<T> — готовый «репозиторий»; эти механизмы используются в любом приложении с EF Core.
  • Почему оценка проектов ~50 %: «свои» репозитории добавляют в основном в энтерпрайз-проектах и по шаблону; в небольших сервисах часто работают прямо с DbContext.
  • Доля ниже всех именно потому, что паттерн дублирует то, что уже даёт ORM — и сообщество до сих пор спорит, нужен ли он.
  • Оговорка: оценка пропорции, а не измерение (глава 1).
★ Что запомнить из главы
  • Репозиторий — «коллекция» доменных объектов; Unit of Work — одна транзакция на набор изменений.
  • В EF Core оба уже есть: DbContext — UoW, DbSet<T> — репозиторий.
  • Свой репозиторий оправдан, когда он выражает доменные запросы или скрывает несколько источников данных.
  • Универсальный IRepository<T> с IQueryable наружу — антипаттерн: ORM всё равно «течёт».
  • Оценка: ~50 % проектов, ~10 % от всех использований паттернов.
