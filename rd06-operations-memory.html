Глава 6. Эксплуатация: память, eviction, персистентность и отказоустойчивость

Что произойдёт, когда память кончится, что теряется при перезапуске и как не превратить кэш в единую точку отказа

основная глава

Память: maxmemory и политики вытеснения

Redis не «сам понимает», сколько памяти ему можно. Пока maxmemory равен нулю, он растёт до исчерпания памяти машины — и тогда его убьёт OOM-killer контейнера или ОС. Поэтому лимит задают явно, а вместе с ним — политику: что делать, когда лимит достигнут.

ПолитикаЧто вытесняетКогда подходит
noevictionНичего: записи начинают падать с ошибкойRedis хранит данные, которые нельзя терять (локи, счётчики, очереди)
allkeys-lruЛюбой ключ, реже всех использованныйЧистый кэш: всё содержимое восстановимо
allkeys-randomСлучайный ключКэш с равномерным доступом
volatile-lru / volatile-ttlТолько ключи с TTL — по давности или по остатку времениСмешанный Redis: кэш с TTL и вечные данные рядом

Значения по умолчанию (проверено):

# CONFIG GET <параметр> — прочитать настройку работающего сервера
#   maxmemory — сколько памяти разрешено данным; 0 = лимита нет
redis-cli config get maxmemory
maxmemory                    # ← сначала печатается имя параметра
0                            # ← затем значение (в байтах; 0 = без лимита)
#   maxmemory-policy — что делать, когда лимит достигнут:
#   noeviction = ничего не удалять, а отклонять записи с ошибкой
redis-cli config get maxmemory-policy
maxmemory-policy
noeviction

То есть «из коробки» Redis не вытесняет ничего: он просто отказывается писать, когда память кончилась. Для кэша это почти всегда неправильная настройка.

Как выглядит вытеснение на практике

Ограничим память 4 МБ и включим allkeys-lru, затем запишем 20 000 ключей по 200 байт (проверено):

# CONFIG SET — меняет настройку «на живом» сервере, без перезапуска
#   (в конфиг-файл это не пишется: после рестарта вернутся прежние значения)
redis-cli config set maxmemory 4mb                # лимит данных — 4 МБ
redis-cli config set maxmemory-policy allkeys-lru # при переполнении вытеснять любые ключи по LRU

# 20 000 команд SET разом через pipe: каждая строка sets.txt — это "SET key value".
# pipe = конвейер: клиент не ждёт ответа на каждую команду, поэтому в разы быстрее цикла
redis-cli --pipe < sets.txt
# All data transferred. Waiting for the last reply...
# Last reply received from server.
# errors: 0, replies: 20000       ← 20 000 команд принято, ни одной ошибки

# INFO memory — сколько занято и какая политика действует прямо сейчас
redis-cli info memory | grep -E 'used_memory_human|maxmemory_policy'
# used_memory_human:4.00M         ← упёрлись в лимит
# maxmemory_policy:allkeys-lru

# INFO stats → evicted_keys: сколько ключей сервер вытеснил сам, без наших команд
redis-cli info stats | grep evicted_keys
# evicted_keys:10536

# DBSIZE — сколько ключей осталось в базе: 20 000 − 10 536 = 9 464
redis-cli dbsize
# 9464

Из 20 000 записанных ключей в памяти осталось 9 464, а 10 536 были вытеснены — и ни одна команда не вернула ошибку. Именно этого и ждут от кэша: память ограничена, старые ключи уходят, приложение работает.

Обратная сторона: noeviction поверх лимита

С той же памятью, но с политикой noeviction, запись падает:

# noeviction: место кончилось, удалять нечего/нельзя — сервер отклоняет запись
redis-cli set probe:key value
(error) OOM command not allowed when used memory > 'maxmemory'.

Чтение при этом продолжает работать. Для кэша это означает, что приложение обязано переживать ошибки записи в Redis: не падать, а просто идти в базу.

Мониторинг: на что смотреть

INFO — команда, которая возвращает снимок состояния сервера: пары «поле: значение». Без аргумента печатает все разделы сразу, с аргументом — только один. Список разделов (реальный вывод на Redis 7.4):

redis-cli info | grep '^#'      # какие разделы вообще есть у этого сервера

redis-cli INFO MEMORY           # регистр не важен: INFO MEMORY = info memory
Где вводятся эти команды

В книге команды записаны коротко: redis-cli info memory. Это то, что набирают внутри контейнера с Redis (он запущен в главе 1 под именем redis7). Три равнозначных способа — все запускаются из обычного терминала на вашей машине:

# 1) одной строкой: redis-cli запускается внутри контейнера, вывод приходит в ваш терминал
docker exec redis7 redis-cli info memory

# 2) войти в оболочку redis-cli и вводить команды там — уже без «redis-cli» и без «docker»
docker exec -it redis7 redis-cli
127.0.0.1:6379> info memory     # приглашение «127.0.0.1:6379>» = вы внутри redis-cli
127.0.0.1:6379> quit              # выход

# 3) если redis-cli установлен на хосте, а порт опубликован (-p 6379:6379 из главы 1)
redis-cli -h localhost -p 6379 info memory

Для команд, читающих файл со stdin, контейнеру нужен флаг -i: docker exec -i redis7 redis-cli --pipe < sets.txt — так и снимались цифры про вытеснение выше. На сам вывод способ запуска не влияет: ниже он ровно такой, каким его печатает сервер.

Что считать нормальным mem_fragmentation_ratio

Сначала — что именно делится: mem_fragmentation_ratio = used_memory_rss / used_memory. Ответ «чем ближе к 1, тем лучше» верен, но бесполезен без второй половины: на маленькой базе метрика ничего не значит. Замеры на одном и том же сервере (Redis 7.4.12, jemalloc):

Состояние сервераused_memoryrss mem_fragmentation_ratio
только запущен, данных нет1.01M9.0M9.26
200 000 ключей по 100 байт (38 МБ данных)38.15M47.59M 1.25
сразу после удаления 190 000 ключей3.16M47.05M 15.07
те же данные через 30 секунд3.16M34.37M11.01
лимит 4 МБ, идёт вытеснение4.00M11.36M2.87

Отсюда правила:

  • Смотрите на базу нормального размера. 9.26 на пустом сервере — не фрагментация, а служебные аллокации процесса, которым не с чем сравниваться.
  • Ориентир для рабочей базы — примерно 1.0–1.5. 1.25 на 38 МБ данных — здоровое значение, и видно, из чего оно сложилось: allocator_frag_ratio:1.01 (аллокатор почти не теряет), allocator_rss_ratio:1.17, rss_overhead_ratio:1.04.
  • Больше 1.5 — разбираться, а не паниковать. Полезно понять, какой компонент виноват: allocator_frag_ratio — «мусор» внутри аллокатора, allocator_rss_ratio — аллокатор держит освобождённые страницы, rss_overhead_ratio — накладные расходы вне аллокатора (буферы, стек, сам процесс).
  • Меньше 1 — плохо. RSS меньше «используемой» памяти значит, что часть страниц ушла в swap: ответы начнут приходить за миллисекунды вместо микросекунд.
  • Один замер обманывает. Сразу после массового удаления ratio взлетает до 15.07, а через 30 секунд jemalloc возвращает часть страниц — уже 11.01 (rss 47.05M → 34.37M). Поэтому смотрят тренд и повторяют замер через полминуты, а не делают вывод по одной точке.

И важное: 11.01 и 2.87 в примерах — не «норма», а следствие того, что база после удаления стала крошечной (3–4 МБ), а процесс держит память, рассчитанную на 38 МБ. На реальной нагрузке держитесь диапазона 1.0–1.5 и реагируйте на устойчивый рост, а не на единичный всплеск.

Если фрагментация устойчивая: activedefrag

У Redis есть активная дефрагментация: она переносит данные внутри страниц аллокатора и отдаёт лишние страницы ОС. По умолчанию выключена, а пороги заданы так, чтобы не тратить CPU зря (значения из CONFIG GET 'active*' на 7.4.12):

ПараметрПо умолчаниюЧто означает
activedefragnoвключена ли дефрагментация
active-defrag-ignore-bytes104857600 (100 МБ) меньше этого объёма «мусора» не начинать вообще
active-defrag-threshold-lower10 начинать, когда фрагментация выше 10 %
active-defrag-threshold-upper100 работать на полную, когда выше 100 %
active-defrag-cycle-min / -max1 / 25 минимум и максимум CPU, который отдаётся дефрагментации, %
active-defrag-max-scan-fields1000 сколько полей большого ключа просматривать за один проход

Включение и проверка — реальный вывод:

redis-cli config set activedefrag yes
# OK
redis-cli info memory | grep -E 'active_defrag_running|mem_fragmentation_ratio'
# active_defrag_running:0
# mem_fragmentation_ratio:3.79
redis-cli info stats | grep -i defrag
# active_defrag_hits:0
# active_defrag_misses:0
# total_active_defrag_time:0        ← не работала ни секунды

Главное в этом выводе — не activedefrag yes, а счётчики. Включить флаг мало: дефрагментация начнётся, только когда фрагментированных байт больше active-defrag-ignore-bytes и отношение выше active-defrag-threshold-lower. Здесь «мусора» было ~9 МБ при пороге 100 МБ, поэтому active_defrag_running:0, а total_active_defrag_time:0 прямо говорит, что она не запускалась. Кстати, падение ratio 15.30 → 3.79 в этом прогоне произошло не из-за дефрагментации (её счётчики нулевые), а потому что jemalloc сам вернул часть страниц через несколько секунд.

Проверять работу дефрагментации нужно именно по active_defrag_hits и total_active_defrag_time: если они растут, а ratio падает — она делает своё дело. Если ratio высокий, а счётчики стоят, — смотрите пороги (или фрагментация не там, где вы думаете).

Доля попаданий: что считать хорошей

Сначала — как считается и что именно двигает счётчики (проверено на пустой базе, по одному вызову):

Что выполнилиkeyspace_hitskeyspace_misses
MSET k1 v1 k2 v2не меняетсяне меняется
GET k1 (ключ есть)+1—
GET nope (ключа нет)—+1
EXISTS k1 / EXISTS nope2+1+1
TTL k1 / TTL nope3+1+1

То есть счётчики двигают чтения по ключу (включая EXISTS и TTL), а записи — нет. Два реальных прогона с разным результатом:

# прогон 1: 90 чтений по существующим ключам + 10 по отсутствующим
docker exec -i ops sh -c 'redis-cli --pipe' < /tmp/gets1.txt     # 100 команд GET
docker exec ops redis-cli info stats | grep -E 'keyspace_(hits|misses)'
# keyspace_hits:90
# keyspace_misses:10              ← 90 / (90 + 10) = 90 %

# прогон 2: те же 100 чтений, но ключей нет вообще (после flushall)
# keyspace_hits:0
# keyspace_misses:100             ← 0 %

Универсальной нормы нет: доля попаданий зависит от того, повторяются ли чтения, насколько короткий TTL и хватает ли памяти. Рабочие ориентиры (это ориентиры, а не норматив):

  • Кэш справочных данных, который читают многократно (каталог, профили, настройки): обычно 90 % и выше. Прогон 1 — ровно этот случай.
  • Кэш ответов с коротким TTL (секунды): 60–80 % — нормально, часть ключей истекает между чтениями, и это не ошибка.
  • Поток уникальных чтений (каждый запрос — новый ключ): 0–20 %, и это сразу видно по второму прогону: кэш почти не помогает.

Если доля ниже ожидаемой, проверяйте по порядку:

  • evicted_keys — если он растёт, память выбрасывает ключи раньше TTL, и промахи «не ваша вина» (лечится maxmemory или политикой).
  • TTL против частоты чтений — при TTL 5 минут редко читаемый ключ истечёт между запросами (глава 3).
  • Негативный кэш — если приложение часто спрашивает то, чего нет (например, удалённые записи), эти обращения всегда будут misses; иногда их кэшируют пустым значением.
  • Инвалидацию — не сбрасываете ли ключ при каждой записи, хотя данные почти не меняются.

И главное: keyspace_hits/misses — глобальные счётчики по всем ключам сервера. Если в одном Redis лежит и «горячий» справочник, и редкие админские выборки, средняя доля будет отражать смесь и ничего не скажет про каждую задачу. Поэтому либо считайте дельту за окно (снимок до и после, CONFIG RESETSTAT — ниже), либо разводите разные задачи по разным базам/инстансам.

Накопительные счётчики против мгновенных значений

В Stats почти всё — счётчики за всё время с момента старта: они только растут. В Memory и Keyspace наоборот — текущее состояние. Поэтому два снимка одного сервера могут не сходиться, и это нормально: сразу после записи 20 000 ключей было evicted_keys:10536 и dbsize 9464, а через несколько наших экспериментов — уже evicted_keys:10853 и 9 148 ключей в базе: мы дописали ещё пару ключей, и вытеснение продолжилось.

# счётчики можно обнулить, не перезапуская сервер (например, чтобы мерить «с этого момента»)
redis-cli config resetstat
OK
redis-cli info stats | grep -E 'rejected_connections|total_commands_processed'
# rejected_connections:0        ← было 1 (эксперимент с maxclients — ниже)
# total_commands_processed:1    ← в счётчик попала только эта же команда INFO

3. INFO keyspace — сколько ключей и сколько из них с TTL

Что такое TTL, как он задаётся и почему перезапись ключа его сбрасывает — глава 3; здесь важно, что INFO keyspace показывает его последствия: сколько ключей со сроком и сколько им осталось.

docker exec redis7 redis-cli info keyspace
# Keyspace
db0:keys=9148,expires=1,avg_ttl=0,subexpiry=0

Одна строка на каждую непустую базу (db0…db15). Если база пуста, строки для неё нет — на пустом сервере вывод состоит из одного заголовка # Keyspace:

  • keys=9148 — сколько ключей в базе сейчас: 20 000 записанных − 10 853 вытесненных + 1 наш session:demo.
  • expires=1 — из них с TTL: только session:demo (остальные 20 000 писали без TTL, и политика allkeys-lru вытесняет в том числе вечные ключи).
  • avg_ttl=0 — средний остаток TTL по ключам с TTL, в миллисекундах. Ноль здесь не потому, что TTL нет (он есть — expires=1), а потому что снимок снят сразу после записи единственного TTL-ключа: значение считает цикл истечения, а не сама команда SET. Воспроизводится в три команды — flushall, set k v ex 600 и сразу info keyspace: время от времени видно avg_ttl=0, а через секунду уже avg_ttl=599900. Когда TTL-ключей много, значение стабильно: 200 ключей по EX 600 дают db0:keys=200,expires=200,avg_ttl=599819,subexpiry=0.
  • subexpiry=0 — сколько полей хешей имеют собственный TTL (команда HEXPIRE, новое в Redis 7.4). Это не то же самое, что expires: TTL поля не делает ключ истекающим. Ниже — как это получить руками, с разбором каждого аргумента.

Сначала — реальный вывод «до и после», потом разбор команд:

docker exec redis7 redis-cli hset h:1 name Алексей plan pro
# 2                                  ← HSET вернул число СОЗДАННЫХ полей
docker exec redis7 redis-cli info keyspace
# db0:keys=1,expires=0,avg_ttl=0,subexpiry=0

docker exec redis7 redis-cli hexpire h:1 100 fields 1 name
# 1                                  ← TTL получило одно поле
docker exec redis7 redis-cli info keyspace
# db0:keys=1,expires=0,avg_ttl=0,subexpiry=1   ← ключ по-прежнему без TTL, но у поля он есть

docker exec redis7 redis-cli hpttl h:1 fields 2 name plan
# 99878                              ← у поля name осталось ~100 секунд (в мс)
# -1                                 ← у поля plan TTL нет
docker exec redis7 redis-cli ttl h:1
# -1                                 ← у КЛЮЧА TTL нет: expires=0 это и означал

Разбор команды hexpire h:1 100 fields 1 name — аргументы по порядку:

АргументЧто значит
hexpireкоманда «поставить TTL полю хеша» (парная к hpttl)
h:1ключ-хеш, в котором лежат поля
100срок жизни поля в секундах; есть HPEXPIRE — то же в миллисекундах
FIELDS 1«дальше будет 1 поле» — можно перечислить несколько: FIELDS 2 name plan
nameимя поля, которому ставим срок

Аналогично hpttl h:1 fields 2 name plan: ключ h:1, FIELDS 2 — два поля, дальше сами поля; ответ — по одному числу на поле: миллисекунды до истечения, -1 («TTL у поля нет») или -2 («поля нет»).

TTL поля — исключение, а не правило

В INFO keyspace поле с TTL видно только в subexpiry, а keys, expires и avg_ttl не меняются: ключ целиком жив, пока живы его поля. Для кэша это значит, что обычная схема «один ключ — один TTL» предсказуемее: инвалидация и мониторинг у неё очевидны, а HEXPIRE стоит брать, когда срок действительно нужен отдельному полю (например, «код подтверждения в профиле»).

4. INFO clients — подключения и те, кто ждёт

docker exec redis7 redis-cli info clients
# Clients
connected_clients:1
cluster_connections:0
maxclients:10000
client_recent_max_input_buffer:0
client_recent_max_output_buffer:0
blocked_clients:0
tracking_clients:0
pubsub_clients:0
watching_clients:0
clients_in_timeout_table:0
total_watched_keys:0
total_blocking_keys:0
total_blocking_keys_on_nokey:0

Смысл полей: connected_clients:1 — прямо сейчас подключён один клиент (сам redis-cli; предыдущая команда уже отключилась). maxclients:10000 — лимит одновременных соединений. blocked_clients:0 — никто не висит в ожидании данных (BLPOP, BRPOP, XREAD BLOCK). Команда WAIT в этот счётчик не попадает — проверено: висящий wait 0 5000 даёт connected_clients:2 при blocked_clients:0, а xread block 5000 — blocked_clients:1. Вот как выглядит вывод, когда один клиент действительно ждёт (в соседнем терминале запущен blpop queue:jobs 0):

docker exec -d redis7 sh -c 'redis-cli blpop queue:jobs 0'   # клиент повис в ожидании элемента
docker exec redis7 redis-cli info clients | head -7
# Clients
connected_clients:2
cluster_connections:0
maxclients:10000
client_recent_max_input_buffer:20520
client_recent_max_output_buffer:0
blocked_clients:1

docker exec redis7 redis-cli client list
# id=41 addr=127.0.0.1:45930 ... flags=b ...     ← b = blocked, это наш BLPOP
# id=43 addr=127.0.0.1:45952 ... flags=N ...     ← N = normal, это сам client list

Растущий blocked_clients — сигнал, что потребители ждут, а producer не успевает; но помните, что в BLPOP висит и «нормальный» потребитель очереди, который просто ждёт работы.

Как своими руками получить ненулевой rejected_connections

Этот счётчик растёт, когда соединений больше, чем maxclients. Чтобы увидеть, а не поверить на слово, эксперимент делали на отдельном контейнере (порт 6380), чтобы не ломать основной: ставим лимит 1, занимаем его висящим BLPOP, затем пробуем подключиться ещё раз.

docker run -d --name redistest -p 6380:6379 redis:7-alpine   # отдельный сервер для опытов
docker exec redistest redis-cli config set maxclients 1
OK
docker exec -d redistest sh -c 'redis-cli blpop q 0'   # единственное разрешённое соединение занято
docker exec redistest redis-cli ping
ERR max number of clients reached                        # ← это и считает rejected_connections

# освободили место и посмотрели счётчик
docker exec redistest sh -c 'pkill -f "redis-cli blpop"'
docker exec redistest redis-cli config set maxclients 10000
OK
docker exec redistest redis-cli info stats | grep rejected_connections
rejected_connections:1

На проде то же самое выглядит как RedisConnectionException в .NET и всплеск rejected_connections: почти всегда это утечка соединений — например, ConnectionMultiplexer создаётся на каждый запрос вместо одного на процесс.

★ Четыре цифры, по которым видно здоровье Redis
  • Доля попаданий keyspace_hits / (hits + misses): в примере 64 %. Падает — кэш перестал помогать: мало памяти, короткий TTL или ключи не те, что читаются.
  • evicted_keys растёт — памяти не хватает на рабочий набор: либо больше памяти, либо меньше TTL и объём значений.
  • blocked_clients — сколько клиентов ждёт в блокирующих командах; устойчивый рост = потребители не успевают.
  • mem_fragmentation_ratio стабильно > 1.5 — фрагментация: помогает activedefrag yes или плановый перезапуск; < 1 — память ушла в swap, это хуже.

Персистентность: что теряется при перезапуске

У Redis два механизма, и по умолчанию включён только первый:

МеханизмЧто делаетПо умолчанию
RDBПериодический снимок всей базы в файл dump.rdb Включён: save 3600 1 300 100 60 10000 — снимок, если за 3600 с изменился хотя бы 1 ключ, за 300 с — 100, за 60 с — 10 000
AOFЖурнал команд, дописываемый на диск Выключен: appendonly no

Отсюда практическое следствие: при аварийном завершении процесса Redis теряет всё, что изменилось после последнего снимка или не успело попасть в AOF. Для кэша это нормально; для данных, которые «нельзя терять», — нет.

Как выбрать

Чистый кэш: персистентность можно отключить целиком — и RDB, и AOF; после перезапуска кэш прогреется сам, но всё, что в нём было, исчезнет. Очереди, локи, счётчики: включайте AOF (appendonly yes) — это единственный механизм, который переживает потерю последнего снимка. И в любом случае реплика — не бэкап.

Как посмотреть, что включено

Настройки — обычные параметры конфигурации, их видно теми же CONFIG GET:

docker exec redis7 redis-cli config get save

# 3600 1 300 100 60 10000        ← правило RDB: «за N секунд изменилось M ключей»
docker exec redis7 redis-cli config get appendonly

docker exec redis7 redis-cli config get appendfsync
# appendfsync

docker exec redis7 redis-cli config get dir
# dir
# /data                         ← куда пишутся файлы (в контейнере)
docker exec redis7 redis-cli config get dbfilename
# dbfilename
# dump.rdb
docker exec redis7 redis-cli config get appendfilename
# appendfilename

А состояние — в разделе Persistence у INFO. Вот реальный вывод (важные строки, остальные — про фоновые операции):

docker exec redis7 redis-cli info persistence

RDB: проверить, включить, отключить

Снимок можно сделать по требованию — это и есть «проверить, что RDB работает»:

docker exec redis7 redis-cli set rdb:probe 1
# OK
docker exec redis7 redis-cli info persistence | grep rdb_changes_since_last_save
# rdb_changes_since_last_save:4       ← четвёртое изменение ждёт снимка

docker exec redis7 redis-cli bgsave
# Background saving started           ← снимок в фоне (есть и SAVE — блокирующий, в проде не нужен)
docker exec redis7 redis-cli lastsave
# 1794916542                          ← unix-время последнего успешного снимка

sleep 2
docker exec redis7 redis-cli info persistence | grep -E 'rdb_changes_since_last_save|rdb_last_bgsave_status'
# rdb_changes_since_last_save:0       ← всё попало в dump.rdb
# rdb_last_bgsave_status:ok

docker exec redis7 ls -l /data
# total 4
# -rw-------    1 redis    redis       99 Nov 17 12:22 dump.rdb   ← снимок на месте

Отключить RDB — значит убрать все правила save; пустая строка означает «никогда»:

docker exec redis7 redis-cli config set save ""
# OK
docker exec redis7 redis-cli config get save
# save
#                               ← пусто: автоснимков больше не будет; BGSAVE по команде всё ещё работает
docker exec redis7 redis-cli config rewrite
# ERR The server is running without a config file
# ↑ важный момент: CONFIG SET меняет только память процесса, на диск его кладёт CONFIG REWRITE,
#   а для этого сервер должен быть запущен с файлом конфигурации

Вывод из последней ошибки — практический: CONFIG SET живёт до перезапуска. У контейнера из главы 1 конфигурационного файла нет (процесс запущен без аргументов), поэтому «навсегда» настройка задаётся либо в файле redis.conf (и монтируется в контейнер), либо аргументами запуска. Отключить RDB на старте:

docker run -d --name cache -p 6379:6379 redis:7-alpine redis-server --save "" --appendonly no
docker exec cache redis-cli config get save
# save
#                               ← автоснимков нет
docker exec cache redis-cli config get appendonly
# appendonly
# no

В файле redis.conf те же две строки выглядят так: save "" и appendonly no.

AOF: включить, проверить, отключить

Включение — одна команда. В Redis 7 журнал лежит не одним файлом, а каталогом appendonlydir:

docker exec redis7 redis-cli config set appendonly yes
# OK
docker exec redis7 redis-cli info persistence | grep -E 'aof_(enabled|rewrites|current_size|last_write_status|last_bgrewrite_status)'
# aof_enabled:1
# aof_rewrites:1                    ← при включении сразу сделана первичная перезапись
# aof_current_size:154              ← журнал уже пишется
# aof_last_write_status:ok
# aof_last_bgrewrite_status:ok

docker exec redis7 ls -l /data
# drwx------    2 redis    redis          100 Nov 17 11:56 appendonlydir
# -rw-------    1 redis    redis          173 Nov 17 11:55 dump.rdb

docker exec redis7 redis-cli bgrewriteaof
# ERR Background append only file rewriting already in progress
# ↑ если перезапись уже идёт, ответ именно такой — это не поломка

Как часто журнал сбрасывается на диск, задаёт appendfsync:

appendfsyncКогда вызывается fsyncСколько можно потерять
alwaysпосле каждой записипочти ничего, но каждая команда ждёт диск — медленно
everysec (по умолчанию)раз в секундудо ~1 секунды записей
noкогда решит ОСбольше секунды, объём непредсказуем

Отключить — config set appendonly no (и, как и с RDB, это будет действовать до перезапуска; постоянно — appendonly no в конфиге или --appendonly no в аргументах).

Проверка «на живом»: CONFIG SET не переживает рестарт

Реальный эксперимент: включили AOF, записали ключ, перезапустили контейнер. Ключ из снимка остался, ключ, попавший только в AOF, — исчез:

docker exec redis7 redis-cli set aof:probe 1
# OK
docker restart redis7
docker exec redis7 redis-cli mget rdb:probe aof:probe
# 1                                 ← rdb:probe был в последнем снимке
#                                   ← aof:probe нет: AOF после рестарта выключен
docker exec redis7 redis-cli config get appendonly
# appendonly
# no                                ← снова значение по умолчанию
docker exec redis7 redis-cli info persistence | grep aof_enabled
# aof_enabled:0                     ← файл AOF на диске остался, но его не читают

Чтобы AOF работал по-настоящему, его включают при запуске:

docker run -d --name redis-aof -p 6380:6379 redis:7-alpine redis-server --appendonly yes
docker exec redis-aof redis-cli set aof:keep 42
docker exec redis-aof redis-cli info persistence | grep -E 'aof_enabled|aof_current_size'
# aof_enabled:1
# aof_current_size:58
docker restart redis-aof
docker exec redis-aof redis-cli get aof:keep
# 42                                ← значение восстановлено из AOF

Что теряется при разных настройках

RDBAOFЧто на дискеЧто можно потерять
включён (по умолчанию)выключенdump.rdb по правилам saveвсё после последнего снимка: при активной записи — до минуты, при редкой — до часа (первое правило — 3600 с)
выключенвыключенничеговсё: после перезапуска база пустая

Отсюда практическое правило: «отключить персистентность» = выключить оба механизма (save "" и appendonly no). Если выключить только AOF, RDB продолжит снимать базу по расписанию — данные будут не «навсегда», но всё равно частично переживут перезапуск.

Отказоустойчивость: Sentinel и Cluster

Один Redis — это одна точка отказа: упал процесс или машина, и кэш исчез (а вместе с ним, возможно, локи и счётчики). Два способа это пережить:

  • Репликация + Sentinel. Есть мастер и реплики; Sentinel следит за мастером и при падении повышает одну из реплик, а клиент получает новый адрес мастера. Данные при этом могут потеряться: репликация асинхронная.
  • Redis Cluster. Данные шардируются между мастерами (у каждого свои реплики), клиент сам находит узел по ключу. Это про горизонтальный масштаб, а не только про отказ: один узел больше не обязан держать весь объём.

Репликация: как проверить, что она работает

Реплика — это обычный Redis, запущенный с указанием мастера. Проверка — тот же INFO replication на обеих сторонах:

# на мастере
docker exec m1 redis-cli info replication | grep -E '^role|connected_slaves'
# role:master
# connected_slaves:1                  ← реплика подключена

# на реплике
docker exec r1 redis-cli info replication | grep -E '^role|master_host|master_link_status'
# role:slave
# master_host:m1
# master_link_status:up               ← данные синхронизированы

# реплика только для чтения: запись в неё — ошибка
docker exec r1 redis-cli set x 1
# READONLY You can't write against a read only replica.

Sentinel: как запустить и проверить переключение

Sentinel — отдельный процесс, который читает свой конфиг. Минимальный файл для одного мастера и одной реплики:

port 26379
sentinel monitor mymaster 172.18.0.2 6379 1     # имя, адрес мастера, порт, кворум
sentinel down-after-milliseconds mymaster 3000  # сколько молчания считать падением
sentinel failover-timeout mymaster 10000
sentinel parallel-syncs mymaster 1

Запуск в Docker и проверка — реальные команды и вывод:

# мастер и реплика в одной сети
docker network create sentnet
docker run -d --name m1 --network sentnet redis:7-alpine
MIP=$(docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' m1)
echo $MIP                             # 172.18.0.2 — этот адрес идёт в конфиг Sentinel
docker run -d --name r1 --network sentnet redis:7-alpine redis-server --replicaof $MIP 6379

# sentinel: конфиг создаём внутри контейнера и запускаем его с флагом --sentinel
docker run -d --name s1 --network sentnet --user root redis:7-alpine sh -c \
  "printf 'port 26379\n\
sentinel monitor mymaster $MIP 6379 1\n\
sentinel down-after-milliseconds mymaster 3000\n\
sentinel failover-timeout mymaster 10000\n' > /tmp/sentinel.conf; exec redis-server /tmp/sentinel.conf --sentinel"

docker exec s1 redis-cli -p 26379 sentinel get-master-addr-by-name mymaster
# 172.18.0.2
# 6379                               ← кто сейчас мастер, по мнению Sentinel
docker exec s1 redis-cli -p 26379 sentinel master mymaster | grep -A1 -E '^(flags|num-slaves|quorum)$'
# flags
# master
# num-slaves
# 1
# quorum
# 1

Теперь проверка самого главного — переключения. Останавливаем мастер и опрашиваем Sentinel раз в секунду:

docker stop m1
# t=1s -> 172.18.0.2      ← Sentinel ещё считает мастером старый адрес
# t=2s -> 172.18.0.2
# t=3s -> 172.18.0.2
# t=4s -> 172.18.0.3      ← повышенная реплика: новый мастер

docker exec r1 redis-cli info replication | grep '^role'
# role:master

# вернули старый мастер — Sentinel переводит его в реплики нового
docker start m1
docker exec m1 redis-cli info replication | grep -E '^role|master_host|master_link_status'
# role:slave
# master_host:172.18.0.3
# master_link_status:up
Две ловушки Sentinel, на которые легко наступить

Имена вместо адресов. По умолчанию Sentinel не разрешает hostname в конфиге: строка sentinel monitor mymaster m1 6379 1 даёт при старте Failed to resolve hostname 'm1'. Нужна настройка sentinel resolve-hostnames yes (тогда в get-master-addr-by-name вернётся IP, а не имя).

Кворум и количество Sentinel. В примере один Sentinel и кворум 1 — этого достаточно для демонстрации, но не для прода: при одном Sentinel его падение оставляет кластер без арбитра. В проде поднимают три и более Sentinel на разных машинах.

Cluster: как запустить и проверить

Cluster — это режим самого Redis (--cluster-enabled yes), а не отдельный процесс. Для проверки хватит трёх мастеров; в одном контейнере их удобно поднять на портах 7000–7002:

docker run -d --name cl1 -p 7000-7002:7000-7002 redis:7-alpine sh -c \
  'for p in 7000 7001 7002; do
     redis-server --port $p --cluster-enabled yes --cluster-config-file nodes-$p.conf \
                  --cluster-node-timeout 5000 --save "" --appendonly no --daemonize yes
   done; sleep infinity'

# создаём кластер: три мастера, без реплик (--cluster-replicas 0)
docker exec cl1 redis-cli --cluster create 127.0.0.1:7000 127.0.0.1:7001 127.0.0.1:7002 \
  --cluster-replicas 0 --cluster-yes
# M: f86d96… 127.0.0.1:7000   slots:[0-5460] (5461 slots) master
# M: 069175… 127.0.0.1:7001   slots:[5461-10922] (5462 slots) master
# M: 23786e… 127.0.0.1:7002   slots:[10923-16383] (5461 slots) master
# [OK] All 16384 slots covered.      ← идентификаторы узлов сокращены

Проверка состояния и того, как клиент находит ключ:

docker exec cl1 redis-cli -p 7000 cluster info | head -7
# cluster_state:ok
# cluster_slots_assigned:16384
# cluster_slots_ok:16384
# cluster_slots_pfail:0
# cluster_slots_fail:0
# cluster_known_nodes:3
# cluster_size:3

docker exec cl1 redis-cli -p 7000 cluster keyslot foo
# 12182                              ← слот, в который попадает ключ

# без -c клиент переадресацию не выполняет, а сообщает, куда идти
docker exec cl1 redis-cli -p 7000 set foo bar
# MOVED 12182 127.0.0.1:7002
# с -c redis-cli сам переходит на нужный узел
docker exec cl1 redis-cli -c -p 7000 set foo bar
# OK
docker exec cl1 redis-cli -c -p 7001 get foo
# bar

Ключи одной сущности в Cluster должны попадать в один слот, иначе многошаговые команды падают. Проверено:

docker exec cl1 redis-cli -c -p 7000 mget user1:a user1:b
# CROSSSLOT Keys in request don't hash to the same slot

docker exec cl1 redis-cli -p 7000 cluster keyslot user1:a     # 1888
docker exec cl1 redis-cli -p 7000 cluster keyslot user1:b     # 14083   ← разные слоты

# хеш-тег в фигурных скобках: слот считается по содержимому скобок
docker exec cl1 redis-cli -p 7000 cluster keyslot '{user1}:a' # 8106
docker exec cl1 redis-cli -p 7000 cluster keyslot '{user1}:b' # 8106    ← один слот
docker exec cl1 redis-cli -c -p 7000 mget '{user1}:a' '{user1}:b'
# 1
# 2

Для приложения главное правило не меняется: потеря Redis не должна быть потерей данных. Если после падения кэша сервис не поднимается — значит, в Redis лежит то, что там лежать не должно.

Типичные ошибки эксплуатации
  • maxmemory = 0 в контейнере с лимитом памяти. Redis считает, что памяти сколько угодно, и его убивает OOM-killer — без предупреждения и без вытеснения.
  • Политика noeviction для кэша. Вместо вытеснения старых ключей записи начинают падать с OOM command not allowed….
  • KEYS * в проде. Одна такая команда блокирует сервер на всё время перебора.
  • Один Redis на кэш, локи, счётчики и очереди. Вытеснение из-под кэша начнёт выбрасывать локи и счётчики. Разные задачи — разные базы или разные инстансы.
  • Нет таймаутов. Клиент без connectTimeout/syncTimeout при проблеме с сетью вешает запросы приложения.
★ Что запомнить из главы
  • Всегда задавайте maxmemory и политику: по умолчанию Redis ничего не вытесняет и падает на записи.
  • Для кэша — allkeys-lru (или volatile-*, если рядом лежат вечные ключи); для данных «нельзя терять» — noeviction плюс персистентность.
  • RDB включён, AOF выключен — значит, свежие записи теряются при аварии; для очередей и счётчиков включайте AOF.
  • mem_fragmentation_ratio смотрят на базе нормального размера: ориентир 1.0–1.5, меньше 1 — swap, больше 1.5 — разбираться по компонентам (allocator_frag_ratio, allocator_rss_ratio, rss_overhead_ratio); один замер после массового удаления обманывает.
  • Доля попаданий — не норматив, а зависимость от нагрузки: справочник с повторными чтениями — 90 %+, короткий TTL — 60–80 %, поток уникальных ключей — 0–20 %. Счётчик глобальный и двигают его чтения, а не записи.
  • Проверяйте персистентность командами: CONFIG GET save, CONFIG GET appendonly, INFO persistence, BGSAVE + LASTSAVE. «Отключить персистентность» = save "" и appendonly no; CONFIG SET живёт до перезапуска.
  • Sentinel и Cluster проверяются теми же командами, что у клиента: sentinel get-master-addr-by-name до и после падения мастера, cluster info, cluster keyslot и ответ MOVED — по ним видно, что отказоустойчивость и шардирование действительно работают.
  • Смотрите keyspace_hits/misses и evicted_keys, а не только «жив ли процесс»: низкая доля попаданий при растущем evicted_keys означает, что памяти не хватает рабочему набору.
  • Репликация и Cluster — про доступность и объём, а не про сохранность данных: истина должна оставаться в PostgreSQL.
