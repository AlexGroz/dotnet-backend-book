Глава 17. Конфигурация и опции

Что такое настройки, где они физически лежат, почему одно и то же значение задают в нескольких местах — и как прочитать его в коде одним классом.

Зачем нужны настройки

Настройка — это значение, которое отличается от запуска к запуску, но не должно быть зашито в код:

  • адрес базы данных: локально localhost, в проде — отдельный сервер;
  • сколько заказов показывать на одной странице списка;
  • логин и адрес SMTP для писем;
  • подробный лог включать или нет.

Код у приложения один, а запусков много: ваш ноутбук, машина коллеги, тестовый стенд, прод. Если адрес базы написать прямо в коде, под каждый стенд придётся собирать отдельную сборку. Поэтому значения выносят наружу — в файлы и переменные окружения, — а приложение читает их при старте.

Всю главу будем смотреть на одном значении — Orders:PageSize, «сколько заказов отдавать на одной странице списка». Клиент дёргает GET /orders?page=2, сервер смотрит в настройки и возвращает столько заказов. На работу приложения это влияет напрямую (реальный запуск, в базе 120 заказов):

всего заказов 120, на страницу 20 → страниц 6
всего заказов 120, на страницу 50 → страниц 3

Локально удобно 20: страница меньше, тесты быстрее. В проде удобно 50: меньше запросов к базе. Приложение одно и то же — значение разное. Дальше вся глава про то, как задать это значение снаружи и как приложение выбирает, какое из заданных взять.

Настройка и секрет — не одно и то же

PageSize спокойно лежит в git: это не тайна. А строку подключения с паролем или ключ платёжного API в репозиторий класть нельзя — про них отдельный раздел в конце главы.

Ключ, значение и стопка источников

Любая настройка — это пара «ключ → значение». Ключ — обычная строка, а двоеточие в ней означает вложенность: запись в JSON "Orders": { "PageSize": 50 } — это ключ Orders:PageSize со значением 50.

Один и тот же ключ можно задать в нескольких местах. Приложение складывает их стопкой, снизу вверх:

  1. appsettings.json — базовые значения, одинаковые для всех;
  2. appsettings.{Окружение}.json — то, что отличается на конкретном стенде;
  3. секреты разработчика (dotnet user-secrets) — только на локальной машине;
  4. переменные окружения — ими настройки задают в контейнере и на сервере;
  5. аргументы командной строки — то, что передали в момент запуска.

Если ключ есть в нескольких слоях, побеждает последний — самый «близкий» к запуску. Верхний слой перекрывает нижние, как правки поверх черновика: читается не всё сразу, а верхняя запись.

appsettings.json              Orders:PageSize = 50    ← база
appsettings.Development.json  Orders:PageSize = 20    ← перекрыл базу
переменные окружения          Orders:PageSize = 100   ← перекрыли файлы
аргументы командной строки    Orders:PageSize = 7     ← перекрыл всё

итог: приложение видит 7, остальные значения «не существуют»
Это один ключ, а не разные настройки

Самая частая путаница: кажется, что Orders:PageSize в файле и Orders__PageSize в переменной окружения — два разных значения, между которыми надо выбирать. Нет: это один ключ, заданный в двух местах. Приложение видит ровно одно значение — из победившего слоя.

И само слово PageSize к порядку источников отношения не имеет: это просто число, на котором удобно показывать, чьё значение победило. Дальше мы будем менять одно и то же число из разных мест и смотреть, какое останется.

Почему не взять значение просто из appsettings.json

Взять можно — приложение так и делает: базовый файл читают всегда. Мешает другое: базовое значение одно на все стенды. Локально нужна своя база и маленькая страница, в проде — своя база и большая. Поэтому в базовом файле держат общее, а отличия кладут слоями выше. Источников несколько не для того, чтобы «выбрать один правильный», а чтобы наложить отличия на общее.

ASPNETCORE_ENVIRONMENT — не второй источник значений, а имя набора отличий: Development → appsettings.Development.json, Production → appsettings.Production.json. Нет такого файла — останется только база.

Где эти настройки лежат

В файлах проекта. Ниже — полное содержимое демо-проекта, на котором получены все числа этой главы; ничего скрытого в нём нет.

appsettings.json — базовые значения, лежит в корне проекта:

{
  "Logging": { "LogLevel": { "Default": "Warning" } },
  "ConnectionStrings": { "Default": "Host=prod-db;Database=shop" },
  "Orders": { "PageSize": 50 }
}

appsettings.Development.json — только отличия локальной машины, и только те, которые действительно отличаются:

{
  "Logging": { "LogLevel": { "Default": "Information" } },
  "ConnectionStrings": { "Default": "Host=localhost;Database=shop" },
  "Orders": { "PageSize": 20 }
}

Properties/launchSettings.json — профиль запуска (показан сокращённо, остальное — адрес и флаги отладки). Создаёт его dotnet new web, а значения отсюда применяются только при dotnet run:

{
  "profiles": {
    "http": {
      "commandName": "Project",
      "applicationUrl": "http://localhost:5104",
      "environmentVariables": { "ASPNETCORE_ENVIRONMENT": "Development" }
    }
  }
}

Обратите внимание: в файлах записаны только 50 и 20. Значения 100 и 7 в файлах не лежат — их задают в момент запуска. Все четыре числа этой главы:

СлойГде лежит значениеPageSize
базовый файлappsettings.json50
файл окруженияappsettings.Development.json20
переменная окруженияOrders__PageSize=100 перед командой запуска 100
аргумент командной строки--Orders:PageSize=7 после -- 7

Файлы читаются из ContentRootPath — каталога, из которого запущено приложение. При dotnet run это каталог проекта, а рядом с dll лежит лишь копия (реальный вывод):

окружение       : Development
ContentRootPath : /tmp/shop
BaseDirectory   : /tmp/shop/bin/Debug/net8.0/

Поэтому правка appsettings.json в проекте действует сразу, без пересборки: читается именно она, а не копия в bin. Но стоит запустить dll из папки сборки — и картина меняется:

$ cd bin/Debug/net8.0 && dotnet shop.dll
окружение       : Production
ContentRootPath : /tmp/shop/bin/Debug/net8.0
BaseDirectory   : /tmp/shop/bin/Debug/net8.0

Теперь читаются копии json, и правки в исходниках ни на что не влияют. Это не баг, а норма: у опубликованного приложения настройки лежат рядом с dll. Но именно на этом ломаются ожидания «я поменял настройку, а ничего не изменилось».

Файла окружения может не быть

Хост подключает appsettings.{Окружение}.json с optional: true. Файла appsettings.Production.json в проекте нет — приложение всё равно стартует и берёт значения из базового файла (PageSize = 50). Заводить отдельный файл под каждое окружение не обязательно.

Пять запусков: кто побеждает

Один проект, один и тот же код — меняется только способ задать значение. Вот что получилось на самом деле:

Что запустилиОкружениеPageSizeПочему
dotnet runDevelopment20файл окружения перекрыл базовый
dotnet run --no-launch-profileProduction50файла Production нет, остался базовый
Orders__PageSize=100 dotnet runDevelopment100 переменная окружения перекрыла файлы
dotnet run -- --Orders:PageSize=7Development7 аргумент перекрыл всё
cd bin/Debug/net8.0 && dotnet shop.dllProduction50 читается копия json из папки сборки

Две строки в таблице выглядят непривычно, разберём их синтаксис:

  • Orders__PageSize=100 dotnet run — в bash переменная окружения задаётся перед командой и действует только для неё;
  • dotnet run -- --Orders:PageSize=7 — всё, что после --, уходит не в dotnet run, а в само приложение (те самые аргументы args из Program.cs).

Почему побеждает именно этот слой — видно в самом объекте конфигурации: он хранит список своих источников. Реальный вывод для обычного dotnet run:

источники (в порядке применения, побеждает последний):
  1) MemoryConfigurationSource
  2) EnvironmentVariablesConfigurationSource  только с префиксом ASPNETCORE_
  3) MemoryConfigurationSource
  4) EnvironmentVariablesConfigurationSource  только с префиксом DOTNET_
  5) JsonConfigurationSource                  appsettings.json
  6) JsonConfigurationSource                  appsettings.Development.json
  7) JsonConfigurationSource                  secrets.json
  8) EnvironmentVariablesConfigurationSource  все переменные окружения
  9) ChainedConfigurationSource

Список читается снизу вверх: побеждает последний. И тут же ответ на вопрос «откуда приложение знает, какой файл окружения брать»:

  • №2 читает переменные с префиксом ASPNETCORE_, №4 — с префиксом DOTNET_. Это происходит до чтения файлов: к моменту №6 хост уже знает имя окружения, поэтому подключает именно appsettings.Development.json;
  • №5–7 — файлы: базовый, файл окружения и secrets.json из user-secrets (он лежит не в проекте, а в профиле пользователя);
  • №8 — все переменные окружения: самый сильный из обычных слоёв;
  • в запуске с аргументами появляются ещё два источника CommandLineConfigurationSource — поэтому аргумент перекрывает вообще всё.
ASPNETCORE_ENVIRONMENT — не источник настроек

Это имя окружения, то есть переключатель, какой файл читать: Development → appsettings.Development.json, Production → appsettings.Production.json. Никаких значений настроек в ней нет — только выбор файла.

Проверено: команда ASPNETCORE_ENVIRONMENT=Production dotnet run всё равно даёт Development и PageSize = 20. Причина — профиль в launchSettings.json: он задаёт свою переменную окружения, и его значение побеждает. Чтобы переключить окружение при dotnet run, нужен --no-launch-profile (или правка профиля). У опубликованного приложения профилей нет — там переменная работает напрямую.

Как записать один и тот же ключ

Ключ один, а синтаксис у источников разный:

ИсточникКак задать Orders:PageSize
appsettings.json"Orders": { "PageSize": 50 }
appsettings.Development.jsonто же самое; перекрывает базовый файл
переменные окруженияOrders__PageSize=100 — двойное подчёркивание вместо двоеточия
аргументы командной строки--Orders:PageSize=7 (годится и --Orders:PageSize 7)
launchSettings.json"environmentVariables": { "Orders__PageSize": "100" } — проверено, даёт 100
user-secretsdotnet user-secrets set "Orders:PageSize" "50"

Правило простое: в JSON — двоеточие, в переменных окружения — двойное подчёркивание (одинарное занято: оно отделяет имя переменной от её значения), в аргументах — как в JSON.

Внутри — плоский список ключей

Хотя в JSON настройки выглядят деревом, внутри IConfiguration — плоский набор пар «ключ → строка». Вложенность превращается в префикс ключа. Реальный вывод перебора всех ключей (в нём есть Orders:Secret — его мы положили через user-secrets, раздел в конце главы):

'ConnectionStrings' = ''
'ConnectionStrings:Default' = 'Host=localhost;Database=shop'
'Orders' = ''
'Orders:PageSize' = '20'
'Orders:Secret' = 's3cr3t'

Массивы станут ключами с индексами: Orders:Items:0:Name, Orders:Items:1:Name. А GetSection("Orders") ничего не вырезает и не копирует: он возвращает вид на этот же список с приписанным префиксом. Поэтому значения «одной секции» спокойно приходят из разных слоёв: PageSize из файла, Secret из user-secrets — для кода это одна секция Orders.

Два следствия, на которых легко попасться:

  • у самой секции Value равно null — потому что у неё есть дети. Чтение cfg.GetSection("Orders").Value даёт null, а не текст секции;
  • имя секции — просто строка в вашем коде. Опечатка не падает: GetSection("Orderss").Exists() возвращает false, детей ноль, класс остаётся с дефолтными значениями. Проверено запуском: приложение стартовало, PageSize = 50 из инициализатора, строка подключения пустая.

Читаем настройки в коде

Читать Configuration["Orders:PageSize"] по всему коду — плохо: ключ приходится писать руками в каждом месте, значение всегда строка, а опечатка видна только в рантайме. Правильный способ — один раз привязать секцию к классу и дальше работать с типизированным объектом:

// using System.ComponentModel.DataAnnotations;

public sealed class OrderOptions
{
    [Range(1, 200)]                            // проверка — атрибутом
    public int PageSize { get; init; } = 50;
}

builder.Services
    .AddOptions<OrderOptions>()                        // 1) объявить опции класса
    .Bind(builder.Configuration.GetSection("Orders"))   // 2) секция → свойства
    .ValidateDataAnnotations()                          // 3) проверять атрибуты
    .ValidateOnStart();                                 // 4) проверять на старте

Что делает каждая строка:

  • AddOptions<OrderOptions>() — включает привязку для этого класса и регистрирует в контейнере IOptions<OrderOptions>, IOptionsSnapshot, IOptionsMonitor и фабрику;
  • Bind(section) — говорит: «заполни свойства этого класса из секции Orders». Это единственное место, где вообще упоминается имя секции;
  • ValidateDataAnnotations() — проверяет атрибуты [Range], [Required]. Если атрибутов нет, проверять нечего: класс без атрибутов проходит валидацию молча, даже когда секции не существует;
  • ValidateOnStart() — выполняет проверку при старте, а не при первом обращении.
init и Bind — совместимы, а лямбда — нет

Bind пишет в свойства через скомпилированные сеттеры, поэтому init-свойства он заполняет нормально. А вот Configure(o => o.PageSize = 1) с init-свойством не скомпилируется:

error CS8852: Init-only property or indexer 'OrderOptions.PageSize' can only be assigned in an object
initializer, or on 'this' or 'base' in an instance constructor or an 'init' accessor.

Если нужна настройка кодом — либо set вместо init, либо .Configure<IConfiguration>((o, cfg) => cfg.GetSection("Orders").Bind(o)).

Зачем ValidateOnStart()

Возьмём заведомо плохое значение: Orders:PageSize = 5000 при [Range(1, 200)]. С ValidateOnStart() приложение не стартует и прямо говорит, что не так:

Microsoft.Extensions.Options.OptionsValidationException: DataAnnotation validation failed for
'OrderOptions' members: 'PageSize' with the error: 'The field PageSize must be between 1 and 200.'.

Без этой строки приложение стартует нормально и падает позже — на первом обращении к options.Value, то есть уже внутри запроса (тот же класс, то же значение):

Application started. Press Ctrl+C to shut down.
--- приложение стартовало нормально
--- упало при ПЕРВОМ обращении к Value
тип: Microsoft.Extensions.Options.OptionsValidationException
DataAnnotation validation failed for 'OrderOptions' members: 'PageSize' with the error: ...
Ошибка конфигурации должна валить старт, а не запрос

Разница видна в проде. С ValidateOnStart() контейнер не поднимется, деплой откатится, и виноватой будет конфигурация. Без неё приложение «работает», а 500-е начинаются при первом заказе — и искать будут в сервисе заказов, а не в настройках.

Если атрибутов мало, есть Validate с предикатом и своим текстом ошибки (реальный вывод):

.Validate(o => o.PageSize > 0, "PageSize должен быть больше нуля")
Microsoft.Extensions.Options.OptionsValidationException: PageSize должен быть больше нуля

Сервис, который пользуется настройками

В коде настройки запрашивают не классом, а обёрткой IOptions<T>:

public sealed class OrderService(IOptions<OrderOptions> options)
{
    private readonly OrderOptions _opt = options.Value;   // ← здесь настройки «появляются»
    public int PageSize => _opt.PageSize;
}

Ни пути к файлу, ни ключей в сервисе нет — и это правильно: он просит готовый объект, а откуда тот взялся, решает Program.cs. Пошагово при запуске происходит вот что:

  1. контейнер создаёт OrderService и видит в его конструкторе IOptions<OrderOptions>;
  2. для него уже есть регистрация (её сделал AddOptions<OrderOptions>()), поэтому приходит объект-обёртка;
  3. строка options.Value запускает сборку: действие привязки читает секцию Orders из конфигурации, объект проверяется валидаторами и кэшируется.

Две вещи, которые легко забыть:

  • private readonly OrderOptions _opt = options.Value; — это снимок на момент создания сервиса. Для IOptions так и надо: значения всё равно не меняются. Но если вы рассчитываете на перезагрузку, нужен IOptionsMonitor и чтение CurrentValue при каждом обращении, а не поле;
  • OrderService тоже надо зарегистрировать (AddScoped<OrderService>()) — конструктор с IOptions сам его в контейнер не добавляет.

Вариант с перезагрузкой выглядит так:

public sealed class OrderService(IOptionsMonitor<OrderOptions> options)
{
    public int PageSize => options.CurrentValue.PageSize;   // читается при каждом обращении
}

builder.Services.AddScoped<OrderService>();

Что за этим стоит: цепочка до файла

Полезно один раз увидеть, что именно попадает в контейнер после цепочки AddOptions().Bind() (вывод по IServiceCollection):

IOptions`1                   UnnamedOptionsManager`1                    Singleton
IOptionsSnapshot`1           OptionsManager`1                           Scoped
IOptionsMonitor`1            OptionsMonitor`1                           Singleton
IOptionsFactory`1            OptionsFactory`1                           Transient
IOptionsMonitorCache`1       OptionsCache`1                             Singleton
IConfigureOptions`1          NamedConfigureFromConfigurationOptions`1  ← добавил .Bind(...)
IOptionsChangeTokenSource`1  ConfigurationChangeTokenSource`1          ← добавил .Bind(...)
IValidateOptions`1           DataAnnotationValidateOptions`1           ← добавил .ValidateDataAnnotations()

То есть .Bind() — не «чтение файла при старте», а регистрация действия настройки: IConfigureOptions<OrderOptions>, внутри которого лежит та самая секция и вызов Bind, плюс источник уведомлений IOptionsChangeTokenSource (он и делает возможной перезагрузку). Регистрирует источник именно Bind: после обычного Configure(o => ...) таких источников 0, после Bind(section) — 1 (проверено).

Дальше при первом обращении к options.Value происходит вот это:

options.Value                     IOptions<OrderOptions> → UnnamedOptionsManager
  └─ IOptionsFactory.Create("")   → OptionsFactory
       ├─ все IConfigureOptions    → NamedConfigureFromConfigurationOptions   читает секцию Orders
       ├─ все IValidateOptions     → DataAnnotationValidateOptions            проверяет атрибуты
       └─ готовый объект → IOptionsMonitorCache (OptionsCache)

Отсюда три следствия, которые и спрашивают на собеседовании:

  • настройки берутся из IConfiguration, которую захватил делегат привязки (builder.Configuration — живой объект, который сам следит за файлами), а не «из класса настроек»;
  • IOptions<T> существует для любого T: если вы забыли Bind, ошибки не будет — придёт объект с дефолтными значениями (проверено: PageSize = 50 из инициализатора);
  • объект собирается один раз и кэшируется: ReferenceEquals(opt.Value, opt.Value) даёт True (проверено). Поэтому «прочитать значение заново» через IOptions не получится — нужен другой интерфейс.
Почему так, а не «прочитать в конструкторе»

Сервис не знает ни про файлы, ни про переменные окружения. Он просит IOptions<OrderOptions> — и получает объект, собранный по правилам, которые описаны в одном месте, в Program.cs. Добавился источник, поменялась секция, пришла переменная окружения — сервис не меняется вообще.

Три интерфейса и их lifetimes

Опции читают одним из трёх интерфейсов. Различаются они жизненным циклом (глава 15) и тем, увидят ли они изменение файла:

ТипLifetimeКогда брать
IOptions<T>SingletonЗначения не меняются на ходу — обычный случай
IOptionsSnapshot<T>ScopedПеречитывать значения на каждый запрос
IOptionsMonitor<T>SingletonНужны уведомления об изменении настроек

Разница не теоретическая. Один запуск, в котором файл настроек меняют на ходу (PageSize: 20 → 99, файл подключён с reloadOnChange: true), а читают все три варианта. Реальный вывод:

до правки файла:  IOptions 20 | Snapshot 20 | Monitor 20
  [OnChange] новые настройки: 99
тот же scope:     IOptions 20 | Snapshot 20 | Monitor 99
новый scope:      IOptions 20 | Snapshot 99 | Monitor 99
  • IOptions — 20 навсегда: значение собрано при первом обращении и лежит в кэше;
  • IOptionsSnapshot — снимок на scope: внутри одного scope значение не меняется (20), в новом scope собирается заново (99);
  • IOptionsMonitor — CurrentValue всегда актуально, а OnChange сам сообщает об изменении.

Плата за scoped-природу IOptionsSnapshot: его нельзя запрашивать из корня контейнера (и держать в singleton-сервисе). Попытка заканчивается так — реальный текст:

InvalidOperationException: Cannot resolve scoped service
'Microsoft.Extensions.Options.IOptionsSnapshot`1[OrderOptions]' from root provider.

И ещё одно условие: перезагрузка работает, только если источник её поддерживает (AddJsonFile(..., reloadOnChange: true) — в веб-хосте так по умолчанию) и если Bind был вызван, потому что источник уведомлений регистрирует именно он.

Строки подключения и секреты

Строка подключения — такой же ключ, только с префиксом ConnectionStrings:, и для неё есть метод-сокращение:

var cs = builder.Configuration.GetConnectionString("Default");
// то же, что Configuration["ConnectionStrings:Default"]

В демо-проекте этот ключ задан дважды: в базовом файле стоит прод-база, а файл окружения перекрывает её локальной. Поэтому обычный dotnet run печатает (реальный вывод):

GetConnectionString(Default) = Host=localhost;Database=shop

В проде ту же строку задают переменной окружения ConnectionStrings__Default, и код не меняется (проверено):

$ ConnectionStrings__Default='Host=localhost;Database=shop_local' dotnet run
GetConnectionString(Default) = Host=localhost;Database=shop_local
Секреты — вне репозитория

Пароли и ключи не хранят в appsettings.json: файл лежит в git и уезжает в образ. Локально — dotnet user-secrets, в проде — переменные окружения или менеджер секретов.

dotnet user-secrets init
dotnet user-secrets set "Orders:Secret" "s3cr3t"

Ключи в user-secrets — те же, что в JSON. Значения хранятся не в проекте, а в профиле пользователя (~/.microsoft/usersecrets/<id>/secrets.json), поэтому в git они не попадают. Проверено: Orders:Secret = 's3cr3t' в Development и '' в Production — user-secrets подключаются только в Development, и в списке источников Production их нет.

★ Что запомнить
  • Настройка — пара «ключ → значение»; вложенность в JSON — это префикс ключа (Orders:PageSize), в переменных окружения — Orders__PageSize.
  • Источники складываются стопкой; ключ задан в нескольких — побеждает последний: файл окружения перекрывает базовый файл, user-secrets и переменные окружения — файлы, аргументы — всё.
  • ASPNETCORE_ENVIRONMENT — не настройка, а переключатель, какой файл окружения читать. При dotnet run её перекрывает профиль из launchSettings.json.
  • Файлы читаются из ContentRootPath: при dotnet run — из проекта, у опубликованного приложения — из папки рядом с dll.
  • В коде секцию один раз привязывают к классу (Bind), проверяют атрибутами и ValidateOnStart, а читают через IOptions / IOptionsSnapshot / IOptionsMonitor.
  • options.Value собирается один раз и кэшируется; перезагрузка — только через IOptionsMonitor (или snapshot на scope).
