Глава 17. Конфигурация и опции

Настройки приложения: откуда они берутся, как их читать и почему у «опций» тоже есть жизненные циклы.

Откуда берётся конфигурация

Хост собирает IConfiguration из нескольких источников (провайдеров). Источники применяются по порядку, и последний перекрывает предыдущие:

  1. appsettings.json — базовые значения;
  2. appsettings.{Environment}.json — переопределения для окружения (глава 16);
  3. секреты разработчика (dotnet user-secrets) — только в Development;
  4. переменные окружения — то, что задаётся в контейнере/на сервере;
  5. аргументы командной строки.

Это не схема из документации: источники можно перечислить в отладочном выводе. Для обычного веб-приложения их список такой (реальный запуск, у JSON-провайдеров видно, какой файл подключён):

1) MemoryConfigurationProvider                     ← то, что хост положил в память
2) EnvironmentVariablesConfigurationProvider        служебные источники хоста
3) MemoryConfigurationProvider
4) EnvironmentVariablesConfigurationProvider
5) JsonConfigurationProvider  <- appsettings.json
6) JsonConfigurationProvider  <- appsettings.Development.json
7) EnvironmentVariablesConfigurationProvider        ← все переменные окружения
8) ChainedConfigurationProvider

Читать этот список нужно снизу вверх: если ключ есть в нескольких источниках, побеждает последний. Проверяется это одним и тем же приложением — меняется только способ задать Orders:PageSize:

Что задалиКакИтоговый PageSize
только базовый файлappsettings.json50
файл окруженияappsettings.Development.json — обычный dotnet run20 (файл окружения перекрыл базовый)
переменная окруженияOrders__PageSize=100 dotnet run100 (перекрыла оба файла)
аргумент командной строкиdotnet run -- --Orders:PageSize=7 7 (перекрыл всё)
окружение ProductionASPNETCORE_ENVIRONMENT=Production, запуск app.dll50 — файл окружения не подключён

Отсюда рабочее правило: файл — значения по умолчанию, окружение — то, что меняется при деплое. Поэтому Orders:PageSize в контейнере задают переменной Orders__PageSize (двойное подчёркивание — это :), а не правкой файла в образе.

Последняя строка про окружение — про ASPNETCORE_ENVIRONMENT / DOTNET_ENVIRONMENT: от него зависит, какой файл appsettings.{Environment}.json будет подключён. При запуске через dotnet run переменную перебивает профиль из Properties/launchSettings.json — поэтому в примере запускается собранный app.dll.

Где эти настройки лежат

Секция, о которой спрашивают «откуда он её берёт», — это кусок JSON-файла в корне проекта по имени appsettings.json. Его подключает не «магия», а WebApplication.CreateBuilder(args): он добавляет appsettings.json и appsettings.{Environment}.json из каталога ContentRootPath.

appsettings.json — корень проекта

{
  "Logging": { "LogLevel": { "Default": "Warning" } },
  "Orders": {
    "PageSize": 50,
    "ConnectionString": "Host=prod-db;Database=shop"
  }
}

appsettings.Development.json — переопределяет только то, что указано

{
  "Orders": { "PageSize": 20 }
}

При сборке оба файла копируются в выходной каталог рядом с приложением, поэтому опубликованное приложение находит их без настроек:

bin/Debug/net8.0/appsettings.json
bin/Debug/net8.0/appsettings.Development.json
bin/Debug/net8.0/shop.dll

Но каталогов два, и путают их постоянно:

ЧтоГде этоИз него читаются файлы настроек?
builder.Environment.ContentRootPathкаталог проекта при dotnet run; каталог с dll у опубликованного приложенияда (appsettings*.json, wwwroot)
AppContext.BaseDirectorybin/Debug/net8.0/нет — здесь лежит только копия для публикации

Именно поэтому при разработке правка appsettings.json в проекте действует без пересборки: во время dotnet run читается файл из каталога проекта, а не копия в bin.

Файл подключается как необязательный (optional: true): если его нет, приложение не упадёт. Проверено — файл убрали, приложение стартовало, и ConnectionString остался пустым, потому что он был только в этом файле. Отсюда мораль: отсутствие файла настроек — не ошибка, ошибкой его делает только валидация (см. ниже).

Секреты — не в файле в репозитории

Пароли и ключи не хранят в appsettings.json: файл лежит в git и уезжает в образ. Локально — user-secrets, в проде — переменные окружения или менеджер секретов (последний раздел главы).

Секция — это «вид» на плоский список ключей

Теперь главное, что объясняет вопрос «откуда он берёт именно эту секцию». Внутри IConfiguration — плоский набор пар «ключ → строка», никакой вложенности там нет. Вложенность из JSON превращается в префикс ключа, разделённый двоеточием:

"Orders": { "PageSize": 50 }        →   ключ Orders:PageSize = "50"
"Orders": { "Items": [ {...} ] }    →   ключи Orders:Items:0:Name, Orders:Items:1:Name, ...

А GetSection("Orders") ничего не вырезает и не копирует: он возвращает IConfigurationSection с Path = "Orders", и любое обращение через неё — это обращение к тому же плоскому списку, только с приписанным префиксом. Реальный вывод для файлов выше:

--- все ключи конфигурации (только Orders)
  Orders = (null)
  Orders:PageSize = 20
  Orders:ConnectionString = Host=prod-db;Database=shop

секция Orders: Path=Orders Value=null ключей=2
  ребёнок: ConnectionString = Host=prod-db;Database=shop
  ребёнок: PageSize = 20
cfg["Orders:PageSize"] = 20
cfg.GetSection("Orders")["PageSize"] = 20

Что здесь важно:

  • файл — не секция. Секция — это префикс в общем списке, поэтому её значения могут прийти из разных источников: PageSize из файла, ConnectionString — из переменной окружения. Для кода это одна и та же секция Orders;
  • у самой секции Value равно null, потому что у неё есть дети — типичная причина «настройка приходит пустая», когда её читают как cfg.GetSection("Orders").Value;
  • имя секции — просто строка, которую вы сами написали в GetSection("Orders") и Bind(...). Опечатка не падает: GetSection("Orderss").Exists() вернёт false, детей будет 0, класс останется с дефолтами из инициализаторов. Проверено: приложение стартовало без ошибок, PageSize = 50, ConnectionString пустой.

Один и тот же ключ в разных источниках записывается по-разному, но это один ключ:

ИсточникКак задать Orders:PageSize
appsettings.json"Orders": { "PageSize": 50 }
переменные окруженияOrders__PageSize=50 — двойное подчёркивание вместо :
аргументы командной строки--Orders:PageSize=50 (годится и --Orders:PageSize 50)
user-secretsdotnet user-secrets set "Orders:PageSize" "50"

Опции: привязка конфигурации к классу

Читать строки конфигурации по всему коду — плохо: ключ пишется руками, тип — строка, ошибка видна только в рантайме. Значения привязывают к классу и инжектят его через DI:

// using System.ComponentModel.DataAnnotations;

public sealed class OrderOptions
{
    [Range(1, 200)]                            // правила проверки — атрибутами
    public int PageSize { get; init; } = 50;

    [Required]
    public string ConnectionString { get; init; } = "";
}

builder.Services
    .AddOptions<OrderOptions>()                        // 1) объявить опции класса
    .Bind(builder.Configuration.GetSection("Orders"))   // 2) секция → свойства
    .ValidateDataAnnotations()                          // 3) проверять атрибуты
    .ValidateOnStart();                                 // 4) проверять на старте

Что делает каждая строка:

  • AddOptions<OrderOptions>() — регистрирует инфраструктуру опций (что именно — в следующем разделе) и возвращает билдер, к которому цепляются остальные вызовы;
  • Bind(section) — «взять секцию и разложить по свойствам»: для каждого свойства ищется ключ Orders:ИмяСвойства. Без этой строки класс останется с дефолтами из инициализаторов (проверено: PageSize = 50);
  • ValidateDataAnnotations() — прогоняет атрибуты [Required], [Range] и остальные из System.ComponentModel.DataAnnotations. Если атрибутов нет, проверять нечего: класс без атрибутов проходит валидацию молча, даже когда секции не существует;
  • ValidateOnStart() — выполняет проверку при старте, а не при первом обращении к значениям.
init и Bind — совместимы, а лямбда — нет

Bind пишет в свойства через скомпилированные сеттеры, поэтому init-свойства он заполняет нормально. А вот Configure(o => o.PageSize = 1) с init-свойством не скомпилируется:

error CS8852: Init-only property or indexer 'OrderOptions.PageSize' can only be assigned in an object
initializer, or on 'this' or 'base' in an instance constructor or an 'init' accessor.

Если нужна настройка кодом — либо set вместо init, либо .Configure<IConfiguration>((o, cfg) => cfg.GetSection("Orders").Bind(o)).

Что даёт ValidateOnStart()

Возьмём заведомо плохое значение: Orders:PageSize = 5000 при [Range(1, 200)]. С ValidateOnStart() приложение не стартует и показывает, что именно не так:

Microsoft.Extensions.Options.OptionsValidationException: DataAnnotation validation failed for
'OrderOptions' members: 'PageSize' with the error: 'The field PageSize must be between 1 and 200.'.

Без этой строки приложение стартует нормально и падает позже — на первом обращении к options.Value, то есть уже внутри запроса. Тот же класс, то же значение, реальный вывод:

Application started. Press Ctrl+C to shut down.
--- приложение стартовало нормально
--- упало при ПЕРВОМ обращении к Value
тип: Microsoft.Extensions.Options.OptionsValidationException
DataAnnotation validation failed for 'OrderOptions' members: 'PageSize' with the error: ...
Ошибка конфигурации должна валить старт, а не запрос

Разница видна в проде. С ValidateOnStart() контейнер не поднимется, деплой откатится, и виноватой будет конфигурация. Без неё приложение «работает», а 500-е начинаются при первом заказе — и искать будут в сервисе заказов, а не в настройках.

Если атрибутов мало, есть Validate с предикатом и своим текстом ошибки (реальный вывод):

.Validate(o => o.PageSize > 0, "PageSize должен быть больше нуля")
Microsoft.Extensions.Options.OptionsValidationException: PageSize должен быть больше нуля

Откуда IOptions<T> берёт значения

Второй вопрос был про сервис: «а здесь откуда взяты настройки?». Ответ: из контейнера, и за этим стоит цепочка из нескольких объектов, которую видно в отладке. Вот что реально оказывается в контейнере после цепочки вызовов из предыдущего раздела (вывод по IServiceCollection):

IOptions`1               UnnamedOptionsManager`1                    Singleton
IOptionsSnapshot`1       OptionsManager`1                           Scoped
IOptionsMonitor`1        OptionsMonitor`1                           Singleton
IOptionsFactory`1        OptionsFactory`1                           Transient
IOptionsMonitorCache`1   OptionsCache`1                             Singleton

IConfigureOptions`1      NamedConfigureFromConfigurationOptions`1  Singleton   ← добавил .Bind(...)
IOptionsChangeTokenSource`1  ConfigurationChangeTokenSource`1       Singleton   ← добавил .Bind(...)
IValidateOptions`1       DataAnnotationValidateOptions`1            Singleton   ← добавил .ValidateDataAnnotations()

То есть .Bind() — это не «чтение файла при старте», а регистрация действия настройки: IConfigureOptions<OrderOptions>, внутри которого лежит та самая секция и вызов Bind, плюс источник уведомлений IOptionsChangeTokenSource (он и делает возможной перезагрузку). Регистрацию источника делает именно Bind: после обычного Configure(o => ...) в контейнере таких источников 0, после Bind(section) — 1 (проверено).

Дальше при первом обращении к options.Value происходит вот это:

options.Value                     IOptions<OrderOptions> → UnnamedOptionsManager
  └─ IOptionsFactory.Create("")   → OptionsFactory
       ├─ все IConfigureOptions    → NamedConfigureFromConfigurationOptions   читает секцию Orders
       ├─ все IValidateOptions     → DataAnnotationValidateOptions            проверяет атрибуты
       └─ готовый объект → IOptionsMonitorCache (OptionsCache)

Отсюда три следствия, которые и спрашивают на собеседовании:

  • настройки берутся из IConfiguration, которую захватил делегат привязки (builder.Configuration — это ConfigurationManager, живой объект, который сам следит за файлами), а не «из класса настроек»;
  • IOptions<T> существует для любого T: это открытый generic, и он уже зарегистрирован хостом. Если вы забыли Bind, ошибки не будет — придёт объект с дефолтными значениями (проверено: без Bind PageSize = 50 из инициализатора);
  • объект собирается один раз и кэшируется: ReferenceEquals(opt.Value, opt.Value) даёт True (проверено). Поэтому «прочитать значение заново» через IOptions не получится — нужен другой интерфейс (следующий раздел).
Почему так, а не «прочитать в конструкторе»

Сервис не знает ни про файлы, ни про переменные окружения. Он просит IOptions<OrderOptions> — и получает объект, собранный из конфигурации по правилам, которые описаны в одном месте, в Program.cs. Добавился источник, поменялась секция, пришла переменная окружения — сервис не меняется вообще.

И сразу про IConfiguration «везде»: технически читать IConfiguration["Orders:PageSize"] можно, но тогда ключ повторяется в каждом месте, тип — строка, а валидации нет. Правильный подход: привязать один раз к классу и инжектить IOptions<T> — настройки типизированы, проверены и не разбросаны по коду.

Три варианта чтения опций (и их lifetimes)

Здесь мы возвращаемся к жизненным циклам из главы 15 — у опций они тоже есть:

ТипLifetimeКогда брать
IOptions<T>SingletonЗначения не меняются на ходу (обычный случай)
IOptionsSnapshot<T>ScopedНужно перечитывать значения на каждый запрос
IOptionsMonitor<T>SingletonНужны уведомления об изменении настроек

Разница не теоретическая. Ниже — один запуск, в котором файл настроек меняют на ходу (PageSize: 10 → 99, файл подключён с reloadOnChange: true), а читают все три варианта. Реальный вывод:

до правки файла:  IOptions 10 | Snapshot 10 | Monitor 10
  [OnChange] новые настройки: 99
тот же scope:     IOptions 10 | Snapshot 10 | Monitor 99
новый scope:      IOptions 10 | Snapshot 99 | Monitor 99
  • IOptions — 10 навсегда: значение собрано при первом обращении и лежит в кэше;
  • IOptionsSnapshot — снимок на scope: внутри одного scope значение не меняется (10), в новом scope собирается заново (99);
  • IOptionsMonitor — CurrentValue всегда актуально, а OnChange сам сообщает об изменении.

Плата за scoped-природу IOptionsSnapshot: его нельзя запрашивать из корня контейнера (и держать в singleton-сервисе). Попытка заканчивается так — реальный текст:

InvalidOperationException: Cannot resolve scoped service
'Microsoft.Extensions.Options.IOptionsSnapshot`1[OrderOptions]' from root provider.

И ещё одно условие: перезагрузка работает, только если источник её поддерживает (AddJsonFile(..., reloadOnChange: true) — в веб-хосте так по умолчанию) и если Bind был вызван, потому что источник уведомлений регистрирует именно он.

Как это выглядит в сервисе

Тот самый класс из вопроса — в нём нет ни пути к файлу, ни ключей, и это правильно:

public sealed class OrderService(IOptions<OrderOptions> options)
{
    private readonly OrderOptions _opt = options.Value;   // ← здесь настройки «появляются»
    public int PageSize => _opt.PageSize;
}

По шагам:

  1. контейнер создаёт OrderService и видит в конструкторе IOptions<OrderOptions>;
  2. отдаёт UnnamedOptionsManager<OrderOptions> — обёртку, а не сами настройки;
  3. строка options.Value запускает цепочку из предыдущего раздела: Bind читает секцию Orders из IConfiguration, объект собирается, валидируется и кэшируется.

Два замечания к этому коду, которые стоит держать в голове:

  • private readonly OrderOptions _opt = options.Value; — это снимок на момент создания сервиса. Для IOptions так и надо: значения всё равно не меняются. Но если вы рассчитываете на перезагрузку, нужен IOptionsMonitor и чтение CurrentValue при каждом обращении, а не поле;
  • OrderService тоже надо зарегистрировать (AddScoped<OrderService>()) — наличие конструктора с IOptions само его в контейнер не добавляет.

Вариант с перезагрузкой выглядит так:

public sealed class OrderService(IOptionsMonitor<OrderOptions> options)
{
    public int PageSize => options.CurrentValue.PageSize;   // читается при каждом обращении
}

builder.Services.AddScoped<OrderService>();

Строки подключения и секреты

Строка подключения — такой же ключ конфигурации, только с префиксом ConnectionStrings:, и для неё есть метод-сокращение:

// appsettings.json: "ConnectionStrings": { "Default": "Host=db;Database=shop" }
var cs = builder.Configuration.GetConnectionString("Default");
// cs = "Host=db;Database=shop" — проверено

В проде ту же строку задают переменной окружения ConnectionStrings__Default, и код не меняется.

Секреты — вне репозитория

Пароли и ключи не хранят в appsettings.json: файл лежит в git и уезжает в образ. Локально — dotnet user-secrets (значения хранятся в профиле пользователя и подключаются только в Development), в проде — переменные окружения или менеджер секретов.

dotnet user-secrets init
dotnet user-secrets set "Orders:ConnectionString" "Host=localhost;Database=shop"

Ключи в user-secrets — те же, что в JSON: Orders:ConnectionString. Меняется только источник, код остаётся прежним.

★ Что запомнить
  • Конфигурация — плоский список ключей из нескольких источников; побеждает последний: файл окружения перекрывает базовый файл, переменные окружения — файлы, аргументы — всё.
  • Вложенность JSON — это префикс ключа (Orders:PageSize); в переменных окружения — Orders__PageSize.
  • GetSection("Orders") возвращает «вид» на этот список по префиксу, а не копию файла секции; опечатка в имени не падает, а даёт дефолты.
  • Опции привязываются к классу в одном месте (Bind), проверяются атрибутами и ValidateOnStart, читаются через IOptions / IOptionsSnapshot / IOptionsMonitor — с их lifetimes.
  • options.Value собирается один раз и кэшируется; для перезагрузки — только IOptionsMonitor (или snapshot на scope).
