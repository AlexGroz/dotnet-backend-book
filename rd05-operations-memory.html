Глава 5. Эксплуатация: память, eviction, персистентность и отказоустойчивость

Что произойдёт, когда память кончится, что теряется при перезапуске и как не превратить кэш в единую точку отказа

основная глава

Память: maxmemory и политики вытеснения

Redis не «сам понимает», сколько памяти ему можно. Пока maxmemory равен нулю, он растёт до исчерпания памяти машины — и тогда его убьёт OOM-killer контейнера или ОС. Поэтому лимит задают явно, а вместе с ним — политику: что делать, когда лимит достигнут.

ПолитикаЧто вытесняетКогда подходит
noevictionНичего: записи начинают падать с ошибкойRedis хранит данные, которые нельзя терять (локи, счётчики, очереди)
allkeys-lruЛюбой ключ, реже всех использованныйЧистый кэш: всё содержимое восстановимо
allkeys-randomСлучайный ключКэш с равномерным доступом
volatile-lru / volatile-ttlТолько ключи с TTL — по давности или по остатку времениСмешанный Redis: кэш с TTL и вечные данные рядом

Значения по умолчанию (проверено):

# CONFIG GET <параметр> — прочитать настройку работающего сервера
#   maxmemory — сколько памяти разрешено данным; 0 = лимита нет
redis-cli config get maxmemory
maxmemory                    # ← сначала печатается имя параметра
0                            # ← затем значение (в байтах; 0 = без лимита)
#   maxmemory-policy — что делать, когда лимит достигнут:
#   noeviction = ничего не удалять, а отклонять записи с ошибкой
redis-cli config get maxmemory-policy
maxmemory-policy
noeviction

То есть «из коробки» Redis не вытесняет ничего: он просто отказывается писать, когда память кончилась. Для кэша это почти всегда неправильная настройка.

Как выглядит вытеснение на практике

Ограничим память 4 МБ и включим allkeys-lru, затем запишем 20 000 ключей по 200 байт (проверено):

# CONFIG SET — меняет настройку «на живом» сервере, без перезапуска
#   (в конфиг-файл это не пишется: после рестарта вернутся прежние значения)
redis-cli config set maxmemory 4mb                # лимит данных — 4 МБ
redis-cli config set maxmemory-policy allkeys-lru # при переполнении вытеснять любые ключи по LRU

# 20 000 команд SET разом через pipe: каждая строка sets.txt — это "SET key value".
# pipe = конвейер: клиент не ждёт ответа на каждую команду, поэтому в разы быстрее цикла
redis-cli --pipe < sets.txt
# All data transferred. Waiting for the last reply...
# Last reply received from server.
# errors: 0, replies: 20000       ← 20 000 команд принято, ни одной ошибки

# INFO memory — сколько занято и какая политика действует прямо сейчас
redis-cli info memory | grep -E 'used_memory_human|maxmemory_policy'
# used_memory_human:4.00M         ← упёрлись в лимит
# maxmemory_policy:allkeys-lru

# INFO stats → evicted_keys: сколько ключей сервер вытеснил сам, без наших команд
redis-cli info stats | grep evicted_keys
# evicted_keys:10536

# DBSIZE — сколько ключей осталось в базе: 20 000 − 10 536 = 9 464
redis-cli dbsize
# 9464

Из 20 000 записанных ключей в памяти осталось 9 464, а 10 536 были вытеснены — и ни одна команда не вернула ошибку. Именно этого и ждут от кэша: память ограничена, старые ключи уходят, приложение работает.

Обратная сторона: noeviction поверх лимита

С той же памятью, но с политикой noeviction, запись падает:

# noeviction: место кончилось, удалять нечего/нельзя — сервер отклоняет запись
redis-cli set probe:key value
(error) OOM command not allowed when used memory > 'maxmemory'.

Чтение при этом продолжает работать. Для кэша это означает, что приложение обязано переживать ошибки записи в Redis: не падать, а просто идти в базу.

Мониторинг: на что смотреть

INFO — команда, которая возвращает снимок состояния сервера: пары «поле: значение». Без аргумента печатает все разделы сразу, с аргументом — только один. Список разделов (реальный вывод на Redis 7.4):

redis-cli info | grep '^#'      # какие разделы вообще есть у этого сервера
# Server
# Clients
# Memory
# Persistence
# Stats
# Replication
# CPU
# Modules
# Errorstats
# Cluster
# Keyspace

redis-cli INFO MEMORY           # регистр не важен: INFO MEMORY = info memory
Где вводятся эти команды

В книге команды записаны коротко: redis-cli info memory. Это то, что набирают внутри контейнера с Redis (он запущен в главе 1 под именем redis7). Три равнозначных способа — все запускаются из обычного терминала на вашей машине:

# 1) одной строкой: redis-cli запускается внутри контейнера, вывод приходит в ваш терминал
docker exec redis7 redis-cli info memory

# 2) войти в оболочку redis-cli и вводить команды там — уже без «redis-cli» и без «docker»
docker exec -it redis7 redis-cli
127.0.0.1:6379> info keyspace     # приглашение «127.0.0.1:6379>» = вы внутри redis-cli
127.0.0.1:6379> quit              # выход

# 3) если redis-cli установлен на хосте, а порт опубликован (-p 6379:6379 из главы 1)
redis-cli -h localhost -p 6379 info memory

Для команд, читающих файл со stdin, контейнеру нужен флаг -i: docker exec -i redis7 redis-cli --pipe < sets.txt — так и снимались цифры про вытеснение выше. На сам вывод способ запуска не влияет: ниже он ровно такой, каким его печатает сервер.

Накопительные счётчики против мгновенных значений

В Stats почти всё — счётчики за всё время с момента старта: они только растут. В Memory и Keyspace наоборот — текущее состояние. Поэтому два снимка одного сервера могут не сходиться, и это нормально: сразу после записи 20 000 ключей было evicted_keys:10536 и dbsize 9464, а через несколько наших экспериментов — уже evicted_keys:10853 и 9 148 ключей в базе: мы дописали ещё пару ключей, и вытеснение продолжилось.

# счётчики можно обнулить, не перезапуская сервер (например, чтобы мерить «с этого момента»)
redis-cli config resetstat
OK
redis-cli info stats | grep -E 'rejected_connections|total_commands_processed'
# rejected_connections:0        ← было 1 (эксперимент с maxclients — ниже)
# total_commands_processed:1    ← в счётчик попала только эта же команда INFO

3. INFO keyspace — сколько ключей и сколько из них с TTL

docker exec redis7 redis-cli info keyspace
# Keyspace
db0:keys=9148,expires=1,avg_ttl=0,subexpiry=0

Одна строка на каждую непустую базу (db0…db15). Если база пуста, строки для неё нет — на пустом сервере вывод состоит из одного заголовка # Keyspace:

  • keys=9148 — сколько ключей в базе сейчас: 20 000 записанных − 10 853 вытесненных + 1 наш session:demo.
  • expires=1 — из них с TTL: только session:demo (остальные 20 000 писали без TTL, и политика allkeys-lru вытесняет в том числе вечные ключи).
  • avg_ttl=0 — средний остаток TTL по ключам с TTL, в миллисекундах. Ноль здесь не потому, что TTL нет (он есть — expires=1), а потому что снимок снят сразу после записи единственного TTL-ключа: значение считает цикл истечения, а не сама команда SET. Воспроизводится в три команды — flushall, set k v ex 600 и сразу info keyspace: время от времени видно avg_ttl=0, а через секунду уже avg_ttl=599900. Когда TTL-ключей много, значение стабильно: 200 ключей по EX 600 дают db0:keys=200,expires=200,avg_ttl=599819,subexpiry=0.
  • subexpiry=0 — сколько полей хешей имеют собственный TTL (команда HEXPIRE, новое в Redis 7.4). Проверяется в две команды: hset h:1 a 1 b 2 → subexpiry=0; hexpire h:1 100 fields 1 a → subexpiry=1 (у поля a свой TTL 100 секунд, hpttl h:1 fields 1 a → 99857).

client_recent_max_input_buffer:0
client_recent_max_output_buffer:0
blocked_clients:0
tracking_clients:0

Смысл полей: connected_clients:1 — прямо сейчас подключён один клиент (сам redis-cli; предыдущая команда уже отключилась). maxclients:10000 — лимит одновременных соединений. blocked_clients:0 — никто не висит в ожидании данных (BLPOP, BRPOP, XREAD BLOCK). Команда WAIT в этот счётчик не попадает — проверено: висящий wait 0 5000 даёт connected_clients:2 при blocked_clients:0, а xread block 5000 — blocked_clients:1. Вот как выглядит вывод, когда один клиент действительно ждёт (в соседнем терминале запущен blpop queue:jobs 0):

docker exec -d redis7 sh -c 'redis-cli blpop queue:jobs 0'   # клиент повис в ожидании элемента
docker exec redis7 redis-cli info clients | head -7
# Clients
connected_clients:2
cluster_connections:0
maxclients:10000
client_recent_max_input_buffer:20520
client_recent_max_output_buffer:0
blocked_clients:1

docker exec redis7 redis-cli client list
# id=41 addr=127.0.0.1:45930 ... flags=b ...     ← b = blocked, это наш BLPOP
# id=43 addr=127.0.0.1:45952 ... flags=N ...     ← N = normal, это сам client list

Растущий blocked_clients — сигнал, что потребители ждут, а producer не успевает; но помните, что в BLPOP висит и «нормальный» потребитель очереди, который просто ждёт работы.

Как своими руками получить ненулевой rejected_connections

Этот счётчик растёт, когда соединений больше, чем maxclients. Чтобы увидеть, а не поверить на слово, эксперимент делали на отдельном контейнере (порт 6380), чтобы не ломать основной: ставим лимит 1, занимаем его висящим BLPOP, затем пробуем подключиться ещё раз.

docker run -d --name redistest -p 6380:6379 redis:7-alpine   # отдельный сервер для опытов
docker exec redistest redis-cli config set maxclients 1
OK
docker exec -d redistest sh -c 'redis-cli blpop q 0'   # единственное разрешённое соединение занято
docker exec redistest redis-cli ping
ERR max number of clients reached                        # ← это и считает rejected_connections

# освободили место и посмотрели счётчик
docker exec redistest sh -c 'pkill -f "redis-cli blpop"'
docker exec redistest redis-cli config set maxclients 10000
OK
docker exec redistest redis-cli info stats | grep rejected_connections
rejected_connections:1

На проде то же самое выглядит как RedisConnectionException в .NET и всплеск rejected_connections: почти всегда это утечка соединений — например, ConnectionMultiplexer создаётся на каждый запрос вместо одного на процесс.

★ Четыре цифры, по которым видно здоровье Redis
  • Доля попаданий keyspace_hits / (hits + misses): в примере 64 %. Падает — кэш перестал помогать: мало памяти, короткий TTL или ключи не те, что читаются.
  • evicted_keys растёт — памяти не хватает на рабочий набор: либо больше памяти, либо меньше TTL и объём значений.
  • blocked_clients — сколько клиентов ждёт в блокирующих командах; устойчивый рост = потребители не успевают.
  • mem_fragmentation_ratio стабильно > 1.5 — фрагментация: помогает activedefrag yes или плановый перезапуск; < 1 — память ушла в swap, это хуже.

Персистентность: что теряется при перезапуске

У Redis два механизма, и по умолчанию включён только первый:

МеханизмЧто делаетПо умолчанию
RDBПериодический снимок всей базы в файл dump.rdb Включён: save "3600 1 300 100 60 10000" — снимок, если за 3600 с изменился хотя бы 1 ключ, за 300 с — 100, за 60 с — 10 000
AOFЖурнал команд, дописываемый на диск Выключен: appendonly no

Отсюда практическое следствие: при аварийном завершении процесса Redis теряет всё, что изменилось после последнего снимка или не успело попасть в AOF. Для кэша это нормально; для данных, которые «нельзя терять», — нет.

Как выбрать

Чистый кэш: персистентность можно вообще отключить — после перезапуска кэш прогреется сам. Очереди, локи, счётчики: включайте AOF (appendonly yes), иначе после рестарта они исчезнут вместе с данными. И в любом случае реплика — не бэкап.

Отказоустойчивость: Sentinel и Cluster

Один Redis — это одна точка отказа: упал процесс или машина, и кэш исчез (а вместе с ним, возможно, локи и счётчики). Два способа это пережить:

  • Репликация + Sentinel. Есть мастер и реплики; Sentinel следит за мастером и при падении повышает одну из реплик, а клиент получает новый адрес мастера. Данные при этом могут потеряться: репликация асинхронная.
  • Redis Cluster. Данные шардируются между мастерами (у каждого свои реплики), клиент сам находит узел по ключу. Это про горизонтальный масштаб, а не только про отказ: один узел больше не обязан держать весь объём.

Для приложения главное правило не меняется: потеря Redis не должна быть потерей данных. Если после падения кэша сервис не поднимается — значит, в Redis лежит то, что там лежать не должно.

Типичные ошибки эксплуатации
  • maxmemory = 0 в контейнере с лимитом памяти. Redis считает, что памяти сколько угодно, и его убивает OOM-killer — без предупреждения и без вытеснения.
  • Политика noeviction для кэша. Вместо вытеснения старых ключей записи начинают падать с OOM command not allowed….
  • KEYS * в проде. Одна такая команда блокирует сервер на всё время перебора.
  • Один Redis на кэш, локи, счётчики и очереди. Вытеснение из-под кэша начнёт выбрасывать локи и счётчики. Разные задачи — разные базы или разные инстансы.
  • Нет таймаутов. Клиент без connectTimeout/syncTimeout при проблеме с сетью вешает запросы приложения.
★ Что запомнить из главы
  • Всегда задавайте maxmemory и политику: по умолчанию Redis ничего не вытесняет и падает на записи.
  • Для кэша — allkeys-lru (или volatile-*, если рядом лежат вечные ключи); для данных «нельзя терять» — noeviction плюс персистентность.
  • RDB включён, AOF выключен — значит, свежие записи теряются при аварии; для очередей и счётчиков включайте AOF.
  • Смотрите keyspace_hits/misses и evicted_keys, а не только «жив ли процесс».
  • Репликация и Cluster — про доступность и объём, а не про сохранность данных: истина должна оставаться в PostgreSQL.
