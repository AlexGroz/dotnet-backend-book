Глава 5. Эксплуатация: память, eviction, персистентность и отказоустойчивость

Что произойдёт, когда память кончится, что теряется при перезапуске и как не превратить кэш в единую точку отказа

основная глава

Память: maxmemory и политики вытеснения

Redis не «сам понимает», сколько памяти ему можно. Пока maxmemory равен нулю, он растёт до исчерпания памяти машины — и тогда его убьёт OOM-killer контейнера или ОС. Поэтому лимит задают явно, а вместе с ним — политику: что делать, когда лимит достигнут.

ПолитикаЧто вытесняетКогда подходит
noevictionНичего: записи начинают падать с ошибкойRedis хранит данные, которые нельзя терять (локи, счётчики, очереди)
allkeys-lruЛюбой ключ, реже всех использованныйЧистый кэш: всё содержимое восстановимо
allkeys-randomСлучайный ключКэш с равномерным доступом
volatile-lru / volatile-ttlТолько ключи с TTL — по давности или по остатку времениСмешанный Redis: кэш с TTL и вечные данные рядом

Значения по умолчанию (проверено):

redis-cli config get maxmemory          # maxmemory  0
redis-cli config get maxmemory-policy   # maxmemory-policy  noeviction

То есть «из коробки» Redis не вытесняет ничего: он просто отказывается писать, когда память кончилась. Для кэша это почти всегда неправильная настройка.

Как выглядит вытеснение на практике

Ограничим память 4 МБ и включим allkeys-lru, затем запишем 20 000 ключей по 200 байт (проверено):

redis-cli config set maxmemory 4mb
redis-cli config set maxmemory-policy allkeys-lru

# 20 000 команд SET через pipe
redis-cli --pipe < sets.txt
# All data transferred. Waiting for the last reply...
# Last reply received from server.
# errors: 0, replies: 20000

redis-cli info memory | grep -E 'used_memory_human|maxmemory_policy'
# used_memory_human:4.00M
# maxmemory_policy:allkeys-lru

redis-cli info stats | grep evicted_keys
# evicted_keys:12796

redis-cli dbsize
# 7208

Из 20 000 записанных ключей в памяти осталось 7 208, а 12 796 были вытеснены — и ни одна команда не вернула ошибку. Именно этого и ждут от кэша: память ограничена, старые ключи уходят, приложение работает.

Обратная сторона: noeviction поверх лимита

С той же памятью, но с политикой noeviction, запись падает:

redis-cli set probe:key value
(error) OOM command not allowed when used memory > 'maxmemory'.

Чтение при этом продолжает работать. Для кэша это означает, что приложение обязано переживать ошибки записи в Redis: не падать, а просто идти в базу.

Мониторинг: на что смотреть

Три блока INFO закрывают почти все вопросы:

redis-cli info memory    # used_memory_human, maxmemory_human, maxmemory_policy,
                         # mem_fragmentation_ratio
redis-cli info stats     # keyspace_hits, keyspace_misses, evicted_keys, expired_keys,
                         # rejected_connections, total_commands_processed
redis-cli info keyspace  # db0:keys=...,expires=...,avg_ttl=...
redis-cli info clients   # connected_clients, blocked_clients
  • Доля попаданий = keyspace_hits / (keyspace_hits + keyspace_misses). Если она падает — кэш перестал помогать: мало памяти, слишком короткий TTL или ключи не те, что читаются.
  • evicted_keys растёт — память закончилась и кэш вытесняет данные быстрее, чем они успевают пригодиться. Либо увеличивать память, либо уменьшать TTL и объём значений.
  • blocked_clients — сколько клиентов висит на BLPOP и подобных командах; резкий рост означает, что потребители ждут, а producer не успевает.
  • mem_fragmentation_ratio заметно больше единицы — память фрагментирована; помогает перезапуск или включение activedefrag (настройка сервера).
  • rejected_connections — упёрлись в maxclients: обычно это утечка соединений (например, мультиплексор создаётся на каждый запрос).

В примере с вытеснением счётчики выглядели так: keyspace_hits:14, keyspace_misses:7 — доля попаданий 67 % на кэше, куда всё только что записали.

Персистентность: что теряется при перезапуске

У Redis два механизма, и по умолчанию включён только первый:

МеханизмЧто делаетПо умолчанию
RDBПериодический снимок всей базы в файл dump.rdb Включён: save "3600 1 300 100 60 10000" — снимок, если за 3600 с изменился хотя бы 1 ключ, за 300 с — 100, за 60 с — 10 000
AOFЖурнал команд, дописываемый на диск Выключен: appendonly no

Отсюда практическое следствие: при аварийном завершении процесса Redis теряет всё, что изменилось после последнего снимка или не успело попасть в AOF. Для кэша это нормально; для данных, которые «нельзя терять», — нет.

Как выбрать

Чистый кэш: персистентность можно вообще отключить — после перезапуска кэш прогреется сам. Очереди, локи, счётчики: включайте AOF (appendonly yes), иначе после рестарта они исчезнут вместе с данными. И в любом случае реплика — не бэкап.

Отказоустойчивость: Sentinel и Cluster

Один Redis — это одна точка отказа: упал процесс или машина, и кэш исчез (а вместе с ним, возможно, локи и счётчики). Два способа это пережить:

  • Репликация + Sentinel. Есть мастер и реплики; Sentinel следит за мастером и при падении повышает одну из реплик, а клиент получает новый адрес мастера. Данные при этом могут потеряться: репликация асинхронная.
  • Redis Cluster. Данные шардируются между мастерами (у каждого свои реплики), клиент сам находит узел по ключу. Это про горизонтальный масштаб, а не только про отказ: один узел больше не обязан держать весь объём.

Для приложения главное правило не меняется: потеря Redis не должна быть потерей данных. Если после падения кэша сервис не поднимается — значит, в Redis лежит то, что там лежать не должно.

Типичные ошибки эксплуатации
  • maxmemory = 0 в контейнере с лимитом памяти. Redis считает, что памяти сколько угодно, и его убивает OOM-killer — без предупреждения и без вытеснения.
  • Политика noeviction для кэша. Вместо вытеснения старых ключей записи начинают падать с OOM command not allowed….
  • KEYS * в проде. Одна такая команда блокирует сервер на всё время перебора.
  • Один Redis на кэш, локи, счётчики и очереди. Вытеснение из-под кэша начнёт выбрасывать локи и счётчики. Разные задачи — разные базы или разные инстансы.
  • Нет таймаутов. Клиент без connectTimeout/syncTimeout при проблеме с сетью вешает запросы приложения.
★ Что запомнить из главы
  • Всегда задавайте maxmemory и политику: по умолчанию Redis ничего не вытесняет и падает на записи.
  • Для кэша — allkeys-lru (или volatile-*, если рядом лежат вечные ключи); для данных «нельзя терять» — noeviction плюс персистентность.
  • RDB включён, AOF выключен — значит, свежие записи теряются при аварии; для очередей и счётчиков включайте AOF.
  • Смотрите keyspace_hits/misses и evicted_keys, а не только «жив ли процесс».
  • Репликация и Cluster — про доступность и объём, а не про сохранность данных: истина должна оставаться в PostgreSQL.
