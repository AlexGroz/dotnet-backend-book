Глава 25. Паттерны сопоставления: switch-выражения, property и list-паттерны

Паттерн — это проверка формы значения вместе с извлечением данных из него. Разбираем реляционные, логические, property-, type- и list-паттерны, порядок ветвей и то, что всё это стоит в рантайме. Все выводы и замеры — с запуска на .NET 8 (Release).

основная глава

Что умеет паттерн

Один и тот же паттерн работает в is, в switch-выражении и в switch-инструкции; разница — в том, что выражение возвращает значение, а инструкция допускает break и goto case.

Реляционные и логические паттерны вместо лестницы if

static decimal Shipping(int weight) => weight switch
{
    < 0 => throw new ArgumentOutOfRangeException(nameof(weight)),
    0 => 0m,
    > 0 and <= 1000 => 350m,
    > 1000 and <= 5000 => 700m,
    _ => 1500m
};
вес     0 г -> доставка 0 руб.
вес   500 г -> доставка 350 руб.
вес  1000 г -> доставка 350 руб.
вес  1001 г -> доставка 700 руб.
вес  5000 г -> доставка 700 руб.
вес  5001 г -> доставка 1500 руб.

Границы включительны так, как написано: 1000 попадает в первую ветвь (> 0 and <= 1000), 1001 — во вторую. Ошибка «на единицу» здесь видна сразу, потому что условие одно, а не размазано по if/else if. Исключение в => — обычное выражение, оно бросается только при совпадении ветви.

Property-паттерны: правила вместо вложенных if

record Order(string Customer, decimal Total, bool IsPaid, int Lines);

static string Describe(Order? order) => order switch
{
    null => "нет заказа",
    { IsPaid: false } => "не оплачен",
    { Total: 0 } => "пустой заказ",
    { Total: > 100_000 } o => $"крупный заказ на {o.Total:N0}",
    { Total: > 10_000, Lines: > 5 } o => $"средний заказ, много позиций ({o.Lines})",
    { Total: > 10_000 } => "средний заказ",
    _ => "мелкий заказ"
};
нет заказа
не оплачен
средний заказ
крупный заказ на 250,000
пустой заказ

Разбор по строкам вывода:

  • null — отдельная ветвь: компилятор с nullable-контекстом требует её, если параметр Order? (глава 26).
  • Заказ bob на 45 000 с тремя позициями попал в { Total: > 10_000 }: ветвь с Lines: > 5 не совпала, и это правильно — порядок ветвей и есть приоритет.
  • { Total: 0 } стоит после проверки оплаты: неоплаченный пустой заказ будет назван «не оплачен». Поменяете ветви местами — поменяется бизнес-смысл.
  • o после паттерна — designator: совпавшую часть можно использовать в выражении ветви.
Геттеры вызываются на каждую проверяемую ветвь

Геттеры в property-паттерне вызываются по одному разу на проверяемое свойство в каждой ветви. Если геттер дорогой (ходит в БД, считает), лучше сначала положить значение в локальную переменную — иначе { Total: > 100_000 } и { Total: > 10_000 } вызовут его дважды.

Порядок ветвей: два предупреждения компилятора

Компилятор проверяет и «лишние», и «недостающие» ветви. Оба случая проверены на стенде.

static string Describe(int x) => x switch
{
    _ => "всё остальное",
    > 10 => "больше десяти"          // никогда не выполнится
};
error CS8510: The pattern is unreachable. It has already been handled by a previous arm
of the switch expression or it is impossible to match.

Неполное покрытие enum — предупреждение, а не ошибка: код соберётся и упадёт в рантайме

public enum Mode { Fast, Safe, Custom }

public static string Describe(Mode mode) => mode switch
{
    Mode.Fast => "быстро",
    Mode.Safe => "безопасно"
};
warning CS8509: The switch expression does not handle all possible values of its input type
(it is not exhaustive). For example, the pattern 'Mode.Custom' is not covered.

Что происходит в рантайме, если такую ветвь всё-таки вызвать

исключение: System.Runtime.CompilerServices.SwitchExpressionException
сообщение: Non-exhaustive switch expression failed to match its input.
Unmatched value was Custom.

Отсюда практика: _ ставят последним и осознанно; для enum и закрытых иерархий _ лучше не писать вовсе, чтобы добавление нового значения давало CS8509 на сборке, а не SwitchExpressionException в проде. Если проект собирается с <TreatWarningsAsErrors>, CS8509 становится ошибкой сборки — самый дешёвый способ поймать забытую ветвь.

List-паттерны: разбор пути без индексов

static string Route(string[] path) => path switch
{
    [] => "корень",
    ["orders"] => "список заказов",
    ["orders", var id] => $"заказ {id}",
    ["orders", var id, "items", .. var rest] => $"заказ {id}, остаток пути: [{string.Join(", ", rest)}]",
    [.., "health"] => "health в конце пути",
    _ => "не найдено"
};
/ -> корень
/orders -> список заказов
/orders/42 -> заказ 42
/orders/42/items/1/2 -> заказ 42, остаток пути: [1, 2]
/internal/health -> health в конце пути
/unknown/x -> не найдено

.. var rest — срез: он забирает «сколько осталось». Важная деталь, которую проверили замером: на массиве срез создаёт новый массив, а на Span — нет.

var arr = new[] { "orders", "42", "items", "1", "2" };
var span = arr.AsSpan();

// 1 000 000 разборов одного и того же пути
if (arr is ["orders", var id, "items", .. var rest]) ...
if (span is ["orders", var id, "items", .. var rest]) ...
массив: 40000000 Б на 1000000 разборов, sink=8000000
span:   0 Б на 1000000 разборов, sink=8000000

40 МБ на миллион разборов — это 40 байт на вызов: ровно новый двухэлементный массив для rest. С ReadOnlySpan<string> (или Span<char> для строки) аллокаций ноль. Поэтому в горячем пути (разбор пути запроса, парсинг протокола) срез берут на спане. И про порядок: [.., "health"] должен стоять последним, иначе он перехватит более специфичные маршруты.

Type-паттерны и null

static string Show(object? value) => value switch
{
    null => "null",
    int n when n < 0 => $"отрицательное число {n}",
    int n => $"число {n}",
    string { Length: 0 } => "пустая строка",
    string s => $"строка из {s.Length} символов",
    Order { Total: 0 } => "заказ без суммы",
    Order o => $"заказ {o.Customer}",
    IEnumerable<int> seq => $"последовательность из {seq.Count()} элементов",
    _ => value.GetType().Name
};
null                         | null
отрицательное число -5       | Int32
число 42                     | Int32
пустая строка                | String
строка из 5 символов         | String
заказ без суммы              | Order
последовательность из 3 элементов | Int32[]
Double                       | Double

Для double не нашлось ветви — сработал _ и вернул имя типа. Порядок важен и здесь: Order проверяется до IEnumerable<int>, хотя формально заказ не реализует IEnumerable; а если бы реализовал — ветвь Order должна стоять выше, иначе её перехватит интерфейс. when добавляет условие, которое не выражается паттерном (обратите внимание: int n с when и без — две отдельные ветви).

is null против == null

Паттерн null не вызывает перегруженный operator ==. Проверено на классе, у которого == всегда возвращает true:

var v = new AlwaysEqual();
Console.WriteLine($"v == null: {v == null}");
Console.WriteLine($"v is null: {v is null}");
v == null: True
v is null: False
v is not null: True
(object?)v is null: False

Отсюда правило: в проверках на null пишите is null/is not null. Это единственный вариант, который гарантированно смотрит на ссылку, а не на чужую логику сравнения (и не падает на перегрузке, которая сама разыменовывает аргумент).

Сколько это стоит

Паттерны не аллоцируют: это проверки типов и сравнения. Замер — 5 000 000 объектов четырёх видов в случайном порядке, Release, один и тот же результат sum во всех трёх вариантах:

var arr = new object[5_000_000];
for (var i = 0; i < arr.Length; i++) arr[i] = data[rnd.Next(data.Length)];

var a0 = GC.GetAllocatedBytesForCurrentThread();
foreach (var o in arr)
{
    if (o is int n) sum1 += n;
    else if (o is string s) sum1 += s.Length;
}
var alloc1 = GC.GetAllocatedBytesForCurrentThread() - a0;
is-паттерны:           56 мс, сумма 10832149, выделено 0 Б
as + null:            57 мс, сумма 10832149, выделено 0 Б
switch expression:    71 мс, сумма 10832149, выделено 0 Б

Выводы: (1) ни один вариант не выделяет память — боксинга нет, потому что значения уже в object; (2) разница 56 и 57 мс — шум; (3) switch-выражение в отдельном методе оказалось на ~25% медленнее — это цена вызова, который не заинлайнился, а не паттернов. В горячем коде порядок действий такой: сначала правильность и читаемость, затем профилировщик, и только потом «переписать switch на if» — если он вообще окажется в профиле.

Где паттерны действительно нужны

  • Разбор внешних данных — форма JSON-узла, путь запроса, набор заголовков; в связке с JsonNode и Utf8JsonReader.
  • Отображение результатов — Result/OneOf в домене: один switch вместо пачки if (result.IsSuccess).
  • Маппинг исключений и кодов — тип исключения и его свойства → HTTP-код и ProblemDetails.
  • Проверки в тестах — Assert.That(x, Is.InstanceOf<...>()) часто заменяется сравнением формы объекта.
  • Горячие пути — только со спанами и с замером: см. аллокации среза выше.
Три ловушки
  • Порядок важнее полноты. CS8509 — предупреждение; забытая ветвь всплывёт в рантайме как SwitchExpressionException. Не глушите его _ ради «чтобы собралось».
  • Побочные эффекты в паттернах. when и геттеры выполняются в момент проверки ветви, а не «один раз». Логирование внутри геттера превратит матчинг в непредсказуемый лог.
  • Паттерны не валидируют вход. Паттерн, совпавший «хоть с чем-то» через _, — это не проверка; валидация живёт отдельно (глава 30 в разделе .NET).
★ Чек-лист
  1. Проверка на null — is null, не == null.
  2. Для enum и закрытых иерархий — без _, чтобы CS8509 ловил новые значения.
  3. Специфичные ветви — выше общих; _ — последним.
  4. Дорогие геттеры — в локальную переменную до switch.
  5. Срез на массиве — аллокация; в горячем пути — Span.
  6. Тесты на «форму» данных дешевле и читаемее, чем цепочки Assert по полям.
★ Что спросят и как отвечать
  1. «Чем switch-выражение отличается от инструкции?» — выражение возвращает значение и должно быть полным; инструкция допускает break/goto и не требует полноты.
  2. «Что будет, если ветвь не совпала?» — SwitchExpressionException в рантайме; компилятор предупредит CS8509, если видит неполноту.
  3. «Паттерны медленнее if?» — на замере 5 млн объектов: 56 мс против 57 мс, аллокаций ноль; разница в пределах шума.
  4. «Почему is null лучше?» — не вызывает перегруженный ==; на стенде объект с ==, всегда возвращающим true, дал v == null: True и v is null: False.
  5. «List-паттерны аллоцируют?» — сам матчинг нет, но срез на массиве создаёт новый массив: 40 байт на разбор; на Span — ноль.
