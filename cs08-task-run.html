Глава 8. Task.Run: когда нужен и когда вредит

«Обернуть в Task.Run, чтобы стало асинхронно» — самый частый способ сделать хуже. Разберём, что именно делает этот метод и где его место.

основная глава

Что делает Task.Run

Task.Run(делегат) ставит делегат в очередь пула потоков и возвращает Task, который завершится, когда делегат отработает. То есть это про выполнение кода на другом потоке, а не про «асинхронность» в смысле освобождения потока.

// тот же код, но выполняется в потоке пула
Task<int> task = Task.Run(() => HeavyCompute(data));
int result = await task;      // ждём результат, не блокируя текущий поток
Асинхронность ≠ многопоточность

Есть два разных типа работы:

  • I/O-bound — ждём сеть, диск, базу. Правильный инструмент — await: поток освобождается и обслуживает другие запросы (глава 12 .NET-раздела).
  • CPU-bound — считаем на процессоре. Здесь await не поможет: кто-то должен реально считать. Поток будет занят — вопрос лишь в том, какой.

Почему на сервере Task.Run вокруг I/O — плохо

// ✘ «сделаем асинхронно»: поток не освобождается, а занимается ожиданием
public async Task<Order> GetAsync(Guid id, CancellationToken ct)
{
    return await Task.Run(() => _db.Orders.FirstAsync(o => o.Id == id, ct), ct);
}
  • Поток всё равно ждёт. Внутри Task.Run выполняется тот же блокирующий вызов — только теперь он занимает поток пула.
  • Работы становится больше: планирование задачи, переключение потока, аллокация Task-объектов.
  • Пулу не хватает потоков. Каждый такой вызов «съедает» поток на всё время ожидания — это и есть голодание пула, о котором глава 9 .NET-раздела.
  • Отмена становится сложнее: токен нужно пробросить внутрь делегата, иначе операция продолжит выполняться после отмены запроса.

Правильно — асинхронный вызов до конца:

// ✔ никакого лишнего потока: ждём ввод-вывод асинхронно
public Task<Order> GetAsync(Guid id, CancellationToken ct) =>
    _db.Orders.FirstAsync(o => o.Id == id, ct);
Где здесь async и await?

Их нет — и не нужно. Асинхронность создаёт сам источник: FirstAsync возвращает Task<Order>, внутри которого уже работает асинхронный ввод-вывод. Наш метод просто возвращает эту задачу дальше, ничего не дожидаясь.

async/await нужны, когда после ожидания надо что-то сделать:

// без async: «верни задачу как есть»
public Task<Order> GetAsync(...) => _db.Orders.FirstAsync(...);

// с async/await: «дождись, потом обработай результат»
public async Task<decimal> GetTotalAsync(Guid id, CancellationToken ct)
{
    var order = await _db.Orders.FirstAsync(o => o.Id == id, ct);  // ← вот здесь await
    return order.Total * 1.2m;                                     // и работа с результатом
}

Проверка: если метод только возвращает результат другого асинхронного вызова, async/await можно убрать — меньше машины состояний и накладных расходов.

Где Task.Run действительно нужен

  • CPU-bound работа, которую надо увести с текущего потока. Классика — десктоп/UI: поток интерфейса не должен считать, иначе окно «зависает».
  • Параллельные вычисления с ограничением степени параллелизма — но чаще удобнее Parallel.ForEachAsync/Parallel.For (глава 13 .NET-раздела).
  • Стартовая инициализация в консольном/фоновом приложении: запустить тяжёлую работу и продолжить настройку.
  • Смешанный сценарий: синхронная библиотека, у которой нет асинхронного API, но вызвать её нужно из асинхронного кода на клиенте (не в обработчике запроса).
«Запустить и забыть» на сервере — нельзя

_ = Task.Run(() => DoWork()) выглядит безобидно, но: исключения теряются, при перезапуске приложения работа обрывается, отменить её невозможно, а пул может быть перегружен. Для фоновых задач есть BackgroundService/очереди (глава 26 .NET-раздела) и outbox (глава 31).

Task.Run, Task.Factory.StartNew и async void

// ✔ async Task: вызывающий может дождаться и обработать ошибку
public async Task SendAsync(CancellationToken ct) => await _client.PostAsync(…, ct);

Исключения, отмена и ConfigureAwait

  • Исключения из Task.Run попадают в Task и пробрасываются при await. Если задачу никто не ожидает, исключение может остаться незамеченным (TaskScheduler.UnobservedTaskException — только диагностика, не обработка).
  • Отмена: передавайте CancellationToken внутрь делегата и проверяйте его в длинных циклах. Сам по себе токен у Task.Run отменяет только запуск, если задача ещё не начала выполняться.
  • ConfigureAwait(false) — в библиотечном коде: «не возвращайся в исходный контекст». В ASP.NET Core контекста синхронизации нет, поэтому эффекта почти нет, но в библиотеках это правильная привычка.
var results = await Task.Run(() =>
{
    var acc = new List<Report>();
    foreach (var chunk in chunks)
    {
        ct.ThrowIfCancellationRequested();       // отмена по-настоящему работает
        acc.Add(ComputeReport(chunk));           // CPU-bound работа
    }
    return acc;
}, ct);
Откуда здесь chunks

chunks — обычная локальная переменная: список частей, на которые заранее разбили данные. Например, так:

// миллион записей разбили на пачки по 1000 — меньше пиков по памяти
List<Order[]> chunks = allOrders.Chunk(1000).ToList();

var results = await Task.Run(() => { /* … foreach (var chunk in chunks) … */ }, ct);

Смысл примера: тяжёлая обработка каждой пачки уходит в пул потоков, а CancellationToken проверяется между пачками — чтобы отмена срабатывала быстро.

Пример: CPU-bound работа с ограничением параллелизма

Если таких задач много, нельзя запускать их «все сразу»: пул потоков будет перегружен. Ограничивают параллелизм — либо семафором, либо Parallel.ForEachAsync (подробный разбор — глава 13 .NET-раздела):

// не больше 8 тяжёлых вычислений одновременно
await Parallel.ForEachAsync(
    documents,
    new ParallelOptions { MaxDegreeOfParallelism = 8, CancellationToken = ct },
    async (doc, token) =>
    {
        var report = await Task.Run(() => BuildReport(doc), token);
        await SaveAsync(report, token);
    });
★ Что запомнить из главы
  • Task.Run — это работа на потоке пула, а не «асинхронность».
  • Для I/O (await) он вреден: поток занят ожиданием, пул голодает, работы больше.
  • Для CPU-bound — уместен, особенно когда нужно уйти с текущего потока (UI, инициализация).
  • На сервере не бывает «запустил и забыл»: для фона есть BackgroundService, очереди и outbox.
  • async void — только обработчики событий UI; отмена и исключения требуют явной передачи CancellationToken и await.
