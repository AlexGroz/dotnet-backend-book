Глава 4. Кэширование: cache-aside, TTL, инвалидация и stampede

Как кэш ускоряет сервис и как он же ломает данные, если ошибиться с временем жизни

основная глава

Cache-aside: самый частый паттерн

Приложение само решает, что и когда кэшировать: сначала спрашивает Redis, при промахе идёт в PostgreSQL и кладёт результат в Redis. Кэш ничего не знает про базу — он просто хранилище по ключу. CatalogRepository ниже — обычный репозиторий поверх DbContext; IDatabase приходит из DI (глава 2).

public sealed record CatalogItem(int Id, string Title);

public sealed class CatalogCache(IDatabase db, CatalogRepository repo)
{
    public async Task<CatalogItem?> GetAsync(int id)
    {
        var key = $"catalog:v1:{id}";

        var cached = await db.StringGetAsync(key);
        if (cached.HasValue)
            return JsonSerializer.Deserialize<CatalogItem>(cached.ToString());

        var item = await repo.FindAsync(id);              // PostgreSQL
        if (item is null) return null;

        await db.StringSetAsync(key, JsonSerializer.Serialize(item),
            TimeSpan.FromMinutes(5));                     // TTL обязателен
        return item;
    }
}
ШагЧто происходитЕсли Redis недоступен
1. Чтение из кэшаGET catalog:v1:42Идём в БД (кэш — ускоритель, не источник истины)
2. ПромахЗапрос в PostgreSQLРаботает как обычно
3. Запись в кэшSET с TTLПропускаем; следующий запрос снова попробует
TTL — не «на всякий случай», а часть контракта

Ключ без времени жизни остаётся в Redis навсегда: данные устаревают, память заканчивается. TTL — единственная гарантия, что кэш сам себя починит, даже если инвалидация где-то не сработала.

Тот же паттерн через IDistributedCache

Если нужен только кэш «байты по ключу», брать StackExchange.Redis не обязательно: в ASP.NET есть абстракция IDistributedCache, а пакет Microsoft.Extensions.Caching.StackExchangeRedis подключает её к Redis. Реальный вывод:

services.AddStackExchangeRedisCache(o =>
{
    o.Configuration = "localhost:6379";
    o.InstanceName  = "shop:";                  // префикс всех ключей
});

await cache.SetStringAsync("catalog:42", "{\"id\":42}",
    new DistributedCacheEntryOptions { AbsoluteExpirationRelativeToNow = TimeSpan.FromSeconds(5) });

Console.WriteLine(await cache.GetStringAsync("catalog:42"));   // {"id":42}
Console.WriteLine((await cache.GetAsync("catalog:42"))?.Length); // 9
await Task.Delay(5500);
Console.WriteLine($"[{await cache.GetStringAsync("catalog:42")}]"); // []

Две детали, которые видно только в самом Redis:

  • InstanceName — это префикс. В Redis ключ называется shop:catalog:42, а не catalog:42: абстракция добавляет префикс сама, чтобы несколько приложений могли делить один Redis.
  • Промах и истечение — это null, а не исключение; после 5,5 секунд вернулось пустое значение.

SlidingExpiration в тех же настройках продлевает жизнь ключа при каждом чтении (проверено: ключ, записанный с окном 3 секунды, имел в Redis TTL 3), но у него есть цена — «горячий» ключ никогда не истечёт, и устаревшее значение может жить бесконечно, пока его читают.

Инвалидация: что делать при записи

Кэш устаревает не сам по себе, а потому что данные изменились. Три рабочих подхода, от простого к сложному:

  1. Удалить ключ после успешной записи в БД — самое частое. Именно удалить, а не «записать новое значение»: между записью в БД и записью в кэш кто-то успеет прочитать старое и положить его обратно.
  2. Версия в ключе. catalog:v2:42: при смене формата или «полном сбросе» поднимается версия, старые ключи просто перестают читаться и истекают сами.
  3. TTL как страховка. Даже если инвалидация не сработала (сообщение потерялось, код забыл), через N минут кэш вернётся к правде.
Порядок операций важен

Инвалидация выполняется после коммита транзакции в БД. Если удалить ключ до коммита, параллельный читатель успеет положить в кэш старое значение, и оно останется там до истечения TTL.

Чего делать точно не стоит: пытаться «синхронизировать» кэш и БД двумя записями без общей транзакции. Атомарно это не сделать, поэтому правильная стратегия — «кэш может быть устаревшим не дольше TTL».

Промах-шторм (stampede) и как его гасят

Популярный ключ истёк — и сто запросов одновременно идут в базу за одним и тем же. Нагрузка на БД умножается на сто, а кэш заполняется одинаковыми значениями. Лечится «право на прогрев»: только один процесс идёт в БД, остальные ждут.

public async Task<CatalogItem?> GetWithLockAsync(int id)   // в том же классе CatalogCache
{
    var key     = $"catalog:v1:{id}";
    var lockKey = $"lock:{key}";
    var token   = Guid.NewGuid().ToString("N");

    // SET lockKey token NX EX 10 — берёт только один
    if (await db.StringSetAsync(lockKey, token, TimeSpan.FromSeconds(10), When.NotExists))
    {
        try
        {
            var item = await repo.FindAsync(id);          // идём в БД один раз
            if (item is null) return null;

            await db.StringSetAsync(key, JsonSerializer.Serialize(item), TimeSpan.FromMinutes(5));
            return item;
        }
        finally
        {
            // снять лок, только если он всё ещё наш (сравнение значения + удаление)
            await db.ScriptEvaluateAsync(
                "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) end",
                new RedisKey[] { lockKey }, new RedisValue[] { token });
        }
    }

    // лок занят: короткая пауза, затем обычное чтение кэша; не дождались — идём в БД сами
    await Task.Delay(50);
    return await GetAsync(id) ?? await repo.FindAsync(id);
}
  • SET … NX EX — и лок, и его таймаут. Проверено: первый вызов получает True, второй — False. TTL обязателен: упавший процесс не должен держать лок вечно.
  • Снимать лок скриптом, а не DEL. Иначе можно удалить чужой лок, который успел истечь и достаться другому процессу.
  • Ждущие не должны висеть. Пауза с повтором, затем — свой запрос в БД: лучше несколько лишних запросов, чем очередь, которая не движется.

Кэш и запись: три схемы

СхемаКак работаетКогда
Cache-asideПриложение читает кэш, при промахе идёт в БД и заполняет кэшПочти всегда: просто, предсказуемо, БД — источник истины
Write-throughПишем в кэш и в БД в одном сценарииРедко: две системы не commit-ятся вместе, нужна компенсация
Write-behindПишем в кэш, в БД — асинхронноТолько когда потеря записи допустима и есть надёжная очередь

Для типового .NET-сервиса правильный выбор — cache-aside плюс инвалидация после коммита. Write-through и write-behind требуют решения проблемы «двух источников истины», а это уже отдельный проект.

★ Что запомнить из главы
  • Cache-aside: кэш — ускоритель, истина — в PostgreSQL; при недоступном Redis сервис работает медленнее, но работает.
  • TTL обязателен у каждого ключа; sliding-окно продлевает жизнь при чтении, поэтому горячие ключи не истекают никогда.
  • Инвалидация — удалением ключа после коммита; версия в имени ключа даёт бесплатный «полный сброс».
  • Промах-шторм гасят локом SET … NX EX с обязательным TTL и снятием через скрипт.
