Глава 19. Конвейер: middleware и маршрутизация

Путь запроса через приложение; Minimal API против MVC

основная глава

Конвейер: запрос идёт «через слои»

Любой запрос в ASP.NET Core проходит конвейер (pipeline): цепочку компонентов middleware. Каждый компонент может что-то сделать до следующего, вызвать следующий и что-то сделать после.

запрос → [логирование] → [обработка ошибок] → [аутентификация] → [авторизация]
       → [маршрутизация] → [эндпоинт] → и обратно по стеку

Компонент выглядит как функция с «следующим» компонентом внутри:

app.Use(async (context, next) =>
{
    var sw = Stopwatch.StartNew();

    await next();                    // передали управление дальше — вплоть до эндпоинта

    sw.Stop();
    logger.LogInformation("{Path} — {Elapsed} мс", context.Request.Path, sw.ElapsedMilliseconds);
});
  • app.Use(...) — «пропусти дальше» (есть next).
  • app.Run(...) — «терминальный» компонент: дальше не идёт.
  • app.Map(...) — ветка по пути: часть запросов уходит в отдельный конвейер.
  • app.UseMiddleware<T>() — то же, но классом (удобно, когда есть зависимости).

Все четыре формы в одном Program.cs

// 1) Use — «пропусти дальше»: своя работа до и после next
app.Use(async (context, next) =>
{
    Console.WriteLine($"→ {context.Request.Path}");
    await next();                                        // ушли в следующие компоненты
    Console.WriteLine($"← {context.Response.StatusCode}");
});

// 2) UseMiddleware — то же, но классом (когда нужны зависимости из DI)
app.UseMiddleware<CorrelationIdMiddleware>();

// 3) Map — ветка по пути: только /admin уходит в отдельный конвейер
app.Map("/admin", admin =>
{
    admin.UseAuthentication();                           // эти компоненты — только для /admin
    admin.Run(async context =>                           // 4) Run — конец цепочки
        await context.Response.WriteAsync("admin area"));
});

// обычные запросы
app.MapGet("/", () => "hello");

Порядок middleware — это поведение

Обработка ошибок должна стоять раньше остальных, аутентификация — до авторизации, маршрутизация — до эндпоинтов. Переставили две строки — получили «ошибки не логируются» или «проверка прав видит пустого пользователя».

Маршрутизация: как запрос находит обработчик

Маршрутизация сопоставляет метод + шаблон пути с обработчиком. Параметры маршрута извлекаются из пути автоматически:

// GET /orders/42
app.MapGet("/orders/{id:int}", (int id) => Results.Ok(new { id }));

Ограничения (:int, :guid) не только документируют формат, но и позволяют не вызывать обработчик для заведомо неподходящих путей.

Minimal API: что это

Minimal API — это способ объявить эндпоинт прямо в Program.cs, функцией, без контроллеров и без отдельных классов:

var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

app.MapGet("/orders/{id:int}", async (int id, OrdersDb db, CancellationToken ct) =>
{
    var order = await db.Orders.FindAsync(new object[] { id }, ct);
    return order is null ? Results.NotFound() : Results.Ok(order);
});

app.Run();

Зависимости (OrdersDb, CancellationToken) подставляются в параметры автоматически — контейнер и привязка модели работают и здесь. OrdersDb — контекст EF Core (глава 24); для валидации ниже он не нужен.

Контроллеры (MVC): что дают

В MVC эндпоинты описываются классами-контроллерами. У них есть атрибуты и соглашения, которые берут часть работы на себя:

[ApiController]                       // ← включает автоматическую валидацию модели
[Route("api/orders")]
public sealed class OrdersController : ControllerBase
{
    [HttpGet("{id:int}")]
    public async Task<ActionResult<Order>> Get(int id, CancellationToken ct)
    {
        var order = await _db.Orders.FindAsync(new object[] { id }, ct);
        return order is null ? NotFound() : Ok(order);
    }

    [HttpPost]
    public async Task<IActionResult> Create(CreateOrderDto dto, CancellationToken ct)
    {
        // если dto невалиден, [ApiController] уже вернул 400 — сюда управление не дошло
        …
    }
}

Почему в Minimal API нет автоматической проверки модели

Автоматическая валидация — это поведение атрибута [ApiController]: он проверяет ModelState до вызова действия и возвращает 400, если данные не прошли проверки. В Minimal API такого атрибута и такого «действия» нет — обработчик просто вызывается. Значит, проверять нужно явно. Два рабочих способа — оба с полным кодом.

Способ 1: ручная проверка

Правила вешаются атрибутами System.ComponentModel.DataAnnotations — теми же, что понимает [ApiController] в MVC:

public sealed record CreateOrderDto(
    [property: Range(1, int.MaxValue, ErrorMessage = "CustomerId должен быть больше 0")]
    int CustomerId,

    [property: Range(0.01, 1_000_000, ErrorMessage = "Total должен быть положительным")]
    decimal Total,

    [property: Required, MinLength(3, ErrorMessage = "Комментарий не короче 3 символов")]
    string? Comment);

Сам Validate — обычный метод на десять строк: прогоняет атрибуты и складывает ошибки в словарь «поле → сообщения». Формат словаря не случаен: ровно его принимает Results.ValidationProblem. Метод можно держать локальной функцией в Program.cs (как ниже) или в отдельном статическом классе — магии в нём нет.

// using System.ComponentModel.DataAnnotations;

static Dictionary<string, string[]> Validate(object dto)
{
    var results = new List<ValidationResult>();

    // validateAllProperties: true — иначе проверятся только [Required]
    if (Validator.TryValidateObject(dto, new ValidationContext(dto), results, validateAllProperties: true))
        return new Dictionary<string, string[]>();

    return results
        .SelectMany(r => (r.MemberNames.Any() ? r.MemberNames : new[] { "" })
            .Select(member => (Member: member, Message: r.ErrorMessage ?? "неверное значение")))
        .GroupBy(x => x.Member)
        .ToDictionary(g => g.Key, g => g.Select(x => x.Message).ToArray());
}

Эндпоинт: проверили — вернули 400; ошибок нет — идём дальше.

app.MapPost("/orders", (CreateOrderDto dto) =>
{
    var errors = Validate(dto);
    if (errors.Count > 0)
        return Results.ValidationProblem(errors);        // 400 + ошибки по каждому полю

    return Results.Created($"/orders/{dto.CustomerId}", dto);
});

Ограничение DataAnnotations

TryValidateObject проверяет только свойства верхнего уровня: вложенный объект с пустым обязательным полем ошибки не даст (проверено: 0 ошибок). Для вложенных данных либо проверяйте детей отдельно, либо берите FluentValidation — у него есть правила для вложенных объектов (ChildRules).

Способ 2: FluentValidation + эндпоинт-фильтр

Когда правил много и они повторяются на десятке эндпоинтов, валидатор выносят в отдельный класс, а проверку — в фильтр. Нужны пакеты FluentValidation и FluentValidation.DependencyInjectionExtensions.

// using FluentValidation;

public sealed class CreateOrderValidator : AbstractValidator<CreateOrderDto>
{
    public CreateOrderValidator()
    {
        RuleFor(x => x.CustomerId).GreaterThan(0).WithMessage("CustomerId должен быть больше 0");
        RuleFor(x => x.Total).GreaterThan(0).WithMessage("Total должен быть положительным");
    }
}

// один фильтр на все DTO: IValidator<T> приходит из контейнера
public sealed class ValidationFilter<T>(IValidator<T> validator) : IEndpointFilter where T : class
{
    public async ValueTask<object?> InvokeAsync(EndpointFilterInvocationContext ctx,
                                              EndpointFilterDelegate next)
    {
        var dto = ctx.Arguments.OfType<T>().FirstOrDefault();
        if (dto is null) return await next(ctx);

        var result = await validator.ValidateAsync(dto);
        return result.IsValid ? await next(ctx) : Results.ValidationProblem(result.ToDictionary());
    }
}
builder.Services.AddValidatorsFromAssemblyContaining<CreateOrderValidator>();
builder.Services.AddScoped(typeof(ValidationFilter<>));       // открытый generic — под любой T

app.MapPost("/orders", (CreateOrderDto dto) => Results.Ok(dto))
   .AddEndpointFilter<ValidationFilter<CreateOrderDto>>();   // ← вся проверка здесь

Обработчик остаётся в одну строку: невалидный запрос до него не доходит. Ответ тот же по форме — на том же плохом запросе реальный вывод: HTTP 400 и "errors": { "CustomerId": [ … ], "Total": [ … ] }.

Что выбрать:

  • 1–2 правила в одном эндпоинте — ручная проверка: правила рядом с обработчиком, ничего не надо регистрировать;
  • много правил или одни и те же правила на многих эндпоинтах — фильтр: код валидации один, обработчики короткие, валидатор тестируется отдельно.
«Почему нельзя как в контроллерах»

Можно — но это придётся сделать явно. Автоматизм — не свойство Minimal API, а конкретная фича контроллеров. Само правило не меняется: клиенту доверять нельзя, проверки нужны (глава 30).

Что выбрать

  • Minimal API — небольшие сервисы, API из нескольких эндпоинтов, микросервисы.
  • Контроллеры — большая команда, много общих правил: валидация, фильтры, соглашения.
  • Можно смешивать: Minimal API для простых частей, контроллеры — для крупных.
★ Что запомнить из главы
  • Запрос идёт по конвейеру middleware; порядок регистрации = порядок выполнения.
  • Маршрутизация сопоставляет метод и шаблон пути; ограничения (:int) отсекают лишнее.
  • Minimal API — эндпоинты функциями в Program.cs; зависимости подставляются в параметры.
  • Контроллеры дают соглашения и автоматическую валидацию через [ApiController].
  • В Minimal API валидация явная: ручная проверка, FluentValidation или эндпоинт-фильтр.
