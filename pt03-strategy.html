Глава 3. Стратегия: if/switch, который захотел стать интерфейсом

Как перестать править один метод при каждом новом способе оплаты, скидки или расчёта — и почему в C# стратегия почти всегда приходит вместе с DI.

основная глава

Разминка: идея на десяти строках

Забудем пока про DI и большие проекты. Есть два способа посчитать доставку, и мы хотим выбирать способ без if внутри расчёта:

public interface IDeliveryCost          // контракт: «умею посчитать стоимость»
{
    decimal Calculate(decimal weight);
}

public sealed class PickupCost : IDeliveryCost       // самовывоз — бесплатно
{
    public decimal Calculate(decimal weight) => 0m;
}

public sealed class CourierCost : IDeliveryCost      // курьер — 300 ₽ + 50 ₽ за кг
{
    public decimal Calculate(decimal weight) => 300m + 50m * weight;
}

// Потребитель не знает, какой вариант ему дали
static decimal Total(IDeliveryCost cost, decimal weight) => 1000m + cost.Calculate(weight);

Console.WriteLine(Total(new PickupCost(), 2));    // 1000
Console.WriteLine(Total(new CourierCost(), 2));   // 1400

Это и есть стратегия: алгоритм вынесен за интерфейс, а вызывающий код просто выбирает реализацию. Дальше — как это выглядит в реальном проекте, где вариантов десять и они приходят из конфигурации.

Проблема: один метод знает всё

Начинается безобидно: у заказа есть тип клиента, и цена считается по-разному.

public decimal CalculateTotal(Order order, CustomerType type)
{
    if (type == CustomerType.Regular)
        return order.Sum;

    if (type == CustomerType.Vip)
        return order.Sum * 0.9m;

    if (type == CustomerType.Partner)
        return order.Sum * 0.8m + 500m;

    throw new ArgumentOutOfRangeException(nameof(type));
}

Что происходит по мере роста:

  • каждый новый тип клиента — правка этого метода (риск сломать существующие ветки);
  • метод растёт, ветки обрастают условиями («а если партнёр и промокод…»);
  • протестировать одну стратегию нельзя — только весь метод целиком;
  • класс, в котором он живёт, начинает зависеть от всех деталей расчёта.

Это нарушение принципа открытости/закрытости: код открыт для расширения, но закрыт для изменения. Здесь же каждое расширение требует изменения.

Решение: вынести алгоритм за интерфейс

// 1) Контракт: «я умею посчитать итог»
public interface IPricingStrategy
{
    decimal Calculate(Order order);
}

// 2) Реализации: каждая отвечает за один вариант
public sealed class RegularPricing : IPricingStrategy
{
    public decimal Calculate(Order order) => order.Sum;
}

public sealed class VipPricing : IPricingStrategy
{
    public decimal Calculate(Order order) => order.Sum * 0.9m;
}

public sealed class PartnerPricing : IPricingStrategy
{
    public decimal Calculate(Order order) => order.Sum * 0.8m + 500m;
}

Теперь выбор стратегии — отдельная задача, и в .NET она решается контейнером, а не switch в бизнес-коде:

// Регистрация один раз при старте
builder.Services.AddKeyedScoped<IPricingStrategy, RegularPricing>(CustomerType.Regular);
builder.Services.AddKeyedScoped<IPricingStrategy, VipPricing>(CustomerType.Vip);
builder.Services.AddKeyedScoped<IPricingStrategy, PartnerPricing>(CustomerType.Partner);

// Использование: сервис зависит от фабрики ключей, а не от всех стратегий
public sealed class OrderService([FromKeyedServices] Func<CustomerType, IPricingStrategy> resolve)
{
    public decimal GetTotal(Order order, CustomerType type)
        => resolve(type).Calculate(order);
}
Почему в регистрации два типа

AddKeyedScoped<IPricingStrategy, VipPricing>(…) — это правило для контейнера: «на запрос IPricingStrategy с этим ключом создай VipPricing». Первый тип — то, что просят (интерфейс в конструкторе), второй — то, что создают.

Двух типов не избежать: у интерфейса три реализации — «очевидной» не существует, её задаёте вы. Все случаи (несколько интерфейсов у одного класса, несколько реализаций, фабричные делегаты, открытые дженерики, TryAdd) разобраны в книге «Backend на .NET», глава 15.

Разбираем строку resolve(type).Calculate(order)
  • Func<CustomerType, IPricingStrategy> — это делегат: «функция, которая принимает CustomerType и возвращает IPricingStrategy». Не коллекция и не интерфейс — тип-функция.
  • resolve — имя параметра конструктора (можно назвать иначе). Контейнер подставляет сюда функцию, которая по ключу достаёт нужную стратегию.
  • resolve(type) — вызов этой функции: «дай мне стратегию для type». Результат — объект IPricingStrategy.
  • .Calculate(order) — вызов метода уже у стратегии: «посчитай по этому заказу».
resolve(CustomerType.Vip) → объект VipPricing → .Calculate(order) → decimal
         ▲                        ▲                      ▲
    «дай стратегию»        «вот она»            «посчитай заказ»

Без DI то же самое писали бы так: var strategy = type switch { … }; strategy.Calculate(order); — только выбор остался бы в бизнес-коде.

Что изменилось
  • Новый тип клиента = новый класс + одна строка регистрации. Существующий код не трогаем.
  • Тесты: каждая стратегия проверяется отдельно, без базы и без остальных ветвей.
  • Ответственность: расчёт цены перестал быть «одним большим методом» в сервисе заказов.

Где стратегия уже работает в .NET

Это и есть проверяемый факт «стратегия используется постоянно»: перечисленные интерфейсы — часть платформы, и приложение подставляет в них свои реализации, даже не называя это паттерном.

Статистика: насколько часто

Оценка: присутствует примерно в 90 % .NET-проектов и занимает ~30 % от всех применений паттернов (если принять сумму за 100 %).

  • Факт, который объясняет цифру: стратегия встроена в платформу — IComparer<T>, IEqualityComparer<T>, IOutputFormatter, ILoggerProvider. Вы используете её в любом проекте, где сортируете или настраиваете сериализацию.
  • Почему доля такая высокая: в C# стратегия — самый дешёвый паттерн: интерфейс и регистрация в DI. Она появляется даже без осознанного решения «применим паттерн».
  • Оговорка: это оценка пропорции, а не измерение (см. главу 1).

Когда стратегия не нужна

  • Вариантов два и они не изменятся. if (isVip) в одном месте читается лучше, чем интерфейс, два класса, регистрация и резолвер.
  • Логика — одна строка. Func<Order, decimal> в параметре метода решает задачу без создания иерархии.
  • Выбор зависит от данных, которых у сервиса нет. Тогда это уже не стратегия, а правило домена — ему место в доменной модели, а не в DI.

Как не путать с соседними паттернами

Кто отвечает за «что делать»Кто создаёт объекты
СтратегияВыбранная реализация алгоритмаКто-то снаружи (DI)
ФабрикаВызывающий кодФабрика (глава 3)
ДекораторОбёрнутая реализация + дополнительное поведениеКто-то снаружи (глава 4)
★ Что запомнить из главы
  • Стратегия заменяет разрастающийся if/switch по варианту набором реализаций одного интерфейса.
  • Выбор стратегии — отдельная ответственность: DI, ключевые сервисы, фабрика; не switch внутри бизнес-логики.
  • Признак, что паттерн оправдан: новый вариант требует правки существующего кода и мешает тестам.
  • В .NET стратегия — почти всегда интерфейс + DI; для простых случаев хватает делегата.
  • Оценка: ~90 % проектов, ~30 % от всех использований паттернов.
