Глава 10. Общие данные и синхронизация

Потоки делят память. Это значит, что два потока могут менять одни и те же данные — и получать непредсказуемый результат. Разберёмся, как с этим быть.

Гонка (race condition)

Операция, которая «выглядит одной», на самом деле состоит из шагов: прочитать значение, изменить, записать обратно. Если два потока делают это одновременно, изменения теряются.

Пример: увеличение общего счётчика из нескольких потоков

private int _counter;                  // общий счётчик (один на все потоки)

public void Increment()                // метод «увеличить на 1»
{
    _counter = _counter + 1;           // то же самое, что _counter++
}
Две вещи, которые нужно понимать в этом коде
  • _counter++ — оператор «инкремент», то есть «увеличить на единицу». Это сокращение от _counter = _counter + 1. Выглядит как одно действие, но внутри это три шага: прочитать значение, прибавить единицу, записать обратно. Именно поэтому два потока и могут «затереть» результат друг друга.
  • => — «лямбда-стрелка». В записи public void Increment() => _counter++; она означает «тело метода — это одно выражение»: сокращённая форма вместо { _counter++; }. Можно писать и полностью — смысл не изменится.

Ошибка коварна тем, что проявляется не всегда: под нагрузкой и на многоядерной машине — чаще, а на тестах и одном ядре может «работать».

Инструменты синхронизации

ИнструментДля чего
lockЗащитить короткий участок кода, чтобы в него входил только один поток
InterlockedАтомарные простые операции над числом/ссылкой, без блокировки
SemaphoreSlimОграничить число одновременных операций; умеет ждать асинхронно
Concurrent*-коллекцииПотокобезопасные словари/очереди и т. п.

Две альтернативы для одной задачи: безопасно увеличить счётчик

// Вариант 1. Блокировка: в участок входит только один поток
private readonly object _gate = new();
private int _counter;

public void IncrementWithLock()
{
    lock (_gate) { _counter++; }
}

// Вариант 2. Атомарная операция: без блокировки и быстрее
private int _counter2;

public void IncrementAtomic()
{
    Interlocked.Increment(ref _counter2);
}
Это альтернативы, а не «делать и то, и другое»

Оба варианта решают одну задачу — защищают _counter++ от гонки. Разница только в способе:

  • lock — универсальный: внутрь блока можно положить любой код (несколько строк, несколько переменных).
  • Interlocked — только для одной простой операции над значением (увеличить, заменить, сравнить и заменить). Зато без блокировки и без ожидания — поэтому быстрее.

В реальном коде берут что-то одно, по ситуации. Оба примера показаны рядом только чтобы было видно: это два решения одной проблемы.

Что такое ref

Обычно аргументы передаются по значению: метод получает копию числа, и оригинал изменить не может.

void PlusOne(int x) { x = x + 1; }   // изменится только копия

int a = 5;
PlusOne(a);
Console.WriteLine(a);   // 5 — оригинал не изменился

ref передаёт саму переменную (по ссылке), а не копию:

void PlusOneRef(ref int x) { x = x + 1; }  // меняем оригинал

int b = 5;
PlusOneRef(ref b);
Console.WriteLine(b);   // 6 — оригинал изменился

Поэтому Interlocked.Increment и требует ref: ему нужно изменить исходную переменную, а не её копию.

Родственные ключевые слова: out — «вернуть» значение наружу (int.TryParse(s, out var v)); in — передать по ссылке только для чтения (экономит копирование больших struct). Подробнее — в главе 5.

Потокобезопасные коллекции — на примере ConcurrentDictionary

private static readonly ConcurrentDictionary<int, User> _cache = new();

// атомарно «получить или добавить» — гонки не будет
var user = _cache.GetOrAdd(id, key => LoadUser(key));

// атомарно увеличить значение по ключу
_cache.AddOrUpdate(hits, 1, (key, old) => old + 1);

// безопасно «прочитать и убрать»
if (_cache.TryRemove(id, out var removed))
{
    Log(removed);
}

Другие примеры таких коллекций: ConcurrentQueue<T>, ConcurrentBag<T>, ConcurrentStack<T>. Они безопасны для нескольких потоков «из коробки» — в отличие от обычных Dictionary и List, которые при одновременной записи могут «побиться».

Важная оговорка

Потокобезопасна одна операция (GetOrAdd, AddOrUpdate). А вот последовательность из нескольких операций может перемешаться — для неё нужна блокировка.

Правила работы с блокировками

  • Держать блокировку коротко. Чем дольше она удерживается, тем больше потоков ждут.
  • Не делать ввод-вывод под блокировкой. Запрос в БД под lock — все остальные потоки замерли.
  • Нельзя await внутри lock. Язык это запрещает — и не зря: ожидание внутри блокировки остановило бы весь процесс.
Если нужно «ждать» внутри защиты

Для асинхронных сценариев используют SemaphoreSlim с WaitAsync — он умеет освобождать поток на время ожидания. Это тот же SemaphoreSlim, которым мы будем ограничивать параллелизм в главе 13.

Лучшая синхронизация — её отсутствие

Самая быстрая блокировка — та, которой нет. Поэтому хороший приём — иммутабельные (неизменяемые) данные: если объект нельзя изменить, то и делить между потоками безопасно. Также помогают локальные данные и передача копий вместо общей изменяемой структуры.

★ Что запомнить из главы

Потоки делят память → возможны гонки. Защищайтесь lock, Interlocked, SemaphoreSlim или конкурентными коллекциями. Блокировку держите коротко и никогда не ждите под ней ввода-вывода. А ещё синхронизация нужна потому, что потоки ждут — об этом в следующей главе.
