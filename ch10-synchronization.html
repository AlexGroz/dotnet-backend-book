Глава 10. Общие данные и синхронизация

Потоки делят память. Это значит, что два потока могут менять одни и те же данные — и получать непредсказуемый результат. Разберёмся, как с этим быть.

Гонка (race condition)

Операция, которая «выглядит одной», на самом деле состоит из шагов: прочитать значение, изменить, записать обратно. Если два потока делают это одновременно, изменения теряются.

Пример: увеличение общего счётчика из нескольких потоков

private int _counter;                  // общий счётчик (один на все потоки)

public void Increment()                // метод «увеличить на 1»
{
    _counter = _counter + 1;           // то же самое, что _counter++
}

// тот же метод, записанный через «лямбда-стрелку» => :
public void IncrementShort() => _counter++;
Две вещи, которые нужно понимать в этом коде
  • _counter++ — оператор «инкремент», то есть «увеличить на единицу». Это сокращение от _counter = _counter + 1. Выглядит как одно действие, но внутри это три шага: прочитать значение, прибавить единицу, записать обратно. Именно поэтому два потока и могут «затереть» результат друг друга.
  • => — «стрелка». В объявлении метода public void IncrementShort() => _counter++; она означает «тело метода — это одно выражение»: сокращённая запись вместо { _counter++; } (по-английски expression body). Можно писать и полностью — смысл не изменится. Это не лямбда: тот же символ в x => x + 1, переданном аргументом, — уже лямбда, потому что там => создаёт значение (делегат), а в объявлении метода — просто короткую форму тела (подробнее — «C#: язык и типы», глава 16).

Ошибка коварна тем, что проявляется не всегда: под нагрузкой и на многоядерной машине — чаще, а на тестах и одном ядре может «работать».

Инструменты синхронизации

ИнструментДля чего
lockЗащитить короткий участок кода, чтобы в него входил только один поток
InterlockedАтомарные простые операции над числом/ссылкой, без блокировки
SemaphoreSlimОграничить число одновременных операций; умеет ждать асинхронно

Две альтернативы для одной задачи: безопасно увеличить счётчик

// Вариант 1. Блокировка: в участок входит только один поток
private readonly object _gate = new();
private int _counter;

public void IncrementWithLock()
{
    lock (_gate) { _counter++; }
}

// Вариант 2. Атомарная операция: без блокировки и быстрее
private int _counter2;

public void IncrementAtomic()
{
    Interlocked.Increment(ref _counter2);
}
Это альтернативы, а не «делать и то, и другое»

Оба варианта решают одну задачу — защищают _counter++ от гонки. Разница только в способе:

  • lock — универсальный: внутрь блока можно положить любой код (несколько строк, несколько переменных).
  • Interlocked — только для одной простой операции над значением (увеличить, заменить, сравнить и заменить). Зато без блокировки и без ожидания — поэтому быстрее.

В реальном коде берут что-то одно, по ситуации. Оба примера показаны рядом только чтобы было видно: это два решения одной проблемы.

Почему _gate, а не сам _counter

Первое, что хочется написать, — lock (_counter). Так не скомпилируется:

error CS0185: 'int' is not a reference type as required by the lock statement

lock держится за объект (у каждого объекта в заголовке есть «флаг занятости»), а int — значение, а не объект. Но дело не только в типах: даже если бы счётчик был ссылочного типа, блокировать его самого всё равно нельзя.

  • Объект блокировки должен быть отдельным. private readonly object _gate — только для lock, никуда не передаётся. Тогда никто снаружи не сможет захватить тот же объект и подвесить ваш код.
  • Не блокируйтесь на this, typeof(T) и строках. ReferenceEquals("gate", "gate") даёт True: строковые литералы и объекты Type существуют в единственном экземпляре на весь процесс, так что «своя» блокировка окажется общей с чужим кодом.
  • Не блокируйтесь на том, что меняется. lock защищает конкретный объект: если поле заменить на другой объект, два потока будут держаться за разные — и гонка вернётся.

Для счётчика блокировка вообще не обязательна: Interlocked делает то же без неё (вариант 2 выше). А lock нужен, когда под защитой несколько строк или несколько переменных.

Что такое ref

Обычно аргументы передаются по значению: метод получает копию числа, и оригинал изменить не может.

void PlusOne(int x) { x = x + 1; }   // изменится только копия

int a = 5;
PlusOne(a);
Console.WriteLine(a);   // 5 — оригинал не изменился

ref передаёт саму переменную (по ссылке), а не копию:

void PlusOneRef(ref int x) { x = x + 1; }  // меняем оригинал

int b = 5;
PlusOneRef(ref b);
Console.WriteLine(b);   // 6 — оригинал изменился

Поэтому Interlocked.Increment и требует ref: ему нужно изменить исходную переменную, а не её копию.

Родственные ключевые слова: out — «вернуть» значение наружу (int.TryParse(s, out var v)); in — передать по ссылке только для чтения (экономит копирование больших struct). Подробнее — в главе 5.

Потокобезопасные коллекции — на примере ConcurrentDictionary

private static readonly ConcurrentDictionary<int, User> _cache = new();

// атомарно «получить или добавить» — гонки не будет
var user = _cache.GetOrAdd(id, key => LoadUser(key));

// атомарно увеличить значение по ключу
_cache.AddOrUpdate(hits, 1, (key, old) => old + 1);

// безопасно «прочитать и убрать»
if (_cache.TryRemove(id, out var removed))
{
    Log(removed);
}

Другие примеры таких коллекций: ConcurrentQueue<T>, ConcurrentBag<T>, ConcurrentStack<T>. Они безопасны для нескольких потоков «из коробки» — в отличие от обычных Dictionary и List, которые при одновременной записи могут «побиться».

Важная оговорка

Потокобезопасна одна операция (GetOrAdd, AddOrUpdate). А вот последовательность из нескольких операций может перемешаться — для неё нужна блокировка.

Правила работы с блокировками

  • Держать блокировку коротко. Чем дольше она удерживается, тем больше потоков ждут.
  • Не делать ввод-вывод под блокировкой. Запрос в БД под lock — все остальные потоки замерли.
  • Нельзя await внутри lock. Язык это запрещает — и не зря: ожидание внутри блокировки остановило бы весь процесс.
  • Объект блокировки — private readonly object. Не this, не typeof(T), не строка и не поле, которое меняется (подробнее — блок выше).

Почему await внутри lock запрещён — и что будет, если обойти

Запрет из списка выше — не стилистика. lock компилируется в Monitor.Enter/Monitor.Exit, а Monitor привязан к потоку: выйти из блокировки обязан тот самый поток, который в неё вошёл. Компилятор это знает, поэтому await внутри lock — ошибка компиляции (проверено):

error CS1996: Cannot await in the body of a lock statement

Причина в том, что await — это «отпусти поток и продолжи позже», а «позже» может случиться на другом потоке. Тогда либо Exit вызовет чужой поток (а он не имеет права), либо блокировка провисит всё время ожидания — секунды и минуты, если ждём сеть.

Обход №1: Monitor вручную. Он компилируется — и иногда даже «работает»:

// ✘ компилируется, но нарушает инвариант Monitor
Monitor.Enter(gate);
try
{
    await Task.Delay(30).ConfigureAwait(false);   // продолжится, возможно, на другом потоке
}
finally
{
    Monitor.Exit(gate);                          // а выходить обязан тот же поток
}

Прогон этого метода 20 раз подряд на .NET 8 дал SynchronizationLockException в 5–7 случаях из 20 — от запуска к запуску по-разному, потому что всё зависит от того, вернётся ли продолжение на прежний поток:

SynchronizationLockException: Object synchronization method was called from an unsynchronized block of code.

«Иногда работает» — худший вид бага: тесты зелёные, прод падает раз в час.

Обход №2: подождать синхронно. Самая частая попытка — оставить lock и добавить .Result/.Wait():

// ✘ поток держит блокировку и при этом заблокирован
lock (gate)
{
    order = LoadOrderAsync(id).GetAwaiter().GetResult();
}

Здесь две беды сразу. Первая: пока поток ждёт, блокировка занята — все остальные стоят в очереди, то есть вся работа стала последовательной. Вторая — настоящая причина «голодания» из главы 9: продолжению ожидаемой операции нужен поток пула, а все потоки заняты такими же ожиданиями. Задаче негде завершиться, и код не двигается вообще.

Замер на маленьком пуле (4 потока — как в контейнере с 4 vCPU, ограничение задано ThreadPool.SetMaxThreads(4, 4)), 8 задач по 30 мс «работы»:

пул: max=4, SetMaxThreads=True, ProcessorCount=4

lock { Task.Delay(30).Wait(); }              → завершилось 0 из 8 за 5000 мс — клинч
await sem.WaitAsync(); await Task.Delay(30); → завершилось 8 из 8 за  249 мс

Во втором случае потоков в пуле тоже четыре — но ни один не занят ожиданием: await вернул поток в пул, пока таймер тикает. Это и есть разница между «ждать потоком» и «ждать асинхронно».

В проде то же самое видно по числам: ThreadPool.ThreadCount упирается в предел, очередь пула (ThreadPool.PendingWorkItemCount) растёт, а latency запросов ползёт вверх при низком CPU. Если видите эту картину — ищите в коде lock с ожиданием внутри, .Result, .Wait() или Task.Run(...).Wait().

Правило

Под lock — только короткий синхронный код: без ввода-вывода, без await, без .Result/.Wait(). Если внутри критической секции нужно ждать — это уже не lock, а SemaphoreSlim.

Чем заменить: SemaphoreSlim(1, 1) и System.Threading.Lock

Если внутри критической секции нужно ждать — берут SemaphoreSlim с WaitAsync. Это тот же SemaphoreSlim, которым мы будем ограничивать параллелизм в главе 13; здесь у него счётчик 1, то есть «пускать по одному»:

private readonly SemaphoreSlim _gate = new(1, 1);   // один «пропуск»

public async Task<Order> LoadAsync(Guid id, CancellationToken ct)
{
    await _gate.WaitAsync(ct);                      // ждём БЕЗ потока
    try
    {
        return await _db.Orders.FirstAsync(o => o.Id == id, ct);   // await внутри — можно
    }
    finally
    {
        _gate.Release();                            // освобождать обязательно, иначе клинч
    }
}

Три отличия от lock, о которых спрашивают (все проверены на .NET 8):

  • Не привязан к потоку. Именно поэтому await внутри допустим: вошёл один поток, а Release может вызвать уже другой (проверено — исключения нет).
  • Нет реентерабельности. lock тем же потоком берётся повторно, а SemaphoreSlim(1, 1) на повторный WaitAsync просто зависнет: в прогоне WaitAsync(300) вернул False, то есть «не дождался».
  • Дороже. Вход — это операции над счётчиком и очередью ожидающих, а не флаг в заголовке объекта. Замер: 20 млн входов в одном потоке — lock 235 мс, SemaphoreSlim 494 мс (≈2 раза медленнее).

В .NET 9 появился третий вариант — System.Threading.Lock. Это только синхронная блокировка (await внутри по-прежнему нельзя — тот же CS1996, проверено), но устроена она легче, чем Monitor:

private readonly Lock _gate = new();          // System.Threading.Lock, .NET 9+

public void Apply(Discount d)
{
    lock (_gate)                              // C# 13 разворачивает это в EnterScope()
    {
        _total -= d.Amount;
    }

    // то же самое явно, если нужен using-блок:
    using (_gate.EnterScope())
    {
        _total -= d.Amount;
    }
}

Что здесь именно измерено на .NET 9.0.23 (16 ядер), а не пересказано из блогов:

  • lock на Lock — это EnterScope, а не Monitor. Пока один поток держит lock (_gate), ручной _gate.TryEnter() из другого возвращает False. Если бы компилятор использовал Monitor, это была бы другая блокировка и TryEnter бы прошёл.
  • Выигрыш скромный и виден под конкуренцией. 20 млн входов в одном потоке: Monitor 235 мс, Lock 242 мс — разницы нет. Четыре потока по 2 млн инкрементов: Monitor 894 мс, Lock 802 мс — около 10 %.
  • Возможности те же, ограничения те же: только синхронный код, привязка к потоку, реентерабельность. «Асинхронным» Lock не стал.

  • Один Release на каждый успешный WaitAsync, и в finally. Забыли — очередь встанет навсегда; лишний — SemaphoreFullException: Adding the specified count to the semaphore would cause it to exceed its maximum count. (проверено).
  • Не ждите без токена. Передавайте CancellationToken в WaitAsync(ct): иначе при остановке приложения или таймауте запрос останется в очереди навсегда (глава 28 — про остановку).

Лучшая синхронизация — её отсутствие

Самая быстрая блокировка — та, которой нет. Поэтому хороший приём — иммутабельные (неизменяемые) данные: если объект нельзя изменить, то и делить между потоками безопасно. Также помогают локальные данные и передача копий вместо общей изменяемой структуры.

★ Что запомнить из главы

Потоки делят память → возможны гонки. Защищайтесь lock, Interlocked, SemaphoreSlim или конкурентными коллекциями. Блокировку держите коротко и никогда не ждите под ней ввода-вывода. Если ждать всё-таки нужно — это SemaphoreSlim(1, 1) с WaitAsync, а не lock: await внутри lock — CS1996, а «обходы» дают SynchronizationLockException (Monitor через await) или клинч пула (.Wait()/.Result под блокировкой). В .NET 9 System.Threading.Lock заменяет lock на object, но остаётся синхронным. А ещё синхронизация нужна потому, что потоки ждут — об этом в следующей главе.
