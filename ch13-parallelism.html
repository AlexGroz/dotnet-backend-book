Глава 13. Параллелизм с ограничениями и потоковая обработка

Мы умеем не блокировать поток (глава 12). Теперь — как запускать несколько операций сразу и почему это обязательно ограничивать.

Независимые операции — параллельно

Если два обращения к БД независимы, нет смысла ждать их по очереди. Их запускают вместе и ждут оба:

// ✘ последовательно: 2 × 100 мс = 200 мс
var a = await GetAAsync(ct);
var b = await GetBAsync(ct);

// ✔ параллельно: ~100 мс
var ta = GetAAsync(ct);
var tb = GetBAsync(ct);
await Task.WhenAll(ta, tb);

Task.WhenAll подходит для небольшого фиксированного набора операций — двух-пяти. Для длинных списков он опасен (см. ниже).

Почему веер запросов обязательно ограничивать

Соблазнительно написать «запустить всё сразу» на тысячу элементов. Но ресурсы конечны:

  • пул соединений к БД — их десятки, а не тысячи (глава 22 книги SQL);
  • потоки пула — их нельзя плодить бесконечно (глава 9);
  • сеть и внешние сервисы — у них свои лимиты.

Если запросов больше, чем «мест», остальные встают в очередь, задержка растёт, а дальше начинаются таймауты. Это называется отсутствием обратного давления (backpressure).

Ограничение параллелизма

Вариант 1: SemaphoreSlim

private static readonly SemaphoreSlim Gate = new(initialCount: 8);

await Gate.WaitAsync(ct);
try   { await ProcessOneAsync(id, ct); }
finally { Gate.Release(); }

Вариант 2 (.NET 6+): Parallel.ForEachAsync — встроенный лимит

await Parallel.ForEachAsync(
    ids,
    new ParallelOptions { MaxDegreeOfParallelism = 8, CancellationToken = ct },
    async (id, token) => await ProcessOneAsync(id, token));
Что означают все части этих примеров

Задача. Есть коллекция ids — например, идентификаторы заказов, которые надо обработать. Обработка одной штуки вынесена в ProcessOneAsync(id, ct): в реальном коде это «сходить в базу», «вызвать внешний сервис», «отправить письмо». Это не метод из .NET — просто имя-заглушка для вашей операции.

Зачем лимит. Если элементов тысяча, а в пуле 20 соединений, то 980 будут ждать и всё кончится таймаутами. Лимит параллелизма — это «не больше N одновременно».

Вариант 1, SemaphoreSlim:

  • new SemaphoreSlim(initialCount: 8) — семафор с 8 разрешениями («пропусками»). initialCount — сколько одновременных входов разрешено.
  • await Gate.WaitAsync(ct) — «возьми пропуск». Если все 8 заняты, вызов ждёт асинхронно (поток не блокируется).
  • try/finally + Gate.Release() — «верни пропуск» всегда, даже при исключении. Забыли вернуть — пропусков стало меньше, и со временем ждут все.
  • Почему 8? Не магическое число, а выбранный лимит: сколько операций пускать одновременно (например, по числу соединений в пуле).

Вариант 2, Parallel.ForEachAsync:

  • ids — что перебираем.
  • new ParallelOptions { MaxDegreeOfParallelism = 8, CancellationToken = ct } — «не больше 8 обработок одновременно» и токен отмены.
  • async (id, token) => … — тело цикла: текущий элемент и токен; внутри — ваша операция.
  • В отличие от семафора, «пропуск» вручную не берут: ForEachAsync сам держит лимит и дожидается завершения всех задач.
Что именно ограничивается (частая путаница)

Семафор не «блокирует ProcessOneAsync» и не «занимает id». Он ограничивает участок кода между WaitAsync и Release — критическую секцию. Внутри неё одновременно находятся не больше 8 элементов, а 9-й даже не начнёт работу: он ждёт на WaitAsync, до вызова ProcessOneAsync дело не доходит.

Пропуск берётся один раз на элемент и возвращается в finally, когда операция завершилась. Токен ct в WaitAsync — это только «выйти из очереди, если отменили».

Проверим: 12 операций по 60 мс, лимит 3 (в логе +id — начал, -id — закончил)

var ids = Enumerable.Range(1, 12);
var ct = CancellationToken.None;

using var gate = new SemaphoreSlim(3);
var log = new List<string>();

await Task.WhenAll(ids.Select(async id =>
{
    await gate.WaitAsync(ct);
    try
    {
        lock (log) log.Add("+" + id);
        await Task.Delay(60, ct);              // «работа»: сходить в БД, вызвать сервис
        lock (log) log.Add("-" + id);
    }
    finally { gate.Release(); }                // пропуск вернули — входит следующий
}));

Вывод

первые 10 событий: +1 +2 +3 -3 -2 +4 +5 -1 +6 -6
максимум одновременно: 3, время: 247 мс

Читается по логу так: начали 1, 2, 3 — и только когда двое освободили пропуска (-3 -2), пошли +4 +5. Порядок событий от запуска к запуску меняется (потоки соревнуются), а вот максимум одновременно — всегда 3. Поэтому 12 операций по 60 мс заняли ~240 мс (12 × 60 / 3), а не 60 мс.

Вариант 2 на тех же данных: лимит внутри Parallel.ForEachAsync

// ids, ct и log — из блока выше
await Parallel.ForEachAsync(ids,
    new ParallelOptions { MaxDegreeOfParallelism = 3, CancellationToken = ct },
    async (id, token) =>
    {
        lock (log) log.Add("+" + id);
        await Task.Delay(60, token);
        lock (log) log.Add("-" + id);
    });                                        // вернётся, когда обработаны ВСЕ элементы

Вывод

первые 10 событий: +1 +2 +3 -1 -2 +4 +5 -3 +6 -6
максимум одновременно: 3, время: 247 мс

Ограничение то же самое — «не больше трёх тел цикла одновременно». Разница в том, что пропусками управляет сам ForEachAsync, а исключение из любого элемента останавливает остальные (в прогоне на 20 элементах, где пятый бросал исключение, успели начаться только 6) и выходит наружу исходным исключением, а не AggregateException.

А теперь без лимита — все 12 сразу

максимум одновременно: 12, время: 62 мс

Для 12 операций это нормально, для 1000 — нет: см. начало главы (пул соединений, потоки, таймауты).

Потоковая обработка: IAsyncEnumerable

Если результат большой, не нужно грузить его целиком в память — можно отдавать по мере чтения:

public async IAsyncEnumerable<OrderDto> StreamAsync(
    [EnumeratorCancellation] CancellationToken ct)
{
    await foreach (var o in _db.Orders.AsNoTracking()
                       .Select(x => new OrderDto(x.Id, x.Total))
                       .AsAsyncEnumerable()
                       .WithCancellation(ct))
    {
        yield return o;   // отдаём по мере чтения, память O(1)
    }
}
Как это устроено: запрос один, но всех строк в памяти нет

Разница с ToListAsync() в том, что материализуется. Обычный запрос выполняется и складывает все строки в список. Потоковый выполняется один раз и читает строки по мере надобности:

  • AsAsyncEnumerable() не делает второй запрос — SQL тот же самый;
  • по сети данные идут порциями: драйвер читает пакет строк (десятки килобайт), отдаёт их по одной, и разобранные строки дальше уже не нужны;
  • в памяти одновременно — текущая строка плюс буфер драйвера, а не весь результат.

Замер на EF Core 8 + SQLite: 300 000 строк, файл базы 12 МБ.

Способ чтенияSQL-командПик памятиВремя
ToListAsync()1+13 МБ1156 мс
AsAsyncEnumerable()1+1 МБ249 мс

Команда одна и там, и там — «поток» не означает «много запросов». А быстрее потому, что 300 000 элементов в списке — это и память, и работа для GC; на реальной базе добавляется ещё и то, что клиент получает первые строки, не дожидаясь конца выборки.

Тот же приём — чтобы отдать данные из базы в HTTP-ответ, не собирая их в память. ASP.NET Core умеет сериализовать IAsyncEnumerable<T> потоком: клиент получает строки по мере их чтения из PostgreSQL.

[HttpGet("orders/export")]
public IAsyncEnumerable<OrderDto> Export(
    [FromQuery] DateOnly day,
    CancellationToken ct)                      // отмена придёт, если клиент отключится
    => _db.Orders
          .AsNoTracking()                      // ничего не отслеживаем: читаем и отдаём
          .Where(o => o.CreatedAt >= day.ToDateTime(TimeOnly.MinValue, DateTimeKind.Utc)
                   && o.CreatedAt <  day.AddDays(1).ToDateTime(TimeOnly.MinValue, DateTimeKind.Utc))
          .Select(o => new OrderDto(o.Id, o.Total))
          .AsAsyncEnumerable()                 // ← поток из БД, без ToListAsync()
          .WithCancellation(ct);
Что происходит по шагам в Export
  1. ASP.NET Core вызывает метод и получает IAsyncEnumerable — запрос ещё не выполнен.
  2. Сериализатор начинает обход: первый MoveNextAsync отправляет SQL в PostgreSQL.
  3. Драйвер отдаёт строки порциями; каждая строка превращается в OrderDto и сразу пишется в ответ (в выходной буфер Kestrel, откуда уходит в сокет). Поэтому память и держится на уровне «строка + буфер», а не «весь ответ».
  4. Обход закончился — соединение с базой освобождается.

Отсюда цена: соединение занято всё время отдачи. Медленный клиент держит и соединение, и открытую транзакцию чтения, поэтому большие выгрузки делят на страницы (keyset-пагинация: WHERE (CreatedAt, Id) > (@last, @lastId)) или пишут CSV в PipeWriter.

  • Что убивает поток: ToListAsync() в середине цепочки; ручная сборка JSON в строку; буферизация на прокси (в nginx — proxy_buffering on) и в самом ответе (HttpResponse.Body копится, если включена буферизация).
  • Время жизни DbContext: перечисление ленивое, поэтому контекст должен жить, пока идёт отдача. В контроллере это норма (scope = время запроса), а вот вернуть такой IAsyncEnumerable из фоновой задачи «наружу» нельзя — получите ObjectDisposedException.
  • Ошибка в середине потока: заголовки уже отправлены, код ответа изменить нельзя — клиент увидит обрыв соединения, а не 500. Поэтому параметры проверяйте до первого yield, а обрыв логируйте.
  • Для больших выгрузок (CSV, лог) берите Response.BodyWriter или PipeWriter и пишите вручную — JSON для гигабайтных выгрузок не нужен вовсе.
  • Отмена работает вся цепочка: клиент ушёл → WithCancellation(ct) → Npgsql отменяет запрос на сервере (а не просто перестаёт читать).
«А если запросов не один, а много?»

Количество запросов задаёт сама цепочка LINQ, а не способ чтения. Один Select(...).AsAsyncEnumerable() — один SQL, сколько бы строк он ни вернул.

Но IAsyncEnumerable — не кэш, а «фабрика»: каждый новый обход выполняет запрос заново.

async IAsyncEnumerable<int> Rows()
{
    queries++;
    Console.WriteLine($"  [БД]  запрос №{queries} выполнен");
    for (var i = 1; i <= 3; i++)
    {
        Console.WriteLine($"  [БД]  строка {i} прочитана");
        yield return i;
    }
}

await foreach (var r in Rows()) Console.WriteLine($"  [код] получил {r}");
await foreach (var r in Rows()) { }          // ← это ВТОРОЙ запрос к базе

Вывод

  [БД]  запрос №1 выполнен
  [БД]  строка 1 прочитана
  [код] получил 1
  [БД]  строка 2 прочитана
  [код] получил 2
  [БД]  строка 3 прочитана
  [код] получил 3
  [БД]  запрос №2 выполнен
  [БД]  строка 1 прочитана
  [БД]  строка 2 прочитана
  [БД]  строка 3 прочитана
запросов после 2-го обхода: 2

Видно и главное достоинство (строки приходят по одной, работа чередуется с чтением), и ловушку: перечислять такой поток нужно один раз — не «сохранить в переменную на потом» и не обходить дважды.

Много запросов появляется в другом месте — когда внутри обхода дёргают навигационное свойство (N+1: одна строка — один запрос). Лечится Include/Select в том же запросе, и тогда «много» не будет.

★ Что запомнить

Распараллеливать стоит только независимые операции, и всегда с ограничением. Это и есть backpressure: лучше подождать в очереди на входе, чем обрушить пул соединений и получить каскадные таймауты.
