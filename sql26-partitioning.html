Глава 26. Секционирование таблиц: Range, List, Hash и pruning

Что делать, когда таблица стала слишком большой: как разделить её на части так, чтобы запросы читали нужную часть, а старые данные уходили одним движением.

основная глава

Когда таблица «слишком большая»

Размер сам по себе не проблема — проблема в том, что с ним становится тяжело делать четыре вещи:

  • читается больше страниц, чем нужно: индексы глубже, кэш работает хуже;
  • обслуживание (VACUUM, ANALYZE, REINDEX) занимает часы и добавляет нагрузку;
  • удаление старых данных превращается в миллионы DELETE и миллионы мёртвых версий (глава 25);
  • архивирование и перенос части данных требуют полной копии таблицы.

Секционирование решает это, разбивая одну логическую таблицу на много физических — секций. Приложение продолжает писать SELECT … FROM orders, а PostgreSQL сам работает с нужной частью.

Декларативное секционирование (PostgreSQL 10+)

Есть «родительская» таблица с описанием ключа секционирования (по нему и идёт разделение) и список секций, каждая со своим диапазоном/списком значений.

CREATE TABLE orders (
    id         bigint      NOT NULL,
    created_at timestamptz NOT NULL,
    user_id    uuid        NOT NULL,
    status     text        NOT NULL,
    total      numeric(18,2) NOT NULL,
    -- ключ секционирования обязан входить в первичный ключ
    PRIMARY KEY (id, created_at)
) PARTITION BY RANGE (created_at);

CREATE TABLE orders_2026_01 PARTITION OF orders
    FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');

CREATE TABLE orders_2026_02 PARTITION OF orders
    FOR VALUES FROM ('2026-02-01') TO ('2026-03-01');

-- «страховка»: строки, не попавшие ни в одну секцию
CREATE TABLE orders_default PARTITION OF orders DEFAULT;
Границы: FROM включается, TO — нет

Диапазон секции полуоткрытый: [FROM, TO). Поэтому строка с created_at = '2026-02-01 00:00:00' попадёт только во вторую секцию (orders_2026_02), а не в обе. Отвечая на вопрос «могут ли одни и те же строки оказаться в двух секциях»: нет — правая граница исключается, поэтому секции стыкуются без дыр и без пересечений.

  • Соседние секции должны начинаться ровно с того значения, на котором закончилась предыдущая: TO ('2026-02-01') и следующая FROM ('2026-02-01').
  • Если значение вышло за границы всех секций, вставка падает с «no partition of relation "orders" found for row». Лечится новой секцией или DEFAULT-секцией (в примере она как раз «страховка»).
  • Для timestamptz границы трактуются в таймзоне сессии — проверьте SHOW TimeZone, если пишете локальное время, а не UTC.
СтратегияЧем разделяетКогда выбирают
RANGEдиапазоны значенийДанные растут во времени; старые периоды уходят целиком — почти всегда это дата/время
LISTперечисление значенийАрендатор, регион, тип документа: значений немного и они известны
HASHхэш от значенияЕстественной оси нет, а нужно равномерно распределить данные (например по user_id)
Как выбирать ключ

Ключ должен совпадать с тем, по чему фильтруют почти все запросы, и с тем, что удобно удалять целиком. Если «разрезать» таблицу не по рабочему фильтру, запросы начнут читать все секции — и станет хуже, чем было.

Что даёт секционирование

  • Отсечение секций (partition pruning). Запрос «за январь» читает одну секцию вместо сотни — меньше страниц, меньше времени.
  • Дешёвое удаление старых данных. Вместо миллионов DELETE (и миллионов мёртвых версий) — DETACH PARTITION и DROP: миллисекунды и никакого bloat.
  • Обслуживание по частям. VACUUM и ANALYZE работают с меньшими объектами; статистика по свежим данным точнее, а очистка быстрее.
  • Меньше «одного гигантского» индекса. У каждой секции свой B-tree — вставки дешевле, перестроить один индекс не страшно.
  • Размещение и хранение. Холодные секции можно положить на медленные диски или сжать, горячие — на быстрые (tablespace).
  • Параллелизм. Секции можно сканировать параллельно, а массовые операции ускоряются.
Чего секционирование не делает

Оно не ускоряет запросы, которые не фильтруют по ключу секционирования. И добавляет свою цену: больше объектов в каталоге, нужно управлять секциями (создавать заранее, обслуживать границы), а уникальные ограничения усложняются.

Индексы и ограничения

  • Индекс создают на родительской таблице — PostgreSQL создаёт такие же индексы на всех существующих секциях, а новые секции получают их автоматически: CREATE INDEX ON orders (user_id, created_at DESC);
  • Уникальность обязана включать ключ секционирования. Это прямое следствие того, что уникальность проверяется внутри секции: PRIMARY KEY (id, created_at), а не просто id.
  • Индексы локальные. Глобальных индексов, которые «знают» про все секции, в PostgreSQL нет — поэтому поиск не по ключу (например, по user_id при ключе по дате) приводит к чтению всех секций. Если так ищут всегда — ключ выбран неверно.
  • Внешние ключи могут ссылаться на секционированную таблицу (начиная с PostgreSQL 12) — но и это стоит проверять при проектировании.

Partition pruning: когда работает, а когда нет

Отсечение происходит на этапе планирования: планировщик сравнивает условия на колонку-ключ с границами секций и выбрасывает те, куда данные попасть не могут. Чтобы это сработало, условие должно быть простым сравнением колонки со значением того же типа.

Как это выглядит из .NET (EF Core)

Отсечение ломается не «в базе», а в LINQ — когда в SQL попадает функция или приведение над колонкой-ключом. Три самых частых случая:

// ✘ 1. Свойство .Date превращается в функцию date() над колонкой
var bad = await db.Orders
    .Where(o => o.CreatedAt.Date == day)
    .ToListAsync(ct);
// SQL: WHERE date(o.created_at) = @__day_0     ← границы секций неизвестны → все секции

// ✘ 2. Сравнение со строкой/приведение типа: параметр приходит как text
var bad2 = await db.Orders
    .FromSqlRaw("SELECT * FROM orders WHERE created_at::text LIKE '2026-01-%'")
    .ToListAsync(ct);
// SQL: WHERE (created_at)::text LIKE '2026-01-%'  ← тоже функция по колонке

// ✔ 3. Диапазон с правильным типом — единственная форма, которая сохраняет pruning
var from = day.ToDateTime(TimeOnly.MinValue, DateTimeKind.Utc);   // 2026-01-01 00:00 UTC
var to   = from.AddDays(1);                                       // 2026-01-02 00:00 UTC
var good = await db.Orders
    .Where(o => o.CreatedAt >= from && o.CreatedAt < to)
    .ToListAsync(ct);
// SQL: WHERE o.created_at >= @__from_0 AND o.created_at < @__to_1

Что видно в плане

✘ date(created_at) = …
Append  (actual time=… rows=1200)
  ->  Seq Scan on orders_2026_01 …            ← 12 секций: Subplans Removed: 0
  ->  Seq Scan on orders_2026_02 …
  … (все секции, включая архивные)

✔ created_at >= … AND created_at < …
Append  (actual time=0.02..0.94 rows=1200)
  Subplans Removed: 11                        ← 11 секций отброшено планировщиком
  ->  Index Scan using orders_2026_01_created_at_idx on orders_2026_01 …
  • Правило: ключ секционирования сравниваем напрямую и с тем же типом — никаких .Date, .Year, .ToString(), ::text, date_trunc() по колонке.
  • Откуда взять границы: не «сегодня минус 30 дней в виде строки», а DateTime/DateTimeOffset — тогда провайдер отправит параметр как timestamptz, и сравнение останется простым.
  • Как проверить из кода: ToQueryString() показывает готовый SQL, а в логах EF видно, что реально ушло в базу. Ищите в SQL date(, ::text, CASE вокруг колонки-ключа.
  • Если функция всё-таки нужна (например, «все заказы за 15-е число»), считайте границы в приложении: День D → [D 00:00, D+1 00:00). Это тот же приём, что и в главе 5 про приведение типов.

Обслуживание секций: кто их создаёт и удаляет

Секции — это регулярная работа, а не разовое решение. На практике:

  • Создавать заранее. Обычно отдельным заданием (например, pg_partman) или cron-скриптом за месяц вперёд. Если секции закончились, строки уйдут в DEFAULT — и запросы начнут читать её целиком.
  • Удалять старые. DETACH PARTITION CONCURRENTLY (не блокирует работу), затем DROP TABLE уже отсоединённой секции. Это принципиально дешевле массового DELETE.
  • Присоединять при миграции. Загрузить данные в обычную таблицу-«близнеца» и затем ATTACH PARTITION — быстрее и безопаснее, чем вставлять миллионы строк прямо в секционированную таблицу.
-- новая секция на следующий месяц
CREATE TABLE orders_2026_03 PARTITION OF orders
    FOR VALUES FROM ('2026-03-01') TO ('2026-04-01');

-- удаление старых данных: отсоединили — и сразу удалили
ALTER TABLE orders DETACH PARTITION orders_2024_01 CONCURRENTLY;
DROP TABLE orders_2024_01;

-- присоединение таблицы, которую наполнили заранее
ALTER TABLE orders ATTACH PARTITION orders_2026_02_old
    FOR VALUES FROM ('2026-02-01') TO ('2026-03-01');

Вопросы, которые возникают всегда

1. Секции создаются — а что происходит с самой таблицей orders?

Родительская таблица после PARTITION BY — не хранилище данных, а описание: у неё есть колонки, ключ секционирования и ограничения, но своих строк в ней нет и быть не может. Все строки лежат в секциях. Поэтому:

  • SELECT … FROM orders — это обращение к «виртуальной» таблице: PostgreSQL подставляет вместо неё список секций (узел Append в плане) и читает только нужные.
  • INSERT INTO orders … — строка уезжает в ту секцию, чей диапазон подходит.
  • Размер родителя — 0 bytes: места она не занимает. Это легко проверить: 
    SELECT relname, relkind, pg_size_pretty(pg_total_relation_size(oid)) AS size
FROM   pg_class
WHERE  relname LIKE 'orders%'
ORDER  BY relname;

--  relname     | relkind | size      ← relkind: 'p' = секционированная (родитель), 'r' = обычная таблица
-- -------------+---------+-------
--  orders      | p       | 0 bytes   ← у родителя нет своих данных
--  orders_2026_01 | r    | 812 MB    ← данные лежат здесь
--  orders_2026_02 | r    | 798 MB

SELECT count(*) FROM ONLY orders;   -- ONLY = «только сама таблица, без секций» → 0
  • Что делать с данными, которые уже были в таблице до секционирования. Превратить обычную таблицу в секционированную «на месте» нельзя — создают новую с PARTITION BY, а данные переносят. Два безопасных способа: 
    -- (а) через секцию: создали таблицу-«близнеца», наполнили, присоединили
CREATE TABLE orders_2025_12 (LIKE orders_old INCLUDING ALL);
INSERT INTO orders_2025_12 SELECT * FROM orders_old
WHERE  created_at >= '2025-12-01' AND created_at < '2026-01-01';
ALTER TABLE orders ATTACH PARTITION orders_2025_12
    FOR VALUES FROM ('2025-12-01') TO ('2026-01-01');   -- ATTACH проверит диапазон

-- (б) через родителя (проще, но медленнее на миллионах строк)
INSERT INTO orders SELECT * FROM orders_old;

2. «Данные нужны через 100 лет» — значит, DROP не нужен

Верно: DROP — это последний шаг, и он допустим только когда данные уже скопированы в архив. Секционирование как раз и даёт возможность отделить старую секцию от рабочей таблицы, ничего не удаляя: DETACH PARTITION превращает её в обычную самостоятельную таблицу со всеми строками. Дальше решаете, что с ней делать:

-- полный безопасный цикл «архивируем старый месяц»
-- 1) вывели из рабочей таблицы (с версии 14 — без длительной блокировки)
ALTER TABLE orders DETACH PARTITION orders_2024_01 CONCURRENTLY;

-- 2) данные остались в базе как отдельная таблица: проверяем объём и что они читаются
SELECT count(*) FROM orders_2024_01;

-- 3) копируем в архив (внешняя команда, не SQL)
--    pg_dump -Fc -t orders_2024_01 appdb > orders_2024_01.dump

-- 4) только после проверки копии — удаляем
DROP TABLE orders_2024_01;

-- 5) старую секцию можно и сохранить, но увести на медленный диск:
--    ALTER TABLE orders_2024_01 SET TABLESPACE archive;

Важно: DETACH PARTITION требует ACCESS EXCLUSIVE на родителя; вариант CONCURRENTLY (PostgreSQL 14+) этого избегает и не может выполняться внутри транзакции — запускайте его отдельной командой.

3. «Секция на месяц вперёд — данные попадут туда сами?»

Да, автоматически. Вставка идёт в родительскую таблицу, а PostgreSQL сам выбирает секцию по значению ключа. Приложение не знает и не должно знать имён секций:

INSERT INTO orders (id, created_at, user_id, status, total)
VALUES (1, '2026-03-15 10:00+00', '…', 'NEW', 100);   -- → уедет в orders_2026_03, хотя её нет в тексте

-- а если подходящей секции НЕТ, вставка падает целиком:
-- ERROR:  no partition of relation "orders" found for row
-- DETAIL:  Partition key of the failing row contains (created_at) = (2026-03-15 10:00:00+00).
  • «Месяц вперёд» — это запас по времени, а не магия. Кончился запас — приложение получает ошибку на INSERT (и это лучше, чем тихо уехать в DEFAULT).
  • Секция на год вперёд — это нормально и не дорого: пустая секция занимает единицы килобайт в каталоге. Проблемой становятся не «лишние» секции, а тысячи секций (слишком мелкая гранулярность «на годы»), поэтому запас делают на 3–12 периодов.
  • DEFAULT-секция ошибку скрывает: строки попадают в неё, но потом её читают все запросы к таблице (она «накрывает» любой диапазон), а присоединить новую секцию на тот же диапазон нельзя, пока в DEFAULT есть подходящие строки. Для горячих данных это скрытая деградация — поэтому алерт «в DEFAULT появились строки» полезнее самого DEFAULT.

4. «Создавать секции руками на год вперёд? А автоматизировать?»

Руками — не надо: это регламентная задача. Скрипт запускается раз в сутки, работает идемпотентно (существующую секцию не трогает) и держит запас на N месяцев вперёд. Минимальный вариант — функция на PL/pgSQL:

CREATE OR REPLACE FUNCTION create_order_partitions(p_months int DEFAULT 12)
RETURNS int                              -- вернёт, сколько секций реально создали
LANGUAGE plpgsql AS $$
DECLARE
    v_month date := date_trunc('month', now())::date;   -- начало текущего месяца
    v_from  date;                                       -- граница FROM (включается)
    v_to    date;                                       -- граница TO   (не включается)
    v_name  text;                                       -- имя секции
    v_made  int := 0;
BEGIN
    FOR i IN 0 .. p_months LOOP                          -- текущий месяц и N следующих
        v_from := (v_month + make_interval(months => i))::date;
        v_to   := (v_month + make_interval(months => i + 1))::date;
        v_name := format('orders_%s', to_char(v_from, 'YYYY_MM'));   -- orders_2026_03

        IF to_regclass(v_name) IS NULL THEN              -- идемпотентность: есть — пропускаем
            EXECUTE format(
                'CREATE TABLE %I PARTITION OF orders FOR VALUES FROM (%L) TO (%L)',
                v_name, v_from, v_to);                   -- %I — идентификатор, %L — литерал
            v_made := v_made + 1;
        END IF;
    END LOOP;
    RETURN v_made;
END $$;

-- дозаполнить запас на год: создаст только недостающие секции
SELECT create_order_partitions(12);      -- → 12 (или меньше, если часть уже была)

Когда запускать. Подойдёт любой планировщик, умеющий выполнить SQL-запрос:

-- (а) pg_cron: планировщик внутри PostgreSQL
CREATE EXTENSION IF NOT EXISTS pg_cron;
SELECT cron.schedule(
    'orders-partitions',                       -- имя задания (по нему же можно изменить/удалить)
    '0 3 * * *',                               -- cron-выражение: каждый день в 03:00
    $$SELECT create_order_partitions(3)$$      -- держим запас 3 месяца и не разрастаемся
);

-- посмотреть задания и историю запусков
SELECT jobid, schedule, command, active FROM cron.job;
SELECT * FROM cron.job_run_details ORDER BY start_time DESC LIMIT 5;
-- (б) снаружи: systemd-таймер, Kubernetes CronJob, Airflow — тот же вызов одной командой
psql "host=db dbname=app" -c "SELECT create_order_partitions(3);"

Или готовое расширение — pg_partman: оно и создаёт будущие секции, и обслуживает их, и умеет отсоединять/удалять старые по политике хранения:

-- один раз: отдать таблицу под управление (native = обычное декларативное секционирование)
SELECT partman.create_parent(
    p_parent_table => 'public.orders',
    p_control      => 'created_at',
    p_interval     => '1 month',
    p_premake      => 4                       -- всегда держать 4 будущие секции
);

-- по расписанию (тем же pg_cron) — создать недостающие и обслужить старые
CALL partman.run_maintenance();
  • Почему format() с %I/%L: это единственный безопасный способ собрать динамический SQL: %I экранирует идентификатор, %L — литерал. Ручная склейка строки здесь была бы SQL-инъекцией.
  • Что мониторить: (1) задание отработало — в cron.job_run_details нет failed; (2) секция на следующий месяц существует: SELECT to_regclass('orders_2026_04') IS NOT NULL; Если нет — алерт, иначе ошибку на INSERT получите ровно в полночь первого числа.
  • Сколько держать: запас 1–3 месяца плюс алерт — достаточно. Год вперёд тоже можно: цена — записи в каталоге, а не место на диске.

Частые ошибки

  1. Ключ выбран не по рабочим фильтрам. Тогда отсечения нет, а накладные расходы есть.
  2. Тысячи секций. Планирование запроса и работа с каталогом дорожают; «десятки-сотни» — это нормальный порядок, «десятки тысяч» — уже проблема.
  3. Ожидание глобального уникального индекса. Уникальность проверяется внутри секции, поэтому ключ секционирования обязан входить в состав уникального ключа.
  4. Слишком широкая секция. «Одна секция на год» почти не даёт отсечения: если запросы идут помесячно, гранулярность должна быть месяц.
  5. Забытая DEFAULT-секция. Она накапливает «неправильные» строки, и её читают все запросы — это скрытая деградация.
  6. Секционирование «чтобы было». Для таблицы на миллион строк оно не нужно: сложность вырастет, а выигрыша не будет.

Как проверить, что всё работает

  • EXPLAIN: в плане виден узел Append, а в нём — сколько секций реально участвует. Строка Subplans Removed показывает, сколько отброшено.
  • EXPLAIN (ANALYZE, BUFFERS): сколько страниц реально прочитано. Если вернулось десять строк, а прочитаны миллионы страниц — отсечения нет (глава 19).
  • pg_stat_user_tables по секциям: если seq_scan растёт у всех секций, запросы ходят по всей таблице.
  • Каталог: сколько секций и какого они размера — SELECT relname, pg_size_pretty(pg_total_relation_size(oid)) FROM pg_class WHERE relname LIKE 'orders_%';
  • Приложение: проверяйте условия, которые оно присылает: функции по дате и сравнение со строками ломают отсечение (пример — в SQL-разделе про планы и в главе про EF Core).
★ Что запомнить из главы
  • Секционирование — про большие таблицы и обслуживание: отсечение при чтении плюс мгновенное удаление старых периодов.
  • Стратегии: RANGE (даты) — чаще всего, LIST (арендатор, регион), HASH (равномерно).
  • Ключ выбирают по рабочим фильтрам; уникальные ключи обязаны его включать; индексы локальные, глобальных нет.
  • Pruning работает только на «простых» условиях: сравнение колонки со значением того же типа. Функции по колонке и приведения его ломают.
  • Проверка — EXPLAIN (Append и Subplans Removed), BUFFERS, статистика по секциям.
