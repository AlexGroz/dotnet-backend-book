Глава 6. Коллекции: generic против non-generic

Почему List<int> лучше ArrayList, что такое generic и как выбрать коллекцию под задачу.

основная глава

Что такое generic

Generic («обобщённый тип») — это тип с параметром типа. Вы пишете List<T>, а при использовании подставляете конкретный тип: List<int>, List<Order>. Компилятор создаёт «специализацию» и знает точный тип элементов.

// generic: тип элемента известен компилятору
var numbers = new List<int>();
numbers.Add(42);
int first = numbers[0];        // никаких приведений

// non-generic: хранит object, тип «стирается»
var legacy = new ArrayList();
legacy.Add(42);                // 42 упаковывается в object
int old = (int)legacy[0];      // приведение вручную

Отсюда три выгоды generic-коллекций, и все три — про надёжность и скорость:

  1. Нет упаковки для значимых типов: List<int> хранит int, а ArrayList — object, то есть каждый элемент упаковывается (глава 2).
  2. Нет приведений при чтении: тип известен, приведение не нужно.
  3. Ошибки видно на компиляции, а не в рантайме.
// ✘ non-generic: компилятор пропустит, упадёт в рантайме
var list = new ArrayList();
list.Add(1);
list.Add("два");                    // никто не запретил
int sum = 0;
foreach (object item in list)
    sum += (int)item;               // InvalidCastException на "два"

// ✔ generic: не скомпилируется — и это хорошо
var list2 = new List<int>();
list2.Add("два");                   // ошибка компиляции

Кто на кого заменяется

Non-generic (старое)Generic (современное)Что изменилось
ArrayListList<T>Нет упаковки и приведений, тип проверяется компилятором
HashtableDictionary<TKey, TValue>Типизированные ключи и значения, быстрее
Queue, StackQueue<T>, Stack<T>То же плюс отсутствие бокса
SortedListSortedList<TKey, TValue>, SortedDictionary<TKey, TValue>Типизация; разная внутренняя структура и сложность
CollectionBaseCollection<T>Готовые проверки и уведомления об изменениях
IEnumerableIEnumerable<T>Типизированное перечисление (глава 7)

Non-generic-версии остались ради совместимости. В новом коде их не используют — исключение только взаимодействие со старыми API.

Интерфейсы коллекций: что возвращать из методов

ИнтерфейсЧто умеетКогда использовать в сигнатуре
IEnumerable<T>Только перечисление (глава 7)«Нужно пройти по элементам» — самый слабый контракт
IReadOnlyCollection<T>Перечисление + CountЧтение набора
IReadOnlyList<T>Плюс доступ по индексуРезультат выборки, который нельзя менять
ICollection<T>, IList<T>Добавление, удаление, индексаторКогда вызывающий действительно должен менять коллекцию
IDictionary<TKey, TValue>Ключ → значениеСловарь
ISet<T>Множество, объединение/пересечениеУникальность и «есть ли элемент»
 
// ✔ ХОРОШО: возвращаем интерфейс «только для чтения».
// Вызывающему хватает перечисления, Count и индексатора,
// но изменить нашу коллекцию он не сможет.
public IReadOnlyList<OrderRow> GetPage(int page) { … }

var page1 = service.GetPage(1);
foreach (var row in page1) Console.WriteLine(row.Total);   // ✔ читать можно
Console.WriteLine(page1.Count);                            // ✔ размер известен
// page1.Add(…)                                            // ✘ метода нет — данные защищены

// ✘ ПЛОХО: вернули List<T> — кто угодно может менять внутренние данные
public List<OrderRow> GetPageBad(int page) { … }

// параметр: если внутри только читаем — достаточно IEnumerable<T>
public decimal Sum(IEnumerable<OrderRow> rows) => rows.Sum(r => r.Total);

Правило простое: возвращайте самый узкий интерфейс, которого хватает вызывающему. Ему нужно только пройти по элементам — IEnumerable<T>; нужен размер — IReadOnlyCollection<T>; нужен ещё и индекс — IReadOnlyList<T>. Чем уже контракт, тем меньше способов случайно испортить данные.

Как выбрать коллекцию

КоллекцияЧто хорошоЧто дорого
List<T>Индекс O(1), добавление в конец амортизированно O(1)Вставка/удаление в середине O(n)
Dictionary<TKey, TValue>Поиск/вставка/удаление по ключу ~O(1)Нет порядка; нужен хороший GetHashCode
HashSet<T>«Есть ли элемент» ~O(1), пересеченияНет индексов и порядка
Queue<T> / Stack<T>FIFO / LIFO за O(1)Нет доступа к произвольному элементу
LinkedList<T>Вставка/удаление по узлу O(1)Плохая локальность памяти, нет индексов
SortedDictionary<TKey,TValue>Всегда отсортировано, O(log n)Медленнее Dictionary
ConcurrentDictionary, ConcurrentQueueБезопасны для нескольких потоковДороже обычных из-за синхронизации
Правило выбора

Сформулируйте операцию, которая выполняется чаще всего. Поиск по ключу → Dictionary. Проверка уникальности → HashSet. Обход в порядке добавления → List. Очередь задач → Queue/Channel. Остальное — редкость.

Ёмкость и рост

List<T> внутри — массив. Когда он заполняется, создаётся новый (обычно вдвое больше) и элементы копируются. Если размер известен заранее, этого можно избежать:

var list = new List<Order>(capacity: 10_000);   // сразу нужный массив
list.EnsureCapacity(20_000);                    // заранее расширить

var dict = new Dictionary<int, Order>(capacity: 10_000);   // меньше перестроений
А если элементов окажется больше?

Ничего страшного: ёмкость — не лимит, а подсказка. Когда внутренний массив заполнится, список создаст новый (обычно вдвое больше), скопирует туда элементы и продолжит работу. Ошибки «переполнения» не будет — вы просто заплатите за копирование.

var list = new List<int>(capacity: 2);    // «на два элемента»
list.AddRange(new[] { 1, 2, 3, 4, 5 });   // ✔ работает: список вырос сам
Console.WriteLine(list.Count);            // 5
Console.WriteLine(list.Capacity);         // 8 — вырос (обычно удвоением)

Поэтому ёмкость указывают не «чтобы поместилось», а чтобы не копировать зря: при известном размере (10 000) вы избегаете десятка промежуточных расширений и копирований.

foreach и скрытая аллокация

  • List<T> в конкретном типе — энумератор это struct, аллокации нет.
  • Через интерфейс IEnumerable<T> — энумератор упаковывается в object: аллокация на каждый цикл.
  • LINQ (Where, Select) — создаёт объекты-итераторы; на горячем пути лучше один явный цикл или Span.
// ✔ без упаковки: foreach по List<T> использует struct-энумератор
foreach (var order in list) { … }

// ✘ параметр объявлен как IEnumerable<T> — энумератор будет упакован
void Print(IEnumerable<Order> orders)
{
    foreach (var order in orders) { … }
}
★ Что запомнить из главы
  • Generic — тип с параметром типа: компилятор знает точный тип элементов.
  • Generic-коллекции дают отсутствие упаковки, отсутствие приведений и ошибки на компиляции.
  • Возвращайте самый узкий интерфейс, которого хватает вызывающему — обычно IReadOnlyList<T> или IEnumerable<T>: нужные операции есть, а менять ваши данные нельзя.
  • Коллекцию выбирают по главной операции: поиск → Dictionary, уникальность → HashSet, порядок → List.
  • Задавайте ёмкость, если размер известен; помните, что перечисление через интерфейс упаковывает энумератор.
