Глава 19. Что искать в EXPLAIN (ANALYZE, BUFFERS)

План — основной инструмент оптимизации. Разберём, какие поля читать и какие значения считать «красными флагами».

Оценка против факта

У каждого узла есть оценка планировщика и — если указан ANALYZE — факт. Весь смысл в сравнении этих двух чисел.

Пример вывода (фрагмент)

EXPLAIN (ANALYZE, BUFFERS)
SELECT o.id, c.name
FROM   orders o
JOIN   customers c ON c.id = o.customer_id
WHERE  o.status = 'NEW'
ORDER  BY o.created_at DESC
LIMIT  50;

Sort  (cost=9430.1..9430.3 rows=50 width=40)
      (actual time=402.1..402.2 rows=50 loops=1)
  Sort Key: o.created_at DESC
  Sort Method: external merge  Disk: 25120kB
  Buffers: shared hit=20114 read=5832, temp read=3140 written=3144
  ->  Hash Join  (cost=1120.5..9430.1 rows=50 width=40)
                 (actual time=8.311..380.9 rows=50 loops=1)
        Hash Cond: (c.id = o.customer_id)
        Buffers: shared hit=20114 read=5832
        ->  Seq Scan on orders o  (cost=0.00..8000.0 rows=5000 width=24)
                                   (actual time=0.02..380.9 rows=480000 loops=1)
              Filter: (status = 'NEW'::text)
              Rows Removed by Filter: 4520000
              Buffers: shared hit=19500 read=5800
        ->  Hash  (actual time=8.1..8.1 rows=200 loops=1)
              Buckets: 1024  Batches: 4  Memory Usage: 1024kB
              Buffers: shared hit=614 read=32
Planning Time: 1.204 ms
Execution Time: 405.771 ms

Здесь сразу три «красных флага»: Seq Scan с огромным Rows Removed by Filter (читаем миллионы строк, чтобы оставить часть), Batches: 4 у Hash (не хватило памяти) и сортировка на диск (external merge Disk).

Sort Method: почему сортировка уходит на диск

В плане есть строка Sort Method: external merge Disk: 25120kB. Разберём её по частям — этой темы мы раньше не касались.

1. У каждой операции есть бюджет памяти. Сортировки, хеши, DISTINCT, GROUP BY и материализация работают в памяти, размер которой задаёт параметр work_mem (по умолчанию 4 МБ). Это бюджет на одну операцию в одном запросе, а не на сервер: в плане из пяти сортировок каждая получит свои work_mem.

2. Если данные в бюджет не влезли, PostgreSQL не падает, а использует диск — и в плане меняется метод:

Sort MethodЧто делаетКогда выбирается
quicksortОбычная быстрая сортировка в памятиВсё влезло в work_mem
top-N heapsortДержит в памяти только N строк (кучу)Есть LIMIT N — сортировать миллион строк целиком не нужно
external merge  Disk: 25120kBРежет данные на части, сортирует каждую, пишет во временные файлы, затем сливаетНе влезло в work_mem

3. Как работает external merge. В память берётся порция, которая помещается в work_mem; она сортируется и сбрасывается в файл (это называется run). Так обрабатываются все данные, после чего отсортированные куски сливаются (merge) в один поток. Поэтому в плане две цены: запись кусков и их повторное чтение — именно это и показывают счётчики temp written и temp read ниже.

4. Что означает Disk: 25120kB. Это суммарный размер временных файлов, которые создала эта операция (≈24,5 МБ). Сравните с work_mem: если он 4 МБ, значит данных примерно в шесть раз больше бюджета. Поле печатается только у метода external merge.

Почему это «красный флаг», даже когда запрос быстрый

Диск на порядок медленнее памяти, и такие сортировки одновременно пишут во временные файлы со всех соединений: десять тяжёлых отчётов = десять наборов временных файлов. Плюс появляется зависимость от свободного места. Лечится точечным SET LOCAL work_mem = '64MB'; для конкретного запроса (глава 20) — не глобальным увеличением: work_mem × число операций × число соединений легко съедает всю RAM.

temp read/written: где это в нашем плане

Это поле — часть строки Buffers, и появляется оно только у того узла, который использовал временные файлы. В примере выше оно есть ровно в одном месте — на верхнем узле Sort:

Sort  (cost=9430.1..9430.3 rows=50 width=40)
      (actual time=402.1..402.2 rows=50 loops=1)
  Sort Key: o.created_at DESC
  Sort Method: external merge  Disk: 25120kB
  Buffers: shared hit=20114 read=5832, temp read=3140 written=3144   ← вот оно
                           └─ обычные буферы ─┘  └─ temp: временные файлы ─┘

Что такое «временный файл». Это обычный файл на диске, который backend создаёт на время запроса и удаляет сразу после него. PostgreSQL использует их как «продолжение памяти» для операций, которым не хватило work_mem: сортировка, хеш-соединение (батчи), DISTINCT, GROUP BY, материализация CTE, а также CREATE INDEX и VACUUM. Лежат они в каталоге данных ($PGDATA/base/pgsql_tmp/, либо в temp_tablespaces, если его настроили) и к вашим таблицам отношения не имеют.

  • temp read=3140 — сколько 8-килобайтных блоков прочитано из временных файлов (3140 × 8 КБ ≈ 25 МБ); written=3144 — сколько записано. Единица та же, что и у shared: блоки, а не строки и не байты.
  • Причина — сортировка не влезла в work_mem, PostgreSQL слил её на диск (external merge). Поэтому на этом узле есть оба поля: Sort Method: external merge Disk и temp … — первое объясняет, почему, второе показывает сколько.
  • read и written почти равны, и это нормально: куски сначала записали, а потом прочитали для слияния. Если written сильно больше read — файлы писались «впустую» (например, операция прервалась по statement_timeout).
  • Если бы временных файлов не было, в строке Buffers не было бы части temp … вообще: Buffers: shared hit=… read=… и всё. Поле не печатается нулём — оно просто отсутствует. Поэтому «ищу temp и не нахожу» чаще всего значит «сортировки и хеши поместились в память» (это хорошо), а не «что-то потерялось».
  • Где ещё бывает temp: у Hash с Batches > 1, у Materialize, у GroupAggregate с сортировкой, у CTE MATERIALIZED. Правило чтения: temp есть → узел работал через диск → смотреть work_mem.
Как увидеть временные файлы не в одном плане, а по всей базе 
-- сколько временных файлов создано и сколько на них ушло (накопительно с последнего сброса)
SELECT datname,
       temp_files,                            -- количество файлов
       pg_size_pretty(temp_bytes) AS temp     -- суммарный объём
FROM   pg_stat_database
ORDER  BY temp_bytes DESC;

-- предохранитель: лимит временных файлов на одну сессию (по умолчанию -1 = без лимита)
SHOW temp_file_limit;      -- например, '10GB' — запрос упадёт, а не забьёт диск

Если temp_bytes растёт каждый час — где-то регулярно не хватает work_mem, и это стоит найти (обычно это отчёты и ORDER BY без подходящего индекса).

Heap Fetches: почему его нет в нашем плане

Heap Fetches печатается только у узла Index Only Scan. В плане выше такого узла нет (там Seq Scan и Hash Join), поэтому строки Heap Fetches тоже нет — это не ошибка плана и не «потерянное поле».

Смысл поля: index-only scan обещает «прочитать всё из индекса, не заглядывая в таблицу». Но PostgreSQL может так поступить, только если уверен, что версия строки видна всем (это хранится в visibility map, её обновляет VACUUM). Когда уверенности нет — он идёт в таблицу; каждый такой поход и считается в Heap Fetches:

EXPLAIN (ANALYZE, BUFFERS)
SELECT id, created_at FROM orders WHERE created_at >= now() - interval '1 day';

Index Only Scan using orders_created_at_idx on orders
  (cost=0.43..180.2 rows=1200 width=16)
  (actual time=0.031..0.940 rows=1200 loops=1)
  Heap Fetches: 1200                  ← пришлось проверить в таблице ВСЕ строки
  Buffers: shared hit=40
  • Heap Fetches ≈ rows → выигрыша от index-only scan почти нет: таблица всё равно читается. Лечится VACUUM (или автоочисткой), после чего счётчик падает к нулю.
  • Heap Fetches = 0 → идеальный случай: всё прочитано из индекса.
  • Для сравнения: у обычного Index Scan этого поля нет вовсе — он всегда идёт в таблицу, там нечего считать.

Поля, по которым читаем план

ПолеЧто означает и на что смотреть
cost=.. rows=..Оценка планировщика: полная стоимость и число строк
actual time=.. rows=.. loops=..Факт. Общее время узла ≈ actual time × loops
rows vs actual rowsГлавный сигнал. Расхождение в разы/порядки → плохая статистика → неверный план
loopsСколько раз выполнялся узел. Большое значение у Nested Loop = неявный цикл
Buffers: hit / readhit — из кэша, read — с диска. Много read → много I/O
Rows Removed by FilterСтолько строк прочитали и выбросили → читаем лишнее, нужен индекс
Sort MethodMemory — хорошо; external merge Disk — не хватило work_mem
Hash: Batches / Memory UsageBatches = 1 — всё в памяти; больше 1 → hash на диск
temp read/writtenВременные файлы на диске (сортировки, hash, материализация)
Planning Time / Execution TimeОтделить построение плана от выполнения
Heap Fetches (index-only scan)Сколько раз всё же пришлось идти в таблицу
★ Чек-лист «красных флагов»
  • Seq Scan на большой таблице там, где ожидался Index Scan.
  • Nested Loop с большим числом loops (выбран из-за недооценки строк).
  • Оценка строк сильно расходится с фактом (в разы или порядки).
  • Sort / Hash на диск (external merge, Batches > 1) — мало work_mem.
  • Много shared read — данные не в кэше.
  • Огромный Rows Removed by Filter — фильтр отсекает почти всё после чтения.
Про ANALYZE на продакшене

EXPLAIN ANALYZE выполняет запрос по-настоящему. Для тяжёлых запросов — снимайте план на реплике или в транзакции: BEGIN; EXPLAIN ANALYZE ...; ROLLBACK;
