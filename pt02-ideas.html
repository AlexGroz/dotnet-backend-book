Глава 2. Четыре идеи, из которых сделаны все паттерны

Прежде чем разбирать паттерны по одному, посмотрим на четыре приёма, из которых они собраны. Примеры здесь короткие и без фреймворков — только суть.

подводящая глава

Идея 1. Контракт: интерфейс вместо конкретного класса

Контракт (интерфейс) — это «договор»: «я умею вот это», без указания, как именно. Код, который пользуется контрактом, не знает и не должен знать, кто его реализует.

// Контракт: «умею отправить сообщение»
public interface IMessageSender
{
    void Send(string to, string text);
}

// Две разные реализации одного контракта
public sealed class EmailSender : IMessageSender
{
    public void Send(string to, string text) => Console.WriteLine($"Email → {to}: {text}");
}

public sealed class SmsSender : IMessageSender
{
    public void Send(string to, string text) => Console.WriteLine($"SMS → {to}: {text}");
}

// Потребитель зависит от КОНТРАКТА, а не от конкретного класса
static void Notify(IMessageSender sender) => sender.Send("+7 900 000-00-00", "Заказ готов");

Notify(new EmailSender());   // письмо
Notify(new SmsSender());     // смс — метод Notify при этом не менялся
  • Замена реализации без правки потребителя: Notify не знает, кто там внутри.
  • Тесты: вместо настоящей отправки подставляется «заглушка», которая ничего не отправляет.
  • Из этой идеи растут стратегия и репозиторий.

Идея 2. Делегирование: не делать самому, а попросить другого

Делегирование — объект получает работу, делает свою часть, а остальное передаёт другому объекту. Тот, другой, хранится в поле.

public sealed class LoggingSender : IMessageSender
{
    private readonly IMessageSender _inner;          // тот, кому делегируем

    public LoggingSender(IMessageSender inner) => _inner = inner;

    public void Send(string to, string text)
    {
        Console.WriteLine($"отправляю на {to}");     // 1) своя работа
        _inner.Send(to, text);                      // 2) отдали работу дальше
        Console.WriteLine("готово");                // 3) своя работа после
    }
}

// Собираем: «отправка с логированием поверх обычной отправки»
IMessageSender sender = new LoggingSender(new EmailSender());
sender.Send("+7 900 000-00-00", "Заказ готов");
  • LoggingSender не отправляет сам — он только оборачивает вызов.
  • Обёртки можно вкладывать: лог поверх retry поверх email.
  • Из этой идеи растут декоратор и цепочка обязанностей.

Идея 3. Композиция вместо наследования

Наследование отвечает на вопрос «является» (EmailSender — это IMessageSender). Композиция — на вопрос «использует» (обёртка использует другую отправку). Для добавления поведения почти всегда лучше второе.

✘ наследование: под каждый вариант — свой класс

EmailSenderWithLog
SmsSenderWithLog
EmailSenderWithLogAndRetry
SmsSenderWithLogAndRetry
…                     ← число классов = произведение вариантов

✔ композиция: собираем из кусочков, как конструктор

new LoggingSender(new EmailSender())                     // логи + email
new RetrySender(new LoggingSender(new SmsSender()))      // retry + логи + смс
  • Новый вариант — новый «кубик», а не правка всех классов.
  • Порядок кубиков виден прямо в коде сборки.
  • Из этой идеи растёт декоратор в его практическом виде.

Идея 4. Создание отдельно от использования

Код, который работает с объектом, не должен знать, как этот объект создавать и настраивать. Иначе настройка расползается по проекту, а в тестах её невозможно заменить.

// ✘ потребитель сам знает, как создать и настроить
public Task PayAsync()
{
    var client = new HttpClient();                       // создаём вручную
    client.BaseAddress = new Uri("https://payments…");   // и настраиваем
    client.Timeout = TimeSpan.FromSeconds(5);
    return client.PostAsync("/pay", null);
}

// ✔ кто-то другой подготовил готовый объект — мы только пользуемся
public sealed class PaymentService(HttpClient client)    // зависимость пришла снаружи
{
    public Task PayAsync() => client.PostAsync("/pay", null);
}
  • Настройка в одном месте — а не в каждом методе.
  • В тестах подставляется поддельный клиент.
  • Из этой идеи растут фабрика и внедрение зависимостей (DI).
Где что разобрано

В таблице шесть имён, но глав пять. Декоратор и цепочка обязанностей — это два применения одной идеи (делегирования), поэтому они идут подряд: главы 5 и 6. DI — не отдельная глава этой книги: его механика разобрана в «Backend на .NET», глава 15, а здесь он используется как инструмент сборки.

Как этим пользоваться при чтении

В каждой следующей главе ищите эти четыре идеи. «Стратегия» — это идея контракта, применённая к алгоритму. «Декоратор» — идея делегирования, применённая к обёртке. Когда видишь паттерн как «контракт + делегирование», он перестаёт быть набором магических классов.

★ Что запомнить из главы
  • Контракт — интерфейс: потребитель зависит от «умею», а не от «кто именно».
  • Делегирование — сделать своё и передать вызов дальше (основа декоратора и цепочки).
  • Композиция — собирать из кубиков: поведение добавляется обёрткой, а не наследником.
  • Создание отдельно — потребитель получает готовый объект, а не создаёт его сам.
