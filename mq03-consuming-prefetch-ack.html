Глава 3. Потребление: prefetch, ack и конкуренция

Сколько сообщений держать «в работе», когда подтверждать и почему одно сообщение приходит дважды

основная глава

Подписка и подтверждение

Потребитель подписывается на очередь и получает сообщения по одному (по умолчанию). Ключевой выбор — autoAck:

  • autoAck: true — брокер считает сообщение доставленным сразу, ещё до обработки. Если процесс упадёт в обработчике, сообщение потеряно.
  • autoAck: false — подтверждение отправляет приложение (BasicAck) после успешной обработки. Это единственный вариант, при котором падение потребителя не теряет работу.
// ch — канал (глава 1), ct — CancellationToken приложения,
// HandleAsync — ваш обработчик сообщения
var consumer = new AsyncEventingBasicConsumer(ch);

consumer.ReceivedAsync += async (_, ea) =>
{
    try
    {
        await HandleAsync(ea.Body, ct);                 // бизнес-логика
        await ch.BasicAckAsync(ea.DeliveryTag, false);  // успех: убрать из очереди
    }
    catch (Exception)
    {
        // вернуть в очередь (requeue) или отправить в DLQ — глава 4
        await ch.BasicNackAsync(ea.DeliveryTag, false, requeue: false);
    }
};

await ch.BasicConsumeAsync("orders.new", autoAck: false, consumer);

Обратите внимание: подтверждение относится к каналу и его DeliveryTag, а не к сообщению «вообще». Поэтому канал, на котором потребляют, не должен использоваться для других подтверждений из другого потока.

Requeue и признак повторной доставки

Если обработка не удалась, сообщение можно вернуть в очередь: requeue: true. Брокер доставит его снова, и в этот раз Redelivered будет true. Реальный вывод:

delivery #1: body=job-1 Redelivered=False
delivery #2: body=job-1 Redelivered=True
q.requeue left=0

Код, который это даёт: первый раз обработчик делает BasicNack(requeue: true), второй — BasicAck. Отсюда два вывода:

  • Доставка — at-least-once. Одно и то же сообщение может быть обработано дважды: из-за requeue, из-за падения потребителя до подтверждения, из-за переподключения. Гарантии «ровно один раз» в RabbitMQ нет.
  • Обработчик должен быть идемпотентным. Повторный job-1 не должен списать деньги второй раз: проверяйте MessageId или уникальный ключ в БД.
Бесконечный requeue — это «отравленное» сообщение

Если обработчик падает всегда, requeue: true превращает сообщение в вечный цикл: оно возвращается, снова падает, снова возвращается — и занимает потребителя. Поэтому после N попыток сообщение отправляют в dead-letter очередь (глава 4), а requeue оставляют для временных сбоев.

Prefetch: сколько сообщений держать в работе

BasicQos (QoS) ограничивает число неподтверждённых сообщений на потребителе. По умолчанию ограничения нет — брокер высылает столько, сколько успеет, и быстрый потребитель забирает всё себе, пока медленный разбирается с первым сообщением. Проверим на двух потребителях одной очереди: 10 сообщений, потребитель A обрабатывает 100 мс, потребитель B — мгновенно.

await ch.BasicQosAsync(prefetchSize: 0, prefetchCount: 1, global: false);
prefetch=1/1, A slow:   A=1  B=9
prefetch=10/10, A slow: A=0  B=10
  • С prefetch = 1 каждый потребитель держит одно сообщение: пока A занят, B забирает остальные. Нагрузка распределяется по скорости обработки.
  • С prefetch = 10 тот, кто подключился первым, забирает всю пачку (в этом прогоне — все 10) и обрабатывает их последовательно, а второй простаивает. Именно так «один медленный потребитель съедает очередь».

Правило: prefetch = столько сообщений, сколько потребитель реально обрабатывает параллельно. Для последовательной обработки — 1. Для пачки из 10 параллельных задач — 10–20. Слишком большой prefetch означает «захват» очереди и большой объём работы, которая при падении начнётся заново.

Конкуренция и масштабирование

Что нужноКак делаетсяСледствие
Больше параллельной обработкиНесколько потребителей на одну очередь (в процессе или на разных репликах)Сообщения делятся между ними; порядок обработки не гарантируется
Несколько независимых обработчиков одного событияНесколько очередей, привязанных к одному exchangeКаждая очередь получает свою копию сообщения
Порядок обработкиОдин потребитель + prefetch = 1Медленнее, но сообщения идут по порядку

Важно: одна очередь = одна работа. Если два разных сервиса подписаны на одну очередь, они будут делить сообщения, а не получать каждому. Для «каждому по копии» нужны разные очереди.

Потребитель в BackgroundService

В ASP.NET потребитель живёт в фоновом сервисе: соединение и канал создаются один раз, подписка — на всё время работы, а при остановке приложения канал закрывается, и неподтверждённые сообщения возвращаются в очередь.

public sealed class OrdersConsumer(IConnection conn, IServiceScopeFactory scopes) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        await using var ch = await conn.CreateChannelAsync(cancellationToken: ct);
        await ch.BasicQosAsync(0, prefetchCount: 10, global: false);

        var consumer = new AsyncEventingBasicConsumer(ch);
        consumer.ReceivedAsync += async (_, ea) =>
        {
            using var scope = scopes.CreateScope();      // scoped-сервисы (DbContext) — из scope
            try
            {
                await scope.ServiceProvider.GetRequiredService<OrderHandler>()   // ваш scoped-обработчик
                           .HandleAsync(ea.Body, ct);
                await ch.BasicAckAsync(ea.DeliveryTag, false);
            }
            catch (Exception)
            {
                await ch.BasicNackAsync(ea.DeliveryTag, false, requeue: false);
            }
        };

        await ch.BasicConsumeAsync("orders.new", autoAck: false, consumer, cancellationToken: ct);
        await Task.Delay(Timeout.Infinite, ct);           // держим сервис живым
    }
}
  • Скоуп на сообщение. DbContext и другие scoped-сервисы нельзя держать в singleton-потребителе: на каждое сообщение — свой IServiceScope.
  • Остановка не теряет работу: канал закрывается, неподтверждённые сообщения возвращаются в очередь и будут доставлены другому экземпляру.
  • Исключение не должно «убивать» подписку. Любая ошибка внутри обработчика должна заканчиваться ack или nack, иначе сообщение останется неподтверждённым.
★ Что запомнить из главы
  • autoAck: false — обязательный минимум: подтверждение после обработки, иначе падение потребителя теряет сообщение.
  • Доставка at-least-once: сообщение может прийти дважды (Redelivered=True) — обработчик должен быть идемпотентным.
  • prefetch определяет справедливость: 1 — по скорости обработки, большое число — «захват» очереди одним потребителем.
  • Одна очередь — одна работа: несколько сервисов на одной очереди делят сообщения; для копий нужны разные очереди.
  • В BackgroundService — свой scope на сообщение и обязательный ack/nack в каждом исходе.
