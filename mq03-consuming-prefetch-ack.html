Глава 3. Потребление: prefetch, ack и конкуренция

Сколько сообщений держать «в работе», когда подтверждать и почему одно сообщение приходит дважды

основная глава

Подписка и подтверждение

Потребитель (consumer — здесь и дальше в книге: ваша программа, подключённая к брокеру, а не человек-пользователь) подписывается на очередь и получает сообщения по одному (по умолчанию). Ключевой выбор — autoAck:

  • autoAck: true — брокер считает сообщение доставленным сразу, ещё до обработки. Если процесс упадёт в обработчике, сообщение потеряно.
  • autoAck: false — подтверждение отправляет приложение (BasicAck) после успешной обработки. Это единственный вариант, при котором падение потребителя не теряет работу.

Ниже — полная программа: подключение, канал, очередь, одно сообщение и потребитель, который его обрабатывает. HandleAsync — ваш метод, в RabbitMQ.Client такого нет: клиент отдаёт только байты тела, а что с ними делать, решает приложение. В листинге он объявлен в конце файла как локальная функция:

using System.Text;                                          // Encoding.UTF8.GetBytes / GetString
using RabbitMQ.Client;                                      // ConnectionFactory, IChannel, BasicProperties
using RabbitMQ.Client.Events;                               // BasicDeliverEventArgs — тип параметра ea

var factory = new ConnectionFactory { HostName = "localhost" };  // порт 5672 и guest/guest — по умолчанию
await using var conn = await factory.CreateConnectionAsync();    // TCP-соединение с брокером
await using var ch   = await conn.CreateChannelAsync();          // канал: в нём живут подписка и ack

await ch.QueueDeclareAsync("q.consume", durable: false, exclusive: false, autoDelete: false); // очередь опыта
await ch.QueuePurgeAsync("q.consume");                           // чистим остатки прошлых прогонов

var props = new BasicProperties { MessageId = "m-1", ContentType = "application/json" }; // свойства (глава 2)
await ch.BasicPublishAsync("", "q.consume", mandatory: false, basicProperties: props,
    body: Encoding.UTF8.GetBytes("{\"id\":42}"));                 // публикуем в default exchange: routing key = имя очереди

var consumer = new AsyncEventingBasicConsumer(ch);          // подписчик, привязанный к каналу

consumer.ReceivedAsync += async (_, ea) =>                  // срабатывает на каждую доставку; ea — параметры доставки
{
    try
    {
        Console.WriteLine($"exchange='{ea.Exchange}' rk='{ea.RoutingKey}' redelivered={ea.Redelivered} " +
                          $"tag={ea.DeliveryTag} msgid={ea.BasicProperties?.MessageId}"); // служебные поля доставки
        await HandleAsync(ea.Body);                          // бизнес-логика: ваш метод, не часть клиента
        await ch.BasicAckAsync(ea.DeliveryTag, false);       // успех: подтвердить; false — только это сообщение
    }
    catch (Exception)
    {
        // requeue: true — вернуть в очередь; здесь false — сообщение уйдёт в DLX (глава 4)
        await ch.BasicNackAsync(ea.DeliveryTag, false, requeue: false);
    }
};

await ch.BasicConsumeAsync("q.consume", autoAck: false, consumer); // подписка: очередь, ручные ack, обработчик
await Task.Delay(1000);                                      // ждём доставку, обработку и подтверждение

static async Task HandleAsync(ReadOnlyMemory<byte> body)     // ВАШ метод: клиент отдаёт только байты
{
    await Task.Delay(10);                                    // имитация работы: запрос в БД, вызов API и т.п.
    Console.WriteLine($"handler: {Encoding.UTF8.GetString(body.Span)}"); // тело — байты, декодируем в строку
}
exchange='' rk='q.consume' redelivered=False tag=1 msgid=m-1   # какой канал, ключ, номер доставки и MessageId
handler: {"id":42}                                            # HandleAsync разобрал тело

Что означает каждый элемент:

ЧтоЧто означает

ea.DeliveryTagномер доставки в рамках канала — по нему сообщение подтверждают или отклоняют
ea.Redeliveredtrue, если брокер доставляет сообщение повторно (после requeue или обрыва соединения). В выводе выше — redelivered=False: сообщение пришло впервые
ea.Exchange, ea.RoutingKeyкак сообщение было опубликовано — удобно для логов и маршрутизации ответа. В выводе выше exchange='' (пустая строка — default exchange, глава 1), rk='q.consume'
ea.BasicPropertiesсвойства из главы 2: MessageId, Headers, Persistent. В выводе выше msgid=m-1 — это MessageId, который положил публикующий код

BasicNackAsync(deliveryTag, multiple, requeue)requeue: true — вернуть в очередь и доставить снова; false — удалить или отправить в DLX, если он настроен (глава 4)

Обратите внимание: подтверждение относится к каналу и его DeliveryTag, а не к сообщению «вообще». Поэтому канал, на котором потребляют, не должен использоваться для других подтверждений из другого потока.

Requeue и признак повторной доставки

Если обработка не удалась, сообщение можно вернуть в очередь: requeue: true. Брокер доставит его снова, и в этот раз Redelivered будет true. Код опыта:

await ch.QueueDeclareAsync("q.requeue", durable: false, exclusive: false, autoDelete: false); // очередь для опыта
await ch.BasicPublishAsync("", "q.requeue", Encoding.UTF8.GetBytes("job-1"));                 // одно сообщение через default exchange

var deliveries = 0;                                            // сколько раз сообщение уже приходило
var consumer = new AsyncEventingBasicConsumer(ch);             // подписчик на том же канале
consumer.ReceivedAsync += async (_, ea) =>                     // обработчик каждой доставки
{
    deliveries++;                                              // считаем доставки
    Console.WriteLine($"delivery #{deliveries}: body={Encoding.UTF8.GetString(ea.Body.Span)} Redelivered={ea.Redelivered}");
    if (deliveries == 1)                                       // первая попытка «падает»
        await ch.BasicNackAsync(ea.DeliveryTag, multiple: false, requeue: true);  // вернуть в очередь
    else
        await ch.BasicAckAsync(ea.DeliveryTag, multiple: false);                  // со второй — подтвердить
};

await ch.BasicConsumeAsync("q.requeue", autoAck: false, consumer); // подписка с ручными подтверждениями
await Task.Delay(1500);                                            // ждём обе доставки

var q = await ch.QueueDeclarePassiveAsync("q.requeue");            // passive: спросить состояние, не создавая очередь
Console.WriteLine($"q.requeue left={q.MessageCount}");             // left=0 — сообщение подтверждено и удалено

Реальный вывод:

delivery #1: body=job-1 Redelivered=False   # первая доставка: сообщение новое
delivery #2: body=job-1 Redelivered=True    # после nack(requeue: true) брокер прислал его снова
q.requeue left=0                            # ack во второй раз убрал сообщение из очереди

Отсюда два вывода:

  • Доставка — at-least-once. Одно и то же сообщение может быть обработано дважды: из-за requeue, из-за падения потребителя до подтверждения, из-за переподключения. Гарантии «ровно один раз» в RabbitMQ нет.
  • Обработчик должен быть идемпотентным. Повторный job-1 не должен списать деньги второй раз: проверяйте MessageId или уникальный ключ в БД.
Бесконечный requeue — это «отравленное» сообщение

Если обработчик падает всегда, requeue: true превращает сообщение в вечный цикл: оно возвращается, снова падает, снова возвращается — и занимает потребителя. Поэтому после N попыток сообщение отправляют в dead-letter очередь (глава 4), а requeue оставляют для временных сбоев.

Prefetch: сколько сообщений держать в работе

BasicQos (QoS) ограничивает число неподтверждённых сообщений на потребителе. По умолчанию ограничения нет — брокер высылает столько, сколько успеет, и быстрый потребитель забирает всё себе, пока медленный разбирается с первым сообщением. Проверим на двух потребителях одной очереди: 10 сообщений, потребитель A обрабатывает 100 мс, потребитель B — мгновенно.

await ch.BasicQosAsync(
    prefetchSize: 0,      // лимит по размеру в байтах; 0 — не ограничивать (на практике всегда 0)
    prefetchCount: 1,     // сколько неподтверждённых сообщений разрешено держать потребителю
    global: false);       // false — лимит на каждого потребителя, true — общий на весь канал
АргументЧто означает
prefetchSizeограничение по суммарному размеру неподтверждённых сообщений в байтах; 0 — без ограничения. Ограничивать «по штукам» практичнее, поэтому обычно 0
prefetchCountсколько сообщений потребитель может держать неподтверждёнными одновременно. 1 — строго по одному; 10 — пачкой
globalfalse — лимит считается для каждого потребителя отдельно; true — на весь канал (все потребители канала делят один лимит)

Код опыта: два потребителя на одной очереди, у A обработка 100 мс, у B — мгновенная. Опыт повторяется дважды — с окном 1 и с окном 10. Подписка A идёт первой, поэтому именно ему брокер отдаёт первое сообщение:

using System.Text;                                          // Encoding.UTF8.GetBytes
using RabbitMQ.Client;                                      // ConnectionFactory, IChannel
using RabbitMQ.Client.Events;                               // AsyncEventingBasicConsumer

var factory = new ConnectionFactory { HostName = "localhost" };  // порт 5672 и guest/guest — по умолчанию

foreach (var prefetch in new[] { 1, 10 })                   // два прогона: окно 1 и окно 10
{
    await using var conn = await factory.CreateConnectionAsync();  // своё соединение на прогон
    await using var pub  = await conn.CreateChannelAsync();        // канал публикации
    await pub.QueueDeclareAsync("q.prefetch", durable: false, exclusive: false, autoDelete: false); // очередь опыта
    await pub.QueuePurgeAsync("q.prefetch");                       // чистим остатки прошлого прогона

    for (int i = 1; i <= 10; i++)                                  // 10 сообщений в очередь
        await pub.BasicPublishAsync("", "q.prefetch", Encoding.UTF8.GetBytes($"job-{i}"));

    int a = 0, b = 0;                                           // сколько сообщений обработал каждый
    var done = new TaskCompletionSource();                      // сигнал «все 10 обработаны»
    await using var chA = await conn.CreateChannelAsync();      // канал потребителя A
    await using var chB = await conn.CreateChannelAsync();      // канал потребителя B
    await chA.BasicQosAsync(0, (ushort)prefetch, false);        // окно A: столько неподтверждённых разрешено
    await chB.BasicQosAsync(0, (ushort)prefetch, false);        // окно B: такое же

    var consA = new AsyncEventingBasicConsumer(chA);            // A — медленный потребитель
    consA.ReceivedAsync += async (_, ea) =>
    {
        await Task.Delay(100);                                  // обработка 100 мс
        Interlocked.Increment(ref a);                           // считаем сообщение на A
        await chA.BasicAckAsync(ea.DeliveryTag, false);         // подтверждаем — окно освобождается
        if (Volatile.Read(ref a) + Volatile.Read(ref b) == 10) done.TrySetResult(); // всё обработано?
    };

    var consB = new AsyncEventingBasicConsumer(chB);            // B — мгновенный потребитель
    consB.ReceivedAsync += async (_, ea) =>
    {
        Interlocked.Increment(ref b);                           // обработал сразу
        await chB.BasicAckAsync(ea.DeliveryTag, false);         // подтверждаем
        if (Volatile.Read(ref a) + Volatile.Read(ref b) == 10) done.TrySetResult();
    };

    await chA.BasicConsumeAsync("q.prefetch", autoAck: false, consA);  // A подписывается первым
    await Task.Delay(50);                                       // A уже получил своё окно
    await chB.BasicConsumeAsync("q.prefetch", autoAck: false, consB);  // затем подписывается B

    await done.Task.WaitAsync(TimeSpan.FromSeconds(10));        // ждём, пока обработаются все 10
    Console.WriteLine($"prefetch={prefetch}/{prefetch}, A slow: A={a} B={b}");  // кто сколько забрал
}
prefetch=1/1, A slow: A=1 B=9     # окно 1: A держит одно, остальные 9 уходят быстрому B
prefetch=10/10, A slow: A=10 B=0  # окно 10: первый подключившийся забрал всю пачку, B простоял
  • С prefetch = 1 каждый потребитель держит одно сообщение: пока A занят, B забирает остальные. Нагрузка распределяется по скорости обработки.
  • С prefetch = 10 тот, кто подключился первым, забирает всю пачку (в этом прогоне — все 10) и обрабатывает их последовательно, а второй простаивает. Именно так «один медленный потребитель съедает очередь».

Правило: prefetch = столько сообщений, сколько потребитель реально обрабатывает параллельно. Для последовательной обработки — 1. Для пачки из 10 параллельных задач — 10–20. Слишком большой prefetch означает «захват» очереди и большой объём работы, которая при падении начнётся заново.

Конкуренция и масштабирование

Что нужноКак делаетсяСледствие
Больше параллельной обработкиНесколько потребителей на одну очередь (в процессе или на разных репликах)Сообщения делятся между ними; порядок обработки не гарантируется
Несколько независимых обработчиков одного событияНесколько очередей, привязанных к одному exchangeКаждая очередь получает свою копию сообщения
Порядок обработкиОдин потребитель + prefetch = 1Медленнее, но сообщения идут по порядку

Важно: одна очередь = одна работа. Если два разных сервиса подписаны на одну очередь, они будут делить сообщения, а не получать каждому. Для «каждому по копии» нужны разные очереди.

Кто может быть этими «несколькими потребителями» — это всегда отдельные подписки, у каждой свой вызов BasicConsumeAsync:

  • в одном процессе — несколько каналов и по объекту AsyncEventingBasicConsumer на каждом (в опыте с prefetch выше — именно так: A и B в одной программе);
  • несколько процессов на одной машине — например, два запущенных экземпляра одной и той же консольной программы;
  • разные машины и реплики — контейнеры одного сервиса на разных узлах.

Для брокера «потребитель» — это конкретная подписка (consumer tag на канале), а не процесс: каждое сообщение он отдаёт ровно одной подписке.

Потребитель в BackgroundService

В ASP.NET потребитель живёт в фоновом сервисе: соединение и канал создаются один раз, подписка — на всё время работы, а при остановке приложения канал закрывается, и неподтверждённые сообщения возвращаются в очередь.

«Один раз» — это «пока приложение работает». Соединение не открывается на каждое сообщение: подписка должна быть активна всё время, иначе брокеру некуда присылать сообщения. Когда приложение останавливается, сервис завершается и соединение закрывается — «вечного» сокета нет. Если соединение разорвётся со стороны сети или брокера, переподключение делает сам клиент: в RabbitMQ.Client 7.x по умолчанию включены AutomaticRecoveryEnabled = true и TopologyRecoveryEnabled = true (проверено на 7.2.2). Проверено и на живом брокере: контейнер RabbitMQ перезапустили, пока потребитель работал, — клиент восстановил соединение, канал, подписку и объявление очереди сам, и следующее сообщение снова дошло до обработчика.

public sealed class OrdersConsumer(IConnection conn, IServiceScopeFactory scopes) : BackgroundService // DI даёт соединение и фабрику scope
{
    protected override async Task ExecuteAsync(CancellationToken ct)  // ct отменяется при остановке приложения
    {
        await using var ch = await conn.CreateChannelAsync(cancellationToken: ct); // свой канал на всё время жизни сервиса
        await ch.BasicQosAsync(0, prefetchCount: 10, global: false);               // не больше 10 неподтверждённых сообщений

        var consumer = new AsyncEventingBasicConsumer(ch);                         // подписчик на этом канале
        consumer.ReceivedAsync += async (_, ea) =>                                 // обработчик каждого сообщения
        {
            using var scope = scopes.CreateScope();      // scoped-сервисы (DbContext) — из scope
            try
            {
                await scope.ServiceProvider.GetRequiredService<OrderHandler>()   // ваш scoped-обработчик
                           .HandleAsync(ea.Body, ct);                            // работа с телом сообщения
                await ch.BasicAckAsync(ea.DeliveryTag, false);                   // успех: убрать из очереди
            }
            catch (Exception)
            {
                await ch.BasicNackAsync(ea.DeliveryTag, false, requeue: false);  // ошибка: в DLX, не в очередь
            }
        };

        await ch.BasicConsumeAsync("orders.new", autoAck: false, consumer, cancellationToken: ct); // подписка
        await Task.Delay(Timeout.Infinite, ct);           // держим сервис живым до остановки
    }
}

Что здесь за что отвечает:

ЭлементЧто означает
OrdersConsumer(IConnection conn, IServiceScopeFactory scopes)первичный конструктор: DI передаёт singleton-соединение и фабрику scope
: BackgroundServiceбазовый класс фонового сервиса ASP.NET: хост вызывает ExecuteAsync при старте и отменяет токен при остановке
CreateChannelAsync(cancellationToken: ct)канал создаётся один раз; токен прерывает открытие, если приложение останавливают
BasicQosAsync(0, prefetchCount: 10, global: false)потребитель держит не больше 10 неподтверждённых сообщений (разбор аргументов — выше)
scopes.CreateScope()новый DI-scope на каждое сообщение: DbContext и другие scoped-сервисы нельзя держать в singleton-потребителе
GetRequiredService<OrderHandler>()получить scoped-обработчик из этого scope
BasicAckAsync / BasicNackAsyncоба исхода обработки обязательны: иначе сообщение останется неподтверждённым
BasicConsumeAsync(..., cancellationToken: ct)подписка на очередь; токен позволяет отменить её при остановке
Task.Delay(Timeout.Infinite, ct)не даёт ExecuteAsync завершиться: иначе хост решит, что сервис закончил работу
  • Скоуп на сообщение. DbContext и другие scoped-сервисы нельзя держать в singleton-потребителе: на каждое сообщение — свой IServiceScope.
  • Остановка не теряет работу: канал закрывается, неподтверждённые сообщения возвращаются в очередь и будут доставлены другому экземпляру.
  • Исключение не должно «убивать» подписку. Любая ошибка внутри обработчика должна заканчиваться ack или nack, иначе сообщение останется неподтверждённым.
★ Что запомнить из главы
  • autoAck: false — обязательный минимум: подтверждение после обработки, иначе падение потребителя теряет сообщение.
  • Доставка at-least-once: сообщение может прийти дважды (Redelivered=True) — обработчик должен быть идемпотентным.
  • prefetch определяет справедливость: 1 — по скорости обработки, большое число — «захват» очереди одним потребителем.
  • Одна очередь — одна работа: несколько сервисов на одной очереди делят сообщения; для копий нужны разные очереди.
  • В BackgroundService — свой scope на сообщение и обязательный ack/nack в каждом исходе.
