Глава 12. Исключения: try/catch/finally, фильтры when, свои исключения

try/catch знают все, но finally, throw; против throw ex;, фильтры when (…) и «когда своё исключение не нужно» — уже нет. Разберём на реальных случаях из бэкенда.

основная глава

Что такое исключение и когда оно уместно

Исключение — сигнал «здесь что-то пошло не так, и я не могу это исправить на месте». Оно раскручивает стек до ближайшего catch.

Почему «исключения вместо if» — плохо

Выброс исключения стоит дорого: создаётся объект, снимается stack trace. В горячем пути такое «управление потоком» съедает больше, чем сам алгоритм.

try / catch / finally

try
{
    var order = await repository.GetAsync(id, ct);   // опасная часть
    return Ok(order);
}
catch (TimeoutException ex)          // 1) конкретный тип — первым
{
    _logger.LogWarning(ex, "таймаут зависимости");
    return StatusCode(504);
}
catch (Exception ex)                  // 2) общий — последним
{
    _logger.LogError(ex, "непредвиденная ошибка");
    throw;                            // 3) throw; — сохраняет исходный стек
}
finally
{
    // выполнится всегда: при успехе, при исключении и при return внутри try
    _metrics.Dec("in_flight");
}
  • Порядок важен: catch проверяются сверху вниз, поэтому конкретные типы идут раньше общего — иначе общий «съест» всё.
  • finally выполняется всегда, в том числе при return внутри try. Для ресурсов предпочтительнее using/await using — это тот же finally, только короче.
  • throw; против throw ex;: throw ex; обнуляет стек и вы теряете место, где ошибка случилась. Внутри catch — только throw;.
  • Не логируйте и не пробрасывайте одновременно на каждом уровне: один и тот же стек окажется в логе трижды. Логирует тот, кто обрабатывает, либо один раз на границе запроса.

Фильтры when: поймать не «всё такое», а «именно это»

catch (Тип e) when (условие) — обработчик срабатывает, только если условие истинно. Главное отличие от if внутри catch: фильтр проверяется до раскрутки стека. Если условие ложно, исключение выглядит так, будто этого catch не было: стек не портится, отладчик останавливается в исходной точке.

// 1) различаем «отменил клиент» и «истёк наш таймаут»
try
{
    return await _client.GetStringAsync(url, cts.Token);
}
catch (OperationCanceledException) when (!ct.IsCancellationRequested)
{
    // клиент НЕ отменял → это наш таймаут, ошибку можно повторить (гл. 27 .NET-раздела)
    throw new TimeoutException("зависимость не ответила");
}
// если клиент отменил — фильтр ложен, и исключение идёт дальше как обычная отмена

// 2) разные HTTP-коды — разные реакции, без вложенных if
catch (HttpRequestException ex) when (ex.StatusCode == HttpStatusCode.TooManyRequests)
{
    await Task.Delay(TimeSpan.FromSeconds(1), ct);   // 429: подождать и повторить
}
catch (HttpRequestException ex) when (ex.StatusCode >= HttpStatusCode.InternalServerError)
{
    throw;                                           // 5xx: отдать наверх как есть
}
  • Зачем фильтр, а не if: с if исключение уже поймано, и чтобы «не обрабатывать», придётся писать throw; — обработчик уже сработал. Фильтр просто не даёт ему сработать.
  • Проверка дешёвая и без побочных эффектов: фильтр выполняется в момент исключения.
  • Классика бэкенда: when (!ct.IsCancellationRequested) отделяет «клиент ушёл» (не ошибка, не логируем) от «мы не успели» (ошибка зависимости).

Свои исключения: когда нужны, а когда нет

public sealed class OrderNotFoundException(Guid orderId)
    : Exception($"Заказ {orderId} не найден")
{
    public Guid OrderId { get; } = orderId;          // полезные данные — в свойство
}

// обёртка чужой ошибки: сохраняем причину
throw new PaymentFailedException("платёж отклонён", innerException: ex);
  • Имя заканчивается на Exception — соглашение, на нём держатся анализаторы и обработчики.
  • Наследуйтесь от Exception, добавьте конструкторы с innerException и, если нужно, данные (например, OrderId).
  • Оправдано: вызывающий должен различать ситуации (catch (OrderNotFoundException) → 404); иначе хватает стандартных (ArgumentNullException, InvalidOperationException).
  • Не заменяйте исключением результат: «не найдено» — нормальный сценарий поиска, верните null/bool.
  • Оборачивая, передавайте причину в innerException — иначе она потеряется в логах.

Исключения и async

  • Исключение внутри async-метода складывается в задачу, а не вылетает при вызове: поймать его можно только через await (C# гл. 9).
  • await пробрасывает первое исключение как есть; AggregateException появляется при Task.Wait()/Task.Result — ещё одна причина их не использовать (гл. 10).
  • При Task.WhenAll задача падает с первым исключением, остальные доступны через task.Exception — если нужно, разбирайте их отдельно.
  • async void — исключение некуда положить: оно уходит в контекст и роняет процесс (гл. 10).

Что не делать

АнтипаттернЧем плохо

catch (Exception ex) { throw ex; }теряется исходный стек
try/catch в цикле на каждую итерациюдорого и маскирует причину; ловите снаружи пачки

★ Что запомнить из главы
  • catch — от конкретного к общему; finally выполняется всегда (для ресурсов есть using).
  • throw; сохраняет стек, throw ex; — нет.
  • when — фильтр, который проверяется до раскрытия стека; так различают «отменил клиент» и «наш таймаут», 429 и 5xx.
  • Своё исключение — когда вызывающий должен различать ситуации; имя — …Exception, причина — в innerException.
  • Исключение в async живёт в задаче и всплывает при await; async void роняет процесс.
  • Не глотать, не дублировать логи, не использовать исключения как if.
