Глава 29. REST, gRPC и брокеры сообщений: что когда выбирать

REST с JSON удобен, но не всегда оптимален: текст и сериализация стоят ресурсов. Разберём, когда остаться на REST, а когда перейти на gRPC или брокер сообщений.

В чём суть вопроса

REST поверх HTTP передаёт данные в текстовом виде (JSON). Это удобно для человека, но каждый вызов стоит: сериализация в JSON и обратно, больше байт по сети, больше парсинга на обеих сторонах. На единичном запросе это незаметно, но между сервисами внутри системы вызовов могут быть миллионы.

Поэтому вариантов три, и это не «лучше/хуже», а «для чего»:

  • REST — публичный, человекочитаемый API;
  • gRPC — быстрые и строгие вызовы между сервисами;
  • брокер сообщений — асинхронная передача, когда ответ не нужен «сейчас».

REST: когда он остаётся правильным выбором

Что это: HTTP + JSON (или XML), ресурсы и методы (GET, POST…), «свободный» контракт.

Плюсы:

  • читается человеком и легко отлаживается (curl, браузер, Postman);
  • работает везде: браузеры, мобильные приложения, любые языки;
  • штатное кэширование по HTTP (заголовки, CDN, прокси);
  • не требует кодогенерации — контракт можно менять эволюционно.

Выбираем REST, когда:

  • API публичный или интеграция с внешними системами (там ждут HTTP+JSON);
  • клиенты — браузер или мобильное приложение;
  • важны простота, совместимость и скорость разработки, а не экономия байтов;
  • вызовы нечастые (в сравнении с внутренним обменом).

gRPC: когда он выигрывает

Что это: HTTP/2 + Protobuf (бинарный формат), контракт описывается в .proto-файле, клиенты и серверы генерируются из него.

Что такое HTTP/2

HTTP — протокол, по которому клиент и сервер обмениваются запросами и ответами. Версия HTTP/1.1 передаёт по одному соединению по одному запросу за раз: чтобы получить десять файлов, браузер открывал около шести соединений параллельно. HTTP/2 (его используют современные сайты и gRPC) устроен иначе:

  • мультиплексирование — много запросов идут одновременно по одному соединению и не блокируют друг друга;
  • сжатие заголовков — служебные поля передаются компактно;
  • бинарные кадры вместо текстовых строк — компактнее и быстрее разбирать;
  • server push (сервер сам присылает нужное) — на практике почти не используется.

Для gRPC это принципиально: мультиплексирование делает дешёвыми частые вызовы, а бинарные кадры дают основу для стриминга — ответа потоком (см. ниже).

Контракт в .proto — из него создаются и сервер, и клиент

service Orders {
  rpc GetOrder (GetOrderRequest) returns (OrderReply);
}

message GetOrderRequest { int32 id = 1; }
message OrderReply      { int32 id = 1; string status = 2; }
Что означает rpc в этом файле

rpc — remote procedure call, «удалённый вызов процедуры». Это ключевое слово Protobuf-контракта: «объяви метод, который можно вызвать по сети».

  • service Orders — набор методов, аналог интерфейса.
  • rpc GetOrder (GetOrderRequest) returns (OrderReply) — метод GetOrder принимает сообщение GetOrderRequest и возвращает OrderReply.
  • message … — структуры данных (аналог DTO); числа = 1 — номера полей для бинарного формата.

Из этого файла генератор создаёт серверный интерфейс и клиентский класс: в C# вызов выглядит как обычный метод, а по сети уходят бинарные кадры HTTP/2.

Плюсы:

  • компактнее и быстрее: бинарный формат + сериализация без лишних строк;
  • HTTP/2: мультиплексирование (много вызовов в одном соединении) и стриминг (поток данных в одну или обе стороны);
  • строгий контракт: если что-то не совпало — видно на этапе сборки, а не в рантайме;
  • кодогенерация для многих языков — удобно в «разноязычной» системе.

Ограничения (о них надо честно сказать):

  • нечитаемо «вручную» — нет простого curl (нужен grpcurl);
  • браузеры требуют прослойку (gRPC-Web), то есть «для сайта» это редко первый выбор;
  • хуже дружит с прокси, кэшированием и просто «поглазеть» в логе;
  • контракт строгий: изменения требуют аккуратности.
curl и grpcurl — в чём разница

curl — консольная утилита, которой отправляют HTTP-запросы прямо из терминала: ей проверяют, что вернёт эндпоинт. Обычный REST-ответ — текст (JSON), поэтому его удобно читать глазами:

curl https://api.example.com/orders/42

grpcurl — отдельная утилита того же назначения, но для gRPC. Она знает .proto-контракт и собирает из него бинарное сообщение. curl здесь не поможет: тело gRPC-запроса — не текст, а бинарные кадры HTTP/2.

grpcurl -d '{"id": 42}' localhost:5001 orders.Orders/GetOrder

Итог: REST удобно «пощупать» обычным curl, gRPC — только grpcurl или специальным клиентом (Postman, Insomnia, grpcui).

Выбираем gRPC, когда:

  • это обмен между своими сервисами, а не с внешним миром;
  • вызовов много и часто, важны задержка и трафик;
  • нужен стриминг (логи, телеметрия, большие выборки потоком).

Брокеры сообщений: когда нужна асинхронность

Что это: отдельная система-«почтальон», куда один сервис кладёт сообщение, а другой забирает и обрабатывает — не одновременно и не дожидаясь друг друга. Таких систем много, вот самые известные:

БрокерЧем известен
RabbitMQКлассические очереди: сообщение достаётся одному потребителю; гибкая маршрутизация
KafkaЖурнал событий: читать можно многократно и несколькими группами; для потоков данных
NATSОчень лёгкий и быстрый; JetStream добавляет надёжную доставку
ActiveMQ / ArtemisПроверенный брокер родом из мира Java, поддерживает JMS и AMQP
Azure Service Bus, Amazon SQS + SNSОблачные очереди «как сервис»: администрировать не нужно
Google Pub/SubОблачные подписки на события
Redis (Pub/Sub, Streams)Годится для простой передачи, если Redis уже есть в проекте

Различаются они деталями (порядок сообщений, повторное чтение, гарантии доставки), но идея одна: сервисы общаются не напрямую, а через посредника.

Плюсы:

  • развязка по времени: отправитель не ждёт, пока получатель закончит;
  • сглаживание пиков: очередь копит сообщения, а обработчик разбирает их в своём темпе (это и есть backpressure из главы 26);
  • надёжность: сообщение не потеряется, если получатель был недоступен;
  • масштабирование: обработчиков можно добавить — они разберут очередь быстрее.

Что нужно понимать (минусы и особенности):

  • ответ приходит не сразу — данные станут согласованными «потом» (eventual consistency);
  • доставка обычно «хотя бы один раз» (at-least-once) → возможны дубликаты, поэтому обработчик должен быть идемпотентным (повторная обработка не должна ломать данные);
  • появляется инфраструктура, которую надо ставить, мониторить и чинить (в отличие от простого HTTP-вызова);
  • порядок сообщений гарантируется не везде и не всегда.

Выбираем брокер, когда:

  • работа долгая и ответ не нужен прямо сейчас (лучше сразу вернуть 202 Accepted — ср. глава 26);
  • нужно сгладить пики нагрузки;
  • это события для других систем («заказ оформлен» → уведомления, отчётность, склад);
  • важна надёжность: «сделать обязательно, даже если сервис падал».

Как выбирать — по вопросам

  1. Кто клиент? Браузер или внешняя система → REST. Свой сервис → можно gRPC.
  2. Ответ нужен прямо сейчас? Да → REST или gRPC. Нет (или «потом») → брокер.
  3. Как много и часто? Внутренний обмен с миллионами вызовов → gRPC.
  4. Нужен стриминг? → gRPC.
  5. Нужно пережить пики и не потерять работу? → брокер.
★ На практике это не «или», а комбинация

В реальной системе почти всегда используют все три:

Клиент (браузер)
     │  REST + JSON
     ▼
Публичный сервис A ──gRPC──► Внутренний сервис B ──gRPC──► Сервис C
     │
     └──сообщение в брокер──► Фоновый воркер (тяжёлая обработка)
                              клиенту сразу ответили 202 Accepted

То есть: REST — на границе с внешним миром, gRPC — внутри, брокер — для того, что можно сделать позже.

Что сказать на интервью

«Я выбираю по трём вопросам: кто клиент, нужен ли ответ сейчас и какова интенсивность обмена. Публичный API — REST: понятно, кэшируется, работает везде. Внутренние вызовы — gRPC: бинарный Protobuf и HTTP/2 дают меньше трафика и задержку, плюс стриминг. Долгие и «пиковые» операции — брокер: клиенту отвечаем 202, а работу делает воркер; там же нужна идемпотентность, потому что доставка «хотя бы один раз». На практике всё три вместе: REST снаружи, gRPC внутри, брокер для событий».
