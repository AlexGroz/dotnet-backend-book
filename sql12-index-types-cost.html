Глава 12. Другие типы индексов и их цена

B-tree покрывает почти всё, но бывают задачи и для других типов. И у любого индекса есть цена — поговорим и о ней.

Типы индексов в PostgreSQL

ТипДля чегоКогда брать
B-tree (по умолчанию)Равенство, диапазоны, сортировка, префикс95% случаев — начинайте с него
HashТолько равенство (=)Редко: B-tree умеет то же и больше

BRINДиапазоны блоковОгромные таблицы с естественным порядком (например, по дате)

GIN — когда значение «составное»

«Составное» значение — это когда внутри одного значения лежит много элементов, и мы ищем не «равно целиком», а «содержит такой-то элемент». B-tree так не умеет: он сравнивает значение как единое целое (глава 10).

Примеры «составных» значений и что значит «содержит»:

  • массив {'новый','срочный'} → «есть ли элемент 'срочный'»;
  • jsonb {"city":"Сургут","tags":[…]} → «есть ли ключ city со значением «Сургут»»;
  • текст, разобранный на слова (тип tsvector) → «встречается ли слово заказ».

Два примера

-- 1) поиск внутри jsonb: «есть ли такое ключ/значение»
CREATE INDEX ON events USING gin (payload);

-- 2) полнотекстовый поиск: «есть ли слово в тексте»
CREATE INDEX ON articles USING gin (to_tsvector('russian', body));
Что такое to_tsvector('russian', body)
  • body — колонка с текстом (например, тело статьи).
  • to_tsvector(...) — функция, которая разбирает текст на слова и собирает из них специальную «карту» (tsvector) — так текст «видит» полнотекстовый поиск.
  • 'russian' — какой словарь использовать: правила разбиения на слова и приведения их к основе. Для русского — 'russian', для английского — 'english'.

Проще говоря, это «подготовка текста к поиску по словам». Что получается — можно посмотреть так:

SELECT to_tsvector('russian', 'Быстрая доставка заказов');
-- 'быстр':2 'доставк':1 'заказ':3   ← слова приведены к основе, с позициями

Именно по такой «карте» GIN-индекс и умеет быстро отвечать на вопрос «встречается ли слово».

Отдельно — про поиск по тексту, потому что здесь чаще всего «индекс есть, а он не работает». Всё решает форма условия:

Условие в запросеИндекс сработает?Что нужно
name = 'Иван'даобычный B-tree
name LIKE 'Иван%' (префикс)даB-tree; при не-C-коллации — text_pattern_ops
name LIKE '%Иван%' (внутри)нетGIN + pg_trgm
name ILIKE '%иван%'нетGIN + pg_trgm (регистр учитывается уже внутри триграмм)
name ~ 'иван' (regex)нетGIN + pg_trgm (он умеет и регулярные выражения)
lower(name) = 'иван'нетфункциональный индекс (lower(name)) — глава 11
 
CREATE EXTENSION IF NOT EXISTS pg_trgm;                        -- «триграммы»: разбивает текст на 3-символьные куски

CREATE INDEX customers_name_trgm ON customers
USING gin (name gin_trgm_ops);                                 -- gin_trgm_ops — операторный класс для LIKE/regex

EXPLAIN (ANALYZE)
SELECT * FROM customers WHERE name ILIKE '%иван%';
-- Bitmap Index Scan on customers_name_trgm    ← индекс реально участвует
--   Index Cond: (name ~~* '%иван%'::text)
  • Почему B-tree не может: он упорядочен по началу строки, поэтому '%Иван%' может встретиться где угодно — придётся прочитать все строки.
  • Цена pg_trgm: индекс заметно больше B-tree, запись медленнее. Ставят его только под реальный поиск по подстроке, а не «на всякий случай».
  • Короткие шаблоны: один-два символа в LIKE '%x%' дают слишком много совпадений — индекс почти не помогает (и это нормально).
  • Проверка обязательна: EXPLAIN должен показать Bitmap Index Scan. Если там Seq Scan — условие написано не в той форме (часто мешает функция над колонкой или конкатенация).

BRIN — «мини-индекс» для огромных таблиц

BRIN хранит не значения строк, а краткие диапазоны по блокам страниц: для каждой группы страниц запоминает минимальное и максимальное значение колонки. Поэтому он занимает килобайты там, где B-tree занимает гигабайты, но полезен только если данные физически упорядочены (типично — таблица, куда пишут «по времени», например журнал событий).

-- индекс по дате: «страницы с 1 по 128» → min/max created_at
CREATE INDEX events_created_brin ON events
USING brin (created_at)
WITH (pages_per_range = 32);           -- сколько страниц в одной «сводке»

-- насколько он меньше B-tree — видно по размеру
SELECT indexrelname, pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM   pg_stat_user_indexes
WHERE  relname = 'events';

-- BRIN обновляет сводки не сразу: новые страницы надо «досчитать»
SELECT brin_summarize_new_values('events_created_brin');
-- (или включить autosummarize = on, чтобы это делалось само)
  • pages_per_range — компромисс: меньше значение → сводки точнее (меньше лишних страниц читаем), но индекс больше и обновляется чаще. Для «журнала по времени» обычно 32–128.
  • Когда BRIN плох: данные в таблице лежат не по порядку (например, created_at приходит «из прошлого» пачками) — тогда в каждом диапазоне окажется «от минимума до максимума», и BRIN не отсечёт ничего. Маленькая таблица тоже не нужна: B-tree дешевле и точнее.
  • Что важно: BRIN хорошо работает вместе с секционированием (глава 26) — и там, и там выигрыш идёт от «данные упорядочены по времени».

GiST — «соседство» и пересечения

GiST нужен, когда условие — не «равно» и не «попадает в диапазон чисел», а пересечение, вхождение, близость: геометрия, диапазоны (tsrange, int4range), полнотекстовый поиск (альтернатива GIN).

-- (а) бронирования: «нет пересечений по времени для одного номера»
CREATE TABLE bookings (
    room_id int,
    period  tsrange,
    EXCLUDE USING gist (room_id WITH =, period WITH &&)   -- && = «пересекается»
);
-- теперь две пересекающиеся брони физически невозможно вставить: база не даст

-- (б) геоданные и «ближайшие» объекты (PostGIS): KNN-поиск по расстоянию
CREATE INDEX ON shops USING gist (location);
SELECT name FROM shops ORDER BY location <-> point '(61.25,73.42)' LIMIT 10;   -- <-> = расстояние

Правило выбора простое: равенство и диапазоны — B-tree, «множества внутри значения» — GIN, пересечения и близость — GiST, «огромная таблица с естественным порядком» — BRIN. Если сомневаетесь — начните с B-tree и проверьте план (глава 15).

Цена индексов

Индекс ускоряет чтение, но у него есть четыре «счёта к оплате»:

Что стоитПочему
Место на диске и в памятиИндекс хранится отдельно и тоже кэшируется; иногда он сравним по размеру с таблицей
Скорость записиКаждый INSERT/UPDATE/DELETE обновляет все индексы таблицы
ОбслуживаниеИндексы «раздуваются» вместе с таблицей и требуют VACUUM / REINDEX (глава 25)
Время планированияЧем больше индексов, тем дольше планировщик перебирает варианты (глава 13)
Правило разумного минимума

Индекс должен отрабатывать конкретные запросы. Индекс «на всякий случай» только замедляет запись и ест место. Если индекс давно никто не использовал — его стоит удалить.

Как найти неиспользуемые индексы

SELECT indexrelname, idx_scan
FROM   pg_stat_user_indexes
WHERE  idx_scan = 0          -- ни разу не использовался
ORDER  BY pg_relation_size(indexrelid) DESC;
Прежде чем удалять: «0 использований» бывает обманчивым
  • Статистика могла быть сброшена. Тогда все счётчики начинаются с нуля, хотя индекс прекрасно работает. Сбрасывается она при: pg_stat_reset(), pg_stat_reset_single_table_counters(), восстановлении из бэкапа и аварийном завершении сервера (при чистой остановке счётчики сохраняются).
  • Индекс редкий. Он нужен раз в месяц для отчёта — в момент проверки idx_scan = 0 это нормально.
  • Индекс новый. Его добавили вчера, и запросы просто ещё не приходили.

Когда статистика сбрасывалась, видно прямо в системном представлении:

-- когда сбрасывалась статистика текущей базы (NULL — ни разу)
SELECT datname, stats_reset, now() - stats_reset AS ago
FROM   pg_stat_database
WHERE  datname = current_database();

-- то же для pg_stat_statements (данные самого расширения)
SELECT stats_reset FROM pg_stat_statements_info;

В PostgreSQL 16 и новее у индексов есть ещё last_idx_scan — время последнего использования. Это точнее счётчика: «ни разу с момента сброса» и «последний раз три месяца назад» — разные вещи. Если у вас версия старше, колонки нет — проверьте \d pg_stat_user_indexes.

-- PostgreSQL 16+: когда индекс реально использовали в последний раз
SELECT indexrelname, idx_scan, last_idx_scan
FROM   pg_stat_user_indexes
ORDER  BY last_idx_scan NULLS FIRST;   -- сначала те, что не использовали ни разу

Практическое правило: удаляем, если idx_scan = 0 и stats_reset был давно (недели или месяцы) и вы понимаете, какие запросы индекс обслуживал. Удалять безопаснее через DROP INDEX CONCURRENTLY (не блокирует запись), а план отката — это сохранённый CREATE INDEX из pg_get_indexdef().

Как проверить размер индексов 
SELECT indexrelname,
       pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM   pg_stat_user_indexes
ORDER  BY pg_relation_size(indexrelid) DESC
LIMIT  10;

Зачем это смотреть на практике:

  • Место и бэкапы. Индекс легко оказывается больше самой таблицы: суммарный размер — pg_size_pretty(pg_indexes_size('orders')), вся таблица с индексами — pg_total_relation_size('orders'). От этого зависят диск, скорость бэкапа и восстановления.
  • Цена записи. Каждый индекс обновляется на каждом INSERT/UPDATE: чем больше «ненужных» индексов, тем медленнее запись и больше WAL.
  • Дубли и раздутие. Два индекса по одним и тем же колонкам — лишняя работа; индекс, раздутый после массовых удалений (bloat), лечится REINDEX — и это видно именно по размеру (pg_relation_size против числа строк).
  • Решение «добавить ещё один». Прежде чем строить новый индекс, полезно увидеть, сколько уже занимают существующие и какой из них реально используется.

Bloat индексов: как измерить и что делать

Индекс «раздувается» так же, как таблица (глава 25): DELETE и UPDATE оставляют мёртвые записи, обычный VACUUM помечает место свободным для повторного использования, но файл не уменьшается. Признак проблемы — индекс занимает в разы больше, чем должен при текущем числе строк: читать его дольше, в кэш он влезает хуже.

-- (а) грубая оценка: размер индекса рядом с размером таблицы и числом использований
SELECT indexrelname,
       pg_size_pretty(pg_relation_size(indexrelid)) AS index_size,
       idx_scan,                                     -- сколько раз индекс использовали
       pg_size_pretty(pg_relation_size(relid))      AS table_size
FROM   pg_stat_user_indexes
WHERE  relid = 'orders'::regclass
ORDER  BY pg_relation_size(indexrelid) DESC;

-- (б) точно: плотность страниц индекса (расширение pgstattuple)
CREATE EXTENSION IF NOT EXISTS pgstattuple;
SELECT * FROM pgstatindex('orders_status_created_at_idx');
-- avg_leaf_density ≈ 90 %  → индекс плотный, всё хорошо
-- avg_leaf_density ≈ 55 %  → половина места пустая, индекс раздут
  • Что считать нормой: avg_leaf_density 90 % и выше. Если он ниже ~70 % при большом leaf_fragmentation — индекс стоит перестроить.
  • Как лечить: REINDEX INDEX CONCURRENTLY orders_status_created_at_idx; — перестраивает без блокировки записи (нужны время и примерно двойное место на диске; внутри транзакции нельзя). Для всей таблицы — REINDEX TABLE CONCURRENTLY (PostgreSQL 12+).
  • Почему раздувается: массовые DELETE/UPDATE, обновления индексируемых колонок (они выключают HOT — глава 25), fillfactor = 100 по умолчанию и autovacuum, который не успевает.
  • Мониторинг в проде: снимать pg_relation_size по индексам раз в сутки в свою таблицу истории и сравнивать с числом строк. Алерт — «размер растёт, а строк столько же»; это надёжнее, чем разово посмотреть глазами (глава 33).
  • Не путать: раздутый индекс продолжает работать — это деградация производительности и места, а не поломка. Поэтому перестройку планируют, а не делают в панике во время инцидента.
★ Что запомнить

Начинайте с B-tree — его хватает почти всегда. Другие типы берите под задачу: GIN — для jsonb/массивов/полнотекста, GiST — для гео и диапазонов, BRIN — для огромных «по времени» таблиц. И помните про цену: место, замедление записи, обслуживание. Индексов должно быть ровно столько, сколько нужно.
