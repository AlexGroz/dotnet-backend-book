Глава 12. Другие типы индексов и их цена

B-tree покрывает почти всё, но бывают задачи и для других типов. И у любого индекса есть цена — поговорим и о ней.

Типы индексов в PostgreSQL

ТипДля чегоКогда брать
B-tree (по умолчанию)Равенство, диапазоны, сортировка, префикс95% случаев — начинайте с него
HashТолько равенство (=)Редко: B-tree умеет то же и больше

GiSTСложные типы и «соседство»Геоданные, диапазоны, поиск ближайшего
BRINДиапазоны блоковОгромные таблицы с естественным порядком (например, по дате)

GIN — когда значение «составное»

«Составное» значение — это когда внутри одного значения лежит много элементов, и мы ищем не «равно целиком», а «содержит такой-то элемент». B-tree так не умеет: он сравнивает значение как единое целое (глава 10).

Примеры «составных» значений и что значит «содержит»:

  • массив {'новый','срочный'} → «есть ли элемент 'срочный'»;
  • jsonb {"city":"Сургут","tags":[…]} → «есть ли ключ city со значением «Сургут»»;
  • текст, разобранный на слова (тип tsvector) → «встречается ли слово заказ».

Два примера

-- 1) поиск внутри jsonb: «есть ли такое ключ/значение»
CREATE INDEX ON events USING gin (payload);

-- 2) полнотекстовый поиск: «есть ли слово в тексте»
CREATE INDEX ON articles USING gin (to_tsvector('russian', body));
Что такое to_tsvector('russian', body)
  • body — колонка с текстом (например, тело статьи).
  • to_tsvector(...) — функция, которая разбирает текст на слова и собирает из них специальную «карту» (tsvector) — так текст «видит» полнотекстовый поиск.
  • 'russian' — какой словарь использовать: правила разбиения на слова и приведения их к основе. Для русского — 'russian', для английского — 'english'.

Проще говоря, это «подготовка текста к поиску по словам». Что получается — можно посмотреть так:

SELECT to_tsvector('russian', 'Быстрая доставка заказов');
-- 'быстр':2 'доставк':1 'заказ':3   ← слова приведены к основе, с позициями

Именно по такой «карте» GIN-индекс и умеет быстро отвечать на вопрос «встречается ли слово».

Ещё GIN (через расширение pg_trgm) — единственный способ ускорить LIKE '%фрагмент%', который B-tree не тянет (глава 10).

BRIN — «мини-индекс» для огромных таблиц

BRIN хранит не значения строк, а краткие диапазоны по блокам страниц. Занимает копейки, но полезен, только если данные физически упорядочены (типично — таблица, куда пишут «по времени», например журнал событий).

Цена индексов

Индекс ускоряет чтение, но у него есть четыре «счёта к оплате»:

Что стоитПочему
Место на диске и в памятиИндекс хранится отдельно и тоже кэшируется; иногда он сравним по размеру с таблицей
Скорость записиКаждый INSERT/UPDATE/DELETE обновляет все индексы таблицы
ОбслуживаниеИндексы «раздуваются» вместе с таблицей и требуют VACUUM / REINDEX (глава 25)
Время планированияЧем больше индексов, тем дольше планировщик перебирает варианты (глава 13)
Правило разумного минимума

Индекс должен отрабатывать конкретные запросы. Индекс «на всякий случай» только замедляет запись и ест место. Если индекс давно никто не использовал — его стоит удалить.

Как найти неиспользуемые индексы

SELECT indexrelname, idx_scan
FROM   pg_stat_user_indexes
WHERE  idx_scan = 0          -- ни разу не использовался
ORDER  BY pg_relation_size(indexrelid) DESC;
Прежде чем удалять: «0 использований» бывает обманчивым
  • Статистика могла быть сброшена. Тогда все счётчики начинаются с нуля, хотя индекс прекрасно работает. Сбрасывается она при: pg_stat_reset(), pg_stat_reset_single_table_counters(), восстановлении из бэкапа и аварийном завершении сервера (при чистой остановке счётчики сохраняются).
  • Индекс редкий. Он нужен раз в месяц для отчёта — в момент проверки idx_scan = 0 это нормально.
  • Индекс новый. Его добавили вчера, и запросы просто ещё не приходили.

Когда статистика сбрасывалась, видно прямо в системном представлении:

-- когда сбрасывалась статистика текущей базы (NULL — ни разу)
SELECT datname, stats_reset, now() - stats_reset AS ago
FROM   pg_stat_database
WHERE  datname = current_database();

-- то же для pg_stat_statements (данные самого расширения)
SELECT stats_reset FROM pg_stat_statements_info;

В PostgreSQL 16 и новее у индексов есть ещё last_idx_scan — время последнего использования. Это точнее счётчика: «ни разу с момента сброса» и «последний раз три месяца назад» — разные вещи. Если у вас версия старше, колонки нет — проверьте \d pg_stat_user_indexes.

-- PostgreSQL 16+: когда индекс реально использовали в последний раз
SELECT indexrelname, idx_scan, last_idx_scan
FROM   pg_stat_user_indexes
ORDER  BY last_idx_scan NULLS FIRST;   -- сначала те, что не использовали ни разу

Практическое правило: удаляем, если idx_scan = 0 и stats_reset был давно (недели или месяцы) и вы понимаете, какие запросы индекс обслуживал. Удалять безопаснее через DROP INDEX CONCURRENTLY (не блокирует запись), а план отката — это сохранённый CREATE INDEX из pg_get_indexdef().

Как проверить размер индексов 
SELECT indexrelname,
       pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM   pg_stat_user_indexes
ORDER  BY pg_relation_size(indexrelid) DESC
LIMIT  10;

Зачем это смотреть на практике:

  • Место и бэкапы. Индекс легко оказывается больше самой таблицы: суммарный размер — pg_size_pretty(pg_indexes_size('orders')), вся таблица с индексами — pg_total_relation_size('orders'). От этого зависят диск, скорость бэкапа и восстановления.
  • Цена записи. Каждый индекс обновляется на каждом INSERT/UPDATE: чем больше «ненужных» индексов, тем медленнее запись и больше WAL.
  • Дубли и раздутие. Два индекса по одним и тем же колонкам — лишняя работа; индекс, раздутый после массовых удалений (bloat), лечится REINDEX — и это видно именно по размеру (pg_relation_size против числа строк).
  • Решение «добавить ещё один». Прежде чем строить новый индекс, полезно увидеть, сколько уже занимают существующие и какой из них реально используется.
★ Что запомнить

Начинайте с B-tree — его хватает почти всегда. Другие типы берите под задачу: GIN — для jsonb/массивов/полнотекста, GiST — для гео и диапазонов, BRIN — для огромных «по времени» таблиц. И помните про цену: место, замедление записи, обслуживание. Индексов должно быть ровно столько, сколько нужно.
