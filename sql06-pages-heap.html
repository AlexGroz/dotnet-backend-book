Глава 7. Страницы и heap: где физически лежат строки

Чтобы понять, почему одни способы чтения быстрые, а другие медленные (глава 16), нужно увидеть, как данные лежат на диске. Здесь — только самое необходимое.

Таблица — это файл, разбитый на страницы

Таблица в PostgreSQL физически хранится в файле (или нескольких). Файл разбит на страницы фиксированного размера — по умолчанию 8 КБ.

  • Строки лежат внутри страниц (одна строка не может пересекать границу страницы).
  • Прочитать данные можно только страницами: даже если нужна одна строка, с диска (или из кэша) читается вся страница целиком.
Главное следствие

«Стоимость» чтения измеряется числом страниц, а не строк. Прочитать 1 строку из страницы и 50 строк из той же страницы — почти одно и то же по цене. А вот добраться до разных страниц — дорого: каждая новая страница это отдельное обращение.

Что такое heap (куча)

Сами таблицы в PostgreSQL называют heap — «куча». Это неупорядоченный набор страниц со строками: они лежат примерно в порядке вставки, но могут «расползаться» по мере изменений (глава 25). То есть «физического порядка» по колонкам у таблицы нет.

Именно поэтому, чтобы найти строки по условию, СУБД приходится либо просматривать все страницы (Seq Scan), либо пользоваться индексом (глава 16).

ctid — физический адрес строки

У каждой строки есть «адрес» — ctid: номер страницы и номер строки внутри неё. Формат — (страница, запись), например (42,3).

ctid нестабилен

При UPDATE строка физически переезжает (глава 7), и ctid меняется. Поэтому использовать ctid как ключ нельзя. Но именно им пользуются индексы: запись в индексе хранит ключ + ctid строки.

Кэш: почему второй запуск быстрее

«Второй запуск» (second run) — это тот же самый запрос, который выполняется повторно. В первый раз PostgreSQL читает нужные страницы с диска, во второй — уже из памяти: прочитанные страницы остаются в shared_buffers (память самого PostgreSQL) и в кэше страниц операционной системы. Память в сотни раз быстрее диска — отсюда и разница.

первый запуск (кэш «холодный»)   Buffers: shared hit=120     read=25_480   ← почти всё с диска
второй запуск (кэш «горячий»)    Buffers: shared hit=25_600  read=0        ← всё из памяти

Именно поэтому в плане есть строка Buffers::

Buffers: shared hit=19500 read=5800
              └─ из кэша     └─ с диска
  • hit — страница уже была в памяти (дёшево);
  • read — пришлось читать с диска (дорого);
  • dirtied — страницы, которые запрос изменил (появятся при UPDATE).
Три вывода, важных на практике
  • «Стало быстрее» ≠ «запрос улучшился». Возможно, вы просто прогрели кэш. Сравнивать «до/после» нужно при одинаковом состоянии кэша, иначе легко обмануть себя.
  • Первый запрос после рестарта медленнее — база «холодная». Для прогрева есть расширение pg_prewarm.
  • Планировщик тоже учитывает кэш: параметр effective_cache_size говорит ему, сколько данных, по его ожиданию, лежит в памяти, — и от этого зависит выбор между индексом и последовательным чтением (глава 13).

Отсюда две стратегии чтения

СтратегияКак читаетКогда выгодна
ПоследовательноСтраница за страницей, подрядКогда нужна большая часть таблицы: подряд читать дешевле
Точечно (по индексу)Прыгая к конкретным страницамКогда нужна маленькая часть строк

Первая стратегия — это Seq Scan, вторая — Index Scan. Их подробный разбор — глава 16, а сначала посмотрим, как устроены индексы (главы 9–12).

★ Что запомнить

Данные лежат страницами по 8 КБ; читаем всегда страницами, а не строками. Таблица (heap) неупорядочена, у строки есть физический адрес ctid (нестабильный). Отсюда две стратегии: читать подряд или прыгать по индексу.
