Глава 4. Команды: run, ps, logs, exec

Десять команд закрывают почти всю ежедневную работу. Важно не выучить их список, а понимать жизненный цикл контейнера — тогда каждая команда встаёт на своё место.

основная глава

Жизненный цикл: четыре состояния

create ──start──▶ running ──stop/kill──▶ exited ──rm──▶ (удалён)
                  │  ▲
                  └──┘ restart
  • created — контейнер создан, процесс ещё не запущен (бывает редко, обычно сразу run).
  • running — живёт PID 1. Как только он завершился, контейнер останавливается — даже если это была ошибка через 0,2 секунды.
  • exited — процесс завершился. Файловая система и логи остались, можно посмотреть причину.
  • удалён — исчезли записываемый слой и метаданные; образ и тома остались.

docker ps показывает только running, docker ps -a — все, включая упавшие. Это первое, что стоит проверить, когда «контейнера нет».

Зачем удалять контейнеры (и когда)

Из жизненного цикла следует неочевидная для новичка вещь: остановка и удаление — разные действия. Остановленный контейнер остаётся объектом со своими логами, кодом выхода и файлами.

Что произошлоЧто осталосьКогда это нужно
Процесс завершился (exited)Контейнер, его логи, код выхода, файлыРазобрать падение: docker logs, inspect -f '{{.State.ExitCode}}'
docker stopТо же; контейнер можно запустить снова (docker start)Временно освободить ресурсы и вернуться позже
docker rmНичего: удалены записываемый слой и метаданные; образ и тома целыКонтейнер больше не нужен

Три бытовых сценария — и в каждом своё действие:

  • Одноразовая команда (docker run --rm alpine ps aux) — с --rm: вывод посмотрели, объект не нужен.
  • Свой сервис (API, база) — без --rm: упал — смотрим логи и код выхода, а не теряем следы. Удаляют его, когда он больше не нужен, — обычно заменяя новым.
  • Уборка — docker rm <имя> для конкретного, docker container prune для всех остановленных, docker system prune -a — «всё неиспользуемое» (осторожно: образы и кэш тоже).
Почему это нормально: контейнер — расходуемый

В Docker не «лечат» контейнер, а заменяют его новым из того же образа: образ неизменяем, поэтому новый запуск предсказуем. В проде это делает оркестратор — при выкатке старые контейнеры удаляются. Данные для этого держат вне контейнера: в томе (глава 9) или в базе.

run: одна команда вместо трёх

docker run = pull + create + start: если образа нет локально, Docker сначала скачает его из реестра (pull), затем создаст контейнер (create) и запустит его (start). Флаги, которые нужны в 95 % случаев:

ФлагЧто делает
-dВ фоне (detached). Без него вывод процесса идёт в терминал, а Ctrl+C контейнер останавливает
--rmУдалить контейнер, когда процесс завершится. Нужно для одноразовых запусков; сервисам — нет, иначе пропадут логи упавшего контейнера
--name apiИмя вместо случайного. Нужно для logs, exec, stop
-p 8080:8080Опубликовать порт: хост:контейнер (глава 8)
-e KEY=valueПеременная окружения — так передают конфигурацию (глава 10)
-v pgdata:/var/lib/postgresql/dataТом или папка с данными (глава 9)
-itИнтерактивно + терминал: для sh и psql
--memory 512m --cpus 1.5Лимиты cgroups (глава 12)
--restart unless-stoppedПерезапускать после падения и перезагрузки хоста
--network appВ какую сеть подключить (глава 8)

Практика: PostgreSQL за тридцать секунд

Самый частый сценарий новичка — «нужна база, а ставить её на машину не хочется»:

# docker run                      создать и запустить контейнер
#   -d                            в фоне (detached): терминал останется свободным
#   --name pg                     имя контейнера: по нему работают exec, logs, stop, rm
#                                 (без имени Docker выдаст случайное вроде happy_turing)
#   -e POSTGRES_PASSWORD=secret   переменная окружения ВНУТРИ контейнера;
#                                 официальный образ postgres требует её при первом старте
#   -p 5432:5432                  опубликовать порт «хост:контейнер»:
#                                 слева порт на вашей машине, справа порт внутри контейнера
#   -v pgdata:/var/lib/postgresql/data
#                                 том pgdata подключить в папку данных PostgreSQL —
#                                 данные переживут удаление контейнера
#   postgres:16                   образ: официальный postgres, тег 16
#   \                             перенос длинной команды на следующую строку (bash)
docker run -d \
  --name pg \
  -e POSTGRES_PASSWORD=secret \
  -p 5432:5432 \
  -v pgdata:/var/lib/postgresql/data \
  postgres:16

# docker ps                       список РАБОТАЮЩИХ контейнеров
#                                 (ID, IMAGE, STATUS, PORTS, NAMES)
docker ps

# docker exec                     выполнить команду внутри работающего контейнера
#   -i                            держать stdin открытым (нужно интерактивным программам)
#   -t                            выделить псевдо-TTY (без него не будет приглашения и ввода)
#   pg                            имя контейнера
#   psql -U postgres              клиент PostgreSQL, пользователь postgres
docker exec -it pg psql -U postgres

# docker logs                     stdout/stderr процесса контейнера
#   pg                            чей лог; без -f выведет накопленное и завершится
docker logs pg

# docker stop                     SIGTERM → ждать 10 секунд → SIGKILL;
#                                 контейнер остаётся в списке docker ps -a
docker stop pg

# docker rm                       удалить остановленный контейнер;
#                                 том pgdata НЕ удаляется — данные останутся
docker rm pg

Что здесь важно: пароль передан переменной окружения, порт опубликован на хост, данные вынесены в том. Уберите -v — и после docker rm база будет пустой (глава 9).

Смотреть: ps, logs, inspect, stats

# docker ps                    список работающих контейнеров
docker ps
#   -a                         все, включая остановленные и упавшие (exited)
#   -q                         только ID — удобно для скриптов: docker stop $(docker ps -q)
#   --format 'шаблон'          свой вывод (Go-шаблон):
#     {{.Names}}               имя контейнера
#     {{.Status}}              «Up 5 minutes» или «Exited (1) 2 minutes ago»
#     {{.Ports}}               опубликованные порты
#     \t                       табуляция между столбцами
docker ps --format '{{.Names}}\t{{.Status}}\t{{.Ports}}'

# docker logs                  что процесс писал в stdout/stderr
#   -f                         следить в реальном времени (как tail -f)
#   --tail 100                 начать с последних 100 строк
#   api                        имя контейнера
docker logs -f --tail 100 api
#   --since 10m                только за последние 10 минут (10m, 2h, 2026-10-26T10:00:00)
docker logs --since 10m api

# docker inspect               полная конфигурация и состояние контейнера (JSON)
docker inspect api
#   -f '{{.State.ExitCode}}'   код выхода: 0 — ок, 137 — SIGKILL/OOM, 143 — SIGTERM
docker inspect -f '{{.State.ExitCode}}' api
#   -f '{{.HostConfig.Memory}}'  лимит памяти в байтах (0 — лимит не задан)
docker inspect -f '{{.HostConfig.Memory}}' api

# docker stats                 живая статистика CPU, памяти и сети по контейнерам
#   --no-stream                вывести один раз и выйти (без него — обновляется, как top)
docker stats --no-stream

inspect — главный инструмент разбора: там видно итоговый образ, переменные, лимиты, сеть, точку монтирования, код выхода. Формат -f принимает Go-шаблоны, поэтому нужное поле достаётся одной командой.

Залезть внутрь: exec

# docker exec                 выполнить команду в работающем контейнере
#   -i                        оставить stdin открытым (ввод с клавиатуры)
#   -t                        псевдо-TTY: получим нормальное приглашение шелла
#   api                       имя контейнера
#   sh                        интерпретатор: sh есть почти везде (alpine, debian, chiseled-extra)
docker exec -it api sh

# bash                        если образ на Debian/Ubuntu — там полноценный bash
docker exec -it api bash

#   -u root                   выполнить от root: приложение работает от пользователя app,
#                             а для чтения защищённых файлов нужны права
docker exec -u root api bash

# printenv                    переменные окружения контейнера — так проверяют, что -e дошло
docker exec api printenv

# ls -la /app                 что реально лежит в папке приложения
#   -l                        длинный формат (права, владелец, размер)
#   -a                        показывать и скрытые файлы
docker exec api ls -la /app
  • exec запускает новый процесс в существующем контейнере — это безопасно, основной процесс не затрагивается.
  • docker attach — наоборот, подключается к stdio самого PID 1. Ctrl+C там убивает контейнер; для отладки почти всегда нужен exec.
  • В минимальных образах (chiseled, distroless) нет шелла вообще — «зайти внутрь» не получится, и это осознанный выбор в пользу безопасности (глава 14).

Остановить и удалить

КомандаЧто делает
docker stop apiSIGTERM, ожидание 10 с, SIGKILL (глава 13)
docker kill apiСразу SIGKILL — без graceful shutdown
docker start apiЗапустить остановленный контейнер снова (тот же записываемый слой)
docker restart apistop + start
docker rm apiУдалить остановленный контейнер
docker rm -f apiУбить и удалить
docker container pruneУдалить все остановленные

Что удаляет что

ОбъектУдаляется командойЧто будет с данными
Контейнерdocker rmЗаписываемый слой пропадёт; тома останутся
Томdocker volume rm, volume pruneДанные пропадут
Образdocker rmi, image pruneРаботающие контейнеры не пострадают
Всё неиспользуемоеdocker system prune -aМожет удалить образы и кэш сборки
Две команды, которые лучше не запускать «на всякий случай»
  • docker system prune -a --volumes — удаляет в том числе тома, то есть базу данных локального стенда.
  • docker kill для приложения, которое пишет данные, — это как выдернуть питание: без graceful shutdown можно потерять незаписанное (глава 13).

Мелочи, которые экономят время

# docker cp                    скопировать файл между контейнером и хостом
#   api:/app/appsettings.json  источник: имя контейнера : путь внутри него
#   .                          назначение: текущая папка на хосте
docker cp api:/app/appsettings.json .

# docker diff                  что изменилось в записываемом слое контейнера
#                              A — файл добавлен, C — изменён, D — удалён
docker diff api

# docker top                   процессы контейнера (ps с учётом его namespace)
docker top api

# docker port                  какие порты опубликованы и куда: 0.0.0.0:8080 → 8080/tcp
docker port api

# docker logs api 2>&1 | head
#   logs api                   лог контейнера
#   2>&1                      направить stderr в stdout, чтобы ошибки тоже попали в вывод
#   | head                     показать только первые 10 строк (если контейнер упал сразу)
docker logs api 2>&1 | head
★ Что запомнить из главы
  • Контейнер живёт, пока живёт PID 1; упал процесс — контейнер exited.
  • docker ps — только запущенные, ps -a — все; начинать разбор всегда с ps -a и logs.
  • run = pull + create + start; -d, --name, -p, -e, -v — обязательный минимум.
  • exec — новый процесс внутри (безопасно), attach — к PID 1 (опасно).
  • rm удаляет контейнер, volume rm/prune — данные; это разные вещи.
