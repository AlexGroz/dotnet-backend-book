Глава 5. Эксплуатация: retention, compaction, lag и мониторинг

Сколько данные живут на диске, что такое компакция, как читать lag и по каким метрикам понимать, что кластер здоров

основная глава

Сколько живут данные: retention

Журнал не вечен: старые сегменты удаляются по времени или по размеру. Настройки действуют на уровне топика и наследуются от брокера:

# --entity-type topics --entity-name orders --all  все настройки топика с источниками значений
docker exec kafka /opt/kafka/bin/kafka-configs.sh --bootstrap-server localhost:9092 \
  --describe --entity-type topics --entity-name orders --all \
  | grep -E 'retention.ms|retention.bytes|cleanup.policy|segment.bytes'
# cleanup.policy=delete     ... DEFAULT_CONFIG:log.cleanup.policy=delete
# retention.bytes=-1        ... DEFAULT_CONFIG:log.retention.bytes=-1
# retention.ms=604800000    ... synonyms={}   <- вычислено из log.retention.hours=168
# segment.bytes=1073741824  ... STATIC_BROKER_CONFIG:log.segment.bytes=1073741824, DEFAULT_CONFIG:...
НастройкаПо умолчаниюЧто означает
retention.ms604800000 (7 дней; по умолчанию считается из log.retention.hours=168)сколько хранить сегмент, прежде чем удалить его целиком
retention.bytes-1лимит размера партиции; -1 — без ограничения. Ограничивает диск, а не возраст
segment.ms604800000через сколько закрывать сегмент по времени (после этого он может быть удалён или компактирован)
segment.bytes1073741824 (1 ГБ)размер сегмента: при заполнении журнал переходит к следующему файлу
log.retention.check.interval.ms300000 (5 минут) как часто брокер проверяет, что можно удалить. Поэтому новый retention.ms действует не мгновенно
cleanup.policydeleteчто делать со старыми сегментами: удалять (delete) или компактировать (compact)

Проверено, как изменить срок и увидеть, что значение стало динамическим (перекрывает настройку брокера):

# --add-config retention.ms=60000  хранить записи одну минуту
docker exec kafka /opt/kafka/bin/kafka-configs.sh --bootstrap-server localhost:9092 \
  --alter --entity-type topics --entity-name orders --add-config retention.ms=60000
# Completed updating config for topic orders.

docker exec kafka /opt/kafka/bin/kafka-configs.sh --bootstrap-server localhost:9092 \
  --describe --entity-type topics --entity-name orders --all | grep retention.ms
# retention.ms=60000 ... synonyms={DYNAMIC_TOPIC_CONFIG:retention.ms=60000}
Retention удаляет сегменты, а не отдельные сообщения

Нельзя «оставить» сообщение, которое старше retention.ms: удаляется целый закрытый сегмент, когда его возраст превысил порог. Поэтому реальное время жизни записи — от retention.ms до retention.ms + segment.ms.

Компакция: хранить последнее значение на ключ

Второй режим — cleanup.policy=compact. Он не удаляет старые записи по времени, а оставляет в закрытых сегментах только последнее значение для каждого ключа. Это превращает топик в «таблицу состояний»: по журналу можно восстановить актуальное значение ключа, прочитав его с начала.

# топик с компакцией; segment.bytes 4096 — чтобы сегменты быстро закрывались на демо-объёме
# min.cleanable.dirty.ratio 0.01 — разрешить чистить сегмент, как только в нём 1% «мусора»
docker exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic state --partitions 1 --replication-factor 1 \
  --config cleanup.policy=compact --config segment.bytes=4096 \
  --config min.cleanable.dirty.ratio=0.01

docker exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic state
# Topic: state  TopicId: BGkHNyFPQsuKLIsHfYEF4w  PartitionCount: 1  ReplicationFactor: 1
#               Configs: cleanup.policy=compact,segment.bytes=4096,min.cleanable.dirty.ratio=0.01

Запишем 400 сообщений: пять ключей a0…a4, у каждого 80 версий. Пишем пачками по 40 — так проще не упереться в размер сегмента:

# внешний цикл — 10 пачек, внутренний — 40 сообщений в пачке
# ключ — a0..a4 (i % 5), значение — версия вида v035
for r in $(seq 0 9); do
  for i in $(seq 0 39); do echo "a$((i % 5)):v$r$i"; done | \
    docker exec -i kafka /opt/kafka/bin/kafka-console-producer.sh \
      --bootstrap-server localhost:9092 --topic state \
      --property parse.key=true --property key.separator=:
done

# сколько всего записано
docker exec kafka /opt/kafka/bin/kafka-get-offsets.sh --bootstrap-server localhost:9092 --topic state
# state:0:400

Через полминуты фоновый cleaner отработает. Читаем с начала:

docker exec kafka /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 \
  --topic state --from-beginning --timeout-ms 8000 --property print.key=true --property print.offset=true
# ...
# Offset:395  a0  v935
# Offset:396  a1  v936
# Offset:397  a2  v937
# Offset:398  a3  v938
# Offset:399  a4  v939
# Processed a total of 125 messages

Из 400 записей читается 125: старые версии ключей удалены, актуальные (последние по оффсету) остались. Число не равно пяти, потому что компакция идёт по закрытым сегментам и порциями, а самый последний (активный) сегмент не компактируется вовсе — допишем ещё 40 сообщений, и после следующего прохода читаться будет 165.

Почему consumer печатает TimeoutException

--timeout-ms 8000 — это «сколько ждать новых сообщений». Когда журнал дочитан, утилита печатает ошибку таймаута и завершает работу. Это не сбой данных: итог — строка Processed a total of N messages.

Удаление ключа в компактированном топике — это запись с тем же ключом и пустым значением (tombstone). После компакции такая запись и предыдущие версии ключа исчезают; на уровне приложения это означает «ключ удалён».

Сегменты на диске

Журнал партиции — набор файлов; имя файла начинается с оффсета первой записи в нём:

# какого размера партиции топика и где они лежат
docker exec kafka /opt/kafka/bin/kafka-log-dirs.sh --bootstrap-server localhost:9092 --describe --topic-list orders
# {"brokers":[{"broker":1,"logDirs":[{"partitions":[
#   {"partition":"orders-0","size":83,"offsetLag":0,"isFuture":false},
#   {"partition":"orders-1","size":83,"offsetLag":0,"isFuture":false},
#   {"partition":"orders-2","size":83,"offsetLag":0,"isFuture":false}],
#  "error":null,"logDir":"/tmp/kraft-combined-logs"}]}],"version":1}

# файлы компактированного топика state: первый сегмент «сжат» до 492 байт
docker exec kafka ls -l /tmp/kraft-combined-logs/state-0
# 00000000000000000000.log   492    <- сегмент с оффсета 0, после компакции
# 00000000000000000280.log  2284    <- следующий сегмент, начинается с оффсета 280

offsetLag в ответе kafka-log-dirs.sh — насколько будущие реплики отстают от лидера; на одном брокере всегда 0.

Мониторинг: lag, репликация, диски

Три вопроса, на которые должна отвечать эксплуатация Kafka: догоняют ли потребители, здоровы ли реплики и хватает ли места.

# 1) отставание групп: LAG = LOG-END-OFFSET - CURRENT-OFFSET (глава 4)
docker exec kafka /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --describe --group orders-workers

# 2) состояние групп: Empty — участников нет, Stable — читают
docker exec kafka /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --describe --all-groups --state
# GROUP           COORDINATOR (ID)   ASSIGNMENT-STRATEGY  STATE   #MEMBERS
# orders-workers  localhost:9092 (1)                      Empty   0

# 3) партиции, у которых реплики отстали от лидера: пусто — всё синхронно
docker exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --describe --under-replicated-partitions
# (пусто)

# 4) размер партиций на диске
docker exec kafka /opt/kafka/bin/kafka-log-dirs.sh --bootstrap-server localhost:9092 \
  --describe --topic-list orders
Что смотретьКакНа что реагировать
Отставание потребителейLAG в kafka-consumer-groups --describeмонотонный рост lag: потребители не успевают или упали
Живость группы--all-groups --stateEmpty при непустом топике — никто не читает
Репликация--describe --under-replicated-partitions, колонка Isrнепустой список — реплика отстала или брокер недоступен
Дискkafka-log-dirs.sh, место на узлерост быстрее retention — топик хранит больше, чем планировали
Публикацияошибки ProduceException в приложениирост Local: Message timed out — брокер не успевает

На стороне приложения метрики снимают с клиента: у Confluent.Kafka есть SetStatisticsHandler — librdkafka отдаёт JSON со счётчиками отправки, ошибок и очередей. На стороне брокера — JMX: число сообщений в секунду, размер партиций, число недореплицированных партиций. Lag удобнее брать из CLI или Admin API: он считается по данным кластера, а не клиента, и виден даже когда потребитель лежит.

Чек-лист перед продакшеном

  • Три брокера и replication-factor=3, min.insync.replicas=2: потеря одного узла не теряет подтверждённые записи.
  • Producer: Acks.All + EnableIdempotence (глава 3); повторы не создают дублей.
  • Consumer: EnableAutoCommit=false и коммит после обработки (глава 4); обработчик идемпотентен.
  • Ключ и партиционер согласованы между всеми клиентами (глава 2), иначе порядок на ключ разваливается.
  • Число партиций спланировано заранее: увеличивать можно, уменьшать нельзя, а увеличение меняет отображение ключей.
  • Автосоздание топиков выключено (auto.create.topics.enable=false): случайный топик получит 1 партицию и 1 реплику.
  • Retention и лимиты заданы: retention.ms, retention.bytes, при необходимости cleanup.policy=compact.
  • Алерты: рост lag, недореплицированные партиции, свободное место, ошибки producer'а.
Типичные ошибки
  • Хранить в Kafka «всё навсегда» — диск закончится раньше, если retention не настроен по объёму.
  • Ждать глобального порядка — его нет: порядок только внутри партиции.
  • Разные партиционеры у Java и .NET — один ключ в двух партициях, порядок потерян без единой ошибки.
  • Автокоммит в consumer — падение процесса теряет уже «закоммиченную» работу.
  • Один брокер и RF=1 в продакшене — перезапуск узла останавливает поток и может потерять данные.
★ Что запомнить из главы
  • Retention задаёт срок жизни сегментов: по умолчанию 7 дней (retention.ms=604800000), retention.bytes=-1 — без лимита по размеру.
  • Проверка удаления идёт периодически: log.retention.check.interval.ms = 5 минут, поэтому новый retention срабатывает не мгновенно.
  • Компакция оставляет последнее значение на ключ и работает по закрытым сегментам: в прогоне из 400 записей читалось 125.
  • Lag — главная метрика: LOG-END-OFFSET − CURRENT-OFFSET; сумма по партициям показывает отставание группы.
  • Здоровье кластера: пустой список under-replicated партиций, синхронный Isr, свободное место и отсутствие ошибок публикации.
