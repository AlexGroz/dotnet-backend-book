Глава 28. Масштабирование и отказоустойчивость

«Поднять вторую реплику» — это не копирование сервиса, а набор требований: отсутствие состояния, три вида health-проб, корректная остановка и лимиты. Разберём каждый пункт и что ломается, когда их забыть.

основная глава

Два способа масштабировать

ВертикальноГоризонтально
Что делаемдаём больше CPU/памяти одной машинезапускаем N копий сервиса
Пределесть: дорого и конечнопочти нет
Отказоустойчивостьнет: одна машина = одна точка отказаесть: реплики подменяют друг друга
Условие—сервис не хранит состояние в памяти

Горизонтальное масштабирование — это отказ от «помнить что-то у себя»: любая реплика должна уметь обработать любой запрос.

Что нельзя хранить в памяти

Если хранить в репликеЧто случитсяКуда переносить
Сессии, токены, «корзина»пользователь попадает на другую реплику и «теряет» себя БД, Redis, подписанный cookie (см. ниже)
Кэшреплики показывают разные данные, инвалидация не работаетобщий кэш (Redis) или TTL-кэш с допустимым расхождением (гл. 25)
Счётчики/лимитылимит «100 в минуту» превращается в «100 × число реплик» общий счётчик или распределённый rate limiter (ниже — про отличие)
Файлы и логи на дискфайл есть только на одной репликеобъектное хранилище (S3/Blob), stdout вместо файлов (гл. 20)
Фоновые задачиодну и ту же job выполняют все репликиотдельный воркер, очередь (гл. 26) или выбор лидера
Sticky sessions — не решение

Можно «прибить» пользователя к реплике на балансировщике, и часть проблем исчезнет. Но: при выкатке реплику всё равно надо выключить, при отказе — сессия теряется, а нагрузка распределяется неравномерно. Sticky — временная мера, а не архитектура.

Три health-пробы — и у каждой своя задача

ПробаВопрос, на который отвечаетЧто делает платформаЧто нельзя проверять
Liveness (живость)«процесс завис или работает?» перезапускает контейнерЗависимости (БД, чужой API): их сбой не лечится перезапуском, зато вызовет лавину перезапусков
Readiness (готовность)«можно ли уже отправлять трафик?» убирает/возвращает реплику из балансировки, не перезапускаяТяжёлые операции: проба вызывается часто, она должна быть дешёвой
Startup (старт)«приложение ещё запускается, не убивай» даёт время на инициализацию (JIT, миграции, прогрев)—
builder.Services.AddHealthChecks()
    // «жив ли процесс»: ничего внешнего, иначе чужая авария перезапустит все наши реплики
    .AddCheck("self", () => HealthCheckResult.Healthy(), tags: ["live"])
    // «готов ли обслуживать»: зависимости, которые нужны для работы
    .AddNpgSql(connectionString, name: "postgres", tags: ["ready"])   // пакет AspNetCore.HealthChecks.NpgSql
    .AddRedis(redisConnection, name: "redis",  tags: ["ready"]);

var app = builder.Build();

app.MapHealthChecks("/health/live",  new HealthCheckOptions
{
    Predicate = r => r.Tags.Contains("live")        // только «процесс жив»
});
app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = r => r.Tags.Contains("ready"),      // только зависимости
    ResponseWriter = async (ctx, report) =>      // свой JSON: имя проверки, статус, длительность
    {
        ctx.Response.ContentType = "application/json";
        await ctx.Response.WriteAsJsonAsync(new
        {
            status = report.Status.ToString(),
            checks = report.Entries.Select(e => new { e.Key, status = e.Value.Status.ToString() })
        });
    }
});
  • Проба должна быть дешёвой: SELECT 1 или проверка соединения из пула, а не «посчитай заказы за месяц».
  • Не открывайте новое соединение на каждую пробу — это лишняя нагрузка на БД при 100 репликах × 1 проба/5 с.
  • Readiness может быть false при живом процессе — это нормальный способ вывести реплику из трафика без убийства (используется при выкатке).

Прогрев: новая реплика не готова в первую секунду

После старта процесс ещё «холодный»: JIT компилирует методы по мере вызова (гл. 3), пул соединений пуст (гл. 23), EF Core строит модель и компилирует первые запросы, кэш пуст (гл. 25). Если трафик придёт сразу, первые сотни запросов будут в разы медленнее — и попадут в p99.

// прогреваем пул и модель до того, как readiness станет true
public sealed class WarmupService(
    IServiceScopeFactory scopes,
    ILogger<WarmupService> log) : BackgroundService
{
    public static volatile bool Ready;          // health-check смотрит на этот флаг

    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        try
        {
            // открываем столько соединений, сколько понадобится под нагрузку
            await Parallel.ForEachAsync(
                Enumerable.Range(0, 10),
                ct,
                async (_, token) =>
                {
                    await using var scope = scopes.CreateAsyncScope();
                    var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
                    await db.Database.ExecuteSqlRawAsync("SELECT 1", token);
                });

            Ready = true;                        // теперь readiness отдаёт 200
            log.LogInformation("прогрев завершён");
        }
        catch (Exception ex)
        {
            log.LogError(ex, "прогрев не удался");   // readiness останется false → трафик не пойдёт
        }
    }
}
  • SELECT 1 через EF прогревает и пул, и модель: первый запрос строит метаданные, дальше они кэшируются в процессе.
  • Health-проверка «ready» возвращает Unhealthy, пока Ready == false: трафик не пойдёт.
  • В Kubernetes для этого есть startupProbe (даёт время, не убивая) и readinessProbe (держит вне трафика до готовности).
Прогрев нужен только при старте? Нет — но «повторный прогрев» выглядит иначе

Сам прогрев JIT и модели EF — свойство процесса: один раз прогрели, и до перезапуска он не «остывает». Но зависимости могут остывать и позже, и тогда прогрев повторяют по требованию:

  • Перезапуск поды / деплой / scale-out — каждый новый процесс холодный, ему нужен свой прогрев (это основной случай).
  • Failover базы: после переключения на реплику/новый мастер старые соединения в пуле мертвы — пул наполняется заново, первые запросы платят за установку TCP+TLS и разбор первого плана. Полезно «прогреть» пул после восстановления зависимости.
  • Долгий простой: пул мог «усохнуть» (idle-таймауты), кэш — остыть; первый всплеск трафика после ночи будет медленнее.
  • Смена конфигурации/секретов (ротация пароля БД) — соединения пересоздаются, пул снова пустой.

Поэтому «прогрев» — это не только код в старте: если у вас есть сценарии выше, делайте повторный прогрев по событию (после восстановления зависимости, по расписанию перед пиковыми часами) и держите метрику «пул заполнен на N %».

Корректная остановка: как не порвать запросы при выкатке

1. SIGTERM → приложение получает ApplicationStopping
2. readiness становится false  → балансировщик перестаёт слать новое
3. «дренаж»: текущие запросы доигрываются (обычно 5–10 с)
4. StopAsync у BackgroundService → фоновые задачи отменяются по CancellationToken
5. Dispose: пулы соединений, буферы, клиенты
6. если не успели за ShutdownTimeout → SIGKILL (жёстко)
// сколько времени даём на дренаж (по умолчанию 30 с)
builder.Services.Configure<HostOptions>(o =>
    o.ShutdownTimeout = TimeSpan.FromSeconds(20));

// фоновый сервис обязан слушать токен остановки
public sealed class ImportWorker : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            await ImportNextBatchAsync(ct);       // отмена дойдёт и внутрь
        }
    }
}
Почему запросы всё равно рвутся
  • Балансировщик узнаёт о завершении не мгновенно. Между «получили SIGTERM» и «трафик перестал идти» проходят секунды. Решение: сначала readiness → false, подождать 5–10 с, и только потом останавливаться (в Kubernetes — preStop с задержкой).
  • Внешний таймаут меньше внутреннего. Правило: terminationGracePeriodSeconds (например 45 с) должно быть больше ShutdownTimeout (20 с), иначе платформа убьёт процесс раньше.
  • Задача не слушает отмену. Если внутри цикл без проверки токена, работу всё равно потеряют. Долгие операции должны быть возобновляемыми и идемпотентными (гл. 26, 31).

Rate limiting: защита от перегрузки

Встроенный middleware (.NET 7+) ограничивает входящий трафик. Алгоритм выбирается по задаче:

АлгоритмКак работаетКогда брать
Fixed windowN запросов на окно (например, 100 в минуту)Простые квоты, биллинг
Sliding windowОкно «съезжает», без всплеска на границеПлавные лимиты для API
Token bucketКопятся «токены», запрос тратит один: есть средняя скорость и запас Разрешить короткие всплески
ConcurrencyНе больше N одновременных запросовЗащита от медленных клиентов и тяжёлых эндпоинтов
builder.Services.AddRateLimiter(o =>
{
    o.RejectionStatusCode = StatusCodes.Status429TooManyRequests;

    // лимит на выгрузку, ключ — пользователь (или IP, если аноним)
    o.AddPolicy("export", ctx =>
        RateLimitPartition.GetFixedWindowLimiter(
            partitionKey: ctx.User.Identity?.Name
                          ?? ctx.Connection.RemoteIpAddress?.ToString() ?? "anon",
            factory: _ => new FixedWindowRateLimiterOptions
            {
                PermitLimit = 5,                       // 5 выгрузок…
                Window      = TimeSpan.FromMinutes(1), // …в минуту
                QueueLimit  = 0                        // не копим: сразу 429
            }));
});

app.UseRateLimiter();
app.MapGet("/export", ExportAsync).RequireRateLimiting("export");
Лимитер в памяти ≠ общий лимит

Встроенный rate limiter считает на каждой реплике отдельно: при 5 репликах и лимите «100 в минуту» клиент фактически получит до 500. Для общего лимита нужен счётчик вне процесса (Redis, API-gateway, ingress). Внутри реплики лимитер полезен и так — он защищает конкретный процесс от перегрузки.

По чему масштабировать и что считать

  • CPU — плохой сигнал для I/O-bound сервиса: он может стоять на 20 %, пока всё ждёт базу; масштабирование по CPU не поможет.
  • Лучше масштабировать по RPS и задержке (p95) относительно SLO, а для воркеров — по длине очереди.
  • Держите запас: при 70 % CPU новый трафик уже не успевает — ориентир 50–70 %, а не «пока не упадёт».
  • Помните про общий ресурс: 20 реплик × пул 100 соединений = 2000 соединений к PostgreSQL, а это может быть больше, чем max_connections (гл. 23).
  • Kestrel-лимиты (MaxConcurrentConnections, MaxRequestBodySize) — последняя линия защиты процесса, но не замена лимитеру.

Чек-лист готовности к двум репликам

  1. Ничего важного не хранится в памяти процесса (сессии, кэш, счётчики, файлы).
  2. Есть /health/live — без зависимостей, и /health/ready — с ними.
  3. Readiness возвращает false, пока идёт прогрев пула/модели.
  4. Graceful shutdown настроен: ShutdownTimeout меньше grace period платформы.
  5. Фоновые задачи идемпотентны или выполняются одним экземпляром.
  6. Миграции БД не запускаются из каждого экземпляра приложения.
  7. Лимиты и счётчики не умножаются на число реплик (или это осознанное решение).
  8. Логи в stdout, метрики с меткой реплики, трейсы сквозные (гл. 20, 21).
  9. Повторные запросы клиента безопасны: ключ идемпотентности на изменяющих операциях (идемпотентность — «повторить дважды = получить тот же результат, что и один раз»; определение — гл. 27, реализация — гл. 31).
  10. У внешних зависимостей есть таймауты, повторы и предохранитель (гл. 27).
★ Что запомнить из главы
  • Горизонтальное масштабирование требует stateless-сервиса: всё «помнимое» — в БД, Redis или подписанном токене.
  • Liveness ≠ readiness: зависимости проверяем только в readiness, иначе чужая авария перезапустит все реплики.
  • Новая реплика должна прогреться (пул, модель EF, JIT), прежде чем получать трафик.
  • Корректная остановка: readiness → false, дренаж, отмена фоновых задач, dispose; ShutdownTimeout меньше, чем grace period платформы.
  • Встроенный rate limiter считает в памяти реплики; общий лимит — на gateway или в Redis.
  • Масштабируйте по RPS/задержке/очереди, а не по «среднему CPU», и следите за общими ресурсами (соединения к БД).
