Глава 2. Публикация из .NET: каналы, свойства и подтверждения

Почему «отправил» не значит «брокер принял», и как это проверить

основная глава

Канал: что это и сколько их нужно

Соединение (IConnection) — это TCP-сессия с брокером, её на процесс обычно одно. Канал (IChannel) — «сессия внутри сессии»: в нём своя нумерация delivery tag, свои подтверждения и свои ошибки.

  • Канал дешёвый. Его открывают под задачу: один на публикацию, один на потребление, а не «один на всё».
  • Канал не потокобезопасен. Нельзя использовать один канал из нескольких потоков одновременно — это самая частая причина «перемешанных» подтверждений.
  • Ошибка уровня протокола закрывает канал, а не соединение. Пример: публикация в несуществующий обменник — канал закрывается с кодом 404, и дальнейшие вызовы на нём падают. Правильно — создать новый канал.

Свойства сообщения

Тело — это байты. Всё остальное (нужно ли сохранять на диск, кто автор, как связать ответ с запросом) передаётся в BasicProperties:

СвойствоЗачем
Persistent = trueПросит брокера записать сообщение на диск (вместе с durable-очередью это переживает перезапуск)
ContentTypeЧтобы потребитель знал, чем разбирать тело (application/json)
MessageIdИдентификатор для дедупликации и трассировки
CorrelationIdСвязь ответа с исходным запросом (RPC-паттерн)
HeadersПроизвольные пары «ключ — значение»: версия схемы, попытка, источник

Тонкость API, на которой легко споткнуться: в RabbitMQ.Client 7.x у BasicPublishAsync свойства идут после флага mandatory. Считаем, что ch — канал из главы 1. Вызов либо без свойств вообще, либо так:

var props = new BasicProperties
{
    Persistent  = true,
    ContentType = "application/json",
    MessageId   = Guid.NewGuid().ToString("N"),
    Headers     = new Dictionary<string, object?> { ["schema"] = 2 },
};

await ch.BasicPublishAsync(
    exchange: "orders",
    routingKey: "order.created",
    mandatory: true,                  // обязательно явно, если передаёте свойства
    basicProperties: props,
    body: Encoding.UTF8.GetBytes("{\"id\":42}"));

Publisher confirms: «брокер принял»

Публикация по AMQP асинхронная: BasicPublishAsync без подтверждений возвращается сразу после записи в сокет. Брокер при этом мог не принять сообщение — например, не найти обменник. Включается подтверждение на уровне канала:

var opts = new CreateChannelOptions(
    publisherConfirmationsEnabled: true,
    publisherConfirmationTrackingEnabled: true);

await using var ch = await conn.CreateChannelAsync(opts);

Теперь await BasicPublishAsync(...) ждёт подтверждения от брокера. Проверено на двух сценариях:

confirm channel: True
published to existing exchange: ok

missing exchange -> AlreadyClosedException: Already closed: The AMQP operation was interrupted:
AMQP close-reason, initiated by Peer, code=404, text='NOT_FOUND - no exchange
'no.such.exchange' in vhost '/''
  • Существующий обменник — подтверждение пришло, вызов завершился успешно.
  • Несуществующий — ошибка 404 NOT_FOUND, причём канал закрыт: это не «одна неудачная публикация», а выход из строя канала. В приложении такой канал пересоздают, а не переиспользуют.
Что говорят документы

«In order to guarantee persistence, a client should use confirms» — без подтверждений брокер может потерять даже persistent-сообщение, если упадёт до записи на диск. И там же: для persistent-сообщений подтверждение может занимать «a few hundred milliseconds», потому что брокер пишет пакет на диск; поэтому подтверждения обрабатывают асинхронно, а не по одному в цикле (RabbitMQ, «Consumer Acknowledgements and Publisher Confirms»).

mandatory и возврат неотправленного

Сообщение может быть «подтверждено», но никуда не положено: обменник есть, а привязки с таким routing key нет. По умолчанию такое сообщение молча выбрасывается. Флаг mandatory: true заставляет брокера вернуть его событием BasicReturnAsync:

// props — объект BasicProperties из предыдущего примера
await ch.ExchangeDeclareAsync("ex.noroute", ExchangeType.Direct, durable: false, autoDelete: false);

ch.BasicReturnAsync += (_, ea) =>
{
    Console.WriteLine($"returned: reply={ea.ReplyText} exchange={ea.Exchange} rk={ea.RoutingKey}");
    return Task.CompletedTask;
};

await ch.BasicPublishAsync("ex.noroute", "no.binding", mandatory: true,
    basicProperties: props, body: Encoding.UTF8.GetBytes("{\"id\":9}"));

// returned: reply=NO_ROUTE exchange=ex.noroute rk=no.binding

NO_ROUTE — это и есть «сообщение не попало ни в одну очередь». Без mandatory вы об этом не узнаете: ни ошибки, ни возврата, сообщение просто исчезло.

Подтверждение не спасает от потери адресата

Confirm отвечает на вопрос «брокер принял сообщение?», а не «сообщение дошло до очереди?». Поэтому надёжная публикация — это confirm + mandatory + обработчик возврата:

  • confirm получен, return не пришёл → сообщение легло в очередь;
  • confirm получен, пришёл NO_ROUTE → адресата нет, это ошибка конфигурации;
  • confirm не пришёл (таймаут) → брокер не принял; сообщение надо отправить снова.

Надёжная публикация: confirm не заменяет outbox

Даже с подтверждениями есть окно: приложение сделало запись в БД, отправило сообщение — и упало до того, как запомнило результат. Или наоборот: сообщение ушло, а транзакция в БД откатилась. Классическое решение — Transactional Outbox: сообщение пишется в таблицу в той же транзакции, что и бизнес-данные, а отдельный воркер публикует его с подтверждениями и помечает отправленным (подробно — в .NET-разделе, глава про Outbox и идемпотентность).

BEGIN;
  INSERT INTO orders …;
  INSERT INTO outbox (type, payload) VALUES ('order.created', …);
COMMIT;                          -- бизнес-данные и намерение отправить — атомарно

-- отдельно, воркер:
--   SELECT … FROM outbox WHERE status = 'new' FOR UPDATE SKIP LOCKED
--   → publish с confirm
--   → UPDATE outbox SET status = 'sent'

Confirm здесь нужен, чтобы понять, когда можно ставить sent: без него воркер не знает, принял ли брокер сообщение, и вынужден либо дублировать, либо помечать отправленным «на веру».

Что происходит при перегрузке

Если брокер упёрся в лимит памяти или диска, он включает alarm и перестаёт читать данные от публикующих соединений. Проверено: с включённым memory alarm публикация без подтверждений завершается «успешно» — сообщение просто остаётся в буфере клиента:

publish: ok                 <- без confirm: вызов вернулся, брокер не принял
channel.IsOpen: True

confirm: NOT received -> TaskCanceledException   <- с confirm: ждём и не дожидаемся

Второй случай — тот же publish, но на канале с подтверждениями и таймаутом 3 секунды. Это лучший аргумент за confirms: без них перегрузка брокера выглядит как нормальная работа, пока очередь не начнёт «непонятно почему» пустеть.

★ Что запомнить из главы
  • Канал дешёвый, но не потокобезопасный; после ошибки протокола (404) его пересоздают.
  • Свойства передаются после mandatory: BasicPublishAsync(exchange, routingKey, mandatory, basicProperties, body).
  • Confirm = «брокер принял», а не «сообщение в очереди»; для адресата нужен mandatory + обработчик BasicReturnAsync.
  • При alarm публикация без confirm «успешна» — перегрузка видна только по таймауту подтверждения.
  • Persistent + durable + confirm — минимальный набор, чтобы сообщение переживало перезапуск; атомарность с БД даёт outbox.
