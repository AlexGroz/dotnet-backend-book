Глава 2. Публикация из .NET: каналы, свойства и подтверждения

Почему «отправил» не значит «брокер принял», и как это проверить

основная глава

Канал: что это и сколько их нужно

Соединение (IConnection) — это TCP-сессия с брокером, её на процесс обычно одно. Канал (IChannel) — «сессия внутри сессии»: в нём своя нумерация delivery tag, свои подтверждения и свои ошибки.

  • Канал дешёвый. Его открывают под задачу: один на публикацию, один на потребление, а не «один на всё».
  • Канал не потокобезопасен. Нельзя использовать один канал из нескольких потоков одновременно — это самая частая причина «перемешанных» подтверждений.
  • Ошибка уровня протокола закрывает канал, а не соединение. Пример: публикация в несуществующий обменник — канал закрывается с кодом 404, и дальнейшие вызовы на нём падают. Правильно — создать новый канал.

Свойства сообщения

Тело — это байты. Всё остальное (нужно ли сохранять на диск, кто автор, как связать ответ с запросом) передаётся в BasicProperties:

СвойствоЗачем
Persistent = trueПросит брокера записать сообщение на диск (вместе с durable-очередью это переживает перезапуск)
ContentTypeЧтобы потребитель знал, чем разбирать тело (application/json)
MessageIdИдентификатор для дедупликации и трассировки
CorrelationIdСвязь ответа с исходным запросом (RPC-паттерн)
HeadersПроизвольные пары «ключ — значение»: версия схемы, попытка, источник

Тонкость API, на которой легко споткнуться: в RabbitMQ.Client 7.x у BasicPublishAsync свойства идут после флага mandatory. Считаем, что ch — канал из главы 1. Вызов либо без свойств вообще, либо так:

var props = new BasicProperties           // свойства сообщения — отдельный объект, тело передаётся отдельно
{
    Persistent  = true,                   // просить брокера записать на диск (работает вместе с durable-очередью)
    ContentType = "application/json",     // подсказка потребителю, чем разбирать тело
    MessageId   = Guid.NewGuid().ToString("N"),   // "N" — 32 hex-символа без дефисов: ключ для дедупликации
    Headers     = new Dictionary<string, object?> { ["schema"] = 2 },  // свои пары «ключ — значение»
};

await ch.BasicPublishAsync(
    exchange: "orders",                   // имя обменника ("" — default exchange, глава 1)
    routingKey: "order.created",          // адрес сообщения: с ним сравниваются ключи привязок
    mandatory: true,                      // вернуть сообщение, если ни одна очередь не подошла
    basicProperties: props,               // объект со свойствами выше
    body: Encoding.UTF8.GetBytes("{\"id\":42}"));   // тело — байты; строка сначала кодируется в UTF-8

Что означает каждое свойство и аргумент:

ЧтоЧто означает
Persistent = trueпросит брокера записать сообщение на диск. Само по себе ничего не гарантирует: нужна ещё durable-очередь, а что запись действительно произошла — подтверждает confirm
ContentTypeMIME-тип тела; потребитель по нему решает, чем десериализовать
MessageIdидентификатор сообщения. Guid.ToString("N") — 32 hex-символа без дефисов; по нему делают дедупликацию и трассировку
Headersпроизвольные пары «ключ — значение»; потребитель видит их в ea.BasicProperties.Headers. Значения — простые типы: строка, число, байты
exchange, routingKeyкуда и с каким адресом публикуем (разобрано в главе 1)
mandatoryпри передаче свойств его нужно указать явно: иначе сообщение без подходящей привязки исчезнет молча
basicPropertiesобъект BasicProperties; порядок аргументов — exchange, routingKey, mandatory, basicProperties, body
bodyReadOnlyMemory<byte>: строку превращают через Encoding.UTF8.GetBytes

Publisher confirms: «брокер принял»

Публикация по AMQP асинхронная: BasicPublishAsync без подтверждений возвращается сразу после записи в сокет. Брокер при этом мог не принять сообщение — например, не найти обменник. Включается подтверждение на уровне канала:

var opts = new CreateChannelOptions(
    publisherConfirmationsEnabled: true,          // включить на канале режим подтверждений (confirm.select)
    publisherConfirmationTrackingEnabled: true);  // BasicPublishAsync должен дождаться ответа брокера

await using var ch = await conn.CreateChannelAsync(opts);   // канал с этими настройками; await using закроет его
ПараметрЧто означает
publisherConfirmationsEnabledброкер подтверждает каждую публикацию (basic.ack) или сообщает об отказе (basic.nack)
publisherConfirmationTrackingEnabledсвязывает подтверждение с конкретным вызовом: BasicPublishAsync не вернётся, пока ответ не пришёл. При false подтверждения тоже идут, но вызов не ждёт их
оба аргументау конструктора CreateChannelOptions нет значений по умолчанию: если передаёте объект, укажите оба. Обычный канал создают без аргументов: CreateChannelAsync()
await usingканал закроется при выходе из области видимости — вместе с ним уходят его подписки и неподтверждённые публикации

Теперь await BasicPublishAsync(...) ждёт подтверждения от брокера. Проверено на двух сценариях:

confirm channel: True                      # канал открыт, режим подтверждений включён
published to existing exchange: ok         # confirm пришёл: брокер принял сообщение

missing exchange -> AlreadyClosedException: Already closed: The AMQP operation was interrupted:
AMQP close-reason, initiated by Peer, code=404, text='NOT_FOUND - no exchange
'no.such.exchange' in vhost '/''           # 404: канал закрыт брокером, а не «сообщение не ушло»
  • Существующий обменник — подтверждение пришло, вызов завершился успешно.
  • Несуществующий — ошибка 404 NOT_FOUND, причём канал закрыт: это не «одна неудачная публикация», а выход из строя канала. В приложении такой канал пересоздают, а не переиспользуют.
Что говорят документы

«In order to guarantee persistence, a client should use confirms» — без подтверждений брокер может потерять даже persistent-сообщение, если упадёт до записи на диск. И там же: для persistent-сообщений подтверждение может занимать «a few hundred milliseconds», потому что брокер пишет пакет на диск; поэтому подтверждения обрабатывают асинхронно, а не по одному в цикле (RabbitMQ, «Consumer Acknowledgements and Publisher Confirms»).

mandatory и возврат неотправленного

Сообщение может быть «подтверждено», но никуда не положено: обменник есть, а привязки с таким routing key нет. По умолчанию такое сообщение молча выбрасывается. Флаг mandatory: true заставляет брокера вернуть его событием BasicReturnAsync:

// using RabbitMQ.Client.Exceptions;   — здесь живёт PublishReturnException
// props — объект BasicProperties из предыдущего примера
await ch.ExchangeDeclareAsync("ex.noroute", ExchangeType.Direct, durable: false, autoDelete: false); // обменник без привязок

ch.BasicReturnAsync += (_, ea) =>                 // событие: брокер возвращает сообщение
{
    Console.WriteLine($"returned: reply={ea.ReplyText} exchange={ea.Exchange} rk={ea.RoutingKey}"); // reply=NO_ROUTE
    return Task.CompletedTask;                    // обработчик асинхронный: возвращаем готовую задачу
};

try
{
    await ch.BasicPublishAsync("ex.noroute", "no.binding", mandatory: true,   // mandatory: вернуть, если маршрута нет
        basicProperties: props, body: Encoding.UTF8.GetBytes("{\"id\":9}"));
}
catch (PublishReturnException e)                  // канал с tracking: возврат приходит ещё и исключением
{
    Console.WriteLine($"publish returned: {e.Message}"); // 312 NO_ROUTE Exchange: ex.noroute Routing Key: no.binding
}

// returned: reply=NO_ROUTE exchange=ex.noroute rk=no.binding

NO_ROUTE — это и есть «сообщение не попало ни в одну очередь». Без mandatory вы об этом не узнаете: ни ошибки, ни возврата, сообщение просто исчезло.

Что лежит в событии возврата (BasicReturnEventArgs) и что означают аргументы:

Поле / аргументЧто означает
ReplyCodeчисловой код причины: 312 — маршрута нет (NO_ROUTE)
ReplyTextтекст причины: NO_ROUTE
Exchange, RoutingKeyкуда и с каким адресом публиковали — по ним видно, какая привязка не сработала
BasicProperties, Bodyсвойства и тело возвращённого сообщения: его можно переотправить или сохранить
mandatory: trueу BasicPublishAsync — «верни сообщение, если очередь не нашлась». При false сообщение выбрасывается молча
PublishReturnExceptionисключение клиента 7.x: возникает, когда на канале включён publisherConfirmationTrackingEnabled и брокер вернул сообщение
В 7.x возврат приходит дважды: событием и исключением

Проверено на канале с подтверждениями и tracking. Сначала срабатывает BasicReturnAsync, затем BasicPublishAsync бросает PublishReturnException с текстом 312 NO_ROUTE Exchange: ex.noroute Routing Key: no.binding. Если tracking выключен (или канал создан без подтверждений), вызов завершается успешно и остаётся только событие. Поэтому обработчик возврата нужен в любом случае, а try/catch — если вы ждёте подтверждения.

Подтверждение не спасает от потери адресата

Confirm отвечает на вопрос «брокер принял сообщение?», а не «сообщение дошло до очереди?». Поэтому надёжная публикация — это confirm + mandatory + обработчик возврата:

  • confirm получен, return не пришёл → сообщение легло в очередь;
  • confirm получен, пришёл NO_ROUTE → адресата нет, это ошибка конфигурации;
  • confirm не пришёл (таймаут) → брокер не принял; сообщение надо отправить снова.

Надёжная публикация: confirm не заменяет outbox

Даже с подтверждениями есть окно: приложение сделало запись в БД, отправило сообщение — и упало до того, как запомнило результат. Или наоборот: сообщение ушло, а транзакция в БД откатилась. Классическое решение — Transactional Outbox: сообщение пишется в таблицу в той же транзакции, что и бизнес-данные, а отдельный воркер публикует его с подтверждениями и помечает отправленным (подробно — в .NET-разделе, глава про Outbox и идемпотентность).

BEGIN;                                         -- одна транзакция на бизнес-запись и намерение отправить
  INSERT INTO orders …;                        -- бизнес-данные
  INSERT INTO outbox (type, payload) VALUES ('order.created', …);  -- сообщение как строка таблицы
COMMIT;                                        -- либо видны оба INSERT, либо ни одного

-- отдельно, воркер в другом процессе:
--   SELECT … FROM outbox WHERE status = 'new' FOR UPDATE SKIP LOCKED
--        ^ берём пачку «новых» и пропускаем строки, которые уже захватил другой воркер
--   → publish с confirm                         -- подтверждение = «брокер принял»
--   → UPDATE outbox SET status = 'sent'         -- помечаем только после confirm

Confirm здесь нужен, чтобы понять, когда можно ставить sent: без него воркер не знает, принял ли брокер сообщение, и вынужден либо дублировать, либо помечать отправленным «на веру».

Что происходит при перегрузке

Если брокер упёрся в лимит памяти или диска, он включает alarm и перестаёт читать данные от публикующих соединений. Проверено: с включённым memory alarm публикация без подтверждений завершается «успешно» — сообщение просто остаётся в буфере клиента:

publish: ok                 <- без confirm: вызов вернулся, брокер не принял
channel.IsOpen: True

confirm: NOT received -> TaskCanceledException   <- с confirm: ждём и не дожидаемся

Второй случай — тот же publish, но на канале с подтверждениями и таймаутом 3 секунды. Это лучший аргумент за confirms: без них перегрузка брокера выглядит как нормальная работа, пока очередь не начнёт «непонятно почему» пустеть.

Деталь, проверенная отдельно: TaskCanceledException означает «подтверждение не пришло», а не «сообщение не отправлено». Оба сообщения остались в буфере клиента и ушли в брокер после снятия alarm — в прогоне очередь содержала ровно 2 сообщения. Значит повтор после таймаута даст дубль, и обработчик должен быть идемпотентным (глава 3).

★ Что запомнить из главы
  • Канал дешёвый, но не потокобезопасный; после ошибки протокола (404) его пересоздают.
  • Свойства передаются после mandatory: BasicPublishAsync(exchange, routingKey, mandatory, basicProperties, body).
  • Confirm = «брокер принял», а не «сообщение в очереди»; для адресата нужен mandatory + обработчик BasicReturnAsync (с tracking возврат приходит ещё и исключением PublishReturnException).
  • При alarm публикация без confirm «успешна» — перегрузка видна только по таймауту подтверждения.
  • Persistent + durable + confirm — минимальный набор, чтобы сообщение переживало перезапуск; атомарность с БД даёт outbox.
