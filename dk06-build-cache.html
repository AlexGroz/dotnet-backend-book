Глава 6. Кэш слоёв и .dockerignore

Почему сборка идёт четыре минуты вместо двадцати секунд и как это исправить

основная глава

Один и тот же проект, разница — в порядке строк

Два Dockerfile для одного и того же приложения. Меняем ровно один файл — Program.cs — и собираем заново:

«COPY . . → restore → publish»    3 мин 47 с   ← пересобирается ВСЁ, включая restore
«csproj → restore → COPY . .»     24 с        ← restore взялся из кэша

Дело не в мощности машины и не в флагах: Docker умеет не переделывать то, что не менялось, но только если вы дали ему такую возможность — порядком инструкций и файлом .dockerignore. Это два рычага, которые дают почти весь эффект, и оба разобраны ниже.

Что такое кэш сборки

В главе 3 мы выяснили: инструкции RUN, COPY и ADD создают слои, а слои неизменяемы и у каждого есть свой идентификатор — хеш. Отсюда главное: если Docker уже построил слой с точно таким же содержимым, второй раз строить его не нужно — можно взять готовый.

Готовые слои лежат не «в образе», а рядом — в кэше сборки локального демона. Сколько он занимает:

Сколько места Docker занимает на диске

$ docker system df
TYPE            TOTAL     ACTIVE    SIZE      RECLAIMABLE
Images          14        3         6.812GB   4.201GB (61%)
Containers      5         1         128.4MB   127.9MB (99%)
Local Volumes   2         2         1.024GB   0B (0%)
Build Cache     96        0         2.318GB   2.318GB
  • docker system df — «сколько занимает Docker» (df = disk free, как у одноимённой команды Linux).
  • Строка Build Cache — это и есть кэш слоёв: 2.3 ГБ промежуточных результатов сборок. Он растёт с каждой сборкой, в которой что-то менялось.
  • ACTIVE = 0 — ни один существующий образ эти слои не использует.
  • RECLAIMABLE — сколько можно освободить; (61%) — доля от строки.
Кэш можно удалить — и вместе с ним уйдёт скорость 
$ docker builder prune          # удалить неиспользуемый кэш сборки (спросит подтверждение)
$ docker builder prune -af      # удалить всё и без вопросов (-a = all, -f = force)
$ docker build --no-cache -t orders-api:1.4.2 .   # собрать, НЕ читая кэш (новые слои в кэш запишутся)

prune — «подрезать»: удалить то, что не используется. Типичная причина прибегнуть к нему — «на диске кончилось место». После него первая сборка снова будет холодной, поэтому в CI это делают редко, а на ноутбуке — когда место реально нужно.

Как Docker решает: взять из кэша или пересобрать

Ключ кэша для каждой инструкции складывается из трёх вещей:

Из чегоЧто это значит на практике
родительский слой слои идут цепочкой: пересобрался слой выше — всё, что ниже, тоже станет другим
текст инструкции изменили строку RUN (даже добавили флаг или лишний пробел) — слой считается новым
содержимое файлов
(для COPY/ADD)		 хеш считается по байтам файлов и их правам, а не по дате изменения

Три вывода, которые надо запомнить сразу:

  • Дата файла не важна. Скопировали файл заново с тем же содержимым — кэш жив. Изменили один байт — кэш этого слоя мёртв.
  • Кэш рвётся цепочкой. Docker идёт по Dockerfile сверху вниз и на первом несовпадении перестаёт искать кэш: этот шаг и все следующие выполняются заново.
  • Инструкции-настройки кэшируются тоже. WORKDIR, ENV, EXPOSE не создают файлов, но если их строка не менялась — шаг мгновенный.

Как это выглядит в выводе. Современный сборщик (BuildKit, он работает по умолчанию в Docker 23 и новее) помечает взятые из кэша шаги словом CACHED:

Повторная сборка без изменений: docker build --progress=plain

$ docker build --progress=plain -t orders-api:1.4.2 .
#1 [internal] load build definition from Dockerfile
#1 DONE 0.0s
#4 [1/5] FROM mcr.microsoft.com/dotnet/sdk:8.0
#4 CACHED
#5 [2/5] WORKDIR /src
#5 CACHED
#6 [3/5] COPY . .
#6 CACHED
#7 [4/5] RUN dotnet publish -c Release -o /app
#7 CACHED
#8 [5/5] WORKDIR /app
#8 CACHED
#9 exporting to image
#9 DONE 0.1s

Вся сборка заняла 1.8 секунды: ни одна инструкция не выполнялась, образ собран из готовых слоёв. --progress=plain — «покажи текстовый лог вместо анимированного списка»; он нужен, когда лог читают глазами или разбирают в CI, где анимация бессмысленна.

В старом сборщике (до Docker 23) то же самое называлось Using cache, и вывод был другим:

Step 4/6 : RUN dotnet publish -c Release -o /app
 ---> Using cache
 ---> 5d3c1b7a9e21

Смысл один: шаг не выполнялся, взят готовый слой 5d3c1b7a9e21. Дальше в книге используется вывод BuildKit — если у вас старый Docker, ищите вместо CACHED строку Using cache.

Что сбрасывает кэш: таблица

Практически важнее не «как считается хеш», а что именно пересобирается в каждом типичном случае. Таблица — для Dockerfile в порядке COPY . . → RUN publish (как в главе 5); как это исправить — в следующем разделе.

Что изменилосьЧто выполняется заново
ничегоничего — все шаги CACHED, секунда-две
один .cs файл COPY . . и всё ниже (то есть restore и publish)
файл .csproj (новый пакет) COPY проекта и всё ниже — здесь пересборка неизбежна: зависимости действительно изменились
строка RUN — добавили флаг этот шаг и всё ниже, даже если команда делает то же самое
базовый образ обновился всё: FROM стоит первым, а под ним меняются все слои. Само по себе это не происходит — нужен --pull или смена тега
--no-cache всё, полностью холодная сборка

Из таблицы видно, что управлять можно только одним: какие файлы попадают в каждый слой COPY. Если в слое лежит весь проект, то любая правка в любом файле убивает этот слой и всё, что после него. Если в слое лежат только файлы проектов — правка кода его не трогает.

Главная ошибка: COPY . . перед restore

Так пишет почти каждый, кто собрал первый образ по образцу из интернета:

Плохо: весь код копируется до восстановления пакетов

FROM mcr.microsoft.com/dotnet/sdk:8.0
WORKDIR /src
COPY . .                                      # ← весь проект, включая bin/obj
RUN dotnet restore                            # ← restore ПОСЛЕ копирования
RUN dotnet publish -c Release -o /app --no-restore

Что происходит, когда вы поменяли одну строку в Program.cs:

  1. Слой COPY . . изменился (изменился файл внутри него) — кэш этого слоя мёртв.
  2. Так как родительский слой стал другим, все следующие шаги тоже выполняются заново.
  3. dotnet restore заново ходит в NuGet и заново разворачивает 180 пакетов.
  4. dotnet publish компилирует весь solution с нуля.

Правильный порядок: сначала копируем только то, от чего зависит restore — файлы проектов и solution, — восстанавливаем пакеты, и лишь потом весь остальной код.

Хорошо: restore зависит только от .csproj

FROM mcr.microsoft.com/dotnet/sdk:8.0
WORKDIR /src

# 1) только описание проектов: список пакетов и ссылки между проектами
COPY Orders.sln ./
COPY Orders.Api/Orders.Api.csproj Orders.Api/
COPY Orders.Domain/Orders.Domain.csproj Orders.Domain/

# 2) restore читает .csproj и качает пакеты — код ему не нужен
RUN dotnet restore

# 3) а теперь весь код: этот слой будет меняться при каждой правке
COPY . .

# 4) --no-restore: пакеты уже восстановлены, второй раз в сеть не идём
RUN dotnet publish Orders.Api/Orders.Api.csproj -c Release -o /app --no-restore

Почему это работает: хеш слоя COPY Orders.Api/Orders.Api.csproj … считается только по содержимому этого файла. Правка Program.cs его не касается, значит и слой RUN dotnet restore остаётся годным. Меняется только слой COPY . . и всё ниже. Проверяется глазами за одну сборку:

Изменили Program.cs — restore берётся из кэша

$ docker build --progress=plain -t orders-api:1.4.2 .
#4 [1/8] FROM mcr.microsoft.com/dotnet/sdk:8.0
#4 CACHED
#5 [2/8] WORKDIR /src
#5 CACHED
#6 [3/8] COPY Orders.sln ./
#6 CACHED
#7 [4/8] COPY Orders.Api/Orders.Api.csproj Orders.Api/
#7 CACHED
#8 [5/8] COPY Orders.Domain/Orders.Domain.csproj Orders.Domain/
#8 CACHED
#9 [6/8] RUN dotnet restore
#9 CACHED                                    ← 1 мин 20 с сэкономлено
#10 [7/8] COPY . .
#10 DONE 0.4s                                 ← выполнился: код изменился
#11 [8/8] RUN dotnet publish ... --no-restore
#11 DONE 22.9s                                ← только компиляция
Цена этого приёма: список COPY надо поддерживать

Добавили новый проект в solution — допишите строку COPY для его .csproj, иначе dotnet restore упадёт с «project not found». В свежих версиях BuildKit есть COPY --parents */*.csproj ./, которая копирует файлы с сохранением путей, но она появилась поздно — в примерах книги используется явный список, он работает везде.

Второй вариант, без списка: положить все .csproj в один слой через COPY */*.csproj ./ нельзя — эта форма «сплющивает» структуру папок, и ссылки между проектами сломаются.

Второй рычаг: .dockerignore

Прежде чем выполнить первую инструкцию, Docker должен получить контекст сборки — ту папку, которую вы указали в конце команды (docker build … . — точка означает «текущая папка»). Всё, что в ней лежит, уходит демону; всё, что ушло, доступно для COPY. По умолчанию туда попадает вся папка, включая то, что к образу отношения не имеет.

Сборка без .dockerignore: сколько уходит демону

$ docker build -t orders-api:1.4.2 .
#1 [internal] load .dockerignore
#1 transferring context: 2B done
#2 [internal] load build context
#2 transferring context: 1.21GB 38.4s done      ← контекст: папка bin, obj, .git, .vs
#2 DONE 38.6s

1.2 ГБ и 38 секунд — до того, как началась хоть одна инструкция. И это каждый раз, потому что Docker обязан пересчитать хеши файлов, чтобы понять, изменился ли слой COPY . ..

Три следствия, каждое из которых ломает работу:

  • Медленно. Передача контекста — это чистые накладные расходы на каждой сборке.
  • Образ пухнет. COPY . . затащит внутрь bin/Debug, obj и .git. В образе окажется старая локальная сборка рядом с новой, а вместе с ней история коммитов.
  • Кэш нестабилен. obj/project.assets.json и obj/*.cache переписываются при каждой локальной сборке. Значит слой COPY . . считается изменённым, даже если вы не тронули ни строки кода.

Лечится файлом .dockerignore в корне контекста (рядом с Dockerfile). Синтаксис — как у .gitignore: по одному шаблону в строке, # — комментарий, ! в начале — исключение из правила.

.dockerignore для .NET-проекта

# артефакты локальной сборки — они появятся внутри образа заново
**/bin/
**/obj/

# git-история и настройки IDE: к сборке отношения не имеют
.git/
.gitignore
.vs/
.vscode/
*.user
*.suo

# тесты и их данные — в продакшен-образ не нужны
tests/
**/*Tests*/

# локальные секреты и файлы окружения
.env
appsettings.Development.json

# сам Dockerfile и этот файл копировать в образ незачем
Dockerfile
.dockerignore

# документация и мусор ОС
*.md
.DS_Store

# исключение из правила: вся папка docs/ не нужна, но одну схему отдаём в образ
docs/
!docs/schema.json
  • **/bin/ — «папка bin на любой глубине»: ** означает любое число вложенных папок. Без звёздочек пришлось бы писать путь для каждого проекта.
  • Слэш в конце (bin/) — «только папка», а не файл с таким именем.
  • ! — исключение из правила, работает в обратную сторону. В примере выше docs/ выбрасывает папку целиком, а следующая строка !docs/schema.json возвращает из неё один файл. Порядок важен: правила применяются сверху вниз, и побеждает последнее совпавшее. Поменяете эти две строки местами — схема снова уедет в игнор.

Тот же проект с .dockerignore: файл — рядом с результатом

# .dockerignore рядом с Dockerfile (ключевые строки; целиком — выше)
**/bin/
**/obj/
.git/
tests/
docs/
!docs/schema.json

$ docker build -t orders-api:1.4.2 .
#1 [internal] load .dockerignore
#1 transferring context: 2B done
#2 [internal] load build context
#2 transferring context: 4.12MB 0.1s done       ← было 1.21GB / 38.4s
#2 DONE 0.2s

И та же разница в одном месте — чтобы не сверять два блока глазами по всей странице:

контекст сборки1.21 ГБ4.12 МБ
передача демону38.4 с0.1 с

что окажется в образестарые dll из bin/Debug рядом с новыми только то, что собралось внутри
Что в .dockerignore класть нельзя

Всё, что нужно самой сборке: *.csproj, *.sln, Directory.Build.props, Directory.Packages.props, nuget.config, global.json. Если исключить их «на всякий случай», сборка упадёт на dotnet restore — причём с сообщением про отсутствующий проект, а не про .dockerignore. Исключённый файл не существует для COPY: попытка скопировать его даёт ошибку "/x.csproj": not found.

Ещё одна тонкость: .dockerignore ищется в корне контекста. Если Dockerfile лежит в подпапке (-f docker/Api.Dockerfile), а контекст — корень репозитория, файл всё равно должен быть в корне. BuildKit дополнительно понимает файл с именем Api.Dockerfile.dockerignore рядом с самим Dockerfile — это удобно, когда Dockerfile'ов несколько.

Кэш пакетов NuGet: --mount=type=cache

Слой RUN dotnet restore кэшируется целиком, но у него есть слабое место: как только меняется хоть один .csproj, слой пересобирается — и restore заново скачивает все пакеты из сети. Пакеты при этом не менялись, качается то же самое по сто раз.

BuildKit умеет выносить папку из слоя в отдельный кэш: инструкция RUN --mount=type=cache монтирует папку target внутрь шага, но не сохраняет её в образ. Живёт такая папка в кэше демона и переживает между сборками.

Dockerfile с кэшем пакетов

# syntax=docker/dockerfile:1
#  ↑ первая строка файла: «какую версию языка Dockerfile использовать».
#    Нужна для новых возможностей вроде --mount; требует BuildKit (он по умолчанию в Docker 23+)

FROM mcr.microsoft.com/dotnet/sdk:8.0
WORKDIR /src

COPY Orders.sln ./
COPY Orders.Api/Orders.Api.csproj Orders.Api/
COPY Orders.Domain/Orders.Domain.csproj Orders.Domain/

# папка /root/.nuget/packages — это и есть локальный «склад» пакетов NuGet.
# target=...   — что монтировать (путь внутри контейнера)
# sharing=locked — не давать двум одновременным сборкам писать в один кэш
RUN --mount=type=cache,target=/root/.nuget/packages,sharing=locked \
    dotnet restore

COPY . .
# --no-restore обязателен: иначе publish сделает restore заново, уже без кэша-монтирования
RUN dotnet publish Orders.Api/Orders.Api.csproj -c Release -o /app --no-restore

Что меняется на практике: первая сборка качает пакеты (как раньше), а все следующие — даже после правки .csproj — берут их с диска.

Изменили .csproj: restore выполняется, но без сети

#9 [6/8] RUN --mount=type=cache,target=/root/.nuget/packages ... dotnet restore
#9 DONE 3.2s          ← без кэша пакетов здесь было бы 28.4s
Три вещи, которые здесь легко понять неправильно
  • Слой всё равно пересобирается. Кэш пакетов экономит скачивание, а не сам restore. Поэтому порядок «сначала .csproj, потом код» из предыдущего раздела всё равно нужен.
  • Пакетов в образе не будет. В образ попадает результат — папка /app с уже собранными dll. Именно поэтому publish идёт с --no-restore: иначе он не найдёт пакетов (их нет в слое) и полезет в сеть.
  • Кэш общий на машину, а не на проект. Два разных проекта с одной версией пакета скачают его один раз — это плюс, но и причина, по которой кэш может занять гигабайты (см. docker system df в начале главы).

Если контейнер работает не от root (глава 5, USER), путь другой: /home/app/.nuget/packages. Проверить, где NuGet держит пакеты внутри контейнера, можно так:

$ docker run --rm mcr.microsoft.com/dotnet/sdk:8.0 \
    dotnet nuget locals global-packages --list
global-packages: /root/.nuget/packages/
  • docker run --rm <образ> <команда> — запустить одноразовый контейнер и удалить его после выхода (--rm); удобно, чтобы что-то посмотреть внутри образа.
  • dotnet nuget locals global-packages --list — «покажи путь, где NuGet хранит пакеты» (locals — локальные хранилища, --list — только вывести, не чистить).

Кэш в CI: почему на сервере всё медленно

Локально кэш живёт в демоне на вашей машине. В CI (continuous integration — сборка и тесты на сервере; расшифровка и зачем это нужно — во врезке в оглавлении раздела) каждый запуск — новый чистый раннер (виртуальная машина, которая создаётся под задачу и потом уничтожается), поэтому кэша там нет и сборка каждый раз холодная. Отсюда классическая жалоба «локально 20 секунд, в пайплайне 5 минут».

Решение: вынести кэш наружу — в реестр образов, который переживает раннер. Собирать нужно через docker buildx build (buildx — плагин сборки на BuildKit; обычный docker build — его упрощённая обёртка, у которой нет флагов --cache-to/--cache-from):

Сборка в CI с кэшем в реестре

$ docker buildx build \
    --cache-from type=registry,ref=ghcr.io/acme/orders-api:buildcache \
    --cache-to   type=registry,ref=ghcr.io/acme/orders-api:buildcache,mode=max \
    --pull \
    -t ghcr.io/acme/orders-api:1.4.2 \
    --push .
  • --cache-from type=registry,ref=… — «возьми кэш из образа …:buildcache в реестре». В первый раз его там нет — сборка просто холодная.
  • --cache-to …,mode=max — «положи кэш обратно в реестр». mode=max кэширует все стадии сборки, а не только финальный образ; для multi-stage (глава 7) это важно, иначе кэш стадии компиляции не сохранится.
  • --pull — «проверь, не обновился ли базовый образ». Без него FROM может годами браться из локального кэша, и security-патчи в образ не приезжают.
  • --push — сразу отправить результат в реестр (глава 3).
  • Нужен docker login к этому реестру — --cache-to пишет туда, а не к вам на диск.

Более дешёвый вариант — inline cache: метаданные кэша встраиваются в сам образ, отдельный образ-кэш не нужен.

# при сборке: встроить метаданные кэша в образ
$ docker buildx build --build-arg BUILDKIT_INLINE_CACHE=1 -t ghcr.io/acme/orders-api:1.4.2 --push .

# при следующей сборке: взять кэш из предыдущего образа
$ docker buildx build --cache-from ghcr.io/acme/orders-api:1.4.2 -t ghcr.io/acme/orders-api:1.4.3 --push .

Минус inline-варианта: кэшируются только слои, попавшие в финальный образ. Если финальная стадия — маленький aspnet-образ, то слой с dotnet restore и компиляцией в него не попадёт, и кэша не будет. Поэтому в реальных пайплайнах чаще берут type=registry,mode=max.

В GitHub Actions то же самое настраивается двумя строками в docker/build-push-action:

- uses: docker/build-push-action@v6
  with:
    context: .
    push: true
    tags: ghcr.io/acme/orders-api:1.4.2
    cache-from: type=gha
    cache-to: type=gha,mode=max

type=gha — кэш силами самого GitHub Actions (отдельного реестра не нужно); работает то же mode=max.

Когда кэш мешает

Кэш — это доверие к прошлым результатам. Если в образ «не приехало» изменение, которое точно закоммичено, первым делом собирают с --no-cache (или чистят кэш в CI) — и смотрят, воспроизводится ли проблема. Частые причины: файл попал в .dockerignore; кэш в реестре остался от другой ветки с тем же тегом; сборка идёт с context не из той папки.

★ Что запомнить из главы
  • Кэш слоёв — это готовые слои в демоне. Ключ слоя = родительский слой + текст инструкции + содержимое файлов, а не дата изменения.
  • Кэш рвётся цепочкой: на первом несовпадении пересобирается этот шаг и все следующие. Поэтому порядок инструкций — главный рычаг.
  • Правильный порядок для .NET: csproj/sln → dotnet restore → COPY . . → dotnet publish --no-restore.
  • .dockerignore с **/bin/, **/obj/, .git/: контекст падает с гигабайта до мегабайт, и кэш перестаёт дёргаться от локальных сборок.
  • RUN --mount=type=cache,target=/root/.nuget/packages — пакеты не перекачиваются; сам restore при изменении .csproj всё равно выполнится.
  • В CI кэша нет по определению: его выносят в реестр через --cache-to/--cache-from type=registry,mode=max и добавляют --pull.
  • Диагностика одной командой: docker build --progress=plain — ищите, с какого шага пропало CACHED; там и причина.
Проверить свой проект за пять минут
  1. docker system df — сколько сейчас занимает Build Cache.
  2. Добавьте .dockerignore из этой главы и соберите: строка transferring context должна упасть в десятки раз.
  3. Поставьте в Dockerfile порядок «csproj → restore → COPY . .» и --no-restore в publish.
  4. Соберите с --progress=plain и запомните время. Поправьте один .cs, соберите снова — шаг RUN dotnet restore должен стать CACHED.
  5. Добавьте # syntax=docker/dockerfile:1 и --mount=type=cache для NuGet; проверьте, что publish с --no-restore не падает.
