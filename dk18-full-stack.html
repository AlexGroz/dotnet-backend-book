Четыре сервиса в четырёх контейнерах: один compose-файл, реальный запуск и граница с Kubernetes

факультатив

Вопрос, с которого всё начинается

В книге по Redis мы подняли один контейнер (redis:7-alpine), в книге по RabbitMQ — второй. И тут возникает естественный вопрос: а как из этого собирается целый проект? Наше .NET-приложение — тоже в контейнере? PostgreSQL? И главное: это четыре отдельных контейнера или один общий, внутри которого всё запущено?

Короткий ответ: каждый процесс — в своём контейнере, а связывает их один файл compose.yaml и одна команда docker compose up -d --build. Ниже — полный рабочий пример на четыре сервиса, все выводы в главе сняты с реального запуска:

СервисОбразКто собираетЧто делает
API на .NET 8свой, из ./api/Dockerfileвы обрабатывает HTTP-запросы, ходит в остальные три
PostgreSQL 16postgres:16-alpineвендоры постоянные данные, том pgdata
Redis 7redis:7-alpineвендоры общий счётчик и кэш, том не нужен
RabbitMQ 3.13rabbitmq:3-management-alpineвендоры очереди, веб-консоль на 15672, том mqdata

Формулировка, которую стоит держать в голове: контейнер — это упаковка для одного главного процесса. Не «маленькая виртуалка, куда можно поставить что угодно», а способ доставить один процесс с его файлами и запустить его изолированно. Отсюда всё остальное в этой главе.

Почему порознь, а не всё в одном контейнере

Шесть причин, каждая из которых на практике оказывается важнее, чем кажется на старте:

  • Разные жизненные циклы. API пересобирается на каждый коммит, PostgreSQL живёт годами, Redis можно перезапустить в любой момент. В одном контейнере любое действие означает перезапуск всех.
  • Масштабирование по отдельности. Реплик API нужно три, Redis — одна, PostgreSQL — одна с репликой. Один контейнер масштабируется только целиком (и утащит за собой базу).
  • Падение одного не должно ронять остальные. Упавший процесс в общем контейнере — это остановленный контейнер: docker ps покажет, что «сервис умер», но не скажет, что именно упало.
  • Healthcheck и логи — по сервису. В примере ниже docker compose ps показывает healthy отдельно у каждого: видно, что именно не поднялось.
  • Обновления безопасности. Вендор выпустил патч Redis — вы меняете тег образа и перезапускаете один контейнер, не пересобирая приложение.
  • Права и лимиты. API работает под non-root и со своим лимитом памяти, PostgreSQL — со своим пользователем и своим лимитом. В общем контейнере это невозможно.
«А если всё-таки сложить всё в один контейнер?»

Технически возможно: entrypoint-скрипт или супервизор (supervisord, s6-overlay) запускает PostgreSQL, Redis, RabbitMQ и dotnet api.dll в одном контейнере. Так иногда делают демо-стенды и старые «монолитные» образы.

Цена: супервизор должен сам перезапускать упавшие процессы (Docker этого не умеет — он следит только за PID 1); healthcheck один на всех, поэтому «контейнер healthy» ничего не говорит о базе; обновить Redis нельзя без пересборки образа; образ весит как все четыре вместе; логи четырёх процессов перемешаны в одном потоке; лимит памяти общий, и OOMKilled убивает сразу всё; при масштабировании API вы получаете вторую копию базы.

Отдельный случай — sidecar в Kubernetes: несколько контейнеров в одном поде делят сеть и диск, но это вспомогательные процессы (прокси, агент сбора логов), а не «всё приложение в одном месте».

Три способа собрать один и тот же проект

Файлы у всех трёх одинаковые — различается только то, где исполняется код:

РежимЧто в контейнерахКомандаКогда
Инфраструктура в Docker,
код на хосте		 только PostgreSQL, Redis, RabbitMQ docker compose up -d db redis rabbit (плюс override с портами, см. ниже), затем dotnet run каждый день: правите код, перезапуск за секунды, отладка в IDE
Всё в Docker все четыре, включая ваш API docker compose up -d --build проверка образа и настроек «как в проде», прогон e2e, демо
Прод ваш API; база, кэш и брокер — обычно managed-сервисы Kubernetes / App Service (глава 15) боевая эксплуатация

Разница между первым и вторым режимом — только в адресах: если код на хосте, он ходит на localhost:5432, localhost:6379, localhost:5672; если код в контейнере — на db:5432, redis:6379, rabbit:5672. Код при этом не меняется вообще — адреса приходят из конфигурации (глава 10).

Как выглядит проект в репозитории

Четыре файла и папка — этого достаточно, чтобы поднять весь стек:

shop/
├─ compose.yaml          ← описание стека: 4 сервиса, 2 тома, 1 сеть
└─ api/
   ├─ api.csproj         ← зависимости: Npgsql, StackExchange.Redis, RabbitMQ.Client
   ├─ Program.cs         ← код API (ниже)
   ├─ Dockerfile         ← как собрать образ API
   └─ .dockerignore      ← bin/ и obj/ не отправлять в контекст сборки

Фронтенд, фоновый воркер, второй сервис — всё это добавляется такими же блоками в compose.yaml: сервис web со своим build, сервис worker с тем же образом и другим command. Один docker compose up поднимает весь проект; на проде ту же роль играет Kubernetes (глава 15).

Код API: три зависимости и один /health

Ничего специфического для Docker здесь нет — обычное минимальное API на .NET 8. Оно нужно, чтобы проверить, что контейнеры видят друг друга:

using Npgsql;
using RabbitMQ.Client;
using StackExchange.Redis;

var builder = WebApplication.CreateBuilder(args);

// три адреса приходят из окружения: ConnectionStrings__Postgres / __Redis / __Rabbit
// (двойное подчёркивание = двоеточие, то есть ConnectionStrings:Postgres)
var pg    = builder.Configuration.GetConnectionString("Postgres")!;
var redis = builder.Configuration.GetConnectionString("Redis")!;
var amqp  = builder.Configuration.GetConnectionString("Rabbit")!;

var app = builder.Build();

// один ConnectionMultiplexer на процесс — как в главе 2 книги по Redis;
// адрес redis:6379 разрешается через DNS Docker, поэтому сервис обязан быть healthy
using var mux = await ConnectionMultiplexer.ConnectAsync(redis);

app.MapGet("/", () => "api is up");

// общий счётчик: значение живёт в Redis, а не в памяти процесса,
// поэтому одинаков для всех реплик API (а вот после down без тома он обнулится — см. ниже)
app.MapGet("/counter", async () =>
    $"counter = {await mux.GetDatabase().StringIncrementAsync("api:counter")}");

// /health проверяет все три зависимости: этот же адрес опрашивает healthcheck в compose
app.MapGet("/health", async () =>
{
    var ping = await mux.GetDatabase().PingAsync();

    string postgres;
    try
    {
        await using var conn = new NpgsqlConnection(pg);
        await conn.OpenAsync();          // реальное TCP-подключение к db:5432
        postgres = "ok";
    }
    catch (Exception e) { postgres = e.GetType().Name; }

    string rabbit;
    try
    {
        var factory = new ConnectionFactory { Uri = new Uri(amqp) };
        await using var conn = await factory.CreateConnectionAsync();   // rabbit:5672
        rabbit = "ok";
    }
    catch (Exception e) { rabbit = e.GetType().Name; }

    return Results.Ok(new
    {
        redis = $"{ping.TotalMilliseconds:F1} ms",
        postgres,
        rabbitmq = rabbit
    });
});

app.Run();
  • GetConnectionString читает ConnectionStrings:* — в контейнере это переменные окружения ConnectionStrings__Postgres и т. д. Ничего не захардкожено: тот же образ работает и с db:5432 в compose, и с настоящей базой в проде.
  • Ошибки не пробрасываются, а возвращаются в JSON — чтобы /health отвечал даже когда база лежит, и было видно, что именно недоступно.
  • Счётчик в Redis, а не в поле класса — иначе у каждой реплики API был бы свой счётчик. Ровно поэтому Redis и появляется в проекте.

Dockerfile: две стадии вместо одной

Собирать образ для API на 4 файла принято так: сначала собрать в контейнере с SDK, затем положить результат в контейнер с рантаймом. Итоговый образ не содержит ни компилятора, ни исходников:

# стадия 1: сборка — здесь есть dotnet SDK (1.03 ГБ), но этот образ в результат не попадёт
FROM mcr.microsoft.com/dotnet/sdk:8.0-alpine AS build
WORKDIR /src
# сначала только csproj: слой с restore переиспользуется, пока не менялись пакеты
COPY api.csproj ./
RUN dotnet restore
COPY . .
RUN dotnet publish -c Release -o /out --no-restore

# стадия 2: запуск — только рантайм ASP.NET Core (160 МБ), без SDK и без исходников
FROM mcr.microsoft.com/dotnet/aspnet:8.0-alpine
WORKDIR /app
COPY --from=build /out .
USER $APP_UID
EXPOSE 8080
ENTRYPOINT ["dotnet", "api.dll"]
  • COPY api.csproj ./ до COPY . . — приём из главы 6: пока не менялся список пакетов, слой dotnet restore берётся из кэша, и пересборка занимает секунды.
  • USER $APP_UID — образ aspnet определяет переменную APP_UID (в проверке — 1654): контейнер запускается не от root.
  • Порт 8080 — не флаг, а настройка образа: в aspnet:8.0 задано ASPNETCORE_HTTP_PORTS=8080, поэтому app.Run() без настроек слушает 8080 (глава 13).
  • Разница в размере — реальная: SDK-образ 1.03 ГБ, итоговый shop-api — 166 МБ. Именно поэтому multi-stage не «оптимизация на потом», а норма (глава 7).

.dockerignore в этой папке — две строки, и обе важны: без них в контекст сборки приедут результаты вашей локальной сборки, и COPY . . положит в образ bin/ с obj/.

compose.yaml: четыре сервиса построчно

Этот файл лежит в корне проекта и целиком заменяет четыре команды docker run с десятком флагов у каждой. Комментарии — прямо в нём:

name: shop        # префикс имён: контейнеры станут shop-api-1, shop-db-1, сеть shop_default

services:
  # 1. наше приложение: не образ из реестра, а сборка из ./api по его Dockerfile
  api:
    build: ./api                     # docker compose сам вызовет docker build
    ports:
      - "8080:8080"                  # единственный публикуемый наружу порт: host 8080 → api 8080
    environment:
      # __ превращается в : — это ConnectionStrings:Postgres для IConfiguration
      ConnectionStrings__Postgres: Host=db;Database=app;Username=app;Password=secret
      ConnectionStrings__Redis: redis:6379
      ConnectionStrings__Rabbit: amqp://app:secret@rabbit:5672
    depends_on:                      # ждать не «запуска», а готовности (healthcheck ниже)
      db:     { condition: service_healthy }
      redis:  { condition: service_healthy }
      rabbit: { condition: service_healthy }
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://localhost:8080/health"]
      interval: 5s
      timeout: 3s
      retries: 5

  # 2. база: официальный образ, своя переменная с паролем и том для файлов
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: app             # создаётся при первом старте (пустой том)
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: app
    volumes:
      - pgdata:/var/lib/postgresql/data   # данные ВНЕ контейнера
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d app"]   # готовность базы, а не «процесс жив»
      interval: 3s
      timeout: 3s
      retries: 10

  # 3. кэш: порт наружу не публикуем — он нужен только api внутри сети
  redis:
    image: redis:7-alpine
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 3s
      timeout: 3s
      retries: 10

  # 4. брокер: 15672 публикуем, чтобы открыть веб-консоль в браузере
  rabbit:
    image: rabbitmq:3-management-alpine
    ports:
      - "15672:15672"
    environment:
      RABBITMQ_DEFAULT_USER: app     # вместо гостя по умолчанию — свой пользователь
      RABBITMQ_DEFAULT_PASS: secret
    volumes:
      - mqdata:/var/lib/rabbitmq     # очереди и пользователи переживают пересоздание
    healthcheck:
      test: ["CMD", "rabbitmq-diagnostics", "-q", "ping"]
      interval: 5s
      timeout: 5s
      retries: 10

volumes:          # объявленные тома: Docker создаёт их при первом up
  pgdata:
  mqdata:

Почему condition: service_healthy, а не просто depends_on

Без условия compose гарантирует только порядок запуска: контейнер db создан раньше api. Но PostgreSQL после старта процесса ещё секунды инициализирует кластер и принимает не все подключения. С условием compose ждёт, пока healthcheck не станет healthy, и лишь потом стартует зависимый сервис — это видно в реальном логе запуска (фрагмент, порядок строк сохранён):

Container shop-redis-1 Started
Container shop-redis-1 Waiting        ← ждём healthcheck redis
Container shop-db-1 Waiting           ← и базы
Container shop-rabbit-1 Waiting       ← и брокера
Container shop-redis-1 Healthy        ← только теперь
Container shop-db-1 Healthy
Container shop-rabbit-1 Healthy
Container shop-api-1 Starting         ← и только после этого — api
Container shop-api-1 Started

Отсюда практическое правило: healthcheck есть у всех, кто нужен другим. Если его нет, service_healthy работать не будет, и придётся либо добавлять проверку, либо жить с гонкой на старте.

Имена и порты: localhost против db

Compose создаёт сеть shop_default и подключает к ней все четыре контейнера. Внутри неё каждый сервис доступен по своему имени из файла и внутреннему порту: db:5432, redis:6379, rabbit:5672. Поэтому в environment у API стоят именно такие адреса.

Главная ловушка новичка: localhost внутри контейнера — это сам контейнер

Если в строке подключения написать Host=localhost;Port=5432, API будет искать базу в своём контейнере — и не найдёт: там только dotnet. Ошибка выглядит как NpgsqlException: Failed to connect или RedisConnectionException, хотя база жива и docker compose ps показывает healthy.

Правило: внутри контейнера — имя сервиса (db, redis), с хоста — localhost и опубликованный порт. Публиковать порт (ports) при этом нужно только ради доступа с хоста: базе и Redis в этой схеме он не нужен.

Теперь три запроса — они и есть проверка, что собран именно проект, а не четыре отдельных контейнера:

curl -s localhost:8080/health
# {"redis":"0.4 ms","postgres":"ok","rabbitmq":"ok"}     ← все три зависимости отвечают

curl -s localhost:8080/
# api is up

curl -s localhost:8080/counter    # первый запрос
# counter = 1
curl -s localhost:8080/counter    # второй
# counter = 2                     ← значение растёт в Redis, а не в памяти процесса

Логи — по сервису, а не «всё в кучу»: docker compose logs api, docker compose logs -f db (потоком), docker compose logs --tail 50 rabbit.

Что в логах API выглядит страшно, но не является ошибкой

В docker compose logs api после старта появляются две строки:

Cannot load library libgssapi_krb5.so.2
Error: Error loading shared library libgssapi_krb5.so.2: No such file or directory

Это Npgsql при первом подключении проверяет, есть ли в системе библиотека Kerberos (GSSAPI): в alpine-образе её нет. Проверено отдельной программой, которая подключается только к PostgreSQL: те же две строки и сразу за ними pg ok: 1. Подключение по логину и паролю от этого не страдает — /health в тот же момент отвечает "postgres":"ok". Если сообщение мешает, поставьте пакет krb5-libs в свой образ или используйте не-alpine базу.

Как убедиться, что внутри действительно четыре разных сервиса

Три команды, по одной на каждую инфраструктурную зависимость (-T отключает TTY — нужно для скриптов и копирования вывода):

# Redis: что в нём лежит после двух /counter
docker compose exec -T redis redis-cli keys '*'
# api:counter
docker compose exec -T redis redis-cli get api:counter
# 2

# PostgreSQL: версия движка и наша таблица
docker compose exec -T db psql -U app -d app -tAc 'select version();'
# PostgreSQL 16.15 on x86_64-pc-linux-musl, compiled by gcc (Alpine 15.2.0) 15.2.0, 64-bit

# RabbitMQ: пользователи брокера
docker compose exec -T rabbit rabbitmqctl list_users
# Listing users ...
# user  tags
# app   [administrator]

Ещё два места, куда стоит заглянуть: веб-консоль брокера http://localhost:15672 (логин app / secret) и docker compose images — видно, что образы разные, и API среди них самый маленький (вывод сокращён: убраны ID, платформа и дата):

CONTAINER           REPOSITORY          TAG                   SIZE
shop-api-1          shop-api            latest                166MB
shop-db-1           postgres            16-alpine             419MB
shop-rabbit-1       rabbitmq            3-management-alpine   275MB
shop-redis-1        redis               7-alpine              58MB

Тома: что переживает down, а что нет

Данные базы лежат на томе pgdata, то есть вне контейнера. Проверка на живом стенде: создаём таблицу, полностью останавливаем и удаляем стек, поднимаем заново:

docker compose exec -T db psql -U app -d app -c 'create table items(id int primary key, name text);
insert into items values (1, $$Молоток$$);'
# CREATE TABLE
# INSERT 0 1

docker compose down          # контейнеры и сеть удалены, тома остались
docker compose up -d         # без --build: образ уже есть
docker compose exec -T db psql -U app -d app -tAc 'select * from items'
# 1|Молоток                  ← строка на месте: она была на томе, а не в контейнере

docker compose exec -T redis redis-cli dbsize
# 0                         ← а Redis без тома пуст: счётчик api:counter пропал
curl -s localhost:8080/counter
# counter = 1               ← нумерация началась заново

Это не случайность, а решение: база и брокер хранят состояние, кэш — нет. Если дать Redis том, он «выживет» пересоздание, но это уже не кэш, а хранилище с обязательствами по персистентности (книга по Redis, глава 5).

down и down -v — разница в одну букву и в ваши данные

docker compose down удаляет контейнеры и сеть, тома сохраняет. docker compose down -v удаляет и тома: PostgreSQL стартует с пустым кластером, RabbitMQ — с пустыми очередями. На проде это выглядит как «мы случайно стёрли базу», поэтому команду с -v выполняют осознанно и только на локальном стенде.

И наоборот: docker compose ps ничего не покажет про данные — «healthy» говорит о процессе, а не о том, что в базе.

Пользователь и пароль: как это ломается на практике

Пароль должен совпадать в двух местах: в переменных брокера (RABBITMQ_DEFAULT_USER/PASS) и в строке подключения у API. Проверка «а что если не совпадёт»: меняем одну строку в environment у api на amqp://guest:guest@rabbit:5672 и пересоздаём сервис:

docker compose up -d api            # compose увидел изменение environment и пересоздал контейнер
curl -s localhost:8080/health
# {"redis":"0.5 ms","postgres":"ok","rabbitmq":"BrokerUnreachableException"}
#                                     ↑ Redis и база живы, брокер — нет

docker compose logs rabbit | grep -i refused
# [error] PLAIN login refused: user 'guest' - invalid credentials

Причина в том, что RABBITMQ_DEFAULT_USER: app заменяет пользователя по умолчанию: пользователя guest в этом брокере просто нет. Обратите внимание на важное: API при этом запустился, docker compose ps покажет его healthy только потому, что healthcheck смотрит на /health, а тот возвращает 200 с описанием проблемы. Если бы /health падал, compose держал бы контейнер в статусе unhealthy — и это правильное поведение: сервис работает частично, и ему нельзя давать трафик.

По умолчанию в RabbitMQ гость ограничен localhost, но не в этом образе

Классическое правило RabbitMQ — пользователь guest может подключаться только с localhost. В образе rabbitmq:3-management-alpine ограничение снято (loopback_users = [], проверено rabbitmq-diagnostics environment): добавленный руками guest подключается из другого контейнера без ошибок. Вывод практический: не полагайтесь на «гостя по умолчанию» ни в одном окружении — создавайте своего пользователя с паролем.

Пароли в compose.yaml — нормально только для локального стенда. В git они попадают вместе с файлом, поэтому для настоящих окружений берут env_file вне репозитория, секреты CI или менеджер секретов (глава 10).

Реплики: что меняется, когда API становится три

В compose можно попросить несколько экземпляров одного сервиса:

docker compose up -d --scale api=2
# Container shop-api-2 Error response from daemon: failed to set up container networking:
# Bind for 0.0.0.0:8080 failed: port is already allocated

Ошибка ожидаемая: ports: "8080:8080" требует один порт хоста на все реплики. В compose это решают так: у сервиса убирают ports (реплики становятся доступны только по имени api внутри сети), а перед ними ставят reverse-proxy — nginx, traefik или caddy, который слушает 80/443 и распределяет запросы по репликам. Здесь начинается граница возможностей compose: полноценные реплики, rolling update и перепланирование на другую машину — это Kubernetes (глава 15).

И главное, что видно на этом примере: реплики не должны хранить состояние в памяти. Счётчик в Redis у всех трёх экземпляров один и тот же — именно для этого он там и лежит.

Режим разработки: код на хосте, инфраструктура в контейнерах

Так работают каждый день: править код и перезапускать его за секунды, не пересобирая образ. Но здесь появляется то, чего не было раньше: порты баз нужно опубликовать, иначе с хоста до них не достучаться. Вместо правки основного файла делают override — compose автоматически склеивает compose.yaml и compose.override.yaml:

# compose.override.yaml — только то, что нужно для разработки; файл подхватывается автоматически
# (если в нём личные настройки — его не коммитят, в .gitignore)
services:
  db:
    ports: ["5432:5432"]     # host 5432 → контейнер 5432
  redis:
    ports: ["6379:6379"]
  rabbit:
    ports: ["5672:5672"]     # сам AMQP, консоль 15672 уже опубликована в основном файле
docker compose up -d db redis rabbit      # только инфраструктура, без api
ss -ltn | grep -E ':5432|:6379|:5672'
# LISTEN 0 4096 0.0.0.0:5672 ...
# LISTEN 0 4096 0.0.0.0:6379 ...
# LISTEN 0 4096 0.0.0.0:5432 ...

# тот же код, но на хосте; --no-launch-profile — чтобы ASPNETCORE_URLS не перебивался launchSettings.json
ConnectionStrings__Postgres='Host=localhost;Port=5432;Database=app;Username=app;Password=secret' \
ConnectionStrings__Redis='localhost:6379' \
ConnectionStrings__Rabbit='amqp://app:secret@localhost:5672' \
ASPNETCORE_URLS='http://localhost:5099' \
dotnet run -c Release --no-launch-profile
# info: Now listening on: http://localhost:5099

curl -s localhost:5099/health
# {"redis":"1.2 ms","postgres":"ok","rabbitmq":"ok"}
curl -s localhost:5099/counter
# counter = 2          ← счётчик ПРОДОЛЖИЛСЯ: в Redis уже лежало 1 от контейнерного API
curl -s localhost:5099/counter
# counter = 3

Две вещи, которые здесь стоит заметить. Во-первых, состояние общее: приложение в контейнере и приложение на хосте — два разных процесса, но счётчик у них один, потому что он в Redis; в этом и смысл внешнего хранилища. Во-вторых, адреса — единственное, что отличается: localhost:6379 с хоста и redis:6379 из контейнера. Код и Dockerfile те же.

Мелкая, но частая заминка

dotnet run без --no-launch-profile берёт порт из Properties/launchSettings.json и игнорирует ASPNETCORE_URLS — в проверке приложение поднялось на 5169 вместо заданного 5099. В контейнере launchSettings.json не используется вообще, поэтому там такой путаницы нет.

Прод: те же четыре сервиса, но другими инструментами

Compose — инструмент одной машины и ручного запуска. На проде каждый сервис живёт своей жизнью:

В composeВ KubernetesИли managed-сервис
api: build + ports Deployment (3 реплики) + Service + Ingress App Service, Cloud Run, ECS
db + том pgdata StatefulSet + PVC RDS, Cloud SQL, Azure Database
redisDeployment/StatefulSet ElastiCache, Memorystore
rabbit + том mqdataStatefulSet CloudAMQP, Amazon MQ
depends_on + healthcheckreadiness/liveness probes —
имена сервисов в сетиDNS Service строка подключения из конфигурации

Чего compose не умеет и почему его не берут на прод: нет rolling update, нет перепланирования контейнера на другую машину при падении хоста, нет автомасштабирования, нет нормального хранения секретов, всё привязано к одному демону Docker. Граница проходит ровно здесь: локально и в CI — compose, в эксплуатации — оркестратор или managed-сервисы (глава 15).

Важно, что ваш образ при этом не меняется: тот же shop-api:latest (точнее, образ с тегом-версией или digest) запускается и в compose, и в Kubernetes. Меняются только адреса в конфигурации — поэтому глава 10 про переменные окружения важнее, чем кажется.

А если Docker не хочется совсем?

Проект остаётся тем же: ваш код не зависит от того, где запущены сервисы — только от адресов в конфигурации. Варианты без Docker:

  • Нативные сервисы на машине разработчика: PostgreSQL из установщика, Redis из apt/brew, RabbitMQ из пакета; dotnet run подключается к localhost. Работает, но версии и настройки у всех свои, а «у меня не воспроизводится» становится нормой.
  • Один сервер с ручной установкой (или виртуалка) — так делали до контейнеров; обновления и бэкапы целиком на вас.
  • CI: сервисы всё равно нужны для тестов. В GitHub Actions это блок services: (он поднимает те же контейнеры), в GitLab CI — services в job. Docker там есть даже в проектах, которые «локально без Docker».
  • Managed-сервисы в облаке прямо во время разработки: дороже, но максимально близко к проду и без локального администрирования.

Поэтому Docker в этой книге — не религия, а способ получить одинаковое окружение: тот же образ базы, та же версия Redis, тот же брокер, что в CI и у коллеги.

★ Что запомнить из главы
  • Один процесс — один контейнер. API, PostgreSQL, Redis и RabbitMQ — четыре контейнера, даже если запускаются одной командой.
  • Связывает их compose.yaml: build/image, environment, volumes, depends_on с condition: service_healthy.
  • Внутри сети — имя сервиса и внутренний порт (db:5432, redis:6379); ports нужны только для доступа с хоста.
  • Данные — на томах, кэш — в памяти. down тома сохраняет, down -v — удаляет.
  • Код не зависит от окружения: различаются только адреса, и они приходят из конфигурации. Поэтому тот же образ идёт в compose, CI и Kubernetes.
