Глава 19. Кейс: тормозит критический REST-эндпоинт

Кейс ровно с собеседования: сложный запрос, перенесённый из Oracle, внезапно стал медленным. Собираем вместе всё из глав 13–18.

Ситуация

Эндпоинт GET /api/orders?status=NEW&page=1 давал p95 в несколько секунд. Запрос соединяет orders, customers, order_items и сортирует по дате. Он был перенесён из Oracle почти «как есть».

Шаг 1. Локализуем

По pg_stat_statements видно: этот запрос лидирует по total_exec_time. Значит, время уходит в БД, а не в приложение (методика — глава 16).

Шаг 2. Снимаем план

EXPLAIN (ANALYZE, BUFFERS) <сам запрос>;

В плане (упрощённо) находим три проблемы:

  • Seq Scan on orders o с Rows Removed by Filter в миллионы строк;
  • Nested Loop с очень большим loops по order_items;
  • Sort Method: external merge Disk — сортировка ушла на диск.

Шаг 3. Причины

  • По status и created_at нет подходящего индекса → Seq Scan.
  • Планировщик недооценил число заказов (статистика устарела) → выбрал Nested Loop (глава 15), который на реальных объёмах превратился в тысячи циклов.
  • Сортировка большого набора не влезла в work_mem.
  • В WHERE было приведение типа/функция над колонкой (наследие Oracle) → индекс не применялся, даже если бы он был.

Шаг 4. Исправляем

  • ANALYZE — обновить статистику; при необходимости поднять default_statistics_target.
  • Составной индекс: (status, created_at) — под фильтр и сортировку сразу.
  • Убрать функцию над колонкой из WHERE; если она нужна — сделать функциональный индекс.
  • Для пагинации — keyset-подход вместо больших OFFSET.
  • Увеличить work_mem для проблемного запроса (точечно, не глобально «на всё»).

Шаг 5. Проверяем

Снова EXPLAIN (ANALYZE, BUFFERS): Index Scan вместо Seq Scan, оценка строк совпала с фактом, сортировка в памяти. Затем — замер p95/p99 эндпоинта на реальной нагрузке (глава 31).

★ Готовый ответ по этому вопросу (сжато)

«Сначала локализую: время в приложении или в БД (pg_stat_statements, логи, трейсы). Затем снимаю EXPLAIN (ANALYZE, BUFFERS) на реальных параметрах. Узкое место ищу по actual time × loops и смотрю три вещи: расхождение rows и actual rows (плохая статистика → неверный план), тип сканирования (Seq Scan там, где нужен индекс) и работу с памятью (сортировки/hash на диск). По соединениям: Nested Loop плох при большом числе циклов, Hash — при нехватке work_mem (батчи на диск), Merge — когда требует дорогой сортировки; но корень обычно в оценке кардинальности. Дальше правлю причину: статистика, индексы, переписывание (убрать функции над колонками, ROWNUM → LIMIT, переписать (+)-джойны), при необходимости work_mem и партиционирование. И обязательно замеряю «до/после» на реальной нагрузке».
