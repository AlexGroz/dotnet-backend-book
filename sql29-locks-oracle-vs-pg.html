Глава 29. Блокировки: Oracle vs PostgreSQL

Второй вопрос интервью про различия: как ведут себя блокировки при чтении и записи в двух системах.

Чтение

В обеих СУБД обычный SELECT не блокируется чужими изменениями — он читает согласованный снимок (глава 28). Но есть нюансы:

  • В PostgreSQL SELECT берёт разделяемую блокировку таблицы (ACCESS SHARE), которая конфликтует с DDL: ALTER TABLE, TRUNCATE берут ACCESS EXCLUSIVE. Поэтому долгий запрос мешает изменить схему — и наоборот.
  • В Oracle SELECT тоже не ждёт писателей, но DDL ведёт себя иначе и авто-коммитится, тогда как в PostgreSQL DDL транзакционный.
  • Общее: длинные транзакции вредны в обеих, а в PostgreSQL они ещё и мешают VACUUM (глава 25).

Запись

  • И там, и там блокировка на уровне строки: UPDATE/DELETE блокируют конкретную строку, второй писатель той же строки ждёт.
  • Читатели строку не блокируют — видят прежнюю версию.
  • Для «прочитать и заблокировать» есть SELECT ... FOR UPDATE.
  • Deadlock обе системы обнаруживают: одну транзакцию отменяют с ошибкой — её нужно повторить (retry).

Что «блокирует» таблицу в PostgreSQL

ALTER TABLE, TRUNCATE, VACUUM FULL, CREATE INDEX (без CONCURRENTLY), CLUSTER берут сильные блокировки таблицы. Поэтому в продакшене используют CREATE INDEX CONCURRENTLY и короткие транзакции.

Уровни изоляции

  • По умолчанию в обеих — READ COMMITTED.
  • Oracle SERIALIZABLE = snapshot isolation; PostgreSQL SERIALIZABLE строже (SSI).
  • Ошибка 40001 (serialization failure) и deadlock в PostgreSQL — нормальная часть работы: критичные транзакции оборачивают в retry.
★ Готовый ответ про блокировки (сжато)

«В обеих системах чтение не блокирует запись и наоборот. Разница в деталях: в PostgreSQL важны table-level блокировки для DDL, поведение VACUUM и то, что долгие транзакции мешают очистке версий. Поэтому мы держали транзакции короткими, использовали CREATE INDEX CONCURRENTLY и добавили retry на сериализационные ошибки».
