Глава 2. Контейнер — это процесс: namespaces, cgroups, слои

Контейнер собран из трёх механизмов ядра Linux. Поняв их, вы перестаёте угадывать, почему команда «не работает», и можете объяснить это на интервью.

подводящая глава

Словарь, без которого дальше не прочитать

Пять слов будут встречаться в каждой главе — договоримся о них сразу.

СловоЧто это
Хост (host)Машина, на которой работает Docker: ваш ноутбук, сервер в облаке, виртуалка. Всё, что «с хоста», — это команды и файлы этой машины, а не контейнера
Демон (dockerd)Фоновый процесс Docker, который и делает всю работу: скачивает образы, создаёт контейнеры, выделяет им изоляцию. Сам он ничего не печатает — им управляют командами
CLI (docker)Программа в терминале. Она не создаёт контейнеры сама — она отправляет просьбу демону и печатает ответ
API«Язык», на котором CLI разговаривает с демоном: набор команд по HTTP через локальный сокет. Поэтому Docker-ом можно управлять и из кода, и из CI
Образ / контейнерОбраз — неизменяемый набор файлов и настроек. Контейнер — запущенный экземпляр образа со своим тонким диском (глава 1)
Как это выглядит в жизни

Вы пишете docker run nginx → CLI отправляет запрос демону → демон (если образа нет) скачивает его из реестра, создаёт контейнер, настраивает изоляцию и запускает процесс → CLI показывает вам ID контейнера. Когда вы позже пишете docker ps, CLI снова спрашивает демона «что запущено» и печатает ответ.

Сначала — жизненный цикл: контейнер не исчезает после остановки

Это место, где новички теряются. Запуск контейнера — создание объекта, а не «выполнение команды». Объект живёт дольше процесса внутри него:

docker run …            создан контейнер и запущен процесс    → процесс работает
процесс завершился      (сам, упал с ошибкой, или Ctrl+C)      → контейнер ОСТАНОВЛЕН, объект на месте
docker rm …             объект удалён                          → исчезли его файлы и метаданные
  • Остановленный контейнер — не мусор по определению. В нём остались docker logs (что писало приложение), код выхода (0 / 1 / 137) и файлы, которые процесс успел создать. Именно так разбирают падения.
  • Но их копится много. Каждый запуск — новый объект: после сотни экспериментов docker ps -a (полный список контейнеров, включая остановленные; подробно — глава 4) показывает сотню остановленных, и все занимают место.
  • Удаление — норма, а не авария. Образ остаётся на месте, поэтому удалённый контейнер ничего не ломает: следующий docker run создаст новый из того же образа. Данные, которые должны пережить удаление, держат в томе (глава 9).
Правило, которое снимает вопрос «зачем удалять»

Одноразовые запуски («посмотреть ps aux», «прогнать миграцию») — с --rm: объект удалится сам, как только процесс закончит работу. Сервисы (ваш API, база) — без --rm: если контейнер упал, нужны его логи и код выхода, чтобы понять причину. Чистка — отдельно: docker rm для конкретного контейнера, docker container prune — для всех остановленных (глава 4).

Один процесс, которому выдали своё окружение

Начнём с команды, которая выглядит непонятно, а делает простую вещь:

docker run --rm alpine ps aux

Разбираем каждую часть — и что она означает:

  • docker run — «создай контейнер из образа и запусти в нём программу».
  • --rm — когда программа закончит работу, удалить контейнер (зачем — в разделе выше).
  • alpine — имя образа: крошечный Linux (~5–8 МБ), поэтому его удобно запускать десятки раз подряд.
  • ps aux — программа внутри образа, а не команда Docker. ps = «process status»: печатает список процессов. Ключи: a — процессы всех пользователей, u — «пользовательский» формат (PID, USER, %CPU, TIME, COMMAND), x — включая процессы без терминала.

Зачем эта команда в примере: чтобы увидеть, что внутри контейнера нет ни одного чужого процесса — только сама ps. Именно это и означает «изоляция».

Вывод (внутри контейнера)

PID   USER     TIME  COMMAND
    1 root      0:00 ps aux
  • PID 1 — нумерация внутри контейнера своя: первый процесс всегда 1. На хосте этот же процесс имеет обычный номер (например, 48173) — увидим ниже.
  • USER root — от какого пользователя работает процесс (в alpine по умолчанию root).
  • TIME 0:00 — сколько процессорного времени потрачено.
  • COMMAND ps aux — сама команда. Больше строк нет: процессов хоста здесь не видно.

Теперь посмотрим на ту же картину с хоста — то есть из терминала на машине, где работает Docker (ваш ноутбук или сервер). Запустим контейнер, который «живёт» 300 секунд, и посмотрим, что видит хост:

Команды и их вывод на хосте

$ docker run -d --name demo alpine sleep 300
8c1f0a9b2c31d4e5…        # ← ID созданного контейнера

$ docker ps
CONTAINER ID   IMAGE    COMMAND       CREATED         STATUS         PORTS   NAMES
8c1f0a9b2c31   alpine   "sleep 300"   5 seconds ago   Up 5 seconds           demo

$ ps aux | grep 'sleep 300'
root   48173  0.0  0.0   1620   4 ?   Ss   12:00   0:00 sleep 300
  • docker run -d — -d (detached) значит «в фоне»: терминал сразу вернётся, а контейнер продолжит работать.
  • --name demo — имя контейнера, придумали сами; нужно, чтобы потом обращаться к нему по имени (docker stop demo), а не по ID.
  • sleep 300 — программа «спать 300 секунд». Контейнер живёт, пока живёт его процесс, поэтому он не завершится раньше.
  • docker ps — список контейнеров (не процессов) и их состояние: Up 5 seconds = работает 5 секунд.
  • ps aux | grep 'sleep 300' — обычная команда хоста: | передаёт вывод ps программе grep, которая оставляет только строки с этим текстом.
  • 48173 — на хосте тот же самый процесс виден как обычный процесс с обычным PID. Это и есть главная мысль главы: контейнер — не «коробка с ОС», а процесс на хосте.

Это главное, что нужно усвоить: контейнер — не «коробка с ОС». На хосте это обычный процесс (или несколько), которому ядро показало другую картину мира: свои процессы, свою сеть, свою файловую систему. Docker — это инструмент, который готовит такую картину и запускает процесс.

Namespaces: что именно изолируется

Namespace — механизм ядра «покажи этому процессу только часть мира». Docker использует несколько:

NamespaceЧто изолируетКак заметно в работе
pidНомера процессовВнутри свой PID 1; процессы хоста не видны
netСетевой стек: интерфейсы, IP-адреса, порты, маршруты У контейнера своя «сетевая карта» (eth0) и свой 127.0.0.1; порт 8080 внутри — не порт хоста (глава 8)
mntТочки монтирования и корень файловой системыВнутри / — это корень образа, а не корень хоста
utsHostname и доменhostname вернёт ID контейнера
ipcРазделяемая память и семафорыСервисы не «увидят» очереди друг друга без явной настройки
userПользователи и их IDМожно быть root внутри и обычным пользователем на хосте (userns-remap)
cgroupДерево контрольных группКонтейнер видит только свои лимиты

Проверим изоляцию тремя командами: процессы, сеть и ядро.

Процессы: ps aux

Команда и вывод

$ docker run --rm alpine ps aux
PID   USER     TIME  COMMAND
    1 root      0:00 ps aux

Один процесс, и он PID 1. Процессы хоста — ваш браузер, демон Docker, база — здесь не видны вообще.

Сеть: ip addr

Команда и вывод

$ docker run --rm alpine ip addr
1: lo: <LOOPBACK,UP,LOWER_UP> mtu 65536
    link/loopback 00:00:00:00:00:00
    inet 127.0.0.1/8 scope host lo
2: eth0@if7: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500
    link/ether 02:42:ac:11:00:02
    inet 172.17.0.2/16 brd 172.17.255.255 scope global eth0
  • lo (loopback) — «петля»: виртуальный интерфейс, который всегда указывает на саму машину. Адрес 127.0.0.1 означает «я сам», и localhost — его имя. В контейнере он свой: localhost внутри — это сам контейнер, а не ваш ноутбук (частая причина ошибки «Connection refused» — глава 8).
  • eth0 — «сетевая карта» контейнера: через неё он общается с другими контейнерами и с интернетом. eth0@if7 — парный интерфейс на стороне хоста (7 — внутренний номер пары).
  • inet 172.17.0.2/16 — IP-адрес, который контейнеру выдал Docker из своей подсети 172.17.0.0/16: первый контейнер обычно получает .2, следующий .3 и так далее. Если создать свою сеть (docker network create), подсеть будет другая — например, 172.18.0.0/16. В Kubernetes адреса выдаёт уже он.
  • mtu 1500 — максимальный размер пакета; brd — широковещательный адрес; scope global — адрес виден всей сети.

Ядро: uname -a

Одна и та же команда внутри контейнера и на хосте

$ docker run --rm alpine uname -a
Linux 8c1f0a9b2c31 6.8.0-45-generic #45-Ubuntu SMP PREEMPT_DYNAMIC x86_64 Linux

$ uname -a                        # на хосте
Linux my-laptop 6.8.0-45-generic #45-Ubuntu SMP PREEMPT_DYNAMIC x86_64 GNU/Linux

Отличается только имя машины (в контейнере — ID контейнера), а версия ядра 6.8.0-45-generic совпадает: своего ядра у контейнера нет, он использует ядро хоста. Поэтому из контейнера нельзя загрузить модуль ядра или поменять sysctl.

cgroups: сколько можно потратить

Namespaces отвечают на вопрос «что видно», cgroups — на вопрос «сколько разрешено». Контрольные группы считают и ограничивают CPU, память, ввод-вывод, число процессов. Запустим контейнер с лимитами и посмотрим, как они выглядят изнутри (образ my-api здесь условный — подставьте свой):

# docker run              создать и запустить контейнер
#   -d                    в фоне (detached), не занимать терминал
#   --name limited        имя контейнера — придумали сами («limited» = «ограниченный»,
#                         потому что задаём лимиты). Имя может быть любым, лишь бы уникальным:
#                         по нему потом обращаемся в exec/inspect
#   --memory 512m         лимит памяти 512 МБ (cgroup); 512m = 512 мебибайт
#   --cpus 1.5            лимит CPU: полтора ядра (cgroup, файл cpu.max)
#   my-api                имя образа
docker run -d --name limited --memory 512m --cpus 1.5 my-api

# docker exec limited ...  выполнить команду в УЖЕ работающем контейнере (новый процесс)
# cat                      вывести содержимое файла
# /sys/fs/cgroup/memory.max  файл cgroup v2: максимум памяти в байтах
#                            536870912 байт = 512 МБ — столько видит сам контейнер
docker exec limited cat /sys/fs/cgroup/memory.max

# /sys/fs/cgroup/cpu.max   два числа: квота и период в микросекундах
#                            150000 / 100000 = 1.5 ядра
docker exec limited cat /sys/fs/cgroup/cpu.max

# docker inspect            показать полную конфигурацию контейнера (JSON)
#   -f 'шаблон'             вывести только нужное поле (Go-шаблон)
#   .HostConfig.Memory      лимит памяти в байтах
#   .HostConfig.NanoCpus    лимит CPU в наноядрах: 1.5 → 1500000000
docker inspect -f '{{.HostConfig.Memory}} {{.HostConfig.NanoCpus}}' limited

Зачем это разработчику: лимиты — не только про «чужой шумный сосед». От них зависит поведение .NET: сколько памяти возьмёт GC, сколько куч создаст Server GC, сколько потоков захочет пул (глава 12). Если лимит не задан, рантайм считает, что ему доступна вся память хоста.

overlayfs: слои и copy-on-write

Файловая система контейнера собрана из слоёв образа (они только для чтения) и одного тонкого записываемого слоя сверху. Никакого копирования при запуске не происходит:

        ОБРАЗ (только чтение)                 КОНТЕЙНЕР
┌────────────────────────────────┐    ┌──────────────────────────────────┐
│ слой 3   ваш код (Api.dll)     │    │ слой 4  ЗАПИСЫВАЕМЫЙ (тонкий)    │ ← сюда пишет приложение
├────────────────────────────────┤    ├──────────────────────────────────┤
│ слой 2   aspnet runtime 8.0    │ ─► │ те же слои 1–3, БЕЗ копии        │
├────────────────────────────────┤    │ (только чтение)                  │
│ слой 1   debian-slim (база)    │    └──────────────────────────────────┘
└────────────────────────────────┘
                                       второй контейнер того же образа:
                                       те же слои 1–3 + свой слой 4
Приложение МЕНЯЕТ файл из слоя 3:
  1) файл копируется наверх — в слой 4   (copy-up)
  2) правка идёт в копии
  3) файл в образе остаётся прежним

Приложение УДАЛЯЕТ файл из слоя 3:
  1) в слое 4 появляется «whiteout»-метка
  2) файл не виден, но физически остаётся в образе
  • Чтение файла идёт из самого верхнего слоя, где он есть.
  • Изменение файла из нижнего слоя сначала копирует его наверх (copy-up) — файл в образе не меняется никогда.
  • Удаление файла из нижнего слоя — это «whiteout»-метка в верхнем; файл остаётся в образе, но не виден.
  • Удаление контейнера удаляет записываемый слой. Всё, что приложение успело записать в файлы, исчезает (глава 9).

Отсюда два практических следствия: образ можно использовать для любого числа контейнеров без копирования, а данные для хранения выносят в volume.

Кто кого запускает

От вашей команды до процесса — пять звеньев, и у каждого своя работа:

ЗвеноЧто делает
docker (CLI)Программа, которую вы вызываете в терминале. Сама контейнеры не создаёт — отправляет запрос и печатает ответ
dockerd (демон)Фоновый процесс Docker: принимает запросы, скачивает образы, создаёт контейнеры. Разговаривает с CLI по API — по HTTP через локальный сокет /var/run/docker.sock
containerdМенеджер контейнеров: ведёт их учёт, качает слои образов
containerd-shimПроцесс-«нянька»: остаётся жить, даже если демон перезапустили, и держит stdio контейнера
runcСоздаёт изоляцию (namespaces, cgroups) и запускает ваш процесс; после запуска уходит
docker (CLI) → dockerd → containerd → containerd-shim → runc → ваш процесс (PID 1)
   просит       решает     ведёт учёт      держит живым      создаёт     исполняется
   по API       что делать контейнеров                      изоляцию

Формат образа и формат запуска описаны стандартами OCI. Поэтому запускать OCI-образы умеет не только Docker:

  • Podman — почти полная замена команд Docker, но без демона: сама команда создаёт контейнер. Образы те же самые.
  • Kubernetes — «оркестратор»: система, которая запускает контейнеры на многих машинах, сама перезапускает упавшие, распределяет трафик и выкатывает новые версии. Обычно работает напрямую с containerd, без Docker. Подробно — глава 15; сейчас достаточно знать, что это следующий уровень над Docker, а не его замена.

Поэтому на вопрос интервью «обязателен ли Docker в Kubernetes» ответ: нет — обязателен OCI-образ, а чем именно его запускать, решает платформа.

Чем это не виртуальная машина

Виртуальная машинаКонтейнер
Ядросвоё, гость ОСобщее с хостом
Запускминуты (загрузка ОС)доли секунды (запуск процесса)
Размергигабайтыдесятки-сотни мегабайт
Изоляциясильнее: своё ядрослабее: общее ядро, namespaces
ОС внутрилюбаята же, что у хоста (Linux-образ на Linux)
Что можно менятьвсёнельзя менять ядро, sysctl, модули
Почему нельзя «поставить в контейнер вторую ОС»

Частая ошибка новичка — тянуть в образ systemd, sshd, cron: «как на сервере». В контейнере должен жить один процесс (и его дети). Второй сервис — второй контейнер. Иначе ломаются сигналы, логи и перезапуск: контейнер считается живым, пока живёт PID 1.

PID 1 и сигналы: задел на главу 13

docker stop посылает процессу SIGTERM, ждёт 10 секунд и добивает SIGKILL. Это два разных сигнала: SIGTERM — «завершись нормально», его можно перехватить и успеть дописать данные; SIGKILL — принудительное убийство, перехватить нельзя. Ядро относится к PID 1 особо: сигнал, для которого не установлен обработчик, по умолчанию не убивает процесс. Поэтому важно, кто у вас PID 1:

# exec-форма: PID 1 = dotnet, поэтому SIGTERM дойдёт до приложения
#   ENTRYPOINT        что запускать при старте контейнера
#   ["dotnet", "..."] JSON-массив: запуск без /bin/sh, лишнего процесса-посредника нет
#   Orders.Api.dll    сборка приложения (лежит в рабочей папке из WORKDIR)
ENTRYPOINT ["dotnet", "Orders.Api.dll"]

# shell-форма: строка без скобок → Docker выполняет /bin/sh -c "dotnet Orders.Api.dll"
#   PID 1 = /bin/sh, и SIGTERM часто не доходит до dotnet
#   зато раскрываются переменные: $ASPNETCORE_URLS подставится
ENTRYPOINT dotnet Orders.Api.dll

Именно из-за этого «контейнер не останавливается, приходится ждать 10 секунд и он умирает жёстко». Подробный разбор — в главе 13.

★ Что запомнить из главы
  • Контейнер — это процесс (PID 1) плюс namespaces (что видно) плюс cgroups (сколько можно) плюс слои (файловая система образа + записываемый слой).
  • Ядро общее с хостом: uname -a показывает ядро хоста, модули и sysctl менять нельзя.
  • Лимиты --memory/--cpus — это cgroups; .NET читает их и под них подстраивает GC (глава 12).
  • Записываемый слой умирает вместе с контейнером — данные выносят в volume (глава 9).
  • Живёт контейнер, пока живёт PID 1; форма ENTRYPOINT решает, дойдёт ли до приложения SIGTERM.
