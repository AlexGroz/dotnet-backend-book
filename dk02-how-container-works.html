Глава 2. Контейнер — это процесс: namespaces, cgroups, слои

Контейнер собран из трёх механизмов ядра Linux. Поняв их, вы перестаёте угадывать, почему команда «не работает», и можете объяснить это на интервью.

подводящая глава

Словарь, без которого дальше не прочитать

Пять слов будут встречаться в каждой главе — договоримся о них сразу.

СловоЧто это
Хост (host)Машина, на которой работает Docker: ваш ноутбук, сервер в облаке, виртуалка. Всё, что «с хоста», — это команды и файлы этой машины, а не контейнера
Демон (dockerd)Фоновый процесс Docker, который и делает всю работу: скачивает образы, создаёт контейнеры, выделяет им изоляцию. Сам он ничего не печатает — им управляют командами
CLI (docker)Программа в терминале. Она не создаёт контейнеры сама — она отправляет просьбу демону и печатает ответ
API«Язык», на котором CLI разговаривает с демоном: набор команд по HTTP через локальный сокет. Поэтому Docker-ом можно управлять и из кода, и из CI
Образ / контейнерОбраз — неизменяемый набор файлов и настроек. Контейнер — запущенный экземпляр образа со своим записываемым слоем (раздел про overlayfs ниже)
Как это выглядит в жизни

Вы пишете docker run nginx → CLI отправляет запрос демону → демон (если образа нет) скачивает его из реестра, создаёт контейнер, настраивает изоляцию и запускает процесс → CLI показывает вам ID контейнера. Когда вы позже пишете docker ps, CLI снова спрашивает демона «что запущено» и печатает ответ.

Как читать примеры в книге
  • $ — приглашение оболочки: строка с $ — команда, которую вы набираете; строки под ней без $ — то, что напечатала программа.
  • Блоки бывают двух видов. Транскрипт — команда и её вывод: команда помечена $, вывод — нет. Справочник — только команды с пояснениями: там $ часто опускают, и тогда ориентир такой: строка без # — команда, строка с # — пояснение к ней.
  • # — комментарий: в команду не входит, объясняет ключи и вывод.
  • … — пропущенные аргументы; <имя> — подставьте своё значение.
  • В блоках Dockerfile и в схемах $ нет никогда: это директивы файла или рисунок, а не команды оболочки. То же правило действует во всех книгах библиотеки. Чем docker run … отличается от RUN … внутри Dockerfile — глава 3.

Сначала — жизненный цикл: контейнер не исчезает после остановки

Это место, где новички теряются. Запуск контейнера — создание объекта, а не «выполнение команды». Сразу договоримся о словах, иначе дальше непонятно:

  • Объект (контейнер) — это запись о контейнере в Docker: имя, конфигурация, с которой его создали, его записываемый слой с файлами, его логи и код выхода. Эта запись существует сама по себе — независимо от того, работает внутри программа или уже нет.
  • Процесс — программа, которая работает внутри объекта. Она может завершиться, а объект при этом останется.
docker run …            создан объект и запущен процесс в нём   → процесс работает
процесс завершился      (сам, упал с ошибкой, или Ctrl+C)      → контейнер ОСТАНОВЛЕН, объект на месте
docker rm …             объект удалён                          → исчезли его файлы и метаданные

Три состояния на примере конкретных команд:

МоментПроцесс внутриОбъект (запись о контейнере)Что доступно
docker run …работаетсоздан docker logs -f, docker exec, docker stop
программа закончила: сама, с ошибкой, Ctrl+C или docker stop нетостался: состояние Exited (0) / (1) / (137), логи и файлы целыdocker logs, docker inspect, docker start, docker rm; в docker ps его уже нет, в docker ps -a — есть
docker rm …нетудалён: пропали логи, код выхода и записываемый слойничего; образ и его слои остались, новый docker run создаст новый объект
  • Остановленный контейнер — не мусор по определению. В нём остались docker logs (что писало приложение), код выхода (0 / 1 / 137) и файлы, которые процесс успел создать. Именно так разбирают падения: docker ps -a — полный список контейнеров, включая остановленные (подробно — глава 4).
  • Удаление — норма, а не авария. Образ остаётся на месте, поэтому удалённый контейнер ничего не ломает: следующий docker run создаст новый из того же образа. Данные, которые должны пережить удаление, держат в томе (глава 9).
Зачем удалять контейнеры и что делает --rm

Проблема, которую надо решить. Каждый docker run создаёт новый объект. Программа закончила работу — объект остался: он всё ещё занимает место (свой записываемый слой с файлами), и в списке docker ps -a появляется строка Exited (0). После сотни экспериментов там сотня строк, и уже непонятно, какая из них нужна. Поэтому остановленные контейнеры время от времени удаляют — это уборка, а не лечение аварии: образ и его слои остаются, следующий docker run создаст новый объект из того же образа.

Что такое --rm. Это ключ команды docker run со смыслом «когда программа внутри закончит работу — удали объект сам». Ничего дополнительно запускать не нужно: контейнер не появится в docker ps -a вовсе.

Когда --rm нужен — для одноразовых задач, результат которых вам не нужен после завершения: посмотреть, что внутри контейнера (список процессов печатает программа ps aux, разбор чуть ниже), выполнить одну команду, прогнать миграцию, проверить новый образ.

Когда --rm вреден — для сервисов (ваш API, база). Если контейнер упал, удалять его нельзя: именно в нём остались docker logs (что писало приложение) и код выхода (0 — успех, 1 — ошибка в программе, 137 — процесс убит по SIGKILL, часто из-за лимита памяти). Без них причину падения не узнать. Поэтому сервисы запускают без --rm, а чистят отдельно и осознанно: docker rm <имя> — один конкретный контейнер, docker container prune — сразу все остановленные (глава 4).

Коротко: посмотреть и забыть → --rm; сервис, падение которого надо разобрать → без --rm.

Один процесс, которому выдали своё окружение

Начнём с команды, которая выглядит непонятно, а делает простую вещь:

$ docker run --rm alpine ps aux

Разбираем каждую часть — и что она означает:

  • docker run — «создай контейнер из образа и запусти в нём программу».
  • --rm — когда программа закончит работу, удалить контейнер (зачем — в разделе выше).
  • alpine — имя образа: крошечный Linux (~5–8 МБ), поэтому его удобно запускать десятки раз подряд.
  • ps aux — программа внутри образа, а не команда Docker. ps = «process status»: печатает список процессов. Ключи: a — процессы всех пользователей, u — «пользовательский» формат (подробные столбцы: USER, PID, %CPU, %MEM, VSZ, RSS, TTY, STAT, START, TIME, COMMAND), x — включая процессы без терминала.
  • Почему в выводе ниже нет %CPU. Столбцы выбирает не Docker, а сама программа ps. В alpine стоит busybox — упрощённый набор утилит, и её ps aux печатает только четыре столбца: PID, USER, TIME, COMMAND. Полный формат с %CPU вы увидите у обычного ps хоста — вторая таблица ниже.

Зачем эта команда в примере: чтобы увидеть, что внутри контейнера нет ни одного чужого процесса — только сама ps. Именно это и означает «изоляция».

Почему в команде нет имени контейнера. Потому что контейнера ещё не существует — docker run его создаёт. Обязателен только образ (из чего создавать); имя Docker придумает сам, а --name нужен лишь для удобства — чтобы потом обращаться к готовому контейнеру по-человечески. Разделение простое:

КомандаЧто делаетЧто нужно указать
docker run <образ> …создаёт новый контейнер и запускает в нём программуобраз и программу; имя — по желанию, через --name
docker start <имя>запускает уже созданный контейнер (тот, что виден в docker ps -a)имя или ID — контейнер уже есть
docker stop <имя>останавливает процесс внутри имя или ID
docker rm <имя>удаляет объектимя или ID

Вывод (внутри контейнера)

PID   USER     TIME  COMMAND
    1 root      0:00 ps aux
  • PID 1 — нумерация внутри контейнера своя: первый процесс всегда 1. На хосте этот же процесс имеет обычный номер (например, 48173) — увидим ниже.
  • USER root — от какого пользователя работает процесс (в alpine по умолчанию root).
  • TIME 0:00 — сколько процессорного времени потрачено.
  • COMMAND ps aux — сама команда. Больше строк нет: процессов хоста здесь не видно.

Теперь посмотрим на ту же картину с хоста — из терминала машины, где работает Docker (ваш ноутбук или сервер). Сразу важное: все команды в книге вы набираете в терминале хоста — и docker run …, и ps aux. Терминал не решает, где выполнится программа; это решает сама команда:

  • docker run <образ> <программа> — всё после имени образа выполняется внутри контейнера (его запускает Docker).
  • строки без слова docker (ps aux, grep, uname) — обычные программы хоста, они видят процессы хоста, в том числе процесс контейнера.
  • $ в примерах — приглашение оболочки (prompt): строка с $ — команда, которую вы набираете; строки под ней без $ — вывод программы. Символ в команду не входит и ни на что не влияет. Полное правило записи примеров — во врезке «Как читать примеры» выше.

Команды в терминале хоста: что где выполняется

$ docker run -d --name demo alpine sleep 300
8c1f0a9b2c31d4e5…          # ← вывод Docker: ID созданного контейнера
#  └─ sleep 300 работает ВНУТРИ контейнера, в фоне

$ docker ps
CONTAINER ID   IMAGE    COMMAND       CREATED         STATUS         PORTS   NAMES
8c1f0a9b2c31   alpine   "sleep 300"   5 seconds ago   Up 5 seconds           demo
#  └─ CLI спрашивает демона «что запущено» и печатает ответ

$ ps aux | grep 'sleep 300'
root   48173  0.0  0.0   1620   4 ?   Ss   12:00   0:00 sleep 300
#  └─ ps и grep — программы ХОСТА: контейнер тут ни при чём,
#     просто среди процессов хоста нашёлся тот самый sleep
  • docker run -d — -d (detached) значит «в фоне»: терминал сразу вернётся, а контейнер продолжит работать.
  • --name demo — имя контейнера, придумали сами; нужно, чтобы потом обращаться к нему по имени (docker stop demo), а не по ID. Не путайте два имени в одной команде: alpine — имя образа («из чего создаём»), demo — имя созданного контейнера («что получилось»). Из одного образа alpine можно сделать сотню контейнеров с разными именами — это будут разные объекты с одинаковым содержимым. Если --name не указывать, Docker придумает имя сам (zen_hopper, bold_turing).
  • Скелет любой команды запуска: docker run [ключи] <образ> [программа и аргументы]. Поэтому docker run -d --name demo alpine sleep 300 читается так: «создай контейнер из образа alpine, назови его demo, работать оставь в фоне и выполни внутри sleep 300».
  • sleep 300 — программа «спать 300 секунд». Контейнер живёт, пока живёт его процесс, поэтому он не завершится раньше.
  • docker ps — список контейнеров (не процессов) и их состояние: Up 5 seconds = работает 5 секунд.
  • ps aux | grep 'sleep 300' — обычная команда хоста: | передаёт вывод ps программе grep, которая оставляет только строки с этим текстом.
  • 48173 — на хосте тот же самый процесс виден как обычный процесс с обычным PID. Это и есть главная мысль главы: контейнер — не «коробка с ОС», а процесс на хосте.

Столбцов в строке хоста больше, чем у busybox в контейнере: здесь %CPU и %MEM как раз есть. Разберём её по столбцам:

СтолбецЧто значит
rootпользователь, от которого работает процесс
48173PID на хосте; внутри контейнера тот же процесс был 1
0.0 (%CPU)сколько процентов процессора процесс занимает прямо сейчас (у sleep — ноль: он спит)
0.0 (%MEM)сколько процентов памяти хоста
1620 (VSZ) / 4 (RSS)виртуальный размер и сколько реально в памяти, в килобайтах
? (TTY)терминала нет — процесс запущен в фоне
Ss (STAT)состояние: S — спит, s — лидер сессии
12:00 (START)когда процесс запущен
0:00 (TIME)сколько процессорного времени потратил
sleep 300 (COMMAND)сама программа

Это главное, что нужно усвоить: контейнер — не «коробка с ОС». На хосте это обычный процесс (или несколько), которому ядро показало другую картину мира: свои процессы, свою сеть, свою файловую систему. Docker — это инструмент, который готовит такую картину и запускает процесс.

Namespaces: что именно изолируется

Namespace — механизм ядра «покажи этому процессу только часть мира». Docker использует несколько:

NamespaceЧто изолируетКак заметно в работе
pidНомера процессовВнутри свой PID 1; процессы хоста не видны
netСетевой стек: интерфейсы, IP-адреса, порты, маршруты У контейнера своя «сетевая карта» (eth0) и свой 127.0.0.1; порт 8080 внутри — не порт хоста (глава 8)
mntТочки монтирования и корень файловой системыВнутри / — это корень образа, а не корень хоста
utsHostname и доменhostname вернёт ID контейнера
ipcРазделяемая память и семафорыСервисы не «увидят» очереди друг друга без явной настройки
userПользователи и их IDМожно быть root внутри и обычным пользователем на хосте (userns-remap)
cgroupДерево контрольных группКонтейнер видит только свои лимиты

Проверим изоляцию тремя командами: процессы, сеть и ядро.

Процессы: ps aux

Команда и вывод

$ docker run --rm alpine ps aux
PID   USER     TIME  COMMAND
    1 root      0:00 ps aux

Один процесс, и он PID 1. Процессы хоста — ваш браузер, демон Docker, база — здесь не видны вообще.

Сеть: ip addr

Команда и вывод

$ docker run --rm alpine ip addr
1: lo: <LOOPBACK,UP,LOWER_UP> mtu 65536
    link/loopback 00:00:00:00:00:00
    inet 127.0.0.1/8 scope host lo
2: eth0@if7: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500
    link/ether 02:42:ac:11:00:02
    inet 172.17.0.2/16 brd 172.17.255.255 scope global eth0
  • lo (loopback) — «петля»: виртуальная сетевая карта, которая всегда ведёт на саму машину. Её адрес виден в третьей строке вывода — inet 127.0.0.1/8 (/8 — размер подсети, у loopback он всегда такой; scope host значит «только внутри этой машины»). localhost — не отдельный адрес, а имя, которое в файле /etc/hosts любого Linux привязано к 127.0.0.1: поэтому curl localhost:8080 и curl 127.0.0.1:8080 — одно и то же. В контейнере этот адрес свой: localhost внутри — сам контейнер, а не ваш ноутбук (частая причина ошибки «Connection refused» — глава 8).
  • eth0 — «сетевая карта» контейнера: через неё он общается с другими контейнерами и с интернетом. eth0@if7 — парный интерфейс на стороне хоста (7 — внутренний номер пары).
  • inet 172.17.0.2/16 — IP-адрес, который контейнеру выдал Docker из своей подсети 172.17.0.0/16: первый контейнер обычно получает .2, следующий .3 и так далее. Если создать свою сеть (docker network create), подсеть будет другая — например, 172.18.0.0/16. В Kubernetes адреса выдаёт уже он.
  • link/ether 02:42:ac:11:00:02 — MAC-адрес интерфейса. Docker не выдаёт его случайно: ac 11 00 02 — это тот же адрес 172.17.0.2, записанный шестнадцатеричными парами.
  • mtu 1500 — в строке 2: eth0@if7 … mtu 1500: максимальный размер пакета в байтах, который интерфейс передаёт за один раз.
  • brd 172.17.255.255 — широковещательный (broadcast) адрес подсети. Он стоит в строке inet 172.17.0.2/16 brd 172.17.255.255 scope global eth0 — сразу после адреса. Пакет, отправленный на этот адрес, получают все машины сети 172.17.0.0/16; 172.17.255.255 — её последний адрес.
  • scope global — адрес доступен всей сети (в отличие от scope host у loopback, который виден только внутри машины).

Ядро: uname -a

Одна и та же команда внутри контейнера и на хосте

$ docker run --rm alpine uname -a
Linux 8c1f0a9b2c31 6.8.0-45-generic #45-Ubuntu SMP PREEMPT_DYNAMIC x86_64 Linux

$ uname -a                        # на хосте
Linux my-laptop 6.8.0-45-generic #45-Ubuntu SMP PREEMPT_DYNAMIC x86_64 GNU/Linux

Отличается только имя машины (в контейнере — ID контейнера), а версия ядра 6.8.0-45-generic совпадает: своего ядра у контейнера нет, он использует ядро хоста. Поэтому из контейнера нельзя загрузить модуль ядра или поменять sysctl.

cgroups: сколько можно потратить

Namespaces отвечают на вопрос «что видно», cgroups — на вопрос «сколько разрешено». Контрольные группы считают и ограничивают CPU, память, ввод-вывод, число процессов.

Ниже три команды, и у них разные роли — не перепутайте: первая задаёт лимиты в момент создания контейнера (значения запоминаются в его конфигурации и применяются cgroup'ами), две следующие только читают — одна изнутри контейнера, другая снаружи. Образ my-api здесь условный — подставьте свой:

# ── 1. ЗАДАЁМ лимиты (в момент создания контейнера) ─────────────────────────
# docker run              создать и запустить контейнер
#   -d                    в фоне (detached), не занимать терминал
#   --name limited        имя контейнера — придумали сами («limited» = «ограниченный»,
#                         потому что задаём лимиты). Имя может быть любым, лишь бы уникальным:
#                         по нему потом обращаемся в exec/inspect
#   --memory 512m         лимит памяти 512 МБ (cgroup); 512m = 512 мебибайт
#   --cpus 1.5            лимит CPU: полтора ядра (cgroup, файл cpu.max)
#   my-api                имя образа
$ docker run -d --name limited --memory 512m --cpus 1.5 my-api

# ── 2. ЧИТАЕМ изнутри: как лимит видит сам контейнер ────────────────────────
# docker exec limited ...  выполнить команду в УЖЕ работающем контейнере (новый процесс)
# cat                      вывести содержимое файла
# /sys/fs/cgroup/memory.max  файл cgroup v2: максимум памяти в байтах
#                            536870912 байт = 512 МБ — столько видит сам контейнер
$ docker exec limited cat /sys/fs/cgroup/memory.max

# /sys/fs/cgroup/cpu.max   два числа: квота и период в микросекундах
#                            150000 / 100000 = 1.5 ядра
$ docker exec limited cat /sys/fs/cgroup/cpu.max

# ── 3. ЧИТАЕМ снаружи: что Docker запомнил в конфигурации ───────────────────
# docker inspect            показать полную конфигурацию контейнера (JSON)
#   -f 'шаблон'             вывести только нужное поле (Go-шаблон)
#   .HostConfig.Memory      лимит памяти в байтах
#   .HostConfig.NanoCpus    лимит CPU в наноядрах: 1.5 → 1500000000
$ docker inspect -f '{{.HostConfig.Memory}} {{.HostConfig.NanoCpus}}' limited

Правило простое: лимиты задаёт только создание контейнера (docker run --memory … --cpus …); docker inspect, docker stats и файлы /sys/fs/cgroup/… — читают. Уже созданному контейнеру лимиты можно поправить на живую: docker update --memory 1g --cpus 2 limited (глава 4).

Зачем это разработчику. Лимиты нужны не только для того, чтобы один контейнер не забрал себе всю память и весь процессор и не затормозил остальные контейнеры на том же сервере — по-английски такую ситуацию называют noisy neighbor, «шумный сосед»: сосед, который мешает всем вокруг. От лимитов зависит и поведение .NET: сколько памяти возьмёт GC, сколько куч создаст Server GC, сколько потоков захочет пул (глава 12). Если лимит не задан, рантайм считает, что ему доступна вся память хоста.

overlayfs: слои и copy-on-write

Файловая система контейнера собрана из слоёв образа (они только для чтения) и одного записываемого слоя сверху. «Тонкий» он потому, что содержит не копию всей файловой системы, а только то, что приложение дописало или изменило: сразу после запуска он практически пуст. Никакого копирования при запуске не происходит:

        ОБРАЗ (только чтение)                 КОНТЕЙНЕР
┌────────────────────────────────┐    ┌──────────────────────────────────┐
│ слой 3   ваш код (Api.dll)     │    │ слой 4  ЗАПИСЫВАЕМЫЙ (изменения) │ ← сюда пишет приложение
├────────────────────────────────┤    ├──────────────────────────────────┤
│ слой 2   aspnet runtime 8.0    │ ─► │ те же слои 1–3, БЕЗ копии        │
├────────────────────────────────┤    │ (только чтение)                  │
│ слой 1   debian-slim (база)    │    └──────────────────────────────────┘
└────────────────────────────────┘
                                       второй контейнер того же образа:
                                       те же слои 1–3 + свой слой 4
Приложение МЕНЯЕТ файл из слоя 3:
  1) файл копируется наверх — в слой 4   (copy-up)
  2) правка идёт в копии
  3) файл в образе остаётся прежним

Приложение УДАЛЯЕТ файл из слоя 3:
  1) в слое 4 появляется «whiteout»-метка
  2) файл не виден, но физически остаётся в образе
  • Чтение файла идёт из самого верхнего слоя, где он есть.
  • Изменение файла из нижнего слоя сначала копирует его наверх (copy-up) — файл в образе не меняется никогда.
  • Удаление файла из нижнего слоя — это «whiteout»-метка в верхнем; файл остаётся в образе, но не виден.
  • Слой 4 «тонкий» — в нём только добавленные и изменённые файлы, а не копия образа: если приложение записало при старте 20 МБ логов, слой весит около 20 МБ.
  • Удаление контейнера удаляет записываемый слой. Всё, что приложение успело записать в файлы, исчезает (глава 9).

Отсюда два практических следствия: образ можно использовать для любого числа контейнеров без копирования, а данные для хранения выносят в volume.

Кто кого запускает

От вашей команды до процесса — пять звеньев, и у каждого своя работа:

ЗвеноЧто делает
docker (CLI)Программа, которую вы вызываете в терминале. Сама контейнеры не создаёт — отправляет запрос и печатает ответ
dockerd (демон)Фоновый процесс Docker: принимает запросы, скачивает образы, создаёт контейнеры. Разговаривает с CLI по API — по HTTP через локальный сокет /var/run/docker.sock
containerdМенеджер контейнеров: ведёт их учёт, качает слои образов
containerd-shimПроцесс-«нянька»: остаётся жить, даже если демон перезапустили, и держит stdio контейнера
runcСоздаёт изоляцию (namespaces, cgroups) и запускает ваш процесс; после запуска уходит
docker (CLI) → dockerd → containerd → containerd-shim → runc → ваш процесс (PID 1)
   просит       решает     ведёт учёт      держит живым      создаёт     исполняется
   по API       что делать контейнеров                      изоляцию

Формат образа и формат запуска описаны стандартами OCI. Поэтому запускать OCI-образы умеет не только Docker:

  • Podman — почти полная замена команд Docker, но без демона: сама команда создаёт контейнер. Образы те же самые.
  • Kubernetes — «оркестратор»: система, которая запускает контейнеры на многих машинах, сама перезапускает упавшие, распределяет трафик и выкатывает новые версии. Обычно работает напрямую с containerd, без Docker. Подробно — глава 15; сейчас достаточно знать, что это следующий уровень над Docker, а не его замена.

Поэтому на вопрос интервью «обязателен ли Docker в Kubernetes» ответ: нет — обязателен OCI-образ, а чем именно его запускать, решает платформа.

Частая ошибка новичка — тянуть в образ systemd, sshd, cron: «как на сервере». В контейнере должен жить один процесс (и его дети). Второй сервис — второй контейнер. Иначе ломаются сигналы, логи и перезапуск: контейнер считается живым, пока живёт PID 1.

PID 1 и сигналы: задел на главу 13

docker stop посылает процессу SIGTERM, ждёт 10 секунд и добивает SIGKILL. Это два разных сигнала: SIGTERM — «завершись нормально», его можно перехватить и успеть дописать данные; SIGKILL — принудительное убийство, перехватить нельзя. Ядро относится к PID 1 особо: сигнал, для которого не установлен обработчик, по умолчанию не убивает процесс. Поэтому важно, кто у вас PID 1:

# exec-форма: PID 1 = dotnet, поэтому SIGTERM дойдёт до приложения
#   ENTRYPOINT        что запускать при старте контейнера
#   ["dotnet", "..."] JSON-массив: запуск без /bin/sh, лишнего процесса-посредника нет
#   Orders.Api.dll    сборка приложения (лежит в рабочей папке из WORKDIR)
ENTRYPOINT ["dotnet", "Orders.Api.dll"]

# shell-форма: строка без скобок → Docker сам оборачивает её в оболочку
#   /bin/sh        командная оболочка Linux (shell) — программа, которая запускает другие программы
#   -c "строка"    ключ оболочки: «выполни эту строку как команду» (c = command)
#   итого PID 1 = /bin/sh, а dotnet — его дочерний процесс: SIGTERM достаётся оболочке
#   и часто не доходит до приложения
#   плюс: строку разбирает оболочка, поэтому $ASPNETCORE_URLS подставится, работают | и &&
ENTRYPOINT dotnet Orders.Api.dll

# ИТОГ: во второй форме /bin/sh -c в файле НЕ написан — его дописывает сам Docker.
# Проверить, что получилось, можно так:
#   docker inspect -f '{{json .Config.Entrypoint}}' my-api
#     exec-форма  →  ["dotnet","Orders.Api.dll"]               ← оболочки нет
#     shell-форма →  ["/bin/sh","-c","dotnet Orders.Api.dll"]  ← Docker добавил её сам
Что такое /bin/sh -c

/bin/sh — стандартная командная оболочка (shell) Linux: программа, которая читает команды и запускает другие программы. Она есть в любом Linux-образе. Ключ -c у неё значит «выполни строку, которая идёт следом, как команду» (c = command). Поэтому запись /bin/sh -c "dotnet Orders.Api.dll" читается так: «запусти оболочку, а она пусть разберёт строку dotnet Orders.Api.dll и выполнит её».

Docker обращается к оболочке потому, что запустить можно только программу с аргументами, а не «строку»: именно оболочка раскрывает $ASPNETCORE_URLS и понимает | и &&. Плата — лишний процесс: PID 1 становится /bin/sh, приложение перестаёт быть главным процессом контейнера, и SIGTERM от docker stop часто до него не доходит (глава 13).

Где он в наших двух записях. В первой — ENTRYPOINT ["dotnet", "Orders.Api.dll"] — его нет и не будет: там массив, Docker запускает dotnet напрямую. Во второй — ENTRYPOINT dotnet Orders.Api.dll — вы его тоже не писали: Docker дописывает оболочку сам, превращая строку в ["/bin/sh", "-c", "dotnet Orders.Api.dll"]. То есть «в коде его не видно» и есть ответ: shell-форма тем и отличается от exec-формы, что оболочка появляется неявно.

Именно из-за этого «контейнер не останавливается, приходится ждать 10 секунд и он умирает жёстко». Подробный разбор — в главе 13.

★ Что запомнить из главы
  • Контейнер — это процесс (PID 1) плюс namespaces (что видно) плюс cgroups (сколько можно) плюс слои (файловая система образа + записываемый слой).
  • Остановка ≠ удаление: процесс умер, а объект остался — с логами, кодом выхода и файлами. Удаляет его docker rm или ключ --rm (для одноразовых запусков).
  • Ядро общее с хостом: uname -a показывает ядро хоста, модули и sysctl менять нельзя.
  • Лимиты --memory/--cpus — это cgroups; .NET читает их и под них подстраивает GC (глава 12).
  • Записываемый слой умирает вместе с контейнером — данные выносят в volume (глава 9).
  • Живёт контейнер, пока живёт PID 1; форма ENTRYPOINT решает, дойдёт ли до приложения SIGTERM.
