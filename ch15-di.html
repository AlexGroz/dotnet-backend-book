Глава 15. Внедрение зависимостей и жизненные циклы

Как собирать приложение из слабосвязанных частей и не сломать его жизненными циклами объектов.

DI-контейнер: как это выглядит в коде

DI-контейнер — это часть приложения, которая умеет создавать объекты за вас. Ему один раз сообщают: «если кто-то попросит IOrderRepository — создай OrderRepository». Дальше он сам смотрит, что нужно классу, создаёт эти зависимости и передаёт их в конструктор. Полное название идеи — IoC-контейнер (Inversion of Control, «инверсия управления»): управление созданием объектов передаётся из вашего кода в контейнер.

В .NET эту роль играет IServiceProvider из Generic Host (глава 16). Работает он в два шага: вы регистрируете сервисы, а контейнер сам собирает объекты и передаёт зависимости в конструкторы.

Что значит «контейнер сам собирает объекты»

Вы запрашиваете OrderService. Контейнер видит: «ему нужен IOrderRepository». Смотрит в свои регистрации: «IOrderRepository → OrderRepository» — и создаёт его. Но и репозиторию может что-то требоваться, например DbContext; контейнер идёт по цепочке, пока не соберёт всё дерево объектов — от самых «внутренних» к внешнему.

Без контейнера то же самое писали руками — new OrderService(new OrderRepository(new DbContext())) — и в каждом месте создания приходилось помнить порядок. С контейнером достаточно запросить OrderService.

Program.cs — регистрация. Делается ОДИН раз при старте приложения

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddScoped<IOrderRepository, OrderRepository>();  // просят интерфейс → создаём реализацию
builder.Services.AddScoped<OrderService>();                        // просят сам класс → его и создаём

var app = builder.Build();
app.Run();

Services/OrderService.cs — сам класс живёт в своём файле

public class OrderService(IOrderRepository repo)  // контейнер передаст сюда репозиторий
{
    public Task<Order> GetAsync(int id) => repo.GetAsync(id);
}
Какой метод выполнится на самом деле

Вот контракт и его реализация, о которых дальше идёт речь (в главе 14 контракт был синхронным — Find; здесь он асинхронный, как в реальном EF Core):

public interface IOrderRepository                     // что видит потребитель
{
    Task<Order?> GetAsync(int id);
}

public sealed class OrderRepository : IOrderRepository // что создаёт контейнер
{
    public string ConnectionString => "Host=db;Database=shop";   // есть только у реализации

    public Task<Order?> GetAsync(int id) => ...;                  // здесь был бы EF Core
}

Выполнится, конечно, OrderRepository.GetAsync — но вызван он через интерфейс. И это важно:

  • тип переменной repo — IOrderRepository, поэтому компилятор разрешает только то, что объявлено в интерфейсе;
  • объект внутри — OrderRepository, и вызывается именно его метод (обычный виртуальный вызов, как с override).
var repo = sp.GetRequiredService<IOrderRepository>();
Console.WriteLine(repo.GetType().Name);        // OrderRepository — настоящий тип объекта
Console.WriteLine(repo.ConnectionString);      // ❌ такого члена в интерфейсе нет

Вывод

OrderRepository

Хотя настоящий объект — OrderRepository, до его собственного свойства ConnectionString через интерфейс не добраться:

Ошибка компиляции

error CS1061: 'IOrderRepository' does not contain a definition for 'ConnectionString' and no accessible
extension method 'ConnectionString' accepting a first argument of type 'IOrderRepository' could be found

То есть сервис получает настоящую реализацию, но видит только контракт — и не может случайно завязаться на её детали. Ради этого интерфейс и стоит в конструкторе.

Где что находится (частая путаница)

Это не «одно действие в разных местах», а два разных шага:

  • Регистрация — в точке входа Program.cs, до builder.Build() (глава 16). Выполняется один раз при запуске.
  • Сами классы — в обычных файлах проекта. Они ничего не знают о контейнере: просто просят зависимости в конструкторе.

Дальше в примерах этой главы строки builder.Services… — это Program.cs, а объявления классов — отдельные файлы.

Где лежат интерфейс и реализация

Правило простое: интерфейс — рядом с тем, кто его просит (потребитель), а реализация — там, где живёт технология (EF Core, HTTP, файлы). В Utils не кладут ни то, ни другое: там утилиты без зависимостей.

ЧтоОдин проект (папки)Несколько проектов
Order и правилаDomain/Shop.Domain
IOrderRepository, OrderService Orders/ (или Services/)Shop.Application
OrderRepository на EF Core Infrastructure/ (она же Persistence/, Repositories/) Shop.Infrastructure
регистрации DIProgram.cs или Orders/OrdersModule.cs метод AddOrders() в Shop.Infrastructure

Раскладка «Services/ + Infrastructure/» — самая частая; имена папок дело вкуса. Важно направление ссылок: Application не должен знать про EF Core, иначе интерфейс ничего не изолирует. Держать интерфейс и реализацию в одной папке Repositories/ можно — но тогда потребитель видит и реализацию, и соблазн сослаться на неё напрямую велик.

Если зависимость не зарегистрирована — приложение падает на старте, а не «где-то потом». Это заставляет держать граф зависимостей в порядке.

Почему в регистрации два типа

Строка AddScoped<IOrderRepository, OrderRepository>() — это не описание класса, а правило для контейнера: «когда попросят IOrderRepository, создай OrderRepository». Два типа — это два разных вопроса:

  • первый тип (service) — то, что просят (обычно интерфейс, который стоит в конструкторах);
  • второй тип (implementation) — то, что создают.

Потребитель никогда не просит конкретный класс — он просит контракт:

public class OrderService(IOrderRepository repo)   // просит ИНТЕРФЕЙС
{
    public Task<Order> GetAsync(int id) => repo.GetAsync(id);
}

Значит, контейнер должен знать, что отдать на запрос IOrderRepository. Если зарегистрировать только реализацию —

builder.Services.AddScoped<OrderRepository>();   // класс зарегистрирован «сам как себя»
// запрос IOrderRepository → ошибка при попытке создать OrderService:
// InvalidOperationException: Unable to resolve service for type
// 'IOrderRepository' while attempting to activate 'OrderService'.

«Но ведь OrderRepository реализует IOrderRepository, это же очевидно» — контейнер так не рассуждает по двум причинам: у класса может быть несколько интерфейсов, а у интерфейса — несколько реализаций. В обоих случаях «очевидного» ответа нет, его задаёте вы — регистрацией.

Случай 1: один класс — несколько интерфейсов

public sealed class OrderService : IOrderService, IOrderValidator, IDisposable
{ … }

// регистрируем отдельно под каждый контракт, который будут просить
builder.Services.AddScoped<IOrderService, OrderService>();
builder.Services.AddScoped<IOrderValidator, OrderService>();   // ⚠ это ДВА разных экземпляра
builder.Services.AddScoped<IDisposable, OrderService>();
Если нужен один и тот же экземпляр под двумя интерфейсами

Обычная регистрация создаст два отдельных объекта. Чтобы отдать один, регистрируют класс и затем ссылаются на него из фабрик:

builder.Services.AddScoped<OrderService>();                     // сам класс
builder.Services.AddScoped<IOrderService>(sp => sp.GetRequiredService<OrderService>());
builder.Services.AddScoped<IOrderValidator>(sp => sp.GetRequiredService<OrderService>());

Случай 2: один интерфейс — несколько реализаций

Это ровно то, ради чего существует стратегия (книга «Паттерны», глава 3). Два способа развести реализации:

// IPricingStrategy, RegularPricing и VipPricing — стратегии из книги «Паттерны», глава 3
// а) ключи (.NET 8+): на запрос с ключом — конкретная реализация
builder.Services.AddKeyedScoped<IPricingStrategy, RegularPricing>(CustomerType.Regular);
builder.Services.AddKeyedScoped<IPricingStrategy, VipPricing>(CustomerType.Vip);

public sealed class OrderService([FromKeyedServices(CustomerType.Vip)] IPricingStrategy pricing) { … }
// или вручную: sp.GetRequiredKeyedService<IPricingStrategy>(CustomerType.Vip)

// б) без ключей: несколько регистраций одного интерфейса
builder.Services.AddScoped<IPricingStrategy, RegularPricing>();
builder.Services.AddScoped<IPricingStrategy, VipPricing>();

// запрос ОДНОГО даст ПОСЛЕДНЮЮ регистрацию:
var one = sp.GetRequiredService<IPricingStrategy>();        // VipPricing

// запрос набора даст ВСЕ, в порядке регистрации:
var all = sp.GetServices<IPricingStrategy>();               // [RegularPricing, VipPricing]

// а конкретную реализацию из набора достают фильтром по типу:
var regular = sp.GetServices<IPricingStrategy>().OfType<RegularPricing>().Single();   // RegularPricing

// либо регистрируют ещё и сам класс — тогда его можно просить напрямую:
builder.Services.AddScoped<RegularPricing>();
var regular2 = sp.GetRequiredService<RegularPricing>();     // RegularPricing

Что вернёт контейнер

одиночный запрос                     = VipPricing
все реализации                       = RegularPricing, VipPricing
OfType<RegularPricing>()             = RegularPricing
GetRequiredService<RegularPricing>() = RegularPricing
это ОДИН и тот же объект?            = False

Обратите внимание на последнюю строку: AddScoped<RegularPricing>() — это отдельная регистрация, поэтому «тот же» класс приходит двумя разными экземплярами. И ещё: GetServices с OfType создаёт все реализации, чтобы потом выбросить лишние, — а GetRequiredService<RegularPricing>() создаёт только один объект. Если выбор зависит от запроса (VIP-клиент или обычный), правильный инструмент — ключи, вариант «а»: там создаётся ровно та реализация, которую попросили.

Вариант «б» — это готовый механизм для цепочки обработчиков или цепочки проверок: получили все реализации и прошли по ним (книга «Паттерны», глава 6).

Случай 3: класс как сам себе сервис

Один тип в регистрации — это законная форма: «на запрос EfProductRepository создай его же». Нужна, когда интерфейса нет или когда класс требуется именно как класс (например, чтобы обернуть его декоратором — книга «Паттерны», глава 5).

builder.Services.AddScoped<EfProductRepository>();

// просят конкретный класс
var repo = sp.GetRequiredService<EfProductRepository>();

Случай 4: фабричный делегат — когда нужна логика создания

Участники примера (в жизни — отдельные файлы):

public interface IProductRepository { string Get(int id); }

public sealed class EfProductRepository : IProductRepository          // «настоящий» репозиторий
{
    public string Get(int id) => $"db:{id}";                          // здесь был бы EF Core
}

// декоратор: добавляет кэш вокруг любого IProductRepository
public sealed class CachedProductRepository(IProductRepository inner, IMemoryCache cache) : IProductRepository
{
    public string Get(int id)
    {
        var key = $"product:{id}";
        if (cache.TryGetValue(key, out string? cached))
            return $"cache:{cached}";

        var value = inner.Get(id);
        cache.Set(key, value, TimeSpan.FromMinutes(5));
        return value;
    }
}
// конструктор декоратора: CachedProductRepository(IProductRepository inner, IMemoryCache cache)

// форма 1: фабрика создаёт объект сама — передаём ВСЕ аргументы, иначе не скомпилируется
builder.Services.AddScoped<IProductRepository>(sp =>
    new CachedProductRepository(
        sp.GetRequiredService<EfProductRepository>(),      // кого оборачиваем
        sp.GetRequiredService<IMemoryCache>()));           // вторая зависимость

// форма 2: ActivatorUtilities — недостающее контейнер подставит сам
builder.Services.AddScoped<IProductRepository>(sp =>
    ActivatorUtilities.CreateInstance<CachedProductRepository>(
        sp,                                                 // 1) кто разрешает недостающие зависимости
        sp.GetRequiredService<EfProductRepository>()));     // 2) что передать руками
Что передавать руками, а что нет

Первый аргумент — это провайдер, а не зависимость: он и «разрешает» недостающее. Дальше идёт список аргументов конструктора, которые нужно подставить вручную; порядок между ними произвольный — ActivatorUtilities сопоставляет их по типу. Компилятор полноту списка не проверяет: всё, чего не хватило, ActivatorUtilities возьмёт из контейнера сам. Поэтому руками передают только то, что контейнер отдать не может. В декораторе это «оборачиваемый» — EfProductRepository: попроси контейнер о IProductRepository внутри декоратора, и он вернёт… сам декоратор, то есть бесконечную рекурсию.

А IMemoryCache писать не нужно: он зарегистрирован (AddMemoryCache()) и будет подставлен. Проверено на .NET 8 — оба варианта дают одинаковый результат:

1-й вызов: db:1
2-й вызов: cache:db:1

Если же зависимость не зарегистрирована, ActivatorUtilities честно об этом скажет:

Unable to resolve service for type 'Microsoft.Extensions.Caching.Memory.IMemoryCache' while attempting
to activate 'CachedProductRepository'.

Когда так делают: декораторы (книга «Паттерны», глава 5), выбор реализации по конфигурации, значения, которые нельзя получить из конструктора.

Параметр Func<IServiceProvider, T> — это делегат, то есть метод, переданный как значение. Что это такое и как с ним работать (лямбды, замыкания, Func/Action) — «C#: язык и типы», глава 16.

Случай 7: библиотеки и TryAdd

// Add — добавит новую регистрацию в любом случае;
// для одиночного запроса побеждает ПОСЛЕДНЯЯ.
builder.Services.AddSingleton<IClock, SystemClock>();

// TryAdd — добавит, только если для IClock ещё НИЧЕГО не зарегистрировано.
// Так делают библиотеки, чтобы не перезаписывать выбор приложения.
builder.Services.TryAddSingleton<IClock, SystemClock>();

Разница видна, если посмотреть не только на «кого вернули», но и на список регистраций:

Приложение — AppClock, библиотека — LibClock

static void Which(string scenario, Action<IServiceCollection> configure)
{
    var services = new ServiceCollection();
    configure(services);
    var sp = services.BuildServiceProvider();

    var all = sp.GetServices<IClock>().Select(x => x.GetType().Name).ToArray();
    Console.WriteLine($"{scenario,-48} -> {sp.GetRequiredService<IClock>().GetType().Name,-10} " +
                      $"регистраций: {all.Length} ({string.Join(", ", all)})");
}

Which("приложение Add(AppClock), потом библиотека TryAdd", s =>
{
    s.AddSingleton<IClock, AppClock>();
    s.TryAddSingleton<IClock, LibClock>();
});
Which("библиотека TryAdd(LibClock), потом приложение Add", s =>
{
    s.TryAddSingleton<IClock, LibClock>();
    s.AddSingleton<IClock, AppClock>();
});
Which("приложение Add(AppClock), потом библиотека Add", s =>
{
    s.AddSingleton<IClock, AppClock>();
    s.AddSingleton<IClock, LibClock>();
});
Which("только библиотека TryAdd(LibClock)", s =>
{
    s.TryAddSingleton<IClock, LibClock>();
});

Вывод

приложение Add(AppClock), потом библиотека TryAdd -> AppClock   регистраций: 1 (AppClock)
библиотека TryAdd(LibClock), потом приложение Add -> AppClock   регистраций: 2 (LibClock, AppClock)
приложение Add(AppClock), потом библиотека Add    -> LibClock   регистраций: 2 (AppClock, LibClock)
только библиотека TryAdd(LibClock)                -> LibClock   регистраций: 1 (LibClock)

Читается так:

  • TryAdd ничего не добавил (строка 1): регистрация приложения уже была, поэтому в списке остался один AppClock. Это и нужно библиотеке — «не мешать».
  • Регистрация библиотеки осталась в списке (строка 2): TryAdd её добавил (до него не было ничего), а Add приложения встал последним и выиграл одиночный запрос. Но GetServices<IClock>() вернёт обе — и LibClock, и AppClock.
  • Add перебивает (строка 3): библиотека добавила свою регистрацию последней и молча отменила выбор приложения. Именно этого TryAdd и позволяет избежать.
  • Приложение ничего не выбрало (строка 4): работает вариант библиотеки — приложение не падает с «Unable to resolve service».

Отсюда правило: библиотека — TryAdd, приложение — Add. Если нужно именно заменить чужую регистрацию, есть Replace и RemoveAll<IClock>() из Microsoft.Extensions.DependencyInjection.Extensions:

builder.Services.RemoveAll<IClock>();                  // убрать все прежние регистрации
builder.Services.AddSingleton<IClock, AppClock>();     // и добавить свою

builder.Services.Replace(ServiceDescriptor.Singleton<IClock, AppClock>());   // убрать и добавить одной строкой

Случай 8: один класс с разным временем жизни

Технически можно зарегистрировать один класс несколько раз — под разные интерфейсы и с разными lifetime. На практике это почти всегда ошибка: получаются разные экземпляры с разным временем жизни, и данные между ними не совпадают. Если нужен один объект — регистрируйте его один раз и ссылайтесь на него через фабрику (случай 1).

Почему дженерики, а не Type

  • Проверка на этапе компиляции: AddScoped<IFoo, Foo>() не скомпилируется, если Foo не реализует IFoo. С типами-аргументами такая ошибка всплыла бы только в рантайме.
  • Не нужно приводить типы и работать с Type вручную.
  • Динамика остаётся доступной: для случаев, когда типы известны только в рантайме, есть Add(ServiceDescriptor) и AddScoped(typeof(IFoo), typeof(Foo)).

Шпаргалка: что просят → что регистрировать

Что стоит в конструкторе потребителяКак регистрировать

OrderRepository (конкретный класс)AddScoped<OrderRepository>()
IPricingStrategy с ключомAddKeyedScoped<IPricingStrategy, VipPricing>(key)
IEnumerable<IPricingStrategy> (все реализации)несколько AddScoped<IPricingStrategy, X>()

Зачем вообще нужны интерфейсы в конструкторах — глава 14. Как выбирать время жизни и не ловить captive dependency — дальше в этой главе.

Жизненные циклы

builder.Services.AddScoped<IOrderRepository, OrderRepository>();

// AddDbContext по умолчанию регистрирует контекст как Scoped.
// То есть это значение по умолчанию — отдельно указывать его не нужно.
builder.Services.AddDbContext<AppDbContext>(o => o.UseNpgsql(cs));
★ Золотое правило

Долгоживущий сервис не должен зависеть от короткоживущего. Singleton не зависит от Scoped.

Captive Dependency

Нарушение правила: долгоживущий сервис «захватывает» короткоживущий. Самый частый случай — Singleton держит DbContext (а он Scoped).

Опасный пример

builder.Services.AddSingleton<ReportService>();                  // живёт всё приложение
builder.Services.AddDbContext<AppDbContext>(o => o.UseNpgsql(cs)); // по умолчанию Scoped

public sealed class ReportService(AppDbContext db) // Scoped попал в Singleton → captive
{
    public Task<Report> BuildAsync() => db.Reports.FirstAsync();
}

Чем плохо: контекст живёт вечно (растёт память, копятся отслеживаемые сущности), появляются ошибки конкурентности («A second operation started on this context…») и устаревшие данные.

Как правильно, если Singleton нужен доступ к БД

Не инжектить DbContext, а создавать scope на операцию:

public sealed class ReportService(IServiceScopeFactory scopeFactory)
{
    public async Task<Report> BuildAsync(CancellationToken ct)
    {
        using var scope = scopeFactory.CreateScope(); // свой scope
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
        return await db.Reports.AsNoTracking().FirstAsync(ct);
    }
}

Как отлавливать Captive Dependency

  1. Валидация графа на старте — главный способ: 
    builder.Host.UseDefaultServiceProvider(o =>
{
    o.ValidateScopes = true;    // ловит: Singleton → Scoped
    o.ValidateOnBuild = true;   // проверяет весь граф при старте
});

    ValidateScopes в момент создания Singleton увидит попытку получить Scoped и бросит понятную ошибку. ValidateOnBuild проверяет весь граф при старте — ловит и captive, и забытые регистрации.

  2. Тест-«сторож»: построить провайдер из реальных регистраций и попытаться получить каждый сервис внутри scope.
  3. Код-ревью: Singleton — только stateless; красные флаги — IServiceProvider или DbContext в Singleton.

Фоновые сервисы

BackgroundService — Singleton, поэтому scope нужно создавать на каждую итерацию:

using (var scope = scopeFactory.CreateScope())
{
    var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
    await db.CleanupAsync(ct);
}
