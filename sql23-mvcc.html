Глава 23. MVCC в PostgreSQL: версии строк и снимки

Как читатели и писатели не мешают друг другу

основная глава

Зачем вообще MVCC

Представьте, что читатель ждёт писателя. Если чтение блокирует запись, а запись блокирует чтение, то под нагрузкой база превращается в очередь: отчёты мешают заказам, а один долгий UPDATE тормозит всех. На высоконагруженном сервисе это неприемлемо.

MVCC (Multi-Version Concurrency Control, «управление конкурентным доступом с помощью версий») решает это так: читатель никогда не блокирует писателя, а писатель — читателя. Каждый видит свою версию данных:

  • читатель видит согласованный снимок (snapshot) — набор версий, актуальных на момент начала его запроса или транзакции;
  • писатель создаёт новую версию строки, не трогая ту, которую кто-то читает.
Следствие, которое надо помнить всегда

В PostgreSQL UPDATE не изменяет строку на месте: он создаёт новую версию, а старая остаётся в странице, пока её не уберёт VACUUM. Отсюда и VACUUM, и bloat, и HOT-апдейты (глава 25), и требование к fillfactor.

Версия строки: xmin, xmax, ctid

У каждой физической версии строки есть системные поля:

ПолеЧто означает
ctidФизический адрес версии: номер страницы и смещение внутри неё. Меняется при каждом UPDATE
xminID транзакции, которая создала эту версию
xmaxID транзакции, которая её удалила или обновила; 0 — версия актуальна
 
INSERT INTO orders (id, status) VALUES (1, 'new');

SELECT ctid, xmin, xmax, status FROM orders WHERE id = 1;
--  ctid  | xmin  | xmax | status
-- -------+-------+------+--------
--  (0,1) | 7401  |    0 | new          ← создана транзакцией 7401, никем не удалена

UPDATE orders SET status = 'paid' WHERE id = 1;

SELECT ctid, xmin, xmax, status FROM orders WHERE id = 1;
--  ctid  | xmin  | xmax | status
-- -------+-------+------+--------
--  (0,2) | 7402  |    0 | paid         ← НОВАЯ версия, созданная 7402

-- старая версия физически осталась: (0,1) с xmax = 7402
SELECT ctid, xmin, xmax, status
FROM orders;   -- обычный SELECT её уже не покажет: правило видимости
Почему «min» и «max» — и почему это не про математику

Имена исторические: поля так и называются в заголовке версии строки — t_xmin и t_xmax. Смысл — границы жизни версии:

ПолеСмыслАналогия
xminxid транзакции, которая создала версию«дата рождения» — нижняя граница
xmaxxid транзакции, которая её удалила или заменила; 0 — версия ещё жива«дата смерти» — верхняя граница

То есть версия «живёт» на отрезке от xmin до xmax. Это не минимум и максимум по таблице и не «самый маленький/большой номер транзакции» — просто имена полей. Рядом в заголовке лежат cmin/cmax — номера команд (операторов) внутри транзакции; они нужны для редких случаев вроде «изменение видно самому себе», и для понимания MVCC вторичны.

заголовок версии строки (heap tuple header):
┌──────────┬──────────┬─────────────────┐
│   xmin   │   xmax   │  данные строки  │
│   7401   │    0     │ status = 'new'  │
└──────────┴──────────┴─────────────────┘
  создана      не удалена
  транзакцией 7401

после UPDATE транзакцией 7402:

  старая версия:  xmin=7401  xmax=7402   ← «умерла» в 7402, но физически ещё лежит
  новая версия:   xmin=7402  xmax=0      ← живёт с 7402

номера транзакций растут со временем:
  7400         7401                7402
                │                    │
                INSERT               UPDATE (и COMMIT)

Важная тонкость: те же имена xmin/xmax есть и у снимка, но там смысл другой — и вот там это действительно границы:

  • xmin снимка — самый старый ещё активный xid (нижняя граница);
  • xmax снимка — первый ещё не выданный xid (верхняя граница).

Поэтому «xmin — кто создал» относится к строке, а «xmin — самый старый активный» — к снимку: два разных объекта с одинаковыми именами полей.

Отсюда три правила, которые объясняют всё остальное:

  • UPDATE = новая версия (xmin = моя транзакция) + у старой проставляется xmax = моя транзакция;
  • DELETE = у версии проставляется xmax, сама строка остаётся на диске;
  • ROLLBACK не удаляет созданную версию — она просто остаётся «невидимой» как прерванная, и её тоже уберёт VACUUM.

Снимок: что именно «видит» транзакция

Снимок (snapshot) — это описание того, какие транзакции уже завершены, а какие ещё «в полёте». Он состоит из трёх вещей:

  • xmin снимка — самый старый номер транзакции, который ещё активен;
  • xmax снимка — граница «будущего»: транзакции с большим номером начались после снимка;
  • список активных — те, что начались, но не завершились.
BEGIN;
SELECT txid_current_snapshot();
-- 7405:7412:7406,7409
--  ^     ^     ^
--  |     |     активные транзакции
--  |     следующая «будущая»
--  все транзакции с номером меньше 7405 уже завершены

-- в PostgreSQL 13+ удобнее смотреть свой xid:
SELECT pg_current_xact_id();

Правило видимости (упрощённо): версия строки видна этой транзакции, если

  1. xmin версии — «свой» или завершённый (зафиксированный) и не входит в список активных снимка, и
  2. xmax версии — пустой (0), либо прерванный, либо «невидимый» снимку.

Из этого правила следуют два вывода, важных на практике:

  • Читатель со «старым» снимком продолжает видеть старые версии — даже если писатель уже закоммитил новые. Именно поэтому чтение не блокирует запись.
  • Пока снимок жив, мёртвые версии убрать нельзя: они ещё кому-то видны. Поэтому долгая транзакция мешает VACUUM и раздувает таблицу (глава 25).

Уровни изоляции: разница именно в снимках

Уровень изоляции в PostgreSQL — это, по сути, ответ на вопрос «когда берётся снимок».

УровеньКогда берётся снимокЧто возможноЧто невозможно
Read Uncommitted—Работает как Read CommittedГрязного чтения в PostgreSQL нет никогда

Repeatable Read в PostgreSQL «сильнее» стандарта

В стандарте SQL Repeatable Read допускает фантомы, но в PostgreSQL этот уровень реализован как snapshot isolation: один снимок на транзакцию, поэтому фантомов тоже нет. А вместо «тихого» потерянного обновления вы получите ошибку could not serialize access due to concurrent update (код 40001) — и транзакцию нужно повторить.

Две сессии: увидеть разницу своими глазами

Один и тот же сценарий при двух уровнях изоляции. Сессия A читает баланс, сессия B его меняет и коммитит, затем A читает снова.

Read Committed: снимок берётся на каждый оператор

-- Сессия A                                  -- Сессия B
BEGIN;
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;

SELECT balance FROM accounts WHERE id = 1;      -- 100

                                              UPDATE accounts SET balance = 50 WHERE id = 1;
                                              COMMIT;

SELECT balance FROM accounts WHERE id = 1;      -- 50   ← новый снимок
COMMIT;

Repeatable Read: снимок один на всю транзакцию

-- Сессия A                                  -- Сессия B
BEGIN;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;

SELECT balance FROM accounts WHERE id = 1;      -- 100

                                              UPDATE accounts SET balance = 50 WHERE id = 1;
                                              COMMIT;

SELECT balance FROM accounts WHERE id = 1;      -- 100  ← тот же снимок
COMMIT;

Это и есть «неповторяющееся чтение»: при Read Committed два одинаковых запроса в одной транзакции дают разные ответы. Отчёт, который делает несколько таких запросов, увидит «рваную» картину.

Какие аномалии ловит какой уровень

АномалияRead CommittedRepeatable ReadSerializable
Грязное чтение (видно незакоммиченное)нетнетнет
Неповторяющееся чтениеданетнет
Фантомное чтение (появились новые строки)данетнет

-- Сессия A: SELECT balance FROM accounts WHERE id = 1;   → 100
-- Сессия B: UPDATE ... SET balance = 50; COMMIT;
-- Сессия A: UPDATE accounts SET balance = 40 WHERE id = 1;  ← записал «своё», 50 потеряно

-- Тот же код при Repeatable Read:
-- UPDATE accounts SET balance = 40 WHERE id = 1;
-- ERROR: could not serialize access due to concurrent update  (SQLSTATE 40001)
Что это значит для кода

Повышение уровня изоляции не убирает конфликт — оно превращает «тихую порчу данных» в ошибку. Значит, транзакцию нужно повторять: код с 40001 обязан иметь retry (глава 24), иначе под нагрузкой вы получите поток ошибок вместо корректных данных.

Повтор транзакции — часть работы с MVCC

Если уровень изоляции Repeatable Read или Serializable «поймал» конфликт, PostgreSQL откатывает транзакцию с кодом 40001. Это не ошибка программиста, а сигнал «повтори». На C# это выглядит так:

public async Task WithdrawAsync(Guid id, decimal amount, CancellationToken ct)
{
    for (var attempt = 1; ; attempt++)
    {
        try
        {
            await using var tx = await db.Database.BeginTransactionAsync(
                IsolationLevel.RepeatableRead, ct);

            var account = await db.Accounts.FirstAsync(a => a.Id == id, ct);
            account.Withdraw(amount);                 // бизнес-правило: баланс не может быть отрицательным
            await db.SaveChangesAsync(ct);
            await tx.CommitAsync(ct);
            return;
        }
        catch (DbUpdateException ex) when (IsSerializationFailure(ex) && attempt < 3)
        {
            db.ChangeTracker.Clear();                 // контекст после ошибки нужно «очистить»
            await Task.Delay(TimeSpan.FromMilliseconds(50 * attempt), ct);   // backoff
        }
    }
}

private static bool IsSerializationFailure(DbUpdateException ex) =>
    ex.InnerException is PostgresException { SqlState: PostgresErrorCodes.SerializationFailure };

Правила, без которых retry бессмысленен: транзакция должна быть целиком повторяемой (никаких внешних вызовов внутри), а контекст после ошибки — очищен, иначе EF Core попытается сохранить «грязное» состояние.

Цена MVCC: горизонт и мёртвые версии

Версии, которые больше никому не видны, — это мусор. Его убирает VACUUM, но у него есть ограничение: пока снимок хоть одной транзакции может видеть версию, удалить её нельзя. Самый старый такой снимок называют горизонтом.

-- кто сейчас держит горизонт (и как долго)
SELECT pid,
       state,
       backend_xmin,
       age(backend_xmin)             AS xmin_age,
       now() - xact_start            AS xact_age,
       left(query, 40)               AS last_query
FROM pg_stat_activity
WHERE backend_xmin IS NOT NULL
ORDER BY age(backend_xmin) DESC
LIMIT 10;
  • Долгая транзакция (или idle in transaction) держит горизонт — и таблица растёт, хотя никто не мешает ей работать.
  • Открытый слот репликации — та же история: он тоже держит версии.
  • Следствие: n_dead_tup растёт, autovacuum не справляется, появляется bloat и деградация (глава 25).
  • Проверка «а не я ли виноват»: посмотрите на самое старое now() - xact_start в pg_stat_activity — если там минуты, проблема в приложении, а не в базе.
Простое правило для сервиса

Транзакция должна жить миллисекунды. Всё, что требует сети (HTTP, брокер, внешний API), выносится до или после транзакции — иначе вы одновременно держите соединение, блокировки и горизонт (глава 4 конспектов и глава 23 .NET-раздела).

Три частые ошибки
  • Ставить Serializable «для надёжности». Получите поток 40001 без выигрыша в корректности; уровень повышают под конкретную операцию.
  • Держать транзакцию во время HTTP-вызова. Горизонт и блокировки живут всё время сетевого ожидания.
  • Игнорировать 40001. Без retry под нагрузкой это выглядит как «случайные» отказы заказов.
★ Что запомнить из главы
  • MVCC: читатель видит снимок и не блокирует писателя; писатель создаёт новую версию строки.
  • UPDATE = новая версия: xmin — кто создал, xmax — кто удалил/обновил, ctid — где физически лежит.
  • Уровень изоляции определяет, когда берётся снимок: на оператор (RC) или на транзакцию (RR, Serializable).
  • Read Committed — по умолчанию; Repeatable Read в PostgreSQL — это snapshot isolation; Serializable ловит аномалии сериализации.
  • Конфликт при высоком уровне изоляции — это ошибка 40001, и её нужно повторять.
  • Цена MVCC — мёртвые версии: VACUUM не может их убрать, пока их «видит» чей-то снимок → горизонт, bloat (глава 25).
