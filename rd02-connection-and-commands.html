Глава 2. Подключение из .NET: ConnectionMultiplexer и первые команды

Одно соединение на процесс, TTL, атомарные операции и что означают ошибки подключения

основная глава

ConnectionMultiplexer: одно соединение на процесс

Клиент StackExchange.Redis устроен вокруг ConnectionMultiplexer: это одно физическое соединение с Redis, которое мультиплексирует все запросы приложения — параллельные команды уходят в один сокет, ответы разбираются по порядку и раскладываются по ожидающим задачам. Отсюда правила:

  • Один мультиплексор на процесс. Создавать его на каждый запрос — значит открывать соединение на каждый запрос: это дороже, чем сама команда.
  • Он потокобезопасен. IDatabase, полученный из мультиплексора, можно использовать из разных потоков.
  • Он сам переподключается. Пока соединение восстанавливается, команды либо ждут, либо падают по таймауту — в зависимости от настроек (ниже).
// Program.cs — регистрация в DI: один экземпляр на всё приложение
// "Redis" — имя строки подключения из appsettings.json (ConnectionStrings:Redis)
var cs = builder.Configuration.GetConnectionString("Redis") ?? "localhost:6379";
//                                                           ↑ запасной вариант, если в конфиге пусто

// AddSingleton — создать ОДИН раз на процесс; параметр «_» — IServiceProvider,
// который фабрике здесь не нужен
builder.Services.AddSingleton<IConnectionMultiplexer>(_ =>
    ConnectionMultiplexer.Connect(cs));   // Connect — синхронный, соединение при старте
                                          // (есть и ConnectAsync — ниже в примере)

// в сервисе — только IDatabase, никаких новых соединений
public sealed class CatalogCache(IConnectionMultiplexer mux)   // мультиплексор из DI
{
    // GetDatabase() не открывает соединение: это «вид» на базу №0 внутри того же сокета
    private readonly IDatabase _db = mux.GetDatabase();
}

Строка подключения — не только адрес: в ней задают пароль, номер базы, таймауты и поведение при недоступном сервере, например redis:6379,password=…,connectTimeout=1000,abortConnect=false. Разбор abortConnect — ниже, потому что это самая частая причина «странных» падений на старте.

Первые команды: SET, GET, TTL, INCR, SET NX

Ниже — программа и её реальный вывод (Redis 7.4.12, клиент StackExchange.Redis 2.8.58). Она проверяет всё, на чём держится дальнейшее: время жизни ключа, атомарный счётчик и «поставить, только если нет».

// ConnectAsync — подключиться к серверу; "localhost:6379" = «хост:порт»
// (в Docker порт проброшен из контейнера, глава 1)
var mux = await ConnectionMultiplexer.ConnectAsync("localhost:6379");

var db  = mux.GetDatabase();                 // база №0 — через неё идут команды данных
var srv = mux.GetServer("localhost:6379");   // «сервер»: версия, INFO, SCAN

// PING — проверка связи; возвращает время ответа (TimeSpan), а не строку «PONG»
Console.WriteLine($"ping:       {await db.PingAsync()}");

// srv.Version — версия из INFO server, это свойство, а не отдельная команда на каждый вызов
Console.WriteLine($"server:     {srv.Version}");

// SET user:1:name "Алексей" EX 2 — значение вместе с TTL 2 секунды
await db.StringSetAsync("user:1:name", "Алексей", TimeSpan.FromSeconds(2));

// GET user:1:name — значение по ключу
Console.WriteLine($"get:        {await db.StringGetAsync("user:1:name")}");

// TTL user:1:name — сколько осталось жить; пусто (null) значит «TTL не задан»
Console.WriteLine($"ttl:        {await db.KeyTimeToLiveAsync("user:1:name")}");

// подождали больше TTL — ключ должен исчезнуть сам, без наших команд
await Task.Delay(2200);

// EXISTS user:1:name → False, GET → пусто (RedisValue без значения)
Console.WriteLine($"after 2.2s: exists={await db.KeyExistsAsync("user:1:name")} " +
                  $"get=[{await db.StringGetAsync("user:1:name")}]");

// атомарный счётчик
// "hits" — имя ключа, придуманное в этом примере; предопределённых ключей в Redis нет
await db.KeyDeleteAsync("hits");              // DEL hits — «начать с нуля»; False, если ключа не было
await db.StringIncrementAsync("hits");        // INCR hits: ключа не было → создан с 0, стало 1
await db.StringIncrementAsync("hits", 5);     // INCRBY hits 5 → 6
Console.WriteLine($"incr:       {await db.StringGetAsync("hits")}");   // GET hits

// «поставить, только если ключа нет» + TTL — основа локов и лимитов:
//   "lock:job" — имя лока, "w1"/"w2" — значения-«владельцы» (кто его взял),
//   When.NotExists = NX, TimeSpan = EX 10: лок истечёт сам, если процесс умрёт
var nx1 = await db.StringSetAsync("lock:job", "w1", TimeSpan.FromSeconds(10), When.NotExists);
var nx2 = await db.StringSetAsync("lock:job", "w2", TimeSpan.FromSeconds(10), When.NotExists);
// первый SET … NX вернул True (лок взят), второй — False (уже занято)
Console.WriteLine($"set nx:     first={nx1} second={nx2}");
ping:       00:00:00.0009830
server:     7.4.12
get:        Алексей
ttl:        00:00:01.9910000
after 2.2s: exists=False get=[]
incr:       6
set nx:     first=True second=False

Что здесь важно:

  • PingAsync возвращает TimeSpan, а не строку: это время round-trip, около 1 мс на локальном сервере.
  • TTL уже меньше двух секунд (00:00:01.99…): время жизни отсчитывается с момента записи на сервере, а не с момента вашего вызова.
  • Пропавший ключ — не ошибка. После истечения StringGetAsync возвращает «пустое» значение (get=[]), а KeyExistsAsync — false. В коде это проверяют через .HasValue, а не сравнением с null.
  • StringIncrementAsync — атомарная операция на сервере: второй воркер не «потеряет» обновление, потому что команда выполняется целиком.
  • hits — это имя ключа, которое придумали мы сами. Никакого «счётчика по умолчанию» в Redis нет: пространство ключей плоское и пустое, ключ появляется в момент первой записи (SET, INCR, HSET…) и исчезает после DEL или истечения TTL. Поэтому hits ничем не отличается от user:1:name — это просто строка-имя, выбранная для примера.
  • KeyDeleteAsync перед счётчиком — чтобы пример начинался с нуля. INCR не сбрасывает значение, а продолжает: если запустить программу второй раз без удаления, получится 7, а не 1. Возвращает метод bool: False, если ключа не было, — это не ошибка, повторное удаление безопасно.
  • INCR на отсутствующем ключе создаёт его со значением 0 и возвращает 1. Тип после этого — строка (KeyTypeAsync → String), TTL нет (KeyTimeToLiveAsync → null).
  • When.NotExists — это SET … NX: первый вызов вернул True, второй — False. На этом строится и распределённый лок (глава 4), и защита от параллельного прогрева кэша.
Почему ключ назван user:1:name — и можно ли назвать иначе

Это не стандарт и не требование Redis. Ключ — произвольная бинарная строка (документация допускает до 512 МБ), сравнение побайтовое: ни таблиц, ни колонок, ни схемы нет. Двоеточия Redis не разбирает — для него user:1:name такая же строка, как hits. Проверено на живом сервере:

set 'ключ с пробелом и : двоеточием' 'значение'   → OK
get 'ключ с пробелом и : двоеточием'               → значение

Двоеточие — соглашение (convention), принятое в документации Redis и в библиотеках: объект:идентификатор:поле. Читается как «поле name объекта user с идентификатором 1» — ближайший аналог ячейки «строка/колонка» в СУБД. Практическая польза в трёх вещах: по имени видно, чей это ключ; можно выбрать все ключи одного объекта маской; при удалении пользователя понятно, что инвалидировать.

mset user:1:name Алексей user:1:email a@b.c user:2:name Мария   → OK
scan 0 match 'user:1:*' count 100
# 0                     ← курсор 0 = обход закончен
# user:1:email
# user:1:name           ← только ключи первого пользователя; user:2:name не попал

Правила, которых стоит держаться — это дисциплина вашего проекта, Redis их не проверяет:

  • один разделитель и один порядок частей во всём проекте: сущность:id:поле;
  • префикс сервиса, если Redis общий (catalog:v2:42): видно владельца и версию формата;
  • если id сам содержит : (составной ключ) — экранируйте часть (Uri.EscapeDataString) или берите другой разделитель, иначе разбор «поплывёт»;
  • ключ — не обязательно «одно значение»: user:1 как хеш вместо трёх отдельных ключей даёт одну команду и один TTL на объект (глава 3).

Поэтому user:1:name, lock:job, hits в книге — просто строки, выбранные для примера: любая другая запись работала бы так же. Подробнее про префиксы и перебор — раздел «Ключи: префиксы и перебор» ниже.

Что происходит с hits на пустом сервере (реальный вывод) 
del (ключа нет): False     ← KeyDeleteAsync: удалять нечего, и это не ошибка
exists:          False     ← ключа действительно нет: по умолчанию не заведено ничего
incr:            1         ← INCR создал ключ: 0 + 1
incr +5:         6
get:             6  type=String ttl=   ← тип string, TTL не задан (null)
incr (повтор):   7         ← без KeyDelete счётчик продолжил бы с прошлого значения
del (ключ есть): True      ← а теперь удалять было что
exists:          False

В приложении такие имена не пишут руками: ключ собирают из префикса и идентификатора ($"user:{id}:hits") или держат строки-константы в одном месте — чтобы по имени было видно, чей это ключ (раздел про префиксы ниже).

Что означают ошибки подключения

Поведение при недоступном сервере зависит от одного флага в строке подключения, и разница принципиальная. Проверено на закрытом порту:

-- abortConnect по умолчанию (true) --
connect -> RedisConnectionException: It was not possible to connect to the redis server(s).
Error connecting right now. To allow this multiplexer to continue retrying until it's able to
connect, use abortConnect=false in your connection string or AbortOnConnectFail=false; in your code.

-- abortConnect=false --
connect: ok (мультиплексор создан)
ping -> RedisConnectionException: The message timed out in the backlog attempting to send because
no connection became available (5000ms) - Last Connection Exception: UnableToConnect on
localhost:6399/Interactive, …
  • По умолчанию ConnectAsync падает, если сервер недоступен. Для приложения, которое должно пережить перезапуск Redis, это означает падение на старте.
  • abortConnect=false не «подключает любой ценой», а разрешает создать мультиплексор, который продолжит пытаться в фоне. Обратная сторона — Connect «успешен» даже когда сервера нет, а первая же команда падает по таймауту (в примере — через 5000 мс).
  • Практический вывод: в приложении ставят abortConnect=false и короткий connectTimeout, а здоровье Redis проверяют отдельно (health check), чтобы не узнавать о проблеме из таймаутов пользовательских запросов.

Ключи: префиксы и перебор

Ключи в Redis — плоское пространство имён, поэтому префикс (shop:, user:42:) несёт смысл: по нему видно, чей это ключ, и по нему же потом делают инвалидацию. Перебирать ключи командой KEYS нельзя: она просматривает всё и блокирует сервер. Для перебора используют SCAN — он идёт порциями, через курсор:

// mux, db и srv — из примера выше: тот же процесс, одно соединение.
// srv — это IServer, «серверная» часть клиента (результат mux.GetServer("localhost:6379")):
//   у IDatabase команды уровня базы (GET/SET/HGET/…), у IServer — уровня сервера:
//   SCAN, INFO, CONFIG, версия. Перебора ключей в IDatabase нет вообще.

await db.StringSetAsync("user:1:name", "Алексей", TimeSpan.FromSeconds(2));   // SET … EX 2
await db.StringSetAsync("user:2:name", "Борис");                             // SET без TTL

var keys = new List<string>();
// KeysAsync(pattern:, pageSize:) — это SCAN: сервер отдаёт очередную порцию
// (до pageSize ключей) и новый курсор, клиент повторяет запрос, пока курсор
// не станет 0. Поэтому сервер не блокируется на всё время перебора.
await foreach (var k in srv.KeysAsync(pattern: "user:*", pageSize: 100))
    keys.Add(k.ToString());                  // RedisKey → string для вывода

// порядок SCAN не определён — сортируем, чтобы вывод был стабильным
Console.WriteLine($"scan:       {string.Join(",", keys.OrderBy(k => k))}");
// scan:       user:1:name,user:2:name

await Task.Delay(2200);            // у первого ключа истёк TTL (2 с)
keys.Clear();
await foreach (var k in srv.KeysAsync(pattern: "user:*"))
    keys.Add(k.ToString());
Console.WriteLine($"after 2.2s: {string.Join(",", keys.OrderBy(k => k))}");
// after 2.2s: user:2:name
  • Почему srv — отдельный объект. Перебор ключей — операция сервера, а не базы: баз в Redis по умолчанию 16 (CONFIG GET databases → 16). Поэтому в API это IServer, а не IDatabase: GetDatabase() такой возможности не даёт.
  • KeysAsync — это SCAN, а не KEYS. Название сбивает: команды KEYS здесь нет, поэтому нет и её блокировки — pageSize как раз задаёт размер порции.
  • Гарантии SCAN слабые, и это нужно помнить: порядок не определён, ключ может прийти дважды, добавленные во время обхода ключи можно не увидеть, удалённые — увидеть. Для инвалидации и админки этого достаточно; для «точного списка» — нет.
  • pattern фильтрует на сервере, но обход всё равно идёт по всей базе: SCAN просматривает словарь ключей целиком, просто отдаёт только совпавшие. Поэтому перебор — редкая операция (CLI, фоновая уборка), а не запрос пользователя.
  • То же в redis-cli: redis-cli --scan --pattern 'user:*' (проверено: user:2:name). redis-cli keys 'user:*' вернёт то же самое, но заблокирует сервер — в проде нельзя.

Значения: что именно кладут в Redis

По проводу ходят байты. RedisValue неявно превращается в строку, число и byte[], но ваш объект он не сериализует: это делает приложение. Практические правила:

  • JSON через System.Text.Json — если значение читают люди и другие сервисы; JsonSerializer.SerializeToUtf8Bytes сразу даёт байты без промежуточной строки.
  • Никаких «бинарных сериализаторов» вроде BinaryFormatter: формат привязан к типам и версиям сборки, и после рефакторинга кэш перестаёт читаться.
  • Версия в ключе (catalog:v2:42) — дешёвый способ «сбросить» весь кэш при смене формата: старые ключи перестают читаться и истекают по TTL.
  • Не кладите всё в один ключ. Большой hash или список на тысячи элементов обрабатывается одной командой — и на это время сервер занят.
★ Что запомнить из главы
  • Один ConnectionMultiplexer на процесс, из него — IDatabase; он потокобезопасен и сам переподключается.
  • TTL ставится при записи (TimeSpan в StringSetAsync), а пропавший ключ возвращает пустое значение, а не ошибку.
  • Атомарность — на стороне сервера: INCR, SET … NX, HSET выполняются целиком.
  • abortConnect=false позволяет приложению пережить недоступный Redis, но не делает команды успешными: они падают по таймауту.
  • Перебор — только SCAN; KEYS в проде запрещён.
