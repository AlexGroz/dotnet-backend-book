Глава 2. Подключение из .NET: ConnectionMultiplexer и первые команды

Одно соединение на процесс, TTL, атомарные операции и что означают ошибки подключения

основная глава

ConnectionMultiplexer: одно соединение на процесс

Клиент StackExchange.Redis устроен вокруг ConnectionMultiplexer: это одно физическое соединение с Redis, которое мультиплексирует все запросы приложения — параллельные команды уходят в один сокет, ответы разбираются по порядку и раскладываются по ожидающим задачам. Отсюда правила:

  • Один мультиплексор на процесс. Создавать его на каждый запрос — значит открывать соединение на каждый запрос: это дороже, чем сама команда.
  • Он потокобезопасен. IDatabase, полученный из мультиплексора, можно использовать из разных потоков.
  • Он сам переподключается. Пока соединение восстанавливается, команды либо ждут, либо падают по таймауту — в зависимости от настроек (ниже).
// Program.cs — регистрация в DI: один экземпляр на всё приложение
var cs = builder.Configuration.GetConnectionString("Redis") ?? "localhost:6379";

builder.Services.AddSingleton<IConnectionMultiplexer>(_ =>
    ConnectionMultiplexer.Connect(cs));

// в сервисе — только IDatabase, никаких новых соединений
public sealed class CatalogCache(IConnectionMultiplexer mux)
{
    private readonly IDatabase _db = mux.GetDatabase();
}

Строка подключения — не только адрес: в ней задают пароль, номер базы, таймауты и поведение при недоступном сервере, например redis:6379,password=…,connectTimeout=1000,abortConnect=false. Разбор abortConnect — ниже, потому что это самая частая причина «странных» падений на старте.

Первые команды: SET, GET, TTL, INCR, SET NX

Ниже — программа и её реальный вывод (Redis 7.4.12, клиент StackExchange.Redis 2.8.58). Она проверяет всё, на чём держится дальнейшее: время жизни ключа, атомарный счётчик и «поставить, только если нет».

var mux = await ConnectionMultiplexer.ConnectAsync("localhost:6379");
var db  = mux.GetDatabase();
var srv = mux.GetServer("localhost:6379");

Console.WriteLine($"ping:       {await db.PingAsync()}");
Console.WriteLine($"server:     {srv.Version}");

// строка с TTL: 2 секунды
await db.StringSetAsync("user:1:name", "Алексей", TimeSpan.FromSeconds(2));
Console.WriteLine($"get:        {await db.StringGetAsync("user:1:name")}");
Console.WriteLine($"ttl:        {await db.KeyTimeToLiveAsync("user:1:name")}");

await Task.Delay(2200);
Console.WriteLine($"after 2.2s: exists={await db.KeyExistsAsync("user:1:name")} " +
                  $"get=[{await db.StringGetAsync("user:1:name")}]");

// атомарный счётчик
await db.KeyDeleteAsync("hits");
await db.StringIncrementAsync("hits");        // 1
await db.StringIncrementAsync("hits", 5);     // 6
Console.WriteLine($"incr:       {await db.StringGetAsync("hits")}");

// «поставить, только если ключа нет» + TTL — основа локов и лимитов
var nx1 = await db.StringSetAsync("lock:job", "w1", TimeSpan.FromSeconds(10), When.NotExists);
var nx2 = await db.StringSetAsync("lock:job", "w2", TimeSpan.FromSeconds(10), When.NotExists);
Console.WriteLine($"set nx:     first={nx1} second={nx2}");
ping:       00:00:00.0009830
server:     7.4.12
get:        Алексей
ttl:        00:00:01.9910000
after 2.2s: exists=False get=[]
incr:       6
set nx:     first=True second=False

Что здесь важно:

  • PingAsync возвращает TimeSpan, а не строку: это время round-trip, около 1 мс на локальном сервере.
  • TTL уже меньше двух секунд (00:00:01.99…): время жизни отсчитывается с момента записи на сервере, а не с момента вашего вызова.
  • Пропавший ключ — не ошибка. После истечения StringGetAsync возвращает «пустое» значение (get=[]), а KeyExistsAsync — false. В коде это проверяют через .HasValue, а не сравнением с null.
  • StringIncrementAsync — атомарная операция на сервере: второй воркер не «потеряет» обновление, потому что команда выполняется целиком.
  • When.NotExists — это SET … NX: первый вызов вернул True, второй — False. На этом строится и распределённый лок (глава 4), и защита от параллельного прогрева кэша.

Что означают ошибки подключения

Поведение при недоступном сервере зависит от одного флага в строке подключения, и разница принципиальная. Проверено на закрытом порту:

-- abortConnect по умолчанию (true) --
connect -> RedisConnectionException: It was not possible to connect to the redis server(s).
Error connecting right now. To allow this multiplexer to continue retrying until it's able to
connect, use abortConnect=false in your connection string or AbortOnConnectFail=false; in your code.

-- abortConnect=false --
connect: ok (мультиплексор создан)
ping -> RedisConnectionException: The message timed out in the backlog attempting to send because
no connection became available (5000ms) - Last Connection Exception: UnableToConnect on
localhost:6399/Interactive, …
  • По умолчанию ConnectAsync падает, если сервер недоступен. Для приложения, которое должно пережить перезапуск Redis, это означает падение на старте.
  • abortConnect=false не «подключает любой ценой», а разрешает создать мультиплексор, который продолжит пытаться в фоне. Обратная сторона — Connect «успешен» даже когда сервера нет, а первая же команда падает по таймауту (в примере — через 5000 мс).
  • Практический вывод: в приложении ставят abortConnect=false и короткий connectTimeout, а здоровье Redis проверяют отдельно (health check), чтобы не узнавать о проблеме из таймаутов пользовательских запросов.

Ключи: префиксы и перебор

Ключи в Redis — плоское пространство имён, поэтому префикс (shop:, user:42:) несёт смысл: по нему видно, чей это ключ, и по нему же потом делают инвалидацию. Перебирать ключи командой KEYS нельзя: она просматривает всё и блокирует сервер. Для перебора используют SCAN — он идёт порциями, через курсор:

var keys = new List<string>();
await foreach (var k in srv.KeysAsync(pattern: "user:*"))
    keys.Add(k.ToString());

Console.WriteLine($"scan:       {string.Join(",", keys)}");
// scan:       user:1

Пример вернул один ключ — остальные уже истекли по TTL. KeysAsync — обёртка над SCAN; в redis-cli то же делает redis-cli --scan --pattern.

Значения: что именно кладут в Redis

По проводу ходят байты. RedisValue неявно превращается в строку, число и byte[], но ваш объект он не сериализует: это делает приложение. Практические правила:

  • JSON через System.Text.Json — если значение читают люди и другие сервисы; JsonSerializer.SerializeToUtf8Bytes сразу даёт байты без промежуточной строки.
  • Никаких «бинарных сериализаторов» вроде BinaryFormatter: формат привязан к типам и версиям сборки, и после рефакторинга кэш перестаёт читаться.
  • Версия в ключе (catalog:v2:42) — дешёвый способ «сбросить» весь кэш при смене формата: старые ключи перестают читаться и истекают по TTL.
  • Не кладите всё в один ключ. Большой hash или список на тысячи элементов обрабатывается одной командой — и на это время сервер занят.
★ Что запомнить из главы
  • Один ConnectionMultiplexer на процесс, из него — IDatabase; он потокобезопасен и сам переподключается.
  • TTL ставится при записи (TimeSpan в StringSetAsync), а пропавший ключ возвращает пустое значение, а не ошибку.
  • Атомарность — на стороне сервера: INCR, SET … NX, HSET выполняются целиком.
  • abortConnect=false позволяет приложению пережить недоступный Redis, но не делает команды успешными: они падают по таймауту.
  • Перебор — только SCAN; KEYS в проде запрещён.
