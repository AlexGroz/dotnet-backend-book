Глава 14. Слабая связанность: зачем внедрять зависимости

Начинаем часть про сборку приложения. Прежде чем говорить о контейнере зависимостей (глава 15), ответим на вопрос «зачем вообще всё это нужно».

Жёсткая связь — это проблема

Класс, который сам создаёт свои зависимости, «прибит» к конкретным реализациям:

// ✘ OrderService жёстко связан с SqlRepository и строкой подключения
public class OrderService
{
    private readonly SqlRepository _repo = new("Host=db;...");

    public Order Get(int id) => _repo.Find(id);
}

Что здесь плохо:

  • нельзя подставить другую реализацию (кэш, тестовый двойник);
  • нельзя протестировать OrderService без настоящей базы;
  • изменения (другая БД, другой способ хранения) задевают этот класс;
  • строка подключения «зашита» внутрь логики.

Интерфейс как контракт

Решение — зависеть от абстракции (интерфейса), а не от конкретного класса:

public interface IOrderRepository
{
    Order? Find(int id);
}

// ✔ класс зависит от контракта и получает его извне
public class OrderService(IOrderRepository repo)
{
    public Order? Get(int id) => repo.Find(id);
}

Теперь OrderService не знает, откуда приходят данные: база, кэш или заглушка в тесте. Это и есть слабая связанность.

Что это даёт на практике

ВыгодаЧто это значит в работе
ТестируемостьВ тестах подставляем поддельный IOrderRepository вместо БД
ЗаменяемостьМеняем реализацию (БД → кэш → внешний API), не трогая потребителя
Изоляция измененийПравки в одной части системы не расползаются по коду
Параллельная работаКоманды договариваются об интерфейсах и работают независимо

Те же четыре выгоды в коде

Потребитель во всех сценариях один и тот же — меняется только то, что ему передали:

public sealed record Order(int Id, decimal Total);  // сущность из Domain

public class OrderService(IOrderRepository repo)    // ← этот класс не меняется нигде ниже
{
    public Order? Get(int id) => repo.Find(id);
}

И три реализации контракта, которые понадобятся ниже (каждая в жизни лежит в своём файле):

public sealed class DbOrderRepository : IOrderRepository
{
    public int Calls { get; private set; }

    public Order? Find(int id)
    {
        Calls++;                                  // считаем обращения, чтобы показать эффект кэша
        return new Order(id, 100m);               // здесь был бы EF Core
    }
}

public sealed class CachedOrderRepository(IOrderRepository inner) : IOrderRepository
{
    private readonly Dictionary<int, Order> _cache = new();

    public Order? Find(int id)
    {
        if (_cache.TryGetValue(id, out var cached)) return cached;
        var order = inner.Find(id);
        if (order is not null) _cache[id] = order;
        return order;
    }
}

public sealed class HttpOrderRepository : IOrderRepository
{
    public Order? Find(int id) => new(id, 100m);  // здесь был бы HTTP-вызов
}

Здесь они собраны вместе только для показа; в реальном коде OrderService про них ничего не знает.

1. Тестируемость: подделка вместо базы

// «подделка»: без базы, без сети, ещё и считает обращения
public sealed class FakeOrderRepository(Order? preset) : IOrderRepository
{
    public int Calls { get; private set; }

    public Order? Find(int id)
    {
        Calls++;
        return preset;
    }
}

// сам тест
var fake = new FakeOrderRepository(new Order(42, 199.90m));
var service = new OrderService(fake);

Console.WriteLine(service.Get(42));
Console.WriteLine($"обращений к подделке: {fake.Calls}");

Вывод

Order { Id = 42, Total = 199.90 }
обращений к подделке: 1

Тест проверяет логику OrderService, а не работу PostgreSQL: ни контейнера, ни строки подключения, ни сети. Если бы сервис создавал new OrderRepository() сам, для теста пришлось бы поднимать настоящую базу.

2. Заменяемость: база → кэш → внешний API

IOrderRepository[] variants =
{
    new DbOrderRepository(),                              // читаем из базы
    new CachedOrderRepository(new DbOrderRepository()),   // база + кэш
    new HttpOrderRepository()                             // внешний сервис
};

foreach (var repo in variants)
    Console.WriteLine($"{repo.GetType().Name,-22} -> {new OrderService(repo).Get(5)}");

Вывод

DbOrderRepository      -> Order { Id = 5, Total = 100 }
CachedOrderRepository  -> Order { Id = 5, Total = 100 }
HttpOrderRepository    -> Order { Id = 5, Total = 100 }

OrderService один и тот же — меняется только объект в конструкторе. В приложении с DI-контейнером эту строку вообще не пишут в коде: её задаёт регистрация (глава 15).

3. Изоляция изменений: правка заперта в одном классе

var db = new DbOrderRepository();
var repo = new CachedOrderRepository(db);          // добавили кэш...
var service = new OrderService(repo);

service.Get(5);
service.Get(5);                                    // ...и второй раз в базу не идём
Console.WriteLine($"в «базу» сходили {db.Calls} раз(а)");

Вывод

в «базу» сходили 1 раз(а)

Появился кэш — изменился один класс, CachedOrderRepository. OrderService, DbOrderRepository и HttpOrderRepository остались как были: их эта правка не касается.

4. Параллельная работа: два класса на одном контракте

IOrderRepository cached = new CachedOrderRepository(new DbOrderRepository());
IOrderRepository http   = new HttpOrderRepository();

Console.WriteLine($"{cached.GetType().Name} и {http.GetType().Name}: общего только Find(int)");

Вывод

CachedOrderRepository и HttpOrderRepository: общего только Find(int)

Здесь «параллельная работа» — про людей, а не про потоки: два разработчика пишут два класса по одному контракту, файлы не пересекаются, мержей нет. Договорились об Find(int) -> Order? — и дальше каждый свободен.

У этого есть цена

Файлов и уровней становится больше, а вызов «прыгает» через интерфейс: чтобы найти реализацию, нужно перейти к ней, а не читать код построчно. Поэтому интерфейс вводят там, где есть вторая реализация (тест, кэш, другой источник) или где граница между слоями, — а не «на каждый класс».

Теперь зависимости нужно «собирать»

Как только класс перестал создавать зависимости сам, кто-то должен их ему передать. Раньше это делали вручную или через статику — и это превращалось в кашу. Поэтому нужен контейнер, который сам собирает объекты и раздаёт зависимости. О нём — глава 15.

★ Что запомнить

Жёсткая связь (класс сам делает new своих зависимостей) мешает тестам и изменениям. Слабая связь — это «зависеть от интерфейса, зависимость получать извне». Именно это и обслуживает внедрение зависимостей в .NET Core.
