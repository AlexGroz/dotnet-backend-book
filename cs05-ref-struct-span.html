Глава 5. ref struct и Span: окно в память без аллокаций

Как смотреть на часть строки или массива, ничего не копируя, — и почему такие типы принципиально не могут попасть в кучу.

основная глава

Проблема: «прочитать часть» обычно значит «скопировать»

string line = "10,20,30";

// Split(',') — разбить строку по запятой. Возвращает МАССИВ строк,
// и каждая часть — НОВАЯ строка в куче (здесь их три: "10", "20", "30").
// Плюс сам массив — ещё один объект в куче.
string[] parts = line.Split(',');

// Substring(0, 2) — взять 2 символа с позиции 0. Возвращает НОВУЮ строку "10"
// (в куче появился ещё один объект), исходная строка не меняется.
string first = line.Substring(0, 2);

// AsSpan(0, 2) — НЕ создаёт строку: возвращает «окно» из двух чисел
// (адрес символа «1» + длина 2) на уже существующей строке в куче.
ReadOnlySpan<char> window = line.AsSpan(0, 2);

Console.WriteLine($"{parts.Length} части, первая = {parts[0]}, окно = {window.ToString()}");

Что окажется на консоли

3 части, первая = 10, окно = 10
Сколько объектов создалось
  • Split: 4 объекта в куче — массив + три строки ("10", "20", "30").
  • Substring: +1 объект — новая строка "10".
  • AsSpan: 0 объектов в куче — только окно на стеке (адрес + длина), которое смотрит на те же символы исходной строки.
  • window.ToString() — вот здесь объект появится: чтобы напечатать окно как строку, её придётся создать. Поэтому в горячем коде с окном работают через индексатор и сравнение, а не через ToString().

Дальше — что такое само окно и почему так получается.

Что такое Span

Span<T> — это ссылка на участок памяти + длина. Он не владеет данными и не копирует их: он указывает на уже существующие символы или элементы.

строка в куче:   " 1 0 , 2 0 , 3 0 "
                   ▲
                   │  line.AsSpan(0, 2)
                   │
                   └─ Span (лежит на стеке, ~16 байт)
                      ┌──────────────────────────┐
                      │ ссылка: на символ «1»     │
                      │ длина: 2                  │
                      └──────────────────────────┘

новых символов в куче нет — есть только два числа на стеке
  • ReadOnlySpan<char> — окно только для чтения; именно его возвращает string.AsSpan().
  • Span<T> — окно, через которое можно и менять данные (для массивов и stackalloc).
  • Слайсинг (span.Slice(начало, длина)) тоже не копирует — создаёт новое окно внутри того же участка.
string line = "10,20,30";
ReadOnlySpan<char> all = line.AsSpan();          // всё окно

ReadOnlySpan<char> first = all.Slice(0, 2);      // "10" — без копии
ReadOnlySpan<char> tail  = all.Slice(3);         // "20,30" — без копии

int value = int.Parse(first);                    // парсинг прямо из окна
Console.WriteLine(value + 1);                    // 11
Почему это быстрее

Обычный путь: Substring → новая строка в куче → мусор → работа GC. Путь со Span: два числа на стеке → работа с теми же символами. На одном вызове разница незаметна; на разборе миллиона строк — это разница в разы.

Пример: разбор строки без единой аллокации

// считает непустые поля в CSV-строке, ничего не копируя
static int CountNotEmpty(ReadOnlySpan<char> line)
{
    int count = 0;

    while (!line.IsEmpty)
    {
        int comma = line.IndexOf(',');
        ReadOnlySpan<char> field = comma < 0 ? line : line.Slice(0, comma);

        if (!field.IsWhiteSpace())
            count++;

        if (comma < 0)
            break;

        line = line.Slice(comma + 1);     // сдвигаем окно, а не строку
    }

    return count;
}

string csv = "10, ,30,";      // три поля с данными + пустое
Console.WriteLine(CountNotEmpty(csv));   // 2
  • IndexOf и Slice не создают объектов — только меняют «окно».
  • field — это тоже окно внутри исходной строки, а не копия.
  • На входе string превращается в ReadOnlySpan<char> одним вызовом AsSpan().

stackalloc: буфер на стеке

Если нужен временный массив, его можно вообще не выделять в куче:

Span<int> buffer = stackalloc int[64];        // память на стеке, GC не участвует
for (int i = 0; i < buffer.Length; i++)
    buffer[i] = i;

// временный буфер символов для форматирования числа
Span<char> chars = stackalloc char[8];
if (123.TryFormat(chars, out int written))
    Console.WriteLine(new string(chars[..written]));   // "123"
Осторожно: стек конечен

Стек потока ~1 МБ. stackalloc на десятки килобайт — путь к StackOverflowException, который нельзя перехватить. Правило: небольшой фиксированный размер (десятки-сотни байт), и только на горячем пути.

Почему Span — ref struct

Span<T> и ReadOnlySpan<T> объявлены как ref struct. Это означает: такой тип может жить только на стеке. Компилятор запрещает всё, что могло бы «утащить» его в кучу.

// ✘ поле класса — окно переживёт данные
public sealed class Parser
{
    private ReadOnlySpan<char> _line;     // CS8345
}

// ✘ в коллекции или массиве
var list = new List<ReadOnlySpan<char>>();   // CS0306

// ✘ в async-методе: окно «переживёт» await
async Task<int> CountAsync(ReadOnlySpan<char> line)   // ошибка компиляции
{
    await Task.Delay(1);
    return line.Length;
}

// ✘ захват в лямбду: переменная уедет в объект-замыкание в куче
ReadOnlySpan<char> line = "10,20".AsSpan();
Func<int> f = () => line.Length;             // ошибка компиляции

Что означает каждое сообщение:

  • CS8345 — «полю запрещено иметь тип ref struct». Поле живёт столько же, сколько объект в куче, а окно должно умереть вместе с данными на стеке. Поэтому окно нельзя хранить в классе.
  • CS0306 — ref struct нельзя подставлять как аргумент типа: List<ReadOnlySpan<char>> хранит элементы в массиве в куче, то есть окна там жить не могут.
  • В async-методе параметр ref struct запрещён: при await состояние метода сохраняется в объект в куче, а окно туда «переехать» не может.
  • В лямбде захваченная переменная копируется в замыкание — объект в куче. Здесь line — это ReadOnlySpan<char> (строка 3 выше), поэтому захват невозможен; для string на этом месте ошибки бы не было — вот в чём разница.

Причина у всех одна: окно не владеет памятью. Если бы его можно было сохранить в куче (или пережить им await), оно могло бы остаться, когда исходные данные уже освобождены или стек «схлопнулся». Компилятор просто не даёт создать такую ситуацию.

Что делать, если очень нужно через await

Используйте Memory<T>/ReadOnlyMemory<T> — это «переносимое» окно (оно может жить в куче), но работать с ним медленнее. Либо передавайте string или массив и внутри метода берите AsSpan() — так делают почти всегда.

Когда Span действительно нужен

  • Да: разбор текста и протоколов, работа с большими массивами, циклы с миллионами итераций, код, где профилировщик показал много мусора (глава 7 .NET-раздела).
  • Нет: обычный прикладной код, где string и List<T> читаются лучше. Преждевременное усложнение здесь дороже выигрыша.
★ Что запомнить из главы
  • Span<T> — «окно»: ссылка на участок памяти + длина; данные не копируются.
  • AsSpan() и Slice() не создают объектов, а Substring/Split — создают.
  • stackalloc даёт буфер на стеке: быстро, но стек конечен — только небольшие фиксированные размеры.
  • ref struct живёт только на стеке: его нельзя в поле класса, в коллекцию, в async-метод, в лямбду.
  • Причина ограничений — безопасность: «окно» не должно пережить данные, на которые смотрит.
  • Применять на горячем пути (парсинг, протоколы), а не везде подряд.
