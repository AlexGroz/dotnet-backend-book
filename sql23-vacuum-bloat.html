Глава 23. VACUUM, autovacuum, bloat и HOT-апдейты

Цена MVCC: очистка версий, раздувание таблиц и место под новые версии строк

основная глава

Почему появляется bloat

Мы уже знаем: UPDATE в PostgreSQL не меняет строку на месте, а создаёт новую версию (глава 5). Старая версия становится мёртвой и ждёт, пока её уберёт VACUUM. То же самое с DELETE: строка не исчезает, а помечается мёртвой.

Если версии не успевают убираться, файлы таблиц и индексов растут быстрее самих данных. Это и есть bloat — «раздувание»:

  • та же выборка требует больше страниц → больше операций чтения;
  • индексы «размягчаются»: больше страниц на тот же набор ключей, хуже работают в кэше;
  • VACUUM и ANALYZE работают дольше и чаще, добавляя нагрузку;
  • в запущенных случаях планировщик начинает предпочитать Seq Scan там, где был индекс.
Формулировка

Bloat — это пространство, занятое мёртвыми версиями строк и «дырками» в страницах. Данные те же, а страниц больше — поэтому запросы дорожают, а autovacuum не успевает.

HOT-апдейты: как PostgreSQL экономит индексы

HOT (Heap-Only Tuples) — механизм, при котором UPDATE не создаёт записей в индексах. Новая версия строки просто цепляется к цепочке в той же странице (HOT chain), а индексы продолжают указывать на неё через «корень» цепочки.

Чтобы HOT сработал, нужны оба условия:

  1. Ни одна из изменяемых колонок не входит ни в один индекс. Обновили колонку, на которой есть индекс — PostgreSQL обязан обновить индекс, и HOT невозможен.
  2. Новая версия помещается в ту же страницу. Если страница заполнена под завязку, версия уходит в другую страницу — тоже мимо HOT.

Второе условие решает fillfactor — доля заполнения страниц. Для таблиц, которые часто обновляются, ставят 80–90 %: часть страницы заранее оставляют пустой, «под будущие версии».

ALTER TABLE orders SET (fillfactor = 85);                 -- место под новые версии строк

CREATE INDEX idx_orders_status ON orders (status)         -- индекс тоже можно «разреждить»
    WITH (fillfactor = 90);
Главная ловушка

Индекс на часто обновляемой колонке — например, updated_at, который приложение пишет при каждом изменении, — отключает HOT. Тогда каждое обновление тянет за собой ещё и запись в индекс: рост индекса, рост bloat, лишний I/O.

Диагностика

Начинаем со статистики по таблицам. Ключевая пара чисел: сколько строк обновлено и какая доля из них обновилась через HOT.

SELECT relname,
       n_live_tup, n_dead_tup,                        -- живые и мёртвые версии
       n_tup_upd, n_tup_hot_upd, n_tup_del,
       last_vacuum, last_autovacuum,
       pg_size_pretty(pg_total_relation_size(relid)) AS total_size
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 20;
  • Доля HOT = n_tup_hot_upd / n_tup_upd. Если она близка к нулю, а n_tup_upd большой — обновления идут мимо HOT (чаще всего из-за индекса на «живой» колонке).
  • n_dead_tup — сколько мёртвых версий ждёт очистки. Растёт и не падает — autovacuum не успевает или ему мешают.
  • last_autovacuum — когда таблицу очищали в последний раз. «Никогда» при большом числе изменений — тревожный знак.
  • Точные размеры даёт расширение pgstattuple: SELECT * FROM pgstattuple('orders'); (доля мёртвых кортежей и свободного пространства) и pgstatindex('idx_orders_created_at') — для индексов.
Кто мешает VACUUM

Мёртвую версию нельзя удалить, пока её «видит» хоть одна открытая транзакция. Поэтому виновниками часто оказываются долгие транзакции, idle in transaction и незакрытые слоты репликации. Чистить базу бессмысленно, пока кто-то держит горизонт.

Что делать: чистка и профилактика

Порог autovacuum «20 % строк» для большой таблицы — это очень много, поэтому его задают отдельно:

ALTER TABLE orders SET (
    autovacuum_vacuum_scale_factor  = 0.01,     -- чистить при 1% изменённых строк
    autovacuum_vacuum_threshold     = 1000,
    autovacuum_vacuum_cost_limit    = 2000,     -- не тормозить очистку «по стоимости»
    autovacuum_analyze_scale_factor = 0.005
);
  • fillfactor 80–90 % для «горячих» таблиц — чтобы HOT было куда положить новую версию.
  • Схема, дружелюбная к HOT: не индексировать колонки, которые меняются на каждом шаге; убрать лишние индексы; историю изменений выносить в отдельную журнальную таблицу.
  • Удалять данные секциями, а не строками (глава 24): DETACH и DROP не создают мёртвых версий вообще.
  • Убрать уже существующий bloat: VACUUM FULL возвращает место ОС, но берёт блокировку ACCESS EXCLUSIVE — только в окно обслуживания; pg_repack делает то же без длительной блокировки; для индексов — REINDEX CONCURRENTLY.
  • Помните: обычный VACUUM не возвращает место операционной системе — он лишь помечает пространство свободным для повторного использования этой же таблицей.

Что зависит от приложения

-- ✘ миллионы удалений создают миллионы мёртвых версий
DELETE FROM orders WHERE created_at < now() - interval '1 year';

-- ✔ массовые изменения — одной командой и по указанным колонкам
UPDATE orders SET status = 'expired' WHERE status = 'new' AND created_at < :cutoff;
  • Меняйте как можно меньше колонок за одно обновление: если затронуты только неиндексируемые поля, HOT продолжает работать.
  • Не индексируйте updated_at, если он обновляется постоянно и сам по себе не используется в условиях поиска.
  • Не держите длинных транзакций и «висящих» соединений (глава 20): они не дают чистить мёртвые версии.
  • Массовые операции — батчами, чтобы autovacuum успевал между ними.
★ Что запомнить из главы
  • Bloat — цена MVCC: мёртвые версии и «дырки» в страницах, из-за которых данных столько же, а страниц больше.
  • HOT работает при двух условиях: изменяемые колонки не индексированы и новая версия помещается в ту же страницу (второе обеспечивает fillfactor).
  • Диагностика — по pg_stat_user_tables (n_dead_tup, n_tup_upd, n_tup_hot_upd, last_autovacuum) и pgstattuple.
  • Лечение: настройки autovacuum для конкретной таблицы, fillfactor, HOT-дружелюбные индексы, секционирование вместо массовых DELETE, pg_repack вместо VACUUM FULL на живой базе.
  • Чистке мешают долгие транзакции и idle in transaction — сначала убираем их.
