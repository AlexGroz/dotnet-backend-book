Глава 35. CTE: WITH, рекурсия и материализация

Именованные подзапросы, которые читаются сверху вниз: деревья и иерархии через рекурсию, события в outbox одним запросом и главное изменение PostgreSQL 12 — CTE больше не «оптимизационный забор». Все выводы и планы — с живой базы PostgreSQL 16.15.

основная глава

Зачем нужен WITH

CTE (common table expression, «общее табличное выражение») — это подзапрос, которому дали имя и на который можно ссылаться как на таблицу:

WITH paid AS (                       -- имя и тело CTE
    SELECT * FROM orders WHERE status = 'paid'
), totals AS (                       -- второй CTE видит первый
    SELECT customer_id, sum(amount) AS total FROM paid GROUP BY customer_id
)
SELECT t.customer_id, c.name, t.total
FROM totals t JOIN customers c ON c.id = t.customer_id
ORDER BY t.total DESC;

Вывод

 customer_id | name  |  total
-------------+-------+---------
           2 | Борис | 3100.00
           4 | Глеб  | 3000.00
           1 | Аня   | 2850.00
           5 | Дина  | 2500.00
           3 | Вера  | 1700.00
(5 rows)

Польза здесь не в скорости, а в структуре: запрос читается как список шагов, и каждый шаг можно проверить отдельно — выделить тело CTE и выполнить. То же самое можно записать вложенными подзапросами, но на третьем уровне вложенности читать их уже невозможно. Именно поэтому CTE — стандартный способ писать «топ-N в группе» (глава 34): оконную функцию нельзя поставить в WHERE, зато её результат можно обернуть.

Материализация: что изменилось в PostgreSQL 12

До версии 12 CTE работал как optimization fence: PostgreSQL вычислял его целиком в отдельную временную структуру и только потом применял внешние условия. Если снаружи стоял фильтр по 60 строкам из 300 000 — сначала считались все 300 000. С 12-й версии нерекурсивный CTE, который используется один раз, просто подставляется в запрос (inlining), и условия проталкиваются внутрь. Проверка на таблице big_orders (300 000 строк):

-- 1. обычный CTE: используется один раз → инлайнится
WITH big AS (SELECT * FROM big_orders)
SELECT count(*) FROM big WHERE customer_id = 42;

-- 2. тот же CTE, но материализация включена принудительно
WITH big AS MATERIALIZED (SELECT * FROM big_orders)
SELECT count(*) FROM big WHERE customer_id = 42;

Планы: в первом случае условие уехало в индекс, во втором — считается вся таблица

-- 1. inlined
 Aggregate (actual time=0.073..0.080 rows=1 loops=1)
   ->  Index Only Scan using big_orders_customer_id_created_at_idx on big_orders
         Index Cond: (customer_id = 42)
         Heap Fetches: 0
 Execution Time: 0.185 ms

-- 2. MATERIALIZED
 Aggregate (actual time=92.306..92.307 rows=1 loops=1)
   CTE big
     ->  Seq Scan on big_orders (actual time=0.011..20.075 rows=300000 loops=1)
   ->  CTE Scan on big (actual time=0.031..92.232 rows=60 loops=1)
         Filter: (customer_id = 42)
         Rows Removed by Filter: 299940
 Execution Time: 95.220 ms

Разница — 500 раз: 0,185 мс против 95 мс. NOT MATERIALIZED возвращает поведение «инлайнить» (0,097 мс). А MATERIALIZED нужен ровно в одном случае: когда вы хотите посчитать дорогой шаг один раз и не дать планировщику продублировать вычисление.

Когда CTE материализуется сам
  • на него ссылаются дважды и больше — тогда вычисление одно, а результат читается дважды;
  • внутри есть изменение данных (INSERT/UPDATE/DELETE ... RETURNING) — такие CTE материализуются всегда;
  • указано MATERIALIZED;
  • CTE рекурсивный.

Во всех остальных случаях PostgreSQL 12+ инлайнит.

CTE, использованный дважды: считается один раз

Если на CTE ссылаются две части запроса, PostgreSQL материализует его сам — и это уже экономия, а не «забор»:

WITH s AS (SELECT customer_id, sum(amount) AS t FROM big_orders GROUP BY customer_id)
SELECT (SELECT count(*) FROM s) AS groups, (SELECT max(t) FROM s) AS best;

План: HashAggregate выполнен один раз, CTE Scan — дважды

 Result (actual time=115.003..115.119 rows=1 loops=1)
   CTE s
     ->  Finalize HashAggregate (actual time=111.086..112.784 rows=5000 loops=1)
           Group Key: big_orders.customer_id
   InitPlan 2 (returns $2)
     ->  Aggregate (actual time=114.150..114.150 rows=1 loops=1)
           ->  CTE Scan on s (actual time=111.089..113.936 rows=5000 loops=1)
   InitPlan 3 (returns $3)
     ->  Aggregate (actual time=0.847..0.847 rows=1 loops=1)
           ->  CTE Scan on s s_1 (actual time=0.000..0.359 rows=5000 loops=1)
 Execution Time: 116.169 ms

Тот же результат двумя независимыми подзапросами — агрегат считается дважды: InitPlan 1 58 мс и InitPlan 2 82 мс, итого 141 мс против 116. Выигрыш здесь скромный (агрегат по 300 000 строк дешёвый), но правило важное: чем дороже шаг, тем выгоднее вынести его в CTE, на который ссылаются несколько раз. Обратная сторона — материализованный CTE нельзя «дофильтровать» снаружи: все строки уже посчитаны.

А вот агрегат внутри CTE, использованного один раз, инлайнится — и внешнее условие проталкивается внутрь агрегата:

WITH totals AS (
    SELECT customer_id, sum(amount) AS t FROM big_orders GROUP BY customer_id
)
SELECT * FROM totals WHERE customer_id = 42;

План: Index Cond — фильтр ушёл внутрь, агрегируются только 60 строк

 GroupAggregate (actual time=0.398..0.399 rows=1 loops=1)
   ->  Bitmap Heap Scan on big_orders (actual time=0.056..0.379 rows=60 loops=1)
         Recheck Cond: (customer_id = 42)
         ->  Bitmap Index Scan on big_orders_customer_id_created_at_idx
               Index Cond: (customer_id = 42)
 Execution Time: 0.456 ms

Это неочевидный, но важный факт для тех, кто привык к версиям до 12: «агрегат в CTE всё равно посчитает всю таблицу» — уже неправда. Смотреть надо на план, а не на форму записи; если инлайнинг нежелателен, MATERIALIZED его запретит.

Рекурсивный CTE: иерархии и деревья

Вторая большая задача, ради которой CTE незаменим, — обход иерархии: категории, подчинённость сотрудников, дерево комментариев, граф связей. Устроен рекурсивный CTE всегда одинаково: якорь (стартовые строки) UNION ALL рекурсивная часть, которая ссылается на сам CTE.

WITH RECURSIVE tree AS (
    SELECT id, name, parent_id, 1 AS depth, name::text AS path   -- якорь: корни
    FROM categories WHERE parent_id IS NULL
  UNION ALL
    SELECT c.id, c.name, c.parent_id, t.depth + 1,               -- шаг: дети найденных
           t.path || ' > ' || c.name
    FROM categories c JOIN tree t ON c.parent_id = t.id
)
SELECT id, name, depth, path FROM tree ORDER BY path;

Вывод: всё дерево с глубиной и путём от корня

 id |    name     | depth |                     path
----+-------------+-------+-----------------------------------------------
  1 | Электроника |     1 | Электроника
  2 | Ноутбуки    |     2 | Электроника > Ноутбуки
  4 | Аксессуары  |     3 | Электроника > Ноутбуки > Аксессуары
  6 | Зарядки     |     4 | Электроника > Ноутбуки > Аксессуары > Зарядки
  5 | Чехлы       |     4 | Электроника > Ноутбуки > Аксессуары > Чехлы
  3 | Телефоны    |     2 | Электроника > Телефоны
  7 | Смартфоны   |     3 | Электроника > Телефоны > Смартфоны
(7 rows)

Если нужен не весь лес, а поддерево, якорь просто меняется на нужный узел:

WITH RECURSIVE sub AS (
    SELECT id, name, parent_id, 0 AS depth FROM categories WHERE id = 2
  UNION ALL
    SELECT c.id, c.name, c.parent_id, s.depth + 1
    FROM categories c JOIN sub s ON c.parent_id = s.id)
SELECT * FROM sub ORDER BY depth, id;

Вывод: сама категория и все её потомки

 id |    name    | parent_id | depth
----+------------+-----------+-------
  2 | Ноутбуки   |         1 |     0
  4 | Аксессуары |         2 |     1
  5 | Чехлы      |         4 |     2
  6 | Зарядки    |         4 |     2
(4 rows)

В плане рекурсия видна как Recursive Union и WorkTable Scan — второй узел читает строки, добавленные на предыдущем шаге (в примере loops=3, по числу итераций):

 CTE Scan on sub (actual time=0.020..0.112 rows=4 loops=1)
   CTE sub
     ->  Recursive Union (actual time=0.018..0.109 rows=4 loops=1)
           ->  Index Scan using categories_pkey on categories (rows=1)   -- якорь
                 Index Cond: (id = 2)
           ->  Hash Join (actual time=0.023..0.023 rows=1 loops=3)       -- шаг
                 Hash Cond: (c.parent_id = s.id)
                 ->  WorkTable Scan on sub s (rows=1 loops=3)             -- строки прошлого шага
Цикл в данных: рекурсия не остановится сама

Если в иерархии есть кольцо (узел оказался потомком самого себя), запрос будет выполняться, пока не кончится память или терпение. Демонстрация: три узла A → C → B → A.

WITH RECURSIVE t AS (
    SELECT id, name, parent_id, 1 AS step FROM cat_cycle WHERE id = 1
  UNION ALL
    SELECT c.id, c.name, c.parent_id, t.step + 1
    FROM cat_cycle c JOIN t ON c.id = t.parent_id)
SELECT * FROM t LIMIT 7;

Вывод: одни и те же три строки по кругу (остановил только LIMIT)

 id | name | parent_id | step
----+------+-----------+------
  1 | A    |         3 |    1
  3 | C    |         2 |    2
  2 | B    |         1 |    3
  1 | A    |         3 |    4
  3 | C    |         2 |    5
  2 | B    |         1 |    6
  1 | A    |         3 |    7
(7 rows)

Лечится тремя способами, и все три стоит знать:

  1. UNION вместо UNION ALL — повторяющиеся строки отбрасываются, и цикл обрывается на третьем шаге (проверено: вывод — ровно 3 строки: 1, 2, 3). Минус — дедупликация стоит денег на больших выборках.
  2. CYCLE (стандарт SQL:2011, в PostgreSQL — с 14-й версии): рекурсия останавливается, а строка, замкнувшая круг, помечается флагом и получает путь.
  3. Ограничение глубины в самом запросе: WHERE step < 100 в рекурсивной части. Грубо, но предсказуемо.
WITH RECURSIVE t AS (
    SELECT id, name, parent_id FROM cat_cycle WHERE id = 1
  UNION ALL
    SELECT c.id, c.name, c.parent_id FROM cat_cycle c JOIN t ON c.id = t.parent_id)
CYCLE id SET is_cycle USING path
SELECT id, name, path, is_cycle FROM t;

Вывод: рекурсия остановилась сама, последняя строка помечена как цикл

 id | name |       path        | is_cycle
----+------+-------------------+----------
  1 | A    | {(1)}             | f
  3 | C    | {(1),(3)}         | f
  2 | B    | {(1),(3),(2)}     | f
  1 | A    | {(1),(3),(2),(1)} | t
(4 rows)

В отличие от MySQL и SQL Server, у PostgreSQL нет настройки «глубина рекурсии по умолчанию»: WITH RECURSIVE без условий остановки будет идти, пока хватает ресурсов. В MySQL 8 предел задаёт cte_max_recursion_depth (по умолчанию 1000), в SQL Server — OPTION (MAXRECURSION n) (по умолчанию 100). Это различие — хороший ответ на вопрос «чем отличается рекурсивный CTE в PostgreSQL и MSSQL».

CTE с изменением данных: outbox одним запросом

В PostgreSQL WITH может содержать INSERT, UPDATE или DELETE с RETURNING, и это даёт очень полезную конструкцию: изменить строку и тут же положить событие в outbox — атомарно, в рамках одного оператора (подробно про сам паттерн — глава 31):

WITH changed AS (
    UPDATE cart SET status = 'paid' WHERE id = 1 RETURNING id, status
)
INSERT INTO outbox (payload)
SELECT jsonb_build_object('cart', id, 'status', status) FROM changed
RETURNING id, payload;

Вывод: строка обновлена и событие вставлено одним запросом

 id |            payload
----+-------------------------------
  1 | {"cart": 1, "status": "paid"}
(1 row)

INSERT 0 1
Две особенности DML-CTE, о которых легко забыть
  • Он выполняется всегда. Даже если к CTE никто не обращается, изменение произойдёт — проверено: UPDATE внутри невыбранного CTE перевёл заказ в paid, а внешний SELECT просто посчитал строки. В отличие от обычного CTE, «лениво» такие вещи не работают.
  • Одну и ту же строку нельзя менять дважды в одном запросе. Два CTE с UPDATE ... WHERE id = 3 не дают ошибки, но второй молча обновит 0 строк: в прогоне первый CTE вернул 1 строку, второй — 0, а в таблице осталось значение первого (x). Документация предупреждает, что «какая из правок победит» не гарантировано, поэтому такую схему нельзя использовать в коде вовсе.

Практический вывод для вакансии, где перечислены PostgreSQL, MySQL и MS SQL: структуру запроса (CTE + оконные функции) можно переносить между ними почти без правок, а вот оптимизационные подсказки и способ фильтрации по окну придётся менять — и это нормальный ответ на интервью.

★ Чек-лист: CTE, подзапрос или временная таблица
  1. Шаг используется больше одного раза? — берите CTE: посчитается один раз.
  2. Снаружи нужен фильтр по дорогому шагу? — проверьте план: в PG 12+ CTE инлайнится, и условие проталкивается внутрь. Увидели CTE Scan с большим rows — уберите MATERIALIZED.
  3. Это иерархия? — рекурсивный CTE, и обязательно защита от цикла (CYCLE или счётчик глубины).
  4. Результат нужен нескольким запросам или индексу? — временная таблица (CREATE TEMP TABLE ... ON COMMIT DROP).
  5. Нужно «топ-N в группе»? — ROW_NUMBER() в CTE и фильтр снаружи (глава 34).
★ Что спросят и как отвечать
  1. «Чем CTE отличается от подзапроса?» — читаемостью и переиспользованием; до PG 12 CTE всегда материализовался и был «забором» для оптимизаций, сейчас нерекурсивный CTE с одним использованием инлайнится, и это видно по плану.
  2. «Что такое рекурсивный CTE и где предел?» — якорь + рекурсивная часть через UNION ALL; в PostgreSQL своего предела нет (нужен CYCLE или счётчик), в MySQL — 1000, в SQL Server — 100 по умолчанию.
  3. «Почему запрос с CTE стал медленнее после переписывания?» — скорее всего, CTE материализовался (используется дважды или указан MATERIALIZED), и внешний фильтр применяется после расчёта всех строк.
  4. «Можно ли в CTE делать UPDATE?» — в PostgreSQL да, с RETURNING; это основа transactional outbox. Дважды одну строку менять нельзя.
