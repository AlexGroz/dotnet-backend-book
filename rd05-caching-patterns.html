Глава 5. Кэширование: cache-aside, TTL, инвалидация и stampede

Как кэш ускоряет сервис и как он же ломает данные, если ошибиться с временем жизни

основная глава

Cache-aside: самый частый паттерн

Приложение само решает, что и когда кэшировать: сначала спрашивает Redis, при промахе идёт в PostgreSQL и кладёт результат в Redis. Кэш ничего не знает про базу — он просто хранилище по ключу. CatalogRepository ниже — обычный репозиторий поверх DbContext; IDatabase приходит из DI (глава 2).

public sealed record CatalogItem(int Id, string Title);   // то, что кэшируем

// db — Redis из DI (глава 2), repo — источник истины (PostgreSQL)
public sealed class CatalogCache(IDatabase db, CatalogRepository repo)
{
    public async Task<CatalogItem?> GetAsync(int id)
    {
        var key = $"catalog:v1:{id}";        // префикс + версия формата + id

        // GET catalog:v1:42 — сначала спрашиваем кэш
        var cached = await db.StringGetAsync(key);
        if (cached.HasValue)                 // HasValue, а не «!= null»: значение может быть пустым
            return JsonSerializer.Deserialize<CatalogItem>(cached.ToString());   // попали в кэш

        // промах: идём в базу за настоящими данными (дорого, но один раз)
        var item = await repo.FindAsync(id);
        if (item is null) return null;       // «нет такого» не кэшируем: null — это не данные

        // SET catalog:v1:42 <json> EX 300 — кладём в кэш с TTL 5 минут
        await db.StringSetAsync(key, JsonSerializer.Serialize(item),
            TimeSpan.FromMinutes(5));
        return item;
    }
}
ШагЧто происходитЕсли Redis недоступен
1. Чтение из кэшаGET catalog:v1:42Идём в БД (кэш — ускоритель, не источник истины)
2. ПромахЗапрос в PostgreSQLРаботает как обычно
3. Запись в кэшSET с TTLПропускаем; следующий запрос снова попробует
TTL — не «на всякий случай», а часть контракта

Ключ без времени жизни остаётся в Redis навсегда: данные устаревают, память заканчивается. TTL — единственная гарантия, что кэш сам себя починит, даже если инвалидация где-то не сработала.

Тот же паттерн через IDistributedCache

У ASP.NET Core есть готовая абстракция кэша — интерфейс IDistributedCache из Microsoft.Extensions.Caching.Abstractions. Это не клиент Redis: это четыре операции «положить/взять/обновить/удалить байты по ключу», за которыми может стоять Redis, память процесса или SQL Server. Реализацию для Redis даёт пакет Microsoft.Extensions.Caching.StackExchangeRedis.

Полный список методов интерфейса (получен рефлексией по сборке, не по памяти):

МетодЧто делает
SetAsync(key, byte[], options)
GetAsync(key)		 записать и прочитать значение; тип — только byte[] (для строк есть расширения SetStringAsync/GetStringAsync)
RemoveAsync(key)удалить ключ
RefreshAsync(key)продлить скользящий срок, не читая значение
Больше ничего: ни чтения TTL, ни атомарных операций, ни перебора ключей. Это и есть главное при выборе.

Чем он хорош — почему в ASP.NET Core его берут по умолчанию:

  • Не нужно знать Redis. Нет команд, структур ключей и ручной сериализации — «ключ → байты». Для кэша ответа этого достаточно.
  • Провайдер меняется одной строкой. AddStackExchangeRedisCache — Redis, AddDistributedMemoryCache — память процесса (проверено: этот метод компилируется в чистом веб-проекте, отдельный пакет не нужен). Код сервисов при смене провайдера не меняется.
  • Три вида срока из главы 3 — готовыми настройками: AbsoluteExpiration, AbsoluteExpirationRelativeToNow, SlidingExpiration.
  • Это стандарт платформы: на той же абстракции работает сессия ASP.NET Core и другие компоненты, которым нужен «распределённый кэш».

Чем он хуже — точный список того, чего в интерфейсе нет:

  • Никакой атомарности. Нет INCR и SET … NX: счётчик через Get + Set теряет обновления при параллельных запросах, а распределённый лок на этой абстракции не построить.
  • Только байты и строки. Хеши, списки, множества и sorted sets недоступны: «профиль по полям» или очередь на IDistributedCache не выразить.
  • Срок не прочитать. Сколько ключу осталось жить, через интерфейс не узнать — только своим клиентом.
  • Нет перебора и пайплайнов. Ни SCAN, ни массовых операций: инвалидация «по префиксу» превращается в список ключей, который ведёте вы.
  • Свой формат внутри Redis. Значение — не строка, а хеш из трёх полей (absexp, sldexp, data), а ключ получает префикс InstanceName (см. ниже). Поэтому такие ключи нельзя читать «руками» и на каждый ключ расходуется чуть больше памяти.
Как решить: «нужен только кэш» или полноценный клиент

Ответьте на четыре вопроса. Если хотя бы один ответ «да» — нужен StackExchange.Redis:

  • нужна атомарная операция «прочитать — изменить — записать» (счётчик INCR, лок SET NX)?
  • нужна структура, а не одно значение: хеш, список, множество, sorted set?
  • нужно знать TTL ключа или перебирать ключи по маске?
  • нужны пайплайны, транзакции или Lua-скрипты?

Если все ответы «нет» — это обычный кэш «байты по ключу», и IDistributedCache короче: меньше кода, меньше знаний, проще сменить провайдера. Обе линии можно держать в одном приложении, если префиксы ключей не пересекаются.

Дальше — тот же cache-aside, но через абстракцию. Реальный вывод:

// Program.cs (top-level statements): builder — WebApplicationBuilder
builder.Services.AddStackExchangeRedisCache(o =>
{
    o.Configuration = "localhost:6379";         // адрес сервера (та же строка подключения)
    o.InstanceName  = "shop:";                  // префикс ВСЕХ ключей этого приложения
});

// дальше — в любом сервисе: cache — это IDistributedCache, пришедший из DI
// (public sealed class CatalogCache(IDistributedCache cache))

// SetStringAsync — «положить строку»; третий аргумент — политика жизни ключа
await cache.SetStringAsync("catalog:42", "{\"id\":42}",
    new DistributedCacheEntryOptions
    {
        AbsoluteExpirationRelativeToNow = TimeSpan.FromSeconds(5)   // умрёт через 5 с
    });

// GetStringAsync — прочитать строку; null, если ключа нет
Console.WriteLine(await cache.GetStringAsync("catalog:42"));      // {"id":42}

// GetAsync — те же байты, что лежат в Redis: 9 = длина {"id":42}
Console.WriteLine((await cache.GetAsync("catalog:42"))?.Length);  // 9

await Task.Delay(5500);                                          // пережили TTL
Console.WriteLine($"[{await cache.GetStringAsync("catalog:42")}]"); // [] — это null в скобках

Две детали, которые видно только в самом Redis:

  • InstanceName — это префикс. В Redis ключ называется shop:catalog:42, а не catalog:42: абстракция добавляет префикс сама, чтобы несколько приложений могли делить один Redis.
  • Промах и истечение — это null, а не исключение; после 5,5 секунд вернулось пустое значение.
Что IDistributedCache реально кладёт в Redis

Важно один раз увидеть: ключ — это не строка, а хеш из трёх полей. Иначе непонятно, почему «руками» такой ключ не прочитать:

$ redis-cli keys '*'
shop:probe                  # InstanceName добавил префикс к имени "probe"
$ redis-cli type shop:probe
hash                        # ХЕШ, а не string
$ redis-cli hgetall shop:probe
absexp
639304252946046557         # когда истекать: абсолютное время в тиках DateTime
sldexp
-1                          # sliding-окно не задано (−1), иначе — его длина
data
x                           # сами данные (байты, которые вы положили)
$ redis-cli pttl shop:probe
294234                      # сколько осталось жить, мс (≈5 минут из теста)

Отсюда практическое следствие: записать такой ключ «в лоб» строкой нельзя — абстракция ждёт хеш. Проверено:

$ redis-cli set shop:manual manual-value    # положили строку
$ # а приложение читает через IDistributedCache:
manual -> RedisServerException: WRONGTYPE Operation against a key holding the wrong kind of value

Поэтому кэш из IDistributedCache и «свой» кэш на StackExchange.Redis не смешивают на одних и тех же ключах: форматы разные.

SlidingExpiration в тех же настройках продлевает жизнь ключа при каждом чтении (проверено: ключ, записанный с окном 3 секунды, имел в Redis TTL 3), но у него есть цена — «горячий» ключ никогда не истечёт, и устаревшее значение может жить бесконечно, пока его читают.

Инвалидация: что делать при записи

Кэш устаревает не сам по себе, а потому что данные изменились. Три рабочих подхода, от простого к сложному:

  1. Удалить ключ после успешной записи в БД — самое частое. Именно удалить, а не «записать новое значение»: между записью в БД и записью в кэш кто-то успеет прочитать старое и положить его обратно.
  2. Версия в ключе. catalog:v2:42: при смене формата или «полном сбросе» поднимается версия, старые ключи просто перестают читаться и истекают сами.
  3. TTL как страховка. Даже если инвалидация не сработала (сообщение потерялось, код забыл), через N минут кэш вернётся к правде.
Порядок операций важен

Инвалидация выполняется после коммита транзакции в БД. Если удалить ключ до коммита, параллельный читатель успеет положить в кэш старое значение, и оно останется там до истечения TTL.

Чего делать точно не стоит: пытаться «синхронизировать» кэш и БД двумя записями без общей транзакции. Атомарно это не сделать, поэтому правильная стратегия — «кэш может быть устаревшим не дольше TTL».

Промах-шторм (stampede) и как его гасят

Популярный ключ истёк — и сто запросов одновременно идут в базу за одним и тем же. Нагрузка на БД умножается на сто, а кэш заполняется одинаковыми значениями. Лечится «право на прогрев»: только один процесс идёт в БД, остальные ждут.

public async Task<CatalogItem?> GetWithLockAsync(int id)   // в том же классе CatalogCache
{
    var key     = $"catalog:v1:{id}";                  // тот же ключ кэша, что и выше
    var lockKey = $"lock:{key}";                       // отдельный ключ-лок для этого id
    var token   = Guid.NewGuid().ToString("N");        // «кто взял лок»: уникально для попытки

    // SET lock:{key} <token> NX EX 10 — берёт лок только один:
    //   NX (When.NotExists) — «поставь, только если ключа нет»,
    //   EX 10 — лок сам истечёт, если процесс умрёт, не сняв его
    if (await db.StringSetAsync(lockKey, token, TimeSpan.FromSeconds(10), When.NotExists))
    {
        try
        {
            var item = await repo.FindAsync(id);       // в базу идёт ОДИН процесс
            if (item is null) return null;

            // заполнили кэш для остальных ожидающих
            await db.StringSetAsync(key, JsonSerializer.Serialize(item), TimeSpan.FromMinutes(5));
            return item;
        }
        finally
        {
            // снять лок, только если он всё ещё наш: GET + сравнение с token + DEL
            // должны быть одной атомарной операцией — иначе можно удалить ЧУЖОЙ лок,
            // который успел истечь и достаться другому процессу (EVAL на Lua)
            await db.ScriptEvaluateAsync(
                "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) end",
                new RedisKey[] { lockKey },    // KEYS[1] = lock:{key}
                new RedisValue[] { token });   // ARGV[1] = наш token
        }
    }

    // лок занят: короткая пауза, чтобы владелец успел заполнить кэш,
    // затем обычное чтение кэша; если он всё ещё пуст — идём в БД сами
    // (без лока: лучше лишний запрос, чем ожидание)
    await Task.Delay(50);
    return await GetAsync(id) ?? await repo.FindAsync(id);
}
  • SET … NX EX — и лок, и его таймаут. Проверено: первый вызов получает True, второй — False. TTL обязателен: упавший процесс не должен держать лок вечно.
  • Снимать лок скриптом, а не DEL. Иначе можно удалить чужой лок, который успел истечь и достаться другому процессу.
  • Ждущие не должны висеть. Пауза с повтором, затем — свой запрос в БД: лучше несколько лишних запросов, чем очередь, которая не движется.

Кэш и запись: три схемы

СхемаКак работаетКогда
Cache-asideПриложение читает кэш, при промахе идёт в БД и заполняет кэшПочти всегда: просто, предсказуемо, БД — источник истины
Write-throughПишем в кэш и в БД в одном сценарииРедко: две системы не commit-ятся вместе, нужна компенсация
Write-behindПишем в кэш, в БД — асинхронноТолько когда потеря записи допустима и есть надёжная очередь

Для типового .NET-сервиса правильный выбор — cache-aside плюс инвалидация после коммита. Write-through и write-behind требуют решения проблемы «двух источников истины», а это уже отдельный проект.

★ Что запомнить из главы
  • Cache-aside: кэш — ускоритель, истина — в PostgreSQL; при недоступном Redis сервис работает медленнее, но работает.
  • TTL обязателен у каждого ключа; sliding-окно продлевает жизнь при чтении, поэтому горячие ключи не истекают никогда.
  • Инвалидация — удалением ключа после коммита; версия в имени ключа даёт бесплатный «полный сброс».
  • Промах-шторм гасят локом SET … NX EX с обязательным TTL и снятием через скрипт.
