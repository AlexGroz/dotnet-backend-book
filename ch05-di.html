Глава 5. Внедрение зависимостей и жизненные циклы

DI в .NET Core встроен и обязателен. Разберём жизненные циклы и самую частую ошибку — Captive Dependency.

Идея внедрения зависимостей

Вместо того чтобы класс сам создавал зависимости (new) или доставал их из статики, зависимости передаются ему извне — обычно через конструктор. Это делает код тестируемым и управляемым.

// ✘ класс сам создаёт зависимость
public class OrderService
{
    private readonly IRepository _repo = new SqlRepository("..."); // привязка к реализации
}

// ✔ зависимость приходит извне
public class OrderService(IRepository repo)
{
    public Task<Order> GetAsync(int id) => repo.GetAsync(id);
}

Жизненные циклы

LifetimeСколько живётТипичный пример
TransientНовый на каждое обращениемапперы, лёгкие сервисы без состояния
ScopedОдин на HTTP-запрос (на «scope»)DbContext, репозитории
SingletonОдин на всё приложениеконфиг, кэши, инфраструктура (потокобезопасна!)
 
builder.Services.AddTransient<IMapper, Mapper>();
builder.Services.AddScoped<IOrderRepository, OrderRepository>();
builder.Services.AddSingleton<IClock, SystemClock>();

// DbContext по умолчанию — Scoped
builder.Services.AddDbContext<AppDbContext>(o => o.UseNpgsql(cs));
★ Золотое правило

Долгоживущий сервис не должен зависеть от короткоживущего. Singleton не зависит от Scoped.

Captive Dependency

Это ситуация, когда долгоживущий сервис «захватывает» короткоживущий. Самый частый случай — Singleton держит DbContext (а он Scoped).

Опасный пример

builder.Services.AddSingleton<ReportService>();     // живёт всё приложение
builder.Services.AddDbContext<AppDbContext>(o => o.UseNpgsql(cs)); // Scoped!

public sealed class ReportService(AppDbContext db) // Scoped попал в Singleton → captive
{
    public Task<Report> BuildAsync() => db.Reports.FirstAsync();
}

Чем плохо: рост памяти (контекст живёт вечно), ошибки конкурентности («A second operation started on this context…»), устаревшие данные.

Как правильно, если Singleton нужен доступ к БД

public sealed class ReportService(IServiceScopeFactory scopeFactory)
{
    public async Task<Report> BuildAsync(CancellationToken ct)
    {
        using var scope = scopeFactory.CreateScope(); // свой scope на операцию
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
        return await db.Reports.AsNoTracking().FirstAsync(ct);
    }
}

Как отлавливать Captive Dependency

  1. Валидация графа на старте — главный способ: 
    builder.Host.UseDefaultServiceProvider(o =>
{
    o.ValidateScopes = true;    // ловит: Singleton → Scoped
    o.ValidateOnBuild = true;   // проверяет весь граф при старте
});
  2. Тест-«сторож», который резолвит все сервисы внутри scope.
  3. Код-ревью: Singleton — только stateless; красные флаги — IServiceProvider или DbContext в Singleton.

Фоновые сервисы

BackgroundService — Singleton, поэтому scope нужно создавать на каждую итерацию:

using (var scope = scopeFactory.CreateScope())
{
    var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
    await db.CleanupAsync(ct);
}

★ Что запомнить из главы

Transient / Scoped / Singleton; долгоживущий не зависит от короткоживущего. Частая ошибка — Singleton→DbContext. Ловим через ValidateScopes/ValidateOnBuild, чиним через IServiceScopeFactory.
