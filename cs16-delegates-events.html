Глава 16. Делегаты, лямбды и события: как метод становится значением

Почему (sender, total) => … — это метод, а не «магия», откуда берутся его параметры, что значит += у события и где здесь утечка памяти.

основная глава

Разминка: в переменной может лежать метод

Обычно в переменной лежит значение: число, строка, ссылка на объект. Делегат — это тип, переменная которого хранит метод. Объявляется он как любой другой тип, только вместо полей и свойств описывает сигнатуру метода:

delegate int Op(int x);        // «метод, который берёт int и возвращает int»

static int Double(int x) => x * 2;
static int Square(int x) => x * x;

Op op = Double;                // в переменной лежит метод, а не число
Console.WriteLine(op(21));     // 42   ← вызов через переменную

op = Square;                   // та же переменная — другой метод
Console.WriteLine(op(8));      // 64

Что окажется на консоли

42
64

Смысл в одной фразе: метод стал значением. Его можно передать в другой метод параметром, положить в поле, вернуть из функции, сохранить в списке. Из этого «кирпичика» дальше собираются LINQ, обработчики событий и регистрация в DI.

Что такое делегат на самом деле

Делегат — ссылочный тип. Внутри него две вещи: на каком объекте вызывать (Target) и какой метод (Method). Для статического метода Target равен null; для метода экземпляра там лежит сам объект — поэтому делегат, как и любой объект, держит его в памяти (это пригодится в разделе про утечки).

Свои делегаты объявляют редко: в .NET уже есть стандартные, и их хватает почти всегда.

Как читается Func<int, int>: последний параметр типа — результат, то есть «дай мне int, верну int»: это метод int F(int x). Именно поэтому в Where стоит Func<T, bool> — он спрашивает «элемент подходит?», ответ булев.

Подстановка метода в переменную-делегат называется method group conversion: вы пишете имя метода без скобок, а компилятор сам делает из него делегат.

Func<int, int> twice = Double;              // имя метода без скобок — стал делегатом
Action<string> log = Console.WriteLine;      // работает и с чужим методом
Predicate<int> positive = n => n > 0;       // свой «фильтр»: лямбда, о ней ниже

var nums = new List<int> { -2, 5, 0, 7 };
Console.WriteLine(string.Join(", ", nums.Where(n => n > 0)));   // Where ждёт Func<int, bool>

Что окажется на консоли

5, 7
Зачем вообще нужны делегаты

Без них «передать поведение» можно было бы только наследованием: класс-параметр с единственным методом. Делегат делает то же одной строкой — поэтому Where, Select, обработчики событий и фабрики в DI выглядят так коротко.

Лямбда: метод без имени

Каждый раз писать static int Double(int x) => x * 2; ради одной строки неудобно. Лямбда — это метод, объявленный в том месте, где он нужен, без имени:

Func<int, int> square = x => x * x;                  // (параметры) => выражение
Func<int, int, int> add = (a, b) => a + b;           // параметров два
Func<int, int> inc = x => { return x + 1; };         // тело-блок: можно несколько строк
Action<string> print = s => Console.WriteLine(s);     // ничего не возвращает

Console.WriteLine(square(9));    // 81
Console.WriteLine(add(2, 3));    // 5

Что окажется на консоли

81
5

Читается так: слева от => — параметры, справа — тело. У лямбды нет собственного типа: она получает его от того места, куда её кладут. Такое место называется целевым типом — именно поэтому в примере выше не написано ни одного int.

Ненужный параметр называют _ — это тот же discard, что был в главе 5: Func<int, int, int> twice = (_, b) => b * 2;, вызов twice(1, 21) даёт 42 — первый аргумент принят и выброшен. А если метод возвращает два значения, его пишут как (bool ok, int half) Try(…) => (…, …) — это выражение-тело плюс кортеж из главы 6.

Почему в (sender, total) => … ничего не объявлено снаружи

Параметры лямбды объявлены в ней самой, в скобках, — как в обычном методе. Отдельной строки «где-то задать sender» не нужно: значения приходят в момент вызова, а не при подписке. Например, у события event EventHandler<decimal> Paid целевой тип — void (object? sender, decimal total), и значения в него кладёт тот, кто поднимает событие: Paid?.Invoke(this, Total) — this уходит в sender, Total — в total. Ненужный параметр заменяют на _: (_, total) => …. Подробный разбор — «Паттерны в .NET», глава 8.

Несколько параметров без скобок нельзя: x => … — один параметр, (a, b) => … — два и больше (или ни одного: () => …). Типы можно указать явно, если компилятор не догадывается: (decimal a, decimal b) => a * b.

Замыкание: лямбда помнит переменные вокруг себя

Лямбда может использовать локальные переменные метода, в котором написана. Компилятор при этом создаёт в куче объект-«замыкание», кладёт туда эти переменные и передаёт его делегату в Target — поэтому переменная живёт дольше своего метода:

static Func<int> MakeCounter()
{
    int count = 0;
    return () => ++count;        // лямбда захватила count
}

var next = MakeCounter();
Console.WriteLine(next());       // 1
Console.WriteLine(next());       // 2   ← count жив, хотя MakeCounter уже завершился

var other = MakeCounter();       // своё замыкание, свой count
Console.WriteLine(other());      // 1

Что окажется на консоли

1
2
1

Где что лежит при захвате — разобрано в главе 1. Здесь важен вывод: лямбда с захватом — это лишний объект в куче на каждое создание. В горячем цикле это заметно, а лямбда без захвата ничего не аллоцирует: компилятор кэширует её делегат в статическом поле.

Классическая ловушка: у цикла for переменная одна на все итерации, поэтому все лямбды видят её последнее значение:

var actions = new List<Action>();

for (int i = 0; i < 3; i++)
    actions.Add(() => Console.WriteLine(i));   // ✘ все три захватили ОДНУ переменную i

foreach (var a in actions) a();

Что окажется на консоли

3
3
3
for (int i = 0; i < 3; i++)
{
    int copy = i;                                // ✔ копия внутри тела — у каждой лямбды своя
    actions.Add(() => Console.WriteLine(copy));
}

Теперь печатается 0 1 2. У foreach такой проблемы нет с C# 5: переменная создаётся заново на каждой итерации. И ещё: начиная с C# 9 лямбду можно пометить static — тогда захват запрещён и компилятор не даст случайно «притащить» переменную в кучу: static x => x * 2.

Мультикаст: несколько методов в одном делегате

Делегат может хранить не один метод, а список. += дописывает метод в конец списка, -= убирает, а вызов обходит всех по очереди:

Action<string> log = Console.WriteLine;
Action<string> toError = s => Console.Error.WriteLine($"[err] {s}");   // в переменной — чтобы потом снять
log += toError;
log += s => Console.WriteLine($"[file] {s}");

log("готово");       // один вызов — три метода
log -= toError;      // сняли подписку, осталось два
log("ещё");

Что окажется на консоли (порядок — как подписывались)

готово
[err] готово
[file] готово
ещё
[file] ещё
Почему лямбду нельзя «отписать»

-= ищет в списке тот же самый делегат. Лямбда, написанная в коде второй раз, — это новый объект, поэтому log -= s => … ничего не снимет. Отсюда правило: если подписка когда-нибудь будет сниматься, обработчик хранят в поле или переменной (как toError выше). Именно на этом ломается отписка в Dispose.

Две ловушки, которые сразу видно на этом примере:

// 1) возвращается значение ПОСЛЕДНЕГО делегата, остальные результаты теряются
Func<int> f = () => 1;
f += () => 2;
Console.WriteLine(f());     // 2, а не 3 и не «оба»

// 2) исключение в середине списка обрывает остальные вызовы
Action a = () => throw new InvalidOperationException("первый");
a += () => Console.WriteLine("второй");
a();                        // «второй» уже НЕ выполнится

Что окажется на консоли (вторая часть)

2
Unhandled exception. System.InvalidOperationException: первый
   at Program.<<Main>$>b__0_0() in /app/Program.cs:line 7
   at System.Action.Invoke()
   at Program.<Main>$(String[] args) in /app/Program.cs:line 9

Поэтому мультикаст берут там, где нужен «веер уведомлений» (события), а не «вычислить результат»: для результата нужен один делегат.

Событие: делегат, который нельзя дёрнуть снаружи

Событие — это поле-делегат с замком: снаружи разрешены только += и -=, а вызвать (Invoke) может лишь сам класс-издатель. Объявляется словом event:

public sealed class Order
{
    public decimal Total { get; init; }

    // EventHandler<decimal> = void (object? sender, decimal total)
    public event EventHandler<decimal>? Paid;

    public void Pay()
    {
        Console.WriteLine($"списываем {Total}");
        Paid?.Invoke(this, Total);      // this → sender, Total → total
    }                                   // ?. — если подписчиков нет, ничего не падает
}
var order = new Order { Total = 1500m };

order.Paid += (sender, total) => Console.WriteLine($"[письмо] оплачен заказ на {total}");
order.Paid += (sender, total) => Console.WriteLine($"[склад] зарезервировать товары");
order.Paid += (_, total) => Console.WriteLine($"[аналитика] +1 оплата на {total}");

order.Pay();

// order.Paid = null;        // ✘ CS0070: снаружи только += и -=
// order.Paid.Invoke(…);     // ✘ CS0070: поднять событие может только сам Order

Что окажется на консоли

списываем 1500
[письмо] оплачен заказ на 1500
[склад] зарезервировать товары
[аналитика] +1 оплата на 1500

Три вещи, которые здесь стоит проговорить явно:

  • Параметры (sender, total) объявлены в самой лямбде, а значения им передаёт Invoke в момент события. sender — это this, то есть сам заказ: в обработчике его можно проверить через if (sender is Order o).
  • ?.Invoke вместо Invoke — потому что поле-делегат равно null, пока нет ни одного подписчика: без ? был бы NullReferenceException на первом же вызове.
  • Порядок вызовов = порядок подписки, но полагаться на это нельзя: подписчики — чужая зона ответственности (в книге «Паттерны в .NET», глава 8, это отдельная ловушка).

Второй параметр вовсе не обязан быть decimal: если данных несколько, берут свой класс или record и EventHandler<OrderPaid>. Но помните: тип T в EventHandler<T> по соглашению наследуют от EventArgs только в старом коде — современный .NET это не требует.

event против списка обработчиков за интерфейсом

Событие удобно внутри процесса: оно синхронное, дёшевое и не требует DI. Но у него нет async, его нельзя получить из контейнера и трудно подменить в тесте. Поэтому в прикладном коде чаще пишут IEnumerable<IHandler> и регистрируют обработчики в DI — сравнение и примеры: «Паттерны в .NET», глава 8.

Лямбда, локальная функция или обычный метод

Одно и то же поведение в C# можно записать четырьмя способами. Разница не «в стиле», а в том, что сгенерирует компилятор:

ФормаКак выглядитКогда брать

Лямбдаnums.Where(n => n > 0)Короткая логика «здесь и сейчас», LINQ, подписки без отписки

static int SumPositive(List<int> nums)
{
    int total = 0;

    void Add(int n) => total += n;        // локальная функция: тоже захватывает total

    foreach (var n in nums)
        if (n > 0) Add(n);

    return total;
}

Console.WriteLine(SumPositive(new List<int> { -2, 5, 0, 7 }));   // 12

Что окажется на консоли

12

Локальная функция дешевле лямбды в одном важном случае: если её не превращать в делегат, она остаётся обычным методом (иногда даже без замыкания — захваченные переменные передаются параметрами). Как только вы написали Action a = Add; — создаётся делегат, и разница исчезает.

public sealed class PriceView : IDisposable
{
    private readonly PriceCache _cache;                      // singleton: живёт всё приложение
    private readonly EventHandler<decimal> _onInvalidated;   // ← храним, чтобы было чем отписаться

    public PriceView(PriceCache cache)
    {
        _cache = cache;
        _onInvalidated = (_, price) => Render(price);
        _cache.Invalidated += _onInvalidated;
    }

    public void Dispose() => _cache.Invalidated -= _onInvalidated;   // без этой строки PriceView жив вечно
    private void Render(decimal price) { /* перерисовать цену */ }
}

★ Что запомнить из главы
  • Делегат — тип, значением которого является метод. Func<…> и Action<…> покрывают почти всё, свой делегат нужен редко.
  • Лямбда — метод без имени: параметры объявлены в ней самой, типы берутся из целевого делегата, а значения приходят в момент вызова (Invoke), а не при подписке.
  • Захват переменной = объект в куче. Переменная цикла for одна на все итерации — копируйте её внутрь тела; static-лямбда запрещает захват.
  • += — это мультикаст: возвращается результат последнего делегата, а исключение в середине списка обрывает остальные вызовы.
  • event = делегат + инкапсуляция: снаружи только += и -=, поднимает событие только владелец и почти всегда через ?.Invoke.
  • Отписывайтесь и держите делегат в поле, если подписка снимается; для async-реакций берите список обработчиков за интерфейсом, а не event («Паттерны в .NET», глава 8).
