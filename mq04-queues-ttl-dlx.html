Глава 4. Очереди, TTL, dead-letter и повторная обработка

Что переживает перезапуск, как отложить сообщение и куда девать то, что не обработалось

основная глава

Параметры очереди: durable, exclusive, autoDelete

Имя очереди — не единственное, что её определяет. Три флага решают её судьбу:

ФлагЧто означаетТипичное применение
durable: trueОчередь переживает перезапуск брокераРабочие очереди, события
durable: falseПосле перезапуска исчезает вместе с сообщениями Временные, тестовые очереди
exclusive: trueДоступна только создавшему соединению и удаляется при его закрытииОтветная очередь для RPC одного клиента
autoDelete: trueУдаляется, когда от неё отписался последний потребитель Временные подписки, reply-очереди

Проверено на перезапуске брокера. До рестарта было семь очередей, после — две:

# до:  rabbitmqctl list_queues name durable messages
q.durable       true    2
q.transient     false   2
orders.new      true    0
q.dlq           false   1
q.ttl           false   0
q.payments      false   0
q.requeue       false   0

# после рестарта:
q.durable       true    0      <- очередь выжила, сообщения — нет
orders.new      true    0

Два вывода, и второй важнее первого:

  • Не-durable очереди исчезли вместе с сообщениями: q.transient, q.ttl, q.dlq, q.payments, q.requeue.
  • У q.durable пропали сообщения, хотя очередь выжила. Причина: они были отправлены без Persistent = true. Очередь durable и сообщение persistent — это два разных флага, и нужны оба.
Минимальный набор для «переживает перезапуск»

durable: true у очереди + Persistent = true у сообщения + публикация с подтверждением (глава 2). Если убрать любой из трёх — сообщение можно потерять, и вы об этом не узнаете.

TTL: когда сообщение устаревает

Время жизни задаётся у самого сообщения свойством Expiration (в миллисекундах, строкой) или у очереди аргументом x-message-ttl. Проверено: сообщение с Expiration = "1000" в очереди без потребителей через две секунды исчезло:

await ch.QueueDeclareAsync("q.ttl", durable: false, exclusive: false, autoDelete: false);

var props = new BasicProperties { Expiration = "1000", ContentType = "application/json" };
await ch.BasicPublishAsync("", "q.ttl", mandatory: false, basicProperties: props,
                           body: Encoding.UTF8.GetBytes("{\"id\":8}"));

await Task.Delay(2000);

var passive = await ch.QueueDeclarePassiveAsync("q.ttl");
var got     = await ch.BasicGetAsync("q.ttl", autoAck: true);
Console.WriteLine($"messages={passive.MessageCount} get={(got is null ? "null" : "…")}");

// messages=0 get=null

Зачем это нужно: сообщение, которое пролежало в очереди час, обычно уже бессмысленно — заказ отменён, цена изменилась. TTL превращает «вечно растущую очередь» в «очередь с осмысленным горизонтом».

Dead-letter: куда девать неудачное

Dead-letter exchange (DLX) — это «перенаправление на отказ». Очереди указывают, куда отправлять сообщение, если:

  • потребитель ответил BasicNack(requeue: false) или BasicReject(requeue: false);
  • истёк TTL сообщения или очереди;
  • сообщение не поместилось в очередь из-за лимита длины.
// 1) обменник для «отказных» сообщений и очередь для них
await ch.ExchangeDeclareAsync("ex.dlx", ExchangeType.Fanout, durable: false, autoDelete: false);
await ch.QueueDeclareAsync("q.dlq", durable: false, exclusive: false, autoDelete: false);
await ch.QueueBindAsync("q.dlq", "ex.dlx", routingKey: "");

// 2) рабочая очередь знает, куда отправлять отказы
var queueArgs = new Dictionary<string, object?> { ["x-dead-letter-exchange"] = "ex.dlx" };
await ch.QueueDeclareAsync("q.payments", durable: false, exclusive: false, autoDelete: false,
                           arguments: queueArgs);

// 3) сообщение и отказ без возврата в очередь
await ch.BasicPublishAsync("", "q.payments", Encoding.UTF8.GetBytes("{\"id\":7}"));

consumer.ReceivedAsync += async (_, ea) =>
{
    await ch.BasicNackAsync(ea.DeliveryTag, multiple: false, requeue: false);
};
payments got {"id":7}, nack(requeue: false)
after nack: payments=0 dlq=1

Сообщение ушло из рабочей очереди и появилось в q.dlq. Дальше с ним можно делать что угодно: разбирать вручную, отправлять в архив или возвращать в работу по расписанию.

DLX не «копирует», а переносит

После срабатывания DLX сообщение существует только в очереди-приёмнике: в исходной очереди его больше нет. Поэтому dead-letter очередь — это место разбора, а не дубликат.

Retry: отложить и попробовать снова

Классическая схема повторной обработки в RabbitMQ строится на двух вещах: DLX и TTL. Рабочая очередь отправляет отказы не сразу в DLQ, а в «очередь задержки», у которой нет потребителей и стоит x-message-ttl; когда TTL истекает, сообщение по DLX возвращается в рабочую очередь.

q.orders ──nack──▶ ex.retry ──▶ q.orders.retry (x-message-ttl = 5s, без потребителей)
                                   │  истёк TTL
                                   ▼
                                ex.dlx ──▶ q.orders   (снова в работу)

после N попыток: q.orders ──nack──▶ ex.failed ──▶ q.orders.failed (DLQ для разбора)
  • Номер попытки хранят в заголовке (x-attempts) или в теле; по нему решают, вернуть сообщение в рабочую очередь или отправить в DLQ.
  • Задержка — это и есть TTL: 5 секунд, 30 секунд, 5 минут — на каждую ступень своя очередь с x-message-ttl. Так проще, чем хранить срок в каждом сообщении: TTL очереди действует на всё, что в неё попало.
  • Без DLQ цикл не заканчивается: «отравленное» сообщение будет возвращаться вечно (глава 3).
★ Что запомнить из главы
  • Durable-очередь и persistent-сообщение — разные флаги. Проверено: очередь пережила перезапуск, а её сообщения без Persistent = true — нет.
  • TTL ограничивает возраст сообщения: свойство Expiration или x-message-ttl у очереди.
  • DLX переносит сообщение в другую очередь при nack(requeue: false), истечении TTL или переполнении; это место разбора, а не копия.
  • Retry = DLX + TTL: очередь задержки без потребителей возвращает сообщение в работу; после N попыток — в DLQ.
  • Без DLQ «отравленное» сообщение крутится вечно и занимает потребителей.
