Глава 4. Очереди, TTL, dead-letter и повторная обработка

Что переживает перезапуск, как отложить сообщение и куда девать то, что не обработалось

основная глава

Параметры очереди: durable, exclusive, autoDelete

Имя очереди — не единственное, что её определяет. Три флага решают её судьбу:

ФлагЧто означаетТипичное применение
durable: trueОчередь переживает перезапуск брокераРабочие очереди, события
durable: falseПосле перезапуска исчезает вместе с сообщениями Временные, тестовые очереди
exclusive: trueДоступна только создавшему соединению и удаляется при его закрытииОтветная очередь для RPC одного клиента
autoDelete: trueУдаляется, когда от неё отписался последний потребитель Временные подписки, reply-очереди

Проверено на перезапуске брокера. До рестарта было семь очередей, после — две:

# колонки: name — имя очереди, durable — переживёт ли рестарт, messages — сколько сообщений лежит
# до рестарта:
q.durable       true    2       # durable-очередь, 2 сообщения
q.transient     false   2       # не-durable: исчезнет вместе с сообщениями
orders.new      true    0       # durable, пустая
q.dlq           false   1
q.ttl           false   0
q.payments      false   0
q.requeue       false   0

# после рестарта брокера:
q.durable       true    0       <- очередь выжила, сообщения — нет: их публиковали без Persistent
orders.new      true    0

Два вывода, и второй важнее первого:

  • Не-durable очереди исчезли вместе с сообщениями: q.transient, q.ttl, q.dlq, q.payments, q.requeue.
  • У q.durable пропали сообщения, хотя очередь выжила. Причина: они были отправлены без Persistent = true. Очередь durable и сообщение persistent — это два разных флага, и нужны оба.
Минимальный набор для «переживает перезапуск»

durable: true у очереди + Persistent = true у сообщения + публикация с подтверждением (глава 2). Если убрать любой из трёх — сообщение можно потерять, и вы об этом не узнаете.

У третьего пункта есть название, но это не флаг сообщения: режим называется publisher confirms (подтверждения публикации), а канал, на котором он включён, — confirm-канал. Включается он не у сообщения, а у канала: CreateChannelOptions(publisherConfirmationsEnabled: true, publisherConfirmationTrackingEnabled: true) — тогда BasicPublishAsync ждёт ответа брокера. Поэтому durable/Persistent — это свойства (очереди и сообщения), а publisher confirms — режим канала, и у самого сообщения такого свойства нет.

TTL: когда сообщение устаревает

Время жизни задаётся у самого сообщения свойством Expiration (в миллисекундах, строкой) или у очереди аргументом x-message-ttl. Проверено: сообщение с Expiration = "1000" в очереди без потребителей через две секунды исчезло:

await ch.QueueDeclareAsync("q.ttl", durable: false, exclusive: false, autoDelete: false); // очередь без потребителей

var props = new BasicProperties { Expiration = "1000", ContentType = "application/json" }; // TTL 1000 мс — строкой
await ch.BasicPublishAsync("", "q.ttl", mandatory: false, basicProperties: props,        // в очередь через default exchange
                           body: Encoding.UTF8.GetBytes("{\"id\":8}"));                  // тело сообщения

await Task.Delay(2000);                                    // ждём дольше TTL: две секунды против одной

var passive = await ch.QueueDeclarePassiveAsync("q.ttl");  // passive: спросить очередь, не создавая её
var got     = await ch.BasicGetAsync("q.ttl", autoAck: true); // забрать одно сообщение, сразу подтвердив
Console.WriteLine($"messages={passive.MessageCount} get={(got is null ? "null" : "…")}"); // messages=0 get=null

// messages=0 get=null

Что означает каждый элемент:

ЭлементЧто означает
Expiration = "1000"TTL сообщения в миллисекундах. В AMQP это строковое поле, поэтому число берут в кавычки. Нет свойства — сообщение не устаревает
x-message-ttlто же самое, но как аргумент очереди: применяется ко всем сообщениям, которые в неё попали. Задаётся в arguments при объявлении
Task.Delay(2000)пауза, чтобы TTL успел истечь: 2000 мс больше, чем 1000 мс
QueueDeclarePassiveAsyncpassive-проверка: очередь не создаётся, а возвращается её состояние — MessageCount и ConsumerCount
BasicGetAsync(queue, autoAck: true)синхронно забрать одно сообщение; autoAck: true — сразу подтвердить. Если сообщений нет, вернётся null

Зачем это нужно: сообщение, которое пролежало в очереди час, обычно уже бессмысленно — заказ отменён, цена изменилась. TTL превращает «вечно растущую очередь» в «очередь с осмысленным горизонтом».

Dead-letter: куда девать неудачное

Dead-letter exchange (DLX) — это «перенаправление на отказ». Очереди указывают, куда отправлять сообщение, если:

  • потребитель ответил BasicNack(requeue: false) или BasicReject(requeue: false);
  • истёк TTL сообщения или очереди;
  • сообщение не поместилось в очередь из-за лимита длины.
// 1) обменник для «отказных» сообщений и очередь для них
await ch.ExchangeDeclareAsync("ex.dlx", ExchangeType.Fanout, durable: false, autoDelete: false); // fanout: отдаст всем привязанным
await ch.QueueDeclareAsync("q.dlq", durable: false, exclusive: false, autoDelete: false);       // очередь разбора
await ch.QueueBindAsync("q.dlq", "ex.dlx", routingKey: "");                                     // у fanout ключ не важен

// 2) рабочая очередь знает, куда отправлять отказы
var queueArgs = new Dictionary<string, object?> { ["x-dead-letter-exchange"] = "ex.dlx" };      // аргумент очереди
await ch.QueueDeclareAsync("q.payments", durable: false, exclusive: false, autoDelete: false,   // рабочая очередь
                           arguments: queueArgs);                                                // со ссылкой на DLX

// 3) сообщение и отказ без возврата в очередь
await ch.BasicPublishAsync("", "q.payments", Encoding.UTF8.GetBytes("{\"id\":7}"));             // кладём в рабочую очередь

var paymentsConsumer = new AsyncEventingBasicConsumer(ch);                                       // отдельный подписчик для рабочей очереди
paymentsConsumer.ReceivedAsync += async (_, ea) =>                                              // обработчик (см. главу 3)
{
    await ch.BasicNackAsync(ea.DeliveryTag, multiple: false, requeue: false);                    // false: не в очередь, а в DLX
};
await ch.BasicConsumeAsync("q.payments", autoAck: false, paymentsConsumer);                      // подписка на рабочую очередь
payments got {"id":7}, nack(requeue: false)
after nack: payments=0 dlq=1

Сообщение ушло из рабочей очереди и появилось в q.dlq. Дальше с ним можно делать что угодно: разбирать вручную, отправлять в архив или возвращать в работу по расписанию.

Аргументы очереди, которые управляют этим механизмом:

АргументЧто означает
x-dead-letter-exchangeимя обменника, куда перенаправлять «мёртвое» сообщение. Без него nack(requeue: false) просто удалит сообщение
x-dead-letter-routing-keyс каким routing key отправлять в DLX; если не задан — сохраняется исходный ключ сообщения
x-message-ttlTTL всех сообщений очереди: истёк — сообщение уходит в DLX
x-max-lengthлимит числа сообщений в очереди: вытесненные тоже уходят в DLX
DLX не «копирует», а переносит

После срабатывания DLX сообщение существует только в очереди-приёмнике: в исходной очереди его больше нет. Поэтому dead-letter очередь — это место разбора, а не дубликат.

Retry: отложить и попробовать снова

Классическая схема повторной обработки в RabbitMQ строится на двух вещах: DLX и TTL. Рабочая очередь отправляет отказы не сразу в DLQ, а в «очередь задержки», у которой нет потребителей и стоит x-message-ttl; когда TTL истекает, сообщение по DLX возвращается в рабочую очередь.

q.orders ──nack──▶ ex.retry ──▶ q.orders.retry (x-message-ttl = 5s, без потребителей)
                                   │  истёк TTL
                                   ▼
                                ex.dlx ──▶ q.orders   (снова в работу)

после N попыток: q.orders ──nack──▶ ex.failed ──▶ q.orders.failed (DLQ для разбора)

По шагам:

  1. Отказ. Обработчик отвечает nack, и рабочая очередь отправляет сообщение в свой x-dead-letter-exchange — ex.retry.
  2. Задержка. Сообщение лежит в q.orders.retry, у которой нет потребителей; x-message-ttl = 5s отсчитывает время.
  3. Возврат. По истечении TTL сообщение «умирает» и уходит в DLX уже этой очереди — ex.dlx, а он кладёт его обратно в q.orders.
  4. Лимит попыток. Если в заголовке x-attempts уже N, обработчик отправляет сообщение в ex.failed вместо ex.retry — и оно остаётся в q.orders.failed для разбора.
  • Номер попытки хранят в заголовке (x-attempts) или в теле; по нему решают, вернуть сообщение в рабочую очередь или отправить в DLQ.
  • Задержка — это и есть TTL: 5 секунд, 30 секунд, 5 минут — на каждую ступень своя очередь с x-message-ttl. Так проще, чем хранить срок в каждом сообщении: TTL очереди действует на всё, что в неё попало.
  • Без DLQ цикл не заканчивается: «отравленное» сообщение будет возвращаться вечно (глава 3).
★ Что запомнить из главы
  • Durable-очередь и persistent-сообщение — разные флаги. Проверено: очередь пережила перезапуск, а её сообщения без Persistent = true — нет.
  • TTL ограничивает возраст сообщения: свойство Expiration или x-message-ttl у очереди.
  • DLX переносит сообщение в другую очередь при nack(requeue: false), истечении TTL или переполнении; это место разбора, а не копия.
  • Retry = DLX + TTL: очередь задержки без потребителей возвращает сообщение в работу; после N попыток — в DLQ.
  • Без DLQ «отравленное» сообщение крутится вечно и занимает потребителей.
