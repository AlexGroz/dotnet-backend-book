Глава 8. Коллекции: generic против non-generic

Почему List<int> лучше ArrayList, что такое generic и как выбрать коллекцию под задачу.

основная глава

Что такое generic

Generic («обобщённый тип») — это тип с параметром типа. Вы пишете List<T>, а при использовании подставляете конкретный тип: List<int>, List<Order>. Компилятор подставляет тип-аргумент и создаёт «специализацию», поэтому знает точный тип элементов. Как выглядит сама подстановка и что из неё получается в рантайме — в разделе «<T> в объявлении и конкретный тип в использовании».

// generic: тип элемента известен компилятору
var numbers = new List<int>();
numbers.Add(42);
int first = numbers[0];        // никаких приведений

// non-generic: хранит object, тип «стирается»
var legacy = new ArrayList();
legacy.Add(42);                // 42 упаковывается в object
int old = (int)legacy[0];      // приведение вручную

Отсюда три выгоды generic-коллекций, и все три — про надёжность и скорость:

  1. Нет упаковки для значимых типов: List<int> хранит int, а ArrayList — object, то есть каждый элемент упаковывается (глава 4).
  2. Нет приведений при чтении: тип известен, приведение не нужно.
  3. Ошибки видно на компиляции, а не в рантайме.
// ✘ non-generic: компилятор пропустит, упадёт в рантайме
var list = new ArrayList();
list.Add(1);
list.Add("два");                    // никто не запретил
int sum = 0;
foreach (object item in list)
    sum += (int)item;               // InvalidCastException на "два"

// ✔ generic: не скомпилируется — и это хорошо
var list2 = new List<int>();
list2.Add("два");                   // ошибка компиляции

<T> в объявлении и конкретный тип в использовании

Выше сказано: «пишете List<T>, а подставляете List<int>». Разберём это буквально — где стоит T, что появляется вместо него и кто это делает. Возьмём свой generic-класс: с List<T> происходит ровно то же самое, просто его объявление написано в BCL, а не у вас в файле.

1. Объявление: T — параметр типа, «местозаполнитель»

public sealed class Box<T>                       // ← T здесь ещё не тип, а имя для него
{
    private readonly List<T> _items = new();      // T стоит вместо типа элемента
    public void Add(T item) => _items.Add(item);   // T — тип параметра
    public T Get(int index) => _items[index];      // T — тип результата
}

2. Использование: вместо T подставлен конкретный тип

var ints = new Box<int>();      // компилятор подставил T = int
ints.Add(42);
int x = ints.Get(0);            // Get вернул int — как будто так и было написано

var names = new Box<string>();  // другой закрытый тип: T = string
names.Add("Аня");
string s = names.Get(0);
// names.Add(42);               // ✘ CS1503: cannot convert from 'int' to 'string'

Что именно делает компилятор. Он подставляет тип-аргумент во все места, где в объявлении стоял T, и получает закрытый (constructed) generic type — Box<int>, Box<string>. Это обычные типы: у Box<int> методы выглядят как void Add(int item) и int Get(int index), никаких приведений и упаковок нет. Проверка типов идёт на этой подстановке — поэтому names.Add(42) не компилируется, а не падает в рантайме. Типы, где параметр ещё не подставлен (Box<>, List<>), называют открытыми (generic type definition).

Что компилятор знает о T: new T(), default и ограничения

Разбирая тело generic-метода, компилятор знает о T только то, что записано в его ограничениях (where). Ограничений нет — известно ровно одно: это некоторый тип, значения которого совместимы с object. Не «класс», не «структура», не «что-то с конструктором» — ничего из этого.

Поэтому всё решает один вопрос: есть ли у T то, что мы собираемся вызвать? Начнём с конструктора.

Есть ли у T конструктор без параметров — неизвестно. У int он есть, у класса без объявленных конструкторов появляется сам, а у класса с public NoCtor(int x) его нет вовсе. Предполагать «повезёт» компилятор не имеет права, поэтому new T() запрещён — и текст ошибки говорит именно об этом:

public static T Make<T>() => new T();   // ✘ без ограничения new()

Что скажет компилятор (CS0304)

error CS0304: Cannot create an instance of the variable type 'T' because it does not
have the new() constraint

Читать её надо буквально: «не хватает ограничения new()». Это не «T — не класс», а «вы не пообещали, что конструктор есть». Обещание даётся в объявлении — и та же строка компилируется:

static T Make<T>() where T : new() => new T();        // ✔ конструктор гарантирован
static T MakeStruct<T>() where T : struct => new T();  // ✔ struct гарантирует его сам

Console.WriteLine(Make<int>());          // 0    — у int конструктор без параметров есть
Console.WriteLine(Make<Point>() is not null);   // True — у Point он неявный
Console.WriteLine(MakeStruct<Guid>());   // 00000000-0000-0000-0000-000000000000

Проверка «повезло или нет» идёт в момент подстановки: подставить тип без подходящего конструктора просто нельзя.

public sealed class NoCtor { public NoCtor(int x) { } }   // без конструктора по умолчанию
var p = Make<NoCtor>();                                   // ✘

Что скажет компилятор (CS0310)

error CS0310: 'NoCtor' must be a non-abstract type with a public parameterless
constructor in order to use it as parameter 'T' in the generic type or method
'Make<T>()'

Альтернатива, которая компилируется, но хуже. Activator.CreateInstance<T>() ограничения не требует — он ищет конструктор в рантайме, рефлексией. Ошибка не исчезает, она просто переезжает из сборки в прод:

try { Activator.CreateInstance<NoCtor>(); }
catch (Exception e) { Console.WriteLine(e.GetType().Name + ": " + e.Message); }

Вывод

MissingMethodException: Cannot dynamically create an instance of type 'NoCtor'.
Reason: No parameterless constructor defined.

Ограничение же переносит проверку на этап компиляции и стоит ноль в рантайме: JIT вызывает конструктор напрямую, без поиска через рефлексию.

Второй вопрос: а что вообще можно сделать с T, если вызвать у него нечего? Тут компилятор спокоен: default определён для любого типа — у значимых это нули, у ссылочных null. Поэтому default(T) (он же default) разрешён без ограничений:

static T Zero<T>() => default!;                    // ✔ ограничения не нужны

Console.WriteLine(Zero<int>());                    // 0
Console.WriteLine(Zero<string>() ?? "<null>");      // <null>
Console.WriteLine(Zero<DateTime>().ToString("yyyy-MM-dd"));   // 0001-01-01
Console.WriteLine(Zero<int?>() is null);           // True

Заодно про ! в конце строки: это оператор «я знаю, что тут возможен null, не предупреждай» (null-forgiving). Без него компилятор скажет warning CS8603: Possible null reference return — ведь для string результат default и есть null. Полный разбор оператора — глава 20.

А оператора + у «любого типа» нет — и ошибка ровно та же по смыслу, что и с конструктором:

static T Add<T>(T a, T b) => a + b;   // ✘

Что скажет компилятор (CS0019)

error CS0019: Operator '+' cannot be applied to operands of type 'T' and 'T'

Лечится так же — ограничением; с C# 11 для арифметики есть INumber<T> (generic math):

static T Sum<T>(T a, T b) where T : INumber<T> => a + b;   // using System.Numerics

Console.WriteLine(Sum(1, 2));        // 3   — T = int
Console.WriteLine(Sum(1.5, 2.5));    // 4   — T = double

Что будет, если подставить не число? Компилятор откажется — но разными ошибками, и различать их полезно: у структуры (bool) не хватает упаковочного преобразования, у класса (string) — ссылочного:

Sum(true, false);      // ✘ bool   — не число
Sum("a", "b");         // ✘ string — не число
Sum(1, "a");           // ✘ а тут даже T не выводится: аргументы разных типов

Вывод компилятора — три разных кода

error CS0315: The type 'bool' cannot be used as type parameter 'T' in the generic type
or method 'Demo.Sum<T>(T, T)'. There is no boxing conversion from 'bool' to
'System.Numerics.INumber<bool>'.

error CS0311: The type 'string' cannot be used as type parameter 'T' in the generic type
or method 'Demo.Sum<T>(T, T)'. There is no implicit reference conversion from 'string'
to 'System.Numerics.INumber<string>'.

error CS0411: The type arguments for method 'Demo.Sum<T>(T, T)' cannot be inferred from
the usage. Try specifying the type arguments explicitly.

И ключевая разница, которую видно на соседнем Max: bool и string проходят ограничение IComparable<T> (у обоих есть порядок), но не проходят INumber<T> (арифметики у них нет):

Про char — это не опечатка: Sum('a', 'b') компилируется и возвращает char с кодом 195 (97 + 98), то есть Ã. Арифметика над char в C# — это арифметика над кодом символа, и generic math её разрешает.

Это только те ограничения, которые нужны, чтобы читать код. Все виды where, T? и notnull, вариантность in/out и generic math — в главе 9; сортировка и IComparable<T> — в главе 10; рефлексия, которой Activator ищет конструктор, — в главе 22.

И последнее в этом блоке — про открытый тип. Объект List<> создать нельзя: подставлять нечего. А new List<T>() — можно, если T объявлен в текущем методе или классе: это уже не определение типа, а «список, тип элементов которого подставит вызывающий».

var raw = new List<>();          // ✘ открытый (unbound) тип — создать не из чего

static void Fill<T>()
{
    var list = new List<T>();      // ✔ T — параметр типа, подставится при вызове
    Console.WriteLine(list.Count);                             // 0
    Console.WriteLine(typeof(List<T>).IsGenericTypeDefinition); // False
    Console.WriteLine(typeof(List<>).IsGenericTypeDefinition);  // True
}

Fill<int>();       // внутри: List<int>
Fill<string>();    // внутри: List<string>

Вывод

0
False
True

Разница ровно в одном: List<> — определение типа, у него нет ни одного аргумента, поэтому объект создать не из чего. List<T> внутри generic-кода — сконструированный тип, где роль аргумента играет параметр типа: он годится для new, для полей, для typeof и для возвращаемого значения — а конкретным он станет в момент подстановки.

error CS7003: Unexpected use of an unbound generic name

Специализация: что из этого получается в рантайме

В .NET тип-аргумент не стирается: он часть типа и лежит в метаданных, поэтому List<int> — настоящий, отдельный тип. Это видно одним typeof:

Console.WriteLine(typeof(List<>));        // открытый
Console.WriteLine(typeof(List<int>));     // закрытый
Console.WriteLine(typeof(List<string>));
Console.WriteLine(typeof(Box<int>) == typeof(Box<string>));    // это разные типы?
Console.WriteLine(typeof(Box<int>) == typeof(Box<int>));       // а это тот же самый?
Console.WriteLine(typeof(Box<int>).GetGenericArguments()[0]);  // что подставлено

Реальный вывод (net8.0)

System.Collections.Generic.List`1[T]
System.Collections.Generic.List`1[System.Int32]
System.Collections.Generic.List`1[System.String]
False
True
System.Int32

List`1 — так тип записан в метаданных: обратная кавычка и число параметров типа. [T] означает «параметр не подставлен», [System.Int32] — подставлен. Отсюда термин reification: обобщение в .NET «овеществлено», тип-аргумент существует в рантайме. В Java его, для сравнения, стирают (erasure), и List<int> там не отличить от List<string>.

Про «специализацию» из первого абзаца — это про машинный код, который генерирует JIT:

  • Значимые типы — отдельный код на каждую подстановку: List<int> и List<long> — разные специализации, внутри массив нужного размера, элементы лежат без упаковки.
  • Ссылочные типы — код общий: все ссылки одного размера, поэтому List<string> и List<object> исполняют один и тот же скомпилированный код и различаются только объектом Type.
Зачем это знать на практике

Любой <T> в вашем коде — такая же подстановка: IRepository<Order>, IOptions<MySettings>, Task<decimal>. Отсюда три бытовых вывода: generic по значимым типам даёт больше кода в образе (не заводите десяток разных числовых аргументов), по ссылочным почти бесплатен, а DI и рефлексия видят настоящий тип-аргумент и умеют различать по нему регистрации (IOptions<A> и IOptions<B> — разные сервисы).

<T> у метода: вывод типа из аргументов

Параметр типа бывает не только у класса. У метода его часто даже не пишут руками — компилятор выводит подстановку из аргументов:

public static T Max<T>(T a, T b) where T : IComparable<T>
    => a.CompareTo(b) >= 0 ? a : b;

var m1 = Max(3, 5);           // T выведен из аргументов: int → и результат int
var m2 = Max("a", "b");       // T = string: строки сравнимы со строками → "b"
var m3 = Max(true, false);    // T = bool:   false < true → True
var m4 = Max<double>(3, 5);   // T указан явно: double

Console.WriteLine($"{m1} {m2} {m3} {m4}");   // 5 b True 5

Вывод

5 b True 5

А вот object не подходит: у него нет CompareTo, и ограничение это ловит.

var bad = Max<object>(1, 2);      // ✘

Что скажет компилятор (CS0311)

error CS0311: The type 'object' cannot be used as type parameter 'T' in the generic type
or method 'Demo.Max<T>(T, T)'. There is no implicit reference conversion from 'object'
to 'System.IComparable<object>'.

where T : IComparable<T> — ограничение (constraint). Оно говорит компилятору, что у T точно есть CompareTo: без него a.CompareTo(b) не скомпилируется, ведь о параметре типа известно только то, что это значение, совместимое с object. Ограничения проверяются в момент подстановки — поэтому Max<object> отвергается компилятором, а не падает в рантайме.

Интерфейсы коллекций: что возвращать из методов

IReadOnlyCollection<T>Перечисление + CountЧтение набора

ICollection<T>, IList<T>Добавление, удаление, индексаторКогда вызывающий действительно должен менять коллекцию

// ✔ ХОРОШО: возвращаем интерфейс «только для чтения».
// Вызывающему хватает перечисления, Count и индексатора,
// но изменить нашу коллекцию он не сможет.
public IReadOnlyList<OrderRow> GetPage(int page) { … }

var page1 = service.GetPage(1);
foreach (var row in page1) Console.WriteLine(row.Total);   // ✔ читать можно
Console.WriteLine(page1.Count);                            // ✔ размер известен
// page1.Add(…)                                            // ✘ метода нет — данные защищены

// ✘ ПЛОХО: вернули List<T> — кто угодно может менять внутренние данные
public List<OrderRow> GetPageBad(int page) { … }

// параметр: если внутри только читаем — достаточно IEnumerable<T>
public decimal Sum(IEnumerable<OrderRow> rows) => rows.Sum(r => r.Total);

Правило простое: возвращайте самый узкий интерфейс, которого хватает вызывающему. Ему нужно только пройти по элементам — IEnumerable<T>; нужен размер — IReadOnlyCollection<T>; нужен ещё и индекс — IReadOnlyList<T>. Чем уже контракт, тем меньше способов случайно испортить данные.

Как выбрать коллекцию

КоллекцияЧто хорошоЧто дорого
List<T>Индекс O(1), добавление в конец амортизированно O(1)Вставка/удаление в середине O(n)
Dictionary<TKey, TValue>Поиск/вставка/удаление по ключу ~O(1)Нет порядка; нужен хороший GetHashCode
HashSet<T>«Есть ли элемент» ~O(1), пересеченияНет индексов и порядка
SortedSet<T>То же плюс порядок: Min/Max, диапазон через GetViewBetweenO(log n) на операцию вместо ~O(1)
Queue<T> / Stack<T>FIFO / LIFO за O(1)Нет доступа к произвольному элементу
LinkedList<T> (глава 14)Вставка/удаление по узлу O(1)Плохая локальность памяти, нет индексов
SortedDictionary<TKey,TValue>Всегда отсортировано, O(log n)Медленнее Dictionary
ConcurrentDictionary, ConcurrentQueueБезопасны для нескольких потоковДороже обычных из-за синхронизации

«Нет порядка» — не приговор. HashSet<T> порядок не хранит вообще: это хеш-таблица. Сортированное множество — отдельный тип: SortedSet<T> (красно-чёрное дерево, O(log n) на операцию; зато доступны Min/Max и диапазон через GetViewBetween, а перебор идёт по возрастанию). Для «заполнили один раз и только читаем» есть ImmutableSortedSet<T> (неизменяемый и отсортированный) и FrozenSet<T> (.NET 8: самый быстрый на чтение, но порядок не гарантирует).

Правило выбора

Сформулируйте операцию, которая выполняется чаще всего. Поиск по ключу → Dictionary. Проверка уникальности → HashSet, а если нужен ещё и порядок по значению → SortedSet. Обход в порядке добавления → List. Очередь задач → Queue/Channel. Остальное — редкость.

Ёмкость и рост

List<T> внутри — массив. Когда он заполняется, создаётся новый (обычно вдвое больше) и элементы копируются. Если размер известен заранее, этого можно избежать:

var list = new List<Order>(capacity: 10_000);   // сразу нужный массив
list.EnsureCapacity(20_000);                    // заранее расширить

var dict = new Dictionary<int, Order>(capacity: 10_000);   // меньше перестроений
А если элементов окажется больше?

Ничего страшного: ёмкость — не лимит, а подсказка. Когда внутренний массив заполнится, список создаст новый (обычно вдвое больше), скопирует туда элементы и продолжит работу. Ошибки «переполнения» не будет — вы просто заплатите за копирование.

var list = new List<int>(capacity: 2);    // «на два элемента»
list.AddRange(new[] { 1, 2, 3, 4, 5 });   // ✔ работает: список вырос сам
Console.WriteLine(list.Count);            // 5
Console.WriteLine(list.Capacity);         // 8 — вырос (обычно удвоением)

Поэтому ёмкость указывают не «чтобы поместилось», а чтобы не копировать зря: при известном размере (10 000) вы избегаете десятка промежуточных расширений и копирований.

foreach и скрытая аллокация

  • List<T> в конкретном типе — энумератор это struct, аллокации нет.
  • Через интерфейс IEnumerable<T> — энумератор упаковывается в object: аллокация на каждый цикл.
  • LINQ (Where, Select) — создаёт объекты-итераторы; на горячем пути лучше один явный цикл или Span.
// ✔ без упаковки: foreach по List<T> использует struct-энумератор
foreach (var order in list) { … }

// ✘ параметр объявлен как IEnumerable<T> — энумератор будет упакован
void Print(IEnumerable<Order> orders)
{
    foreach (var order in orders) { … }
}
★ Что запомнить из главы
  • Generic — тип с параметром типа: компилятор знает точный тип элементов.
  • List<T> — открытый тип (форма), List<int> — закрытый: подстановку делает компилятор, ошибки типов видны на ней же; new T() без ограничения new() не собрать (CS0304), открытый тип создать нельзя (CS7003).
  • В рантайме тип-аргумент сохраняется (typeof(List<int>) — настоящий тип, reification): JIT делает отдельный код на каждый значимый тип и общий — на ссылочные.
  • Generic-коллекции дают отсутствие упаковки, отсутствие приведений и ошибки на компиляции.
  • Возвращайте самый узкий интерфейс, которого хватает вызывающему — обычно IReadOnlyList<T> или IEnumerable<T>: нужные операции есть, а менять ваши данные нельзя.
  • Коллекцию выбирают по главной операции: поиск → Dictionary, уникальность → HashSet, порядок → List.
  • Задавайте ёмкость, если размер известен; помните, что перечисление через интерфейс упаковывает энумератор.
