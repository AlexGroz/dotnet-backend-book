Глава 3. Время жизни ключа: TTL, EX/PX и истечение

Что именно истекает, какие бывают сроки, как они задаются из C# и почему обычная перезапись ключа их сбрасывает

основная глава

В главе 2 TTL появился как третий параметр вызова: SET user:1:name … EX 2 — «и это значение умрёт само через 2 секунды». Дальше TTL используется везде: в кэше (глава 5), в локах, в лимитах, в эксплуатации (глава 6). Поэтому разберём его отдельно и до конца: без этого «5 минут» в коде — просто число, скопированное у соседа.

Что такое TTL

TTL (time to live, «время жизни») — это свойство самого ключа, а не значения внутри него. Ключ с TTL существует до указанного момента; когда срок истёк, Redis считает ключ отсутствующим, а память под ним освобождает. Ничего «помечать» и «чистить» приложению не нужно — это единственный механизм, который убирает данные без чьей-либо команды.

Посмотреть срок можно двумя командами, и они отличаются только единицами:

# TTL — сколько секунд осталось жить; PTTL — то же в миллисекундах
docker exec redis7 redis-cli set user:1:name Алексей EX 2
# OK
docker exec redis7 redis-cli ttl user:1:name
# 2
docker exec redis7 redis-cli pttl user:1:name
# 1881      ← вторая команда выполнилась на ~120 мс позже первой

Кроме числа у этих команд есть два специальных ответа, которые нужно узнавать сразу:

Ответ TTLЧто значитЧто делать
-2ключа нет (не было, удалили или истёк) это нормальный промах кэша, а не ошибка
-1ключ есть, но TTL у него нет — он будет жить, пока его не удалятдля кэша это обычно ошибка: такой ключ никто не уберёт
0жить осталось меньше секунды. Ключ ещё жив не путать с «истёк»: PTTL покажет, скажем, 385
Положительное числостолько секунд (или миллисекунд для PTTL) осталось —
TTL и KeyTimeToLiveAsync отвечают по-разному

В redis-cli «нет ключа» и «нет TTL» — это -2 и -1. В StackExchange.Redis метод KeyTimeToLiveAsync возвращает TimeSpan? и в обоих случаях даёт null: различить «ключа нет» и «срок не задан» им нельзя. Если различие важно, проверяйте KeyExistsAsync отдельно или берите сырое значение: (long)await db.ExecuteAsync("TTL", key).

Как задать срок: команды

Способов несколько, и они отличаются не «синтаксисом», а смыслом: срок можно задать вместе с записью значения или отдельной командой, а отсчитывать — от текущего момента или от конкретной даты.

КомандаЧто делаетКогда удобна
SET k v EX 300записать значение и срок 300 с обычная запись кэша

SET k v EXAT 1730000000
SET k v PXAT 1730000000123		 срок — конкретный момент (unix-время, с или мс) «умрёт в 12:00», а не «через 5 минут»

Из StackExchange.Redis это выглядит короче, чем кажется: срок — просто параметр. Что именно уходит на провод, видно в MONITOR — это реальный перехват вызовов клиента 2.8.58:

# что печатает redis-cli monitor, пока выполняется C#-код
"SETEX" "m1" "100" "v"          ← StringSetAsync("m1", "v", TimeSpan.FromSeconds(100))
"PSETEX" "m2" "500" "v"         ← StringSetAsync("m2", "v", TimeSpan.FromMilliseconds(500))
"EXPIRE" "m1" "30"              ← KeyExpireAsync("m1", TimeSpan.FromSeconds(30))
"PEXPIREAT" "a1" "1794912759009" ← KeyExpireAsync("a1", DateTime.UtcNow.AddMinutes(3))
"PTTL" "a1"                     ← KeyTimeToLiveAsync("a1")
"SET" "lk" "w1" "EX" "10" "NX"  ← StringSetAsync("lk", "w1", TimeSpan…, When.NotExists)

Два вывода из этого перехвата. Первый: клиент сам выбирает команду — целые секунды уходят как SETEX/EX 10, миллисекунды как PSETEX, а если нужен NX, то SET … EX … NX (у SETEX такого флага нет). Второй: отдельной перегрузки StringSetAsync с DateTime в 2.8.58 нет — попытка даёт ошибку компиляции CS1503: cannot convert from 'System.DateTime' to 'System.TimeSpan?'; абсолютный срок ставят через KeyExpireAsync(key, DateTime).

Срок — у ключа, а не у типа данных

TTL не связан со строкой: его можно повесить на хеш, список, множество, sorted set, поток. Ниже — реальный прогон, показывающий сразу всё поведение: как читать срок, как его ставить и снимать, и что бывает с ключом после истечения. Вспомогательная функция Ttl нужна только для того, чтобы null печатался словом, а не пустой строкой:

static string Ttl(TimeSpan? t) => t?.ToString() ?? "null";

// «ключа нет» и «срок не задан» — разные ответы в Redis
Console.WriteLine(await db.ExecuteAsync("TTL", "nope"));            // -2
await db.StringSetAsync("k", "v");                                  // SET k v
Console.WriteLine(await db.ExecuteAsync("TTL", "k"));               // -1
Console.WriteLine(Ttl(await db.KeyTimeToLiveAsync("k")));           // null

// относительный срок: клиент отправит SETEX k 100 v
await db.StringSetAsync("k", "v", TimeSpan.FromSeconds(100));
Console.WriteLine(Ttl(await db.KeyTimeToLiveAsync("k")));           // 00:01:39.9990000

// ОБЫЧНАЯ перезапись без срока его сбрасывает
await db.StringSetAsync("k", "v2");                                 // SET k v2
Console.WriteLine(Ttl(await db.KeyTimeToLiveAsync("k")));           // null

// KEEPTTL — перезапись с сохранением прежнего срока
await db.StringSetAsync("k", "v3", TimeSpan.FromSeconds(100));      // SETEX k 100 v3
await db.ExecuteAsync("SET", "k", "v4", "KEEPTTL");                 // SET k v4 KEEPTTL
Console.WriteLine(Ttl(await db.KeyTimeToLiveAsync("k")));           // 00:01:39.9990000

// поставить и снять срок отдельными командами
await db.StringSetAsync("k", "v5");
Console.WriteLine(await db.KeyExpireAsync("k", TimeSpan.FromSeconds(30)));   // True   (EXPIRE k 30)
Console.WriteLine(Ttl(await db.KeyTimeToLiveAsync("k")));           // 00:00:29.9990000
Console.WriteLine(await db.KeyPersistAsync("k"));                   // True   (PERSIST k)
Console.WriteLine(Ttl(await db.KeyTimeToLiveAsync("k")));           // null
Console.WriteLine(await db.KeyPersistAsync("k"));                   // False  — снимать уже нечего

// миллисекунды: TTL округляет вниз, PTTL — нет
await db.StringSetAsync("ms", "v", TimeSpan.FromMilliseconds(500));  // PSETEX ms 500 v
Console.WriteLine($"{await db.ExecuteAsync("PTTL", "ms")} {await db.ExecuteAsync("TTL", "ms")}");
// 499 0

// срок живёт на ключе любого типа; новые поля хеша его не сбрасывают
await db.HashSetAsync("h", "f1", "v");
await db.KeyExpireAsync("h", TimeSpan.FromSeconds(50));
await db.HashSetAsync("h", "f2", "v");
Console.WriteLine($"{await db.KeyTypeAsync("h")} {Ttl(await db.KeyTimeToLiveAsync("h"))}");
// Hash 00:00:49.9960000

// GETEX — прочитать значение и обновить срок одним обращением
db.StringSet("g", "v");
Console.WriteLine($"{await db.ExecuteAsync("GETEX", "g", "EX", 20)} {Ttl(await db.KeyTimeToLiveAsync("g"))}");
// v 00:00:20

// абсолютный срок: клиент отправит PEXPIREAT abs <мс>
await db.StringSetAsync("abs", "v");
Console.WriteLine(await db.KeyExpireAsync("abs", DateTime.UtcNow.AddMinutes(3)));   // True
Console.WriteLine(Ttl(await db.KeyTimeToLiveAsync("abs")));         // 00:02:59.9980000

// истёкший ключ для клиента просто не существует
await db.StringSetAsync("gone", "v", TimeSpan.FromMilliseconds(200));
await Task.Delay(400);
Console.WriteLine($"{await db.KeyExistsAsync("gone")} {Ttl(await db.KeyTimeToLiveAsync("gone"))} {await db.ExecuteAsync("TTL", "gone")}");
// False null -2

Из этого прогона следуют три вещи, которые чаще всего и ломают кэш:

  • Перезапись значения без срока убивает TTL. SET k v2 — и ключ снова «вечный»: в кэше это значит, что после первого же обновления данные останутся навсегда. Если значение обновляют, а срок хотят сохранить, нужен KEEPTTL.
  • Изменение содержимого срок не сбрасывает. HSET нового поля в хеш, INCR счётчика, LPUSH в список — TTL остаётся прежним (в прогоне: хеш после второго HSET всё ещё 49.996). Это удобно: счётчик с TTL не «продлевается» каждым инкрементом.
  • PERSIST возвращает false, если снимать нечего. Это не ошибка: так же, как DEL отсутствующего ключа.

Как именно происходит истечение

Redis не заводит «будильник» на каждый ключ: держать таймер на миллион ключей дороже, чем сами данные. Работают два механизма вместе:

  • Ленивое истечение: когда команда обращается к ключу, сервер проверяет его срок. Если срок прошёл — ключ считается отсутствующим прямо в этот момент: GET вернул nil, EXISTS — 0, TTL — -2.
  • Активный цикл: несколько раз в секунду (по умолчанию hz 10) сервер порциями просматривает словарь ключей со сроком и удаляет истёкшие — чтобы они не висели в памяти до первого обращения.

Проверка «второго механизма» без единого обращения к ключам — 2000 ключей со сроком 120 мс, потом ожидание:

# 2000 команд SET exp:N v PX 120 — одной пачкой через pipe
python3 -c "print('\r\n'.join(f'SET exp:{i} v PX 120' for i in range(2000)))" > /tmp/exp.txt
docker exec -i redis7 sh -c 'redis-cli --pipe' < /tmp/exp.txt
# errors: 0, replies: 2000

docker exec redis7 redis-cli dbsize
# 2000                                   ← сразу после записи ключи ещё на месте
docker exec redis7 redis-cli info stats | grep expired_keys
# expired_keys:0

sleep 1.5        # ни одной команды к самим ключам не посылаем

docker exec redis7 redis-cli dbsize
# 0                                      ← ключей нет
docker exec redis7 redis-cli info stats | grep expired_keys
# expired_keys:2000                      ← их удалил фоновый цикл

Следствия, важные на практике:

  • Истечение — не мгновенное событие, а процесс. В момент TTL ключ уже недоступен для команд, но память под него освобождается чуть позже. Поэтому INFO stats и DBSIZE могут «не сходиться» с ожиданием — это нормально.
  • expired_keys — счётчик именно истечений, отдельно от evicted_keys (вытеснение при maxmemory, глава 6). Рост первого — норма, рост второго — сигнал, что памяти не хватает.
  • Память освобождается не всегда сразу: флаг lazyfree-lazy-expire по умолчанию no, то есть большой ключ удаляется синхронно в момент истечения. Для ключей на сотни мегабайт это заметная пауза, и флаг включают.

Три вида срока и когда какой брать

«TTL 300» можно понимать трояко, и разница проявляется именно в кэше:

ВидКак задатьСмыслКогда брать
Относительный SET … EX 300, SETEX,
TimeSpan в StringSetAsync		 «300 секунд с момента записи» обычный кэш: чем свежее записали, тем дольше живёт
Абсолютный SET … EXAT, EXPIREAT,
KeyExpireAsync(key, DateTime)		 «умрёт в 12:00», независимо от того, когда записали данные с известным дедлайном: прогноз, расписание, «до конца дня»
Скользящий GETEX … EX 300 или EXPIRE при каждом чтении; в IDistributedCache — SlidingExpiration «300 секунд с последнего чтения» сессии: пока человек активен, данные живут

Скользящий срок — единственный, который меняет поведение при чтении, и у него есть цена: «горячий» ключ, который читают чаще, чем раз в 5 минут, не истечёт никогда. Если данные при этом устарели, кэш будет отдавать устаревшее бесконечно — об этом уже сказано в главе 5 про IDistributedCache.

Абсолютный срок и DateTime: Kind обязан быть Utc или Local

KeyExpireAsync(key, DateTime) не принимает «время без зоны». Если у значения Kind = Unspecified (так ведёт себя new DateTime(2026, 11, 17, 16, 0, 0)), клиент бросает System.ArgumentException: Expiry time must be either Utc or Local (Parameter 'when') — проверено. А вот Utc и Local обрабатываются правильно: для DateTime.UtcNow.AddMinutes(3) и DateTime.Now.AddMinutes(3) TTL получился 00:02:59.995 и 00:02:59.986 — локальное время клиент приводит к UTC сам.

Сколько ставить: как выбирать TTL

Универсального числа нет, но есть три вопроса, которые дают ответ почти всегда:

  1. Насколько устаревшие данные допустимы? Если показать цену, которая изменилась минуту назад, — это нормально, TTL в минутах. Если это баланс или остаток на складе — минуты недопустимы, и основную работу делает инвалидация при записи (глава 5), а TTL только страхует.
  2. Сколько стоит промах? Запрос в PostgreSQL за 5 мс — можно ставить срок коротко. Вызов внешнего API за 800 мс с лимитом запросов — срок ставят длиннее, потому что промах дорогой.
  3. Сколько памяти это съест? Время жизни умножается на скорость записи: 1000 ключей в секунду с TTL в час — это 3,6 млн ключей одновременно (глава 6, eviction).

Стартовые значения, с которых обычно начинают (их меняют по результатам измерений, а не копируют вслепую):

Что кэшируем / для чего срокСтартовый TTLПочему так
Ответ API, страница, список30–300 с устаревание на минуты допустимо, промах дешёвый
Справочник, каталог5–60 мин + сброс при записи меняется редко, но «навсегда» кэшировать нельзя
Профиль пользователя1–5 мин + сброс при записи пользователь ждёт своих изменений сразу
Сессия20–30 мин, скользящий пока человек активен, сессия живёт
Одноразовый код (OTP)3–5 минсрок — часть бизнес-правила
Ключ идемпотентности запросачасы–сутки столько живёт окно повторной доставки
Распределённый лок5–30 с страховка, если владелец умер, не сняв лок (глава 5)
Окно лимита запросовровно окно: 60 с элементы старше окна не должны учитываться
Данные, которые не должны протухатьTTL нет это уже не кэш, а хранилище

Два правила, которые важнее конкретных цифр:

  • TTL — страховка, а не замена инвалидации. Кэш обязан сбрасываться при изменении данных; TTL лишь гарантирует, что забытая инвалидация не превратится в вечное вранье.
  • Один ключ — один срок. Если у части данных требования разные (цена меняется чаще описания), это разные ключи, а не один с общим TTL.

TTL и память: истечение — это не вытеснение

Эти два механизма часто путают, хотя они делают разное:

Истечение (expiration)Вытеснение (eviction)
Кто решаетвы, задавая TTLRedis, когда упёрся в maxmemory
Когда срабатываеткогда прошёл срок ключакогда не хватает памяти, даже если срок ещё не вышел
Счётчик в INFO statsexpired_keys evicted_keys
Что значит для приложениянормальная работа кэша данные пропали раньше срока: рабочих ключей больше, чем памяти

Практический вывод: TTL не спасает от нехватки памяти. Если записывать быстрее, чем истекает, объём растёт, и при maxmemory Redis начнёт вытеснять ключи по политике (allkeys-lru и другие — глава 6). TTL уменьшает объём, но не ограничивает его.

TTL у полей хеша

Исторически срок был только у ключа целиком. В Redis 7.4 появились команды для полей: HEXPIRE/HPEXPIRE, а INFO keyspace показывает счётчик subexpiry (проверено в главе 6: hexpire на одном поле → subexpiry=1). Это удобно для «хеш на пользователя, у каждого поля свой срок», но по умолчанию проектируют всё же «один ключ — один TTL»: меньше сюрпризов и работает на любой версии.

★ Что запомнить из главы
  • TTL — свойство ключа, а не значения: срок можно повесить на любой тип, и по истечении ключ для команд просто перестаёт существовать.
  • -2 — ключа нет, -1 — срока нет, 0 — меньше секунды до конца. В KeyTimeToLiveAsync первые два случая неразличимы: оба null.
  • Перезапись без KEEPTTL сбрасывает срок, а HSET, INCR, RENAME его сохраняют.
  • Истечение ленивое + фоновый цикл (hz 10): ключ недоступен сразу, а память освобождается чуть позже; expired_keys — счётчик этого процесса.
  • Относительный, абсолютный и скользящий срок — три разных инструмента: кэш, дедлайн, сессия.
  • TTL не заменяет инвалидацию и не ограничивает память: он уменьшает объём и страхует от забытых сбросов, а от maxmemory защищает eviction (глава 6).
