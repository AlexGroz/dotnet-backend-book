Глава 31. Типы, синтаксис и план миграции

Завершаем часть про миграцию: маппинг типов, замена функций и синтаксиса, а также порядок работ — «как это делали по шагам».

«Можно смело брать text вместо varchar?» — да, с одной оговоркой

В PostgreSQL text и varchar — один и тот же способ хранения: оба переменной длины, строка занимает «столько, сколько нужно» плюс маленький заголовок. Никакого «резерва под 255 символов» нет. Разница ровно одна: у varchar(n) есть проверка длины.

textvarchar(n)char(n)
Место на дискепо фактупо факту (n — не резерв)всегда n, добивается пробелами
Ограничение длинынет (технический предел — 1 ГБ)n; при превышении — ошибка 22001 value too longn + пробелы
Скорость, индексы, план запросаидентичны — планировщик не различает эти типы по стоимостимедленнее: пробелы участвуют в сравнениях
Когда выбиратьпо умолчанию для строккогда лимит — бизнес-правило («код страны = 2»)почти никогда (наследие Oracle)
-- эти два объявления эквивалентны по хранению и скорости
CREATE TABLE t1 (name text);
CREATE TABLE t2 (name varchar);              -- varchar без (n) — это буквально text

-- а это — text + проверка длины (то же, что varchar(100), но лимит можно менять отдельно)
CREATE TABLE t3 (name text CONSTRAINT name_len CHECK (length(name) <= 100));

Когда всё-таки varchar(n):

  • ограничение — часть модели данных, и вы хотите, чтобы база отвергала «слишком длинное» значение сама (код региона, ISO-код валюты, ИНН);
  • миграция из Oracle: VARCHAR2(4000) → varchar(4000) сохраняет привычную семантику и ловит те же ошибки;
  • внешний контракт (интеграция, чужой API) явно ограничивает длину.

Когда text: во всех остальных случаях — имена, адреса, комментарии, JSON-фрагменты, произвольный пользовательский ввод. Лимит, если он нужен, ставят CHECK (length(x) <= n): его можно изменить одной командой, не меняя тип колонки.

  • Про «изменить длину»: в varchar(n) увеличение n в PostgreSQL 9.2+ — операция только по каталогу (таблица не перезаписывается), а уменьшение требует проверки всех строк. С text + CHECK таких операций с типом вообще нет.
  • Про «без ограничений»: предел всё же есть — 1 ГБ на значение. Длинные значения (обычно больше ~2 КБ) PostgreSQL автоматически выносит в отдельное хранилище TOAST и сжимает; это работает одинаково для text и varchar, поэтому «text медленнее на больших строках» — миф.
  • Единственная реальная ловушка: длинную строку нельзя положить в обычный B-tree индекс — есть лимит на размер записи индекса (≈2704 байта). Это ограничение не типа, а индекса: для длинных значений индексируют префикс (left(x, 200)) или хеш (md5(x)), либо используют hash-индекс.
  • Осторожно с char(n): он дополняет значение пробелами до n, из-за чего сравнения и length() ведут себя неожиданно. Из Oracle его почти всегда надо переводить в text/varchar, а не в char.

Ещё несколько «коварных» мест

  • Регистр идентификаторов: Oracle хранит имена в верхнем регистре, PostgreSQL приводит к нижнему — код с именами в кавычках может «не найти» объект.
  • Порядок NULL при сортировке: по умолчанию похож, но лучше указывать NULLS LAST/FIRST явно.
  • Автокоммит DDL: в Oracle DDL фиксируется сам, в PostgreSQL — часть транзакции; это меняет логику скриптов миграции.
  • Неявные преобразования: в PostgreSQL строже — часть «магии» Oracle просто не скомпилируется (что скорее хорошо: ошибки видны сразу).

План миграции: как делали по шагам

  1. Инвентаризация. Переписать все объекты БД: таблицы, представления, индексы, последовательности, триггеры, пакеты/процедуры/функции, задания, внешние связи.
  2. Маппинг типов и конвертация схемы. Oracle-типы → PostgreSQL (особенно DATE → timestamp, NUMBER → numeric/bigint).
  3. Конвертация PL/SQL. Пакеты → схемы с функциями (глава 30); автономные транзакции → dblink или смена архитектуры; функции/триггеры → PL/pgSQL. Часть — автоматической конвертацией, часть — вручную.
  4. Миграция данных. Перенос, setval для последовательностей, проверка объёмов и контрольных сумм.
  5. Тесты эквивалентности. Одни и те же запросы/отчёты прогоняли на Oracle и PostgreSQL и сравнивали результаты. Это ловило и ''-vs-NULL, и порядок NULL, и ошибки в ROWNUM-логике.
  6. Сравнение производительности. Планы и замеры на сопоставимых объёмах данных (часть IV–V); подгонка индексов и статистики.
  7. Настройка PostgreSQL. autovacuum, work_mem, random_page_cost под SSD, сбор статистики, мониторинг (глава 33).
  8. Поэтапное переключение с возможностью отката.
★ Готовый ответ по Вопросу о миграции (сжато)

«MVCC в обеих СУБД даёт главное: читатели не блокируют писателей. Различие — где хранятся прошлые версии: в Oracle — в undo (снимок по SCN), в PostgreSQL — прямо в страницах таблиц (xmin/xmax), а старые версии убирает VACUUM; отсюда bloat, важность autovacuum и влияние долгих транзакций. По блокировкам: изменение — на уровне строки, чтение никого не блокирует, но DDL в PostgreSQL конфликтует с чтениями — поэтому используем CREATE INDEX CONCURRENTLY и retry на сериализационные ошибки. По конвертации труднее всего дались: '' ≠ NULL, отсутствие PACKAGE (группировали в схемы) и автономных транзакций (dblink или вынос логов из транзакции), а также DATE, который в Oracle содержит время. Плюс массовая замена NVL/DECODE/ROWNUM/ (+)/CONNECT BY».

Что подчеркнуть про свой опыт

Миграция — это не «перенести данные», а перенести поведение: типы, семантику NULL, логику в коде БД и производительность. Тесты эквивалентности и замеры — в центре процесса: только так ловятся «тихие» расхождения.
