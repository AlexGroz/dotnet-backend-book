Ещё несколько «коварных» мест

  • Регистр идентификаторов: Oracle хранит имена в верхнем регистре, PostgreSQL приводит к нижнему — код с именами в кавычках может «не найти» объект.
  • Порядок NULL при сортировке: по умолчанию похож, но лучше указывать NULLS LAST/FIRST явно.
  • Автокоммит DDL: в Oracle DDL фиксируется сам, в PostgreSQL — часть транзакции; это меняет логику скриптов миграции.
  • Неявные преобразования: в PostgreSQL строже — часть «магии» Oracle просто не скомпилируется (что скорее хорошо: ошибки видны сразу).

План миграции: как делали по шагам

  1. Инвентаризация. Переписать все объекты БД: таблицы, представления, индексы, последовательности, триггеры, пакеты/процедуры/функции, задания, внешние связи.
  2. Маппинг типов и конвертация схемы. Oracle-типы → PostgreSQL (особенно DATE → timestamp, NUMBER → numeric/bigint).
  3. Конвертация PL/SQL. Пакеты → схемы с функциями (глава 30); автономные транзакции → dblink или смена архитектуры; функции/триггеры → PL/pgSQL. Часть — автоматической конвертацией, часть — вручную.
  4. Миграция данных. Перенос, setval для последовательностей, проверка объёмов и контрольных сумм.
  5. Тесты эквивалентности. Одни и те же запросы/отчёты прогоняли на Oracle и PostgreSQL и сравнивали результаты. Это ловило и ''-vs-NULL, и порядок NULL, и ошибки в ROWNUM-логике.
  6. Сравнение производительности. Планы и замеры на сопоставимых объёмах данных (часть IV–V); подгонка индексов и статистики.
  7. Настройка PostgreSQL. autovacuum, work_mem, random_page_cost под SSD, сбор статистики, мониторинг (глава 33).
  8. Поэтапное переключение с возможностью отката.
★ Готовый ответ по Вопросу о миграции (сжато)

«MVCC в обеих СУБД даёт главное: читатели не блокируют писателей. Различие — где хранятся прошлые версии: в Oracle — в undo (снимок по SCN), в PostgreSQL — прямо в страницах таблиц (xmin/xmax), а старые версии убирает VACUUM; отсюда bloat, важность autovacuum и влияние долгих транзакций. По блокировкам: изменение — на уровне строки, чтение никого не блокирует, но DDL в PostgreSQL конфликтует с чтениями — поэтому используем CREATE INDEX CONCURRENTLY и retry на сериализационные ошибки. По конвертации труднее всего дались: '' ≠ NULL, отсутствие PACKAGE (группировали в схемы) и автономных транзакций (dblink или вынос логов из транзакции), а также DATE, который в Oracle содержит время. Плюс массовая замена NVL/DECODE/ROWNUM/ (+)/CONNECT BY».

Что подчеркнуть про свой опыт

Миграция — это не «перенести данные», а перенести поведение: типы, семантику NULL, логику в коде БД и производительность. Тесты эквивалентности и замеры — в центре процесса: только так ловятся «тихие» расхождения.
