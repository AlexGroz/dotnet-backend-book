Глава 6. IEnumerable, yield и IAsyncEnumerable

Что значит «по чему-то можно пройти в foreach», откуда берётся отложенное выполнение LINQ и зачем понадобился IAsyncEnumerable.

основная глава

Идея: не «коллекция», а «умение выдавать элементы»

IEnumerable<T> — это контракт: «я умею выдавать элементы по одному». Ему не важно, что у вас внутри — массив, список, результат запроса к базе или бесконечная последовательность. Методу достаточно этого контракта, чтобы пройти по данным.

Работают два интерфейса в паре:

  • IEnumerable<T> — «источник»: умеет создать курсор (GetEnumerator()).
  • IEnumerator<T> — «курсор»: MoveNext() (есть ли следующий), Current (текущий), Dispose() (освободить ресурсы).
// orders — это ЛЮБОЙ IEnumerable: List, массив, результат LINQ
IEnumerable<Order> orders = new List<Order> { new() { Id = 1 }, new() { Id = 2 } };

// то, что делает foreach, — примерно так:
IEnumerator<Order> e = orders.GetEnumerator();
try
{
    while (e.MoveNext())
    {
        Order current = e.Current;
        Console.WriteLine(current.Id);
    }
}
finally
{
    e.Dispose();               // важно: освобождает ресурсы (файл, соединение, курсор БД)
}
Кто здесь кто
  • orders — IEnumerable<Order>: это «источник», у него есть метод GetEnumerator().
  • e — IEnumerator<Order>: это «курсор», у него есть MoveNext() и Current.
  • Один источник создаёт сколько угодно курсоров: поэтому по одному и тому же IEnumerable можно пройти несколько раз — каждый раз с новым GetEnumerator().
Зачем Dispose в перечислении

Источником может быть не массив, а файл или результат запроса к БД: у него есть ресурсы. Поэтому foreach всегда вызывает Dispose, даже если внутри было исключение.

Свой итератор: yield return

Писать класс с MoveNext вручную не нужно: компилятор делает это за вас, если метод содержит yield return.

static IEnumerable<int> EvenNumbers(int limit)
{
    for (int i = 0; i <= limit; i += 2)
        yield return i;             // «выдать значение и запомнить, где остановились»
}

foreach (var n in EvenNumbers(6))
    Console.WriteLine(n);           // 0, 2, 4, 6

Компилятор превращает такой метод в машину состояний: она хранит текущую позицию и продолжает работу с того места, где остановилась. Отсюда два следствия:

  • Ленивость: код внутри итератора выполняется не при вызове метода, а при каждом MoveNext().
  • Бесконечные последовательности возможны: while (true) yield return … — пока вызывающий не остановится.

Отложенное выполнение LINQ

Where, Select, OrderBy ничего не выполняют в момент вызова — они строят описание запроса. Работа начинается при перечислении:

var query = numbers
    .Where(n => { Console.WriteLine($"проверяю {n}"); return n % 2 == 0; });

Console.WriteLine("запрос построен");       // ни одной проверки ещё не было

foreach (var n in query) { }                // вот теперь пошли проверки

В EF Core это же свойство означает: запрос к базе выполняется при перечислении, а не при сборке LINQ. Пока вы не начали перечислять (или не вызвали ToList/First), SQL не отправлен.

Главная ловушка: многократное перечисление

Каждое перечисление IEnumerable может заново выполнить работу. Для LINQ-to-Objects это лишние вычисления, для EF Core — повторные SQL-запросы. Если последовательность нужна дважды, материализуйте её: var list = query.ToList().

Ещё три бытовые ловушки

  • Count() против Any(). Вопрос «есть ли хоть один элемент?» — это Any(): он останавливается на первом же. Count() > 0 на «чистом» IEnumerable<T> вынужден пройти все элементы, чтобы их посчитать. Исключение — если коллекция реализует ICollection<T>: у неё есть свойство Count (не метод), и оно возвращает число мгновенно.
  • Изменение коллекции во время перечисления — InvalidOperationException. Нужно менять — сначала соберите список изменений, потом применяйте.
  • using внутри итератора: ресурс освободится, когда вызывающий вызовет Dispose у энумератора (то есть выйдет из foreach или прервёт перечисление).
static IEnumerable<string> ReadLines(string path)
{
    using var reader = new StreamReader(path);   // файл закроется при Dispose
    string? line;
    while ((line = reader.ReadLine()) is not null)
        yield return line;
}

// ✔ foreach гарантирует Dispose — файл не «утечёт»
foreach (var line in ReadLines("log.txt")) { … }

IEnumerable, ICollection, IList: кто что умеет

ИнтерфейсВозможностиКогда достаточен
IEnumerable<T>Только перечисление«Мне нужно пройти по элементам»
ICollection<T>+ Count, Add, RemoveНужен размер или изменение
IList<T>+ индексаторНужен доступ по номеру
IReadOnlyList<T>Индексатор и Count, без измененияРезультат выборки «только для чтения»

Практический смысл: IEnumerable<T> ничего не обещает про размер и повторяемость. Если вы принимаете его как параметр, не вызывайте Count несколько раз и не перечисляйте дважды, не сказав об этом в документации.

IAsyncEnumerable<T>: перечисление с ожиданием

Обычный IEnumerable<T> синхронный: чтобы получить следующий элемент, поток ждёт (например, пока база вернёт порцию строк). На сервере это то же самое, что блокирующий вызов — мы уже знаем, чем это плохо (глава 9 .NET-раздела).

IAsyncEnumerable<T> — тот же «контракт выдачи элементов», но MoveNext асинхронный:

// источник: итератор, который может ждать
public async IAsyncEnumerable<OrderRow> StreamAsync(
    [EnumeratorCancellation] CancellationToken ct = default)
{
    await foreach (var order in db.Orders.AsAsyncEnumerable().WithCancellation(ct))
    {
        yield return Map(order);          // отдаём по одному, не загружая всё в память
    }
}

// потребитель
await foreach (var row in StreamAsync(ct))
    await WriteAsync(row, ct);
  • await foreach — аналог foreach, но каждый шаг может ждать, не занимая поток.
  • yield return работает и в async-итераторах (C# 8+).
  • [EnumeratorCancellation] нужен, чтобы токен отмены передавался в итератор (иначе компилятор предупредит).
Почему не Task<IEnumerable<T>>

Task<IEnumerable<T>> означает «подожди, пока весь результат будет готов, и получи последовательность». Для потока из базы или файла это плохо: всё окажется в памяти до начала обработки. IAsyncEnumerable<T> отдаёт элементы по мере появления — это и есть потоковая обработка (backpressure обсуждается в главе 13 .NET-раздела).

// ✘ сначала всё в память, потом обработка
Task<List<OrderRow>> GetAllAsync();

// ✔ элементы приходят по одному
IAsyncEnumerable<OrderRow> StreamAsync(CancellationToken ct);

IQueryable<T>: тот же LINQ, но для базы

Рядом с IEnumerable<T> всегда стоит IQueryable<T> — и их постоянно путают. Разница в одном: где выполняется работа.

IEnumerable<T>IQueryable<T>
Где выполняетсяВ памяти, обычный C#-кодВ базе: провайдер переводит LINQ в SQL
Когда «данные»Уже загружены (или генерируются)Это ещё описание запроса
WhereФильтрует то, что уже в памятиДобавляет WHERE в SQL
Кто умеет продолжать запросКто угодно, но в памятиТолько тот, у кого есть провайдер
 
IEnumerable<Order> inMemory = list.Where(o => o.Total > 100);      // фильтр выполнится сразу, в памяти
IQueryable<Order>   inDb     = db.Orders.Where(o => o.Total > 100);  // фильтр уйдёт в SQL как WHERE
Почему IQueryable не отдают наружу

IQueryable — это «недоделанный запрос». Тот, кто его получил, может добавить условия, и SQL изменится. Пример, который ломает план:

// репозиторий отдал IQueryable («вызывающий может собрать любой SQL»)
public IQueryable<Order> Query() => db.Orders;

// сервис «дописал» условие — и индекс по created_at больше не работает
var bad = repo.Query().Where(o => o.CreatedAt.Year == 2026).ToList();
// в SQL превратится в date_part('year', created_at) = 2026 → Seq Scan

// ✔ наружу — только готовый результат или «безопасный» интерфейс
public Task<List<Order>> GetForYearAsync(int year, CancellationToken ct) =>
    db.Orders.Where(o => o.CreatedAt >= new DateTime(year, 1, 1, 0, 0, 0, DateTimeKind.Utc)
                      && o.CreatedAt < new DateTime(year + 1, 1, 1, 0, 0, 0, DateTimeKind.Utc))
             .ToListAsync(ct);

То же самое с Include, AsNoTracking и пагинацией: их «доклеивают» снаружи, и никто уже не отвечает за итоговый запрос. Подробно — .NET-книга, глава 24 (EF Core), и SQL-раздел про планы.

★ Что запомнить из главы
  • IEnumerable<T> — это контракт «выдаю элементы по одному», а не «коллекция»; за него отвечает IEnumerator<T> с MoveNext/Current.
  • foreach всегда вызывает Dispose — поэтому итератор может держать файл или соединение.
  • yield return превращает метод в машину состояний: код выполняется по мере перечисления.
  • LINQ ленив: запрос выполняется при перечислении. Поэтому повторное перечисление — это повторная работа (в EF Core — повторный SQL).
  • IAsyncEnumerable<T> + await foreach — потоковая выдача без блокировки потока; Task<IEnumerable<T>> этого не даёт.
