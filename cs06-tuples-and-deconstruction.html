Глава 6. Кортежи: (bool ok, int half) и деконструкция

Кортеж — это несколько значений, склеенных в одно, без объявления класса. Им возвращают «второй результат» из метода, им же разбирают результат на части одной строкой. Внутри — обычная структура ValueTuple, поэтому аллокаций нет, а имена элементов существуют только до компиляции.

основная глава

В главе 5 был out: метод «дописывает» значение в вашу переменную. Это работает, но выглядит странно, когда результатов два-три и они равноправны:

static bool TryHalf(int v, out int half)      // глава 5: out
{
    half = v / 2;
    return v % 2 == 0;
}

static (bool ok, int half) TryHalfTuple(int v) // глава 6: кортеж
    => (v % 2 == 0, v / 2);

Вторая строка делает то же самое, но результат — одно значение из двух элементов. Его можно вернуть, присвоить, передать дальше, положить в List или в Dictionary и разобрать на части. Дальше — что это за тип, как он устроен и где ломается.

Что такое кортеж

Кортеж (tuple) — это тип, который «собирается на месте» из перечисленных типов. Пишется в скобках:

var t = (5, 7);                  // кортеж из двух int, тип выводится
Console.WriteLine(t);            // (5, 7)
Console.WriteLine(t.Item1);      // 5
Console.WriteLine(t.Item2);      // 7

Вывод

(5, 7)
5
7

Запись (int, int) — сокращение для типа System.ValueTuple<int, int>. Это структура (глава 4): лежит там же, где и переменная, отдельных объектов в куче не появляется. Item1/Item2 — не свойства, а public-поля: их можно менять напрямую (t.Item1 = 9), а печать структуры выводит значения по порядку.

Имена Item1, Item2 — не прихоть

Так элементы называются в самом типе. Свои имена (следующий раздел) — это только псевдонимы для компилятора; если их нет, остаются Item1…Item7.

Имена элементов: (bool ok, int half)

В объявлении можно дать элементам имена. Тогда вместо Item1 пишут ok, и код читается как обычный объект с полями:

(bool ok, int half) res = (true, 4);

Console.WriteLine(res);              // печать имён не показывает
Console.WriteLine($"{res.ok} {res.half}");
Console.WriteLine(res.Item1);        // Item1 никуда не делся
Console.WriteLine(res.GetType());    // что за тип на самом деле

Вывод

(True, 4)
True 4
True
System.ValueTuple`2[System.Boolean,System.Int32]

Вывод выше говорит главное: имена — подсказка компилятора, а не часть типа. В рантайме существует ValueTuple<bool, int>, и никаких ok/half в нём нет. Компилятор хранит имена отдельно, в атрибуте TupleElementNamesAttribute — его читают IDE и рефлексия (глава 22), чтобы подсказывать вам .ok вместо .Item1.

Практические следствия
  • Имена не влияют на равенство: (x: 1, y: 2) == (1, 2) — это true, тип один и тот же.
  • Имена берутся из целевого типа: если метод возвращает (bool ok, int half), а вы объявили (bool first, int second) x = …, обращаться надо к x.first/x.second.
  • Присваивание между кортежами с разными именами работает — типы совпадают.
  • Имена не переживают упаковку, JSON и передачу через границу типов — см. «Ловушки».

Возврат из метода: разбираем строку по частям

Вот та строка, из-за которой обычно и возникает вопрос. Разберём её слева направо:

static (bool ok, int half) TryHalfTuple(int v) => (v % 2 == 0, v / 2);
КусокЧто это
staticМетод (здесь — локальная функция) ничего не захватывает снаружи. Захват и лямбды — глава 16; для кортежей это не важно, но static запрещает случайный захват
(bool ok, int half)Тип возвращаемого значения: кортеж из двух элементов с именами. То же, что ValueTuple<bool, int>, только с именами
TryHalfTuple(int v)Имя и параметры. Один параметр int, без out: результат уходит в возвращаемое значение, а не в параметр
=>Выражение-тело (expression body): сокращение вместо { return …; }. Это не лямбда — слева стоит обычное имя метода. Та же запись бывает у свойств: public int Double => _x * 2;
(v % 2 == 0, v / 2)Литерал кортежа: два выражения через запятую, каждое становится элементом — первое (bool) в ok, второе (int) в half

То же самое в полной форме — чтобы связь была очевидной:

static (bool ok, int half) TryHalfTuple(int v)
{
    bool ok = v % 2 == 0;
    int half = v / 2;
    return (ok, half);              // литерал кортежа из двух переменных
}

Проверим, что возвращается:

Console.WriteLine(TryHalfTuple(8));         // чётное
Console.WriteLine(TryHalfTuple(7));         // нечётное
Console.WriteLine(TryHalfTuple(7).half);    // к элементу можно обратиться сразу

Вывод

(True, 4)
(False, 3)
3

Обратите внимание: при нечётном v метод вернул (False, 3) — «половина» посчитана всегда, даже когда ok равно false. Если такое значение недопустимо, это оговаривают отдельно: возвращают bool плюс out (глава 5), запись с валидацией в конструкторе (глава 17) или бросают исключение (глава 21).

Деконструкция: разобрать кортеж на переменные

Обратная операция — деконструкция: кортеж «раскладывается» по переменным в том же порядке, в котором объявлены элементы.

static (bool ok, int half) TryHalfTuple(int v) => (v % 2 == 0, v / 2);

var (ok, half) = TryHalfTuple(8);           // две НОВЫЕ переменные
Console.WriteLine($"{ok} {half}");

(bool o2, int h2) = TryHalfTuple(7);        // то же, но типы написаны явно
Console.WriteLine($"{o2} {h2}");

int a = 0, b = 0;
(a, b) = (1, 2);                            // в уже существующие
Console.WriteLine($"{a} {b}");

var (onlyOk, _) = TryHalfTuple(9);          // второе значение не нужно
Console.WriteLine(onlyOk);

Вывод

True 4
False 3
1 2
False

Четыре формы — это одно и то же действие. Ключевое отличие от «просто присваивания»: переменных становится несколько, а справа стоит одно значение. _ в последней строке — тот самый discard из главы 5: значение вычислено, но переменной не существует.

ЗаписьЧто делает
var (ok, half) = …Объявляет переменные, типы выводит из кортежа
(bool o2, int h2) = …Объявляет переменные с явными типами
(a, b) = …Присваивает существующим переменным (они должны быть объявлены заранее)
var (ok, _) = …Нужен только первый элемент, второй выбрасывается
Ловушка: деконструкция — это не «две переменные с одним значением»

Справа обязан быть кортеж (или тип с методом Deconstruct). Запись var (ok, half) = TryHalfTuple(8); — одно присваивание: сначала вычисляется кортеж целиком, потом раскладывается. Поэтому если метод бросает исключение, ни одна из переменных не будет создана.

Равенство, хеш и кортеж как ключ

Кортеж сравнивается поэлементно: для ValueTuple оператор == существует с C# 7.3 и сравнивает элементы через их собственный ==. Имена в сравнении не участвуют, участвуют только значения и типы.

Console.WriteLine((1, 2) == (1, 2));
Console.WriteLine((x: 1, y: 2) == (1, 2));      // имена не важны

var m = new Dictionary<(int, int), string> { [(1, 2)] = "a" };
Console.WriteLine(m[(1, 2)]);

Вывод

True
True
a

Последняя строка объясняет, почему кортеж годится в ключ: ValueTuple реализует IEquatable и GetHashCode по всем элементам (глава 3), поэтому пара «координата → значение» работает без собственного типа. Подробно про словари — глава 11.

Не путайте с Tuple<,>

До C# 7 в .NET был класс Tuple<int, int>. Он жил в куче, элементы были свойствами без имён, и == сравнивал ссылки:

Console.WriteLine(Tuple.Create(1, 2) == Tuple.Create(1, 2));       // False
Console.WriteLine(Tuple.Create(1, 2).Equals(Tuple.Create(1, 2)));   // True

Вывод

False
True

Сегодня Tuple нужен только для совместимости со старыми API. Везде, где вы пишете «кортеж», имеется в виду ValueTuple и синтаксис со скобками.

Кортеж изменяемый: это поля, а не свойства

У ValueTuple элементы — открытые поля. Значит, кортеж в переменной можно менять по частям, а default даёт «нулевой» кортеж:

var t = (ok: true, half: 4);
t.ok = false;                 // поле, поэтому компилятор не против
Console.WriteLine(t);

(bool ok, int half) empty = default;
Console.WriteLine(empty);     // все элементы по умолчанию

Вывод

(False, 4)
(False, 0)

Изменяемость — следствие того, что ValueTuple структура (глава 4). Плюс: не нужно создавать новый кортеж ради одного поля. Минус: получив кортеж из метода, помните, что вы держите копию — изменения не «дойдут» до того, кто этот кортеж создал.

Где кортежи уже работают

Два места, где вы встретите их постоянно:

var ages = new Dictionary<string, int> { ["Аня"] = 30, ["Боб"] = 25 };

foreach (var (name, age) in ages)          // деконструкция KeyValuePair
    Console.WriteLine($"{name}: {age}");

var picked = new[] { "Аня", "Боб" }.Select(n => (n, n.Length)).ToList();
foreach (var (n, len) in picked)
    Console.WriteLine($"{n}={len}");

Вывод

Аня: 30
Боб: 25
Аня=3
Боб=3

В первом случае кортеж создаёт сам Dictionary: элемент перебора — пара «ключ-значение», и её можно разложить прямо в foreach (глава 11). Во втором кортеж создаёте вы, чтобы вернуть из Select два значения сразу (глава 15).

Ловушки, на которых кортежи кусаются

Кортеж в JSONSystem.Text.Json по умолчанию сериализует свойства, а у ValueTuple — поля. Результат: {} Для DTO — record, а не кортеж
Имена в отладчике/логахПечать даёт (True, 4); имена не видны Печатать по элементам или использовать record.ToString()

Первая ловушка — самая дорогая, посмотрим на неё в коде:

(bool ok, int half) res = (true, 4);

Console.WriteLine(JsonSerializer.Serialize(res));
Console.WriteLine(JsonSerializer.Serialize(res, new JsonSerializerOptions { IncludeFields = true }));

Вывод

{}
{"Item1":true,"Item2":4}

Даже с IncludeFields имена потеряны — в JSON уйдут Item1/Item2. Для записи (глава 17) тот же код даёт {"Ok":true,"Half":4}: имена полей — часть типа, их видно и сериализатору, и клиенту.

out, кортеж или record

Три инструмента для одной задачи «вернуть больше одного значения». В главе 5 был out; вот как выбирать между всеми тремя:

СитуацияИнструментПочему
«Получилось ли» + значение, шаблон Try*out Так устроен BCL: TryParse, TryGetValue, TryDequeue
Два-три равноправных значения в своём кодекортеж Аллокаций нет, работает в async, разбирается деконструкцией
Имена нужны снаружи: JSON, лог, публичный методrecord Имена — часть типа: их видят сериализатор, IDE и клиент
Результат «обрастает» логикой и меняется со временемrecord/класс Можно добавить свойства, валидацию, методы; кортеж так расширять нельзя
Нужен null как «не получилось»T? / record Кортеж — структура, null у него не бывает: default даст (False, 0)

Та же логика, но записью:

var r = new HalfResult(true, 4);
Console.WriteLine(r);                              // печать с именами
Console.WriteLine(r.Ok);
Console.WriteLine(JsonSerializer.Serialize(r));    // имена в JSON

public readonly record struct HalfResult(bool Ok, int Half);

Вывод

HalfResult { Ok = True, Half = 4 }
True
{"Ok":true,"Half":4}

Разница в двух строках: кортеж — одноразовая форма («здесь и сейчас, внутри метода»), запись — тип с именем, который живёт в API и документации. Правило простое: если кортеж выходит за пределы сборки или попадает в JSON — меняйте на record (подробно — глава 17).

Что спрашивают на собеседовании

Вопросы, которые стоит держать в голове
  • Чем ValueTuple отличается от Tuple? Структура против класса: нет аллокации, есть имена и == по значениям; у Tuple == — сравнение ссылок.
  • Где лежит кортеж? Там же, где переменная: локальная — на стеке, поле класса — в куче внутри объекта, элемент массива — в массиве. Сам по себе «в куче» он не оказывается.
  • Имена элементов — часть типа? Нет. Тип — ValueTuple<bool, int>; имена хранятся в TupleElementNamesAttribute и нужны компилятору и IDE.
  • Почему кортеж можно вернуть из async, а out — нельзя? ValueTuple — обычное значение, а ref/out/in в асинхронных методах запрещены (CS1988): метод завершается не сразу.
  • Почему кортеж годится в ключ словаря? Он реализует IEquatable и GetHashCode по всем элементам (глава 3).
  • Когда кортеж — плохая идея? В публичном API, в JSON-контрактах и там, где результатов больше трёх: имена теряются, читаемость падает.

Ловушки

  • Преобразования между кортежами — поэлементные. (int, int) спокойно станет (long, long): компилятор преобразует каждый элемент отдельно. Но если хотя бы у одного элемента преобразования нет, падает весь кортеж: error CS0029: Cannot implicitly convert type '(int a, string b)' to '(long p, int q)'.
  • Деконструкция требует точного количества. var (a, b, c) = (1, 2); — error CS8132: Cannot deconstruct a tuple of '2' elements into '3' variables; отказаться можно только от «хвоста» через _.
  • Кортеж в сигнатуре — часть контракта. Поменяли порядок элементов — сломали вызывающих молча: типы совпадают, если оба элемента int. Два безымянных int рядом — повод взять record с осмысленными именами.
  • Экономия на читаемости. (int, int, string, bool) в возврате метода никто, кроме автора, не разберёт.
★ Что запомнить из главы
  • Кортеж — это ValueTuple: структура из нужных вам типов, аллокаций нет, элементы — поля Item1…ItemN.
  • Имена (ok, half) — подсказка компилятора. В типе их нет: GetType() покажет ValueTuple`2[Boolean,Int32], а JSON — {}.
  • Деконструкция — var (ok, half) = …; работает и для KeyValuePair в foreach.
  • == сравнивает поэлементно (в отличие от старого Tuple), поэтому кортеж годится в ключ словаря.
  • Кортеж — для «здесь и сейчас». Как только результат выходит в API или JSON — берите record (глава 17).
