основная глава

Что мониторить

Очередь — это буфер, и у него есть три состояния, которые надо видеть раздельно:

МетрикаЧто означаетНа что указывает
messages_readyСколько лежит и ждёт потребителяРастёт — потребители не успевают или лежат
messages_unacknowledgedСколько выдано, но не подтвержденоРастёт — обработка «зависла» или prefetch слишком большой
consumersСколько подписок на очередьНоль при растущей очереди — потребитель упал
message_stats.publish / deliverСкорости публикации и доставкиПубликация больше доставки — очередь неизбежно растёт

Первые три видны и в CLI, и в панели. Проверено:

docker exec rmq3 rabbitmqctl list_queues name type durable messages
# name            type     durable  messages
# q.durable       classic  true     0
# q.alarm         classic  false    4
# orders.new      classic  true     0

Колонка type показывает, что все очереди — classic. Это важно для разговора о репликации (ниже).

Панель и HTTP API

Плагин rabbitmq_management даёт не только веб-интерфейс на :15672, но и JSON API — удобно для дашбордов и алертов. Например, состояние одной очереди:

curl -s -u guest:guest 'http://localhost:15672/api/queues/%2F/q.dlq'

# {'name': 'q.dlq', 'messages': 1, 'consumers': 0, 'durable': False, 'auto_delete': False, ...}

Список очередей — /api/queues, конкретная — /api/queues/{vhost}/{name} (vhost по умолчанию в URL кодируется как %2F). Для алертов достаточно двух правил: «messages_ready растёт N минут» и «consumers = 0 при непустой очереди».

Alarms: что происходит при перегрузке

RabbitMQ следит за памятью и местом на диске. Когда порог превышен, включается alarm, и брокер перестаёт читать данные от публикующих соединений — это защита, чтобы не упасть целиком.

# порог по умолчанию — 0.4 доступной памяти; поставим заведомо низкий
docker exec rmq3 rabbitmqctl set_vm_memory_high_watermark 0.000001

docker exec rmq3 rabbitmqctl status | grep -A2 '^Alarms'
# Alarms
#
# Memory alarm on node rabbit@6a1d93a32e2d

# вернуть как было
docker exec rmq3 rabbitmqctl set_vm_memory_high_watermark 0.4

Самое интересное — как это выглядит из приложения. Проверено дважды, на одном и том же publish:

# канал БЕЗ подтверждений
publish: ok
channel.IsOpen: True

# канал С подтверждениями, таймаут 3 секунды
confirm: NOT received -> TaskCanceledException
  • Без confirm публикация «успешна»: клиент записал байты в сокет и пошёл дальше. Ни ошибки, ни задержки — просто сообщения никуда не делись.
  • С confirm вызов ждёт подтверждения, не получает его и падает по таймауту. Только так перегрузка брокера становится видимой.
Что делать при alarm
  • Разбирать очередь, а не «поднимать порог»: alarm — симптом, что потребители не успевают.
  • Проверить messages_unacknowledged: если оно большое, а messages_ready маленькое — сообщения «зависли» в обработчиках (prefetch слишком большой).
  • Ограничить очереди: x-max-length и TTL не дают одному потоку данных занять всю память.
  • Не публиковать «в никуда»: без confirms приложение не узнает, что брокер перестал принимать сообщения.

Кластер и репликация

Один узел RabbitMQ — одна точка отказа: он упал, и публикация (а с ней и приложение) встала. В продакшене ставят кластер из трёх узлов. Что при этом важно понимать:

  • Кластер RabbitMQ — это не шардирование. Очередь живёт на одном узле, остальные знают о ней метаданные. Клиент может подключиться к любому узлу, но сообщения одной очереди обрабатывает узел-владелец.
  • Репликация очередей — через quorum-очереди. В примерах этой книги все очереди типа classic; такие очереди не реплицируются. Для «пережить потерю узла» объявляют очередь x-queue-type: quorum — она хранится на нескольких узлах и переживает потерю одного.
  • Клиент должен уметь переподключиться. RabbitMQ.Client поддерживает список хостов в ConnectionFactory; после падения узла соединение пересоздаётся, а неподтверждённые сообщения возвращаются в очередь.
Что реплицируется, а что нет

Реплика очереди защищает сообщения, но не избавляет от простоя: пока идёт выбор нового лидера, публикация может быть недоступна. Поэтому у приложения всё равно должны быть повторные попытки и подтверждения — «кластер есть» не значит «сбой незаметен».

Чек-лист перед продакшеном

  • Отдельный пользователь и vhost, guest отключён или ограничен localhost.
  • Очереди durable, сообщения persistent, публикация — с подтверждениями (CreateChannelOptions).
  • mandatory: true + обработчик BasicReturnAsync — чтобы «некуда положить» не терялось молча.
  • autoAck: false и обязательный ack/nack в каждом исходе обработки.
  • DLX и DLQ у каждой рабочей очереди; алерт на рост DLQ.
  • Prefetch выставлен осознанно (не «по умолчанию без лимита»).
  • Метрики: длина очередей, messages_unacknowledged, число потребителей, alarms.
  • Лимиты: x-max-length, TTL, а также лимит памяти брокера — чтобы одна очередь не съела узел.
  • Кластер из трёх узлов и quorum-очереди для критичных потоков.
Типичные ошибки
  • autoAck: true — падение потребителя теряет сообщения, и никто об этом не узнает.
  • Публикация без confirm — перегрузка брокера выглядит как нормальная работа (проверено выше).
  • Одна очередь на несколько сервисов — сообщения делятся вместо копирования.
  • Без DLQ — «отравленное» сообщение крутится вечно и блокирует обработку.
  • Наблюдение только за «жив ли процесс» — рост очереди и DLQ видно лишь по метрикам.
  • Один узел в продакшене — перезапуск брокера останавливает публикацию во всех сервисах.
★ Что запомнить из главы
  • Три метрики очереди: messages_ready, messages_unacknowledged, consumers — по ним видно, где застряло.
  • Alarm памяти или диска блокирует публикацию; без confirms приложение этого не замечает.
  • HTTP API (/api/queues) — источник данных для дашбордов и алертов.
  • Кластер ≠ шардирование: очередь живёт на узле; репликация — quorum-очереди.
  • Надёжность собирается из мелочей: durable + persistent + confirm + mandatory + ack + DLQ + prefetch + метрики.
