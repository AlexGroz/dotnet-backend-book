Глава 26. Nullable reference types: контракт, который проверяет компилятор

NRT не запрещает null в рантайме — они переносят договорённость «здесь null возможен / невозможен» в сигнатуру и заставляют компилятор следить за ней. Разбираем, какие предупреждения он выдаёт, что из этого реально защищает, а что создаёт ложное чувство безопасности. Проект с намеренными ошибками собран и запущен на .NET 8.

основная глава

Как включить

<PropertyGroup>
  <Nullable>enable</Nullable>   <!-- аннотации + предупреждения -->
</PropertyGroup>

У настройки три режима: enable (аннотации и предупреждения), annotations (аннотации видны в метаданных, предупреждений нет), warnings (предупреждения есть, но собственные аннотации не пишутся), disable. Локально контекст переключают директивами #nullable enable / #nullable restore — так включают NRT в одном файле legacy-кода, не трогая остальные.

Какие предупреждения выдаёт компилятор

Один файл с типичными ошибками, Nullable=enable, сборка dotnet build:

string name2 = maybe;                          // null в non-nullable переменную

Строка «рантайм без предупреждения» — самая важная: метод был объявлен как возвращающий string, внутри стояло null!, компилятор промолчал, приложение упало. NRT — это утверждение разработчика, и если утверждение ложное, компилятор не поможет.

Аннотации — только метаданные

string и string? — один и тот же тип CLR. Это видно по трём проверкам:

public void Print(string s) => ...
public void Print(string? s) => ...          // перегрузка невозможна

var t = typeof(string?);                     // оператор запрещён

if (default(string?) is null) ...            // компилятор: всегда true
error CS0111: Type 'Formatter' already defines a member called 'Print' with the same parameter types
error CS8639: The typeof operator cannot be used on a nullable reference type
warning CS8520: The given expression always matches the provided constant.

Отсюда следствия: аннотации не проверяются в рантайме; null из JSON, БД, кэша или рефлексии проходит сквозь любую сигнатуру; сериализатор, построенный на рефлексии, видит string независимо от ?. Поэтому проверки на null на границах (вход API, ответ БД, десериализация) остаются обязательными.

Как писать так, чтобы предупреждений не было честно

// 1) связь «bool == true ⇒ out не null» описывается атрибутом
public bool TryFind(string id, [NotNullWhen(true)] out User? user) => _users.TryGetValue(id, out user);

if (repo.TryFind("alice", out var found))
    Console.WriteLine(found.Name.Length);        // предупреждения нет — компилятор понял

// 2) обязательное свойство: объект нельзя создать без него
class Settings
{
    public required string ApiKey { get; init; }
    public string Endpoint { get; init; } = "https://api.example.com";
}

// 3) инициализация в методе: атрибут объясняет компилятору, что после вызова поле не null
class ConnectionHolder
{
    private string _connection;

    [MemberNotNull(nameof(_connection))]
    private void Init() => _connection = "Host=localhost";

    public ConnectionHolder() => Init();
    public string Connection => _connection;
}

Где NRT создаёт ложное чувство безопасности

  • null! как заглушка. Самая частая причина падений: «поле придёт из БД, зачем проверять». На стенде такой метод дал NullReferenceException без единого предупреждения.
  • Границы системы. JSON без поля, LEFT JOIN в SQL, null в кэше — всё это приходит как «не null» по сигнатуре. Проверять обязательно.
  • #nullable disable в legacy-файлах. Проверено: файл с такой директивой собрался без предупреждений, хотя содержал public string Get() => null; и s.Length без проверки.
  • Рефлексия и динамическая загрузка. Аннотации не видны Activator и JsonSerializer без явной поддержки — тип один и тот же.
NRT не заменяет валидацию

Nullability — про форму кода, а не про данные. Обязательность полей в API задаётся атрибутами и валидацией (глава 30 раздела .NET), проверки в домене — инвариантами, а на границах БД — ограничениями NOT NULL. Компилятор ловит только те null, которые вы сами «протащили» в коде, и только если вы не соврали ему !.

Как включать в существующем проекте

  1. Начать с annotations на весь solution: аннотации появляются в метаданных, сборка не завалена предупреждениями, другие проекты получают корректные сигнатуры.
  2. Затем warnings по проектам, начиная с новых: библиотеки, новые сервисы. Legacy — по файлу через #nullable enable.
  3. Сделать CS86xx ошибками в CI: <WarningsAsErrors>CS8600;CS8602;CS8603;CS8604;CS8618</WarningsAsErrors> — иначе предупреждения просто не читают.
  4. Вычистить null! в критичных местах: заменить на явную проверку или на ? в сигнатуре с обработкой на вызывающей стороне.
  5. Не отключать предупреждения точечно без причины. #pragma warning disable CS8618 в конструкторе EF-сущности — нормально; в бизнес-коде — почти всегда спрятанный баг.
NRT и EF Core

EF Core понимает nullability: non-nullable свойство сущности по умолчанию мапится на NOT NULL, string? — на nullable-колонку. Поэтому «! в сущности» часто превращается в ошибку вставки в рантайме вместо понятного предупреждения на этапе модели. Правильнее сделать свойство nullable и обработать это в запросе (глава 24 раздела .NET).

★ Чек-лист
  1. <Nullable>enable</Nullable> в новых проектах; в legacy — annotations, затем warnings.
  2. CS86xx — ошибки в CI, а не «шум в логе сборки».
  3. null! только там, где инвариант доказан рядом; каждый случай объяснён комментарием.
  4. На границах (JSON, БД, кэш, рефлексия) — явные проверки, независимо от сигнатуры.
  5. Try*-методы — с [NotNullWhen(true)], а не с null! внутри.
  6. Обязательные поля — required или валидация, а не «доверимся DTO».
★ Что спросят и как отвечать
  1. «NRT защищает от NullReferenceException?» — нет, это compile-time анализ: аннотации стираются, null из внешних источников проходит. Он защищает от тех null, которые вы сами вносите в код.
  2. «Чем string? отличается от Nullable<int>?» — Nullable<T> — реальный тип-обёртка для value-типов, string? — только аннотация: типы CLR одинаковые (CS0111 при попытке перегрузки).
  3. «Почему CS8618?» — non-nullable поле/свойство не инициализировано в конструкторе; лечится инициализатором, required, [MemberNotNull] или ?.
  4. «Зачем [NotNullWhen(true)]?» — чтобы после if (TryGet(..., out var v)) компилятор не считал v возможно-null; иначе придётся писать v! и терять проверку.
  5. «Что такое ! и когда он опасен?» — подавление предупреждения без проверки; опасен как заглушка: код компилируется, падает в рантайме (проверено на стенде).
