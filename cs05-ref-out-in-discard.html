Глава 5. ref, out, in и _: передача по ссылке на практике

Метод по умолчанию получает копию: структура копируется целиком, ссылка на объект — тоже копия ссылки. ref, out и in — три способа сказать «не копируй», а _ — способ сказать «результат мне не нужен».

основная глава

Это глава про маленькие слова, которые встречаются в каждой второй сигнатуре: TryParse(s, out var n), Interlocked.CompareExchange(ref x, …), Sum(in value), TryDequeue(out var item, out _). Все четыре отвечают на один вопрос: что именно попало в метод — копия или сама переменная?

Короткая версия того же разговора есть и в .NET-книге (глава 5 «ref, out и in»), но там она нужна как вводная к Interlocked и памяти. Здесь — язык целиком: правила, коды ошибок, область видимости out var, discard и замеры.

Проблема: метод получает копию

Из главы 4 известно, что структура копируется при присваивании. Аргумент метода — то же самое: в метод попадает копия, и всё, что метод с ней сделает, вызывающего не касается.

var p = new Point(1, 2);
p.MoveThis(10);                  // метод вызван НА САМОЙ переменной
Console.WriteLine(p.X);          // 11 — переменная изменилась

var q = new Point(1, 2);
MoveCopy(q);                     // а тут метод получил КОПИЮ
Console.WriteLine(q.X);          // 1 — изменилась копия, оригинал цел

static void MoveCopy(Point pt) => pt.X += 10;

struct Point
{
    public int X, Y;
    public Point(int x, int y) { X = x; Y = y; }
    public void MoveThis(int by) { X += by; }
}

Вывод

11
1

С классом история та же, только копируется не объект, а ссылка: через неё объект менять можно, а переприсвоить параметр — нет, это останется внутри метода.

var c = new Cnt { N = 1 };
Reassign(c);
Console.WriteLine(c.N);      // 1 — параметр стал указывать на другой объект, c не изменился

static void Reassign(Cnt c) => c = new Cnt { N = 99 };

class Cnt { public int N; }

Вывод

1

Дальше — четыре инструмента, каждый на свой случай:

  • ref — «измени мою переменную»;
  • out — «запиши сюда ещё один результат»;
  • in — «не копируй, но и не смей менять»;
  • _ — «этот результат мне не нужен».

ref: «работай с моей переменной»

ref в сигнатуре означает, что параметр — не копия, а псевдоним переменной вызывающего. Всё, что метод сделает с параметром, произойдёт с оригиналом: копии просто нет.

int n = 5;
Increase(ref n);
Console.WriteLine(n);                 // 6 — изменилась наша переменная

var pt = new Point(1, 2);
MoveRef(ref pt);                      // структура тоже передаётся без копии
Console.WriteLine(pt.X);              // 11

int a = 1, b = 2;
Swap(ref a, ref b);
Console.WriteLine($"a={a} b={b}");    // a=2 b=1

static void Increase(ref int x) => x++;
static void MoveRef(ref Point pt) => pt.X += 10;
static void Swap(ref int x, ref int y) { int t = x; x = y; y = t; }

Вывод

6
11
a=2 b=1

Три правила объясняют почти все ошибки с ref:

  • Аргумент должен быть переменной. У литерала, результата выражения и свойства нет адреса, который можно взять.
  • Переменная должна быть инициализирована до вызова: метод имеет право её прочитать.
  • ref пишется с двух сторон — в сигнатуре и у вызывающего. Это сделано специально: по вызову видно, что он может изменить вашу переменную.
int n = 5;
Increase(n);                  // error CS1620: Argument 1 must be passed with the 'ref' keyword
Increase(ref 5);              // error CS1510: A ref or out value must be an assignable variable
Increase(ref order.Total);    // error CS0206: A non ref-returning property or indexer may not be used
                              //              as an out or ref value

Типичное применение: Swap, счётчики в вызывающем коде, «заполни мой буфер» — словом, когда метод должен оставить результат в вашей переменной. Отдельный случай — методы, которым ссылка нужна по определению: Interlocked.CompareExchange(ref x, …) не смог бы работать с копией.

out: «верни мне ещё одно значение»

out — тоже «по ссылке», но с другим контрактом: метод обязан записать в параметр значение, а вызывающий не обязан его инициализировать. Из этой пары «обязан записать / можно не готовить» вырос главный шаблон BCL — Try*: успех возвращается bool, а результат уходит в out.

if (TryHalf(10, out int half))
    Console.WriteLine($"чётное, половина = {half}");   // чётное, половина = 5

Console.WriteLine($"{TryHalf(7, out int odd)} {odd}"); // False 3 — посчитал, но сказал «нет»

static bool TryHalf(int value, out int half)
{
    half = value / 2;          // записать ОБЯЗАНЫ до любого return
    return value % 2 == 0;
}

Вывод

чётное, половина = 5
False 3

Обратите внимание: во второй строке метод вернул false, но odd всё равно получил значение 3. out-параметр заполняется всегда — «не получилось» сообщается отдельным bool, а не пустотой в out.

Компилятор следит за контрактом с обеих сторон:

static bool TryHalf(int v, out int half)
{
    if (v > 0) half = v / 2;   // error CS0177: The out parameter 'half' must be assigned to
    return true;               //              before control leaves the current method
}

static void ReadFirst(out int x)
{
    Console.WriteLine(x);      // error CS0269: Use of unassigned out parameter 'x'
    x = 1;
}

TryGet(v);                     // error CS1620: Argument 1 must be passed with the 'out' keyword
Почему Try*, а не исключение

«Ключа нет», «строка не число», «очередь пуста» — это ожидаемые исходы, а не аварии. Исключение на каждый такой случай дорого: раскрутка стека, сбор StackTrace, а в цикле — ещё и постоянный мусор. Try* возвращает ответ бесплатно. Когда исключения уместны, а когда нет — глава 20.

out var: переменная, объявленная на месте

Раньше рядом с вызовом приходилось заводить переменную заранее. С C# 7 её объявляют прямо в вызове, а тип выводится из сигнатуры метода:

if (int.TryParse("42", out var parsed))
    Console.WriteLine(parsed + 1);       // 43
Console.WriteLine(parsed);               // 42 — переменная жива до конца блока

var q = new Queue<string>();
q.Enqueue("a"); q.Enqueue("b");
while (q.TryDequeue(out var item))
    Console.Write(item + " ");           // a b
// Console.WriteLine(item);              // error CS0103: The name 'item' does not exist in the current context

Вывод

43
42
a b

Тонкость ровно одна, но её ловят на практике: область видимости зависит от конструкции. В if переменная объявляется в окружающем блоке — поэтому parsed видна и после if. В while условие образует свою область, и после цикла item не существует — это и есть ошибка CS0103 в комментарии.

_ — discard: «значение не нужно»

Иногда результат нужен только чтобы понять «получилось ли». Тогда на месте переменной пишут _ — discard (дословно «выбрасывание»). Это не переменная: у неё нет типа, её нельзя прочитать и нельзя передать дальше. Встречается в четырёх местах:

Console.WriteLine(int.TryParse("abc", out _));    // False — важно только «да или нет»

var pq = new PriorityQueue<string, int>();
pq.Enqueue("x", 1);
while (pq.TryDequeue(out var el, out _))          // приоритет не нужен
    Console.Write(el + " ");                      // x

Func<int, int, int> twice = (_, b) => b * 2;     // первый аргумент не нужен
Console.WriteLine(twice(1, 21));                  // 42

var (_, name) = (7, "x");                         // деконструкция кортежа
Console.WriteLine(name);                          // x

Вывод

False
x
42
x

Четвёртый случай — отказ от результата вызова: _ = Task.Run(() => Work());. Это уже не про параметры, а про «я сознательно не жду задачу»; чем это опасно на сервере — глава 18. А чтобы компилятор не ругался предупреждением CS4014 («вызов не ожидается»), _ как раз и ставят.

Ловушка: var _ = 5 — это не discard

Если написать var _ = 5;, вы объявите обычную переменную с именем _, и её можно прочитать: Console.WriteLine(_) напечатает 5. Discard — это отсутствие переменной, и он возможен только в контекстах out _, (_, x) = … и параметров лямбды. Разница видна по коду ошибки: попытка прочитать настоящий discard даёт CS0103: The name '_' does not exist in the current context.

В лямбде с двумя параметрами (C# 9 и новее) можно выбросить и оба сразу — (_, _) => …, если важны только побочные действия, а не аргументы.

in: без копии, но только на чтение

in — компромисс между «без копии» и «нельзя менять»: параметр передаётся по ссылке, но метод не имеет права его изменять. Смысл появляется на больших структурах, которые жалко копировать ради чтения.

var big = new Big(1, 2, 3, 4);
Console.WriteLine(SumByValue(big));     // 10 — структура скопирована в параметр
Console.WriteLine(SumIn(in big));       // 10 — та же ссылка, без копии

static long SumByValue(Big b) => b.A + b.B + b.C + b.D;
static long SumIn(in Big b) => b.A + b.B + b.C + b.D;

struct Big
{
    public long A, B, C, D;
    public Big(long a, long b, long c, long d) { A = a; B = b; C = c; D = d; }
}

Вывод

10
10

Запись в in-параметр компилятор запрещает:

static long Bad(in Big b) { b.A = 1; return b.A; }
// error CS8332: Cannot assign to a member of variable 'b' or use it as the right hand side of
// a ref assignment because it is a readonly variable
Ловушка: in не отменяет копию насовсем

Если внутри метода вызвать у in-параметра изменяющий метод, компилятор не ошибётся: он молча сделает защитную копию, и все изменения пропадут.

var s = new S { A = 1 };
Bump(in s);
Console.WriteLine(s.A);        // 1 — Bump менял копию

static void Bump(in S s) => s.Grow();

struct S { public long A; public void Grow() { A++; } }

Вывод

1

Поэтому структуры, которые передают через in, объявляют readonly struct (глава 4): у неё нет изменяющих методов, защитных копий не возникает, а намерение видно в типе.

Сколько это стоит: два замера

Первое ожидание — «in всегда быстрее, копии ведь нет». На маленьких структурах это неправда: JIT встраивает метод и передаёт поля в регистрах, так что копирования как такового не остаётся.

struct 32 байта, 200 млн вызовов, Release:
by value 187 ms, in 186 ms        — разницы нет

А теперь структура на 512 байт и метод, который JIT не встраивает ([MethodImpl(MethodImplOptions.NoInlining)]):

struct 512 байт, 20 млн вызовов, Release, NoInlining:
by value 615 ms, in 36 ms         — в 17 раз

Вывод не «пишите in везде», а «сначала измерьте». Для int, DateTime, Guid, пары полей — смысла нет (только шум в сигнатуре). Для структур в десятки байт, которые передают в горячем цикле, — есть. Как мерить так, чтобы цифры не врали, — глава 21 .NET-книги.

Когда in не работает как задумано: если аргумент — не переменная, а, например, свойство или результат выражения, компилятор сначала создаёт временную переменную, и копия всё равно случается. Проверять надо на реальном коде, а не на «кажется, так быстрее».

ref-локальные и ref-возврат

Тот же смысл работает не только у параметров: переменная может быть псевдонимом чужого значения, и менять через неё — значит менять оригинал.

var arr = new[] { 10, 20, 30 };
ref int slot = ref arr[1];                 // slot — второе имя для arr[1]
slot = 99;
Console.WriteLine(string.Join(",", arr));  // 10,99,30

Вывод

10,99,30

На этом механизме держится Span<T>: его индексатор возвращает ref на элемент массива, а не копию. Как это устроено и почему такая ссылка не может уехать в кучу — глава 6. Ограничение, которое стоит помнить: ref-локальную нельзя захватить в лямбду — error CS8175: Cannot use ref local 'r' inside an anonymous method, lambda expression, or query expression.

out или кортеж?

С C# 7 «второй результат» можно вернуть кортежем, и обычно это читается лучше, потому что значения приходят в одном объекте, а не через параметры:

var (ok, half) = TryHalfTuple(10);
Console.WriteLine($"{ok} {half}");       // True 5

static (bool ok, int half) TryHalfTuple(int v) => (v % 2 == 0, v / 2);

Вывод

Где это встречается в BCL

Дальше по книге эти модификаторы будут попадаться постоянно — вот карта, чтобы не спотыкаться:

Тот же Math.DivRem — самый короткий пример «зачем out вообще придумали»:

int quotient = Math.DivRem(7, 2, out int remainder);
Console.WriteLine($"частное {quotient}, остаток {remainder}");   // частное 3, остаток 1

Вывод

частное 3, остаток 1

Что спрашивают на собеседовании

ВопросКороткий ответ
Чем ref отличается от out? Оба передают по ссылке. ref: значение уже есть, метод может читать и менять. out: значение обязан записать метод, до вызова оно не нужно.
Зачем in, если есть ref? in запрещает запись — контракт «только читаю». Для больших структур: без копии и без риска, что метод их испортит.
Почему ref/out нельзя в async? Ссылка указывает на стек вызывающего, а тело async-метода после первого await продолжается уже в другом месте. Компилятор: CS1988. Для итераторов с yield — CS1623.
Можно ref на свойство? Нет, CS0206: свойство — это вызов метода, у него нет адреса. Исключение — ref-возвращающие свойства.
Что такое discard? _ — «не сохраняй»: out _, параметр лямбды, элемент деконструкции. Не переменная: прочитать нельзя.
TryGetValue правда быстрее ContainsKey + индексатора? Да: в варианте из двух вызовов ключ ищется дважды. TryGetValue ищет один раз и отдаёт значение через out.
Когда in реально ускоряет? Когда структура большая (десятки байт) и метод не встраивается. На 32 байтах разницы может не быть вовсе — надо мерить.

Ловушки

  • Забыли модификатор у вызывающего. CS1620: Argument 1 must be passed with the 'ref' keyword (или 'out'). Модификатор пишется с двух сторон намеренно.
  • Передали не переменную. Литерал — CS1510, свойство — CS0206.
  • out не присвоен на всех путях — CS0177; попытка прочитать его до присваивания — CS0269.
  • in + изменяющий метод = тихая защитная копия. Кода ошибки нет, просто изменения пропали. Лечится readonly struct.
  • out var в while не видна после цикла (CS0103), а в if — видна: условие цикла образует свою область видимости.
  • var _ = 5 — не discard, а настоящая переменная с именем _.
  • ref в лямбде. Захватить ref-локальную нельзя — CS8175.
  • «Поставлю in — станет быстрее» без замера: на маленьких структурах JIT и так обходится без копии.
★ Что запомнить из главы
  • По умолчанию параметр — копия: что метод с ней сделает, вызывающий не увидит.
  • ref — псевдоним переменной: инициализирована до вызова, может меняться, пишется с двух сторон.
  • out — «обязан записать»: до вызова не нужна, после вызова заполнена всегда. Отсюда шаблон Try* во всём BCL.
  • out var — объявление на месте; в if переменная живёт до конца блока, в while — только внутри цикла.
  • _ — discard: значения не существует, прочитать нельзя. var _ = 5 — это уже обычная переменная.
  • in — без копии, только чтение; выгода есть на больших структурах, и её надо мерить.
  • В async и итераторах ref/out/in запрещены (CS1988, CS1623) — там возвращают кортеж.
