Глава 30. Валидация входных данных в ASP.NET Core

Правило номер один: клиенту доверять нельзя. Разберём, где и как проверять входящие данные и что возвращать при ошибке.

Зачем это вообще нужно

Любой ввод извне — потенциальный источник проблем: мусор в базе, падения, уязвимости (например, «перезапись» лишних полей). Валидация — это граница системы: всё, что прошло через неё, считается корректным, и по этой же границе мы ограничиваем нагрузку.

Валидация на клиенте — не считается

Проверки в браузере (или в мобильном приложении) нужны только ради удобства пользователя: показать ошибку сразу. Злоумышленник обойдёт их за секунду — поэтому сервер проверяет всё сам.

Уровни защиты (идут друг за другом)

  1. Ранние лимиты инфраструктуры: ограничение размера тела запроса, rate limiting (глава 28), таймауты. Это «отсечь совсем наглое» ещё до логики.
  2. Формат и модель: правильные типы и обязательные поля (валидация модели).
  3. Бизнес-правила: «дата окончания позже даты начала», «сумма больше нуля», «такого статуса не бывает».
  4. Гарантия в базе данных: NOT NULL, UNIQUE, CHECK, внешние ключи — последняя линия обороны (глава 21 SQL).

Хорошая система использует все четыре: первые три дают понятные ошибки пользователю, четвёртый не даёт испортить данные, даже если в коде где-то промахнулись.

Уровень 1–2: валидация модели (DataAnnotations)

В ASP.NET Core можно описать правила прямо на модели атрибутами, а контроллер с [ApiController] сам вернёт 400, если правила нарушены.

Модель запроса с правилами (файл Contracts/CreateOrderRequest.cs)

public sealed class CreateOrderRequest
{
    // [Required] на int не нужен: у значимого типа не бывает null, поэтому атрибут
    // не сработает никогда, а 0 для него — валидное значение; ноль отсекает [Range].
    [Required]
    [Range(1, int.MaxValue)]                    // должно быть больше нуля
    public int CustomerId { get; init; }

    [Required]
    [StringLength(200, MinimumLength = 3)]      // длина строки
    public string Title { get; init; } = "";

    [EmailAddress]                              // формат e-mail
    public string? ContactEmail { get; init; }

    [Range(0.01, 1_000_000)]                    // цена в разумных пределах
    public decimal Total { get; init; }
}

Контроллер: модель проверится сама

[ApiController]                                // ← без этого атрибута авто-проверки не будет
[Route("api/orders")]
public class OrdersController : ControllerBase
{
    [HttpPost]
    public IActionResult Create(CreateOrderRequest request)
    {
        // сюда управление дойдёт только если модель валидна,
        // иначе ASP.NET Core вернёт 400 с описанием ошибок
        return Ok(_service.Create(request));
    }
}
Почему CreateOrderRequest, а не сущность БД

Так вы защищаетесь от «перезаписи лишних полей» (over-posting): клиент не сможет прислать Id, Status или CreatedAt и «назначить» их сам. В модель запроса попадает только то, что клиенту действительно разрешено задавать.

Minimal API: валидация вручную или через фильтр

В Minimal API нет автоматической проверки модели — её делают сами:

app.MapPost("/orders", (CreateOrderRequest request) =>
{
    // 1) проверяем формат/обязательные поля
    var errors = new List<string>();
    if (request.CustomerId <= 0)           errors.Add("CustomerId должен быть больше нуля");
    if (string.IsNullOrWhiteSpace(request.Title)) errors.Add("Title обязателен");

    if (errors.Count > 0)
        return Results.ValidationProblem(new Dictionary<string, string[]>
        {
            ["request"] = errors.ToArray()
        });   // = 400 с описанием проблем

    return Results.Ok(_service.Create(request));
});

Чтобы не повторять это в каждом обработчике, проверку выносят в endpoint filter — он выполняется до обработчика и может «отсечь» запрос. Для сложных правил на Minimal API удобно подключить FluentValidation (см. ниже).

Уровень 3: бизнес-правила (FluentValidation)

Атрибуты неудобны, когда правил много или они зависят друг от друга. Тогда правила описывают в отдельном классе-валидаторе, а на самой модели не ставят ничего. Библиотека — FluentValidation, ставится обычным пакетом:

dotnet add package FluentValidation

Правила пишутся в конструкторе валидатора, «цепочкой» вызовов. Модель — та же, CreateOrderRequest:

using FluentValidation;   // без него не видно ни AbstractValidator, ни RuleFor

public sealed class CreateOrderValidator : AbstractValidator<CreateOrderRequest>
{
    public CreateOrderValidator()
    {
        RuleFor(x => x.CustomerId).GreaterThan(0)
            .WithMessage("CustomerId должен быть больше нуля");

        // два правила на одно свойство: цепочка
        RuleFor(x => x.Title).NotEmpty()
            .WithMessage("Title обязателен")
            .MaximumLength(200)
            .WithMessage("Title длиннее 200 символов");

        RuleFor(x => x.Total).GreaterThan(0)
            .WithMessage("Сумма должна быть больше нуля");
    }
}
Что здесь что
  • AbstractValidator<CreateOrderRequest> — базовый класс; тип в угловых скобках говорит, какую модель проверяет валидатор.
  • RuleFor(x => x.CustomerId) — «завести правило для свойства CustomerId». Лямбда не вычисляется: из неё библиотека берёт имя свойства — оно попадёт и в текст ошибки, и в ключ JSON с ошибками ("errors": { "CustomerId": [ … ] }).
  • GreaterThan(0) — встроенный валидатор сравнения: значение должно быть строго больше нуля, то есть 0 не пройдёт, а 1 пройдёт. Родственные: GreaterThanOrEqualTo, LessThan, InclusiveBetween, NotEmpty, MaximumLength.
  • .NotEmpty().MaximumLength(200) — цепочка: два независимых правила на одно свойство, проверяются оба.
  • .WithMessage("…") — заменяет сообщение по умолчанию у предыдущего валидатора в цепочке. Без него текст останется английским и с именем свойства из лямбды (проверено): 'Customer Id' must be greater than '0'. Поэтому в примере WithMessage стоит у каждого правила.

Правило, которое зависит от другого поля той же модели, задаётся не константой, а выражением: порог берётся из самой модели. Пример для заказа с датами (это уже другой DTO — CreateBookingRequest):

public sealed class CreateBookingRequest
{
    public DateTime StartsAt { get; init; }
    public DateTime EndsAt { get; init; }
}

public sealed class CreateBookingValidator : AbstractValidator<CreateBookingRequest>
{
    public CreateBookingValidator()
    {
        // порог — не число, а поле x.StartsAt той же модели: «конец позже начала»
        RuleFor(x => x.EndsAt).GreaterThan(x => x.StartsAt)
            .WithMessage("Дата окончания должна быть позже даты начала");
    }
}

Реальный вывод: оба валидатора прогнаны на разных моделях

валидная модель: IsValid=True
CustomerId=0: IsValid=False
    [CustomerId] code=GreaterThanValidator msg="CustomerId должен быть больше нуля"
Title пустой: IsValid=False
    [Title] code=NotEmptyValidator msg="Title обязателен"
Title 201 символ: IsValid=False
    [Title] code=MaximumLengthValidator msg="Title длиннее 200 символов"

два поля:
    EndsAt раньше StartsAt: IsValid=False msg="Дата окончания должна быть позже даты начала"
    EndsAt == StartsAt: IsValid=False msg="Дата окончания должна быть позже даты начала"
    EndsAt позже: IsValid=True

В выводе видно две вещи. Сообщения русские, потому что у каждого правила стоит WithMessage. И EndsAt == StartsAt — тоже ошибка: GreaterThan строгий, «позже» не включает «в тот же момент». Если равенство допустимо, нужно GreaterThanOrEqualTo.

Валидатор сам по себе ничего не проверяет

Класс выше — только описание правил. Чтобы он срабатывал, его регистрируют в DI и вызывают перед обработчиком (endpoint-фильтр) — как именно, разобрано в главе 19. Здесь важен сам способ: правила — обычный C#-код, поэтому в них есть то, чего нет у атрибутов, — правила на два поля, свои сообщения и класс, который тестируется без HTTP.

Что возвращать при ошибке

СитуацияКодПочему
Неверный формат, обязательное поле пустое, кривой JSON400 Bad RequestКлиент прислал «не то» — ему надо исправить запрос
Формат ок, но нарушено бизнес-правило (например, нельзя отменить оплаченный заказ)422 (или 409)Запрос понятен, но правило не позволяет его выполнить
Нет прав403Это уже не про валидацию ввода, а про доступ
Ошибка на нашей стороне500Никогда не отдаём 500 на плохой ввод: это путает клиента и мониторинг
Частая ошибка

Возвращать 500 (или падать) на некорректный ввод. Плохой ввод — ожидаемая ситуация, а не авария: это 400/422 с понятным описанием. Иначе и клиент не поймёт, что делать, и дежурный будет искать «поломку сервера», которой нет.

Практики, которые стоит назвать

  • Не доверять вводу — проверять всё на сервере, даже если клиент «уже проверил».
  • DTO вместо сущностей БД — защита от over-posting (см. выше).
  • Ограничить размер тела запроса — иначе можно «залить» сервис мегабайтами: MaxRequestBodySize (Kestrel, глава 18) и лимиты на уровне прокси.
  • Rate limiting — защита от перебора и флуда (глава 28).
  • Не логировать чувствительное — пароли, номера карт; в логи попадёт то, что вернули в ошибке (глава 20).
  • Дублировать правила в БД — NOT NULL, UNIQUE, CHECK: последний рубеж.
★ Что сказать на интервью

«Валидация у меня на нескольких уровнях. Сначала инфраструктурные лимиты: размер тела, rate limiting, таймауты. Затем формат и модель — в ASP.NET Core это атрибуты на DTO плюс [ApiController] (или endpoint-фильтр в Minimal API), для сложных правил — FluentValidation. Бизнес-правила проверяются в сервисном слое, а гарантию дают ограничения в базе: NOT NULL, UNIQUE, CHECK. Плохой ввод возвращаю как 400/422 с описанием, никогда не 500. И обязательно модели запроса (DTO), а не сущности БД, — чтобы клиент не мог перезаписать лишние поля».
