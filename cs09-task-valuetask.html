Глава 9. Task, ValueTask и стейт-машина async/await

Что такое Task на самом деле, когда ValueTask экономит аллокацию, а когда превращается в скрытый баг, во что компилятор разворачивает async/await и что делает ConfigureAwait(false).

основная глава

Task — это не поток, а обещание результата

Task — объект-обещание: «результат будет позже». Внутри нет потока; есть:

  • состояние: WaitingForActivation → RanToCompletion / Faulted / Canceled;
  • результат (для Task<T>) или исключение;
  • список продолжений (continuations) — что выполнить после завершения.
var task = _http.GetStringAsync(url);   // объект создан СРАЗУ, работа идёт фоном

Console.WriteLine(task.Status);         // WaitingForActivation
var body = await task;                  // подождать и получить результат
Console.WriteLine(task.Status);         // RanToCompletion
Сколько стоит Task

Task — класс, то есть объект в куче: заголовок + поля + результат. Для API, который вызывается миллионы раз, это лишние аллокации и работа. Отсюда два кэша в BCL: Task.CompletedTask (один объект на всех) и Task.FromResult, который для часто встречающихся значений возвращает готовый кэшированный экземпляр.

ValueTask: структура, которая экономит аллокацию

ValueTask / ValueTask<T> — это struct, который внутри хранит либо готовый результат, либо Task, либо источник значения (IValueTaskSource). Если результат уже есть — объекта в куче не появляется вообще.

// кэш: чаще всего значение уже есть → Task создавать незачем
public ValueTask<string> GetNameAsync(int id)
{
    if (_cache.TryGetValue(id, out string? cached))
        return new ValueTask<string>(cached);      // 0 аллокаций: struct с готовым значением

    return new ValueTask<string>(LoadFromDbAsync(id));  // реально асинхронный путь
}

Часто такие методы вызываются в «горячих» местах, где синхронный путь — норма: чтение из кэша, PipeReader.ReadAsync, IAsyncEnumerator.MoveNextAsync, ChannelReader.ReadAsync. Именно поэтому BCL местами возвращает ValueTask.

Цена ValueTask: правила, которые нельзя нарушать

ValueTask — не «более быстрый Task». Это одноразовое значение: его разрешено прочитать (дождаться) ровно один раз.

НельзяЧто произойдёт
await vt; await vt; (повторное ожидание)InvalidOperationException или неверный результат: объект уже вернулся в пул и переиспользован
vt.Result, vt.Wait(), GetAwaiter().GetResult() синхронное ожидание запрещено контрактом — легко получить зависание или исключение
Task.WhenAll(vt1, vt2)не компилируется: ValueTask не приводится к Task
Сохранить в поле и ждать позже, передать другому потокуисточник значения уже освобождён — гонки и порча данных
Использовать в lock/foreach как обычное значениекопирование структуры даёт вторую «ссылку» на одноразовый источник
// ✘ классическая ошибка: значение нужно дважды — а ValueTask одноразовый
ValueTask<string> vt = GetNameAsync(42);
if (await vt is null) return;
var name = await vt;                    // второе ожидание: уже сломанный объект

// ✔ нужен повторный доступ — превращаем в Task (одна аллокация, зато безопасно)
Task<string> task = GetNameAsync(42).AsTask();
if (await task is null) return;
var name = await task;                  // Task можно ожидать сколько угодно раз

Откуда строгость: производители ValueTask (например, PipeReader) отдают объект из пула. После первого await он возвращается в пул и может быть выдан следующему вызову — поэтому «сохранённое» значение превращается в чужое.

Когда ValueTask даёт профит, а когда вредит

ПрофитВред
Метод часто завершается синхронно (кэш, буфер, готовые данные) Метод почти всегда реально асинхронный — структура ничего не экономит, только усложняет API
Очень горячий путь: миллионы вызовов, где важна каждая аллокацияВызывающий код может законно захотеть .Result, WhenAll, повторный await
Метод — внутренний, и вы контролируете всех вызывающихПубличный API библиотеки: ломать ожидания пользователей ради пары байт — плохая сделка
Реализация интерфейса, где так задумано BCL (IAsyncEnumerator, ChannelReader)Возвращать ValueTask из async-метода «на всякий случай» — почти всегда ошибка: компилятор всё равно создаст объект состояния
Правило выбора

Начинайте с Task. Переходите на ValueTask только если есть замер (гл. 21 .NET-раздела), который показывает, что аллокации Task заметны, и метод действительно часто завершается синхронно. И тогда соблюдайте контракт «одно ожидание».

Во что компилятор разворачивает async/await

async/await — не «магия рантайма», а переписывание метода компилятором. Метод превращается в маленький автомат состояний (стейт-машину), который умеет «приостановиться» и потом продолжить с того же места.

Исходный код

public async Task<int> SumAsync(int a, int b)
{
    var x = await GetAAsync(a);
    var y = await GetBAsync(b);
    return x + y;
}

Как это выглядит после компиляции (упрощённо)

public Task<int> SumAsync(int a, int b)          // метод-обёртка: создаёт машину и запускает
{
    var sm = new SumAsyncStateMachine();          // структура; в Debug-сборке — класс (для отладчика)
    sm._this = this;
    sm.a = a;                                     // параметры → поля структуры
    sm.b = b;
    sm._builder = AsyncTaskMethodBuilder<int>.Create();
    sm._state = -1;                               // «ещё не начинали»
    sm._builder.Start(ref sm);                    // синхронно вызывает MoveNext()
    return sm._builder.Task;                      // наружу — обещание результата
}

struct SumAsyncStateMachine : IAsyncStateMachine
{
    public int _state;                            // на каком await мы остановились
    public AsyncTaskMethodBuilder<int> _builder;  // «обещание» + способы завершить его
    public TaskAwaiter<int> _awaiter;             // ожидатель текущей задачи
    public int a, b, x, y;                        // параметры и локальные — теперь ПОЛЯ

    public void MoveNext()                        // основной цикл автомата
    {
        try
        {
            switch (_state)
            {
                case 0: goto AfterFirst;          // продолжили после первого await
                case 1: goto AfterSecond;         // после второго
            }

            _awaiter = GetAAsync(a).GetAwaiter();

            if (!_awaiter.IsCompleted)            // задача ещё не готова
            {
                _state = 0;                       // запомнили точку возврата
                _builder.AwaitUnsafeOnCompleted(ref _awaiter, ref this);
                return;                           // ВЫХОД из метода: поток свободен
            }
        AfterFirst:
            x = _awaiter.GetResult();             // результат или исключение

            _awaiter = GetBAsync(b).GetAwaiter();
            if (!_awaiter.IsCompleted)
            {
                _state = 1;
                _builder.AwaitUnsafeOnCompleted(ref _awaiter, ref this);
                return;
            }
        AfterSecond:
            y = _awaiter.GetResult();

            _builder.SetResult(x + y);            // задача завершена успешно
        }
        catch (Exception ex)
        {
            _builder.SetException(ex);            // ошибка тоже «внутри» задачи
        }
    }
}

Что из этого следует:

  • До первого незавершённого await метод выполняется синхронно. Start вызывает MoveNext прямо в вызывающем потоке — именно поэтому «асинхронный» метод успевает сделать часть работы до возврата управления.
  • await — это не блокировка. Если задача не готова, машина запоминает состояние и return: поток возвращается в пул, а продолжение (MoveNext) вызовут, когда задача завершится (гл. 12 .NET-раздела).
  • Если задача уже завершена (IsCompleted), продолжение идёт сразу, без переключения потоков и без постановки в очередь.
  • Исключения не «вылетают» из метода: они ловятся и складываются в задачу (SetException), а await потом их пробрасывает. Поэтому try/catch вокруг вызова без await исключение не поймает.
  • Локальные переменные стали полями x, y: их нужно сохранить между «приостановками». Параметры тоже.
  • Память: пока метод не приостановился, машина — структура на стеке. При первой приостановке её нужно сохранить дольше, чем живёт стек, — она упаковывается в кучу (бокс). Отсюда правило: async-метод, который завершился синхронно, почти ничего не стоит; метод, который реально ждал, — стоит объект состояния.

ConfigureAwait(false): где продолжится код после await

По умолчанию после await продолжение пытается вернуться в исходный контекст (SynchronizationContext или TaskScheduler). ConfigureAwait(false) говорит: «мне всё равно, в каком потоке продолжать» — продолжение пойдёт в потоке пула.

  • Зачем в библиотеках: библиотека не знает, кто её вызвал. Если это UI-приложение, возврат в UI-поток после каждого await — лишние переключения и риск дедлока при синхронном ожидании снаружи.
  • В ASP.NET Core контекста синхронизации нет, поэтому эффект почти нулевой — но правило остаётся: библиотечный код не должен зависеть от контекста вызывающего.
  • Что он не делает: не отменяет операцию, не ускоряет её и не влияет на код до await — только на то, где выполнится код после.
  • Для ValueTask и IAsyncEnumerable он тоже есть: await vt.ConfigureAwait(false), enumerable.ConfigureAwait(false).
// библиотечный метод: после каждого await — ConfigureAwait(false)
public async Task<string> GetAsync(string url, CancellationToken ct)
{
    var response = await _client.GetAsync(url, ct).ConfigureAwait(false);
    return await response.Content.ReadAsStringAsync(ct).ConfigureAwait(false);
}

Сколько всё это стоит: сводка по памяти

СценарийЧто попадает в кучу
async Task без результата, завершился синхронноничего: отдаётся кэшированный Task.CompletedTask
async Task<T>, завершился синхроннообъект Task<T> (для некоторых значений — кэшированный)
async Task, был реальный awaitбокс стейт-машины + объект Task
async ValueTask, завершился синхронноничего — это и есть смысл ValueTask
async ValueTask, был awaitбокс стейт-машины; результат может вернуться из пула (есть PoolingAsyncValueTaskMethodBuilder)
Task.FromResult(0)кэшированный экземпляр — ничего

Вывод: ValueTask выигрывает на синхронном пути. Если метод всё равно уходит в реальное ожидание, экономии не будет — останутся только ограничения.

Правила, которые стоит запомнить

  1. По умолчанию — Task. Он безопасен: его можно ожидать сколько угодно раз, складывать в WhenAll, хранить.
  2. ValueTask — только по замеру и только для методов, которые часто завершаются синхронно.
  3. Одно ожидание. Нужно больше — .AsTask().
  4. Никогда не блокируйте Task/ValueTask через .Result/.Wait(): это и голодание пула (гл. 9 .NET-раздела), и дедлоки.
  5. В библиотеках — ConfigureAwait(false) после каждого await.
  6. async void — только для обработчиков событий: исключение из него не попадает в задачу (гл. 10).

★ Что запомнить из главы
  • Task — обещание результата (класс в куче), а не поток; await освобождает поток, а не блокирует его.
  • ValueTask — структура для одноразового ожидания; экономит аллокацию только на синхронном пути.
  • ValueTask нельзя ожидать дважды, блокировать и складывать в WhenAll; нужен повтор — AsTask().
  • async/await — переписывание в стейт-машину: state, builder, awaiter, локальные переменные как поля; при приостановке машина уходит в кучу.
  • Метод выполняется синхронно до первого незавершённого await; исключения складываются в задачу и пробрасываются при await.
  • ConfigureAwait(false) — «мне не нужен исходный контекст»; в библиотеках — всегда.
