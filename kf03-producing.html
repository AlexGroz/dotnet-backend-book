Глава 3. Producer из .NET: acks, ключи и идемпотентность

Когда запись считается доставленной, что означает каждая настройка и почему «отправил» — не то же самое, что «брокер записал»

основная глава

Клиент: один пакет, без Java

Рабочий клиент Kafka для .NET — Confluent.Kafka. Внутри пакета лежит нативная библиотека librdkafka, поэтому JVM и отдельной установки Kafka на машине приложению не нужно:

# dotnet add package       — добавить NuGet-пакет в проект: правит .csproj, ставит ссылку
# Confluent.Kafka          — имя пакета: клиент Kafka для .NET (внутри — нативная librdkafka)
# --version 2.16.0         — зафиксировать версию; без флага ставится последняя стабильная
dotnet add package Confluent.Kafka
# info : PackageReference for package 'Confluent.Kafka' version '2.16.0' added to file '.../P.csproj'.
#        ^ ответ CLI: в файл проекта добавлена ссылка на пакет версии 2.16.0

Версию лучше фиксировать, как и в случае с любым клиентом сети: dotnet add package Confluent.Kafka --version 2.16.0. Все примеры книги сняты на 2.16.0 и Kafka 3.9.1.

Настройки producer'а

Конфигурация — обычный объект; каждая настройка отвечает на свой вопрос:

var config = new ProducerConfig
{
    BootstrapServers  = "localhost:9092",   // точка входа: адрес любого брокера кластера
    ClientId          = "orders-producer",  // имя клиента в логах брокера и в метриках
    Acks              = Acks.All,           // ждать подтверждения от всех синхронных реплик
    EnableIdempotence = true,               // не создавать дубли при повторных попытках
    MessageTimeoutMs  = 5000,               // сколько ждать доставки, прежде чем вернуть ошибку
};
НастройкаЧто означает
BootstrapServersсписок host:port через запятую — любые брокеры кластера. Клиент подключается к одному, получает метаданные и находит остальных
ClientIdметка клиента: по ней его видно в логах и метриках. Помогает понять, какой сервис создал нагрузку
Acksсколько подтверждений ждать: None — не ждать, Leader — от лидера, All — от всех синхронных реплик (разбор ниже)
EnableIdempotenceброкер отбрасывает повторные записи с тем же номером продюсера и последовательности. Защищает от дублей при ретраях и требует Acks.All
MessageTimeoutMsпредельное время ожидания доставки одного сообщения. По истечении ProduceAsync вернёт ошибку Local: Message timed out
Partitionerкак выбирается партиция по ключу; по умолчанию consistent_random (CRC32), для совместимости с Java — Murmur2Random (глава 2)

Первое сообщение: программа и разбор строк

Ниже — полная программа; она пишет три сообщения в топик orders (три партиции, создан заранее) и печатает, куда именно попало каждое:

using Confluent.Kafka;                                   // ProducerConfig, ProducerBuilder, Message, ProduceException

var config = new ProducerConfig                          // все настройки клиента в одном объекте
{
    BootstrapServers  = "localhost:9092",                // адрес брокера; для кластера — список через запятую
    ClientId          = "orders-producer",               // имя клиента в логах брокера и в метриках
    Acks              = Acks.All,                        // ждать подтверждения от всех синхронных реплик
    EnableIdempotence = true,                            // брокер отбросит дубли, если клиент повторит запись
    MessageTimeoutMs  = 5000,                            // 5 секунд на доставку, дальше — ошибка
};

using var producer = new ProducerBuilder<string, string>(config).Build(); // ключ и значение — строки

for (int i = 1; i <= 3; i++)
{
    var msg = new Message<string, string> { Key = $"order-{i}", Value = $"{{\"id\":{i}}}" }; // ключ задаёт партицию
    try
    {
        var dr = await producer.ProduceAsync("orders", msg);   // ждём отчёт о доставке этого сообщения
        Console.WriteLine($"delivered: key={msg.Key} partition={dr.Partition.Value} offset={dr.Offset.Value}");
    }
    catch (ProduceException<string, string> e)               // брокер не принял или истёк таймаут
    {
        Console.WriteLine($"failed: key={msg.Key} error={e.Error.Reason}");
    }
}

producer.Flush(TimeSpan.FromSeconds(5));                   // дождаться того, что ещё висит в очереди клиента
delivered: key=order-1 partition=1 offset=0
delivered: key=order-2 partition=0 offset=0
delivered: key=order-3 partition=2 offset=0

Три разных партиции и оффсет 0 в каждой — потому что ключи разные, а топик новый (глава 2). Если запустить программу ещё раз, те же ключи попадут в те же партиции, а оффсеты станут 1, 1, 1: ключ определяет журнал, а оффсет — место в нём.

Что лежит в отчёте о доставке (DeliveryResult<TKey, TValue>):

ПолеЧто означает
Topicтопик, в который записано сообщение
Partitionномер партиции; .Value — int
Offsetоффсет записи в партиции; .Value — long. По нему потом можно проверить, что сообщение действительно лежит в журнале
StatusPersistenceStatus: NotPersisted, PossiblyPersisted, Persisted — насколько уверенно можно считать запись сохранённой
Message, Key, Valueсамо сообщение и его ключ и значение в исходном виде
Timestamp, Headersвремя записи (по умолчанию — создания сообщения) и заголовки
ProduceException.Errorпри ошибке: Code (например, Local_MsgTimedOut) и Reason — текст, который удобно писать в лог
Оффсет — это подтверждение записи

Если ProduceAsync вернул delivered с оффсетом, запись уже лежит в журнале лидера (а при Acks.All — и на синхронных репликах). Прочитать её можно консольной утилитой по этому же оффсету: kafka-console-consumer.sh … --property print.offset=true.

acks: когда считать запись доставленной

ЗначениеЧего ждёт producerПоследствия
Acks.None (0)Ничего: отправил и забылСамая высокая скорость; потеря сообщений при падении брокера останется незамеченной
Acks.Leader (1)Подтверждение лидера партицииБыстро, но если лидер упадёт до репликации, запись пропадёт
Acks.All (-1)Подтверждение всех синхронных реплик (min.insync.replicas)Медленнее, зато переживает потерю лидера; требуется для идемпотентности

Проверено, что идемпотентность действительно требует Acks.All: клиент не даёт собрать несовместимую конфигурацию:

var bad = new ProducerConfig
{
    BootstrapServers  = "localhost:9092",
    Acks              = Acks.None,     // несовместимо с идемпотентностью
    EnableIdempotence = true,
};
using var p = new ProducerBuilder<string, string>(bad).Build();
InvalidOperationException: `acks` must be set to `all` when `enable.idempotence` is true

Что такое идемпотентность producer'а

Producer сам повторяет отправку при сбоях сети — иначе любая заминка означала бы потерю. Но повтор создаёт риск дубля: первая запись могла дойти до брокера, а ответ — потеряться. С EnableIdempotence = true клиент получает от брокера producer id и нумерует сообщения в каждой партиции; брокер отбрасывает повтор с уже виденным номером.

  • Это защита от дублей внутри одной сессии producer'а, а не «ровно один раз» для приложения: процесс упал и перезапустился — новый producer id, новая сессия.
  • Порядок в партиции сохраняется и при ретраях.
  • Требует Acks.All (проверено выше) и заметно не замедляет запись на фоне сетевых задержек.

Когда брокер недоступен

Остановим контейнер и запустим ту же программу. Каждое сообщение ждёт MessageTimeoutMs и затем возвращает ошибку:

failed: key=order-1 error=Local: Message timed out
failed: key=order-2 error=Local: Message timed out
failed: key=order-3 error=Local: Message timed out
Почему в консоли ещё куча строк %3|...FAIL...

librdkafka пишет сообщения о соединении в stderr: попытки подключиться, таймауты, переподключения. Это не исключения приложения — ловить и логировать нужно строки failed: ... из ProduceException. Уровень логов клиента настраивается в ProducerConfig и через SetLogHandler.

Важно: Local: Message timed out — это «за отведённое время подтверждение не пришло», а не «сообщение точно не записано». Брокер мог принять запись, а ответ — потеряться. Поэтому повтор после таймаута без идемпотентности даёт дубль.

Производительность: не ждите каждое сообщение

ProduceAsync в цикле — самый простой, но и самый медленный способ: программа ждёт подтверждения, прежде чем отправить следующее. Для потока событий применяют асинхронную отправку с отчётом в callback и периодический Flush:

// Produce не блокирует: сообщение уходит в очередь клиента и батчится с соседними
producer.Produce("orders", msg, report =>
{
    if (report.Error.IsError)                       // ошибка приходит сюда, а не исключением
        Console.WriteLine($"failed: {report.Error.Reason}");
});

// Flush возвращает число сообщений, которые не удалось доставить за отведённое время
int left = producer.Flush(TimeSpan.FromSeconds(5));
Console.WriteLine($"in flight after flush: {left}");

Правило простое: ждём подтверждения пачкой, а не по одному. Flush перед остановкой процесса обязателен — иначе очередь клиента потеряется вместе с процессом.

★ Что запомнить из главы
  • Confluent.Kafka — самодостаточный клиент: внутри librdkafka, Java на машине не нужна.
  • Основные настройки: BootstrapServers, Acks, EnableIdempotence, MessageTimeoutMs, Partitioner.
  • delivered с партицией и оффсетом — запись в журнале; failed с Local: Message timed out — подтверждения нет, но сообщение могло дойти.
  • Acks.All + EnableIdempotence — минимальный набор против потерь и дублей; без All идемпотентность не собирается.
  • Не ждите каждое сообщение: Produce + callback + Flush перед остановкой.
