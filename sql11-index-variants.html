Глава 11. Составные, частичные, покрывающие и функциональные индексы

Составные, частичные, покрывающие и функциональные индексы — те приёмы, которые реально ускоряют запросы. Каждый — с «когда применять» и примером.

1. Составной индекс (composite)

Индекс по нескольким колонкам. Помогает, когда запрос фильтрует и сортирует по ним вместе.

CREATE INDEX ON orders (status, created_at DESC);

-- подходит запросу:
SELECT id FROM orders
WHERE status = 'NEW'
ORDER BY created_at DESC
LIMIT 50;
Зачем DESC в индексе, если строки в таблице не отсортированы

Сомнение правильное: строки таблицы ни в каком порядке не лежат — новая строка пишется туда, где нашлось место. Сортирован не файл таблицы, а сам индекс: B-tree — отдельная структура, все записи которой физически упорядочены по ключу. Запись (status, created_at DESC) означает буквально: «сначала группировка по status (по возрастанию), внутри каждой группы — created_at по убыванию».

Дальше работает главное свойство B-tree: по нему можно идти в обе стороны. Порядок записей в индексе + направление чтения = порядок, в котором строки выходят наружу:

ИндексЧитаем вперёд (Index Scan)Читаем назад (Backward)
(status, created_at)дата ↑ ASCдата ↓ DESC
(status, created_at DESC)дата ↓ DESCдата ↑ ASC

Поэтому для одной сортируемой колонки DESC часто не обязателен: PostgreSQL возьмёт обычный индекс и прочитает его «задом наперёд» (в плане — Index Scan Backward). DESC становится обязательным, когда направления в ORDER BY разные — тогда «обратный ход» уже даёт не тот порядок:

-- нужно: статусы по убыванию, внутри — свежие заказы первыми
ORDER BY status DESC, created_at DESC

-- индекс (status, created_at), прочитанный НАЗАД, даёт: status ASC, created_at ASC — не то → Sort
-- индекс (status DESC, created_at DESC), прочитанный ВПЕРЁД, даёт ровно нужное → Sort не нужен
CREATE INDEX ON orders (status DESC, created_at DESC);

И второе, из-за чего это вообще важно. Когда порядок индекса совпал с ORDER BY, база вообще не сортирует — узла Sort в плане нет, а с LIMIT 50 чтение останавливается на 50-й записи:

-- с индексом (status, created_at DESC): ни Sort, ни чтения всей таблицы
Limit  (actual time=0.041..0.402 rows=50 loops=1)          ← взяли 50 и остановились
  ->  Index Scan using orders_status_created_at_idx on orders
        Index Cond: (status = 'NEW'::text)
        (actual time=0.038..0.395 rows=50 loops=1)         ← прочитано ровно 50 записей

-- без индекса: сначала прочитать и отсортировать ВСЁ, только потом взять 50
Limit  (actual time=402.1..402.2 rows=50 loops=1)
  ->  Sort  (Sort Method: external merge  Disk: 25120kB)  ← платим за все 480 000 строк
        Sort Key: created_at DESC
        ->  Seq Scan on orders  (rows=480000)
              Filter: (status = 'NEW'::text)

Итог: DESC — не «ускоритель сам по себе», а описание того порядка, который уже есть у индекса. Совпал с ORDER BY (с учётом направления чтения) — сортировка исчезает из плана; не совпал — база отсортирует результат отдельно и заплатит за это.

Помните правило «слева направо» (глава 10): условие должно быть на первых колонках. Индекс (status, created_at) не поможет запросу только по created_at.

2. Частичный индекс (partial)

Индексируются не все строки, а только подходящие под условие. Индекс получается меньше и быстрее, а его поддерживать дешевле.

-- индексируем только «новые» заказы (их мало, а запрашивают часто)
CREATE INDEX ON orders (created_at DESC)
WHERE status = 'NEW';

Когда применять: горячее подмножество данных — «активные», «не удалённые», «не обработанные». Именно по ним идёт основная работа, а остальное — архив.

3. Покрывающий индекс (covering, INCLUDE)

В индекс добавляют колонки, которых нет в условии, но которые нужны в результате. Тогда запрос обслуживается целиком индексом — это Index Only Scan (глава 16), в таблицу ходить не нужно.

CREATE INDEX ON orders (status) INCLUDE (created_at, total);

-- запросу нужны только status, created_at, total — таблица не читается:
SELECT created_at, total FROM orders WHERE status = 'NEW';
Почему status в скобках, а created_at — через INCLUDE?

Потому что у колонок разная роль в индексе:

  • колонки в скобках — это ключи: именно по ним индекс упорядочен, и по ним можно искать и сортировать;
  • колонки в INCLUDE — это «полезная нагрузка»: они просто хранятся в индексе (чтобы не ходить в таблицу), но искать по ним нельзя и на порядок индекса они не влияют.

Можно было написать и «через запятую»: (status, created_at) — индекс тоже был бы рабочим. Но тогда created_at стал бы ключом: попал бы в сортировку индекса, увеличил его и добавил правил, которых нам не нужно.

Как написатьРоль created_atКогда так писать
(status, created_at)Ключ: можно искать и сортироватьКогда по created_at тоже ищут или сортируют
(status) INCLUDE (created_at)Нагрузка: только хранитсяКогда created_at нужен только в ответе

Правило: по чему ищем — в скобки; что просто возвращаем — в INCLUDE.

Когда применять: частый запрос возвращает 1–3 колонки, и вы хотите убрать «прыжки» в таблицу.

4. Функциональный индекс (expression)

Индекс не по колонке, а по выражению. Нужен, когда условие содержит функцию — иначе обычный индекс не сработает.

-- запрос: WHERE lower(email) = 'user@example.com'
-- обычный индекс по email НЕ поможет, нужен такой:
CREATE INDEX ON users (lower(email));

Когда применять: поиск без учёта регистра, по части значения, по приведению типа — везде, где над колонкой вызывается функция.

5. Уникальный индекс (UNIQUE)

Обеспечивает уникальность и ускоряет поиск. Бывает и частичным:

-- уникальность только среди «активных» (удалённые могут повторяться)
CREATE UNIQUE INDEX ON users (email) WHERE deleted_at IS NULL;

Не переусердствуйте

Каждый индекс — это место на диске и замедление записи (глава 12). Индексы ставят под конкретные запросы, а не «на всякий случай». И обязательно проверяют результатом: план должен реально использовать новый индекс (главы 15–16).

★ Что запомнить

Составной — под фильтр+сортировку (порядок колонок важен). Частичный — когда горячее лишь подмножество. Покрывающий (INCLUDE) — чтобы не ходить в таблицу. Функциональный — когда в условии функция. И всегда проверяем, что индекс действительно используется.
