Глава 27. Устойчивость внешних вызовов

Свой сервис редко падает от своих ошибок — он падает от чужих. Разберём таймауты, повторы, предохранитель, изоляцию и правильный HttpClient: что делать, когда зависимость тормозит, отвечает 500 или исчезает совсем.

основная глава

Что именно ломается

У внешнего вызова (чужой API, платёжный шлюз, брокер, база) четыре режима отказа, и они требуют разных реакций:

РежимКак выглядитЧто происходит с нашим сервисом, если ничего не делать
Медленноответ за 5–30 с вместо 100 мсзапросы висят и занимают потоки/соединения — растёт очередь, потом пул, потом отказывает весь сервис (гл. 9)
Ошибки500, 503, обрывы TCPкаждый клиентский запрос — ошибка; при повторах нагрузка на упавшую зависимость растёт (шторм повторов)
Полный отказDNS не резолвится, порт закрытбыстрые ошибки — не так страшно, но пользователь видит 500
«Полуживой»часть запросов проходит, часть виситсамый опасный: без таймаута и предохранителя сервис деградирует постепенно и незаметно
Главная мысль главы

Устойчивость — не «сделать так, чтобы зависимость не падала» (мы на неё не влияем), а пережить её отказ предсказуемо: быстро отказать, не потратить все ресурсы, восстановиться автоматически.

Правило №1: у каждого вызова есть таймаут

Без таймаута «медленная зависимость» превращается в «наш сервис не отвечает»: запрос занимает поток (гл. 8), соединение и место в пуле, а результата нет. HttpClient по умолчанию ждёт 100 секунд — для API это вечность.

// ✘ бесконечное ожидание: если зависимость «полуживая», запрос займёт до 100 с
var response = await _client.GetAsync("/stock/42", ct);

// ✔ дедлайн на конкретный вызов: не больше 2 секунд
using var cts = CancellationTokenSource.CreateLinkedTokenSource(ct);
cts.CancelAfter(TimeSpan.FromSeconds(2));

try
{
    var response = await _client.GetAsync("/stock/42", cts.Token);
}
catch (OperationCanceledException) when (!ct.IsCancellationRequested)
{
    // отменил таймаут, а не клиент → это ошибка зависимости, её можно повторить
    _logger.LogWarning("inventory: таймаут 2 с");
    throw new TimeoutException("inventory timeout");
}
  • CreateLinkedTokenSource — важно: таймаут должен дополнять клиентский токен, а не заменять его. Иначе отмена запроса пользователем не остановит вызов.
  • Различайте причины: если ct.IsCancellationRequested — ушёл клиент (не ошибка), иначе — таймаут зависимости (ошибка, её можно повторить).
  • Таймаут на клиенте не отменяет работу на сервере: зависимость может продолжать обрабатывать запрос. Поэтому для операций с побочными эффектами нужен ключ идемпотентности (гл. 31).

Повтор (retry): когда помогает, а когда добивает

Повтор помогает только на временных сбоях. Правила, без которых retry делает хуже:

ПравилоПочему
Повторять только транзиентные ошибки: таймаут, обрыв соединения, 408, 429, 500, 502, 503, 504 400, 401, 403, 404, 409, 422 повтор не исправит — ответ будет тем же, только нагрузка вырастет
Повторять только идемпотентные операции (GET, PUT, DELETE) или POST с ключом идемпотентностииначе «повтор» создаст второй платёж/заказ
Пауза растёт: 100 мс → 200 → 400 (экспонента) + jitterбез jitter все клиенты повторяют одновременно и добивают зависимость «волной»
Ограничить число попыток и общее время3 попытки по 2 с при дедлайне 2 с — это не retry, а гарантированный таймаут
Учитывать Retry-After429/503 часто говорят, сколько ждать: игнорировать — значит нарушать лимит снова
// Polly v8: политика повторов для не-HTTP зависимости
var pipeline = new ResiliencePipelineBuilder()
    .AddRetry(new RetryStrategyOptions
    {
        MaxRetryAttempts = 3,                                   // всего 4 попытки
        BackoffType = DelayBackoffType.Exponential,             // 100 мс, 200 мс, 400 мс…
        UseJitter = true,                                       // ± случайный разброс
        ShouldHandle = new PredicateBuilder()
            .Handle<TimeoutException>()                         // таймаут — можно
            .Handle<HttpRequestException>(e => IsTransient(e))  // сеть/5xx — можно
    })
    .Build();

await pipeline.ExecuteAsync(async ct => await CallAsync(ct), ct);
Три способа испортить retry
  • Повторять всё подряд, включая 400 и 404: ошибка не исчезнет, а запросов станет в 4 раза больше.
  • Retry поверх retry: политика на HttpClient + своя в сервисе + ещё одна в шлюзе → 3×3×3 = 27 запросов на один клиентский. Повтор должен быть в одном месте (обычно — в HTTP-клиенте).
  • Retry на POST без ключа идемпотентности: «попробуем ещё раз» = второй заказ. Решение — Idempotency-Key и дедупликация на стороне получателя (гл. 31).

Предохранитель (circuit breaker): перестать биться в закрытую дверь

Retry лечит редкие сбои. Если зависимость лежит целиком, повторы только тратят наши ресурсы: каждый запрос ждёт таймаут, и клиенты нашего сервиса ждут вместе с ним. Предохранитель разрывает цепь:

СостояниеЧто делаетКак переходит дальше
Closed (замкнут)Пропускает вызовы и считает долю ошибок Превышен порог ошибок → Open
Open (разомкнут)Сразу отвечает ошибкой, не вызывая зависимостьЧерез BreakDuration → Half-Open
Half-OpenПропускает пробные вызовыУспех → Closed; ошибка → снова Open
var breaker = new ResiliencePipelineBuilder()
    .AddCircuitBreaker(new CircuitBreakerStrategyOptions
    {
        FailureRatio = 0.5,                          // 50 % ошибок…
        MinimumThroughput = 20,                      // …минимум на 20 вызовах
        SamplingDuration = TimeSpan.FromSeconds(30), // в окне 30 секунд
        BreakDuration = TimeSpan.FromSeconds(10)     // разомкнут 10 секунд
    })
    .Build();

Что возвращать, когда цепь разомкнута: не «500 — всё плохо», а понятную деградацию: 503 с Retry-After, данные из кэша, упрощённый ответ. Предохранитель существует для того, чтобы мы пережили отказ соседа, а не чтобы красиво логировать исключения.

Почему без half-open нельзя

Если после размыкания никогда не пробовать снова, сервис останется «сломанным» даже после того, как зависимость восстановилась. Half-open — это и есть проверка «а вдруг уже можно».

Изоляция (bulkhead): одна зависимость не должна съесть весь сервис

Если платёжный шлюз «подвис», наши запросы к нему копятся и занимают все ресурсы — и сервис перестаёт обслуживать остальные операции, хотя они ни в чём не виноваты. Изоляция — это лимит на каждую зависимость отдельно:

public sealed class PaymentClient(HttpClient http)
{
    // не больше 10 одновременных вызовов к платёжному шлюзу
    private static readonly SemaphoreSlim Gate = new(initialCount: 10, maxCount: 10);

    public async Task<PaymentResult> PayAsync(Payment p, CancellationToken ct)
    {
        if (!await Gate.WaitAsync(TimeSpan.FromSeconds(1), ct))   // не ждём бесконечно место
            throw new TimeoutException("payment: очередь переполнена");

        try
        {
            using var cts = CancellationTokenSource.CreateLinkedTokenSource(ct);
            cts.CancelAfter(TimeSpan.FromSeconds(2));             // и таймаут на сам вызов
            return await http.PostAsJsonAsync("/pay", p, cts.Token) is var r
                ? await r.Content.ReadFromJsonAsync<PaymentResult>(cts.Token)!
                : throw new HttpRequestException();
        }
        finally
        {
            Gate.Release();                                        // обязательно в finally
        }
    }
}
  • Зачем: «медленный платёж» перестаёт забирать потоки у «быстрого каталога» — у каждой зависимости свой бюджет.
  • Сколько ставить: примерно столько, сколько зависимость обещает держать (её лимит конкурентности) и сколько нужно, чтобы не копить очередь.
  • Что вернуть при переполнении: 503/429 с понятным текстом, а не «висим в ожидании освобождения слота».

HttpClient: как не убить соединения и DNS

Классическая ошибка — создавать клиент на каждый вызов:

// ✘ новый HttpClient на каждый запрос: каждый раз новый пул сокетов
using var client = new HttpClient();
await client.GetAsync(url);
  • Каждый new HttpClient() создаёт свой пул соединений. Сокеты после закрытия остаются в состоянии TIME_WAIT (десятки секунд), и при сотнях запросов в секунду заканчиваются эфемерные порты — падает весь исходящий трафик, а ошибка выглядит как «нет свободных сокетов».
  • Один долгоживущий HttpClient — тоже не решение: он держит DNS-запись навсегда и не увидит переезд зависимости на новый IP.
  • Правильно — IHttpClientFactory (гл. 4 паттернов): фабрика переиспользует обработчики и периодически пересоздаёт их.
builder.Services
    .AddHttpClient<PaymentClient>(c =>
    {
        c.BaseAddress = new Uri("https://pay.internal");
        c.Timeout = Timeout.InfiniteTimeSpan;   // таймауты задаёт resilience-пайплайн (гл. ниже)
    })
    .ConfigurePrimaryHttpMessageHandler(() => new SocketsHttpHandler
    {
        PooledConnectionLifetime = TimeSpan.FromMinutes(5),  // перечитать DNS через 5 минут
        MaxConnectionsPerServer  = 20,                       // не открывать бесконечно много
        ConnectTimeout           = TimeSpan.FromSeconds(2)   // отдельно — установка соединения
    });
Три таймаута, которые надо различать
  • ConnectTimeout — сколько ждать TCP/TLS-соединение.
  • Таймаут попытки (AttemptTimeout) — сколько ждать ответ на один HTTP-запрос.
  • Общий таймаут (TotalRequestTimeout) — сколько времени есть на все попытки вместе, включая паузы между ними.

Если задать только HttpClient.Timeout = 2s и при этом 3 попытки — ретраи не успеют начаться: первый же таймаут закроет весь вызов.

Дедлайн на весь запрос, а не на каждый вызов

Клиент ждёт ответ эндпоинта, скажем, не дольше 2 секунд (SLO). За это время мы успеваем сделать три внешних вызова. Считаем бюджет:

ЧтоСколькоИтог
Проверка остатка на складедо 700 мс (1 попытка)0,7 с
Списание в платёжном шлюзедо 900 мс (2 попытки по 400 мс)1,6 с
Запись заказа в БДдо 300 мс1,9 с
Итого1,9 с — влезает в 2 с

Если бы каждому вызову поставили «удобные» 2 секунды, худший случай был бы 6 секунд. Поэтому дедлайн спускается сверху: остаток бюджета передаётся в зависимость (в gRPC — штатный grpc-timeout, в HTTP — свой заголовок вроде X-Request-Timeout-Ms), а всё, что не успевает, отменяется через CancellationToken, а не «дорабатывает в фоне».

Собираем вместе: пайплайн для HTTP-клиента

В .NET 8 есть готовая связка: IHttpClientFactory + Microsoft.Extensions.Http.Resilience. Порядок слоёв не случайный — он идёт снаружи внутрь:

запрос
  │
  ├─ Rate limiter        не больше N одновременных вызовов и M в секунду
  ├─ Total timeout       весь вызов (все попытки) ≤ 3 с
  │    ├─ Retry          до 3 попыток, экспонента + jitter
  │    │    ├─ Breaker   50 % ошибок на 20 вызовах → пауза 10 с
  │    │    │    └─ Attempt timeout    один запрос ≤ 1 с
  │    │    │         └─ HTTP
  ▼    ▼    ▼    ▼
ответ или ошибка
builder.Services
    .AddHttpClient<InventoryClient>(c =>
    {
        c.BaseAddress = new Uri("https://inventory.internal");
        c.Timeout = Timeout.InfiniteTimeSpan;      // не дублировать общий таймаут
    })
    .AddStandardResilienceHandler(o =>
    {
        o.TotalRequestTimeout.Timeout = TimeSpan.FromSeconds(3);   // весь вызов
        o.AttemptTimeout.Timeout      = TimeSpan.FromSeconds(1);   // одна попытка
        o.Retry.MaxRetryAttempts      = 3;
        o.Retry.BackoffType           = DelayBackoffType.Exponential;
        o.Retry.UseJitter             = true;
        o.CircuitBreaker.FailureRatio      = 0.5;                  // 50 % ошибок
        o.CircuitBreaker.MinimumThroughput = 20;                   // минимум на 20 вызовах
        o.CircuitBreaker.SamplingDuration  = TimeSpan.FromSeconds(30);
        o.CircuitBreaker.BreakDuration     = TimeSpan.FromSeconds(10);
    });
  • Total timeout снаружи retry — иначе каждая попытка получит полный бюджет и общий вызов растянется втрое.
  • Attempt timeout внутри — чтобы одна «зависшая» попытка не съела весь бюджет.
  • Rate limiter снаружи — ограничивает число одновременных вызовов до того, как начнут работать таймауты.
  • Для не-HTTP зависимостей (брокер, чужой SDK) то же собирается вручную через Polly: ResiliencePipelineBuilder с retry → breaker → timeout.

Что должно быть видно в метриках и логах

  • Задержка по каждой зависимости (гистограмма, p95/p99) — гл. 21. Средняя скрывает «хвост», а именно он и валит сервис.
  • Число попыток и доля запросов, завершившихся после повтора: рост = зависимость деградирует.
  • Состояние предохранителя: переход в Open — событие уровня warning, его надо видеть на графике, а не в чате.
  • Таймауты отдельно от отмены клиентом — иначе метрика ошибок врёт: ушедший клиент не должен выглядеть как сбой зависимости.
  • Насыщение: занятость слотов изоляции и пула соединений — это то, что превращает «медленную зависимость» в «наш отказ» (гл. 23).

★ Что запомнить из главы
  • Таймаут есть у каждого вызова; таймаут попытки, общий таймаут и ConnectTimeout — разные вещи.
  • Retry — только транзиентные ошибки и идемпотентные операции, с экспонентой и jitter, в одном месте.
  • Breaker превращает медленный отказ в быстрый: closed → open → half-open → closed.
  • Изоляция (лимит параллелизма на зависимость) не даёт одному сбою съесть весь сервис.
  • IHttpClientFactory, PooledConnectionLifetime, MaxConnectionsPerServer — минимум для HttpClient.
  • Дедлайн считается на весь запрос и спускается вниз; таймауты складываются, а не «выбираются удобные».
