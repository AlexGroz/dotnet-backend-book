Глава 9. Адаптер: как подружить чужой SDK с вашим кодом

У вас есть свой аккуратный интерфейс, а у подрядчика — SDK из 2011 года: синхронный, суммы строками, ошибки через out. Менять SDK нельзя, менять весь свой код — не хочется. Адаптер — это один класс-переводчик между двумя мирами. Разберём его построчно и проверим на запуске.

основная глава

Разминка: идея на пятнадцати строках

Представим, что мы уже написали свой код так, как удобно нам:

public sealed record PaymentRequest(decimal Amount, string Currency);

public interface IPaymentGateway
{
    Task<PaymentResult> PayAsync(PaymentRequest request, CancellationToken ct);
}

А платёжный SDK подрядчика выглядит так:

public sealed class LegacyPaymentSdk
{
    // сумма — строкой, результат — int, ошибка — через out
    public int Charge(string amount, string currency, out string? error);
}

Два интерфейса несовместимы: разные типы аргументов, разная модель ошибок, разная асинхронность. Адаптер — класс, который реализует IPaymentGateway и внутри вызывает Charge:

public sealed class LegacyPaymentAdapter : IPaymentGateway
{
    private readonly LegacyPaymentSdk _sdk;
    public LegacyPaymentAdapter(LegacyPaymentSdk sdk) => _sdk = sdk;

    public Task<PaymentResult> PayAsync(PaymentRequest request, CancellationToken ct)
    {
        ct.ThrowIfCancellationRequested();
        var amount = request.Amount.ToString("0.00", CultureInfo.InvariantCulture);
        var id = _sdk.Charge(amount, request.Currency, out var error);
        return Task.FromResult(error is null
            ? new PaymentResult(true, $"TX-{id}", null)
            : new PaymentResult(false, null, error));
    }
}

Всё остальное приложение продолжает работать с IPaymentGateway и не знает, что внутри — legacy-SDK. Это и есть адаптер: обёртка, которая переводит один интерфейс в другой, не меняя ни тот, ни другой.

Адаптер — это про несовместимость, а не про «добавить поведение»

Декоратор (глава 5) оборачивает объект того же интерфейса, чтобы добавить кэш или лог. Адаптер оборачивает объект другого интерфейса, чтобы вообще иметь возможность его вызвать. Если вы оборачиваете то же самое — это декоратор, а не адаптер.

Полный пример: платёжный SDK и наш контракт

Чтобы глава не была «на словах», берём рабочую программу (.NET 8, консоль). Чужой SDK — тот, который нельзя менять: он sealed, синхронный, сумма приходит строкой, ошибка — через out.

public sealed class LegacyPaymentSdk
{
    private int _seq = 1000;
    public int Charge(string amount, string currency, out string? error)
    {
        error = null;
        if (decimal.Parse(amount, CultureInfo.InvariantCulture) <= 0) { error = "invalid_amount"; return 0; }
        if (currency == "XXX") { error = "unsupported_currency"; return 0; }
        return ++_seq;                                  // номер транзакции
    }
}
  • private int _seq = 1000 — счётчик «транзакций», чтобы номера были разными. В настоящем SDK тут был бы HTTP-вызов.
  • Charge(string amount, string currency, out string? error) — три особенности legacy: сумма строкой (никаких decimal), ошибка через out, возвращаемое значение — int (0 при ошибке).
  • error = null; — out-параметр обязан быть присвоен до любого return, иначе код не скомпилируется (CS0177). Поэтому присваиваем в первой строке.
  • decimal.Parse(amount, CultureInfo.InvariantCulture) — парсим строку обратно в число. CultureInfo.InvariantCulture важен: если полагаться на текущую культуру, в русской локали «1499.00» может быть прочитано неверно (, вместо .).
  • return ++_seq; — префиксный инкремент: сначала увеличить, потом вернуть. Первый успешный вызов вернёт 1001.

Наш контракт — то, как хотим работать мы. Заметьте: здесь нет ни одного типа из SDK.

public sealed record PaymentRequest(decimal Amount, string Currency);
public sealed record PaymentResult(bool Success, string? TransactionId, string? ErrorCode);

public interface IPaymentGateway
{
    Task<PaymentResult> PayAsync(PaymentRequest request, CancellationToken ct);
}
  • PaymentRequest — сумма как decimal (деньги в double — плохая идея из-за двоичного представления), валюта отдельным полем.
  • PaymentResult(bool Success, string? TransactionId, string? ErrorCode) — результат значением, а не исключением: «недостаточно средств» — это нормальный бизнес-ответ, а не сбой программы.
  • Task<PaymentResult> PayAsync(..., CancellationToken ct) — асинхронная подпись с токеном отмены: даже если SDK синхронный, наш контракт имеет право быть асинхронным.
Правило: интерфейс пишем первым

Сначала описываем, как хотим вызывать платёж, и только потом смотрим, что нам даёт подрядчик. Если делать наоборот — «как в SDK, только переименовать» — адаптер превращается в бессмысленную прослойку, через которую наружу протекают чужие типы и чужие ошибки.

Адаптер через композицию: разбор построчно

Самый распространённый вариант — объектный адаптер: наш класс содержит экземпляр SDK и делегирует ему работу.

public sealed class LegacyPaymentAdapter : IPaymentGateway
{
    private readonly LegacyPaymentSdk _sdk;
    public LegacyPaymentAdapter(LegacyPaymentSdk sdk) => _sdk = sdk;

    public Task<PaymentResult> PayAsync(PaymentRequest request, CancellationToken ct)
    {
        ct.ThrowIfCancellationRequested();
        var amount = request.Amount.ToString("0.00", CultureInfo.InvariantCulture);
        var id = _sdk.Charge(amount, request.Currency, out var error);
        return Task.FromResult(error is null
            ? new PaymentResult(true, $"TX-{id}", null)
            : new PaymentResult(false, null, error));
    }
}
  • : IPaymentGateway — адаптер реализует наш интерфейс. Это единственное, что видит остальное приложение.
  • private readonly LegacyPaymentSdk _sdk — внутри лежит чужой объект. readonly — ссылка не меняется после конструктора: адаптер не должен незаметно «переключаться» на другой SDK.
  • public LegacyPaymentAdapter(LegacyPaymentSdk sdk) => _sdk = sdk; — SDK приходит снаружи (constructor injection), а не создаётся через new внутри. Так адаптер можно протестировать с подставным SDK и зарегистрировать в DI.
  • ct.ThrowIfCancellationRequested() — проверка отмены до вызова SDK. Если токен уже отменён, бросается OperationCanceledException, и чужой код не вызывается вообще.
  • request.Amount.ToString("0.00", CultureInfo.InvariantCulture) — перевод decimal → string в том формате, который ждёт SDK: ровно два знака после точки, точка как разделитель, независимо от культуры машины. Это и есть «перевод интерфейса» в буквальном смысле.
  • _sdk.Charge(amount, request.Currency, out var error) — единственный настоящий вызов чужого кода. out var error объявляет переменную прямо в вызове.
  • Task.FromResult(...) — оборачиваем синхронный результат в уже завершённый Task. Никакого потока не создаётся, состояние-машина не нужна: результат готов сразу.
  • error is null ? ... : ... — перевод модели ошибок: null в out означает успех, строка — код ошибки. Наружу отдаём PaymentResult с тем же кодом, но уже в нашем типе.
  • $"TX-{id}" — приводим номер транзакции к нашему формату. Приложение не должно знать, что «на самом деле» это int из SDK.
Почему метод не помечен async

PayAsync возвращает готовый Task, поэтому async и await внутри не нужны. Побочный эффект: ThrowIfCancellationRequested бросает исключение синхронно — в момент вызова метода, а не при await. Для вызывающего кода разницы нет, если вызов стоит внутри try, — но знать об этом полезно: исключение «прилетает» раньше, чем появился Task.

Запускаем: успех, ошибка, отмена

var gateway = new LegacyPaymentAdapter(new LegacyPaymentSdk());

var ok = await gateway.PayAsync(new PaymentRequest(1499m, "EUR"), CancellationToken.None);
Console.WriteLine($"[1] success={ok.Success} txn={ok.TransactionId}");

var bad = await gateway.PayAsync(new PaymentRequest(10m, "XXX"), CancellationToken.None);
Console.WriteLine($"[2] success={bad.Success} code={bad.ErrorCode}");

using var cts = new CancellationTokenSource();
cts.Cancel();
try
{
    await gateway.PayAsync(new PaymentRequest(10m, "EUR"), cts.Token);
    Console.WriteLine("[3] отмена не сработала");
}
catch (OperationCanceledException)
{
    Console.WriteLine("[3] OperationCanceledException: SDK не вызывался");
}

Реальный вывод программы:

[1] success=True txn=TX-1001
[2] success=False code=unsupported_currency
[3] OperationCanceledException: SDK не вызывался
  • [1] — 1499m ушло в SDK строкой "1499.00", SDK вернул 1001 (первый инкремент счётчика), адаптер превратил это в TX-1001.
  • [2] — валюта XXX не поддерживается: SDK вернул 0 и заполнил error. Наружу пришёл PaymentResult с Success=false и кодом. Исключения нет — это бизнес-ответ, а не сбой программы.
  • [3] — токен отменён заранее, поэтому ThrowIfCancellationRequested сработал до _sdk.Charge: SDK не вызывался, транзакция не создавалась. Именно так и должно быть — отмена должна предотвращать побочный эффект, а не «отменять» его задним числом.
Отмена после старта — уже не отмена

У Charge нет параметра отмены. Если токен отменят во время синхронного вызова, адаптер об этом не узнает, и транзакция всё равно пройдёт. Честный вариант для такого SDK — идемпотентность на стороне приёмника (свой Idempotency-Key), чтобы повторный вызов после таймаута не списал деньги дважды. Адаптер не может дать гарантию, которой нет у SDK, и не должен делать вид, что даёт.

Коды ошибок SDK наружу не пропускаем

Сейчас в PaymentResult.ErrorCode уходит строка SDK как есть. Это удобно для отладки, но опасно как контракт: подрядчик переименует unsupported_currency — и ваши switch-и перестанут ловить этот случай. В реальном коде коды маппят в собственный enum, а незнакомый код превращают в Unknown, чтобы новая версия SDK не ломала обработку:

public enum PaymentFailure { None, InsufficientFunds, CardDeclined, UnsupportedCurrency, Unknown }

public static PaymentFailure Map(string? code) => code switch
{
    null => PaymentFailure.None,
    "insufficient_funds" => PaymentFailure.InsufficientFunds,
    "card_declined" => PaymentFailure.CardDeclined,
    "unsupported_currency" => PaymentFailure.UnsupportedCurrency,
    _ => PaymentFailure.Unknown          // важно: SDK может добавить новый код
};

_ => ... — обязательная «ловушка по умолчанию»: без неё компилятор выдаёт предупреждение о неполном сопоставлении, а новый код от подрядчика привёл бы к исключению в рантайме.

Второй способ: наследование вместо композиции

Есть и «классовый адаптер»: наш класс наследует чужой и реализует наш интерфейс. Проверим на том же наборе типов — сначала попытка адаптировать LegacyRefundSdk, который объявлен sealed:

public sealed class LegacyRefundSdk                        // sealed — наследовать нельзя
{
    public string MakeRefund(decimal amount) => "R-77";
}

public sealed class LegacyRefundAdapter : LegacyRefundSdk, IRefundService   // так нельзя
{
    public string Refund(decimal amount) => MakeRefund(amount);
}

Компилятор не пропускает это — реальное сообщение сборки:

/tmp/ad/Program.cs(54,43): error CS0509: 'LegacyRefundAdapter': cannot derive from sealed type 'LegacyRefundSdk'

Вывод: класс-адаптер возможен, только если чужой класс не sealed. Многие SDK специально закрывают классы — и тогда остаётся единственный путь: композиция. Так и сделали для возвратов:

public sealed class LegacyRefundAdapter : IRefundService   // тот же приём, другой SDK
{
    private readonly LegacyRefundSdk _sdk;
    public LegacyRefundAdapter(LegacyRefundSdk sdk) => _sdk = sdk;
    public string Refund(decimal amount) => _sdk.MakeRefund(amount);
}

А для открытого класса LegacyReportSdk наследование работает. Проверяем оба варианта в одной программе:

public class LegacyReportSdk                               // не sealed — можно наследовать
{
    public virtual string BuildReport(int rows) => $"report({rows} rows)";
}

public sealed class LegacyReportAdapter : LegacyReportSdk, IReportService
{
    public string GetReport(int rows) => BuildReport(rows);   // переименовали вызов
}
[4] композиция: refund=R-77
[5] наследование: report(42 rows)
  • [4] — Refund(500m) вызвал _sdk.MakeRefund(500m), вернулось R-77. Снаружи виден только IRefundService.
  • [5] — GetReport(42) вызвал унаследованный BuildReport(42). Здесь адаптер даже не хранит поле: он сам является SDK.

Почему композиция лучше и здесь

Классовый адаптер связывает вас с иерархией чужого класса навсегда: обновление SDK, меняющее базовый класс, ломает адаптер. Композиция зависит только от публичных методов, которые вы вызываете. Плюс объект-адаптер нельзя случайно привести к типу SDK и начать вызывать чужой API в обход перевода — то есть адаптер действительно остаётся единственной точкой контакта.

Адаптер и асинхронность: из IEnumerable в IAsyncEnumerable

Адаптеры нужны не только между «своим» и «чужим» API. В .NET есть целый класс типовых несовместимостей — например, старый код отдаёт IEnumerable<T>, а новый endpoint хочет IAsyncEnumerable<T>, чтобы отдавать ответ потоком. Переходником служит маленький адаптер-итератор:

public static class AsyncEnumerableAdapter
{
    public static async IAsyncEnumerable<string> ToAsync(IEnumerable<string> source)
    {
        foreach (var item in source)                     // синхронный источник
        {
            await Task.Delay(50);                        // эмуляция асинхронной загрузки
            yield return item;                           // отдаём по одному
        }
    }
}
  • async IAsyncEnumerable<string> — асинхронная последовательность: каждый следующий элемент может потребовать ожидания.
  • foreach (var item in source) — читаем синхронный источник как обычно. Адаптер не «ускоряет» его — он лишь меняет форму интерфейса.
  • await Task.Delay(50) — здесь эмуляция ввода-вывода (в реальном коде было бы await reader.ReadAsync(ct)). Поток в это время свободен.
  • yield return item — элемент отдаётся сразу, без накопления в списке: вызывающая сторона получает первый результат, не дожидаясь последнего.
var sw = Stopwatch.StartNew();
await foreach (var item in AsyncEnumerableAdapter.ToAsync(new[] { "a", "b", "c" }))
    Console.WriteLine($"[6] {item} на {sw.ElapsedMilliseconds} мс");
[6] a на 55 мс
[6] b на 107 мс
[6] c на 157 мс

Разбор. await foreach — потребление асинхронной последовательности; между элементами поток не занят. Тайминги показывают главное: элементы приходят по одному, с шагом ≈50 мс (55 → 107 → 157), а не все сразу в конце. Если бы адаптер сначала собрал List<string> и только потом вернул его, первый элемент появился бы лишь на ~150 мс — для потоковой отдачи больших ответов это неприемлемо.

Токен отмены в async-итератор нужно добавить явно

Асинхронный итератор без CancellationToken нельзя отменить: клиент оборвал соединение, а адаптер продолжает читать источник. Правильная подпись — с параметром и атрибутом [EnumeratorCancellation]. Если атрибут забыть, компилятор предупредит (реальный текст предупреждения):

warning CS8425: Async-iterator 'Probe.Gen(CancellationToken)' has one or more parameters of type
'CancellationToken' but none of them is decorated with the 'EnumeratorCancellation' attribute,
so the cancellation token parameter from the generated 'IAsyncEnumerable<>.GetAsyncEnumerator'
will be unconsumed
public static async IAsyncEnumerable<string> ToAsync(
    IEnumerable<string> source,
    [EnumeratorCancellation] CancellationToken ct)       // без атрибута токен не дойдёт
{
    foreach (var item in source)
    {
        ct.ThrowIfCancellationRequested();               // проверяем на каждом шаге
        await Task.Delay(50, ct);
        yield return item;
    }
}

«unconsumed» в тексте предупреждения означает ровно то, что написано: токен, переданный через WithCancellation(...), не попадёт в ваш параметр — итератор его просто не увидит.

Тот же приём используют, когда синхронный источник надо «завернуть» в адаптер наоборот — IAsyncEnumerable в IEnumerable. Так делать почти всегда не стоит: получить асинхронные данные синхронно можно только блокировкой потока (.ToBlockingEnumerable() в .NET 8 или ручной .GetAwaiter().GetResult()), а это прямой путь к исчерпанию пула потоков под нагрузкой.

Регистрация в DI: одна строка на весь адаптер

Самое приятное в адаптере — остальное приложение вообще не меняется: достаточно сказать контейнеру, какой класс стоит за интерфейсом.

var services = new ServiceCollection();
services.AddSingleton<LegacyPaymentSdk>();
services.AddSingleton<IPaymentGateway, LegacyPaymentAdapter>();
using var provider = services.BuildServiceProvider();
Console.WriteLine($"[7] DI: {provider.GetRequiredService<IPaymentGateway>().GetType().Name}");
[7] DI: LegacyPaymentAdapter
  • AddSingleton<LegacyPaymentSdk>() — регистрируем сам SDK: он может держать соединения и внутренние пулы, создавать его на каждый запрос нельзя.
  • AddSingleton<IPaymentGateway, LegacyPaymentAdapter>() — «когда просят IPaymentGateway, отдай LegacyPaymentAdapter». Контейнер увидит, что конструктору нужен LegacyPaymentSdk, и подставит зарегистрированный экземпляр.
  • BuildServiceProvider() — собирает контейнер; using нужен, чтобы при выходе освободились IDisposable-сервисы.
  • GetRequiredService<IPaymentGateway>() — если регистрации нет, бросает исключение. GetService в той же ситуации вернул бы null, и ошибка всплыла бы позже и в другом месте.
  • Вывод LegacyPaymentAdapter доказывает, что за интерфейсом действительно стоит наш адаптер — приложение про SDK ничего не знает.

Практический тест: спросите, чей интерфейс снаружи. Если он существовал до вас, а внутри чужой код с другим API — это адаптер. Если интерфейс тот же, что у обёрнутого объекта, — декоратор.

Ловушки

  • Чужие типы протекают наружу. Если метод адаптера возвращает int из SDK или пишет в лог LegacyPaymentSdkException, весь смысл теряется: при замене SDK придётся править вызывающий код. Признак хорошего адаптера — SDK встречается только в одном файле.
  • Task.Run вокруг синхронного SDK не делает его асинхронным. Task.Run(() => _sdk.Charge(...)) освобождает вызывающий поток, но занимает поток пула на всё время блокирующего вызова. При сотнях одновременных оплат пул закончится, и начнётся «thread starvation» — асинхронная подпись при этом создаёт ложное ощущение, что всё хорошо.
  • Бизнес-логика внутри адаптера. Ретраи, валидация, округления «по-нашему» — это уже декоратор или сервис. Адаптер должен оставаться предсказуемым переводчиком: один вызов на входе — один вызов SDK внутри.
  • new внутри адаптера. new LegacyPaymentSdk() в конструкторе прячет зависимость и мешает тестам. SDK приходит параметром конструктора (как в примере).
  • Один адаптер на несколько SDK. Класс, который умеет и оплату, и возвраты, и отчёты, быстро превращается во второй монолит. По адаптеру на каждый чужой API — дешевле.
  • Адаптер там, где можно поменять сам код. Если у вас есть доступ к исходникам «чужого» класса — просто реализуйте нужный интерфейс там. Адаптер оправдан, когда менять нельзя (сторонний пакет, чужой сервис, legacy-модуль).

Чек-лист перед тем, как писать адаптер

  1. Наш интерфейс описывает наши типы и нашу модель ошибок? (Ни одного типа SDK в подписи.)
  2. Чужой класс sealed? Тогда только композиция — и это нормально.
  3. SDK приходит через конструктор и регистрируется в DI как синглтон (он держит соединения)?
  4. Перевод суммы/валюты/дат делается с CultureInfo.InvariantCulture?
  5. Коды ошибок SDK маппятся в наш enum, неизвестный код → Unknown?
  6. Отмена проверяется до вызова SDK, а для «отмены после старта» есть идемпотентность?
  7. В адаптере нет ретраев, кэша и бизнес-правил?
  8. Есть тест, который подставляет фейковый SDK и проверяет маппинг успеха и ошибки?
★ Что запомнить
  • Адаптер переводит один интерфейс в другой; декоратор добавляет поведение к тому же интерфейсу.
  • Объектный адаптер (композиция) — выбор по умолчанию: работает с sealed-классами и не выпускает чужие типы наружу.
  • Классовый адаптер (наследование) требует не-sealed класса: попытка унаследовать закрытый класс даёт error CS0509.
  • Перевод затрагивает всё: типы аргументов (decimal → "1499.00"), формат (InvariantCulture), модель ошибок (out string? → PaymentResult) и асинхронность (Task.FromResult вместо блокировки).
  • Асинхронный адаптер IEnumerable<T> → IAsyncEnumerable<T> отдаёт элементы по одному (в замере 55, 107, 157 мс вместо одного «залпа» на ~150 мс) и требует [EnumeratorCancellation] для отмены — иначе warning CS8425.
  • Гарантий, которых нет у SDK (отмена посреди вызова, идемпотентность), адаптер не добавляет; он лишь честно ограничивает ожидания.
  • Регистрация — одна строка: AddSingleton<IPaymentGateway, LegacyPaymentAdapter>(); остальной код о существовании SDK не знает.
