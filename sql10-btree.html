Глава 10. B-tree и порядок колонок в индексе

B-tree — индекс по умолчанию и в 95% случаев достаточный. Разберёмся, как он устроен и почему порядок колонок решает, будет ли он полезен.

Что такое B-tree

B-tree — это сбалансированное дерево: значения в нём отсортированы, а поиск идёт «спуском» сверху вниз (примерно log N шагов вместо просмотра всего). Это тот самый «алфавитный указатель» из главы 9, только организованный деревом.

Как читать команду создания индекса

CREATE INDEX ON orders (created_at);
--     ▲        ▲      ▲
--     │        │      └── по КАКОЙ КОЛОНКЕ строим индекс
--     │        └───────── по КАКОЙ ТАБЛИЦЕ (имя таблицы)
--     └────────────────── команда «создать индекс»

-- имя индекса можно задать самому (тогда оно стоит вторым словом):
CREATE INDEX idx_orders_created_at ON orders (created_at);
Что здесь что
  • CREATE INDEX — команда «создать индекс».
  • orders — имя таблицы, по которой строится индекс.
  • created_at — имя колонки этой таблицы (в примере — дата/время создания заказа). Именно по ней и будут искать.
  • Имя индекса не указано — PostgreSQL придумает его сам (что-то вроде orders_created_at_idx). Если хотите своё — поставьте его вторым словом: CREATE INDEX моё_имя ON orders (created_at);

По умолчанию (когда нет слова USING) создаётся именно B-tree.

Индекс отсортирован по тексту с начала строки. Поэтому он быстро находит значения, которые начинаются с заданного куска, и не может — те, где кусок спрятан в середине.

Слово «слева» — потому что в записи LIKE 'Иван%' значимая часть стоит слева, а «звёздочка» — справа. Как только % появляется слева, индекс перестаёт помогать.

Главное: порядок колонок в составном индексе

Индекс можно построить по нескольким колонкам — и порядок в них важен. Работает правило «слева направо»: индекс (a, b, c) помогает условиям на a, a, b и a, b, c, но не на одни b или c.

Аналогия: телефонная книга

Справочник отсортирован «по фамилии, затем по имени». Найти всех «Иванов» — легко. Найти всех, кого зовут «Пётр», — нельзя (придётся перелистать всё). Так же и с составным индексом.

Пример: индекс под конкретный запрос

-- запрос:
SELECT id FROM orders
WHERE  status = 'NEW'
ORDER  BY created_at DESC
LIMIT  50;

-- индекс «под него»: сначала равенство, потом сортировка
CREATE INDEX ON orders (status, created_at DESC);

Почему такой порядок: СУБД сначала отберёт строки по status (равенство), а внутри — они уже отсортированы по created_at, поэтому ORDER BY станет бесплатным и LIMIT сработает сразу.

Правило выбора порядка колонок
  1. Сначала колонки равенства (col = …) — они сужают выборку сильнее всего.
  2. Потом диапазоны/сортировка (>, <, ORDER BY).
  3. Колонки «на всякий случай» не добавляйте — индекс должен отрабатывать конкретные запросы.

ASC / DESC и NULL

В индексе можно задать направление и положение NULL: CREATE INDEX ON orders (created_at DESC NULLS LAST);. Это нужно, когда запрос сортирует именно так — тогда сортировка не потребуется вовсе.

Когда B-tree не поможет, даже если он есть

  • Функция над колонкой: WHERE lower(email) = … — нужен функциональный индекс (глава 11).
  • Несовпадение типов: сравнение с приведением может «отключить» индекс.
  • Лидирующая колонка не в условии: индекс (a, b) не поможет условию только по b.
  • Слишком большая выборка: при этом планировщик честно предпочтёт Seq Scan (глава 16).
★ Что запомнить

B-tree — индекс по умолчанию: он умеет равенство, диапазоны, сортировку и префикс строки. В составном индексе порядок колонок критичен: сначала равенство, затем диапазон/сортировка, и работает правило «слева направо». Если условие стоит не на первой колонке — индекс не поможет.
