Глава 6. Кластер из трёх узлов: quorum-очереди, отказ лидера и отсутствие потерь

Что реально реплицируется в кластере, как убить узел-лидер и не потерять ни одного сообщения, зачем нужен x-delivery-limit и что происходит, когда кворум потерян

основная глава

Что даёт кластер, а что нет

Кластер RabbitMQ — это несколько узлов с общими метаданными (пользователи, vhost'ы, обменники, привязки, очереди) и общей маршрутизацией: подключившись к любому узлу, клиент может опубликовать сообщение в очередь, которая «живёт» на другом узле.

А вот сообщения по умолчанию не реплицируются. У классической очереди данные лежат на одном узле; если он недоступен, очередь недоступна, а при потере диска — потеряны и сообщения. Именно для этого появились quorum-очереди: очередь — это Raft-группа из нескольких реплик, записи подтверждаются большинством, лидер выбирается автоматически.

Классические mirrored-очереди (HA policies) в 4.x удалены — quorum-очереди стали штатным способом репликации. Дальше соберём кластер и проверим всё руками.

Стенд: три узла в одной сети

# docker network create mqnet — своя сеть: узлы находят друг друга по именам r1, r2, r3
docker network create mqnet

# docker run -d                    — запустить контейнер в фоне
# --name r1 --hostname r1          — имя контейнера и сетевое имя узла (hostname = имя для Erlang!)
# --network mqnet                  — та же сеть, что у остальных узлов
# -p 5672:5672                     — AMQP-порт наружу (нужен клиенту с хоста)
# -p 15672:15672                   — веб-интерфейс управления
# -e RABBITMQ_ERLANG_COOKIE=secretcookie — общая «кука» Erlang: без неё узлы не доверяют друг другу
# rabbitmq:3.13-management         — образ с плагином management (rabbitmqctl и rabbitmqadmin внутри)
docker run -d --name r1 --hostname r1 --network mqnet -p 5672:5672 -p 15672:15672 \
  -e RABBITMQ_ERLANG_COOKIE=secretcookie rabbitmq:3.13-management
# r2 и r3 — то же самое, но со своими портами хоста, чтобы можно было подключиться к каждому
docker run -d --name r2 --hostname r2 --network mqnet -p 5673:5672 \
  -e RABBITMQ_ERLANG_COOKIE=secretcookie rabbitmq:3.13-management
docker run -d --name r3 --hostname r3 --network mqnet -p 5674:5672 \
  -e RABBITMQ_ERLANG_COOKIE=secretcookie rabbitmq:3.13-management

# rabbitmqctl stop_app       — остановить приложение RabbitMQ, оставив узел запущенным
# rabbitmqctl join_cluster rabbit@r1 — присоединиться к кластеру с узлом-«эталоном» rabbit@r1
# rabbitmqctl start_app      — снова запустить приложение уже в составе кластера
docker exec r2 rabbitmqctl stop_app
docker exec r2 rabbitmqctl join_cluster rabbit@r1     # Clustering node rabbit@r2 with rabbit@r1
docker exec r2 rabbitmqctl start_app
docker exec r3 rabbitmqctl stop_app
docker exec r3 rabbitmqctl join_cluster rabbit@r1     # Clustering node rabbit@r3 with rabbit@r1
docker exec r3 rabbitmqctl start_app

# rabbitmqctl cluster_status — состояние кластера: кто в running, кто в stopped, версии
docker exec r1 rabbitmqctl cluster_status
# Running Nodes
# rabbit@r1
# rabbit@r2
# rabbit@r3

Разбор. --hostname обязан совпадать с именем, под которым узел известен другим: RabbitMQ строит имя узла как rabbit@<hostname>, и в join_cluster мы указываем именно его. RABBITMQ_ERLANG_COOKIE — общий секрет Erlang-кластера: с разными куками узлы не увидят друг друга (симптом — not a node или бесконечные попытки подключения). join_cluster делается на остановленном приложении, иначе узел держит собственные метаданные и присоединение отклоняется.

Кластер помнит состав и после перезапуска: docker start r2 вернёт узел в кластер без повторного join_cluster.

Quorum-очередь из .NET: объявление и публикация с подтверждениями

using RabbitMQ.Client;

var factory = new ConnectionFactory
{
    HostName = "localhost",          // узел r1 опубликован на хосте
    Port = 5672,                     // AMQP-порт
    UserName = "guest",              // учётка по умолчанию (guest пускают только с localhost)
    Password = "guest",
    ClientProvidedName = "cluster-demo"  // имя видно в rabbitmqctl list_connections
};

await using var connection = await factory.CreateConnectionAsync();   // одно TCP-соединение
await using var channel = await connection.CreateChannelAsync(
    new CreateChannelOptions(publisherConfirmationsEnabled: true,      // включить publisher confirms
                             publisherConfirmationTrackingEnabled: true)); // BasicPublishAsync ждёт confirm

await channel.QueueDeclareAsync(queue: "q.orders", durable: true, exclusive: false,
    autoDelete: false,
    arguments: new Dictionary<string, object?>
    {
        ["x-queue-type"] = "quorum"  // тип очереди: Raft-репликация на узлы кластера
    });

var sw = Stopwatch.StartNew();
for (var i = 0; i < 500; i++)
{
    var body = Encoding.UTF8.GetBytes($"order-{i}");
    await channel.BasicPublishAsync(exchange: "", routingKey: "q.orders",   // "" — default exchange
        mandatory: false, body: body);          // с tracking=true ждём подтверждения на каждое
}
sw.Stop();
// 500 сообщений подтверждено за 943 мс

Разбор построчно.

  • CreateChannelOptions(publisherConfirmationsEnabled: true, publisherConfirmationTrackingEnabled: true) — включает режим подтверждений и «ожидание»: BasicPublishAsync завершается, когда брокер подтвердил запись. Без этого публикация — «выстрелил и забыл».
  • QueueDeclareAsync(..., durable: true, arguments: {"x-queue-type": "quorum"}) — тип задаётся при объявлении и потом не меняется: переобъявить существующую классическую очередь как quorum нельзя, будет PRECONDITION_FAILED. durable: true для quorum обязательна.
  • exchange: "" — default exchange: маршрутизация по имени очереди, удобно для примеров.
  • mandatory: false — не требуем возврата, если маршрут не найден (в этой главе маршрут всегда есть).
  • 500 подтверждённых сообщений за 943 мс — цена репликации: каждое сообщение должно быть записано в большинство реплик, и клиент ждёт этого подтверждения.

Куда именно легли данные и кто лидер:

# rabbitmq-queues quorum_status q.orders — состояние Raft-группы очереди по узлам
docker exec r1 rabbitmq-queues quorum_status q.orders
# Node Name   Raft State  Membership  Last Log Index  Last Written  Last Applied  Commit Index  Term
# rabbit@r1   leader      voter       504             504           504           504           1
# rabbit@r2   follower    voter       504             504           504           504           1
# rabbit@r3   follower    voter       504             504           504           504           1

Разбор. Один лидер и два followers — классический Raft. Last Log Index 504 — 500 сообщений плюс служебные записи журнала Raft. Commit Index совпадает с Last Log Index: все записи применены на большинстве. Term 1 — поколение лидера; оно увеличится, как только лидер сменится.

Убиваем лидера

Лидер q.orders — узел r1. Убиваем его без предупреждения:

# docker kill r1 — жёстко остановить контейнер (аналог падения узла, без graceful shutdown)
docker kill r1

# ждём выборов и смотрим состояние очереди уже с другого узла
sleep 12
docker exec r2 rabbitmq-queues quorum_status q.orders
# rabbit@r1  {nodedown,rabbit@r1}   — узел потерян
# rabbit@r2  follower   505  Term 3
# rabbit@r3  leader     505  Term 3   ← лидером стал r3, поколение выросло с 1 до 3

Разбор. Пока узел r1 был лидером, r2 и r3 были followers. После падения оставшиеся два узла — это большинство из трёх (кворум 2), поэтому они выбрали нового лидера: Term вырос, Last Log Index стал 505 (Raft дописал служебную запись о смене лидера). Если бы упали два узла из трёх, большинства не осталось бы и очередь стала бы недоступной — об этом ниже.

Публикация во время отсутствия лидера — обычная, только подключаемся к живому узлу:

// тот же клиент, но HostName/Port указывают на живой узел r2 (порт 5673 на хосте)
var factory = new ConnectionFactory
{
    HostName = "localhost",
    Port = int.TryParse(Environment.GetEnvironmentVariable("MQ_PORT"), out var port) ? port : 5672,
    UserName = "guest",
    Password = "guest"
};
// ... дальше без изменений: BasicPublishAsync в q.orders
// 200 сообщений подтверждено за 435 мс
# публикуем 200 сообщений, пока узел r1 лежит (порт r2 — 5673)
MQ_PORT=5673 dotnet run -c Release -- publish 200
# 200 сообщений подтверждено за 435 мс   ← брокер принял их без «убитого» лидера

# смотрим очередь на живом узле
docker exec r3 rabbitmqctl list_queues name type messages messages_ready messages_unacknowledged
# q.orders  quorum  700  700  0

Разбор. Клиенту не нужно знать, кто лидер: подключение к любому узлу кластера маршрутизирует запрос к лидеру очереди. Подтверждения приходят только после записи в большинство (r2 + r3), поэтому 200 сообщений уже переживут потерю любого из оставшихся узлов. Обратите внимание на цифры: messages 700 — это 500 «до» плюс 200 «во время аварии».

Статистика очередей обновляется не мгновенно

Сразу после публикации rabbitmqctl list_queues может показать старое число (в прогоне — 500 вместо 700), а через несколько секунд — правильное. list_queues читает статистику, которую узел собирает асинхронно, и не делает запрос к очереди. Для проверок «здесь и сейчас» надёжнее quorum_status (журнал Raft) или rabbitmqadmin get.

Возвращаем узел и считаем потери

# docker start r1 — вернуть узел в кластер (состав кластера он помнит)
docker start r1
sleep 25

# проверяем, что вернувшийся узел догнал журнал: индексы должны совпасть
docker exec r2 rabbitmq-queues quorum_status q.orders
# rabbit@r1  follower   707   Term 3   ← был {nodedown}, стал follower
# rabbit@r2  follower   707   Term 3
# rabbit@r3  leader     707   Term 3

Разбор. r1 вернулся не лидером: лидерство осталось у r3, а вернувшийся узел сначала догоняет журнал (Raft-лог) и только потом становится полноценным voter'ом. Индексы 707 на всех трёх узлах — данные реплицированы полностью: 700 сообщений и 7 служебных записей.

Теперь вычитываем очередь целиком и смотрим, сколько дошло:

await using var connection = await factory.CreateConnectionAsync();
await using var channel = await connection.CreateChannelAsync();

// prefetch 50: не больше 50 неподтверждённых сообщений на канал (глава 3)
await channel.BasicQosAsync(prefetchSize: 0, prefetchCount: 50, global: false);

var consumer = new AsyncEventingBasicConsumer(channel);
var consumed = 0;
consumer.ReceivedAsync += async (_, ea) =>
{
    consumed++;                                        // обработали сообщение
    await channel.BasicAckAsync(ea.DeliveryTag, multiple: false);   // подтвердили брокеру
};
// autoAck: false — подтверждаем вручную, иначе сообщение считается доставленным до обработки
await channel.BasicConsumeAsync("q.orders", autoAck: false, consumer: consumer);
// обработано 700
# после вычитки очередь пуста
docker exec r3 rabbitmqctl list_queues name type messages
# q.orders  quorum  0

Итог аварии: 500 сообщений до убийства лидера, 200 — во время его отсутствия, 700 обработано после возврата узла. Потерь нет, и ни одно сообщение не потребовалось публиковать повторно. Это и есть смысл quorum-очереди: подтверждение приходит после записи в большинство, а не в один узел.

x-delivery-limit: «ядовитое» сообщение само уходит в DLQ

В главе 4 повторную обработку делали через TTL и DLX. У quorum-очередей есть встроенный счётчик доставок: сообщение, которое раз за разом возвращают в очередь, после N попыток уезжает в dead-letter — без самодельных счётчиков в заголовках.

await channel.QueueDeclareAsync("q.poison", durable: true, exclusive: false, autoDelete: false,
    arguments: new Dictionary<string, object?>
    {
        ["x-queue-type"] = "quorum",                 // реплицируемая очередь
        ["x-delivery-limit"] = 3,                    // максимум 3 «неудачные» доставки
        ["x-dead-letter-exchange"] = "",             // DLX: default exchange ("" — по умолчанию)
        ["x-dead-letter-routing-key"] = "q.dead"     // ключ маршрутизации = имя очереди мёртвых писем
    });
await channel.QueueDeclareAsync("q.dead", durable: true, exclusive: false, autoDelete: false,
    arguments: new Dictionary<string, object?> { ["x-queue-type"] = "quorum" });

await channel.BasicPublishAsync("", "q.poison", mandatory: false,
    body: Encoding.UTF8.GetBytes("bad-order"));      // одно «ядовитое» сообщение

var consumer = new AsyncEventingBasicConsumer(channel);
consumer.ReceivedAsync += async (_, ea) =>
{
    Console.WriteLine($"redelivered={ea.Redelivered}");     // признак повторной доставки
    await channel.BasicNackAsync(ea.DeliveryTag, multiple: false, requeue: true); // «не смог» — вернуть
};
await channel.BasicConsumeAsync("q.poison", autoAck: false, consumer: consumer);

Разбор. x-delivery-limit=3 считает не любые доставки, а доставки, после которых сообщение вернулось в очередь (basic.nack с requeue: true или отключение потребителя). Как только счётчик достигает лимита, брокер делает то же, что и при reject: публикует сообщение в DLX с ключом x-dead-letter-routing-key. ea.Redelivered — флаг из AMQP-конверта (redelivered), по нему в обработчике видно, что это повтор.

Что получилось в прогоне:

получено #1, redelivered=False
получено #2, redelivered=True
получено #3, redelivered=True
получено #4, redelivered=True
в q.dead сообщений: 1

Четыре доставки при лимите 3: три «неудачных» возврата исчерпывают лимит, а четвёртая — это уже последняя попытка, после которой сообщение уходит в q.dead. Проверяем очередь мёртвых писем и заголовки:

# rabbitmqctl list_queues name type messages — сколько сообщений в каждой очереди
docker exec r1 rabbitmqctl list_queues name type messages
# q.dead    quorum  1
# q.poison  quorum  0
# q.orders  quorum  0

# rabbitmqadmin get queue=q.dead count=1 — забрать сообщение из очереди и показать его свойства
# --format=raw_json — вывести JSON (иначе таблица без заголовков)
docker exec r1 rabbitmqadmin get queue=q.dead count=1 --format=raw_json
headers: {
  "x-death": [ { "count": 1, "exchange": "", "queue": "q.poison",
                 "reason": "delivery_limit", "routing-keys": ["q.poison"], "time": 1795272494 } ],
  "x-delivery-count": 1,
  "x-first-death-exchange": "", "x-first-death-queue": "q.poison",
  "x-first-death-reason": "delivery_limit",
  "x-last-death-exchange": "",  "x-last-death-queue": "q.poison",
  "x-last-death-reason": "delivery_limit"
}

Разбор заголовков. x-death — массив записей о «смертях» сообщения: очередь, обменник, reason и время. reason: delivery_limit — сработал лимит доставок (бывает ещё rejected, expired, maxlen). Пара x-first-death-* / x-last-death-* хранит первую и последнюю причину — удобно, когда сообщение прошло несколько DLQ. x-delivery-count — счётчик доставок quorum-очереди. На этих заголовках строится разбор «почему сообщение оказалось в DLQ» без похода в логи приложения.

DLQ — не свалка

Сообщение в q.dead — это сигнал, что обработчик не справился. Нужен владелец очереди, алерт на её рост и процедура разбора (переопубликовать после исправления, либо закрыть как невалидное). Иначе «мёртвые» сообщения просто копятся, а проблема остаётся незамеченной.

Что будет, когда кворума нет

Кворум — это большинство: для трёх узлов нужно два. Проверяем, что будет, если «пропали» оба оставшихся (docker pause имитирует зависший или потерявший сеть узел):

# docker pause r2 r3 — «заморозить» узлы: процесс жив, но не отвечает
docker pause r2 r3
sleep 6

# list_queues с оставшегося узла: q.orders пропала из списка — очередь недоступна
docker exec r1 rabbitmqctl list_queues name type state
# q.dead    quorum  running
# q.poison  quorum  running

# quorum_status: r1 не может стать лидером, остальные — timeout
docker exec r1 timeout 15 rabbitmq-queues quorum_status q.orders
# rabbit@r1  pre_vote  voter  1223 …
# rabbit@r2  timeout
# rabbit@r3  timeout

# возвращаем узлы — очередь снова доступна
docker unpause r2 r3
sleep 6
docker exec r1 rabbitmqctl list_queues name type state
# q.dead    quorum  running
# q.poison  quorum  running
# q.orders  quorum  running

Разбор. Пока живы два узла из трёх, очередь работает (выборы проходят). Когда остался один, Raft не может набрать большинство: узел r1 уходит в pre_vote (пытается начать выборы), остальные помечены timeout, а сама очередь исчезает из list_queues — она не running. Публикация в неё в этот момент не подтверждается. Как только большинство вернулось, очередь снова running, и всё, что было записано до потери кворума, на месте.

Два узла — это не «кластер с запасом»

При двух узлах кворум равен двум: падение любого узла останавливает очередь. Поэтому минимальный практический размер кластера — три узла, а лучше пять, размещённые в разных зонах доступности. При docker pause на двух узлах очередь становится недоступной, даже если один узел полностью здоров.

Как это применять: короткие правила

  • Очереди — quorum по умолчанию. Классические очереди оставьте там, где потеря сообщений при падении узла допустима (логи, метрики, временные данные).
  • Три реплики — минимум. Число реплик задаётся не отдельной настройкой, а составом группы (x-quorum-initial-group-size при объявлении, по умолчанию — все узлы кластера).
  • Публикуйте с подтверждениями (publisherConfirmationTrackingEnabled) и persistent-сообщениями. Без подтверждений quorum-очередь не спасает: клиент не знает, дошло ли сообщение до большинства.
  • Потребляйте с autoAck: false и подтверждайте после обработки — иначе сбой обработчика теряет сообщение, хотя оно было реплицировано.
  • Стройте DLQ на x-delivery-limit, а не на счётчиках в заголовках: лимит ведёт брокер, и он же формирует x-death.
  • Следите за кворумом: алерт на отсутствие лидера дольше N секунд, на узлы в pre_vote/timeout и на рост partitions в cluster_status.
  • Сетевые разделения опасны: узел, потерявший связь с большинством, останавливает свои quorum-очереди — это защита от split-brain, а не ошибка. Лечится возвратом сети, а не перезапуском «наугад».

★ Что запомнить
  • Кластер реплицирует метаданные; сообщения реплицирует quorum-очередь (x-queue-type=quorum), а не «кластер вообще».
  • Тип очереди задаётся при объявлении и не меняется; durable для quorum обязательна.
  • Лидер очереди — один; после docker kill лидера выборы подняли новый (Term 3), и очередь продолжила принимать сообщения (200 подтверждено за 435 мс).
  • Вернувшийся узел догоняет журнал и становится follower'ом: индексы сравнялись (707), после вычитки обработано 700 из 700 — потерь нет.
  • Публикация «в большинство» — это подтверждения: без publisherConfirmationTrackingEnabled гарантий нет.
  • x-delivery-limit=3 + DLX: 4 доставки, затем сообщение в q.dead с x-death.reason=delivery_limit.
  • Кворум = большинство: один узел из трёх — очередь недоступна (pre_vote/timeout), два из трёх — работает.
