Глава 6. Сборка мусора и цена аллокаций

Теперь, когда мы знаем, где живут объекты, разберём, как их убирает GC и почему под нагрузкой важна не «память вообще», а скорость создания объектов.

Идея сборщика мусора

Вы не освобождаете память вручную. За вас это делает Garbage Collector: он отслеживает, какие объекты ещё достижимы (на них есть ссылки), а остальные считает мусором и освобождает. Это снижает число утечек, но у работы GC есть цена — процессорное время.

Поколения: почему сборка дешёвая

GC построен на наблюдаемом факте: большинство объектов умирает молодыми. Поэтому объекты делят по «возрасту»:

ПоколениеЧто тамСтоимость сборки
Gen0Молодые объекты (DTO, строки на запрос)Часто и дёшево
Gen1Пережившие одну сборку (буфер)Дёшево
Gen2Долгоживущие (кэши, синглтоны)Редко и дороже; может давать паузы
LOHКрупные объекты (массивы от ~85 КБ)Собирается вместе с Gen2
Что за «DTO» и что за «строки на запрос»

DTO (Data Transfer Object) — простой объект «для передачи данных», без логики: например, то, что вы отдаёте клиенту в ответе API.

public sealed class UserDto      // ← это и есть DTO
{
    public int    Id   { get; init; }
    public string Name { get; init; } = "";
}

«Строки на запрос» — это строки, которые создаются при обработке каждого запроса и тут же становятся ненужными: собрать JSON-ответ, склеить сообщение для лога, сформировать ключ кэша, отформатировать дату.

Их особенность: их много и они живут очень коротко — то есть как раз Gen0-объекты: создались и сразу умерли.

Как читать таблицу поколений (пример)

При обработке одного запроса к API обычно получается примерно такая картина:

  • Gen0: UserDto, строки для JSON и лога, список результатов — создались на время запроса и умерли.
  • Gen2: DbContext-синглтоны, кэш справочника, настройки — созданы один раз при старте.
  • LOH: большой массив на 1 МБ (например, буфер выгрузки) — попадает сюда, потому что больше 85 КБ (глава 7).

Server GC vs Workstation GC

Для серверных приложений (ASP.NET Core) обычно включён Server GC: отдельная куча и поток GC на ядро. Это повышает пропускную способность ценой большего потребления памяти.

<PropertyGroup>
  <ServerGarbageCollection>true</ServerGarbageCollection>
</PropertyGroup>

Крупные объекты (LOH)

Массивы и буферы от ~85 КБ попадают в Large Object Heap и собираются только вместе с Gen2. Поэтому большие временные буферы дороги: их лучше не создавать заново, а переиспользовать (об этом — глава 7).

★ Что запомнить из главы

Под нагрузкой важна скорость аллокаций, а не объём памяти. Gen0 дёшев, Gen2 и LOH дороже. Практический вывод: не создавать лишний мусор на горячем пути. Как именно — в главе 7; измерять — в главе 21.
