Глава 23. using, await using и IDisposable: кто освобождает ресурсы

Где именно заканчивается жизнь объекта, объявленного через using var, чем это отличается от using (...) со скобками, почему await using — отдельная конструкция и как всё это связано с DI-scope. Поведение проверено запусками на .NET 8.

основная глава

Зачем вообще что-то освобождать

Сборщик мусора освобождает управляемую память: объекты в куче. Но многие ресурсы живут вне кучи и GC о них ничего не знает:

  • TCP-сокет и файловый дескриптор (открытый файл, соединение с БД);
  • аренда места в пуле (соединение, взятое у пула, надо вернуть);
  • блокировка или мьютекс (её надо отпустить, иначе ждут остальные);
  • нативная память, выделенная в C-библиотеке.

Если такой ресурс не освободить, GC рано или поздно соберёт объект-обёртку, но дескриптор может остаться занятым до финализатора, а финализатор работает когда-нибудь. Для сокетов это означает исчерпанные порты, для БД — исчерпанный пул соединений. Поэтому у ресурса есть явный контракт: IDisposable.Dispose() (или IAsyncDisposable.DisposeAsync()), а у языка — две конструкции, которые его гарантированно вызывают: using и await using.

Dispose — это не «удалить объект»

После Dispose() объект остаётся в памяти (и GC его соберёт когда захочет). Dispose освобождает ресурс: закрывает файл, возвращает соединение в пул, отпускает блокировку. Поэтому «вызвать Dispose» и «обнулить ссылку» — разные действия.

using (...): блок, который гарантирует Dispose

Классическая форма — инструкция со скобками. Компилятор разворачивает её в try/finally, поэтому Dispose выполнится и при исключении:

using (var file = File.OpenRead(path))     // Dispose вызовется на закрывающей скобке
{
    var buffer = new byte[1024];
    file.Read(buffer);
}   // ← здесь file.Dispose(), даже если внутри было исключение

// во что это превращается:
var file2 = File.OpenRead(path);
try
{
    var buffer = new byte[1024];
    file2.Read(buffer);
}
finally
{
    file2?.Dispose();
}

Проверим, когда именно вызывается Dispose — с метками времени:

using (new Probe("braces", sw))
{
    Console.WriteLine($"[{sw.ElapsedMilliseconds,3} мс] внутри скобок");
    Thread.Sleep(50);
}
Console.WriteLine($"[{sw.ElapsedMilliseconds,3} мс] после скобок");
[  0 мс] старт
[ 10 мс] внутри скобок
[ 60 мс] Dispose(braces)
[ 60 мс] после скобок

using var: объявление без скобок

Та же гарантия, но записанная иначе: using var x = ...; — это using-объявление (using declaration). Ключевое отличие от скобок одно: ресурс живёт до конца текущего блока — того { }, внутри которого стоит объявление. Не до конца строки и не до конца метода обязательно: до конца именно этого блока.

static void WithDeclaration(Stopwatch sw)
{
    using var p = new Probe("declaration", sw);      // объявили здесь
    Console.WriteLine($"[{sw.ElapsedMilliseconds,3} мс] внутри метода");
    Thread.Sleep(50);
    Console.WriteLine($"[{sw.ElapsedMilliseconds,3} мс] метод заканчивается");
}   // ← Dispose(p) только здесь
[ 61 мс] внутри метода
[111 мс] метод заканчивается
[111 мс] Dispose(declaration)          ← через 50 мс после объявления, в конце блока
[111 мс] после вызова метода с using var

То есть using var — это «объявил и забыл»: компилятор сам оборачивает остаток блока в try/finally. Отсюда три следствия, которые чаще всего и удивляют.

1. Порядок Dispose — обратный порядку объявления

void Run()
{
    using var a = new Probe("a");
    using var b = new Probe("b");
}   // сначала b, потом a
порядок Dispose: Dispose(b), Dispose(a)

Так же ведёт себя и вложенный using (...): using (first) using (second) { } освобождает second, затем first. Это логично: ресурсы освобождаются в порядке, обратном захвату (как в стеке), — и outer-ресурс не остаётся с уже освобождённым inner.

2. В цикле using var живёт до конца итерации

for (var i = 1; i <= 3; i++)
{
    using var c = new Probe($"c{i}");
    Console.WriteLine($"   итерация {i}, до конца блока");
}   // ← Dispose на каждой итерации
   итерация 1, до конца блока
   итерация 2, до конца блока
   итерация 3, до конца блока
Dispose: Dispose(c1), Dispose(c2), Dispose(c3)

Это ровно то поведение, которое нужно в фоновом воркере: объявили контекст в начале тела while — он освободится в конце этой итерации, а не в конце метода.

3. Но всё, что после объявления, — внутри области жизни

Самая практическая ловушка: если объявление стоит в начале длинного блока, ресурс держится до конца блока, включая ожидания, HTTP-вызовы и Task.Delay. Замер на том же Probe:

for (var i = 1; i <= 2; i++)
{
    using var db = new Probe($"db-итерация-{i}", sw);   // объявили в начале
    Console.WriteLine($"итерация {i}: работа");
    Thread.Sleep(100);                                  // «сон» внутри области жизни
    Console.WriteLine($"итерация {i}: сон закончился");
}   // ← Dispose только здесь
[112 мс] итерация 1: работа
[212 мс] итерация 1: сон закончился
[212 мс] Dispose(db-итерация-1)     ← ресурс был занят все 100 мс сна
[212 мс] итерация 2: работа
[313 мс] итерация 2: сон закончился
[313 мс] Dispose(db-итерация-2)

Для DbContext это значит: сам контекст (и всё, что он отслеживает) живёт до конца блока. Соединение EF обычно возвращает в пул сразу после операции, но если внутри блока открыта транзакция или явно открыто соединение — они будут держаться до Dispose. Поэтому «живёт до конца блока» — это про ресурсы объекта, а не только про память. Если нужно отпустить раньше — сузьте блок:

// ✘ контекст живёт весь цикл, включая паузу
while (!ct.IsCancellationRequested)
{
    await using var db = await factory.CreateDbContextAsync(ct);
    await ProcessAsync(db, ct);
    await Task.Delay(1000, ct);        // контекст (и его ChangeTracker) всё ещё жив
}

// ✔ контекст живёт только работу
while (!ct.IsCancellationRequested)
{
    await using (var db = await factory.CreateDbContextAsync(ct))
    {
        await ProcessAsync(db, ct);
    }                                   // ← Dispose здесь, пауза уже без контекста
    await Task.Delay(1000, ct);
}

await using: асинхронное освобождение

Некоторые ресурсы освобождаются асинхронно: закрыть сетевое соединение, отправить финальный пакет, дождаться подтверждения. Для них есть IAsyncDisposable с методом DisposeAsync(), возвращающим ValueTask, и конструкция await using:

public sealed class AsyncProbe(string name, List<string> log) : IAsyncDisposable
{
    public ValueTask DisposeAsync()
    {
        log.Add($"DisposeAsync({name})");
        return ValueTask.CompletedTask;
    }
}

async Task UseAsync()
{
    await using var e = new AsyncProbe("async", log);   // вызовет DisposeAsync, а не Dispose
    Console.WriteLine("тело await using");
}
тело await using
Dispose: DisposeAsync(async)

Правила те же, что у using: область — до конца блока, порядок — обратный, при исключении DisposeAsync всё равно будет ожидаться. Разница только в том, что освобождение можно await-ить. Если тип реализует оба интерфейса, компилятор в await using предпочтёт DisposeAsync, а в обычном using — Dispose.

Скобки или объявление: в чём разница на практике

using (x) { ... }using var x = ...;

Где заканчиваетсяЯвно видно: закрывающая скобкаНе видно: ищи конец блока
Можно сузитьДа — просто поставить скобки раньшеТолько дополнительным блоком { }
Несколько ресурсовusing (a) using (b) { } или using (a, b)* using Probe a = ..., b = ...; (с явным типом)

* using (Probe a = ..., b = ...) — несколько ресурсов в одной инструкции: это одна декларация с несколькими переменными. С var так нельзя (ошибка CS0819: «Implicitly-typed variables cannot have multiple declarators»), нужен явный тип. Порядок освобождения — обратный.

Одинаково ли они работают «под капотом»

Да: обе формы компилируются в try/finally с вызовом Dispose. Разница только в том, где компилятор закрывает try. Поэтому «преимущество» скобок — не производительность, а контроль области жизни: раннее освобождение видно глазами и не зависит от того, где заканчивается метод.

Где using не поможет

  • Объект вам не принадлежит. Если DbContext или HttpClient пришёл из DI, освобождать его вручную не нужно: контейнер сам вызовет Dispose у scoped-сервисов при закрытии scope, а HttpClient из IHttpClientFactory — лёгкая обёртка, которую можно и using, но connection pool живёт отдельно (глава про фабрику в книге паттернов). «Двойной Dispose» обычно безопасен, но признак того, что владение ресурсом определено неверно.
  • Ресурс передан наружу. Если метод возвращает объект, using var внутри метода освободит его до возврата — наружу уедет уже освобождённый объект.
  • Освобождение нужно позже, чем заканчивается блок. Тогда using не подходит: владение должно быть у того, кто живёт дольше (контейнер, scope, вызывающий код).

struct, бокс и using var

Если тип — struct и реализует IDisposable, using вызывает Dispose напрямую, без упаковки. А вот если сначала привести структуру к IDisposable, получится бокс — объект в куче на каждой итерации. Замер на 1 000 000 итераций:

struct using:          0 байт на 1 000 000 итераций
через IDisposable:     24000336 байт на 1 000 000 итераций    (~24 байта на бокс)

Поэтому в горячем коде не «приводите к интерфейсу ради using»: using var s = new StructProbe(); дешевле, чем IDisposable d = s; using (d) { }.

using и DI-scope: кто кого освобождает

В приложении с DI у ресурса часто есть владелец — контейнер. Граница владения — scope: когда scope закрывается, контейнер вызывает Dispose (или DisposeAsync) у всех scoped-сервисов, которые он создал в этом scope. Проверено на сервисе, который просто считает свои освобождения:

E) IServiceScopeFactory один и тот же: True        ← это Singleton
F) два scope -> два экземпляра: True               ← scoped-сервис свой в каждом scope
G) после Dispose scope: освобождено 2              ← контейнер вызвал Dispose за нас

Поэтому в коде, который получил DbContext или репозиторий через конструктор, using не нужен: освободит контейнер. А вот если singleton (фоновый воркер) создаёт scoped-сервис сам, границу нужно создать вручную:

public sealed class Worker(IServiceScopeFactory scopeFactory) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            await using var scope = scopeFactory.CreateAsyncScope();     // граница владения
            var repo = scope.ServiceProvider.GetRequiredService<IOrdersRepository>();

            await repo.DoWorkAsync(ct);
        }   // DisposeAsync(scope) → контейнер освободит repo и всё scoped внутри
    }
}
  • CreateScope() против CreateAsyncScope(). Если среди scoped-сервисов есть реализующий только IAsyncDisposable, обычный CreateScope() при закрытии упадёт: InvalidOperationException: 'AsyncThing' type only implements IAsyncDisposable. Use DisposeAsync to dispose the container. Проверено: CreateAsyncScope() в том же сценарии работает.
  • IServiceScopeFactory — Singleton, его можно держать в поле singleton-сервиса (проверено: один и тот же экземпляр и в корне, и внутри scope). А вот IServiceProvider из корня — нельзя: резолв scoped-сервиса оттуда либо бросит Cannot resolve scoped service ... from root provider, либо (без валидации) отдаст объект, живущий всё время процесса.
  • Scope ≠ using одного объекта. using освобождает один объект; scope освобождает все scoped-сервисы, созданные внутри, в обратном порядке, — это одно и то же правило, применённое к дереву объектов.
  • Scope не хранят в поле и не переиспользуют между операциями: он живёт ровно столько, сколько единица работы.
★ Что запомнить
  • using var освобождает ресурс в конце текущего блока, а не на строке объявления; порядок — обратный порядку объявления.
  • using (...) и using var дают одинаковую гарантию (try/finally), разница — в области жизни и читаемости. Скобки позволяют освободить раньше.
  • await using нужен для IAsyncDisposable (сеть, БД, потоки).
  • Объект, пришедший из DI, освобождает контейнер; ручной using нужен только для того, чем вы владеете сами.
  • using var на struct не создаёт бокс; приведение к IDisposable — создаёт (~24 байта на итерацию).
