Глава 8. Сравнение и порядок: IComparable, IComparer и сортировка

«Равны ли» и «кто раньше» — два разных вопроса с двумя разными интерфейсами. Как устроен CompareTo, зачем нужен IComparer<T>, почему List.Sort и OrderBy дают разный порядок равных элементов и почему строки нельзя сравнивать «просто так».

основная глава

В главе 3 речь шла о равенстве: Equals и GetHashCode отвечают на вопрос «это одно и то же?». Порядок — другой вопрос: «кто из двух раньше?». Он нужен везде, где есть сортировка, бинарный поиск, диапазоны, приоритеты и «взять минимум»:

list.Sort();                     // List<T>.Sort — по умолчанию через CompareTo
array.Sort();                    // Array.Sort
var sorted = query.OrderBy(x => x.Total);      // LINQ
binSearch = Array.BinarySearch(array, key);    // требует отсортированный массив
var set = new SortedSet<int>();  // всегда по порядку
var pq = new PriorityQueue<Job, int>();        // «самый важный» — это тоже порядок

Все они опираются на один контракт — IComparable<T> (у самого типа) или IComparer<T> (снаружи). В главах 6–7 эти интерфейсы встречались как ограничения where T : IComparable<T>; здесь — что они на самом деле обещают.

CompareTo: важен не результат, а знак

Метод возвращает int, но сравнивать его с 1 нельзя: контракт говорит только о знаке — отрицательное значит «я меньше», ноль — «равны», положительное — «я больше».

Console.WriteLine(5.CompareTo(3));       // 1
Console.WriteLine(3.CompareTo(5));       // -1
Console.WriteLine(3.CompareTo(3));       // 0
Console.WriteLine(int.MaxValue.CompareTo(int.MinValue));   // 1

Свой тип имеет право вернуть любые числа нужного знака — и это нормально:

public sealed class BySign : IComparable<BySign>
{
    public int Value { get; init; }

    // -42 и 7 — законные результаты: важен только знак
    public int CompareTo(BySign? other) =>
        Value < other!.Value ? -42 : Value > other.Value ? 7 : 0;
}

Console.WriteLine(Math.Sign(new BySign { Value = 1 }.CompareTo(new BySign { Value = 2 })));  // -1

Отсюда первое правило реализации: не «я минус он». Вычитание переполняется, и порядок ломается молча — без исключения, просто неверно:

int max = int.MaxValue, min = int.MinValue;
Console.WriteLine(unchecked(max - min));      // -1 !

list.Sort((a, b) => a - b);                   // «работает» на маленьких числах и врёт на больших

Вывод

-1

Правильно — a.CompareTo(b) (у чисел он не вычитает, а сравнивает) или Math.Sign. Второе правило: порядок должен быть непротиворечивым — элемент равен сам себе (CompareTo возвращает 0), и если a < b и b < c, то a < c. Проверено экспериментально: если это нарушить, компилятор и рантайм ничего не заметят — сортировка пройдёт и выдаст неправильный порядок. Ошибок не будет, поэтому контракт надо держать в голове.

Кто пользуется CompareTo

Один и тот же контракт обслуживает и сортировку, и поиск, и «взять крайний». Достаточно, чтобы тип умел сравнить себя с другим таким же:

var numbers = new List<int> { 5, 1, 3 };
numbers.Sort();                                   // List<T>.Sort() → CompareTo
Console.WriteLine(string.Join(",", numbers));      // 1,3,5

Console.WriteLine(Array.BinarySearch(new[] { 1, 3, 5, 7 }, 5));   // 2 — индекс
// Array.BinarySearch(new[] { 5, 1, 3 }, 5);       // ✘ на неотсортированном — мусор, не исключение

var set = new SortedSet<int> { 5, 1, 3 };
Console.WriteLine(string.Join(",", set) + " Min=" + set.Min);      // 1,3,5 Min=1

Console.WriteLine(new[] { 3, 1, 2 }.Max());        // 3 — LINQ тоже использует порядок

Вывод

1,3,5
2
1,3,5 Min=1
3

Бинарный поиск отдельно стоит запомнить: он требует отсортированных данных и на неотсортированных не бросает исключение — просто вернёт бессмысленный индекс (или отрицательное число). Это дефект, который живёт в проде годами.

IComparer<T>: порядок снаружи типа

IComparable<T> — это «у типа есть один естественный порядок». Но порядков может быть много: по сумме, по дате, по убыванию, по двум полям. Для этого есть второй интерфейс — IComparer<T>: отдельный объект, который знает, как сравнивать.

// Любой компаратор можно собрать из лямбды
IComparer<int> descending = Comparer<int>.Create((a, b) => b.CompareTo(a));

Console.WriteLine(string.Join(",", new[] { 1, 3, 2 }.OrderBy(x => x, descending)));   // 3,2,1
numbers.Sort(descending);                        // и для List.Sort тоже
Console.WriteLine(string.Join(",", numbers));    // 5,3,1

Вывод

3,2,1
5,3,1

Где брать готовые компараторы:

Что нужноЧем пользоваться
Естественный порядок типаComparer<T>.Default (он же IComparable<T> типа)
Свой порядок из лямбдыComparer<T>.Create((a, b) => …)
Строки: байтовый порядокStringComparer.Ordinal, StringComparer.OrdinalIgnoreCase
Строки: как у людейStringComparer.CurrentCulture, StringComparer.CurrentCultureIgnoreCase
Обратный порядокComparer<T>.Create((a, b) => b.CompareTo(a)) или OrderByDescending
Несколько ключейOrderBy(…).ThenBy(…) — или один компаратор, сравнивающий поля по очереди

Свой компаратор полезен и как отдельный класс — тогда логику можно переиспользовать, тестировать и кэшировать:

public sealed class ByTotalDescending : IComparer<Order>
{
    public int Compare(Order? x, Order? y)
    {
        if (ReferenceEquals(x, y)) return 0;
        if (x is null) return 1;      // null — в конец
        if (y is null) return -1;
        return y.Total.CompareTo(x.Total);      // «y с x» = по убыванию
    }
}

Обратите внимание на null: IComparer<T>.Compare принимает T?, и решать, где стоят null, — обязанность компаратора. Встроенные компараторы считают null самым маленьким:

Console.WriteLine(Comparer<string>.Default.Compare(null, "a"));   // -1
Console.WriteLine("a".CompareTo(null));                          // 1 — string.CompareTo(null) = 1

Вывод

-1
1

Стабильность: List.Sort и OrderBy — разные сортировки

Сортировка стабильна, если равные элементы сохраняют исходный порядок. Это не абстракция: именно на этом держится «сортировка по двум ключам в два прохода» и предсказуемость результатов в отчётах. Возьмём 20 элементов с тремя значениями ключа и отсортируем их двумя способами:

var pairs = Enumerable.Range(0, 20).Select(i => (Key: i % 3, Id: i)).ToList();

var bySort = pairs.ToList();
bySort.Sort((x, y) => x.Key.CompareTo(y.Key));      // List<T>.Sort — НЕстабильная

var byLinq = pairs.OrderBy(x => x.Key).ToList();    // LINQ — стабильная

Console.WriteLine(string.Join(",", bySort.Select(p => p.Id)));
Console.WriteLine(string.Join(",", byLinq.Select(p => p.Id)));

Вывод (net8.0): внутри каждой группы одинаковых ключей — разный порядок

0,15,12,18,6,9,3,4,7,10,13,1,16,19,8,11,2,14,17,5
0,3,6,9,12,15,18,1,4,7,10,13,16,19,2,5,8,11,14,17

OrderBy сохранил исходный порядок внутри групп (0,3,6…), а List.Sort — нет: он использует интроспективную сортировку (introsort), которой стабильность не нужна. Отсюда практические правила:

  • Два ключа — два ключа в одном выражении: OrderBy(x => x.Date).ThenBy(x => x.Id). Это надёжнее, чем «сначала отсортировал по Id, потом по дате» — второй способ работает только при стабильной сортировке.
  • Нужна стабильность при сортировке списка — сортируйте через OrderBy или добавляйте в ключ «тай-брейкер» (уникальный Id).
  • Одинаковые ключи в SortedSet/SortedDictionary — это не «порядок как попало», а дубликаты: второй элемент может не добавиться вовсе.

Строки: культура, регистр и Ordinal

У строк порядок зависит от культуры: string.CompareTo использует текущую культуру потока, а не «побайтовое» сравнение. Один и тот же набор строк сортируется по-разному:

CultureInfo.CurrentCulture = new CultureInfo("ru-RU");

Console.WriteLine("ёж".CompareTo("ель"));      // -1

var words = new[] { "ёж", "ель", "жизнь" };
Console.WriteLine(string.Join(",", words.OrderBy(x => x, StringComparer.CurrentCulture)));
Console.WriteLine(string.Join(",", words.OrderBy(x => x, StringComparer.Ordinal)));

Вывод

-1
ёж,ель,жизнь
ель,жизнь,ёж

В русской культуре «ё» стоит рядом с «е», а в ordinal-порядке — после «ж» (у неё просто больший код символа). Отсюда правило, которое экономит нервы в CI:

  • Идентификаторы, ключи, имена файлов, протоколы, сортировка в тестах — StringComparer.Ordinal: детерминированно и одинаково на любой машине.
  • Текст для человека (список городов, фамилии в UI) — CurrentCulture: тогда «ё» окажется там, где её ждёт читатель.
  • Регистр — отдельный компаратор: OrdinalIgnoreCase или CurrentCultureIgnoreCase; сам по себе CompareTo регистр различает.

null и NaN: у порядка есть крайние случаи

null встроенные компараторы считают самым маленьким, а вот NaN ведёт себя так, что это стоит запомнить: для порядка он «меньше любого числа» и «равен сам себе», хотя обычное == говорит иначе.

Console.WriteLine(double.NaN.CompareTo(1.0));       // -1  — NaN «меньше»
Console.WriteLine(1.0.CompareTo(double.NaN));       // 1
Console.WriteLine(double.NaN.CompareTo(double.NaN)); // 0   — для порядка NaN = NaN

Console.WriteLine(double.NaN == double.NaN);        // False — а обычное равенство так не считает
Console.WriteLine(double.NaN.Equals(double.NaN));   // True

Вывод

-1
1
0
False
True

Поэтому SortedSet<double> спокойно примет NaN (и даже не один — они «равны» по порядку, значит второй не добавится), а HashSet<double> — тоже, потому что Equals для NaN возвращает true. А вот код, который проверяет «отсортировано ли», сравнивая через <, с NaN сломается: и NaN < 1, и 1 < NaN — это false, то есть «ни меньше, ни больше» превращается в «не сравнимо».

Свой тип: IComparable<T> и согласие с Equals

Минимальная реализация — сравнить одно поле через CompareTo этого поля (не через вычитание):

public sealed record Order(int Id, decimal Total) : IComparable<Order>
{
    public int CompareTo(Order? other) =>
        other is null ? 1 : Total.CompareTo(other.Total);   // null — «больше любого»
}

Но здесь спрятана ловушка, которая тихо ломает коллекции. Если CompareTo возвращает 0, а Equals при этом false — два разных заказа с одинаковой суммой поведут себя по-разному в разных коллекциях:

var a = new Order(1, 100m);
var b = new Order(2, 100m);

Console.WriteLine(a.Equals(b) + " " + a.CompareTo(b));    // False 0 — «разные, но порядково равны»

var sorted = new SortedSet<Order> { a, b };
var hash = new HashSet<Order> { a, b };

Console.WriteLine(sorted.Count + " " + hash.Count);       // 1 2

Вывод: множество «по порядку» потеряло один элемент

False 0
1 2

Причина: SortedSet и SortedDictionary ищут дубликаты через порядок (CompareTo == 0), а HashSet и Dictionary — через Equals/GetHashCode. Правило: CompareTo == 0 должно означать Equals == true. Если естественный порядок не различает объекты — сравнивайте больше полей (в примере выше: Total, потом Id), либо не делайте тип IComparable вовсе и передавайте компаратор явно.

Второе следствие того же правила: не сравнивайте результат с 1.

if (a.CompareTo(b) == 1) { }        // ✘ там может быть 5 или 42 — любое положительное
if (a.CompareTo(b) > 0) { }         // ✔

Ловушки

  • a - b вместо CompareTo — переполнение и неверный порядок без единой ошибки (int.MaxValue - int.MinValue = -1, см. выше).
  • Несогласованный компаратор (не транзитивный, «элемент не равен сам себе») не ловится ни компилятором, ни рантаймом: сортировка просто даст неверный результат. Проверено: сортировка с компаратором, который всегда возвращает 1, завершается без исключения.
  • IComparable без <T> — старый интерфейс с object: требует упаковки для значимых типов (глава 4) и падает, если подсунуть чужой тип.
try { 1.CompareTo("a"); }
catch (Exception e) { Console.WriteLine(e.GetType().Name + ": " + e.Message); }

Вывод

ArgumentException: Object must be of type Int32.
  • Array.BinarySearch на неотсортированных данных — не исключение, а бессмысленный результат. Поиск должен идти тем же компаратором, которым сортировали.
  • Ключ, который меняется во время сортировки (поле мутируют из компаратора или из другого потока) — неопределённый результат и «потерянные» элементы.
  • Строки по умолчанию culture-sensitive. Тест, «зелёный локально», в CI с другой локалью может упасть: в проверках берите StringComparer.Ordinal.
  • List.Sort() без компаратора требует IComparable<T>: для типа без него — InvalidOperationException, а не «сортировка по ссылке».
★ Что запомнить из главы
  • CompareTo возвращает знак, а не число: сравнивайте с нулём, никогда с 1. Внутри — a.CompareTo(b), а не a - b (переполнение).
  • IComparable<T> — «естественный порядок у типа»; IComparer<T> — порядок снаружи (Comparer<T>.Create, StringComparer, свой класс).
  • List.Sort нестабилен, OrderBy стабилен. Два ключа — OrderBy(…).ThenBy(…), а не два прохода сортировки.
  • Строки: идентификаторы и тесты — Ordinal, текст для человека — CurrentCulture.
  • Крайние случаи: null меньше всех; NaN «меньше» любого числа и равен сам себе по порядку, хотя == говорит иначе.
  • CompareTo == 0 должно совпадать с Equals == true, иначе SortedSet и HashSet будут вести себя по-разному.
  • Array.BinarySearch требует отсортированных данных тем же компаратором — иначе молча неверный результат.
