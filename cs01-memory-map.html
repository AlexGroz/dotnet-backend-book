Глава 1. Стек, куча и статическая память: карта

Прежде чем говорить про строки, struct и Span, нужно увидеть, где что лежит. Дальше вся книга опирается на эту карту.

подводящая глава

Четыре места, о которых пойдёт речь

┌────────────────────────────────────────────────────────────────────┐
│ 1. СТЕК — у каждого потока свой. Кадры методов: параметры и         │
│    локальные переменные. Освобождается сам при выходе из метода.    │
├────────────────────────────────────────────────────────────────────┤
│ 2. УПРАВЛЯЕМАЯ КУЧА — одна на процесс. Объекты классов, массивы,    │
│    упакованные значения. Освобождает сборщик мусора (GC).           │

├────────────────────────────────────────────────────────────────────┤
│ 3. СТАТИЧЕСКАЯ ПАМЯТЬ — своя у каждого типа: static-поля.           │
│    Живёт до конца работы процесса.                                  │
├────────────────────────────────────────────────────────────────────┤
│ 4. МЕТАДАННЫЕ СБОРКИ — на диске, в файле .dll: код (IL), описание    │

│    литерал становится объектом в куче и попадает в ПУЛ СТРОК.       │
└────────────────────────────────────────────────────────────────────┘

Как это выглядит в коде: слева стек, справа куча, а ссылка их соединяет.

        СТЕК                                  КУЧА
┌──────────────────────┐          ┌──────────────────────────────┐
│ кадр Main()          │          │ объект User                   │
│   user  ─────────────┼─────────►│   Id   = 1                    │
│   count = 42         │          │   Name ──────────────┐       │
└──────────────────────┘          └──────────────────────┼───────┘
                                                         ▼
                                                ┌─────────────────┐
                                                │ "Алексей"        │
                                                │ объект строки    │
                                                └─────────────────┘
  • Стек: user — это не объект, а ссылка (адрес). Сам объект лежит в куче.
  • Куча: объект User содержит поле Name, которое тоже является ссылкой — на объект строки.
  • count — значимый тип: само значение 42 лежит прямо в кадре стека, никакого объекта в куче нет.

Зачем эта карта

Почти все вопросы «почему так» сводятся к одному из трёх: где лежит значение, кто его освободит и сколько стоит его создание. Дальше мы будем возвращаться к этой таблице.

Стек: бесплатно и автоматически

При вызове метода рантайм «откусывает» от стека кусок — кадр: в нём параметры, локальные переменные и адрес возврата. При выходе кадр просто отбрасывается сдвигом указателя.

  • Аллокация на стеке почти бесплатна — это сдвиг указателя, без поиска места и без GC.
  • Освобождать не нужно — кадр исчезает сам.
  • Стек ограничен (обычно ~1 МБ на поток). Глубокая рекурсия даёт StackOverflowException, который нельзя поймать — процесс завершается.
  • Ссылку на стек нельзя сохранить дольше кадра. Именно поэтому существуют ref struct вроде Span<T> (глава 5): они физически не могут «убежать» в кучу.

Куча: объекты, поколения и сборка мусора

Каждый объект в куче — это заголовок (указатель на таблицу методов типа и служебные поля) плюс поля, выровненные по границе 8 байт. Поэтому даже «пустой» объект занимает около 24 байт.

┌──────────────────────────────────────────────────────────────┐
│ SOH (Small Object Heap) — обычные объекты, поколения:        │
│     gen0 — новые объекты        ← аллокация здесь, дёшево     │
│     gen1 — пережили одну сборку                               │
│     gen2 — долгоживущие (кэши, синглтоны)                     │
├──────────────────────────────────────────────────────────────┤
│ LOH (Large Object Heap) — массивы от ~85 000 байт             │
│     собирается вместе с gen2, по умолчанию не уплотняется     │
├──────────────────────────────────────────────────────────────┤
│ POH (Pinned Object Heap, с .NET 5) — объекты, которые должны  │
│     оставаться на месте (для нативной памяти, I/O)            │
└──────────────────────────────────────────────────────────────┘
  • Аллокация — это сдвиг указателя в gen0. Быстро. Дорого становится потом: когда GC собирает мусор и двигает живые объекты.
  • Поколения — оптимизация под наблюдаемый факт: большинство объектов умирает молодыми (подробно — глава 6 .NET-раздела).
  • Большие объекты попадают в LOH и по умолчанию там не двигаются — отсюда фрагментация, о которой помнят при работе с буферами (глава 7 .NET-раздела).
Что изменилось в .NET 5–9
  • .NET 5: появился POH — отдельная куча для «закреплённых» объектов, чтобы они не фрагментировали основной SOH.
  • .NET 7: GC перешёл на регионы вместо сегментов — проще возвращать память ОС и масштабировать кучу.
  • .NET 8: DATAS (Dynamic Adaptation To Application Sizes) — размер кучи подстраивается под реальную нагрузку; появились FrozenDictionary/FrozenSet для быстрых неизменяемых коллекций.
  • .NET 9: продолжены улучшения DATAS, новый System.Threading.Lock (C# 13) и params ReadOnlySpan<T> — меньше аллокаций в типовых сценариях.

Что НЕ изменилось: модель «стек + управляемая куча + статика + пул строк» осталась той же, и все выводы этой книги про .NET 8/9 верны. Меняются детали реализации, а не правила.

Статическая память: где живут static-поля

Короткий ответ: ни на стеке, ни в обычном объекте, который вы создавали. У каждого типа есть собственная «статика», и она выделяется один раз на тип.

public sealed class Config
{
    public static string DefaultPath = "/etc/app";   // статическая память типа Config
    public static readonly int Version = 3;
}

// сколько бы объектов Config вы ни создали, DefaultPath — один на всех.
СТАТИЧЕСКАЯ ПАМЯТЬ ТИПА Config                КУЧА
┌───────────────────────────────┐
│ тип Config:                   │
│   DefaultPath ────────────────┼──────► объект строки "/etc/app"
│   Version = 3                 │
└───────────────────────────────┘
  • Время жизни — до конца процесса; GC их не собирает (это корни).
  • Значимые static-поля хранят значение прямо в блоке статики типа; ссылочные — ссылку на объект в куче.
  • Статический конструктор выполняется один раз, лениво, при первом обращении к типу.
  • Потокобезопасность: изменяемое статическое поле общее для всех потоков — это источник гонок (глава 3 .NET-раздела и глава 10).
«Рядом»: ещё два вида хранения, которые путают со static
ЧтоГде хранитсяВремя жизни
[ThreadStatic]В хранилище конкретного потока (TLS)Пока жив поток
AsyncLocal<T>В ExecutionContext, который копируется при awaitПока длится асинхронная цепочка
constВ метаданных/коде: значение подставляется на этапе компиляцииВсегда (но это не переменная)

Метаданные сборки и пул интернированных строк

Строковый литерал в коде — это не «создание строки» в момент выполнения. Компилятор кладёт его в таблицу метаданных сборки (#US heap), и она лежит в файле .dll на диске, а не в памяти процесса.

При первом обращении к литералу рантайм делает три шага:

  1. смотрит в пул интернированных строк (intern pool): есть ли уже такой объект;
  2. если нет — создаёт объект строки в обычной управляемой куче и записывает его в пул;
  3. возвращает ссылку на этот объект.
  ФАЙЛ СБОРКИ (диск)                     ПРОЦЕСС (память)
┌────────────────────────┐
│ app.dll                │
│  IL-код                │
│  метаданные типов      │      ПУЛ СТРОК (intern pool)
│  таблица строк #US:    │      ┌───────────────────────────┐
│    "Алексей" ──────────┼─────►│ хеш-таблица: ключ → объект│
│    "admin"             │      └────────────┬──────────────┘
└────────────────────────┘                   │ ссылка
                                             ▼
                                 КУЧА ┌──────────────────────┐
                                       │ объект "Алексей"     │
                                       │ (GC его не собирает: │
                                       │  пул держит ссылку)  │
                                       └──────────────────────┘

Отсюда четыре следствия, которые стоит запомнить:

  • Пул — это не отдельная область памяти, а таблица ссылок внутри рантайма; сами строки лежат в обычной управляемой куче.
  • Строки в пуле не собираются GC: пул — корень. Поэтому string.Intern для миллионов разных строк — это утечка.
  • Пул один на процесс (в .NET Core нет изоляции по AppDomain, как было в .NET Framework).
  • Проверка пула не бесплатна: это хеширование. Поэтому интернируют повторяющиеся строки (имена типов, ключи), а не всё подряд.
А есть ли «отдельная» память для литералов?

Деталь реализации: при публикации с ReadyToRun часть предсозданных объектов (включая некоторые литералы) может попасть в frozen segment — «замороженную» область, которая не участвует в обычных поколениях и не собирается. На логику это не влияет: для вас литерал — обычный объект, который живёт всё время работы процесса.

Замыкание: как локальная переменная «переезжает» в кучу

Разберём на конкретном примере — здесь всё видно, если показать, что делает компилятор.

static Func<int> MakeCounter()
{
    int counter = 0;                    // обычная локальная переменная
    Func<int> next = () => ++counter;   // лямбда ИСПОЛЬЗУЕТ counter
    return next;                        // и мы возвращаем её наружу
}

var c1 = MakeCounter();
var c2 = MakeCounter();

Console.WriteLine(c1());   // 1
Console.WriteLine(c1());   // 2   ← помнит предыдущее значение
Console.WriteLine(c1());   // 3
Console.WriteLine(c2());   // 1   ← у второго счётчика своя переменная

В чём проблема. Локальная переменная живёт, пока выполняется метод: после return кадр стека уничтожается, и counter должен исчезнуть. Но лямбда вызывается позже — уже после выхода из MakeCounter — и продолжает видеть counter. Значит, переменная должна жить дольше метода. Стек для этого не годится, поэтому компилятор переносит её в объект в куче.

Во что это превращает компилятор (упрощённо)

// 1) скрытый класс: поле для каждой захваченной переменной
sealed class Closure                    // реальное имя: <>c__DisplayClass0_0
{
    public int counter;                 // ← сюда «переехала» локальная переменная

    public int Next() => ++counter;     // ← сюда переехало тело лямбды
}

// 2) метод теперь создаёт объект этого класса и делегат на его метод
static Func<int> MakeCounter()
{
    var closure = new Closure();        // объект-замыкание в КУЧЕ
    closure.counter = 0;                // начальное значение

    return closure.Next;                // делегат запомнил объект closure
}

Пошагово — что именно произошло:

  1. Какую переменную захватила лямбда? Локальную counter — ту, которую она читает и меняет.
  2. Какой объект появился? Экземпляр скрытого класса Closure (в IL он называется <>c__DisplayClass…). Он создаётся при каждом вызове MakeCounter — поэтому c1 и c2 независимы.
  3. В какое поле переехала переменная? В поле counter этого объекта. В стеке её больше нет: все обращения идут к полю.
  4. Кто держит объект живым? Делегат: он хранит ссылку на closure. Пока жива лямбда, живы и захваченная переменная, и всё, что она держит.
Что в этом «страшного»: три практических следствия
  • Аллокация на каждую лямбду с захватом. В горячем цикле это лишние объекты и мусор для GC (гл. 6, 7 .NET-раздела). Лямбда без захвата (или static-лямбда) объект не создаёт: захватывать нечего.
  • Время жизни. Захваченная переменная — и всё, что она держит (например, DbContext, соединение, большой массив) — живёт, пока жива лямбда, а не пока выполняется метод. Отсюда «странные» утечки.
  • Общая переменная у нескольких лямбд. Если захватить переменную цикла, все лямбды увидят одну переменную — классический баг:
// ✘ все три лямбды захватили ОДНУ переменную i
var actions = new List<Action>();
for (int i = 0; i < 3; i++)
    actions.Add(() => Console.WriteLine(i));
actions.ForEach(a => a());          // 3 3 3

// ✔ копия внутри тела цикла — у каждой лямбды своя переменная
for (int i = 0; i < 3; i++)
{
    int copy = i;
    actions.Add(() => Console.WriteLine(copy));
}
// 0 1 2

async: где живёт состояние после await

Вторая «невидимая» аллокация — машина состояний async-метода. Как именно компилятор её строит — в C# гл. 9; здесь важна только сторона памяти.

async Task<int> LoadAsync(Guid id, CancellationToken ct)
{
    var order = await _db.Orders.FirstAsync(o => o.Id == id, ct);   // ← точка приостановки
    return order.Total;
}

Компилятор превращает метод в машину состояний, у которой:

  • поля — это всё, что нужно помнить между приостановками: id, ct, локальная order, this и текущее состояние (_state);
  • метод MoveNext() — тело вашего метода, разбитое на части вокруг await.

Что происходит по шагам

1. Вы вызвали LoadAsync
   → создана машина состояний (структура) и запущена синхронно
   → она на стеке, в куче пока ничего нет

2. Дошли до await, задача БД ещё не готова
   → машина УПАКОВЫВАЕТСЯ в объект в куче (потому что должна пережить возврат из метода)
   → метод возвращает вызывающему Task<int> («результат будет позже»)
   → поток свободен и уходит обслуживать другие запросы

3. БД ответила
   → продолжение вызывает MoveNext() у той же машины из кучи
   → order берётся из ПОЛЯ машины (в стеке его давно нет)

4. Метод дошёл до return
   → результат кладётся в Task, машина больше не нужна и становится мусором
Отсюда — что это значит на практике
  • Платите один объект состояния за вызов, который реально чего-то ждал. Вызов, завершившийся синхронно (всё уже в кэше), в кучу не уходит — поэтому в горячих местах кэш и ValueTask заметно дешевле (C# гл. 9).
  • Локальные переменные живут дольше метода: order останется в памяти до завершения await. Большой массив или MemoryStream, захваченный перед await, будет держаться всё время ожидания — а при параллельных запросах это умножается на их число.
  • Это не «плохо» и не повод убирать async: альтернатива — блокировка потока — стоит дороже (гл. 9, 12 .NET-раздела). Просто знайте, за что платите.
★ Что запомнить из главы
  • Четыре места: стек (кадры, автоосвобождение), куча (объекты, GC), статика (на тип, до конца процесса), метаданные (в файле сборки).
  • Значимые значения часто живут на стеке — но только если это локальные переменные; поля, массивы, замыкания и await уводят их в кучу.
  • Строковые литералы лежат в метаданных, а во время работы — объектами в куче, на которые ссылается пул интернированных строк.
  • static-поля — не стек и не «ваш» объект: у типа своя статическая память, живущая до конца процесса.
  • Модель памяти в .NET 8/9 та же, что и раньше (менялись детали: POH, регионы GC, DATAS).
