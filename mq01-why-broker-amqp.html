Глава 1. Зачем брокер сообщений и как устроен AMQP

Очередь, обменник и маршрутизация: модель, в которой сообщение находит потребителя

подводящая глава

Зачем вообще брокер

Интеграция «сервис А вызывает сервис Б по HTTP» проста, пока Б доступен. Как только он недоступен, перегружен или обрабатывает операцию десять минут, вызывающий начинает страдать: он ждёт, падает по таймауту или теряет операцию. Брокер сообщений убирает эту связь по времени:

  • Буфер. Сообщения лежат в очереди, пока потребитель не заберёт их — даже если он перезапускается.
  • Развязка по темпу. Producer отдаёт 10 000 сообщений в секунду, consumer обрабатывает 100 — очередь сглаживает разницу.
  • Несколько потребителей. Одно сообщение может уйти в несколько очередей (например, на биллинг и на аналитику) — producer об этом не знает.
  • Повторная обработка. Сообщение можно вернуть в очередь, отложить или отправить в dead-letter очередь, а не «потерять при ошибке».

Цена — новая инфраструктура: брокер надо поднять, мониторить, и он сам становится частью контура надёжности. Поэтому брокер берут там, где нужна именно асинхронность, а не «потому что модно».

Модель AMQP 0-9-1: обменник, привязка, очередь

RabbitMQ работает по протоколу AMQP 0-9-1. В нём producer не пишет в очередь напрямую: он публикует сообщение в exchange (обменник), а тот по binding (привязке) решает, в какие очереди его положить.

producer ──publish(routing key)──▶ exchange ──binding──▶ queue ──consume──▶ consumer
                                      │
                                      └─ тип решает, кому достанется сообщение

direct:  routing key = ключ привязки       (order.new → order.new)
topic:   шаблон с * и #                    (order.* → order.new, order.paid)
fanout:  всем привязанным очередям          (игнорирует routing key)
headers: по значениям заголовков
  • Очередь — это буфер, у неё есть имя, durability и аргументы (TTL, dead-letter, лимит длины). Сообщения хранятся в ней, пока их не подтвердят.
  • Обменник — это правило маршрутизации. Если ни одна привязка не подошла, сообщение отбрасывается (об этом ниже — флаг mandatory).
  • Default exchange — пустая строка "": у него автоматически есть привязки ко всем очередям по их именам. Поэтому publish(exchange: "", routingKey: "payments") кладёт сообщение прямо в очередь payments.
  • Consumer подписывается на очередь и получает сообщения по мере готовности; сколько он держит «в работе» одновременно — регулирует prefetch (глава 3).

Запуск и первая проверка

Для локальной работы — официальный образ с панелью управления (проверено на 3.13.7, Erlang/OTP 26):

docker run --rm -d --name rmq3 -p 5672:5672 -p 15672:15672 rabbitmq:3-management-alpine

# 5672  — AMQP (сюда подключается приложение)
# 15672 — веб-панель: http://localhost:15672 (guest / guest, только с localhost)

docker exec rmq3 rabbitmq-diagnostics -q ping
# Ping succeeded

docker exec rmq3 rabbitmqctl version
# 3.13.7
guest/guest — только для локальной машины

Учётная запись guest по умолчанию может подключаться только с самого узла RabbitMQ. В контейнере это значит «из другого контейнера — уже нет». Для приложения создают отдельного пользователя и отдельный vhost, а guest оставляют для отладки.

Первое сообщение из .NET

Клиент RabbitMQ.Client начиная с 7.x — полностью асинхронный: соединение и канал создаются через await, публикация и подтверждения тоже. Ниже — полный цикл: объявить обменник, очередь и привязку, отправить сообщение и принять его с подтверждением.

using System.Text;
using RabbitMQ.Client;
using RabbitMQ.Client.Events;

var factory = new ConnectionFactory
{
    HostName = "localhost", Port = 5672, UserName = "guest", Password = "guest",
};

await using var conn = await factory.CreateConnectionAsync();
await using var ch   = await conn.CreateChannelAsync();

Console.WriteLine($"connected: {conn.IsOpen}, channel: {ch.IsOpen}");

// обменник topic + очередь + привязка по шаблону
await ch.ExchangeDeclareAsync("orders", ExchangeType.Topic, durable: true);
await ch.QueueDeclareAsync("orders.new", durable: true, exclusive: false, autoDelete: false);
await ch.QueueBindAsync("orders.new", "orders", "order.created");

// публикация: exchange, routing key, тело
var body = Encoding.UTF8.GetBytes("{\"id\":42}");
await ch.BasicPublishAsync("orders", "order.created", body);

// подписка: подтверждаем вручную, после обработки
var consumer = new AsyncEventingBasicConsumer(ch);
consumer.ReceivedAsync += async (_, ea) =>
{
    Console.WriteLine($"received: {Encoding.UTF8.GetString(ea.Body.Span)} tag={ea.DeliveryTag}");
    await ch.BasicAckAsync(ea.DeliveryTag, false);
};

await ch.BasicConsumeAsync("orders.new", autoAck: false, consumer);
await Task.Delay(1500);

var q = await ch.QueueDeclarePassiveAsync("orders.new");
Console.WriteLine($"messages in queue: {q.MessageCount}");
connected: True, channel: True
published 9 bytes
received: {"id":42} tag=1
messages in queue: 0

Разбор вывода:

  • BasicAckAsync убрал сообщение из очереди — поэтому MessageCount равен нулю. Если не подтверждать, сообщение останется в очереди и будет доставлено снова (глава 3).
  • tag=1 — delivery tag, номер доставки в рамках канала; по нему и подтверждают, и отклоняют.
  • QueueDeclarePassiveAsync не создаёт очередь, а спрашивает её состояние (в том числе число сообщений) и падает, если очереди нет — удобно для проверок в тестах.

RabbitMQ, Kafka и список Redis: что выбрать

RabbitMQKafkaRedis list/stream
МодельОчередь: сообщение достаётся одному потребителю (или копии — каждой очереди) Журнал: сообщения читают со своего места, хранятся заданное времяСписок: простой буфер без гарантий
МаршрутизацияБогатая: direct/topic/fanout/headers, DLXТопики и партиции Нет: забрал — и всё
Повторное чтениеНет: подтверждённое сообщение удаляетсяЕсть: сдвиг offset Нет
КогдаЗадачи, команды, RPC, сложная маршрутизацияПотоки событий, аналитика, воспроизведениеЛёгкая очередь внутри одного приложения

Правило простое: если сообщение — команда сделать работу и после выполнения оно больше не нужно, берите RabbitMQ. Если это событие, которое многие будут перечитывать и анализировать, — Kafka.

★ Что запомнить из главы
  • Producer публикует в exchange, а не в очередь; exchange по binding решает, куда положить сообщение.
  • Типы exchange: direct (точный ключ), topic (шаблон), fanout (всем), headers (по заголовкам); пустой "" — default exchange по имени очереди.
  • Сообщение без подходящей привязки исчезает, если не выставлен mandatory (глава 2).
  • Подтверждение (BasicAck) удаляет сообщение; без него оно вернётся другому потребителю.
