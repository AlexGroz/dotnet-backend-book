Глава 1. Зачем брокер сообщений и как устроен AMQP

Очередь, обменник и маршрутизация: модель, в которой сообщение находит потребителя

подводящая глава

Зачем вообще брокер

Интеграция «сервис А вызывает сервис Б по HTTP» проста, пока Б доступен. Как только он недоступен, перегружен или обрабатывает операцию десять минут, вызывающий начинает страдать: он ждёт, падает по таймауту или теряет операцию. Брокер сообщений убирает эту связь по времени:

  • Буфер. Сообщения лежат в очереди, пока потребитель не заберёт их — даже если он перезапускается.
  • Развязка по темпу. Producer отдаёт 10 000 сообщений в секунду, consumer обрабатывает 100 — очередь сглаживает разницу.
  • Несколько потребителей. Одно сообщение может уйти в несколько очередей (например, на биллинг и на аналитику) — producer об этом не знает.
  • Повторная обработка. Сообщение можно вернуть в очередь, отложить или отправить в dead-letter очередь, а не «потерять при ошибке».

Цена — новая инфраструктура: брокер надо поднять, мониторить, и он сам становится частью контура надёжности. Поэтому брокер берут там, где нужна именно асинхронность, а не «потому что модно».

Модель AMQP 0-9-1: обменник, привязка, очередь

RabbitMQ работает по протоколу AMQP 0-9-1. В нём producer не пишет в очередь напрямую: он публикует сообщение в exchange (обменник) и указывает routing key — «адрес на конверте». Кому достанется сообщение, решают две вещи вместе:

  • Тип обменника — это правило сравнения. Тип определяет, как routing key сообщения сопоставляется с привязками: direct требует точного совпадения, topic — совпадения с шаблоном, fanout не сравнивает ничего, headers смотрит на заголовки сообщения.
  • Привязки (bindings) — это участники сравнения. Каждая привязка говорит: «очередь X хочет сообщения из этого обменника с таким-то ключом». Без привязок обменник не отправит сообщение ни в одну очередь — каким бы ни был его тип.
producer ──publish(routing key, заголовки)──▶ exchange ──binding──▶ queue ──consume──▶ consumer
                                                │
        тип обменника — КАК сравнивать routing key с привязками
        привязки      — КАКИЕ очереди и с какими ключами участвуют в сравнении

«Обменник решил по привязке» и «тип решил» — это одна и та же операция с двух сторон: тип — правило, привязки — данные для этого правила. Поэтому обменник не «знает» очереди заранее: он перебирает свои привязки и применяет к каждой правило своего типа.

  • Очередь (queue) — это буфер. У неё есть имя, durability и аргументы (TTL, dead-letter, лимит длины). Сообщения лежат в ней, пока их не подтвердят.
  • Обменник (exchange) — это сортировочный пункт. Сам он сообщения не хранит: он сравнивает routing key с привязками и раскладывает копии по очередям. Если ни одна привязка не подошла, сообщение отбрасывается (как это заметить — флаг mandatory, глава 2).
  • Привязка (binding) — это запись «очередь + ключ». Она создаётся отдельно (QueueBindAsync), у неё есть ключ привязки (для direct и topic) или аргументы с заголовками (для headers).
  • Consumer подписывается на очередь и получает сообщения по мере готовности; сколько он держит «в работе» одновременно — регулирует prefetch (глава 3).

Четыре типа: чем они отличаются

Разница только в правиле сравнения. Возьмём routing key order.created и посмотрим, что сделает с ним каждый тип:

ТипЧто сравниваетПример привязкиЧто дойдёт
direct routing key и ключ привязки должны совпасть точно, символ в символ ключ order.created order.created — да; order.created.eu — нет
topic routing key проверяется по шаблону: * — ровно одно слово, # — ноль и более слов; слова разделены точкой order.* и order.# order.created — оба; order.created.eu — только order.#; order — только order.#
fanout ничего: сообщение получают все очереди, привязанные к обменнику любой ключ — он игнорируется все привязанные очереди, независимо от routing key
headers заголовки сообщения и аргументы привязки: x-match=all — должны совпасть все пары, x-match=any — хотя бы одна x-match=all, format=pdf, type=report сообщения, у которых в заголовках есть нужные пары
Слова и точки в topic

Ключ режется на слова по точке: order.created.eu — три слова. order.* совпадёт с двумя словами, но не с тремя и не с одним; order.# совпадёт и с order, и с order.created.eu. Шаблон работает только целым словом: в order.*.eu звёздочка — отдельное слово, а не часть слова.

Проверка: один и тот же routing key в четырёх типах

Программа создаёт по обменнику каждого типа, привязывает к ним очереди и печатает глубину очередей после каждой публикации (консольный проект .NET 8 с включёнными неявными using; проверено на RabbitMQ 3.13.7, клиент RabbitMQ.Client 7.2.2):

using System.Text;                                                  // Encoding.UTF8.GetBytes
using RabbitMQ.Client;                                              // ConnectionFactory, IChannel, ExchangeType

var factory = new ConnectionFactory { HostName = "localhost" };      // порт 5672 и guest/guest — по умолчанию
await using var conn = await factory.CreateConnectionAsync();       // TCP-соединение с брокером
await using var ch = await conn.CreateChannelAsync();               // канал: в нём живут объявления и публикации

async Task<uint> Depth(string q) =>                                // сколько сообщений в очереди
    (await ch.QueueDeclarePassiveAsync(q)).MessageCount;            // passive: не создаёт, а только спрашивает

async Task Publish(string ex, string rk, string body)               // публикация с паузой
{
    await ch.BasicPublishAsync(ex, rk, Encoding.UTF8.GetBytes(body)); // exchange, routing key, тело
    await Task.Delay(200);                                          // без publisher confirms публикация асинхронна
}

// ---- direct: ключ сообщения и ключ привязки должны совпасть точно
await ch.ExchangeDeclareAsync("ex.direct", ExchangeType.Direct, durable: false, autoDelete: false); // обменник; durable=false — до перезапуска
await ch.QueueDeclareAsync("q.d.created", durable: false, exclusive: false, autoDelete: false);     // очередь для order.created
await ch.QueueDeclareAsync("q.d.paid", durable: false, exclusive: false, autoDelete: false);        // очередь для order.paid
await ch.QueueBindAsync("q.d.created", "ex.direct", "order.created"); // привязка: обменник ex.direct → очередь q.d.created, ключ order.created
await ch.QueueBindAsync("q.d.paid", "ex.direct", "order.paid");       // вторая привязка: тот же обменник, другой ключ
await Publish("ex.direct", "order.created", "1");                     // routing key совпал с первой привязкой
Console.WriteLine($"direct order.created    -> created={await Depth("q.d.created")} paid={await Depth("q.d.paid")}");
await Publish("ex.direct", "order.created.eu", "1");                  // не совпал ни с одной привязкой
Console.WriteLine($"direct order.created.eu -> created={await Depth("q.d.created")} paid={await Depth("q.d.paid")}");

// ---- topic: ключ проверяется по шаблону, * — одно слово, # — ноль и более
await ch.ExchangeDeclareAsync("ex.topic", ExchangeType.Topic, durable: false, autoDelete: false);   // обменник topic
await ch.QueueDeclareAsync("q.t.star", durable: false, exclusive: false, autoDelete: false);        // очередь под шаблон order.*
await ch.QueueDeclareAsync("q.t.hash", durable: false, exclusive: false, autoDelete: false);        // очередь под шаблон order.#
await ch.QueueBindAsync("q.t.star", "ex.topic", "order.*");           // ключ привязки — шаблон «order и ровно одно слово»
await ch.QueueBindAsync("q.t.hash", "ex.topic", "order.#");           // ключ привязки — шаблон «order и сколько угодно слов»
await Publish("ex.topic", "order.created", "1");                      // два слова: подходят оба шаблона
Console.WriteLine($"topic  order.created    -> star={await Depth("q.t.star")} hash={await Depth("q.t.hash")}");
await Publish("ex.topic", "order.created.eu", "1");                   // три слова: подходит только order.#
Console.WriteLine($"topic  order.created.eu -> star={await Depth("q.t.star")} hash={await Depth("q.t.hash")}");
await Publish("ex.topic", "order", "1");                              // одно слово: # допускает ноль слов после order
Console.WriteLine($"topic  order            -> star={await Depth("q.t.star")} hash={await Depth("q.t.hash")}");

// ---- fanout: ключи не сравниваются вообще
await ch.ExchangeDeclareAsync("ex.fanout", ExchangeType.Fanout, durable: false, autoDelete: false); // обменник fanout
await ch.QueueDeclareAsync("q.f.one", durable: false, exclusive: false, autoDelete: false);         // первая очередь
await ch.QueueDeclareAsync("q.f.two", durable: false, exclusive: false, autoDelete: false);         // вторая очередь
await ch.QueueBindAsync("q.f.one", "ex.fanout", "");                  // ключ привязки пустой — и это нормально
await ch.QueueBindAsync("q.f.two", "ex.fanout", "ignored.key");       // можно написать что угодно: fanout его не смотрит
await Publish("ex.fanout", "any.key", "1");                           // получат обе очереди
Console.WriteLine($"fanout any.key          -> one={await Depth("q.f.one")} two={await Depth("q.f.two")}");

// ---- headers: сравниваются заголовки сообщения и аргументы привязки
await ch.ExchangeDeclareAsync("ex.headers", ExchangeType.Headers, durable: false, autoDelete: false); // обменник headers
await ch.QueueDeclareAsync("q.h.all", durable: false, exclusive: false, autoDelete: false);           // очередь «все пары»
await ch.QueueDeclareAsync("q.h.any", durable: false, exclusive: false, autoDelete: false);           // очередь «любая пара»
await ch.QueueBindAsync("q.h.all", "ex.headers", "", new Dictionary<string, object?>   // привязка с аргументами
{
    ["x-match"] = "all", ["format"] = "pdf", ["type"] = "report",     // нужны оба заголовка и x-match=all
});
await ch.QueueBindAsync("q.h.any", "ex.headers", "", new Dictionary<string, object?>   // вторая привязка
{
    ["x-match"] = "any", ["format"] = "pdf", ["type"] = "report",     // достаточно одного совпадения
});

async Task PublishHeaders(Dictionary<string, object?> h)              // публикация с заголовками
{
    var props = new BasicProperties { Headers = h };                  // заголовки живут в свойствах сообщения
    await ch.BasicPublishAsync("ex.headers", "", mandatory: false, basicProperties: props, body: Encoding.UTF8.GetBytes("1"));
    await Task.Delay(200);                                            // пауза, чтобы брокер разложил сообщение
    Console.WriteLine($"headers {string.Join(",", h.Select(kv => $"{kv.Key}={kv.Value}"))} -> all={await Depth("q.h.all")} any={await Depth("q.h.any")}");
}

await PublishHeaders(new() { ["format"] = "pdf" });                   // all: не хватает type, any: хватает format
await PublishHeaders(new() { ["format"] = "pdf", ["type"] = "report" }); // all: обе пары на месте
await PublishHeaders(new() { ["format"] = "csv", ["type"] = "report" }); // all: format не тот, any: type совпал
direct order.created    -> created=1 paid=0
direct order.created.eu -> created=1 paid=0
topic  order.created    -> star=1 hash=1
topic  order.created.eu -> star=1 hash=2
topic  order            -> star=1 hash=3
fanout any.key          -> one=1 two=1
headers format=pdf -> all=0 any=1
headers format=pdf,type=report -> all=1 any=2
headers format=csv,type=report -> all=1 any=3

Что видно в выводе:

  • direct — order.created попало только в свою очередь, а order.created.eu не совпало ни с одним ключом: created=1 paid=0 не изменилось, сообщение исчезло.
  • topic — order.* поймал два слова, но не три (star=1), а order.# поймал и order.created.eu, и даже order без хвоста (hash=3).
  • fanout — ключи привязок "" и ignored.key ни на что не повлияли: сообщение с ключом any.key получили обе очереди.
  • headers — x-match=all требует все пары (с одним заголовком очередь осталась пустой), x-match=any — хотя бы одну.

Default exchange: обменник с пустым именем

Обменник с именем "" — не «без обменника» и не сокращение: это настоящий обменник, который существует в каждом vhost с момента его создания. У него тип direct и durable: true, и у него уже есть привязка к каждой очереди — с ключом, равным имени очереди. Поэтому публикация с пустым именем обменника попадает прямо в очередь:

await ch.QueueDeclareAsync("payments", durable: false, exclusive: false, autoDelete: false); // объявляем очередь payments
await ch.BasicPublishAsync("", "payments", Encoding.UTF8.GetBytes("hello"));                 // exchange "", routing key = имя очереди
await Task.Delay(300);                                                                       // даём брокеру разложить сообщение
var q = await ch.QueueDeclarePassiveAsync("payments");                                       // спрашиваем состояние очереди
Console.WriteLine($"payments depth after publish to \"\": {q.MessageCount}");                // 1

Теперь посмотрим на брокер со стороны: в списке обменников он последний — с пустым именем, а в списке привязок появляется строка с пустым source_name:

docker exec rmq3 rabbitmqctl list_exchanges name type
# Listing exchanges for vhost / ...
# name                type
# amq.direct          direct
# amq.topic           topic
# amq.headers         headers
# amq.fanout          fanout
# amq.rabbitmq.trace  topic
# amq.match           headers
#                     direct      <- пустое имя: это и есть default exchange

docker exec rmq3 rabbitmqctl list_bindings source_name destination_name routing_key
# Listing bindings for vhost /...
# source_name  destination_name  routing_key
#              payments          payments    <- неявная привязка: из "" в очередь payments по ключу payments

docker exec rmq3 rabbitmqctl list_queues name messages
# name      messages
# payments  1

Объявить его, привязать к нему очередь или удалить его нельзя: сервер отвечает 403 ACCESS_REFUSED и закрывает канал, в котором была команда. Это касается и «безобидной» проверки ExchangeDeclarePassiveAsync("") — она падает так же:

try
{
    await ch.QueueBindAsync("payments", "", "payments");   // попытка привязать очередь к default exchange
}
catch (Exception e)
{
    Console.WriteLine(e.Message);
    // ... code=403, text='ACCESS_REFUSED - operation not permitted on the default exchange'
    Console.WriteLine($"channel open: {ch.IsOpen}");       // False: канал уже закрыт брокером
}
Тихая потеря на default exchange

Если routing key не совпал с именем ни одной очереди, ошибки не будет: сообщение исчезнет, а канал останется открытым (проверено: publish("", "no-such-queue", ...) → open=True). Заметить потерю можно только флагом mandatory: true — тогда брокер вернёт сообщение с кодом 312 NO_ROUTE (глава 2).

Default exchange удобен там, где маршрут — «ровно одна очередь с известным именем». Как только нужна копия в несколько очередей или фильтрация по шаблону, объявляют свой обменник: default exchange больше ничего не умеет.

Запуск и первая проверка

Для локальной работы — официальный образ с панелью управления (проверено на 3.13.7, Erlang/OTP 26):

# образ rabbitmq:3-management-alpine = RabbitMQ 3.x + плагин веб-панели, на Alpine Linux
# ключи docker run:
#   --rm          удалить контейнер после остановки (данные внутри пропадут)
#   -d            запустить в фоне; без -d терминал займут логи брокера
#   --name rmq3   имя контейнера — по нему работают docker exec и docker rm
#   -p 5672:5672      пробросить порт AMQP (host:container) — сюда подключается .NET
#   -p 15672:15672    пробросить порт веб-панели: http://localhost:15672
docker run --rm -d --name rmq3 -p 5672:5672 -p 15672:15672 rabbitmq:3-management-alpine

# брокер стартует 10-20 секунд; команда ждёт, пока узел будет готов
docker exec rmq3 rabbitmqctl await_startup
# Still booting, will check again in 10 seconds...   <- пока брокер не готов
# (когда готов — команда завершается без вывода)

# ping — «узел жив?»; -q оставляет только результат (без служебных строк)
docker exec rmq3 rabbitmq-diagnostics -q ping
# Ping succeeded

# версия RabbitMQ внутри контейнера
docker exec rmq3 rabbitmqctl version
# 3.13.7

# обменники: name — имя, type — тип; строка с пустым именем в конце — default exchange
docker exec rmq3 rabbitmqctl list_exchanges name type

# очереди: name — имя, messages — сколько сообщений лежит прямо сейчас
docker exec rmq3 rabbitmqctl list_queues name messages

# привязки: source_name — обменник, destination_name — очередь, routing_key — ключ привязки
docker exec rmq3 rabbitmqctl list_bindings source_name destination_name routing_key

Первое сообщение из .NET

Клиент RabbitMQ.Client начиная с 7.x — полностью асинхронный: соединение и канал создаются через await, публикация и подтверждения тоже. Ниже — полный цикл: объявить обменник, очередь и привязку, отправить сообщение и принять его с подтверждением.

using System.Text;                                             // Encoding.UTF8.GetBytes
using RabbitMQ.Client;                                         // ConnectionFactory, IChannel, ExchangeType
using RabbitMQ.Client.Events;                                  // AsyncEventingBasicConsumer, BasicDeliverEventArgs

var factory = new ConnectionFactory                            // объект с настройками подключения
{
    HostName = "localhost", Port = 5672,                       // адрес и порт AMQP (не 15672 — это панель)
    UserName = "guest", Password = "guest",                    // логин и пароль по умолчанию
};

await using var conn = await factory.CreateConnectionAsync();   // TCP-соединение; await using закроет его в конце
await using var ch   = await conn.CreateChannelAsync();         // канал: через него идут объявления и публикации

Console.WriteLine($"connected: {conn.IsOpen}, channel: {ch.IsOpen}"); // connected: True, channel: True

// объявления идемпотентны: если объект уже есть с теми же параметрами, ошибки не будет
await ch.ExchangeDeclareAsync("orders", ExchangeType.Topic, durable: true);    // обменник orders, правило topic, переживает рестарт
await ch.QueueDeclareAsync("orders.new", durable: true, exclusive: false, autoDelete: false); // очередь orders.new, тоже durable
await ch.QueueBindAsync("orders.new", "orders", "order.created");              // привязка: orders -> orders.new по ключу order.created

var body = Encoding.UTF8.GetBytes("{\"id\":42}");               // тело сообщения — массив байт, не строка
await ch.BasicPublishAsync("orders", "order.created", body);     // публикация: exchange, routing key, тело
Console.WriteLine($"published {body.Length} bytes");             // published 9 bytes

var consumer = new AsyncEventingBasicConsumer(ch);              // потребитель, привязанный к каналу
consumer.ReceivedAsync += async (_, ea) =>                      // обработчик каждой доставки
{
    Console.WriteLine($"received: {Encoding.UTF8.GetString(ea.Body.Span)} tag={ea.DeliveryTag}"); // тело и номер доставки
    await ch.BasicAckAsync(ea.DeliveryTag, false);               // подтверждаем: false — только это сообщение
};

await ch.BasicConsumeAsync("orders.new", autoAck: false, consumer); // подписка с ручными подтверждениями
await Task.Delay(1500);                                         // даём consumer время обработать сообщение

var q = await ch.QueueDeclarePassiveAsync("orders.new");         // passive: очередь не создаётся, а спрашивается
Console.WriteLine($"messages in queue: {q.MessageCount}");       // messages in queue: 0
connected: True, channel: True
published 9 bytes
received: {"id":42} tag=1
messages in queue: 0

Разбор вывода:

  • connected: True, channel: True — соединение с брокером и канал открыты; published 9 bytes — длина тела в байтах (строка {"id":42} — это 9 символов).
  • BasicAckAsync убрал сообщение из очереди — поэтому MessageCount равен нулю. Если не подтверждать, сообщение останется в очереди и будет доставлено снова (глава 3).
  • tag=1 — delivery tag, номер доставки в рамках канала; по нему и подтверждают, и отклоняют.
  • QueueDeclarePassiveAsync не создаёт очередь, а спрашивает её состояние (в том числе число сообщений) и падает, если очереди нет — удобно для проверок в тестах.

Теперь те же строки по аргументам — что означает каждый параметр вызова:

В IChannelExtensions у QueueDeclareAsync параметры по умолчанию такие: durable: false, exclusive: true, autoDelete: true. То есть вызов QueueDeclareAsync("orders.new") создаст очередь, которая исчезнет вместе с соединением: rabbitmqctl list_queues name durable auto_delete exclusive показывает false true true, а после закрытия соединения очереди уже нет. Повторное объявление той же очереди с другими флагами падает с 405 RESOURCE_LOCKED. Поэтому флаги в примере выше заданы явно.

RabbitMQ, Kafka и список Redis: что выбрать

RabbitMQKafkaRedis list/stream

МаршрутизацияБогатая: direct/topic/fanout/headers, DLXТопики и партиции Нет: забрал — и всё

Правило простое: если сообщение — команда сделать работу и после выполнения оно больше не нужно, берите RabbitMQ. Если это событие, которое многие будут перечитывать и анализировать, — Kafka.

★ Что запомнить из главы
  • Producer публикует в exchange, а не в очередь; маршрут определяют две вещи: тип обменника (правило сравнения) и привязки (какие очереди и с какими ключами).
  • Типы exchange: direct (точный ключ), topic (* — одно слово, # — ноль и более), fanout (всем привязанным, ключ игнорируется), headers (x-match=all / any).
  • Пустой "" — это default exchange: существует всегда, тип direct, неявная привязка к каждой очереди по её имени; объявить, привязать или удалить его нельзя (403 ACCESS_REFUSED).
  • Сообщение без подходящей привязки исчезает, если не выставлен mandatory (глава 2); на default exchange это происходит при несовпадении ключа с именем очереди.
  • Подтверждение (BasicAck) удаляет сообщение; без него оно вернётся другому потребителю.
