Глава 33. Мониторинг и эксплуатация

Четыре вопроса дежурного — «кто работает», «что тормозит», «кто кого блокирует», «не раздулась ли таблица» — и представления PostgreSQL, которые отвечают на них. Все выводы в главе получены на живой базе PostgreSQL 16.15.

Всё это — обычные представления и функции; их можно опрашивать из того же psql, из Npgsql (глава 32) и из систем мониторинга. Права: обычный пользователь видит свои запросы полностью, а чужие — с усечённым текстом, поэтому для дежурства нужна роль с pg_read_all_stats (или суперпользователь).

pg_stat_activity: кто работает и чего ждёт

Одна строка — одно соединение. Важные колонки:

SELECT pid,                  -- идентификатор серверного процесса (по нему можно убить/отменить)
       usename,              -- роль, под которой подключились
       application_name,     -- имя из строки подключения (глава 32)
       client_addr,          -- IP клиента; NULL — локальное подключение
       state,                -- active / idle / idle in transaction / idle in transaction (aborted)
       wait_event_type,      -- чего ждёт: Lock, IO, Client, Timeout, LWLock, …
       wait_event,           -- конкретнее: transactionid, PgSleep, ClientRead, …
       now() - query_start AS running_for,   -- сколько выполняется текущий запрос
       now() - state_change AS in_state_for, -- сколько находится в этом состоянии
       left(query, 80) AS query              -- текст; чужие запросы могут быть усечены
FROM pg_stat_activity
WHERE backend_type = 'client backend'   -- только клиентские соединения, без фоновых процессов
ORDER BY query_start NULLS LAST;        -- сверху — самые давно работающие

Главное различие: state отвечает «что делает», а wait_event — «на что застряло». Пример из прогона: две сессии, первая держит транзакцию и спит, вторая ждёт её блокировку.

 pid  | state  | wait_event_type |  wait_event   | blockers
------+--------+-----------------+---------------+----------
 4043 | active | Timeout         | PgSleep       | {}
 4050 | active | Lock            | transactionid | {4043}

Читается так: 4043 «работает», но на самом деле спит в pg_sleep (тип ожидания Timeout), а 4050 ждёт блокировку транзакции (Lock / transactionid), и виноват в этом 4043 — колонка blockers из pg_blocking_pids(pid).

Три состояния, которые надо узнавать
  • idle in transaction — транзакция открыта, но сервер ничего не делает. Это худшее состояние: снимок держится, VACUUM не может убрать мёртвые версии, блокировки висят. Причина почти всегда — «открыли транзакцию и ушли в HTTP-вызов».
  • idle in transaction (aborted) — в транзакции была ошибка, и её забыли завершить; дальше все команды в этой сессии будут падать.
  • active + wait_event_type = Lock — запрос ждёт чужую блокировку, а не работает. Высокий CPU тут не при чём: время уходит на ожидание.

Блокировки: кто кого держит

Читать pg_locks напрямую утомительно, но в паре с pg_blocking_pids() он отвечает на главный вопрос сразу. Снимок во время ожидания из прогона:

 pid  | locktype |       mode       | granted | blockers
------+----------+------------------+---------+----------
 4043 | relation | RowExclusiveLock | t       | {}
 4050 | relation | RowExclusiveLock | t       | {4043}
 4050 | tuple    | ExclusiveLock    | t       | {4043}

Разбор: обе сессии взяли RowExclusiveLock на таблицу — он совместим, поэтому обе получили его (granted = t). А вот tuple-блокировку на строку вторая сессия получить не смогла: она ждёт освобождения транзакции первой, на что и указывают wait_event = transactionid и blockers = {4043}.

SELECT pid,                 -- чей процесс
       locktype,             -- relation / tuple / transactionid / virtualxid / …
       mode,                 -- RowExclusiveLock, ExclusiveLock, AccessShareLock, …
       granted,              -- t — блокировка получена, f — ждём
       pg_blocking_pids(pid) -- массив PID, которые держат нужную блокировку
FROM pg_locks
WHERE relation = 'mon_orders'::regclass   -- только блокировки этой таблицы
ORDER BY pid, locktype, mode;

Таймауты вместо бесконечного ожидания

Чтобы приложение не висело в очереди на блокировку, ставят два предела — оба проверены на живой базе:

SET lock_timeout = '500ms';                          -- сколько ждать блокировку, максимум
UPDATE mon_orders SET total = total WHERE id = 1;    -- ждёт чужую транзакцию
-- ERROR:  canceling statement due to lock timeout
-- CONTEXT:  while updating tuple (0,2) in relation "mon_orders"

SET statement_timeout = '200ms';                     -- сколько может выполняться сама команда
SELECT pg_sleep(1);                                  -- заведомо дольше предела
-- ERROR:  canceling statement due to statement timeout

Разница: lock_timeout ограничивает ожидание блокировки, а statement_timeout — всё время команды. Оба можно выставить на уровне роли (ALTER ROLE app SET lock_timeout = '2s') — это надёжнее, чем надеяться на дисциплину в коде.

Отменить или убить

-- отменить текущий запрос: соединение остаётся, транзакция будет откачена
SELECT pg_cancel_backend(4118);   -- вернул t — сигнал отправлен

-- закрыть соединение целиком: когда сессия «залипла» (idle in transaction)
SELECT pg_terminate_backend(4118);

В логе отменённый запрос выглядит так (проверено): ERROR: canceling statement due to user request, SQLSTATE 57014 (query_canceled) — в приложении это не сбой БД, если отменяли вы сами (например, по CancellationToken).

pg_stat_statements: что тормозит

Расширение собирает статистику по нормализованным запросам: параметры заменяются на $1, поэтому тысяча вызовов с разными id — одна строка. Включается в два шага:

# 1) Загрузить библиотеку при старте сервера (нужен перезапуск).
docker run -d --name sqldemo \                     # -d: в фоне, --name: имя контейнера
  -e POSTGRES_PASSWORD=secret \                    # -e: переменная окружения, пароль postgres
  -e POSTGRES_DB=demo \                            # создать базу demo при первом старте
  -p 55432:5432 \                                  # -p хост:контейнер — пробросить порт 5432 наружу
  postgres:16-alpine \                             # образ и тег
  -c shared_preload_libraries=pg_stat_statements \ # -c: параметр сервера, загрузить расширение
  -c pg_stat_statements.track=all \                # считать все запросы, включая вложенные
  -c log_min_duration_statement=200 \              # в лог — всё, что дольше 200 мс
  -c track_io_timing=on                            # измерять время ввода-вывода в статистике

# 2) Создать расширение в базе (один раз)
docker exec -i sqldemo psql -U postgres -d demo -c 'CREATE EXTENSION pg_stat_statements'

Дальше — обычный SQL. Замер после сброса статистики и нескольких запросов:

SELECT pg_stat_statements_reset();          -- обнулить накопленное (перед экспериментом)

SELECT calls,                                -- сколько раз вызывали
       round(total_exec_time::numeric, 1) AS total_ms,   -- суммарное время выполнения
       round(mean_exec_time::numeric, 2) AS mean_ms,     -- среднее на вызов
       rows,                                 -- сколько строк вернули всего
       shared_blks_hit AS hit,               -- страниц взято из кеша
       shared_blks_read AS read,             -- страниц прочитано с диска
       left(query, 45) AS query              -- нормализованный текст
FROM pg_stat_statements
ORDER BY total_exec_time DESC                -- «что съело больше всего времени суммарно»
LIMIT 6;
 calls | total_ms | mean_ms | rows | hit | read |                     query
-------+----------+---------+------+-----+------+-----------------------------------------------
     1 |    300.4 |  300.37 |    1 |   0 |    0 | SELECT pg_sleep($1)
     1 |     18.0 |   17.98 |    2 | 358 |    0 | SELECT status, count(*) FROM mon_orders GROUP
     1 |      4.4 |    4.38 |    1 | 148 |    0 | SELECT count(*) FROM mon_orders WHERE status
     1 |      0.1 |    0.11 |    5 |   8 |    0 | SELECT * FROM mon_orders WHERE total = $1 LIM
     1 |      0.1 |    0.07 |    1 |   7 |    0 | SELECT * FROM mon_orders WHERE id = $1

Как читать: total_exec_time отвечает «куда уходит время в сумме», mean_exec_time — «что медленно по одному вызову». Частый запрос с маленьким средним может съесть больше, чем один медленный, поэтому смотрят два среза — по сумме и по среднему с фильтром по числу вызовов:

SELECT round(mean_exec_time::numeric, 1) AS mean_ms, calls, left(query, 60) AS query
FROM pg_stat_statements
WHERE calls > 100                -- отбрасываем редкие «одноразовые» запросы
ORDER BY mean_exec_time DESC     -- самый медленный в среднем
LIMIT 10;
Что ещё есть в pg_stat_statements
  • shared_blks_hit/shared_blks_read — попадания в кеш и чтения с диска: запрос с большим read — кандидат на индекс или на уменьшение выборки.
  • temp_blks_written — временные файлы: сортировка или хеш не влезли в work_mem.
  • wal_bytes — сколько журнала записал запрос: видно нагрузку на репликацию.
  • Сбрасывать статистику (pg_stat_statements_reset()) стоит перед экспериментом, но не в проде «просто так»: история пропадёт.

Индексы: кто работает, а кто мёртвый груз

Два представления закрывают вопрос «нужен ли этот индекс»: pg_stat_user_indexes (сколько раз индекс использовали) и pg_stat_user_tables (сколько раз таблицу читали последовательно).

SELECT indexrelname,     -- имя индекса
       idx_scan,         -- сколько раз по нему искали
       idx_tup_read      -- сколько строк из него прочитали
FROM pg_stat_user_indexes
WHERE relname = 'mon_orders'      -- таблица, к которой относится индекс
ORDER BY indexrelname;
     indexrelname      | idx_scan | idx_tup_read
-----------------------+----------+--------------
 mon_orders_pkey       |        7 |            7
 mon_orders_status_idx |        5 |       333333
 mon_orders_unused_idx |        1 |            5

Читается так: pkey использовался 7 раз (точечные выборки по id), индекс по status — 5 раз, но вытащил 333 тысячи строк, а unused_idx — 1 раз и 5 строк. Индекс с idx_scan = 0 на протяжении недели-двух — кандидат на удаление: он занимает место и замедляет каждую вставку и обновление. Но сначала проверьте, что он не обслуживает уникальность или внешний ключ: такие индексы «не читаются», а работают как ограничение.

SELECT relname, seq_scan, seq_tup_read, idx_scan, n_live_tup, n_dead_tup,
       last_autovacuum, autovacuum_count
FROM pg_stat_user_tables
ORDER BY seq_scan DESC           -- сверху — таблицы, которые читают целиком
LIMIT 10;

seq_scan много больше idx_scan при большой n_live_tup — сигнал, что либо индекса нет, либо он не подходит под запросы (глава 12), либо запрос написан так, что индекс невозможен.

Раздувание индекса: pgstatindex

Индекс тоже состоит из страниц, и после массовых UPDATE в нём остаются «мёртвые» страницы. Проверка одного индекса (расширение pgstattuple, в прогоне — после 400 тысяч обновлений):

SELECT * FROM pgstatindex('mon_orders_unused_idx');
 tree_level | index_size | leaf_pages | deleted_pages | avg_leaf_density | leaf_fragmentation
------------+------------+------------+---------------+------------------+--------------------
          2 |   20783104 |       1524 |          1000 |            32.52 |              62.86

deleted_pages = 1000 и avg_leaf_density = 32.52 %: две трети места в листьях пустует, страницы разбросаны (leaf_fragmentation = 62.86 %). Лечится пересборкой — REINDEX INDEX CONCURRENTLY mon_orders_unused_idx: CONCURRENTLY строит новый индекс параллельно и подменяет его без блокировки записи (обычный REINDEX берёт блокировку и останавливает работу с таблицей).

Bloat: почему VACUUM не уменьшает размер

Самый частый вопрос дежурного: «сделал VACUUM, а таблица того же размера». Прогон на таблице в 200 тысяч строк, у которой отключён autovacuum и сделано 400 тысяч обновлений:

до VACUUM:          n_dead_tup = 466666, total_size = 70 MB (heap 31 MB, indexes 39 MB)
после VACUUM:       n_dead_tup = 0,      total_size = 70 MB (heap 31 MB, indexes 39 MB)
после VACUUM FULL:                       total_size = 21 MB

Причина: VACUUM помечает место как свободное для повторного использования, но не отдаёт его операционной системе. Таблица не «худеет», она перестаёт расти: новые версии строк ложатся в освободившиеся страницы. Это видно через pgstattuple:

SELECT * FROM pgstattuple('mon_orders');   -- расширение pgstattuple
 table_len | tuple_percent | dead_tuple_percent | free_percent
-----------+---------------+--------------------+--------------
  36143104 |         30.99 |               0.00 |        66.42

free_percent = 66.42 — две трети файла пустует, но место занято. Вернуть его можно только перезаписью: VACUUM FULL mon_orders (в прогоне 70 МБ → 21 МБ), но он держит ACCESS EXCLUSIVE — таблица недоступна всё время работы. Для больших таблиц вместо него используют пересборку без блокировки (расширение pg_repack) — отдельная установка и отдельная процедура.

Порог autovacuum: откуда берётся

Autovacuum запускается, когда мёртвых строк больше, чем autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor × n_live_tup. Значения по умолчанию в прогоне: autovacuum_vacuum_threshold = 50, autovacuum_vacuum_scale_factor = 0.2, autovacuum_naptime = 1min. Для таблицы на 200 000 строк порог = 50 + 0.2 × 200 000 = 40 050 мёртвых строк. Для таблицы на 50 млн это уже 10 млн — слишком поздно, поэтому у больших таблиц scale_factor понижают на уровне таблицы: ALTER TABLE big SET (autovacuum_vacuum_scale_factor = 0.01).

SELECT relname, n_live_tup, n_dead_tup,
       round(100.0 * n_dead_tup / nullif(n_live_tup + n_dead_tup, 0), 1) AS dead_pct,
       last_vacuum, last_autovacuum, vacuum_count, autovacuum_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC          -- сверху — самые «грязные» таблицы
LIMIT 10;

Общая картина: pg_stat_database и pg_stat_io

Прежде чем лезть в конкретные запросы, полезно посмотреть на базу целиком — один запрос даёт большинство «здоровых» метрик:

SELECT datname,                                   -- имя базы
       xact_commit,                               -- успешных транзакций
       xact_rollback,                             -- откатов
       blks_read,                                 -- страниц прочитано с диска
       blks_hit,                                  -- страниц взято из кеша
       round(100.0 * blks_hit / nullif(blks_hit + blks_read, 0), 2) AS cache_hit_pct,
       temp_files,                                -- временных файлов создано
       deadlocks                                  -- обнаруженных дедлоков
FROM pg_stat_database
WHERE datname = current_database();
 datname | xact_commit | xact_rollback | blks_read | blks_hit | cache_hit_pct | temp_files | deadlocks
---------+-------------+---------------+-----------+----------+---------------+------------+-----------
 demo    |       77861 |            19 |      1178 | 36988237 |        100.00 |         11 |         0

Как читать: cache_hit_pct близко к 100 — данные в памяти, диск почти не читается (на «прогретой» базе это норма). Рост temp_files — нехватка work_mem для сортировок и хешей. Ненулевые deadlocks — повод смотреть порядок блокировок в коде (глава 24). Много xact_rollback относительно xact_commit — приложение часто падает в ошибку.

С PostgreSQL 16 появилось представление pg_stat_io: ввод-вывод по типам процессов. Оно отвечает на вопрос «кто именно читает и пишет»:

SELECT backend_type,                    -- checkpointer / client backend / autovacuum worker / …
       object,                          -- relation или temp relation
       round(sum(reads)::numeric, 0)  AS reads,    -- сколько блоков прочитано
       round(sum(writes)::numeric, 0) AS writes,   -- сколько записано
       round(sum(extends)::numeric, 0) AS extends  -- сколько блоков файла расширено
FROM pg_stat_io
GROUP BY backend_type, object
ORDER BY backend_type;
    backend_type     |    object     | reads | writes | extends
---------------------+---------------+-------+--------+---------
 autovacuum worker   | relation      |   450 |        |      20
 checkpointer        | relation      |       |  17504 |
 client backend      | relation      |  2167 |        |   37747

Пустая ячейка — показатель не отслеживается для этого типа процессов. Полезное наблюдение: клиентские процессы расширяют файл (extends — новые страницы), а записывает их потом checkpointer; всплеск writes у checkpointer совпадает с контрольными точками.

Логи: что включить и как читать

Логи — второй источник после представлений: в них попадают ошибки, отмены и медленные запросы. Параметры, которые имеют смысл (в прогоне включены первые три):

log_min_duration_statement = 200      -- в лог каждый запрос дольше 200 мс
log_lock_waits = on                   -- писать, когда сессия ждёт блокировку дольше deadlock_timeout
log_autovacuum_min_duration = 250ms   -- писать про autovacuum дольше 250 мс
log_checkpoints = on                  -- писать про контрольные точки
log_temp_files = 0                    -- писать про любые временные файлы (0 = все)

Так выглядят медленный запрос и работа checkpointer в логе контейнера (реальные строки прогона):

docker logs sqldemo 2>&1 | grep duration | tail -3   # 2>&1: stderr тоже в поток; tail: последние строки
LOG:  duration: 300.740 ms  statement: SELECT pg_sleep(0.3);
LOG:  duration: 380.979 ms  statement: VACUUM FULL mon_orders;
LOG:  checkpoint complete: wrote 9075 buffers (55.4%); … write=269.318 s, total=269.343 s;

Порог log_min_duration_statement — компромисс: слишком низкий завалит диск, слишком высокий пропустит проблему. Рабочий вариант: 200–500 мс, а «хвост» медленных запросов смотреть по pg_stat_statements.

★ Алгоритм дежурного (по шагам)
  1. Что сейчас происходит: pg_stat_activity — сколько active, есть ли idle in transaction, на чём висят wait_event.
  2. Кто кого блокирует: pg_blocking_pids(pid) и pg_locks; если блокировка чужая и надолго — pg_cancel_backend, затем pg_terminate_backend.
  3. Что тормозит: pg_stat_statements по total_exec_time и по mean_exec_time с calls > 100; дальше EXPLAIN (ANALYZE, BUFFERS) на конкретном запросе.
  4. Индексы и bloat: pg_stat_user_indexes (idx_scan = 0), pgstatindex/pgstattuple, n_dead_tup и last_autovacuum.
  5. Общее здоровье: pg_stat_database (cache hit, temp_files, deadlocks) и pg_stat_io; затем логи по duration.
  6. Профилактика: lock_timeout/statement_timeout на роли, пониженный autovacuum_vacuum_scale_factor у больших таблиц, REINDEX CONCURRENTLY для раздутых индексов.
