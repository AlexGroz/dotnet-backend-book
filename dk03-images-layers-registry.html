Глава 3. Образ, слой и реестр

Образ — это файлы плюс конфигурация, нарезанные на слои. Отсюда сразу объясняются теги, digest, размер, кэш сборки и «почему на сервере другая версия».

подводящая глава

Что лежит внутри образа

Образ — не «архив с программой». Внутри две части:

  • Слои — наборы файлов (по сути tar-архивы), наложенные друг на друга. Каждый слой неизменяем.
  • Конфигурация — JSON: переменные окружения, Entrypoint, Cmd, пользователь, открытые порты, рабочая папка, healthcheck.
# docker image inspect             показать конфигурацию образа в виде JSON
#   mcr.microsoft.com/dotnet/aspnet:8.0   имя образа: реестр/имя:тег
#   --format '{{json .Config}}'     вывести только поле .Config (Go-шаблон); json — компактно, в одну строку
#   | head -c 400                   обрезать вывод до 400 байт, чтобы влезло в экран
docker image inspect mcr.microsoft.com/dotnet/aspnet:8.0 --format '{{json .Config}}' | head -c 400

# docker history                   список слоёв образа: команда сборки, размер, хеш
#   mcr.microsoft.com/dotnet/aspnet:8.0   какой образ смотреть
docker history mcr.microsoft.com/dotnet/aspnet:8.0
#   --no-trunc     показать команды слоёв целиком, без «…»

Идентификатор образа — хеш, посчитанный по содержимому конфигурации и слоёв. Поэтому один и тот же Dockerfile при тех же входных данных даёт один и тот же образ, а «поменяли файл вручную внутри контейнера» на образ не влияет вообще — контейнер пишет только в свой записываемый слой (глава 2).

Слои: почему десять контейнеров не занимают десять образов

Слои разделяются между образами и контейнерами на диске. Схема для трёх контейнеров одного приложения:

слой N        ваш код (Api.dll, appsettings.json)          ← общий, лежит один раз
слой N-1      aspnet runtime 8.0
слой N-2      debian bookworm-slim (базовые библиотеки)
...
контейнер 1   + тонкий записываемый слой
контейнер 2   + тонкий записываемый слой
контейнер 3   + тонкий записываемый слой

По этой же причине docker pull скачивает только то, чего у вас нет: если базовый слой aspnet:8.0 уже загружен, новый образ приложения «весит» только свои несколько мегабайт.

Dockerfile → образ

Инструкции делятся на два типа:

Тип инструкцииЧто создаётПримеры
Меняет файловую системуНовый слой (и участвует в кэше) RUN, COPY, ADD
Меняет только конфигурациюЗапись в конфиг образа, файлы не добавляет ENV, ARG, WORKDIR, USER, EXPOSE, ENTRYPOINT, CMD, LABEL, HEALTHCHECK
Почему из этого следует «не удаляйте файлы в следующей инструкции»

RUN curl ... -o big.tar && ... && rm big.tar — файл не попадёт в образ, потому что создание и удаление произошли в одном слое. А если разнести на два RUN, удаление попадёт в верхний слой, а сам файл останется в нижнем — образ будет весить столько же, сколько и без удаления. Правило: «скачал и удалил» — в одной инструкции.

Теги и digest: почему latest — ловушка

Тег — это указатель на образ. Он изменяем: завтра 8.0 может означать другой набор слоёв (вышел патч). Digest — хеш содержимого, он неизменяем.

# имя образа с тегом: удобно, но тег — «плавающий» указатель, его могут перевесить
#   mcr.microsoft.com   реестр
#   dotnet/aspnet       репозиторий: владелец/имя
#   8.0                 тег — версия .NET
mcr.microsoft.com/dotnet/aspnet:8.0

# тот же образ, зафиксированный по содержимому: тег + digest через @
#   sha256:…   digest — хеш содержимого; неизменяем: это именно этот образ,
#              а не «что сейчас лежит под тегом 8.0»
mcr.microsoft.com/dotnet/aspnet:8.0@sha256:3f1a2b...

# docker image inspect ... --format '{{index .RepoDigests 0}}'
#   .RepoDigests   массив строк «имя@digest»
#   index ... 0    взять первый элемент массива (то есть digest этого образа)
docker image inspect mcr.microsoft.com/dotnet/aspnet:8.0 --format '{{index .RepoDigests 0}}'
  • latest — это просто тег по умолчанию, а не «самая свежая версия». docker pull postgres и docker pull postgres:latest — одно и то же, и там может быть что угодно.
  • В Dockerfile приложения фиксируйте конкретную версию (8.0, лучше — с дистрибутивом: 8.0-bookworm-slim).
  • В проде полезно фиксировать digest: тогда «пересобрали и выкатили» не значит «внезапно другой рантайм» (глава 15).

Реестр: как образ доезжает до сервера

Реестр (registry) — хранилище образов по имени и тегу. Локально образ живёт в вашем Docker, в CI и на сервере его берут из реестра.

РеестрГде встречается
mcr.microsoft.comОфициальные образы .NET и ASP.NET Core
Docker Hub (docker.io)Публичные образы: postgres, redis, nginx; у анонимных pull есть ограничения по частоте
GHCR, GitLab RegistryОбразы вашего проекта рядом с репозиторием
ECR, ACR, Artifact RegistryОблачные реестры (AWS, Azure, GCP)
Harbor, Nexus, ArtifactoryСвой реестр внутри компании
# docker login            войти в реестр; данные сохранятся в ~/.docker/config.json
#   ghcr.io               адрес реестра (GitHub Container Registry)
#   пароль                personal access token с правом write:packages, а не пароль от аккаунта
docker login ghcr.io

# docker build            собрать образ из Dockerfile в текущей папке
#   -t ghcr.io/acme/orders-api:1.4.2   имя:тег результата; адрес реестра сразу в имени,
#                                      чтобы docker push нашёл, куда отправлять
#   .                                  контекст сборки — текущая папка
docker build -t ghcr.io/acme/orders-api:1.4.2 .

# docker push             отправить образ в реестр (недостающие слои загрузятся)
docker push ghcr.io/acme/orders-api:1.4.2

# docker pull             забрать образ из реестра; скачаются только те слои, которых нет локально
docker pull ghcr.io/acme/orders-api:1.4.2

Имя образа — это адрес: реестр/владелец/имя:тег. Если реестр не указан, используется Docker Hub. Отсюда частая ошибка в CI: собрали как orders-api, а push делают в ghcr.io/acme/orders-api — это разные имена, и «образа нет».

Образы .NET: какой тег за что отвечает

ОбразЧто внутриГде использовать
dotnet/sdk:8.0SDK: компилятор, MSBuild, NuGetТолько на стадии сборки (глава 7)
dotnet/aspnet:8.0ASP.NET Core runtimeФинальный образ веб-приложения
dotnet/runtime:8.0Только .NET runtimeКонсольные сервисы, воркеры
dotnet/runtime-deps:8.0Зависимости без рантаймаSelf-contained и Native AOT приложения

Версия в теге должна совпадать с целевой платформой проекта: приложение на net8.0 не запустится на aspnet:6.0 — увидите You must install .NET to run this application.

Мультиархитектура: почему «exec format error»

Образ собирается под архитектуру процессора. На Apple Silicon (arm64) по умолчанию получится arm64-образ, который не запустится на amd64-сервере — и наоборот.

# docker buildx build        сборка через BuildKit; единственный способ собрать под другую архитектуру
#   --platform linux/amd64   под какое железо собирать: amd64 — обычные серверы Intel/AMD,
#                            linux/arm64 — Apple Silicon и ARM-серверы
#   -t ghcr.io/...:1.4.2     имя и тег результата
#   --push                   сразу отправить в реестр; мультиарх-образ локально в docker images не «загрузить»
#   .                        контекст сборки
docker buildx build --platform linux/amd64 -t ghcr.io/acme/orders-api:1.4.2 --push .

# два значения через запятую → один тег с манифестом сразу под обе архитектуры:
# один и тот же 1.4.2 скачается arm64 на Mac и amd64 на сервере
docker buildx build --platform linux/amd64,linux/arm64 \
  -t ghcr.io/acme/orders-api:1.4.2 --push .
#   \  в конце первой строки — перенос длинной команды в bash

Ошибка выглядит как exec /usr/bin/dotnet: exec format error — это не «битый образ», а несовпадение архитектур.

Сколько это занимает на диске

# docker system df         сколько занимают образы, контейнеры, тома и кэш сборки
#                          (ключей нет — команда только показывает статистику)
docker system df

# docker image prune       удалить «висячие» образы — те, что остались без тега (<none>:<none>)
docker image prune
#   -a       удалить ВСЕ образы, которые не используются ни одним контейнером,
#            а не только висячие
#   -f       не спрашивать подтверждение

# docker system prune -a   удалить всё неиспользуемое: остановленные контейнеры,
#                          сети, образы и кэш сборки
docker system prune -a
#   -a           «все неиспользуемые образы», а не только висячие
#   --volumes    дополнительно удалить неиспользуемые тома (это данные! по умолчанию не трогает)
Что стоит запомнить про размер

Размер образа — это сумма слоёв, а не «размер папки приложения». Поэтому образ на sdk весит около гигабайта: там компилятор. Именно поэтому в проде используют многостадийную сборку (глава 7), а не «один Dockerfile на всё».

★ Что запомнить из главы
  • Образ = слои файлов + конфигурация; образ неизменяем, у него есть хеш.
  • Слои общие для всех контейнеров и образов — поэтому десять контейнеров не занимают десять копий.
  • RUN/COPY/ADD создают слои; ENV, ENTRYPOINT, USER — только конфигурацию.
  • Тег может переехать, digest — нет; latest ничего не значит.
  • Реестр — это адрес образа; имя с реестром и без — разные образы.
  • Архитектура (amd64/arm64) должна совпадать, иначе exec format error.
