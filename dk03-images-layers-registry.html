Глава 3. Образ, слой и реестр

Образ — это файлы плюс конфигурация, нарезанные на слои. Отсюда сразу объясняются теги, digest, размер, кэш сборки и «почему на сервере другая версия».

подводящая глава

Какие вопросы закрывает эта глава
  • Что физически лежит внутри образа и почему он весит столько, сколько весит.
  • Почему rm «следующей строкой» не уменьшает образ и как правильно писать RUN.
  • Чем тег отличается от digest, что писать в Dockerfile, а что — в манифесте деплоя.
  • Куда отправляется образ (docker push) и почему имя при сборке должно совпадать с именем в реестре.
  • Какой из образов .NET брать: sdk, aspnet или runtime.
  • Почему возникает exec format error и как собрать под нужную архитектуру.

Предполагается только одно: вы умеете открыть терминал и перейти в папку. Всё остальное — незнакомые программы Linux (curl, tar, ps) и слова Docker — объясняются там, где появляются впервые.

Что лежит внутри образа

Образ — не «архив с программой». Внутри две части:

  • Слои — наборы файлов (по сути tar-архивы), наложенные друг на друга. Каждый слой неизменяем.
  • Конфигурация — JSON: переменные окружения, Entrypoint, Cmd, пользователь, открытые порты, рабочая папка, healthcheck.

Сначала — про длинное имя, которое будет встречаться в каждом примере. Оно устроено как адрес: сначала «где лежит», потом «что именно», в конце — версия:

mcr.microsoft.com / dotnet/aspnet : 8.0
      реестр          репозиторий    тег
   где лежит образ   что именно   какая версия
  • Реестр (mcr.microsoft.com) — сервер, на котором хранятся образы. Microsoft Container Registry — официальный реестр .NET-образов.
  • Репозиторий (dotnet/aspnet) — «папка» внутри реестра: владелец dotnet, образ aspnet.
  • Тег (8.0) — версия.
  • Части можно опускать, и Docker подставит значения по умолчанию: alpine — это на самом деле docker.io/library/alpine:latest (Docker Hub, официальный образ, тег latest). Поэтому alpine и alpine:latest — одно и то же.

Конфигурация образа: команда и вывод (сокращённо)

$ docker image inspect mcr.microsoft.com/dotnet/aspnet:8.0 --format '{{json .Config}}'
{"User":"","Env":["PATH=/usr/local/sbin:…",
                  "APP_UID=1654",
                  "ASPNETCORE_HTTP_PORTS=8080"],
 "Cmd":null,"Entrypoint":null,"WorkingDir":"","ExposedPorts":null}
  • --format '{{json .Config}}' — вывести только раздел Config (это Go-шаблон: .Config — поле объекта, json — «в одну строку»).
  • … в выводе — сокращение автора: настоящий JSON длиннее. Если он не влезает в терминал, вывод обрезают на лету: | head -c 400 — «взять первые 400 байт».
  • Env — переменные окружения, которые автоматически попадут в контейнер. Здесь видно, что образ .NET задаёт APP_UID=1654 и ASPNETCORE_HTTP_PORTS=8080.
  • User пустой — значит по умолчанию контейнер запустится от root (поэтому в Dockerfile пишут USER, глава 5).
  • Cmd и Entrypoint пустые: это базовый образ, у него нет «команды по умолчанию» — её задаёт ваш образ.

Слои: команда и вывод

$ docker history mcr.microsoft.com/dotnet/aspnet:8.0
IMAGE          CREATED      CREATED BY                                      SIZE
<missing>      2 weeks ago  /bin/sh -c #(nop)  ENV ASPNETCORE_HTTP_PORTS=8080   0B
<missing>      2 weeks ago  /bin/sh -c #(nop)  ENV APP_UID=1654                0B
<missing>      2 weeks ago  /bin/sh -c apt-get update && apt-get install …     38MB
<missing>      2 weeks ago  /bin/sh -c #(nop) ADD file:3a1b… in /              75MB
  • IMAGE <missing> — промежуточные слои не имеют собственного тега: их нельзя запустить отдельно, они существуют только как часть образа.
  • CREATED BY — команда, которая создала слой. #(nop) значит «ничего не выполнялось»: инструкция меняла только настройки (ENV), поэтому слой весит 0B.
  • SIZE — сколько добавил именно этот слой, а не размер всего образа. Сумма столбца = размер образа.
  • --no-trunc — ключ, который добавляют к команде, чтобы увидеть CREATED BY целиком: по умолчанию Docker обрезает длинные команды, и в выводе выше стоит ….

Идентификатор образа — хеш, посчитанный по содержимому конфигурации и слоёв. Поэтому один и тот же Dockerfile при тех же входных данных даёт один и тот же образ, а «поменяли файл вручную внутри контейнера» на образ не влияет вообще — контейнер пишет только в свой записываемый слой (глава 2).

Слои: почему десять контейнеров не занимают десять образов

Слои не входят в контейнер и не копируются в него. Контейнер — это ссылка на те же самые слои образа (только для чтения) плюс один собственный тонкий слой. На диске слои лежат в одном экземпляре:

Один образ — три контейнера

ОБРАЗ orders-api:1.4.2 (слои лежат на диске ОДИН раз)
  слой 3   ваш код: Api.dll, appsettings.json          40 МБ
  слой 2   aspnet runtime 8.0                         220 МБ
  слой 1   debian bookworm-slim (базовые библиотеки)  120 МБ

КОНТЕЙНЕР 1 ─┐
КОНТЕЙНЕР 2 ─┼─► каждый: ссылка на слои 1–3 + свой записываемый слой (пустой при старте)
КОНТЕЙНЕР 3 ─┘

Итого на диске: 380 МБ (образ) + почти ничего за контейнеры

Сравните с тем, как было бы при копировании: три контейнера × 380 МБ = 1,1 ГБ. Поэтому контейнер стартует мгновенно: копировать нечего.

По этой же причине docker pull скачивает только то, чего у вас нет: если базовый слой aspnet:8.0 уже загружен, новый образ приложения «весит» только свои несколько мегабайт.

Dockerfile → образ

RUN, COPY, FROM — это инструкции Dockerfile: текстового файла-рецепта, в котором записано, как собрать образ. Пишут их заглавными (большими) буквами — просто по традиции, для наглядности; Docker понимает и строчные, но так никто не пишет. Сами по себе эти слова ничего не выполняют: их читает docker build сверху вниз. RUN значит «выполни эту команду внутри собираемого образа».

Три вида строк — не путайте их
СтрокаЧто этоКто выполняет
docker run alpine ps auxкоманда, которую вы набираете в терминалепрограмма docker на хосте
RUN curl -o /tmp/a.tar …инструкция из файла Dockerfiledocker build, внутри собираемого образа
curl -o /tmp/a.tar …обычная программа Linux тот, кто её вызвал: вы — на хосте, docker run — в контейнере, RUN — на этапе сборки

Одна и та же команда curl в трёх ролях — сравните первые слова:

docker run alpine curl -o /tmp/a.tar https://example.com/a.tar      ← curl работает В КОНТЕЙНЕРЕ
RUN    curl -o /tmp/a.tar https://example.com/a.tar                 ← та же команда ПРИ СБОРКЕ образа
       curl -o /tmp/a.tar https://example.com/a.tar                 ← та же команда НА ХОСТЕ

Общее правило: docker … — это про Docker, RUN … — строка Dockerfile, а всё остальное — обычные программы Linux (curl, tar, rm, apt-get, ps). Docker их не заменяет — он просто запускает их там, куда его попросили.

И уточнение, которое снимает путаницу: RUN, COPY, ENV — ключевые слова файла, а не программы в системе. Их читает docker build, поэтому своя программа с именем run ничего не путает: в строке RUN run --verbose первое слово — инструкция, второе — уже программа (подробно — глава 5).

Инструкции делятся на два типа (подробный разбор каждой — глава 5):

Тип инструкцииЧто создаётПримеры
Меняет файловую системуНовый слой (и участвует в кэше) RUN, COPY, ADD
Меняет только конфигурациюЗапись в конфиг образа, файлы не добавляет ENV, ARG, WORKDIR, USER, EXPOSE, ENTRYPOINT, CMD, LABEL, HEALTHCHECK

Это ключевые слова файла Dockerfile, а не команды Linux: их понимает только docker build, и с программами в системе они не конфликтуют (разбор — глава 5). И ещё одно: сами по себе они ничего не делают — файл нужно собрать командой docker build, и только потом запускать получившийся образ.

В примере ниже встретятся три незнакомые программы. Вот что каждая делает — по одному слову за раз:

  • curl https://example.com/big.tar — «скачай то, что лежит по этому адресу» (curl — клиент для HTTP). Ничего не устанавливает и не запускает: просто забирает файл по сети.
  • -o /tmp/big.tar — ключ -o (output) у curl: «сохрани скачанное в файл /tmp/big.tar». Без -o curl вывел бы содержимое файла в терминал. Ключ -o есть и у других программ, но у каждой он свой — смотрите curl --help.
  • tar -xf /tmp/big.tar -C /opt — распаковать архив: -x — «извлечь», -f — «архив называется вот так», -C /opt — «распаковать в папку /opt».
  • rm /tmp/big.tar — удалить файл (remove).
Зачем думать о слоях: «скачал — удалил в одной инструкции»

Как устроен слой. Одна инструкция RUN — один слой: снимок файловой системы после её выполнения. Слои не перезаписывают друг друга, а накладываются (глава 2). Значит, rm в следующей инструкции файл из нижнего слоя не удаляет — он только прячет его (whiteout), а байты остаются в образе.

Плохо — две инструкции, два слоя:

RUN curl -o /tmp/big.tar https://example.com/big.tar   # слой A: +500 МБ (архив лежит здесь)
RUN rm /tmp/big.tar                                    # слой B: 0 МБ + метка «файла нет»
# что произошло: скачали архив (500 МБ попали в слой A), потом «удалили» —
# но файл физически остался в слое A. Образ весит +500 МБ, хотя в контейнере файла не видно

Хорошо — одна инструкция, один слой:

RUN curl -o /tmp/big.tar https://example.com/big.tar \
 && tar -xf /tmp/big.tar -C /opt \
 && rm /tmp/big.tar
# три команды выполнились подряд, а слой создался уже ПОСЛЕ всех трёх:
#   скачали → распаковали в /opt → удалили архив
# в слой попал только результат — файлы в /opt; самого архива там никогда не было

В чём разница по сути: в первом варианте 500 МБ «запомнились» в момент создания слоя A, и стереть их можно только пересборкой образа. Во втором варианте слой создаётся один раз и уже без архива — поэтому && (а не два RUN) и есть решение.

Проверяется это docker history: в плохом варианте видно слой на 500 МБ, в хорошем такого слоя нет. Зачем важно: меньше образ — быстрее скачивается из реестра, меньше места занимает в CI и на серверах. CI (continuous integration, «непрерывная интеграция») — это сервер, который по каждому коммиту сам собирает проект, прогоняет тесты и публикует образ; он хранит свои копии образов, поэтому размер там тоже считается. Именно поэтому в главе 5 установку пакетов и очистку кэша пишут одной командой RUN.

Тег и digest: указатель и сам образ

Тег — это ярлык-указатель на образ, и ярлык можно перевесить. Сегодня 8.0 — один набор слоёв, а через месяц, после патча безопасности, — уже другой. Это не ошибка, а смысл тега версии: вы получаете обновления, не меняя имени. Но следствие важное: одно и то же имя не гарантирует один и тот же образ — «у меня локально 8.0» и «на сервере 8.0» могут быть разными образами.

Digest (sha256:…) — это хеш содержимого: он считается по слоям и конфигурации. Разные образы дают разные digest, один и тот же — всегда одинаковый. Перевесить digest нельзя: он и есть «именно этот образ, вот с таким содержимым».

# 1) обычная запись: имя + тег — указатель, который могут перевесить
$ docker pull mcr.microsoft.com/dotnet/aspnet:8.0

# 2) имя + digest через @ — «этот образ, с вот таким содержимым»
$ docker pull mcr.microsoft.com/dotnet/aspnet:8.0@sha256:3f1a2b…

# 3) digest не пишут руками — его копируют из вывода команды:
$ docker image inspect mcr.microsoft.com/dotnet/aspnet:8.0 --format '{{index .RepoDigests 0}}'
mcr.microsoft.com/dotnet/aspnet@sha256:3f1a2b…

#   .RepoDigests              массив строк «имя@digest»
#   index ... 0               взять первый элемент массива
#   docker image ls --digests посмотреть digest у всех локальных образов
  • В Dockerfile достаточно тега версии — FROM mcr.microsoft.com/dotnet/aspnet:8.0 (ещё точнее с дистрибутивом: 8.0-bookworm-slim), чтобы образ не «самообновился» до следующего мажора.
  • В деплое (compose, Kubernetes, CI) фиксируют digest или свой неизменяемый тег 1.4.2: тогда «пересобрали и выкатили» не превращается в «внезапно другой рантайм» (глава 15).
  • Для аудита: сканер проверил образ с digest X — и на сервере запущен именно X, а не «что-то, что сейчас лежит под тем же тегом».
  • Портянку @sha256:… руками никто не пишет: её подставляет CI, скрипт деплоя или инженер, фиксирующий версию в манифесте. В обычной работе вы видите только имя:тег.
  • Тег по умолчанию — latest: docker pull postgres и docker pull postgres:latest — одно и то же. И это не «самая свежая версия», а просто имя, под которым может лежать что угодно.
  • В своём реестре (Harbor, ACR, Artifactory) можно запретить перезапись тега — тогда тег тоже становится неизменяемым, и digest нужен только для проверки.

Реестр: как образ доезжает до сервера

Реестр (registry) — хранилище образов по имени и тегу. Локально образ живёт в вашем Docker, в CI и на сервере его берут из реестра.

РеестрГде встречается
mcr.microsoft.comОфициальные образы .NET и ASP.NET Core
Docker Hub (docker.io)Публичные образы: postgres, redis, nginx; у анонимных pull есть ограничения по частоте
GHCR, GitLab RegistryОбразы вашего проекта рядом с репозиторием
ECR, ACR, Artifact RegistryОблачные реестры (AWS, Azure, GCP)
Harbor, Nexus, ArtifactoryСвой реестр внутри компании

Адрес реестра — это настройка, а не часть Docker. Если вы работаете в компании, где есть свой реестр (Harbor, Nexus, Artifactory, GitLab, ACR, ECR — строки в таблице выше), имя образа будет вида registry.company.local/team/orders-api:1.4.2. В примерах ниже стоит ghcr.io — просто как образец: подставьте адрес вашего реестра, остальное не меняется.

# docker login            войти в реестр; данные сохранятся в ~/.docker/config.json
#   ghcr.io               адрес реестра — здесь GitHub Container Registry; у вас может быть свой
#   пароль                personal access token с правом write:packages, а не пароль от аккаунта
docker login ghcr.io

# docker build            собрать образ из Dockerfile в текущей папке
#   -t ghcr.io/acme/orders-api:1.4.2   имя:тег результата; адрес реестра сразу в имени,
#                                      чтобы docker push нашёл, куда отправлять
#   .                                  контекст сборки — текущая папка
docker build -t ghcr.io/acme/orders-api:1.4.2 .

# docker push             отправить образ в реестр (недостающие слои загрузятся)
docker push ghcr.io/acme/orders-api:1.4.2

# docker pull             забрать образ из реестра; скачаются только те слои, которых нет локально
docker pull ghcr.io/acme/orders-api:1.4.2

Имя образа — это адрес: реестр/владелец/имя:тег. Если реестр не указан, используется Docker Hub. Отсюда частая ошибка в CI: собрали как orders-api, а push делают в ghcr.io/acme/orders-api — это разные имена, и «образа нет».

Образы .NET: какой тег за что отвечает

ОбразЧто внутриГде использовать
dotnet/sdk:8.0SDK: компилятор, MSBuild, NuGetТолько на стадии сборки (глава 7)
dotnet/aspnet:8.0ASP.NET Core runtimeФинальный образ веб-приложения
dotnet/runtime:8.0Только .NET runtimeКонсольные сервисы, воркеры
dotnet/runtime-deps:8.0Зависимости без рантайма Self-contained (приложение со встроенным рантаймом) и Native AOT (заранее скомпилировано в машинный код)
*-alpine, *-chiseledМинимальные варианты без лишнего (часто без ICU — библиотеки языков и форматов, и без tzdata — базы часовых поясов) Когда важен размер, с оговорками из главы 14: без ICU .NET иначе форматирует даты, числа и валюты, а без tzdata не знает часовых поясов

Версия в теге должна совпадать с целевой платформой проекта: приложение на net8.0 не запустится на aspnet:6.0 — увидите You must install .NET to run this application.

Мультиархитектура: почему «exec format error»

Образ собирается под архитектуру процессора. На Apple Silicon (arm64) по умолчанию получится arm64-образ, который не запустится на amd64-сервере — и наоборот.

# docker buildx build        сборка под другую архитектуру. buildx — расширение сборки,
#                            работающее на BuildKit (движок сборки Docker)
#   --platform linux/amd64   под какое железо собирать: amd64 — обычные серверы Intel/AMD,
#                            linux/arm64 — Apple Silicon и ARM-серверы
#   -t ghcr.io/...:1.4.2     имя и тег результата
#   --push                   сразу отправить в реестр; мультиарх-образ локально в docker images не «загрузить»
#   .                        контекст сборки
docker buildx build --platform linux/amd64 -t ghcr.io/acme/orders-api:1.4.2 --push .

# два значения через запятую → один тег с манифестом сразу под обе архитектуры:
#   манифест — файл-описание: под одним тегом лежит несколько вариантов образа,
#   и docker сам скачивает тот, который подходит вашей машине
# один и тот же 1.4.2 скачается arm64 на Mac и amd64 на сервере
docker buildx build --platform linux/amd64,linux/arm64 \
  -t ghcr.io/acme/orders-api:1.4.2 --push .
#   \  в конце первой строки — перенос длинной команды в bash

Ошибка возникает при запуске (docker run), а не при сборке: exec /usr/bin/dotnet: exec format error — «ядро не может выполнить файл /usr/bin/dotnet из этого образа». Причина одна: образ собран под другую архитектуру. Например, на Mac с Apple Silicon (arm64) по умолчанию получился arm64-образ, а запускаете вы его на сервере amd64 — или наоборот.

Как проверить, в чём дело

# архитектура образа
$ docker image inspect orders-api:1.4.2 --format '{{.Os}}/{{.Architecture}}'
linux/arm64

# архитектура машины, где запускаем
$ docker version --format '{{.Server.Os}}/{{.Server.Arch}}'
linux/amd64          # ← не совпадает → exec format error

Лечится сборкой под нужную платформу: docker buildx build --platform linux/amd64 … (пример — ниже).

Сколько это занимает на диске

# docker system df         сколько занимают образы, контейнеры, тома и кэш сборки
#                          (ключей нет — команда только показывает статистику)
docker system df

# docker image prune       удалить «висячие» образы — те, что остались без тега (<none>:<none>)
docker image prune
#   -a       удалить ВСЕ образы, которые не используются ни одним контейнером,
#            а не только висячие
#   -f       не спрашивать подтверждение

# docker system prune -a   удалить всё неиспользуемое: остановленные контейнеры,
#                          сети, образы и кэш сборки
docker system prune -a
#   -a           «все неиспользуемые образы», а не только висячие
#   --volumes    дополнительно удалить неиспользуемые тома (это данные! по умолчанию не трогает)
Что стоит запомнить про размер

Размер образа — это сумма слоёв, а не «размер папки приложения». Поэтому образ на sdk весит около гигабайта: там компилятор. Именно поэтому в проде используют многостадийную сборку (глава 7), а не «один Dockerfile на всё».

★ Что запомнить из главы
  • Образ = слои файлов + конфигурация; образ неизменяем, у него есть хеш.
  • Слои общие для всех контейнеров и образов — поэтому десять контейнеров не занимают десять копий.
  • RUN/COPY/ADD создают слои; ENV, ENTRYPOINT, USER — только конфигурацию.
  • Тег — указатель, его можно перевесить; digest — нет. Тег по умолчанию — latest, и он ничего не обещает.
  • Реестр — это адрес образа; имя с реестром и без — разные образы.
  • Архитектура (amd64/arm64) должна совпадать, иначе exec format error.
