Глава 4. Параметры в SQL: :имя, @имя и $1

В книге постоянно встречается created_at >= :from. Разберём, что это такое, кто подставляет значение и почему это не «синтаксис PostgreSQL».

подводящая глава

Что такое параметр

Параметр — это место в тексте запроса, вместо которого подставляется значение отдельно от самого текста. Запрос отправляется на сервер один раз в виде «шаблона», а значения приходят отдельным сообщением:

-- шаблон, который видит сервер
SELECT id, created_at FROM orders
WHERE  created_at >= $1 AND created_at < $2;

-- значения, которые приходят вместе с ним (Bind): ['2026-01-01', '2026-02-01']

Два следствия, ради которых это придумано:

  • Безопасность. Значение никогда не становится частью SQL-текста, поэтому «кавычка в данных» не может превратиться в код (SQL-инъекция).
  • Переиспользование плана. Один и тот же шаблон с разными значениями сервер планирует один раз (prepared statement) — на частых запросах это экономит время разбора и планирования.

Три разных «двоеточия»: не перепутать

Синтаксис зависит от того, кто подставляет значение. Одно и то же место в книге может выглядеть по-разному:

Где пишетеКак выглядитКто подставляет
Протокол PostgreSQL$1, $2 Сервер: значения приходят отдельным сообщением Bind
Драйвер .NET (Npgsql, Dapper)@from Драйвер: превращает @from в $1 и отправляет значения
EF Core@__from_0 (генерируется само) EF: строит SQL с параметрами, вы их обычно не пишете
psql (консоль):from psql: подставляет текст до отправки на сервер
Главное различие

$1 и @from — настоящие параметры протокола: запрос приходит на сервер с «дырками», значения отдельно. :from в psql — это подстановка на клиенте: psql склеивает текст сам, и на сервер уходит уже готовый запрос с литералом. По смыслу похоже, но защита от инъекций и кэш планов работают только в первом случае.

Примеры для каждого инструмента

1. psql: переменные :имя

-- \set задаёт переменную psql (это команда самого psql, а не SQL)
\set from '2026-01-01'

-- :'from' — подставить как строковый литерал: psql сам поставит кавычки
SELECT count(*) FROM orders WHERE created_at >= :'from';

-- :"from" — подставить как ИДЕНТИФИКАТОР (имя таблицы или колонки)
SELECT 1 AS :"column_name";

-- без кавычек :from подставляется «как есть» — легко получить ошибку синтаксиса
-- удобный приём: взять значение из запроса и использовать дальше
SELECT min(created_at) AS from_date FROM orders \gset
-- теперь :from_date — это значение из предыдущего запроса
SELECT count(*) FROM orders WHERE created_at >= :'from_date';

2. Npgsql / Dapper: @имя

// Npgsql: параметры добавляются в команду, а не склеиваются в строке
await using var cmd = new NpgsqlCommand(
    "SELECT id, created_at FROM orders WHERE created_at >= @from AND created_at < @to", conn);
cmd.Parameters.AddWithValue("from", from);   // @from → $1 на проводе
cmd.Parameters.AddWithValue("to",   to);     // @to   → $2
await using var reader = await cmd.ExecuteReaderAsync();
// Dapper: имена параметров берутся из свойств объекта
var rows = await conn.QueryAsync<Order>(
    "SELECT * FROM orders WHERE created_at >= @from AND created_at < @to",
    new { from, to });

// список значений: Dapper сам развернёт @ids в набор параметров
var byIds = await conn.QueryAsync<Order>(
    "SELECT * FROM orders WHERE id = ANY(@ids)", new { ids });

3. EF Core: параметры создаются сами

// вы пишете LINQ — EF строит SQL с параметрами
var list = await db.Orders
    .Where(o => o.CreatedAt >= from && o.CreatedAt < to)
    .ToListAsync();

// в логе это выглядит так:
//   WHERE o.created_at >= @__from_0 AND o.created_at < @__to_1
//   @__from_0='2026-01-01T00:00:00'

4. PL/pgSQL: $1 в теле функции

CREATE FUNCTION orders_between(p_from timestamptz, p_to timestamptz)
RETURNS bigint LANGUAGE sql AS $$
    SELECT count(*) FROM orders
    WHERE created_at >= $1 AND created_at < $2   -- $1 = p_from, $2 = p_to
$$;

Почему в книге встречается :from

В примерах я пишу created_at >= :from AND created_at < :to как общепринятую запись «здесь будет параметр»: так запрос читается без привязки к конкретному драйверу. Читать это надо как «значение подставит приложение». В реальном коде на .NET это будет @from, в psql — :'from', в PL/pgSQL — $1.

Почему нельзя «просто склеить строку»

// ✘ так делать нельзя: значение становится частью SQL
var sql = $"SELECT * FROM orders WHERE status = '{status}'";
// status = "NEW' OR '1'='1"  →  вернутся ВСЕ строки (SQL-инъекция)
// status = "O'Brien"         →  синтаксическая ошибка
  • Инъекция. Любое значение извне (query-параметр, заголовок, поле формы) при склейке может изменить смысл запроса. С параметрами — не может: значение остаётся значением.
  • Кэш планов. При склейке каждый новый текст — новый запрос: сервер каждый раз разбирает и планирует. С параметрами — один подготовленный запрос.
  • Типы. Драйвер знает тип параметра и передаёт дату как дату, а не как строку.
  • Логи и статистика. В pg_stat_statements запросы с параметрами группируются в одну строку (… WHERE status = $1), а не распадаются на тысячи вариантов.

★ Что запомнить
  • Параметр — место в запросе; значение приходит отдельно от текста.
  • $1 — протокол PostgreSQL, @имя — синтаксис драйвера, :имя — переменная psql (подстановка на клиенте).
  • Настоящие параметры защищают от инъекций и позволяют переиспользовать план; склейка строк — нет.
  • Имена таблиц и колонок параметрами не передаются — только значения.
  • Параметр не должен прятаться внутри функции над колонкой, иначе индекс не применится.
