Глава 5. Dockerfile: инструкции и их смысл

Dockerfile — это рецепт сборки: каждая инструкция либо добавляет файлы, либо меняет конфигурацию будущего контейнера. Разберём инструкции на работающем примере, а не списком.

основная глава

Минимальный Dockerfile, который собирается

Возьмём простое ASP.NET Core API и опишем его «в лоб» — так делают все в первый раз:

FROM mcr.microsoft.com/dotnet/sdk:8.0
WORKDIR /src
COPY . .
RUN dotnet publish -c Release -o /app
WORKDIR /app
ENTRYPOINT ["dotnet", "Orders.Api.dll"]

Что произошло построчно:

  1. FROM — взяли базовый образ SDK: там компилятор, MSBuild, NuGet.
  2. WORKDIR /src — создали рабочую папку и перешли в неё (аналог cd, но ещё и «по умолчанию» для последующих инструкций).
  3. COPY . . — скопировали в образ весь контекст сборки: код, проекты, bin, obj, .git.
  4. RUN dotnet publish — собрали Release-версию в папку /app.
  5. WORKDIR /app — сделали её рабочей.
  6. ENTRYPOINT — сказали, что запускать при старте контейнера.

Образ соберётся и даже запустится. Проблемы начнутся позже, и они системные:

  • Он огромный — в нём SDK (компилятор, NuGet, MSBuild), то есть около гигабайта вместо ~200 МБ.
  • В нём исходники — весь код приложения лежит в образе, который уезжает в registry.
  • Он собирается долго — любое изменение в любом файле пересобирает всё, включая восстановление NuGet.

Правильное решение — многостадийная сборка (глава 7). Но сначала нужно понять инструкции, из которых она состоит.

Инструкции, которые вы будете использовать

ИнструкцияЧто делаетНужна, когда
FROMБазовый образ, с которого начинается стадияВсегда; может быть несколько (multi-stage)

COPY против ADD

# обычное копирование — предсказуемо
COPY src/Api/Api.csproj src/Api/

# ADD: распакует archive.tar.gz или скачает URL — «магия», которую потом ищут полчаса
ADD https://example.com/tool.tar.gz /opt/

Правило из официальных рекомендаций: используйте COPY. Если нужен архив — распакуйте его явной командой (RUN tar -xf), если нужен файл из сети — скачайте curl в RUN и проверьте контрольную сумму.

RUN: форма записи и «скачал — удалил в том же слое»

У RUN две формы:

# shell-форма: команда идёт через /bin/sh -c, работают && и $VAR
RUN apt-get update && apt-get install -y --no-install-recommends curl \
    && rm -rf /var/lib/apt/lists/*

# exec-форма: без шелла, массив аргументов
RUN ["dotnet", "restore"]

Три правила, которые сразу отличают аккуратный Dockerfile:

  • Обновление и установка — в одной инструкции с очисткой кэша пакетов. Иначе список пакетов из старого слоя останется в образе навсегда.
  • Не ставьте лишнего. Каждый пакет — это мегабайты и новые уязвимости в сканере.
  • Не используйте apt-get upgrade внутри образа: получится непредсказуемая смесь версий; обновляться нужно сменой базового образа.

ENV против ARG

ARG APP_VERSION=1.0.0             # только во время сборки
ENV ASPNETCORE_URLS=http://+:8080 # попадёт в контейнер и в IConfiguration

RUN echo "собираем $APP_VERSION"

# передаётся при сборке: docker build --build-arg APP_VERSION=1.4.2 .
# ENV можно переопределить при запуске: docker run -e ASPNETCORE_URLS=http://+:9000 ...
Секреты не передают ни через ARG, ни через ENV

Оба значения остаются в метаданных образа: docker history --no-trunc покажет строку сборки, а docker inspect — переменные. Токен NuGet, пароль БД и ключ подписи передаются отдельно — через BuildKit secrets или переменные окружения при запуске (глава 10).

ENTRYPOINT и CMD: кто что запускает

ENTRYPOINT — это «что за программа», CMD — «аргументы по умолчанию».

ENTRYPOINTCMDЧто выполнится
["dotnet","Api.dll"]["--urls","http://+:8080"] dotnet Api.dll --urls http://+:8080
["dotnet","Api.dll"]—dotnet Api.dll
—["dotnet","Api.dll"]dotnet Api.dll; легко переопределить: docker run img sh
["dotnet","Api.dll"]—docker run img --help добавит аргумент, а не заменит команду

Форма записи важнее, чем кажется:

# exec-форма (правильно): PID 1 = dotnet, SIGTERM доходит до приложения
ENTRYPOINT ["dotnet", "Orders.Api.dll"]

# shell-форма: PID 1 = /bin/sh -c, переменные раскрываются,
# но сигналы часто не доходят (глава 13)
ENTRYPOINT dotnet Orders.Api.dll

Переопределить точку входа можно на запуске — это удобно для отладки:

docker run --rm -it --entrypoint bash orders-api:1.4.2
docker run --rm --entrypoint dotnet orders-api:1.4.2 Orders.Api.dll --help

EXPOSE и USER: две инструкции, которые понимают неправильно

  • EXPOSE 8080 ничего не публикует. Это документация: «приложение слушает 8080 внутри». Наружу порт выводит только -p (или mapping в compose / Service в Kubernetes).
  • USER переключает пользователя для всех последующих инструкций и для запуска. В образах .NET 8 уже есть пользователь app (UID 1654) и переменная APP_UID, поэтому достаточно USER $APP_UID.
ENV ASPNETCORE_HTTP_PORTS=8080
EXPOSE 8080
USER $APP_UID

HEALTHCHECK: полезно, но с оговоркой

HEALTHCHECK --interval=30s --timeout=3s --start-period=10s --retries=3 \
  CMD curl -f http://localhost:8080/health || exit 1
В образе aspnet нет curl

Команда выше упадёт не потому, что приложение больно, а потому что утилиты нет. Варианты: добавить curl своим слоем (плюс мегабайты и уязвимости), проверять порт иначе или — что правильнее в проде — отдать проверку оркестратору (Kubernetes httpGet-проба не требует утилит внутри образа). Подробно — в главе 13.

Сборка

docker build -t orders-api:1.4.2 .          # . — контекст сборки (папка)
docker build -f docker/Api.Dockerfile -t orders-api:1.4.2 .
docker build --progress=plain -t orders-api:1.4.2 .   # подробный лог шагов

Точка в конце — не опечатка: это контекст, папка, содержимое которой Docker отправляет демону и из которой работает COPY. Чем контекст больше, тем дольше сборка — поэтому нужен .dockerignore (глава 6).

★ Что запомнить из главы
  • RUN/COPY меняют файловую систему и создают слои; ENV/ENTRYPOINT/USER/EXPOSE — только конфигурацию.
  • COPY вместо ADD; «скачал и удалил» — в одном RUN.
  • ARG — только сборка, ENV — и сборка, и запуск; секреты — ни там, ни там.
  • ENTRYPOINT в exec-форме — иначе сигналы не дойдут до приложения.
  • EXPOSE — документация, порт публикует -p.
  • Наивный одностадийный Dockerfile тянет SDK и исходники в прод — лечится multi-stage (глава 7).
