Глава 5. Dockerfile: инструкции и их смысл

Dockerfile — это текстовый файл с инструкциями, по которому собирается образ. Разберём не список команд, а конвейер: что происходит на каждом шаге, зачем инструкция нужна и что будет, если её убрать.

основная глава

Dockerfile сам ничего не делает: сначала сборка, потом запуск

Dockerfile — это инструкция для docker build, а не программа. Пока сборка не выполнена, никакого образа нет: файл просто лежит в папке проекта. Порядок всегда такой:

1) вы пишете файл Dockerfile                       ← всё, что в этой главе ниже
2) docker build -t orders-api:1.4.2 .              ← читает файл, создаёт ОБРАЗ
3) docker run -p 8080:8080 orders-api:1.4.2        ← создаёт и запускает КОНТЕЙНЕР

Поэтому примеры в главе — это содержимое файла (шаг 1), а не команды терминала. Сборка разобрана в конце главы, в разделе «Сборка»; запуск — в главе 4.

Что происходит при сборке

На входе — Dockerfile и папка с кодом (она называется контекст сборки). На выходе — образ. Внутри — последовательность шагов:

папка проекта + Dockerfile
        │
        │  docker build
        ▼
 1) Docker читает Dockerfile сверху вниз
 2) выполняет инструкцию за инструкцией
 3) каждая RUN / COPY / ADD создаёт НОВЫЙ СЛОЙ
 4) остальные инструкции (WORKDIR, ENV, USER, EXPOSE, ENTRYPOINT, CMD, HEALTHCHECK)
    файлов не добавляют — они записывают НАСТРОЙКИ в конфиг образа
        │
        ▼
     ОБРАЗ  =  слои (файлы)  +  конфиг (с чем и от кого запускать)
        │
        │  docker run
        ▼
   КОНТЕЙНЕР = слои образа (только чтение) + свой записываемый слой
«Будущий контейнер» и «текущий образ» — это одно и то же?

Почти. Dockerfile собирает образ. Контейнера на этом этапе ещё нет. Но конфиг образа — это, по сути, «инструкция для будущего контейнера»: в нём записано, что запускать (ENTRYPOINT/CMD), от какого пользователя (USER), с какими переменными (ENV), какой порт слушать (EXPOSE). Каждый контейнер, созданный из этого образа, заберёт эти настройки.

Две группы инструкций

ГруппаЧто делаетИнструкции
Меняют файлыДобавляют, удаляют, изменяют файлы → создают слой (и участвуют в кэше)RUN, COPY, ADD
Задают настройкиФайлов не добавляют (размер образа не растёт), но определяют, как запустится контейнерFROM, WORKDIR, ENV, ARG, EXPOSE, USER, ENTRYPOINT, CMD, HEALTHCHECK, LABEL

Это деление объясняет, почему в docker history у инструкций из второй группы размер 0B: они не положили в образ ни одного файла, только записали настройку (глава 3). Одна оговорка: FROM стоит во второй группе потому, что сам файлов не создаёт — он берёт уже готовые слои базового образа.

Почему эти слова не путаются с командами Linux

RUN, COPY, ENV и остальные — не команды Linux. Их не видит ни оболочка, ни ядро: файл читает docker build и смотрит на первое слово каждой строки. Совпало с названием инструкции — значит, это инструкция, а всё остальное в строке — её аргументы. Если первое слово не из списка, сборка останавливается с ошибкой unknown instruction: FOO.

Поэтому своя программа с именем run ничего не сломает. Строка RUN run --verbose читается как «инструкция RUN, выполнить команду run --verbose»: первое слово — инструкция файла, второе — уже программа. А если программа названа так же, как инструкция (например, ENV), её вызывают по полному пути: RUN /usr/local/bin/ENV.

Отдельно про shell-форму RUN: Docker передаёт остаток строки оболочке (/bin/sh -c "…"), и уже оболочка ищет программу по PATH — так же, как если бы вы набрали её в терминале. В exec-форме (RUN ["run","--verbose"]) оболочки нет: программа запускается напрямую (Docker ищет её по PATH), но строку никто не разбирает — поэтому &&, | и $VAR там не работают.

Пример: простейший Dockerfile для API — и его цена

Такой Dockerfile пишут в первый раз почти все — он работает, но обходится дорого:

FROM mcr.microsoft.com/dotnet/sdk:8.0
WORKDIR /src
COPY . .
RUN dotnet publish -c Release -o /app
WORKDIR /app
ENTRYPOINT ["dotnet", "Orders.Api.dll"]

1. FROM: с какого образа начинаем

Всё, что стоит после FROM, — это полное имя образа, а не «просто тег». Оно состоит из трёх частей:

mcr.microsoft.com / dotnet/sdk : 8.0
└──── реестр ────┘   └ репозиторий┘ └тег┘
   где лежит образ    что за образ    какая версия
  • Реестр — сервер с образами. Здесь Microsoft Container Registry; мог быть docker.io (Docker Hub) или ваш внутренний, например registry.company.local.
  • Репозиторий — имя образа внутри реестра. dotnet/sdk — SDK .NET: компилятор, MSBuild, NuGet.
  • Тег — версия: 8.0. Тег можно не писать — тогда подставится latest (глава 3), но так делать не стоит.

Нужен ли интернет? Демон сначала ищет образ у себя. Если его нет — качает из реестра. Если интернета нет:

  • на машине с интернетом: docker pull mcr.microsoft.com/dotnet/sdk:8.0, затем docker save mcr.microsoft.com/dotnet/sdk:8.0 -o sdk.tar — save значит «упаковать образ в файл», -o (output) — «в какой файл»;
  • на изолированной машине: docker load -i sdk.tar — load «загрузить образ из файла», -i (input) «из какого файла». После этого FROM возьмёт образ из локального хранилища, интернет не понадобится.

То же можно делать через свой реестр: собрать базовый образ один раз, запушить и ссылаться на него. FROM scratch — особый случай: «пустой» образ, с которого начинают self-contained приложения.

2. WORKDIR /src: где мы находимся

У образа есть текущая папка — та, в которой выполняются RUN и относительно которой работает COPY. По умолчанию это / (корень файловой системы образа), если базовый образ не задал свою.

  • WORKDIR /src создаёт папку /src (если её нет) и делает её текущей для всех следующих инструкций — аналог cd, но действующий до конца файла.
  • Никакой «рабочей директории на вашем компьютере» тут нет: всё происходит внутри образа.

3. COPY . .: две точки — это источник и назначение

COPY <откуда> <куда>. Две точки — это два пути:

ЧастьЧто значитКуда ведёт
первая .весь контекст сборкипапка, из которой вы запустили docker build (обычно корень проекта)
вторая .текущая папка образа то, что задал WORKDIR, здесь /src

То есть «скопируй мою папку проекта в /src внутри образа». Копируется всё: код, bin, obj, .git — поэтому нужен .dockerignore (глава 6).

4. RUN dotnet publish: сборка внутри образа

RUN выполняется в текущей папке — в /src, где лежит проект.

  • dotnet publish — собрать проект и подготовить к запуску (в отличие от build, который только компилирует).
  • -c Release — конфигурация Release: оптимизации, без отладочных символов.
  • -o /app — куда положить результат. Путь абсолютный, поэтому от текущей папки не зависит: результаты окажутся в /app.

5. WORKDIR /app: это другая папка

/src и /app — разные папки. В /src лежат исходники, в /app — то, что собрал publish (dll и конфиги). После этой инструкции текущая папка — /app, и ENTRYPOINT будет искать файл там.

6. ENTRYPOINT ["dotnet", "Orders.Api.dll"]: что запускать

Orders.Api.dll — имя собранной сборки, а не класс и не «startup». Оно берётся из <AssemblyName> в .csproj (по умолчанию — имя проекта). dotnet publish создаёт этот файл в /app.

.NET-приложение запускается командой dotnet <имя>.dll: рантайм загружает сборку и сам находит точку входа Main (в ASP.NET Core она генерируется из Program.cs). Поэтому в ENTRYPOINT пишут файл, а не метод или класс.

Инструкции по одной: что делает, зачем, что будет без неё

RUN: выполнить команду при сборке

Что делает: запускает команду внутри образа и сохраняет изменения как новый слой. Выполняется только при docker build — при запуске контейнера не повторяется.

Зачем: поставить пакеты, собрать проект, создать папки — всё, что нужно подготовить.

Две формы записи — и зачем каждая:

# 1) shell-форма: строка → Docker запускает /bin/sh -c "строка"
#    /bin/sh — командная оболочка (shell) Linux; ключ -c = «выполни эту строку как команду»
#    Нужна, когда используются возможности шелла: && (и), | (пайп),
#    > (редирект), $VAR (переменные), подстановки и glob-маски
RUN apt-get update && apt-get install -y curl && rm -rf /var/lib/apt/lists/*
#    что в этой строке по частям:
#      apt-get                    менеджер пакетов Debian/Ubuntu (системные пакеты; NuGet — это другое)
#      update                     обновить СПИСКИ доступных пакетов, а не сами пакеты
#      install -y curl            поставить curl; -y = «на все вопросы отвечай да»
#      &&                          «и затем»: следующая команда выполнится, только если предыдущая удалась
#      rm -rf /var/lib/apt/lists/*  удалить списки; -r — с папками, -f — без вопросов

# 2) exec-форма: JSON-массив, без шелла — аргументы передаются как есть
#    Нужна, когда шелла в образе нет вообще (chiseled/distroless — минимальные образы,
#    где есть только ваше приложение) или важны точные аргументы (пробелы, кавычки)
RUN ["dotnet", "restore"]
#    restore — восстановить NuGet-пакеты проекта (аналог npm install)

# --- та же установка curl, но в exec-форме: два рабочих способа ---

# а) одна команда — одна инструкция: шелла нет, поэтому просто не склеиваем их
RUN ["apt-get", "update"]
RUN ["apt-get", "install", "-y", "curl"]

# б) шелл вызвать явно: тогда && и редиректы снова работают
RUN ["/bin/sh", "-c", "apt-get update && apt-get install -y curl && rm -rf /var/lib/apt/lists/*"]

# А ТАК НЕ СРАБОТАЕТ: нет шелла, поэтому "&&" останется обычным аргументом для apt-get
# RUN ["apt-get", "update", "&&", "apt-get", "install", "-y", "curl"]   ✘
#    apt-get получит первый аргумент update и лишние слова после него и ответит:
#    E: The update command takes no arguments

Отсюда правило: exec-форма — это «программа плюс список аргументов», а не строка. Склеить две команды можно только тем, кто умеет это делать, — оболочкой. Поэтому либо по одной команде на RUN (вариант «а»), либо явный вызов /bin/sh -c (вариант «б»). Вариант «б» недоступен в образах без оболочки — там остаётся только «а».

Тогда зачем вообще exec-форма, если shell удобнее?

Потому что она предсказуема: аргументы не проходят через разбор оболочкой, и Docker не нужно, чтобы внутри образа был /bin/sh. В минимальных образах (chiseled, distroless) оболочки нет вообще — там RUN ["apt-get", …] единственно возможный вариант (и такие образы обычно ничего не устанавливают, а копируют готовое из стадии сборки — глава 7).

Почему установка и очистка — одной строкой: каждая RUN — отдельный слой, а слои не перезаписывают друг друга. Если разделить «поставил» и «удалил кэш» на два RUN, кэш останется в нижнем слое и образ не уменьшится (подробно — глава 3).

Что такое /var/lib/apt/lists/* и кто его создал

apt-get update не «обновляет программы» — он скачивает индексы пакетов (списки того, что доступно в репозиториях) и кладёт их в /var/lib/apt/lists/. Это стандартное место apt в Debian/Ubuntu — поэтому путь именно такой. После apt-get install индексы в готовом образе не нужны: они занимают десятки мегабайт и никем не читаются. rm -rf /var/lib/apt/lists/* удаляет их в том же слое, поэтому в образ они не попадают.

ENV и ARG: переменные

ARGENV
Когда существуеттолько во время сборкии при сборке, и в контейнере
Виден приложениюнетда — как переменная окружения; .NET читает её через IConfiguration
Переопределяетсяdocker build --build-arg docker run -e
Зачемверсия сборки, флаги, адрес NuGet-фиданастройки запуска: порт, окружение, пути
ARG APP_VERSION=1.0.0              # имя и значение придумываете ВЫ; Docker их не толкует
ENV ASPNETCORE_HTTP_PORTS=8080     # попадёт в контейнер; docker run -e ASPNETCORE_HTTP_PORTS=9000

RUN echo "собираем $APP_VERSION"   # ARG доступен на сборке
LABEL version=$APP_VERSION         # LABEL пишет метку (ключ=значение) в конфиг образа

RUN dotnet publish -c Release -o /app -p:Version=$APP_VERSION --no-restore

Что за версия в APP_VERSION. Это не версия Docker и не «версия образа» — это произвольная переменная сборки, которую придумываете вы. Docker лишь подставляет её значение везде, где встретит $APP_VERSION. Что туда класть — ваш выбор:

  • версию приложения из git tag: тогда в publish уходит -p:Version=1.4.2, и .NET записывает её в метаданные сборки (её видно в свойствах dll и в эндпоинте /info, если вы его сделали);
  • номер сборки из CI — 1.4.2-241: так потом понятно, из какого пайплайна образ;
  • что-то совсем служебное: адрес NuGet-фида, флаг -p:ContinuousIntegrationBuild=true.

Значение после = — значение по умолчанию: если --build-arg не передан, подставится 1.0.0. Проверить, что именно попало в образ, проще всего по метке:

$ docker build --build-arg APP_VERSION=1.4.2 -t orders-api:1.4.2 .
$ docker inspect --format '{{json .Config.Labels}}' orders-api:1.4.2
{"version":"1.4.2"}

Что если не указать ENV: приложение возьмёт значения по умолчанию (порт 5000) — частая причина «контейнер запустился, а порт не отвечает».

Секреты не передают ни через ARG, ни через ENV

Оба значения остаются в метаданных образа: docker history --no-trunc покажет строку сборки, docker inspect — переменные. Пароли и токены передаются при запуске (глава 10).

COPY и ADD: файлы в образ

COPY <откуда> <куда> — простое копирование из контекста сборки в образ. Ничего не распаковывает и никуда не ходит по сети: взял файл — положил файл. Разбор COPY . . был выше, а вот другие формы:

COPY Orders.Api/Orders.Api.csproj Orders.Api/   # файл → в папку Orders.Api/
COPY appsettings.Production.json ./             # файл → в текущую папку (WORKDIR)
COPY wwwroot ./wwwroot                          # папку целиком, со всем содержимым
COPY --chown=$APP_UID:0 . .                     # скопировать и сразу сменить владельца
  • Пути внутри контекста (то, что вы передали в docker build … .). Файл, исключённый в .dockerignore, скопировать нельзя — его «не существует» (глава 6).
  • Если куда кончается слэшем или это существующая папка — файл кладётся внутрь неё; иначе куда считается именем файла.
  • --chown=uid:gid — сменить владельца на лету; иначе файлы принадлежат root (об этом — в разделе про USER и в главе 7).

ADD умеет то же самое плюс два действия, которые выполняет сам, без спроса:

Что в источникеADD делает самЧем это плохо
локальный архив app.tar.gz распаковывает его в целевую папку — самого архива в образе не остаётся что и куда распаковалось, видно только после сборки: в Dockerfile написано «добавь архив», а получилось «добавь содержимое»
URL https://…/tool.tgz скачивает по сети прямо во время сборки нет проверки того, что скачалось: подменённый на сервере файл никто не заметит; к тому же обновили файл на сервере — Docker может этого и не увидеть: кэш такого слоя зависит от заголовков удалённого сервера, а не от вашего Dockerfile

То же самое, но COPY + явная команда — так видно каждое действие:

# 1) архив: сначала копируем как файл, потом распаковываем отдельной командой
COPY app.tar.gz /tmp/
RUN tar -xzf /tmp/app.tar.gz -C /app && rm /tmp/app.tar.gz
#   tar -xzf  распаковать: -x извлечь, -z gzip, -f файл; -C /app — в какую папку
#   && rm      убрать сам архив в том же слое (иначе он останется в образе — глава 3)

# 2) файл из сети: скачать, сверить контрольную сумму, только потом использовать
RUN curl -fsSL -o /tmp/tool.tgz https://example.com/tool-1.2.3.tgz \
 && echo "9f2c1a4b8e6d0f3a5c7b9e1d2f4a6c8b0e2d4f6a8c0b2e4d6f8a0c2b4e6d8f0a  /tmp/tool.tgz" | sha256sum -c - \
 && tar -xzf /tmp/tool.tgz -C /usr/local/bin \
 && rm /tmp/tool.tgz
  • curl -fsSL: -f — «HTTP-ошибка = ошибка» (без неё страница 404 сохранится как файл и сборка «удастся»), -s — без индикатора прогресса, -S — но ошибки показывать, -L — идти по редиректам, -o <файл> — куда сохранить.
  • sha256sum -c - — «сверь файл с суммой из стандартного ввода» (-c = check, - = читать список из stdin). Не совпало — команда вернёт ненулевой код, и && остановит сборку.
  • Сумму берут из документации проекта или со страницы релиза и вписывают в Dockerfile. Тогда подмена файла на сервере ломает сборку, а не тихо попадает в прод.

Правило: ADD — только если он действительно нужен (например, распаковать локальный архив в образе, где нет tar). Во всех остальных случаях — COPY.

EXPOSE: заявить порт

Что делает: записывает в конфиг образа «приложение слушает этот порт» — документация для людей и подсказка инструментам. Чего не делает: не открывает порт наружу.

EXPOSE 8080         # один порт (протокол по умолчанию tcp)
EXPOSE 8080/tcp     # то же самое, записано явно
EXPOSE 8080/udp     # другой протокол — тоже можно заявить

Заявленное видно в конфиге образа, а реально опубликованное — в docker ps. Сравните два запуска одного и того же образа:

$ docker image inspect orders-api:1.4.2 --format '{{json .Config.ExposedPorts}}'
{"8080/tcp":{}}                     ← заявлено в образе

# 1) запуск БЕЗ -p: порт заявлен, но снаружи закрыт
$ docker run -d --name api-noport orders-api:1.4.2
$ curl -s -m 2 http://localhost:8080/health
curl: (7) Failed to connect to localhost port 8080
$ docker ps --format '{{.Names}}\t{{.Ports}}'
api-noport                            ← столбец портов пуст

# 2) запуск С -p: тот же образ, тот же EXPOSE — и порт работает
$ docker run -d --name api -p 8080:8080 orders-api:1.4.2
$ curl -s http://localhost:8080/health
{"status":"Healthy"}
$ docker ps --format '{{.Names}}\t{{.Ports}}'
api     0.0.0.0:8080->8080/tcp
  • 0.0.0.0:8080->8080/tcp читается как «порт 8080 на всех интерфейсах машины → порт 8080 в контейнере».
  • curl -m 2 — ждать ответа не дольше двух секунд (-m = max time), иначе команда висит.
  • Код выхода 7 у curl — «не удалось подключиться». Именно так выглядит «порт не опубликован», в отличие от 404 (порт открыт, адрес неверный).

Если EXPOSE не указать: ничего не сломается — трафик пойдёт, если порт опубликован -p. Но: docker ps не покажет порт, флаг -P (заглавная) не будет знать, что публиковать, а человек, читающий Dockerfile, не поймёт, куда стучаться.

  • -p 8080:8080 — «опубликуй вот этот порт контейнера на вот этот порт машины».
  • -P — «опубликуй все заявленные в EXPOSE порты, каждый на случайный свободный порт машины». Поэтому EXPOSE — не только документация.

Подробно про порты, интерфейсы и localhost — глава 8.

USER: от какого пользователя работать

Что делает: переключает пользователя для следующих инструкций и для запуска. Зачем: по умолчанию контейнер работает от root — при взломе приложения у атакующего будут root-права внутри контейнера. В образах .NET 8 уже есть пользователь app (APP_UID=1654):

USER $APP_UID      # процесс работает от app, а не от root
USER 1654          # то же самое, если переменная недоступна

Если не указать: контейнер запустится от root — работает, но считается плохой практикой (глава 14).

HEALTHCHECK: как Docker узнаёт, что приложение живо

Зачем: «процесс запущен» ≠ «приложение отвечает». HEALTHCHECK даёт Docker команду проверки: он будет выполнять её периодически и менять статус контейнера в docker ps на healthy/unhealthy. По этому статусу, например, depends_on в compose ждёт базу.

HEALTHCHECK --interval=30s --timeout=3s --start-period=10s --retries=3 \
  CMD curl -f http://localhost:8080/health || exit 1
#   --interval      как часто проверять
#   --timeout       сколько ждать ответа
#   --start-period  льготное время после старта (приложение греется)
#   --retries       сколько провалов подряд → unhealthy
#   curl -f         HTTP 4xx/5xx считается ошибкой (без -f curl «успешен» даже на 500)
#   ||              «или иначе»: выполнить команду справа, только если левая провалилась
#   exit 1          ненулевой код выхода = проверка провалена → статус unhealthy
#   /health         адрес проверки в ВАШЕМ приложении: эндпоинт, который отвечает 200,
#                   когда всё в порядке. Нет такого эндпоинта — проверка всегда падает
Проверка упадёт не из-за приложения, а из-за отсутствия утилиты

В образе aspnet нет ни curl, ни wget: он собран «тонким» — только рантайм .NET. Поэтому статус будет честным, но причина — не та, которую вы ищете:

$ docker ps
CONTAINER ID   IMAGE                STATUS
3f2c9a1b7d4e   orders-api:1.4.2     Up 2 minutes (unhealthy)

$ docker inspect --format '{{json .State.Health}}' 3f2c9a1b7d4e | head -c 400
{"Status":"unhealthy","FailingStreak":3,
 "Log":[{"Output":"/bin/sh: 1: curl: not found\n"}]}

Приложение при этом живое — упала проверка (что делает запись --format '{{json …}}' — разобрано в главе 4). Рабочих вариантов три, и выбирают их по ситуации.

Вариант 1: поставить утилиту в образ. Тот самый слой apt-get из раздела про RUN, и обязательно в финальную стадию (в multi-stage — в ту, что станет образом, глава 7):

RUN apt-get update \
 && apt-get install -y --no-install-recommends curl \
 && rm -rf /var/lib/apt/lists/*

HEALTHCHECK --interval=30s --timeout=3s --start-period=10s --retries=3 \
  CMD curl -f http://localhost:8080/health || exit 1
  • --no-install-recommends — не тянуть «рекомендованные» пакеты: нужен один curl, а не двадцать его знакомых.
  • rm -rf /var/lib/apt/lists/* — стереть индексы пакетов в том же слое (глава 3: иначе эти мегабайты останутся в образе навсегда).
  • Цена: curl умеет ходить в сеть и качать файлы — в проде это лишняя возможность для атакующего (глава 14). Поэтому вариант 3 часто лучше.

Вариант 2: проверить только порт, без утилит. У bash есть встроенное перенаправление /dev/tcp — «открой TCP-соединение с адресом»:

HEALTHCHECK --interval=30s --timeout=3s --retries=3 \
  CMD bash -c '</dev/tcp/127.0.0.1/8080' || exit 1

Работает там, где есть bash (в aspnet:8.0 на Debian он есть, в alpine — нет). Минус: проверяется «порт слушается», а не «приложение отвечает 200». Приложение может висеть и не отвечать — проверка этого не заметит.

Вариант 3: отдать проверку наружу. Ничего не ставить в образ, а проверять снаружи: Kubernetes-проба httpGet или healthcheck в compose, который выполняет утилита другого контейнера. Так делают в проде — подробно в главах 11 и 13.

ENTRYPOINT и CMD: что запускать и с какими аргументами

Зачем их две. ENTRYPOINT — «что за программа»: он не переопределяется аргументами в конце docker run. CMD — «аргументы по умолчанию»: их легко заменить.

Что такое «аргументы». Это всё, что написано в командной строке после имени образа. В строке docker run -d -p 8080:8080 orders-api:1.4.2 --urls http://+:9000 аргументы — только --urls http://+:9000: всё до имени образа — флаги самого docker run (-d, -p), а всё после — то, что получит программа внутри контейнера.

В таблице два разных вопроса, и именно поэтому её раньше читали как противоречие: что запустится, если ничего не дописывать, и что запустится, если дописать аргументы в docker run. Теперь это разные столбцы.

ENTRYPOINTCMDПо умолчанию:
docker run img		 С аргументами:
docker run img --help
["dotnet","Orders.Api.dll"] ["--urls","http://+:8080"] dotnet Orders.Api.dll --urls http://+:8080 dotnet Orders.Api.dll --help
(CMD выброшен, его место заняли аргументы)
—["dotnet","Orders.Api.dll"] dotnet Orders.Api.dll --help → ошибка «executable file not found»
(CMD был единственной командой, поэтому заменён целиком — вместе с программой)
["dotnet","Orders.Api.dll"]— dotnet Orders.Api.dll dotnet Orders.Api.dll --help
(CMD не было, поэтому аргументы дописались в конец ENTRYPOINT)

Правило, из которого следуют все три строки: аргументы из docker run заменяют CMD — целиком, как один блок. Был CMD — он выброшен; не было — дописанное просто добавляется к ENTRYPOINT. Программу (ENTRYPOINT) так подменить нельзя: во второй строке «замена» случилась только потому, что программы в ENTRYPOINT нет вообще — её роль играл CMD.

Таблица объясняет правило, но не показывает, что вы увидите на экране. Поэтому те же три случая — так, как они выглядят в терминале; в каждом сначала смотрим конфиг образа, потом запускаем:

Случай 1: заданы и ENTRYPOINT, и CMD

# Dockerfile этого образа:
#   ENTRYPOINT ["dotnet", "Orders.Api.dll"]
#   CMD ["--urls", "http://+:8080"]

$ docker image inspect orders-api:1.4.2 \
    --format '{{json .Config.Entrypoint}} | {{json .Config.Cmd}}'
["dotnet","Orders.Api.dll"] | ["--urls","http://+:8080"]
#   в конфиге лежат ОБЕ части: программа и аргументы по умолчанию

$ docker run --rm orders-api:1.4.2
info: Now listening on: http://[::]:8080
#   выполнилось: dotnet Orders.Api.dll --urls http://+:8080   ← ENTRYPOINT + CMD

$ docker run --rm orders-api:1.4.2 --urls http://+:9000
info: Now listening on: http://[::]:9000
#   выполнилось: dotnet Orders.Api.dll --urls http://+:9000   ← CMD выброшен целиком

$ docker run --rm orders-api:1.4.2 --urls http://+:9000 --environment Development
info: Now listening on: http://[::]:9000
info: Hosting environment: Development
#   два аргумента — тоже вместо CMD, а не в дополнение к нему

Случай 2: задан только CMD

# Dockerfile этого образа:
#   CMD ["dotnet", "Orders.Api.dll"]           ← ENTRYPOINT отсутствует

$ docker image inspect orders-cmd:1.0 \
    --format '{{json .Config.Entrypoint}} | {{json .Config.Cmd}}'
null | ["dotnet","Orders.Api.dll"]
#   Entrypoint = null: значит программой считается сам CMD, другой программы нет

$ docker run --rm orders-cmd:1.0
info: Now listening on: http://[::]:8080
#   выполнилось: dotnet Orders.Api.dll

$ docker run --rm orders-cmd:1.0 --help
docker: Error response from daemon: … exec: "--help": executable file not found in $PATH.
#   аргументы заменили CMD целиком, а ENTRYPOINT нет — значит подменилась и ПРОГРАММА:
#   Docker попытался запустить "--help" как исполняемый файл

$ docker run --rm -it orders-cmd:1.0 bash
root@7d1e2f9a0c44:/app#
#   а вот шелл здесь РАБОТАЕТ: bash занял место CMD и стал программой контейнера

Случай 3: задан только ENTRYPOINT

# Dockerfile этого образа:
#   ENTRYPOINT ["dotnet", "Orders.Api.dll"]    ← CMD отсутствует

$ docker image inspect orders-entry:1.0 \
    --format '{{json .Config.Entrypoint}} | {{json .Config.Cmd}}'
["dotnet","Orders.Api.dll"] | null
#   Cmd = null: заменять нечего

$ docker run --rm orders-entry:1.0
info: Now listening on: http://[::]:8080
#   выполнилось: dotnet Orders.Api.dll
#   порт 8080 здесь не из CMD, а из переменной ASPNETCORE_HTTP_PORTS базового образа

$ docker run --rm orders-entry:1.0 --urls http://+:9000
info: Now listening on: http://[::]:9000
#   аргументы дописались в конец ENTRYPOINT: dotnet Orders.Api.dll --urls http://+:9000

$ docker run --rm -it orders-entry:1.0 bash
info: Now listening on: http://[::]:8080
#   шелла НЕТ: bash стал аргументом → dotnet Orders.Api.dll bash
#   приложение получило лишний аргумент и запустилось как обычно (выйти — Ctrl+C);
#   внутрь пускает только --entrypoint bash (врезка ниже)

Сравните последние строки случаев 2 и 3: одна и та же команда docker run img bash в одном случае даёт шелл, в другом — лишний аргумент приложению. А случаи 1 и 3 внешне неотличимы, пока не допишешь аргументы: разница лишь в том, что в первом есть значения по умолчанию, которые можно потерять.

Зачем тогда две инструкции, если хватает одной? Они отвечают на разные вопросы, и в жизни это удобно:

Что нужноКак записать
«По умолчанию работает так, но адрес и флаги я смогу поменять без пересборки» ENTRYPOINT = программа, CMD = аргументы по умолчанию (наш случай)
«Хочу иметь возможность подменить саму программу» — например, тот же образ запустить как миграции: docker run img dotnet ef database update только CMD, без ENTRYPOINT
«Программа фиксирована, аргументов нет» только ENTRYPOINT
Как всё-таки «залезть внутрь» образа, у которого есть ENTRYPOINT

docker run -it orders-api:1.4.2 bash шелл не откроет: bash станет аргументом и превратится в dotnet Orders.Api.dll bash — приложение просто получит лишний аргумент. Нужен флаг --entrypoint:

$ docker run --rm -it --entrypoint bash orders-api:1.4.2
root@4b1f9c2a7d31:/app#
  • --entrypoint bash — «забудь ENTRYPOINT из образа, запусти вот это».
  • -it — интерактивный режим с терминалом (-i = подавать мой ввод, -t = выделить tty); без них шелл сразу закроется.
  • --rm — удалить контейнер после выхода, чтобы не копить остановленные.
  • Если в образе задан ещё и CMD, его аргументы допишутся к новой команде — ровно по правилу из таблицы выше. В Dockerfile из начала главы CMD нет, поэтому там всё чисто.
  • Для уже запущенного контейнера то же делают через docker exec -it <имя> bash (глава 4) — там ENTRYPOINT вообще ни при чём.

Ещё две вещи в таблице читаются не сразу: — значит «инструкция не задана», а http://+ — «слушать на всех адресах» (+ = любой IP, включая 127.0.0.1 внутри контейнера). Если написать http://localhost:8080, приложение будет принимать запросы только от самого контейнера, и публикация порта -p не поможет.

Форма записи важнее, чем кажется. Запуск без shell:

# exec-форма: PID 1 = dotnet → SIGTERM от docker stop доходит до приложения
ENTRYPOINT ["dotnet", "Orders.Api.dll"]

# shell-форма: Docker выполнит /bin/sh -c "dotnet Orders.Api.dll"
#   (/bin/sh — оболочка, -c = «выполни строку»; см. пояснение в главе 2)
#   PID 1 = /bin/sh; плюс — раскрываются переменные, минус — сигналы часто не доходят
ENTRYPOINT dotnet Orders.Api.dll

Если в Dockerfile нет ни ENTRYPOINT, ни CMD: контейнер выполнит CMD из базового образа — у aspnet это bash. Приложение не запустится, а контейнер сразу завершится: docker ps -a покажет Exited (0) через секунду после старта.

Сборка

Здесь Dockerfile из начала главы превращается в образ — это тот самый шаг 2.

Команда и её вывод (в книге — без цвета: пояснение ниже)

$ docker build -t orders-api:1.4.2 .
[+] Building 41.7s (10/10) FINISHED
 => [internal] load build definition from Dockerfile
 => [internal] load metadata for mcr.microsoft.com/dotnet/sdk:8.0
 => [1/5] FROM mcr.microsoft.com/dotnet/sdk:8.0
 => [2/5] WORKDIR /src
 => [3/5] COPY . .
 => [4/5] RUN dotnet publish -c Release -o /app
 => [5/5] WORKDIR /app
 => exporting to image
 => => naming to docker.io/library/orders-api:1.4.2

Почему в книге «не так, как у меня». В живом терминале этот вывод цветной и анимированный: строки дописываются по мере выполнения, справа тикают секунды, готовые шаги помечаются зелёными галочками, внизу бежит индикатор. Здесь — статичный «снимок» без цвета. Ровно такое же содержимое Docker печатает, когда вывод не терминал (например, лог в CI) или когда добавлен --progress=plain. То есть расхождение — про оформление, а не про смысл; во всей книге вывод сборки показан в этом виде.

Разберём команду по частям:

  • docker build — собрать образ по Dockerfile.
  • -t orders-api:1.4.2 — имя и тег результата (-t = tag). Без него образ будет без имени, только с ID.
  • . — контекст сборки: папка, содержимое которой отправляется демону и доступно для COPY. Чем больше контекст, тем дольше сборка — поэтому нужен .dockerignore (глава 6).
  • Строки [1/5] … [5/5] — шаги сборки. Шагов пять, хотя инструкций в Dockerfile шесть: ENTRYPOINT ничего не выполняет, он только записывает настройку в конфиг образа. Если шаг не изменился, при следующей сборке он берётся из кэша (глава 6).
  • Число (10/10) в первой строке считает все шаги, включая внутренние: загрузку самого Dockerfile, запрос метаданных базового образа, экспорт результата. Ваших шагов из Dockerfile среди них пять — [1/5] … [5/5], поэтому числа и не совпадают.

Флагов, которых в этой команде не было, но они понадобятся, — четыре. Каждый показан со своей командой, чтобы было видно, куда он ставится:

Ещё четыре сборки — по одному новому флагу

# 1) Dockerfile лежит не в корне, а в подпапке: -f = file
$ docker build -f docker/Api.Dockerfile -t orders-api:1.4.2 .

# 2) нужен читаемый текстовый лог вместо анимации (например, чтобы сохранить в CI)
$ docker build --progress=plain -t orders-api:1.4.2 .

# 3) собрать заново, не читая кэш (проверить, не «залип» ли он — глава 6)
$ docker build --no-cache -t orders-api:1.4.2 .

# 4) передать значение ARG из раздела выше
$ docker build --build-arg APP_VERSION=1.4.2 -t orders-api:1.4.2 .
  • -f <путь> — «взять этот файл вместо ./Dockerfile». Контекст (точка в конце) при этом не меняется: пути внутри COPY по-прежнему считаются от него.
  • --progress=plain — печатать шаги строками, без анимации; то же самое Docker делает сам, когда вывод перенаправлен в файл.
  • --no-cache — не читать кэш при сборке (новые слои в кэш всё равно запишутся).
  • --build-arg ИМЯ=значение — задать значение для ARG из Dockerfile. Имя должно быть объявлено через ARG, иначе Docker предупредит, что аргумент не используется.

Что получилось:

$ docker images orders-api
REPOSITORY    TAG     IMAGE ID       CREATED          SIZE
orders-api    1.4.2   5d3c1b7a9e21   10 seconds ago   1.02GB

Гигабайт — потому что в финальном образе остался SDK (компилятор, MSBuild, NuGet), а вместе с ним и исходники. Для разработки это терпимо, для продакшена — нет: образ качается минутами и содержит то, чем можно собрать вредоносный код. Лечится многостадийной сборкой — глава 7.

★ Что запомнить из главы
  • Dockerfile читается сверху вниз; RUN/COPY/ADD создают слои, остальные инструкции пишут настройки в конфиг образа.
  • FROM — полное имя образа: реестр/репозиторий:тег; без интернета образ берётся из локального хранилища (docker load).
  • WORKDIR задаёт текущую папку; COPY . . — «контекст → текущая папка».
  • RUN — две формы: shell (нужны &&, $VAR) и exec (без шелла); установка и очистка — в одной инструкции.
  • ARG — только сборка, ENV — и сборка, и запуск; секреты — ни там, ни там.
  • EXPOSE — документация; USER — non-root; HEALTHCHECK — как Docker проверяет живость.
  • ENTRYPOINT — программа (в exec-форме), CMD — аргументы по умолчанию.
