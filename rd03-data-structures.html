Redis · Часть II · Структуры и кэш

Глава 3. Структуры данных: строки, хеши, списки, множества, sorted sets

Что выбрать под задачу и как это выглядит в StackExchange.Redis

основная глава

Смысл Redis в том, что структура данных живёт на сервере. Вместо «взять JSON, распарсить, изменить, положить обратно» приложение говорит «добавь элемент в множество» — и сервер делает это атомарно, не пересылая весь объект. Ниже — пять базовых типов, каждый с реальным выводом. Во всех примерах главы db — это IDatabase из мультиплексора (глава 2), а Stopwatch — из System.Diagnostics. Имена ключей (hits, user:1, board) и элементов (alice, task-1) тоже придуманы: предопределённых ключей в Redis нет, ключ появляется с первой записи (глава 2).

Договоримся о формате, он одинаковый во всей главе: в коде комментарий рядом со строкой объясняет команду Redis и её аргументы, а строки сразу после Console.WriteLine — это реальный вывод программы ровно в том виде, в каком он был получен.

Строка: string

Универсальное значение: JSON, число, флаг, сериализованный объект. Отдельно ценны атомарные операции над числами — INCR/INCRBY:

// "hits" — имя ключа-счётчика; имена ключей придумываем мы (глава 2)
await db.StringSetAsync("hits", 0);          // SET hits 0   — стартовое значение

await db.StringIncrementAsync("hits");       // INCR hits    → 0 + 1 = 1
await db.StringIncrementAsync("hits", 5);    // INCRBY hits 5 → 1 + 5 = 6

Console.WriteLine($"after incr: {await db.StringGetAsync("hits")}");   // GET hits
// after incr: 6

А что будет, если в тот же ключ положить не число? Проверено теми же вызовами (продолжение программы):

// SET hits один — Redis не проверяет, что именно вы кладёте: это просто строка
await db.StringSetAsync("hits", "один");
try { await db.StringIncrementAsync("hits"); }          // INCR hits
catch (RedisServerException e) { Console.WriteLine($"word:   {e.Message}"); }
// word:   ERR value is not an integer or out of range

// SET hits 2.75 — double уезжает в Redis строкой "2.75"
await db.StringSetAsync("hits", 2.75);
Console.WriteLine($"stored double: [{await db.StringGetAsync("hits")}]");
// stored double: [2.75]
try { await db.StringIncrementAsync("hits"); }          // INCR hits — снова ошибка: это не целое
catch (RedisServerException e) { Console.WriteLine($"double: {e.Message}"); }
// double: ERR value is not an integer or out of range

// INCRBYFLOAT hits 0.5 — вот так дробное считается;
// перегрузка StringIncrementAsync с параметром double уходит именно этой командой
Console.WriteLine($"incrbyfloat: {await db.StringIncrementAsync("hits", 0.5)}");
// incrbyfloat: 3.25

// SET hits 1: bool клиент кодирует как "1"/"0", а не как "true"/"false"
await db.StringSetAsync("hits", true);
Console.WriteLine($"bool: [{await db.StringGetAsync("hits")}] incr -> {await db.StringIncrementAsync("hits")}");
// bool: [1] incr -> 2

// INCR по ключу, который держит хеш, а не строку, — отдельная ошибка
await db.HashSetAsync("user:1", "name", "Алексей");     // HSET user:1 name Алексей
try { await db.StringIncrementAsync("user:1"); }
catch (RedisServerException e) { Console.WriteLine($"hash:   {e.Message}"); }
// hash:   WRONGTYPE Operation against a key holding the wrong kind of value

Причина в том, что INCR — не «сложение вообще», а разбор строки в 64-битное целое (long) и запись результата обратно десятичными цифрами. Типа у значения нет: Redis хранит байты, а смысл им придаёт команда. Это видно по самому ключу: TYPE hits → string (не «integer»), а OBJECT ENCODING hits → int — внутренняя компактная кодировка для маленьких чисел; после INCR она остаётся int, а у положенного нами "2.75" — embstr. Для команд кодировка не важна, для разбора — важна: строка должна целиком читаться как целое. Отсюда четыре следствия:

  • Слово числом не станет. INCR отвечает ERR value is not an integer or out of range, в .NET это RedisServerException; команда не выполнена, значение осталось прежним (один так и лежит в ключе).
  • Дробное число — тоже. 2.75 хранится строкой "2.75", и INCR её не разбирает. Для дробей есть INCRBYFLOAT — в клиенте перегрузка StringIncrementAsync(key, 0.5) с параметром double: она вернула 3.25. Для денег всё равно надёжнее хранить целые копейки и считать INCRBY.
  • bool приезжает числом. Клиент кодирует true как "1", false как "0" — поэтому INCR после true дал 2. Это кодировка клиента, а не «понимание bool» сервером: строка "true", положенная через redis-cli, даёт ошибку.
  • Разбор строгий, а не «почти числовой». Пробелы, +5, 0x10, ведущие нули и переполнение long — всё это отдельные отказы (таблица ниже). При этом INCR не сбрасывает TTL: SET hits 1 EX 100 → TTL 100 → INCR → значение 2, TTL по-прежнему 100.

Практический вывод: «счётчик» и «просто строка» — один и тот же тип; всё зависит от того, что в ключ положили. Если ключ мог достаться от старого кода или из JSON, ошибку INCR нужно обрабатывать либо нормализовать значение перед первым инкрементом.

  • Когда: кэш ответа, счётчик, distributed-флаг, «ключ-значение с TTL».
  • Не когда: нужно менять одно поле большого объекта — это hash, иначе каждый раз пересылается весь JSON.
  • Сложность: GET/SET/INCR — O(1).

Хеш: hash

Объект, разложенный по полям: HSET user:1 name … plan …. Читать можно как весь объект, так и одно поле, и менять одно поле, не пересылая остальные.

// "user:1" — ключ-хеш; HashEntry — пара «поле + значение»
await db.HashSetAsync("user:1", new[]
{
    new HashEntry("name", "Алексей"),        // HSET user:1 name Алексей
    new HashEntry("plan", "pro"),            // HSET user:1 plan pro
});

// HGETALL user:1 — все поля разом
var all = await db.HashGetAllAsync("user:1");
Console.WriteLine($"hgetall: {string.Join(", ", all.Select(e => $"{e.Name}={e.Value}"))}");
// hgetall: name=Алексей, plan=pro

// HSET user:1 visits 10 — заводим счётчик в поле «visits»
await db.HashSetAsync("user:1", "visits", 10);
// HINCRBY user:1 visits 5 — атомарно +5, метод возвращает новое значение
var visits = await db.HashIncrementAsync("user:1", "visits", 5);
Console.WriteLine($"hincrby visits={visits}");
// hincrby visits=15
  • Когда: сущность с небольшим числом полей, которую читают частично (профиль, настройки, счётчики по дням).
  • Плюс: TTL ставится на весь хеш целиком (у полей своего TTL нет — это важно помнить).
  • Сложность: HSET/HGET/HINCRBY — O(1), HGETALL — O(N) по числу полей.
Откуда у e берутся Name и Value

Компилятор знает о них из типа, который возвращает метод. Вот объявление из сборки StackExchange.Redis 2.8.58 (получено рефлексией, не по памяти): HashGetAllAsync(RedisKey key, CommandFlags flags) → Task<HashEntry[]>. Значит all — это массив HashEntry. В выражении all.Select(e => …) параметр e получает тип HashEntry по выводу типов, и дальше действует обычное правило C#: у значения доступны ровно те члены, что объявлены в его типе.

Что объявлено в HashEntry (тоже из рефлексии): это struct (isValueType = True) с двумя свойствами типа RedisValue — Name и Value — и единственным публичным конструктором HashEntry(RedisValue name, RedisValue value). Есть ещё свойство Key, но оно помечено [Obsolete("Please use Name")] — это старый алиас, использовать не надо.

Теперь про new HashEntry("name", "Алексей"): это вызов конструктора, а не «объявление полей». Каждый вызов создаёт одно значение-пару; два ваших вызова — две пары, которые уедут одной командой HSET user:1 name Алексей plan pro. Слова «name» и «plan» здесь — данные (имена полей хеша), а Name/Value — члены типа, через которые программа эти данные читает. Одно и то же слово в двух ролях — отсюда и ощущение, что поля «откуда-то взялись».

Проверка: если написать e.Title, сборка падает с error CS1061: 'HashEntry' does not contain a definition for 'Title'. Список доступных членов задаёт тип, а не то, что вы указывали при создании значения. Что HashEntry — структура, а не класс, тоже не случайность: массив пар тогда лежит одним блоком значений, без отдельного объекта на каждую пару.

Список: list

Двусторонняя очередь: LPUSH/RPUSH с одного конца, LPOP/RPOP с другого. Из неё получается и стек, и очередь. Главное — блокирующее чтение: клиент ждёт на сервере, пока элемент появится, вместо опроса в цикле.

await db.KeyDeleteAsync("q");                // DEL q — чистим ключ от прошлых запусков

// RPUSH q task-1 task-2 — два элемента в правый конец одной командой
await db.ListRightPushAsync("q", new RedisValue[] { "task-1", "task-2" });

// LPOP q — забрать элемент с левого конца (FIFO: что раньше положили, то раньше и взяли)
Console.WriteLine($"lpop:   {await db.ListLeftPopAsync("q")}");
// lpop:   task-1

// LLEN q — сколько элементов осталось
Console.WriteLine($"length: {await db.ListLengthAsync("q")}");
// length: 1

// RPUSH q task-3 — добавить СЛЕДУЮЩИЙ элемент: та же команда, но с одним значением.
// Перегрузка здесь принимает RedisValue, а не массив; возвращает она новую длину списка
var lenAfter = await db.ListRightPushAsync("q", "task-3");
Console.WriteLine($"pushed task-3, length: {lenAfter}");
// pushed task-3, length: 2

// RPUSH q task-4 task-5 — а можно снова пачкой, массивом (отдельной перегрузкой)
await db.ListRightPushAsync("q", new RedisValue[] { "task-4", "task-5" });

// LRANGE q 0 -1 — что лежит в очереди сейчас: 0 — первый элемент, -1 — последний
Console.WriteLine($"q: {string.Join(", ", await db.ListRangeAsync("q"))}");
// q: task-2, task-3, task-4, task-5

// LPUSH q task-0 — тот же список, но с ДРУГОГО конца (левого): элемент встал первым
await db.ListLeftPushAsync("q", "task-0");
Console.WriteLine($"after lpush task-0: {string.Join(", ", await db.ListRangeAsync("q"))}");
// after lpush task-0: task-0, task-2, task-3, task-4, task-5

Итого добавить элемент можно тремя способами — это RPUSH с одним значением, RPUSH с массивом и LPUSH с другого конца:

C#КомандаРезультат
ListRightPushAsync("q", "task-3")RPUSH q task-3 один элемент в правый конец, возвращает новую длину (2)
ListRightPushAsync("q", new RedisValue[] { … }) RPUSH q task-4 task-5несколько элементов одной командой, длина 4
ListLeftPushAsync("q", "task-0")LPUSH q task-0 в левый конец — элемент становится первым

Массива в параметрах «через запятую» у метода нет: пачка передаётся именно RedisValue[]. Зато обратно метод возвращает long — новую длину списка, поэтому LLEN после вставки вызывать не нужно. И обратите внимание на порядок: RPUSH добавляет в конец, а LPOP забирает из начала — это и есть очередь «первым пришёл, первым ушёл» из первой части примера.

Блокирующий вариант в Redis — команда BLPOP. Тонкость, которая ломает половину примеров из интернета: в StackExchange.Redis 2.8 у IDatabase нет типизированного ListLeftPop(key, timeout) — есть только неблокирующий вариант и вариант с количеством. Поэтому BLPOP вызывают как обычную команду:

var sw = Stopwatch.StartNew();

// BLPOP empty:list 2 — «ждать в очереди empty:list до 2 секунд».
// Ключа "empty:list" нет, поэтому сервер держит соединение и ждёт появления
// элемента; по таймауту возвращает nil.
var blpop = await db.ExecuteAsync("BLPOP", "empty:list", 2);

Console.WriteLine($"blpop: {blpop} after {sw.ElapsedMilliseconds} ms");
// blpop: (nil) after 2022 ms

Через 2 секунды сервер вернул «nil», а клиент — примерно 2100 мс ожидания. Это дешевле, чем опрос LPOP раз в 100 мс: один «спящий» запрос вместо сотни пустых.

  • Когда: лёгкая очередь задач без сложной маршрутизации, стек «последние N», LRANGE для ленты.
  • Осторожно: это не брокер. Нет подтверждений, dead-letter и повторной доставки при падении потребителя — для надёжной очереди нужен RabbitMQ (следующая книга).
  • Сложность: LPUSH/RPOP — O(1), LRANGE — O(S+N) (сколько записей пролистали плюс сколько вернули).

Множество: set

Неупорядоченный набор уникальных значений. Проверка вхождения — O(1); пересечения и объединения считает сервер.

await db.KeyDeleteAsync("tags:post:1");      // DEL — начинаем с чистого ключа

// SADD tags:post:1 redis cache dotnet — три элемента одной командой;
// дубликаты игнорируются, поэтому повторный SADD ничего не изменит
await db.SetAddAsync("tags:post:1", new RedisValue[] { "redis", "cache", "dotnet" });

// SISMEMBER tags:post:1 redis — «есть ли элемент»: True или False
Console.WriteLine($"contains redis: {await db.SetContainsAsync("tags:post:1", "redis")}");
// contains redis: True
Console.WriteLine($"contains cobol: {await db.SetContainsAsync("tags:post:1", "cobol")}");
// contains cobol: False

// SCARD tags:post:1 — размер множества
Console.WriteLine($"length:         {await db.SetLengthAsync("tags:post:1")}");
// length:         3

Строки с капсом в комментариях выше — это имена команд Redis, которые вызываются за каждым методом (SET, GET, INCR, HSET, SADD, SMEMBERS). Полезно уметь читать обе записи: в redis-cli, логах и документации Redis вы увидите команды, а в коде — методы, названные по-человечески. Те же три операции «руками» (реальный вывод):

$ redis-cli sismember tags:post:1 redis    # ↔ SetContainsAsync
1                                          # 1 = есть, 0 = нет (число, а не True/False)
$ redis-cli sismember tags:post:1 cobol
0
$ redis-cli scard tags:post:1              # ↔ SetLengthAsync
3
$ redis-cli smembers tags:post:1           # ↔ SetMembersAsync: все элементы
redis
cache
dotnet

SMEMBERS отдаёт элементы без определённого порядка — полагаться на последовательность нельзя. Для больших множеств есть SSCAN: обход порциями, как SCAN вместо KEYS (глава 2).

  • Когда: теги, «кто уже видел», дедупликация, пересечение аудиторий (SINTER), чёрные списки.
  • Плюс: вставка дубликата ничего не меняет — идемпотентность бесплатно.
  • Сложность: SADD/SISMEMBER/SREM — O(1), SMEMBERS — O(N), SINTER — O(N×M) в худшем случае.

Сортированное множество: sorted set

Множество, где у каждого элемента есть вес (score), и сервер держит элементы отсортированными по нему. Это «рейтинг» и «окно времени» одновременно.

await db.KeyDeleteAsync("board");            // "board" — ключ-рейтинг (leaderboard), имя наше

// ZADD board 10 alice — ПЕРВЫЙ способ: один элемент за вызов
//   аргументы: ключ "board", элемент "alice", вес (score) 10
await db.SortedSetAddAsync("board", "alice", 10);

// ZADD board 30 bob 20 carol — ВТОРОЙ способ: та же команда, но пачкой.
// Здесь второй параметр — массив SortedSetEntry, где каждый элемент — пара
// «элемент + вес». Оба вызова делают одно и то же, разница только в форме.
await db.SortedSetAddAsync("board", new[]
{
    new SortedSetEntry("bob", 30),
    new SortedSetEntry("carol", 20),
});

// ZREVRANGE board 0 1 WITHSCORES — топ-2 по убыванию веса:
//   0 и 1 — индексы (с нуля), Order.Descending — от большего веса к меньшему
var top2 = await db.SortedSetRangeByRankWithScoresAsync("board", 0, 1, Order.Descending);
Console.WriteLine($"top2: {string.Join(", ", top2.Select(t => $"{t.Element}={t.Score}"))}");
// top2: bob=30, carol=20

// ZINCRBY board 15 alice — прибавить 15 к весу alice; вернётся НОВЫЙ вес
var score = await db.SortedSetIncrementAsync("board", "alice", 15);
Console.WriteLine($"zincrby alice={score}");
// zincrby alice=25

// ZCARD board — сколько элементов в множестве
Console.WriteLine($"length: {await db.SortedSetLengthAsync("board")}");
// length: 3

Что происходит с весами по шагам: alice=10, bob=30, carol=20 → топ-2 это bob и carol → после ZINCRBY у alice становится 25, и она обгоняет carol. В redis-cli то же видно наглядно (WITHSCORES печатает элемент и вес):

$ redis-cli zrange board 0 -1 withscores   # все элементы от меньшего веса к большему

$ redis-cli zrevrange board 0 1 withscores  # топ-2 от большего к меньшему

Вес — число с плавающей точкой, а не обязательно «очки»: часто туда кладут метку времени, и тогда получается очередь с приоритетом по времени (следующий пример). Элемент уникален: повторный ZADD с тем же именем не добавит второй, а заменит вес.

Ничьи: что будет, если у двух элементов одинаковый вес

Равные веса — обычное дело (у двух игроков по 30 очков). Порядок внутри такой группы задаёт имя элемента, побайтово, а не порядок вставки: Redis его просто не хранит. Проверено на том же board, к которому добавили dave с весом 30, как у bob:

// ZADD board 30 dave — вес тот же, что у bob: получается ничья
await db.SortedSetAddAsync("board", "dave", 30);

// ZRANGE board 0 -1 WITHSCORES — по возрастанию веса; внутри равных весов — по возрастанию имени
var asc = await db.SortedSetRangeByRankWithScoresAsync("board", 0, -1);
Console.WriteLine($"zrange:    {string.Join(", ", asc.Select(x => $"{x.Element}={x.Score}"))}");
// zrange:    carol=20, alice=25, bob=30, dave=30

// ZREVRANGE board 0 -1 WITHSCORES — по убыванию веса; внутри ничьей — по УБЫВАНИЮ имени
var desc = await db.SortedSetRangeByRankWithScoresAsync("board", 0, -1, Order.Descending);
Console.WriteLine($"zrevrange: {string.Join(", ", desc.Select(x => $"{x.Element}={x.Score}"))}");
// zrevrange: dave=30, bob=30, alice=25, carol=20

// ZRANK / ZREVRANK — позиции в этих двух порядках у ничьей разные
Console.WriteLine($"rank bob={await db.SortedSetRankAsync("board", "bob")} dave={await db.SortedSetRankAsync("board", "dave")}");
// rank bob=2 dave=3
Console.WriteLine($"revrank bob={await db.SortedSetRankAsync("board", "bob", Order.Descending)} dave={await db.SortedSetRankAsync("board", "dave", Order.Descending)}");
// revrank bob=1 dave=0

// Топ-2 после ничьей: dave и bob (по 30), carol с 20 из топ-2 выпал
var top2 = await db.SortedSetRangeByRankWithScoresAsync("board", 0, 1, Order.Descending);
Console.WriteLine($"top2 now: {string.Join(", ", top2.Select(x => $"{x.Element}={x.Score}"))}");
// top2 now: dave=30, bob=30

// ZADD board 30 bob — повторный ZADD того же элемента не создаёт дубликат
await db.SortedSetAddAsync("board", "bob", 30);
Console.WriteLine($"length after zadd bob 30 again: {await db.SortedSetLengthAsync("board")}");
// length after zadd bob 30 again: 4

// ZADD board 30 Zoe — ещё одна ничья: 'Z' = 0x5A, 'b' = 0x62, значит Zoe идёт РАНЬШЕ bob
await db.SortedSetAddAsync("board", "Zoe", 30);
var tie = await db.SortedSetRangeByScoreWithScoresAsync("board", 30, 30);
Console.WriteLine($"ties 30: {string.Join(", ", tie.Select(x => $"{x.Element}={x.Score}"))}");
// ties 30: Zoe=30, bob=30, dave=30

top2 = await db.SortedSetRangeByRankWithScoresAsync("board", 0, 1, Order.Descending);
Console.WriteLine($"top2 with Zoe: {string.Join(", ", top2.Select(x => $"{x.Element}={x.Score}"))}");
// top2 with Zoe: dave=30, bob=30
  • Ничья разрешается именем, а не временем вставки. dave добавлен позже bob и с тем же весом — в ZRANGE он стоит после него, но не потому, что «пришёл вторым».
  • В ZREVRANGE порядок ничьей переворачивается вместе с весом: было bob, dave, стало dave, bob. Поэтому и ранги разные: ZRANK bob=2, dave=3, а ZREVRANK bob=1, dave=0.
  • Сравнение побайтовое ('Z' = 0x5A < 'b' = 0x62): Zoe оказывается первой в группе с весом 30. Это не «алфавитный порядок по локали», а сравнение имён как строк байтов — важно для смешанного регистра и не-ASCII имён.
  • Топ-N при ничьих зависит от имён, но результат детерминирован: после добавления Zoe топ-2 — dave и bob, а не Zoe: в обратном порядке dave и bob стоят раньше Zoe.
  • Повторный ZADD — не дубликат: длина осталась 4, у bob просто ещё раз записан вес 30.

Если «кто первый при равных очках» важно по смыслу (кто раньше набрал те же 30), одного веса недостаточно: Redis не хранит порядок вставки. Тогда вес делают уникальным (например, составным) или держат порядок отдельно — иначе место в топе будет решать имя.

Второе применение — лимит запросов («не больше N за минуту»): элементы — запросы, вес — метка времени, а количество считается по диапазону:

await db.KeyDeleteAsync("rate:user:1");      // «журнал» запросов одного пользователя

// Три запроса: элемент "req:0", "req:1", "req:2" — сами запросы (имена уникальны),
// вес — время запроса в миллисекундах: ZADD rate:user:1 <время> req:i
for (var i = 0; i < 3; i++)
    await db.SortedSetAddAsync("rate:user:1", $"req:{i}", DateTimeOffset.UtcNow.ToUnixTimeMilliseconds());

// ZCOUNT rate:user:1 <минуту назад> +inf — сколько весов попало в окно 60 секунд:
//   от = сейчас − 60 с (в мс), до = +∞, то есть «всё, что новее»
var from = DateTimeOffset.UtcNow.AddSeconds(-60).ToUnixTimeMilliseconds();
var count = await db.SortedSetLengthAsync("rate:user:1", from, double.PositiveInfinity);

Console.WriteLine($"rate last 60s={count}");
// rate last 60s=3

Два продолжения, без которых лимит в проде не работает: старые записи нужно удалять — ZREMRANGEBYSCORE rate:user:1 0 <минуту назад>, иначе множество растёт бесконечно; и проверку «сколько уже было» вместе с добавлением делают атомарно — скриптом на Lua, как снятие лока в главе 4, — иначе два параллельных запроса оба увидят 3 и оба пройдут.

  • Когда: рейтинги и лидерборды, отложенные задачи (вес = время выполнения), лимиты, «последние N по времени».
  • Сложность: ZADD/ZINCRBY — O(log N), ZRANGE — O(log N + M) по числу возвращаемых элементов.

Антипаттерны структур
  • Гонять весь объект ради одного поля. JSON в string, где меняется один флаг, — это чтение и запись всего объекта; hash дешевле.
  • Хранить счётчик в JSON. «Прочитать, прибавить, записать» теряет обновления; INCR/HINCRBY — нет.
  • Один ключ на миллион элементов. Любая команда над ним блокирует сервер на всё время работы: делите на части (tags:post:1, tags:post:2, …).
  • Строить надёжную очередь на list. Без подтверждений и dead-letter сообщения теряются при падении потребителя.
★ Что запомнить из главы
  • Структура выбирается по операции, а не по привычке: поля — hash, уникальность — set, порядок — sorted set, очередь — list.
  • Атомарные команды сервера (INCR, SADD, ZINCRBY) заменяют «прочитать-изменить-записать».
  • Блокирующее чтение (BLPOP) вызывается через ExecuteAsync; в 2.8 типизированного метода с таймаутом нет.
  • TTL — на весь ключ. У полей хеша и элементов списка своего времени жизни нет.
