Глава 3. Структуры данных: строки, хеши, списки, множества, sorted sets

Что выбрать под задачу и как это выглядит в StackExchange.Redis

основная глава

Смысл Redis в том, что структура данных живёт на сервере. Вместо «взять JSON, распарсить, изменить, положить обратно» приложение говорит «добавь элемент в множество» — и сервер делает это атомарно, не пересылая весь объект. Ниже — пять базовых типов, каждый с реальным выводом. Во всех примерах главы db — это IDatabase из мультиплексора (глава 2), а Stopwatch — из System.Diagnostics.

Строка: string

Универсальное значение: JSON, число, флаг, сериализованный объект. Отдельно ценны атомарные операции над числами — INCR/INCRBY:

await db.StringSetAsync("hits", 0);
await db.StringIncrementAsync("hits");        // 1
await db.StringIncrementAsync("hits", 5);     // 6
Console.WriteLine(await db.StringGetAsync("hits"));   // 6
  • Когда: кэш ответа, счётчик, distributed-флаг, «ключ-значение с TTL».
  • Не когда: нужно менять одно поле большого объекта — это hash, иначе каждый раз пересылается весь JSON.
  • Сложность: GET/SET/INCR — O(1).

Хеш: hash

Объект, разложенный по полям: HSET user:1 name … plan …. Читать можно как весь объект, так и одно поле, и менять одно поле, не пересылая остальные.

await db.HashSetAsync("user:1", new[]
{
    new HashEntry("name", "Алексей"),
    new HashEntry("plan", "pro"),
});

var all = await db.HashGetAllAsync("user:1");
Console.WriteLine(string.Join(", ", all.Select(e => $"{e.Name}={e.Value}")));
// name=Алексей, plan=pro

await db.HashSetAsync("user:1", "visits", 10);
var visits = await db.HashIncrementAsync("user:1", "visits", 5);
Console.WriteLine($"hincrby visits={visits}");          // hincrby visits=15
  • Когда: сущность с небольшим числом полей, которую читают частично (профиль, настройки, счётчики по дням).
  • Плюс: TTL ставится на весь хеш целиком (у полей своего TTL нет — это важно помнить).
  • Сложность: HSET/HGET/HINCRBY — O(1), HGETALL — O(N) по числу полей.

Список: list

Двусторонняя очередь: LPUSH/RPUSH с одного конца, LPOP/RPOP с другого. Из неё получается и стек, и очередь. Главное — блокирующее чтение: клиент ждёт на сервере, пока элемент появится, вместо опроса в цикле.

await db.KeyDeleteAsync("q");

// producer: кладём в правый конец
await db.ListRightPushAsync("q", new RedisValue[] { "task-1", "task-2" });

// consumer: забираем с левого — FIFO
Console.WriteLine(await db.ListLeftPopAsync("q"));     // task-1
Console.WriteLine(await db.ListLengthAsync("q"));      // 1

Блокирующий вариант в Redis — команда BLPOP. Тонкость, которая ломает половину примеров из интернета: в StackExchange.Redis 2.8 у IDatabase нет типизированного ListLeftPop(key, timeout) — есть только неблокирующий вариант и вариант с количеством. Поэтому BLPOP вызывают как обычную команду:

var sw = Stopwatch.StartNew();
var blpop = await db.ExecuteAsync("BLPOP", "empty:list", 2);   // ждать 2 секунды
Console.WriteLine($"[{blpop}] after {sw.ElapsedMilliseconds} ms");
// [(nil)] after 2108 ms

Через 2 секунды сервер вернул «nil», а клиент — примерно 2100 мс ожидания. Это дешевле, чем опрос LPOP раз в 100 мс: один «спящий» запрос вместо сотни пустых.

  • Когда: лёгкая очередь задач без сложной маршрутизации, стек «последние N», LRANGE для ленты.
  • Осторожно: это не брокер. Нет подтверждений, dead-letter и повторной доставки при падении потребителя — для надёжной очереди нужен RabbitMQ (следующая книга).
  • Сложность: LPUSH/RPOP — O(1), LRANGE — O(S+N) (сколько записей пролистали плюс сколько вернули).

Множество: set

Неупорядоченный набор уникальных значений. Проверка вхождения — O(1); пересечения и объединения считает сервер.

await db.KeyDeleteAsync("tags:post:1");
await db.SetAddAsync("tags:post:1", new RedisValue[] { "redis", "cache", "dotnet" });

Console.WriteLine(await db.SetContainsAsync("tags:post:1", "redis"));  // True
Console.WriteLine(await db.SetContainsAsync("tags:post:1", "cobol"));  // False
Console.WriteLine(await db.SetLengthAsync("tags:post:1"));              // 3

// sismember redis=True cobol=False
// scard=3 smembers=redis,cache,dotnet
  • Когда: теги, «кто уже видел», дедупликация, пересечение аудиторий (SINTER), чёрные списки.
  • Плюс: вставка дубликата ничего не меняет — идемпотентность бесплатно.
  • Сложность: SADD/SISMEMBER/SREM — O(1), SMEMBERS — O(N), SINTER — O(N×M) в худшем случае.

Сортированное множество: sorted set

Множество, где у каждого элемента есть вес (score), и сервер держит элементы отсортированными по нему. Это «рейтинг» и «окно времени» одновременно.

await db.KeyDeleteAsync("board");
await db.SortedSetAddAsync("board", "alice", 10);
await db.SortedSetAddAsync("board", new[]
{
    new SortedSetEntry("bob", 30),
    new SortedSetEntry("carol", 20),
});

var top2 = await db.SortedSetRangeByRankWithScoresAsync("board", 0, 1, Order.Descending);
Console.WriteLine(string.Join(", ", top2.Select(t => $"{t.Element}={t.Score}")));
// bob=30, carol=20

// прибавить к весу атомарно
var score = await db.SortedSetIncrementAsync("board", "alice", 15);
Console.WriteLine(score);                                  // 25
Console.WriteLine(await db.SortedSetLengthAsync("board")); // 3

Второе применение — лимит запросов («не больше N за минуту»): элементы — запросы, вес — метка времени, а количество считается по диапазону:

await db.KeyDeleteAsync("rate:user:1");
for (var i = 0; i < 3; i++)
    await db.SortedSetAddAsync("rate:user:1", $"req:{i}", DateTimeOffset.UtcNow.ToUnixTimeMilliseconds());

var from = DateTimeOffset.UtcNow.AddSeconds(-60).ToUnixTimeMilliseconds();
var count = await db.SortedSetLengthAsync("rate:user:1", from, double.PositiveInfinity);
Console.WriteLine($"rate last 60s={count}");     // rate last 60s=3
  • Когда: рейтинги и лидерборды, отложенные задачи (вес = время выполнения), лимиты, «последние N по времени».
  • Сложность: ZADD/ZINCRBY — O(log N), ZRANGE — O(log N + M) по числу возвращаемых элементов.

Антипаттерны структур
  • Гонять весь объект ради одного поля. JSON в string, где меняется один флаг, — это чтение и запись всего объекта; hash дешевле.
  • Хранить счётчик в JSON. «Прочитать, прибавить, записать» теряет обновления; INCR/HINCRBY — нет.
  • Один ключ на миллион элементов. Любая команда над ним блокирует сервер на всё время работы: делите на части (tags:post:1, tags:post:2, …).
  • Строить надёжную очередь на list. Без подтверждений и dead-letter сообщения теряются при падении потребителя.
★ Что запомнить из главы
  • Структура выбирается по операции, а не по привычке: поля — hash, уникальность — set, порядок — sorted set, очередь — list.
  • Атомарные команды сервера (INCR, SADD, ZINCRBY) заменяют «прочитать-изменить-записать».
  • Блокирующее чтение (BLPOP) вызывается через ExecuteAsync; в 2.8 типизированного метода с таймаутом нет.
  • TTL — на весь ключ. У полей хеша и элементов списка своего времени жизни нет.
