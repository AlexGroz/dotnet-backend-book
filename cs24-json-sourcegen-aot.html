Глава 24. Сериализация без рефлексии: System.Text.Json, source generators и AOT

По умолчанию System.Text.Json строит метаданные о типе рефлексией при первом вызове. Разбираем, сколько это стоит (с замерами), как включить генератор исходников (JsonSerializerContext), какие ограничения он накладывает на DTO и почему в Native AOT без него нельзя. Всё измерено на .NET 9 в Release.

основная глава

Что делает сериализатор по умолчанию

Вызов JsonSerializer.Serialize(order) без явных настроек использует JsonSerializerOptions.Default. При первом обращении к типу сериализатор строит метаданные рефлексией: перечисляет свойства, читает атрибуты, создаёт план сериализации и кэширует его в объекте настроек. Дальше работа идёт по готовому плану, но:

  • первый вызов дороже — рефлексия и создание делегатов;
  • метаданные и делегаты — это управляемая память, живущая столько же, сколько процесс;
  • триммер (trimming) и AOT не видят, какие свойства нужны: они используются по имени, которого в коде нет (глава 22 про рефлексию и AOT).

Замер: сто тысяч сериализаций одного заказа (две позиции), минимум из трёх прогонов в Release:

100 000 сериализаций одного и того же заказа (.NET 9, Release, 16 ядер):
   рефлексия:   400 мс, выделено 74 МБ
   source-gen:  280 мс, выделено 45 МБ

первый вызов в свежем процессе:
   рефлексия:  49.3 мс
   source-gen: 33.9 мс

То есть выигрыш — примерно 30 % по времени и 40 % по аллокациям, а не «в десять раз», как иногда обещают. На один запрос это доли микросекунды. Зачем тогда генератор? Ответ ниже: из-за AOT.

Как включить: JsonSerializerContext

Генератор исходников — это анализатор в SDK: он видит атрибуты и дописывает класс с готовым планом сериализации. Нужен partial-класс, унаследованный от JsonSerializerContext, с атрибутами [JsonSerializable] на каждый корневой тип:

[JsonSourceGenerationOptions(PropertyNamingPolicy = JsonKnownNamingPolicy.CamelCase,
                             UseStringEnumConverter = true)]
[JsonSerializable(typeof(OrderDto))]
[JsonSerializable(typeof(List<OrderDto>))]
internal partial class AppJsonContext : JsonSerializerContext;   // вторая половина генерируется

Сгенерированный код появляется в obj/Release/net9.0/System.Text.Json.SourceGeneration/… — это обычный C#, его можно открыть и посмотреть. Использование — через Default, где на каждый тип есть свойство JsonTypeInfo<T>:

var json = JsonSerializer.Serialize(order, AppJsonContext.Default.OrderDto);
var dto  = JsonSerializer.Deserialize(json, AppJsonContext.Default.OrderDto);

// вариант «по типу»: план берётся из контекста, а не из рефлексии
var loose = JsonSerializer.Serialize(order, typeof(OrderDto), AppJsonContext.Default);

В ASP.NET Core контекст подключается к Minimal API одной строкой (проверено: компилируется и работает):

builder.Services.ConfigureHttpJsonOptions(o =>
    o.SerializerOptions.TypeInfoResolverChain.Insert(0, AppJsonContext.Default));
Что такое TypeInfoResolverChain

Это список «поставщиков метаданных». Первым ставится сгенерированный контекст: если тип в нём есть — используется он; если нет — цепочка идёт дальше, к рефлексии. Так можно включить генератор постепенно, не переписывая все DTO сразу.

Что генератор накладывает на DTO

Ограничения не выдуманные: каждое видно в прогоне. Ниже — то, на чём чаще всего спотыкаются.

1. Все типы должны быть известны заранее

Если типа нет в контексте и он не достижим из перечисленных, сериализация падает (проверено):

InvalidOperationException: JsonTypeInfo metadata for type 'LegacyDto' was not provided by
TypeInfoResolver of type 'AppJsonContext'. If using source generation, ensure that all root types
passed to the serializer have been annotated with 'JsonSerializableAttribute', along with any
types that might be serialized polymorphically.

Это же и плюс: ошибка видна сразу, а не в проде. Но цена — [JsonSerializable] нужно поддерживать: новый DTO в API = новая строка в контексте.

2. Полиморфизм: без атрибута поля наследника пропадают

Свойство базового типа сериализуется по плану базового типа. Замер на abstract record PaymentDto(decimal Amount) и наследнике с номером карты:

без [JsonDerivedType]: {"amount":100}
с  [JsonDerivedType]: {"kind":"card","pan":"4111","amount":100}

В первом случае pan исчез молча — ни ошибки, ни предупреждения в рантайме. Лечится явным описанием иерархии:

[JsonPolymorphic(TypeDiscriminatorPropertyName = "kind")]
[JsonDerivedType(typeof(CardPaymentDto), "card")]
public abstract record PaymentDto(decimal Amount);

public sealed record CardPaymentDto(string Pan, decimal Amount) : PaymentDto(Amount);
// в JSON появится "kind":"card" — по нему при десериализации выбирается наследник

3. object и dynamic: в JIT работает, в AOT — нет

Свойство типа object сериализуется по фактическому типу значения (проверено):

{"type":"order.paid","data":{"pan":"4111","amount":100}}

Но «по фактическому типу» — это ровно тот сценарий, который требует метаданных во время работы. В обычном .NET он поддержан, в Native AOT — нет: там действует правило «тип известен на компиляции». Поэтому object/dynamic в DTO — красный флаг для AOT-сборки.

4. Настройки контекста и рантайма должны совпадать

Политика именования задаётся в [JsonSourceGenerationOptions] и должна совпадать с JsonSerializerOptions, которыми вы пользуетесь в остальном коде. Проверка: контекст с camelCase против JsonSerializer.Serialize(order) без настроек дал разный JSON — "id" против "Id". После выравнивания настроек строки совпали (проверено).

5. Enum: по умолчанию число

Без настройки перечисление уходит числом — "status":0. Чтобы строками, нужен флаг (проверено):

[JsonSourceGenerationOptions(PropertyNamingPolicy = JsonKnownNamingPolicy.CamelCase,
                             UseStringEnumConverter = true)]
// → "status":"New"   (значения перечисления политикой именования не меняются)

Мелочь, но именно она чаще всего ломает контракт при переходе с рефлексии на генератор: раньше JsonStringEnumConverter мог быть добавлен в Converters где-то в другом месте, и никто об этом не помнил.

Связь с Native AOT и trimming

Native AOT компилирует приложение в машинный код до запуска. Значит, «построить метаданные рефлексией в рантайме» негде: кода, который это делает, в сборке нет. Поэтому рефлексивные перегрузки JsonSerializer помечены атрибутами [RequiresUnreferencedCode] и [RequiresDynamicCode], а анализатор говорит об этом прямо. Проверка — сборка с <IsAotCompatible>true</IsAotCompatible>:

warning IL2026: Using member 'JsonSerializer.Serialize<TValue>(TValue, JsonSerializerOptions)'
which has 'RequiresUnreferencedCodeAttribute' can break functionality when trimming application
code. JSON serialization and deserialization might require types that cannot be statically analyzed.
Use the overload that takes a JsonTypeInfo or JsonSerializerContext, or make sure all of the required
types are preserved.

warning IL3050: Using member 'JsonSerializer.Serialize<TValue>(TValue, JsonSerializerOptions)'
which has 'RequiresDynamicCodeAttribute' can break functionality when AOT compiling. JSON
serialization and deserialization might require types that cannot be statically analyzed and might
need runtime code generation. Use System.Text.Json source generation for native AOT applications.

Читается это так: для AOT сериализация обязана быть сгенерированной. Перегрузки, принимающие JsonTypeInfo/JsonSerializerContext, таких предупреждений не дают — ровно поэтому в контексте есть свойства вида Default.OrderDto.

Trimming ломает мягче, чем AOT

При обрезке кода свойство, к которому обращаются только по имени, может быть вырезано: сборка соберётся, а в рантайме придёт null вместо значения — тот же механизм, что описан в главе 22. Сгенерированный план ссылается на свойства кодом, поэтому триммер их видит и сохраняет.

Когда включать, а когда не стоит

СитуацияРешениеПочему
Native AOT, CLI, serverlessОбязательно Без генератора сериализация не работает (IL3050)
Trimmed-публикацияОбязательноИначе свойства вырежутся (IL2026)
Горячий API на JITСтоит включить−30 % CPU и −40 % аллокаций на сериализацию, меньше давления на GC (глава 6)
Пара эндпоинтов, редкая сериализацияМожно не включатьКодоген добавляет строки в контекст, которые надо поддерживать

Практическое правило: один контекст на приложение, подключённый первым в TypeInfoResolverChain; тест, который сериализует каждый публичный DTO, ловит забытый [JsonSerializable] до прода — ошибка из раздела выше (InvalidOperationException про отсутствующие метаданные) и есть этот сигнал.

★ Что запомнить
  • System.Text.Json по умолчанию строит метаданные рефлексией и кэширует их; первый вызов дороже, и этот путь несовместим с AOT.
  • Генератор включается partial-классом : JsonSerializerContext с [JsonSerializable]; в Minimal API — через ConfigureHttpJsonOptions(... TypeInfoResolverChain.Insert(0, Context.Default)).
  • Выигрыш на JIT — около 30 % времени и 40 % аллокаций (замер), главная же причина — AOT и trimming.
  • Ограничения на DTO: все типы перечислены (иначе InvalidOperationException про метаданные); полиморфизм — только через [JsonPolymorphic]/[JsonDerivedType], иначе поля наследника исчезают молча; object/dynamic в AOT не работают; настройки контекста и JsonSerializerOptions должны совпадать; enum — число, пока не включён UseStringEnumConverter.
  • Для AOT сериализация обязана идти через JsonTypeInfo/контекст: рефлексивные перегрузки дают IL2026 и IL3050.
