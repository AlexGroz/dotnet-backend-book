Глава 16. Способы сканирования: Seq, Index, Index Only, Bitmap

«Scan» — это способ, которым СУБД достаёт строки таблицы. Разберём каждый способ с нуля: как работает, как выбирается и как его изменить.

Что такое «сканирование» (scan)

Когда в плане (глава 15) появляется строка вида Seq Scan on orders или Index Scan using orders_pkey on orders — это узел, который достаёт строки из таблицы. Способов сделать это несколько, и называется каждый scan.

Все способы сводятся к двум стратегиям из главы 6:

  • читать подряд — страница за страницей (последовательно);
  • читать точечно — прыгать к нужным страницам по индексу.

Прямой ответ: когда выбирается Seq Scan

Seq Scan ≠ «нет индекса»

Это решение по стоимости (главы 13–14), а не признак отсутствия индекса. Возможны два случая:

  • Подходящего индекса нет — тогда выбора просто нет, и будет Seq Scan.
  • Индекс есть, но планировщик считает полное чтение дешевле — например, запрос выбирает большую часть таблицы. Тогда он сознательно выберет Seq Scan, проигнорировав индекс.

Поэтому если ты видишь Seq Scan — нельзя сразу делать вывод «нет индекса». Сначала смотрим, сколько строк реально нужно (глава 15).

Seq Scan — последовательное чтение

Читает все страницы таблицы подряд, строка за строкой, и проверяет каждую на условие.

->  Seq Scan on orders o  (cost=0.00..8000.00 rows=5000 width=24)
                          (actual time=0.02..380.90 rows=480000 loops=1)
      Filter: (status = 'NEW'::text)
      Rows Removed by Filter: 4520000        ← прочитали, но выбросили
      Buffers: shared hit=1800 read=45000    ← 45 000 страниц прочитано с ДИСКА
  • Хорош, когда: таблица небольшая, или нужна большая доля её строк — тогда подряд читать дешевле, чем прыгать.
  • Плох, когда: таблица большая, а нужна малая часть строк: читаем миллионы, выбрасываем почти всё (Rows Removed by Filter огромный).
  • Признак проблемы в плане: Seq Scan + большая таблица + большой Rows Removed by Filter.

Index Scan — чтение по индексу

Сначала ищет нужные строки в индексе (глава 9), получает их адреса (ctid), а затем идёт в таблицу за остальными колонками.

Хороший случай: нужна одна строка

->  Index Scan using orders_pkey on orders  (cost=0.42..8.44 rows=1 width=24)
                                            (actual time=0.02..0.03 rows=1 loops=1)
      Index Cond: (id = 12345)
      Buffers: shared hit=4            ← всего 4 страницы, и все из кэша

Плохой случай: «прыжков» слишком много

->  Index Scan using orders_status_idx on orders
      (cost=0.42..18400.00 rows=480000 width=24)
      (actual time=0.03..310.50 rows=480000 loops=1)
      Index Cond: (status = 'NEW'::text)
      Buffers: shared hit=1200 read=15800
                    ▲           ▲
                    │           └─ read: читали с ДИСКА (дорого)
                    └─ hit: взяли из кэша (дёшево)
  • Хорош, когда: нужна малая часть строк — читаем точечно (первый пример: 4 страницы).
  • Плох, когда: строк по индексу набирается много — каждое обращение к таблице это «случайное» чтение отдельной страницы, а их тысячи (второй пример: 15 800 страниц с диска). Тогда Seq Scan может оказаться дешевле — поэтому планировщик его и выбирает.
  • Признак в плане: узел Index Scan с большим actual rows и большим Buffers: read.
Откуда в плане строка Buffers:

Она появляется только если снимать план с опцией BUFFERS: EXPLAIN (ANALYZE, BUFFERS) … (глава 15). Без неё этой строки в выводе не будет — поэтому в примерах её иногда не видно.

  • hit — страница уже была в памяти (быстро);
  • read — страницу читали с диска (медленно).

Много read = чтения «прыгают» по диску. Это и есть цена плохого Index Scan.

Почему «случайные» чтения дороже

Читать страницы подряд диск умеет быстро (последовательный доступ). А прыгать к разбросанным страницам — медленнее, и это отражено в настройках: seq_page_cost = 1, random_page_cost = 4 (глава 13). Поэтому при большом числе строк индекс проигрывает.

Index Only Scan — «всё нужное в индексе»

Если все колонки, которые нужны запросу, уже есть в индексе (это называют покрывающим индексом, глава 11), в таблицу можно вообще не ходить.

->  Index Only Scan using orders_status_idx on orders
      Index Cond: (status = 'NEW')
      Heap Fetches: 0        ← 0 значит: в таблицу не ходили вообще
  • Хорош, когда: индекс «покрывает» запрос — это самый быстрый способ чтения.
  • Нюанс: работает в полную силу, только если актуальна карта видимости (её обновляет VACUUM). Если нет — в плане появится Heap Fetches, то есть СУБД всё равно пойдёт в таблицу.
  • Как получить: добавить нужные колонки в индекс (CREATE INDEX ON orders (status) INCLUDE (created_at);). Почему именно через INCLUDE, а не «через запятую» — объяснено в главе 11.

Bitmap — «двухшаговое» чтение

Промежуточный вариант между Index Scan и Seq Scan. Работает в два этапа:

  1. Bitmap Index Scan — по индексу собирается «карта» подходящих страниц (не строк).
  2. Bitmap Heap Scan — эти страницы читаются в порядке возрастания, а не вразнобой.
->  Bitmap Heap Scan on orders  (actual rows=12000 loops=1)
      Recheck Cond: (status = 'NEW')
      ->  Bitmap Index Scan on orders_status_idx
            Index Cond: (status = 'NEW')
  • Хорош, когда: строк «средне» — не мало (тогда хватило бы Index Scan) и не почти вся таблица (тогда Seq Scan).
  • Плюс: меньше «случайных» чтений, чем у обычного Index Scan.
  • Минус: теряется порядок — если запрос сортирует, сортировку придётся делать отдельно (Sort).

Как планировщик выбирает способ

По стоимости (главы 13–14). Ключевые факторы: сколько строк вернёт запрос (доля от таблицы), сколько страниц придётся прочитать и насколько чтения «разбросаны».

Пример на числах (таблица 1 000 000 строк)
Запрос возвращаетЧто выберет планировщикПочему
10 строк из 1 000 000 (0,001%)Index ScanПара «прыжков» до страниц — дёшево
~10 000 строк (1%)Bitmap (часто) или Index ScanСредний случай: карта страниц экономит прыжки
~700 000 строк (70%)Seq ScanЧитать почти всю таблицу подряд дешевле, чем прыгать

Обрати внимание: в третьей строке индекс есть — просто он не помогает на такой доле строк.

Ещё два фактора:

  • Корреляция (глава 13, correlation): если данные физически упорядочены по колонке индекса, «прыжки» становятся почти последовательным чтением — и Index Scan дешевеет.
  • random_page_cost: на SSD случайные чтения дешевле, поэтому его снижают до ≈1.1 — и планировщик охотнее выбирает индексы.

Как изменить способ чтения (и можно ли «заставить»)

Прямого «приказа» использовать индекс в PostgreSQL нет (подсказок, как в Oracle, — тоже, глава 20). Но на выбор можно влиять. По шагам:

  1. Посчитать долю строк. Если запрос по факту возвращает больше ~5–10% таблицы — Seq Scan это правильный выбор, «чинить» нечего. Если меньше — идём дальше.
  2. Проверить, есть ли подходящий индекс. Он должен совпадать с условием и порядком колонок (главы 10–11). Нет — создать: CREATE INDEX ON orders (status, created_at DESC);
  3. Убрать функцию/приведение над колонкой. WHERE lower(email) = … по индексу на email не пойдёт — либо убираем функцию, либо делаем функциональный индекс.
  4. Обновить статистику. ANALYZE orders; Если оценка доли строк неверна (глава 14), планировщик выберет план «вслепую» — например, посчитает, что строк много, и возьмёт Seq Scan.
  5. Сделать индекс покрывающим — если запросу нужны ещё колонки, добавить их в INCLUDE, чтобы получить Index Only Scan.
  6. Настроить random_page_cost под SSD (≈1.1) — тогда индекс станет «дешевле» в глазах планировщика.

★ Что запомнить

Способ чтения выбирает планировщик по стоимости, а не «наличие индекса». Seq Scan — это не всегда «нет индекса»: при большой доле строк это правильный выбор. Index Scan выгоден на малой доле, Index Only Scan — когда всё нужное в индексе, Bitmap — в середине. Влиять можно индексами, статистикой и random_page_cost, но «приказать» — нельзя.
