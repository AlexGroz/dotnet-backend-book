Глава 23. Подключение к БД из .NET: ADO.NET и пул соединений

Соединение как ресурс: пул соединений и его связь с нагрузкой

подводящая глава

Кто и как ходит в базу

Снизу вверх: ADO.NET — базовый слой .NET для работы с БД (в PostgreSQL это драйвер Npgsql): соединение, команда, чтение результата. Поверх него работают Dapper (микро-ORM) и EF Core (полноценный ORM, глава 24). Внизу всегда одно и то же — сокет, протокол и соединение.

// «Сырой» ADO.NET: минимум слоёв, полный контроль
await using var conn = new NpgsqlConnection(connectionString);
await conn.OpenAsync(ct);

await using var cmd = new NpgsqlCommand(
    "SELECT id, total FROM orders WHERE user_id = $1 ORDER BY created_at DESC LIMIT 20", conn);
cmd.Parameters.Add(new NpgsqlParameter { Value = userId, NpgsqlDbType = NpgsqlDbType.Uuid });

await using var reader = await cmd.ExecuteReaderAsync(ct);
while (await reader.ReadAsync(ct))
{
    var id = reader.GetInt64(0);
    var total = reader.GetDecimal(1);
}

Обратите внимание на NpgsqlDbType.Uuid: тип параметра задан явно. Это не педантизм — несовпадение типа параметра с типом колонки мешает базе использовать индекс (глава 22 и SQL-раздел про планы).

Соединение — дорогой ресурс, поэтому пул

Установить соединение с БД — это сетевой обмен, аутентификация и создание серверного процесса. Делать это на каждый запрос невозможно, поэтому в .NET соединения переиспользуются через пул.

  • Пул привязан к строке подключения (её тексту): разные строки — разные пулы.
  • OpenAsync() не создаёт соединение, а берёт свободное из пула (или ждёт, если свободных нет).
  • Dispose/Close не закрывают физическое соединение, а возвращают его в пул.
  • Если соединение не возвращать (не вызвать Dispose), пул исчерпается — и сервис встанет.
Главное правило

Соединение нужно возвращать как можно быстрее. Держать его открытым, пока идут расчёты, HTTP-вызовы или ожидание в очереди, — значит вычитать этот ресурс у всех остальных запросов.

Настройки пула в строке подключения

Host=db;Database=app;Username=app;Password=***
Maximum Pool Size=100      -- сколько соединений этот процесс держит одновременно
Minimum Pool Size=5        -- сколько держать «тёплыми»
Timeout=15                 -- сколько ждать свободное соединение (секунд)
Command Timeout=30         -- предел выполнения одной команды
Multiplexing=true          -- (Npgsql) несколько команд через одно физическое соединение

Бюджет соединений: сколько их вообще нужно

У сервера PostgreSQL есть свой предел — max_connections. И соединения нужны не только вашему сервису: администрирование, миграции, репликация, другие приложения. Отсюда простое бюджетное правило:

Maximum Pool Size × число инстансов сервиса  ≤  max_connections − запас
                                                 (админ, миграции, другие сервисы)

Пример: при max_connections = 200 и трёх инстансах, каждый с пулом в 100 соединений, мы гарантированно упрёмся в лимит сервера — причём ошибки прилетят не из нашего кода, а от БД.

Что здесь что — и где смотреть
  • Инстанс — одна запущенная копия сервиса: процесс, контейнер, pod, «реплика». Считать по факту: число реплик в деплойменте (kubectl get pods), число серверов за балансировщиком, число экземпляров приложения.
  • Max Pool Size — сколько соединений держит один инстанс. Смотреть: в строке подключения (Maximum Pool Size=100), в коде (new NpgsqlConnectionStringBuilder(cs).MaxPoolSize) или в конфиге приложения.
  • max_connections — лимит сервера: SHOW max_connections; или SELECT setting FROM pg_settings WHERE name = 'max_connections';
  • Запас — соединения, нужные не вашему сервису: админ (psql), миграции, мониторинг, репликация, другие сервисы. Без запаса вы «съедите» весь лимит и не сможете даже подключиться, чтобы починить.
max_connections = 200
запас (админ + миграции + мониторинг) = 20
3 инстанса сервиса → 200 − 20 = 180 на всех → 180 / 3 = 60 соединений на инстанс
Большой пул — не всегда хорошо

Каждое соединение занимает память сервера и требует переключения контекста. Часто лучше меньший пул (например, 20–50): он естественным образом ограничивает параллелизм, запросы встают в очередь, и БД не захлёбывается. Небольшой пул работает как backpressure — защита от перегрузки «изнутри».

Транзакции: сколько держать соединение

Открытая транзакция удерживает соединение до коммита (или отката). Отсюда правило: транзакция — только вокруг работы с БД, а подготовка и внешние вызовы — вне её.

// ✘ ПЛОХО: транзакция открыта, пока идут сетевые вызовы
await using var tx = await db.Database.BeginTransactionAsync(ct);  // 1) взяли соединение из пула
db.Orders.Add(order);                                              // 2) заказ в память (в БД ещё ничего)
await db.SaveChangesAsync(ct);                                     // 3) INSERT, транзакция ОТКРЫТА
await _payment.ChargeAsync(order.Id, ct);                          // 4) HTTP 300 мс…3 с, соединение занято
await tx.CommitAsync(ct);                                          // 5) только теперь освободили

// ✔ ХОРОШО: в транзакции — только работа с БД
var total = await _pricing.CalculateAsync(order, ct);              // 1) расчёт — вне транзакции
order.Total = total;

await using var tx2 = await db.Database.BeginTransactionAsync(ct); // 2) открыли транзакцию
db.Orders.Add(order);                                              // 3) заказ
db.Outbox.Add(OutboxMessage.For(order));                           // 4) событие — в ТОЙ ЖЕ транзакции
await db.SaveChangesAsync(ct);                                     // 5) один пакет INSERT
await tx2.CommitAsync(ct);                                         // 6) сразу закрыли — миллисекунды

// 7) событие отправит воркер из outbox (глава 31), уже без транзакции

Главная мысль: в транзакции держим только работу с БД. Всё, что требует сети (платёж, уведомление, брокер), — до или после; а событие для соседей надёжно сохраняется в outbox внутри той же транзакции.

Подготовленные запросы и типы параметров

  • Prepared statements: сервер разбирает и планирует запрос один раз, затем выполняет по параметрам. В Npgsql это включается автоматически при частом повторе (auto prepare), а сами запросы видны в pg_stat_statements (глава 21).
  • Типы параметров задавайте явно (NpgsqlDbType) — это и защита от инъекций, и отсутствие неявных приведений, которые мешают использовать индексы.
  • Не собирайте SQL строками из значений: страдает и план, и безопасность.
  • Не забывайте про CancellationToken во всех вызовах: если клиент отключился, работа должна прекратиться, а соединение — вернуться в пул (глава 12).

Dapper: между ADO.NET и EF Core

Dapper — «микро-ORM»: набор extension-методов над ADO.NET. Он не пишет SQL за вас — вы даёте готовый запрос, а Dapper выполняет его и раскладывает строки в объекты.

await using var conn = new NpgsqlConnection(cs);

// SQL пишем сами; @userId — параметр (Dapper подставит безопасно)
var rows = await conn.QueryAsync<OrderRow>(
    """
    SELECT id, total, created_at
    FROM orders
    WHERE user_id = @userId
    ORDER BY created_at DESC
    LIMIT 20
    """,
    new { userId });

// один объект
var one = await conn.QuerySingleOrDefaultAsync<OrderRow>(
    "SELECT id, total FROM orders WHERE id = @id", new { id });

// команда без результата
await conn.ExecuteAsync("UPDATE orders SET status = @status WHERE id = @id",
    new { status = "paid", id });

Две вещи, которые надо помнить
  • Параметры обязательны. Склейка значений в строку SQL — это и инъекция, и поломанный план (глава 22).
  • Схему Dapper не знает. Опечатка в имени колонки всплывёт только в рантайме — в отличие от EF Core, где модель проверяется при старте.
★ Что запомнить из главы
  • Под всеми ORM лежит ADO.NET и соединение из пула.
  • Соединение берут и быстро возвращают; долгое удержание останавливает сервис под нагрузкой.
  • Бюджет: Max Pool Size × инстансы ≤ max_connections − запас. Небольшой пул = backpressure.
  • Транзакция держит соединение до коммита, поэтому внешние вызовы — вне неё.
  • Явные типы параметров — и безопасность, и работающие индексы.
