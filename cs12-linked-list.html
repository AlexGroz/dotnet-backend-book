Глава 12. LinkedList: связный список

Коллекция, которую почти не берут в руки, но почти всегда спрашивают: как устроен связный список, что даёт LinkedListNode<T>, почему O(1) на вставке так редко помогает, где LinkedList действительно незаменим (LRU-кэш) и чем он отличается от List, Queue и Stack.

основная глава

До этого вся часть II работала с одной идеей: элементы лежат в массиве подряд. Так устроены List<T>, Queue<T>, Stack<T>, Dictionary (массив корзин) и даже куча внутри PriorityQueue. LinkedList<T> — исключение: элементов в массиве нет вообще. Есть отдельные объекты-узлы, связанные ссылками, и это меняет всё: доступ, вставку, память, скорость перебора.

List — это полка с пронумерованными ячейками: чтобы поставить предмет в середину, надо сдвинуть всё, что правее, зато «дай мне пятый» — мгновенно. LinkedList — это цепочка вагонов: чтобы попасть в середину, надо пройти от головы, зато прицепить новый вагон между двумя уже найденными — две операции, без сдвигов.

Узлы: LinkedListNode<T>

Главное отличие от всех остальных коллекций части II: узел — это объект, который можно держать в руках. Методы возвращают не «позицию» или «индекс», а сам узел, и пока вы держите узел, вы можете вставлять и удалять рядом с ним за O(1), не ища ничего заново.

var list = new LinkedList<string>();
list.AddLast("b");
list.AddFirst("a");
list.AddLast("c");

var nodeB = list.Find("b");        // O(n): проходит по списку и возвращает узел
list.AddAfter(nodeB!, "b2");       // O(1): узел уже известен

Console.WriteLine(string.Join(",", list));
Console.WriteLine("Count=" + list.Count);
Console.WriteLine("First=" + list.First!.Value + " Last=" + list.Last!.Value);
Console.WriteLine("nodeB.Value=" + nodeB!.Value
    + " Next=" + nodeB.Next!.Value + " Prev=" + nodeB.Previous!.Value);

Вывод

a,b,b2,c
Count=4
First=a Last=c
nodeB.Value=b Next=b2 Prev=a

У узла четыре члена: Value (данные), Next и Previous (соседи или null на концах) и List (какому списку принадлежит, или null, если узел удалён). Ссылки Next/Previous — это и есть весь список: пройти от list.First по Next до null — значит перебрать всё.

Отдельно стоит запомнить: ICollection<T>.Add у LinkedList — это AddLast (проверено: asCollection.Add("c") в {"a","b"} даёт a,b,c), поэтому он спокойно работает в коде, написанном под интерфейс.

O(1) — только когда узел уже в руках

Это главное недопонимание про LinkedList. «Вставка O(1)» относится к операции по узлу: список не ищет ничего, он просто переставляет две ссылки. Вопрос всегда в одном — откуда берётся узел. Если его надо найти по значению, к O(1) добавляется O(n) на поиск, и вся выгода исчезает:

var list = new LinkedList<string>(new[] { "a", "b", "c" });

// «удалить значение b» — это ДВА шага: найти (O(n)) и удалить (O(1))
Console.WriteLine(list.Remove("b"));      // True
Console.WriteLine(list.Remove("нет"));    // False — и это не ошибка

// а вот если узел сохранён заранее, повторные операции бесплатны
var node = list.Find("c");
Console.WriteLine(node!.List is not null ? "узел в списке" : "узел свободен");

Отсюда практическое правило: LinkedList имеет смысл, когда узлы хранятся отдельно — в словаре, в поле класса, в другом списке, и вы возвращаетесь к ним снова и снова. Ровно так устроен LRU-кэш ниже.

Узел из прошлого: что будет после удаления

Удалённый узел не «умирает» — объект жив, если вы держите на него ссылку, но из списка он выпадает: List становится null, а попытка использовать его в операциях списка даёт исключение (проверено на .NET 8):

var list = new LinkedList<string>(new[] { "a", "b", "c" });
var nodeB = list.Find("b")!;
list.Remove(nodeB);

Console.WriteLine("nodeB.List is null: " + (nodeB.List is null));

try { list.AddBefore(nodeB, "x"); }
catch (Exception e) { Console.WriteLine(e.GetType().Name + ": " + e.Message); }

try { new LinkedList<string>().RemoveFirst(); }
catch (Exception e) { Console.WriteLine(e.GetType().Name + ": " + e.Message); }

Вывод

nodeB.List is null: True
InvalidOperationException: The LinkedList node does not belong to current LinkedList.
InvalidOperationException: The LinkedList is empty.

То же исключение — если попытаться подставить узел из другого списка. Проверка дешёвая: node.List == list, и её полезно делать в коде, который держит узлы «между вызовами».

Чего у него нет

  • Индексатора. list[0] не компилируется: error CS0021: Cannot apply indexing with [] to an expression of type 'LinkedList<string>'.
  • Быстрого «дай i-й элемент». list.ElementAt(2) — это LINQ, и он идёт от головы: O(n). Цикл вида for (int i = 0; i < list.Count; i++) list.ElementAt(i) — O(n²).
  • Обратного перебора через foreach. Есть только вперёд; назад — вручную: от list.Last по Previous.
  • Изменений во время foreach. Даже AddLast в теле цикла рвёт перебор: InvalidOperationException: Collection was modified after the enumerator was instantiated. Нужно добавлять — собирайте узлы и меняйте список после цикла.
  • Потокобезопасности. Как и List, LinkedList не защищён: одновременное добавление из двух потоков может порвать ссылки и «потерять» часть элементов без единого исключения.

Сколько это стоит: замер

Цифры важнее слов, поэтому — один и тот же миллион int в двух коллекциях:

const int N = 1_000_000;

// память считаем вместе с созданием самой коллекции — иначе сравнение нечестное
long before = GC.GetAllocatedBytesForCurrentThread();
var list = new List<int>(N);
for (int i = 0; i < N; i++) list.Add(i);
long listBytes = GC.GetAllocatedBytesForCurrentThread() - before;

before = GC.GetAllocatedBytesForCurrentThread();
var linked = new LinkedList<int>();
for (int i = 0; i < N; i++) linked.AddLast(i);
long linkedBytes = GC.GetAllocatedBytesForCurrentThread() - before;

static long SumList(List<int> xs) { long s = 0; foreach (var x in xs) s += x; return s; }
static long SumLinked(LinkedList<int> xs) { long s = 0; foreach (var x in xs) s += x; return s; }

SumList(list); SumLinked(linked);              // прогрев: JIT и кэши

var sw = Stopwatch.StartNew();
SumList(list);
sw.Stop();
var listMs = sw.Elapsed.TotalMilliseconds;

sw.Restart();
SumLinked(linked);
sw.Stop();

Console.WriteLine($"перебор: List {listMs:F2} ms, LinkedList {sw.Elapsed.TotalMilliseconds:F2} ms");
Console.WriteLine($"память:  List {listBytes / 1024 / 1024.0:F1} МБ, LinkedList {linkedBytes / 1024 / 1024.0:F1} МБ");

Вывод (net8.0, Release)

перебор: List 0.85 ms, LinkedList 4.19 ms
память:  List 3.8 МБ, LinkedList 45.8 МБ

Почему перебор медленнее, хотя «просто идём по ссылкам»: элементы List лежат подряд, и процессор читает их пачками из кэша; каждый узел LinkedList — отдельный объект в куче, и переход по Next часто означает промах кэша (глава 1). Почему память в 12 раз больше: на каждый int приходится объект-узел (заголовок + значение + две ссылки) плюс работа для GC.

И честная обратная сторона — 20 000 вставок в середину, когда узел уже найден: List ≈ 0,7 с (каждый раз сдвиг половины массива), LinkedList ≈ 1 мс. То есть в «своём» сценарии LinkedList быстрее на три порядка.

Где он действительно нужен: LRU-кэш

Классическая задача: кэш фиксированной ёмкости, из которого вылетает то, что дольше всего не использовали (least recently used). Нужны три операции: найти по ключу за ~O(1), сделать запись «самой свежей» и выбросить самую старую — всё без сдвигов. Словарь даёт первую, связный список — две другие, если хранить в словаре не значения, а узлы:

public sealed class LruCache<TKey, TValue> where TKey : notnull
{
    private readonly int _capacity;
    private readonly Dictionary<TKey, LinkedListNode<(TKey Key, TValue Value)>> _map = new();
    private readonly LinkedList<(TKey Key, TValue Value)> _order = new();   // голова — самый свежий

    public LruCache(int capacity) => _capacity = capacity;

    public IEnumerable<TKey> Keys => _order.Select(e => e.Key);

    public TValue Get(TKey key)
    {
        if (!_map.TryGetValue(key, out var node))
            throw new KeyNotFoundException($"нет ключа {key}");

        _order.Remove(node);        // O(1): узел уже известен, искать не надо
        _order.AddFirst(node);      // теперь он самый свежий
        return node.Value.Value;
    }

    public void Set(TKey key, TValue value)
    {
        if (_map.TryGetValue(key, out var node))
        {
            _order.Remove(node);
            _map.Remove(key);
        }
        else if (_map.Count == _capacity)
        {
            var oldest = _order.Last!;              // хвост — то, что дольше всего не трогали
            _map.Remove(oldest.Value.Key);
            _order.RemoveLast();
        }

        var fresh = new LinkedListNode<(TKey, TValue)>((key, value));
        _order.AddFirst(fresh);
        _map[key] = fresh;
    }
}

Проверка: ёмкость 2, «a» и «b», затем читаем «a», затем добавляем «c»

ключи: b,a
ключи: c,a
b в кэше: False, a в кэше: True

Разбор: после Set("a") и Set("b") свежий — «b», он в голове. Get("a") переставил «a» в голову, поэтому при добавлении «c» места не хватило именно «b» — он оказался в хвосте. Все операции — O(1), и всё это держится на одном свойстве: словарь хранит узлы, а не значения. Если хранить значения и искать «а который из них самый старый», каждый Get станет O(n) и смысл пропадёт.

Две задачи, которые любят давать на собеседовании

1. Найти середину за один проход. Соблазн — узнать Count и пройти Count / 2 шагов, но это два прохода. Классика — «медленный и быстрый» указатели:

var nums = new LinkedList<int>(new[] { 1, 2, 3, 4, 5, 6 });
Console.WriteLine("середина: " + Middle(nums));

static int Middle(LinkedList<int> list)
{
    var slow = list.First!;
    var fast = list.First!;

    while (fast.Next is not null && fast.Next.Next is not null)
    {
        slow = slow.Next!;          // шаг 1
        fast = fast.Next.Next!;     // шаг 2
    }

    return slow.Value;
}

Вывод (у чётного списка берётся левая середина)

середина: 3

2. Развернуть список. Здесь видно главное преимущество: узлы можно переставлять, не создавая новых объектов — ни одной аллокации на весь разворот:

var list = new LinkedList<int>(new[] { 1, 2, 3, 4 });
Reverse(list);
Console.WriteLine(string.Join(",", list));

static void Reverse(LinkedList<int> list)
{
    var node = list.First;
    while (node is not null)
    {
        var next = node.Next;   // запомнили, иначе потеряем хвост
        list.Remove(node);      // O(1): узел уже в руках
        list.AddFirst(node);    // тот же самый узел, без new
        node = next;
    }
}

Вывод

4,3,2,1

Что спрашивают на собеседовании

ВопросКороткий ответ
Чем отличается от List<T>?Устройством: массив против узлов со ссылками. У List доступ по индексу O(1) и быстрый перебор; у LinkedList — O(1) на вставку/удаление по узлу, но поиск O(n), индекса нет, память и перебор хуже.
Когда выберете LinkedList?Когда узлы хранятся отдельно (в словаре, в поле) и операции идут по ним: LRU-кэш, очередь с удалением из середины, подписки с отпиской по узлу.
Почему его почти не используют?В обычных задачах нужен поиск или индекс — а это O(n). Плюс в 12 раз больше памяти и в 5 раз медленнее перебор из-за локальности кэша.
Сложность операций?AddFirst/AddLast/Remove(node) — O(1); Find/Contains/Remove(value)/ElementAt — O(n).
Как найти середину за один проход?Два указателя: один идёт на шаг, второй на два; когда быстрый упрётся в конец, медленный — в середине.
Чем отличается от Queue/Stack?Те внутри — массив, работать умеют только с краями (зато O(1) и без объектов-узлов). LinkedList даёт доступ к любому узлу, если вы его сохранили.
Можно ли сделать из него очередь?Да: AddLast + RemoveFirst. Но Queue<T> проще, экономнее и быстрее (глава 11).
Потокобезопасен?Нет. Как и List: нужен lock или другая коллекция.
Зачем в словаре хранят LinkedListNode?Чтобы получать узел за ~O(1) и дальше работать с ним за O(1) — на этом стоит LRU-кэш.

Ловушки

  • Ждать от него скорости на поиске. Find, Contains, Remove(value) — O(n), как у List, только с большей константой.
  • Пытаться индексировать. list[i] не компилируется (CS0021), а ElementAt(i) в цикле превращает обход в O(n²).
  • Держать узел после удаления. node.List станет null, а операции с этим узлом бросят InvalidOperationException: The LinkedList node does not belong to current LinkedList. Проверяйте node.List == list.
  • Менять список внутри foreach — InvalidOperationException: Collection was modified after the enumerator was instantiated.
  • RemoveFirst/RemoveLast на пустом списке — InvalidOperationException: The LinkedList is empty. В цикле сначала проверяйте list.First is not null.
  • Забыть про память. Каждый элемент — объект: миллион int даёт ~46 МБ вместо 3,8 МБ и лишнюю работу сборщику мусора.
  • Использовать его «по умолчанию». Нужен список — нужен List<T>; LinkedList — инструмент под конкретную задачу, а не «более умный список».
★ Что запомнить из главы
  • Связный список: элементов в массиве нет, каждый элемент — объект-узел со ссылками Next/Previous. Индекса нет вообще.
  • O(1) — только по узлу: AddFirst/AddLast/ AddBefore/AddAfter/Remove(node). Поиск и Remove(value) — O(n).
  • Узел — это LinkedListNode<T>: Value, Next, Previous, List. Удалённый узел выпадает из списка (List == null), и операции с ним бросают исключение.
  • Цена: перебор ~в 5 раз медленнее List (локальность кэша), память ~в 12 раз больше (по объекту на элемент).
  • Его сценарий — LRU-кэш: Dictionary<TKey, LinkedListNode<TValue>> + LinkedList, где голова — самый свежий элемент, хвост — кандидат на вылет.
  • Сравнение: List — по умолчанию; Queue/Stack — только края на массиве (глава 11); LinkedList — вставки и удаления по уже известному узлу.
