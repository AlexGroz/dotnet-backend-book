Переписывание запроса — частые приёмы

  • Убрать вычисления над колонкой в условии: WHERE to_char(dt,'YYYY')='2026' мешает индексу — лучше диапазон dt >= ... AND dt < ....
  • OR → UNION ALL, если ветки используют разные индексы.
  • IN → EXISTS для больших подзапросов.
  • Убрать лишние JOIN, если таблицу не используем в результате.
  • Ограничить выборку (LIMIT) и не тянуть лишние колонки.
  • CTE (WITH …): в PostgreSQL 12+ обычный CTE «инлайнится» — его текст как бы подставляется в основной запрос, как обычный подзапрос. Планировщик видит всю картину целиком: может применить индекс и «протолкнуть» условие внутрь CTE. WITH … AS MATERIALIZED инлайн запрещает: CTE вычисляется один раз и сохраняется во временном наборе. Это полезно, если он тяжёлый и используется несколько раз, и вредно, если после инлайна план был лучше. Проверять — планом, а не догадками.

Пагинация: почему OFFSET дорогой и что такое keyset

Сначала — что означает OFFSET: это «пропусти первые N строк». Классическая пагинация «по номеру страницы» выглядит так:

-- страница 1
SELECT id, created_at, total FROM orders ORDER BY created_at DESC LIMIT 20 OFFSET 0;
-- страница 1000
SELECT id, created_at, total FROM orders ORDER BY created_at DESC LIMIT 20 OFFSET 19980;

Проблема: OFFSET 19980 никуда не «прыгает». База честно читает и сортирует первые 20000 строк, 19980 выбрасывает и отдаёт 20. Чем глубже страница, тем дороже запрос — время растёт линейно. Индекс здесь не спасает: он помогает найти начало диапазона, а не «двадцатитысячную» строку.

Keyset-пагинация («пагинация по ключу», seek method) — вместо номера страницы клиент присылает значения последней увиденной строки, и запрос продолжает с этого места. Разберём это на маленькой таблице, потому что именно здесь обычно возникает вопрос «а откуда я знаю этот id?».

Пусть в orders шесть строк, и у трёх из них одинаковое created_at — так почти всегда и бывает в реальности:

idcreated_at
1022026-01-05 10:00
1012026-01-05 10:00
1002026-01-05 10:00
992026-01-05 09:00
982026-01-05 09:00
972026-01-05 08:00

Шаг 1. Первая страница. Курсора ещё нет, поэтому запрос обычный:

SELECT id, created_at, total
FROM   orders
ORDER  BY created_at DESC, id DESC
LIMIT  2;

-- результат (страница 1):
--   id  |      created_at
--  -----+---------------------
--   102 | 2026-01-05 10:00:00
--   101 | 2026-01-05 10:00:00     ← последняя строка страницы

Шаг 2. Сервер запоминает последнюю строку. «Курсор» — это просто два значения из последней отданной строки: created_at = '2026-01-05 10:00:00' и id = 101. Приложение возвращает их клиенту, обычно одной непрозрачной строкой:

{
  "items": [ { "id": 102, ... }, { "id": 101, ... } ],
  "nextCursor": "MjAyNi0wMS0wNVQxMDowMDowMHwxMDE="   // base64 от "2026-01-05T10:00:00|101"
}

Клиент не придумывает эти значения и не собирает их из даты — он просто возвращает то, что получил. Поэтому «откуда я знаю, какой id» — вопрос снимается: это id той строки, которую клиент уже показал пользователю.

Шаг 3. Вторая страница. Запрос продолжает с курсора:

SELECT id, created_at, total
FROM   orders
WHERE  (created_at, id) < (:'last_created_at', :'last_id')    -- ('2026-01-05 10:00:00', 101)
ORDER  BY created_at DESC, id DESC
LIMIT  2;

-- результат (страница 2): ровно то, что идёт ПОСЛЕ строки (10:00, 101)
--   id  |      created_at
--  -----+---------------------
--   100 | 2026-01-05 10:00:00     ← та же дата, но id меньше
--    99 | 2026-01-05 09:00:00

Как читается (created_at, id) < (…, …). Это сравнение кортежей: оно идёт по порядку — сначала сравнивается дата, и только если даты равны, сравнивается id. Поэтому «id сам по себе» здесь не участвует в решении: строка с датой 09:00 проходит по первому признаку, независимо от её id. Для наглядности тот же смысл можно записать через OR:

WHERE created_at < :'last_created_at'                       -- дата раньше — точно «после неё»
   OR (created_at = :'last_created_at' AND id < :'last_id')  -- дата та же → решает id
Что будет, если взять только дату

Кажется, что id не нужен: «фильтра по created_at < :last достаточно». Но граница страницы почти никогда не совпадает с границей одинаковых дат:

-- ✘ только дата: строка с id=100 (10:00) ПОТЕРЯНА — она не попала ни на первую, ни на вторую страницу
WHERE created_at < '2026-01-05 10:00:00'
-- → 99, 98   (а 100 пропала)

-- ✘ нестрогое сравнение: строки 102 и 101 придут ВТОРОЙ раз
WHERE created_at <= '2026-01-05 10:00:00'
-- → 102, 101, 100 …

-- ✔ кортеж: и без потерь, и без дублей
WHERE (created_at, id) < ('2026-01-05 10:00:00', 101)
-- → 100, 99

Именно поэтому id называется tie-breaker («разруливающий ничьи»): он делает порядок строк однозначным, а значит «следующая страница» определена без вариантов.

Что нужно на стороне базы. Индекс в точности по тому же порядку, что и ORDER BY:

CREATE INDEX ON orders (created_at DESC, id DESC);

EXPLAIN (ANALYZE, BUFFERS)
SELECT id, created_at FROM orders
WHERE  (created_at, id) < ('2026-01-05 10:00:00', 101)
ORDER  BY created_at DESC, id DESC
LIMIT  2;

Limit  (actual time=0.021..0.028 rows=2 loops=1)
  ->  Index Only Scan using orders_created_at_id_idx on orders
        Index Cond: (ROW(created_at, id) < ROW('2026-01-05 10:00:00+00'::timestamptz, 101))
        Heap Fetches: 0

-- ВЫВОД: база «прыгает» по индексу сразу в нужное место (Index Cond) и читает ровно 2 записи.
-- Глубина страницы на стоимость не влияет: страница №1 и страница №5000 стоят одинаково.

Почему в этом EXPLAIN в SELECT только id и created_at: это ровно колонки индекса, поэтому база обошлась индексом (Index Only Scan, Heap Fetches: 0). Если добавить total (его в индексе нет), появится чтение самой таблицы, но Index Cond и число прочитанных строк (rows=2) останутся теми же — это видно в замерах ниже.

Стоимость страницы не зависит от её номера — в этом и выигрыш. Пара (created_at, id) сравнивается целиком, и ORDER BY должен идти по тем же колонкам: иначе порядок неоднозначен (у двух заказов может совпасть created_at).

Одна и та же задача, два способа

Чтобы сравнение было честным, возьмём один и тот же вопрос — «двадцатка строк №19981–20000 в порядке created_at DESC, id DESC» — и решим его обоими способами на одной таблице из 1 млн заказов, с одинаковыми колонками и одинаковым LIMIT:

-- способ 1: «страница №1000» через OFFSET — пропустить 19980 строк
SELECT id, created_at, total FROM orders
ORDER BY created_at DESC, id DESC
LIMIT 20 OFFSET 19980;

-- способ 2: keyset — продолжить от последней строки предыдущей страницы
SELECT id, created_at, total FROM orders
WHERE  (created_at, id) < ('2026-12-16 14:22:03+00', 980021)   -- строка №19 980
ORDER  BY created_at DESC, id DESC
LIMIT  20;

Оба вернули одни и те же 20 строк (сверил списки id — совпали). Разница только в том, как база добирается до начала страницы:

СпособЧто делает базаБуферовВремя
LIMIT 20 OFFSET 19980 Index Scan, прочитано rows=20000, из них 19 980 выброшено 2273,05 мс
keyset с курсором Index Scan + Index Cond, прочитано rows=20 50,14 мс

И как это меняется с глубиной (та же таблица, тот же LIMIT 20, те же колонки):

Начало страницыOFFSET: время / буферов keyset: время / буферов

Отсюда видно, откуда «время растёт линейно»: OFFSET каждый раз честно проходит все предыдущие строки — растут и время, и число прочитанных буферов. Keyset читает ровно 20 записей индекса, поэтому его столбец практически не меняется (разброс вправо-влево на десятые доли миллисекунды — шум замера). Огромная таблица: партиционирование и материализованные представления

Дальше — два ответа на строку «Очень большая таблица» из вводной таблицы главы. Задачи у них разные: партиционирование уменьшает объём читаемых данных, материализованное представление избавляет от повторного вычисления.

Партиционирование

Это разбиение одной логической таблицы на физические куски (секции) по правилу — чаще всего по дате. Приложение по-прежнему пишет INSERT INTO orders … и читает FROM orders: PostgreSQL сам выбирает нужную секцию.

  • Зачем: запрос с условием по дате читает только подходящие секции (pruning) — меньше страниц; VACUUM и удаление старых данных идут по секции целиком (DROP TABLE orders_2025_01 вместо DELETE миллионов строк).
  • Когда: таблица в сотни миллионов строк, данные «по времени», старые периоды можно выбрасывать.
  • Подробно: глава 26 — PARTITION BY RANGE, границы секций, pruning в плане.

Материализованные представления под агрегаты

Агрегат — свёртка многих строк в несколько значений: SUM(total), COUNT(*), GROUP BY день. Считать их на каждый запрос по большой таблице дорого. Материализованное представление (materialized view) — это сохранённый на диске результат запроса: читается как обычная таблица, без пересчёта.

CREATE MATERIALIZED VIEW orders_daily AS
SELECT date_trunc('day', created_at) AS day,
       status,
       count(*)   AS orders,
       sum(total) AS revenue
FROM   orders
GROUP  BY 1, 2;

-- данные устарели → пересчитать (для CONCURRENTLY нужен UNIQUE-индекс)
REFRESH MATERIALIZED VIEW CONCURRENTLY orders_daily;

Что такое GROUP BY 1, 2. Это номера столбцов в списке SELECT, а не значения и не колонки таблицы: 1 — первый столбец результата (date_trunc('day', created_at) AS day), 2 — второй (status). База подставляет на эти места сами выражения, поэтому запись равносильна любой из двух:

GROUP BY date_trunc('day', created_at), status   -- те же выражения «словами»
GROUP BY day, status                             -- или по имени выходного столбца

Проверил, что множества строк у всех трёх вариантов совпадают (EXCEPT даёт 0 строк), а что номера считаются именно по списку SELECT — видно по ошибке: если вторым столбцом стоит агрегат, база отказывается по нему группировать.

-- ✘ второй столбец SELECT — агрегат, группировать по нему нельзя
SELECT status, count(*) FROM orders GROUP BY 2;
-- ERROR:  aggregate functions are not allowed in GROUP BY

Цена краткости: поменяли порядок столбцов в SELECT — и 1, 2 стали означать другие столбцы, а на глаз это не видно (проверил: при SELECT status, date_trunc(…) то же GROUP BY 1, 2 группирует сначала по status). Поэтому в длинных запросах надёжнее писать выражения или имена (GROUP BY day, status), а GROUP BY 1, 2 держать для коротких запросов, где список SELECT рядом и его видно.

  • Выигрыш: отчёт читает готовые строки вместо сканирования миллионов. Замер на 1 млн заказов, вопрос «выручка по дням за 2026 год»: GROUP BY по таблице — 297 мс и 7 353 буфера (сортировка ещё и ушла в temp), чтение из представления — 0,75 мс и 18 буферов.
  • Цена: данные несвежие — между REFRESH есть отставание; само обновление дорогое. Политике обновления посвящён раздел ниже.
  • Альтернативы: таблица-кэш, заполняемая заданием; или обычный индекс под конкретный запрос, если агрегат простой.

Когда обновлять: раз в минуту, раз в час или по событию

Политика обновления — это три числа: допустимое отставание (насколько устаревшие данные терпит бизнес), стоимость одного пересчёта и как часто результат читают. Расписание оправдано, когда пересчёт заметно дешевле интервала и когда результат кто-то читает.

Сначала важная деталь: REFRESH в PostgreSQL — всегда полный пересчёт запроса представления, сколько бы строк ни изменилось. Замер: на 1 млн заказов пересчёт занял 343 мс; изменил одну строку из миллиона и пересчитал снова — 344 мс. На 10 млн строк (таблица 1,3 ГБ) — 3,4 с и 3,0 с. Значит «обновлять почаще» не дешевеет от того, что данные меняются мало: каждый раз читается вся таблица.

ПолитикаОправдана, когдаПримерЧем платим
Раз в минуту данные меняются постоянно, читают постоянно и многие, отставание до минуты приемлемо, а пересчёт — доли секунды дашборд склада «заказы за сегодня»: 20 операторов, виджеты обновляются каждые 10 с, само представление маленькое (2 190 строк из 1 млн заказов) 1 440 пересчётов в сутки × 343 мс ≈ 8 минут CPU в сутки (≈0,6 % времени). На 10 млн строк те же 1 440 пересчётов — уже ≈ 81 минута в сутки
Раз в час отставание в час приемлемо, читают несколько раз в час, пересчёт дорогой относительно минуты отчёт «выручка по дням за месяц» для менеджеров: по прошедшим дням данные не меняются, свежим должен быть только сегодняшний день прошедшие дни пересчитываются впустую, но 24 пересчёта в сутки этого не заметят (на 10 млн строк это ≈ 1,4 минуты в сутки)
По событию данные меняются пачками, и момент, когда агрегат должен быть свежим, известен ночная загрузка заказов из маркетплейсов: последняя строка задания загрузки — REFRESH MATERIALIZED VIEW CONCURRENTLY orders_daily; ни одного холостого пересчёта. Риск — забыть вызвать, и данные «застынут»; поэтому событие часто подстраховывают редким контрольным пересчётом раз в сутки
По требованию (без расписания) читают редко, а пересчёт дорогой — ровно случай «данных много, обращаются редко» годовой отчёт, который открывают раз в неделю свежесть проверяет приложение: хранит признак «когда обновляли» и, если прошло больше N минут, вызывает REFRESH перед чтением. Нужна защита от одновременных пересчётов — второй REFRESH того же представления ждёт первого

Если читают редко, расписание — худший вариант: платим за пересчёт, а выигрыш не используем. 1 440 пересчётов в сутки по 343 мс — это ≈ 8 минут работы CPU в сутки на отчёт, который открывают раз в неделю (на 10 млн строк — уже ≈ 81 минута). В такой ситуации либо не материализуем вовсе (агрегат простой, и его закрывает индекс), либо обновляем по требованию, либо заполняем таблицу-кэш заданием — но у задания снова будет расписание.

А читателей блокировать можно? REFRESH без CONCURRENTLY берёт ACCESS EXCLUSIVE и на время пересчёта не пускает SELECT к представлению (глава 24): на 10 млн строк это 3,4 с «тишины» для дашборда. CONCURRENTLY читателей не блокирует (EXCLUSIVE), но требует UNIQUE-индекса по всем строкам и допускает только один пересчёт представления в момент времени. По стоимости на наших данных разницы почти нет (358 мс против 343 мс на 1 млн, 3,2 с против 3,4 с на 10 млн) — потому что изменилась всего одна строка; чем больше строк меняется, тем дороже CONCURRENTLY относительно обычного пересчёта (так это и описано в документации).

Настройки, которые реально влияют

  • work_mem — память на сортировки и хеши (умножается на число операций, осторожно).
  • random_page_cost — для SSD ниже (≈1.1), иначе планировщик недооценивает индексы.
  • effective_cache_size — сколько данных «примерно в кэше»; влияет на выбор индекса.
  • enable_seqscan / enable_hashjoin и т. п. — только для диагностики, не как постоянное решение.
Чего в PostgreSQL нет

Подсказок планировщику (как /*+ INDEX(...) */ в Oracle). Есть расширение pg_hint_plan, но правильнее починить статистику и индексы, а не «заставлять» план.

★ Правило оптимизации

Меняем одно и заново снимаем план. Иначе невозможно понять, что помогло. И обязательно измеряем на реальной нагрузке (глава 33), а не только «в консоли».
