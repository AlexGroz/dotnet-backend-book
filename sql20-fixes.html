Переписывание запроса — частые приёмы

  • Убрать вычисления над колонкой в условии: WHERE to_char(dt,'YYYY')='2026' мешает индексу — лучше диапазон dt >= ... AND dt < ....
  • OR → UNION ALL, если ветки используют разные индексы.
  • IN → EXISTS для больших подзапросов.
  • Убрать лишние JOIN, если таблицу не используем в результате.
  • Ограничить выборку (LIMIT) и не тянуть лишние колонки.
  • CTE (WITH …): в PostgreSQL 12+ обычный CTE «инлайнится» — его текст как бы подставляется в основной запрос, как обычный подзапрос. Планировщик видит всю картину целиком: может применить индекс и «протолкнуть» условие внутрь CTE. WITH … AS MATERIALIZED инлайн запрещает: CTE вычисляется один раз и сохраняется во временном наборе. Это полезно, если он тяжёлый и используется несколько раз, и вредно, если после инлайна план был лучше. Проверять — планом, а не догадками.

Пагинация: почему OFFSET дорогой и что такое keyset

Сначала — что означает OFFSET: это «пропусти первые N строк». Классическая пагинация «по номеру страницы» выглядит так:

-- страница 1
SELECT id, created_at, total FROM orders ORDER BY created_at DESC LIMIT 20 OFFSET 0;
-- страница 1000
SELECT id, created_at, total FROM orders ORDER BY created_at DESC LIMIT 20 OFFSET 19980;

Проблема: OFFSET 19980 никуда не «прыгает». База честно читает и сортирует первые 20000 строк, 19980 выбрасывает и отдаёт 20. Чем глубже страница, тем дороже запрос — время растёт линейно. Индекс здесь не спасает: он помогает найти начало диапазона, а не «двадцатитысячную» строку.

Keyset-пагинация («пагинация по ключу», seek method) — вместо номера страницы клиент присылает значения последней увиденной строки, и запрос продолжает с этого места:

-- клиент передал курсор: created_at и id последней строки предыдущей страницы
SELECT id, created_at, total
FROM   orders
WHERE  (created_at, id) < (:'last_created_at', :'last_id')   -- «после неё»
ORDER  BY created_at DESC, id DESC
LIMIT  20;

Здесь работает индекс по (created_at DESC, id DESC): база делает seek сразу к нужному месту и читает ровно 20 строк — стоимость страницы не зависит от её номера. Пара (created_at, id) сравнивается целиком, и ORDER BY должен идти по тем же колонкам: иначе порядок неоднозначен (у двух заказов может совпасть created_at).

LIMIT/OFFSETKeyset

Вставки между запросамистроки «съезжают»: возможны дубли и пропуски стабильно: продолжаем от конкретной строки

В примерах книги это встречалось в кейсе эндпоинта (GET /api/orders?page=1, глава 21): «страница» там — как раз OFFSET.

Огромная таблица: партиционирование и материализованные представления

Две техники из таблицы выше решают разные задачи: первая уменьшает объём читаемых данных, вторая избавляет от повторного вычисления.

Партиционирование

Это разбиение одной логической таблицы на физические куски (секции) по правилу — чаще всего по дате. Приложение по-прежнему пишет INSERT INTO orders … и читает FROM orders: PostgreSQL сам выбирает нужную секцию.

  • Зачем: запрос с условием по дате читает только подходящие секции (pruning) — меньше страниц; VACUUM и удаление старых данных идут по секции целиком (DROP TABLE orders_2025_01 вместо DELETE миллионов строк).
  • Когда: таблица в сотни миллионов строк, данные «по времени», старые периоды можно выбрасывать.
  • Подробно: глава 26 — PARTITION BY RANGE, границы секций, pruning в плане.

Материализованные представления под агрегаты

Агрегат — свёртка многих строк в несколько значений: SUM(total), COUNT(*), GROUP BY день. Считать их на каждый запрос по большой таблице дорого. Материализованное представление (materialized view) — это сохранённый на диске результат запроса: читается как обычная таблица, без пересчёта.

CREATE MATERIALIZED VIEW orders_daily AS
SELECT date_trunc('day', created_at) AS day,
       status,
       count(*)   AS orders,
       sum(total) AS revenue
FROM   orders
GROUP  BY 1, 2;

-- данные устарели → пересчитать (для CONCURRENTLY нужен UNIQUE-индекс)
REFRESH MATERIALIZED VIEW CONCURRENTLY orders_daily;
  • Выигрыш: отчёт читает готовые строки вместо сканирования миллионов.
  • Цена: данные несвежие — между REFRESH есть отставание; само обновление дорогое. Нужна политика: раз в минуту/час или по событию.
  • Альтернативы: таблица-кэш, заполняемая заданием; или обычный индекс под конкретный запрос, если агрегат простой.

Настройки, которые реально влияют

  • work_mem — память на сортировки и хеши (умножается на число операций, осторожно).
  • random_page_cost — для SSD ниже (≈1.1), иначе планировщик недооценивает индексы.
  • effective_cache_size — сколько данных «примерно в кэше»; влияет на выбор индекса.
  • enable_seqscan / enable_hashjoin и т. п. — только для диагностики, не как постоянное решение.
Чего в PostgreSQL нет

Подсказок планировщику (как /*+ INDEX(...) */ в Oracle). Есть расширение pg_hint_plan, но правильнее починить статистику и индексы, а не «заставлять» план.

★ Правило оптимизации

Меняем одно и заново снимаем план. Иначе невозможно понять, что помогло. И обязательно измеряем на реальной нагрузке (глава 33), а не только «в консоли».
