Глава 20. Логирование и наблюдаемость

В проде нельзя подключиться отладчиком. Остаются три инструмента — логи, метрики и трейсы — и умение связать их между собой. Разберём, что и как писать, чтобы по инциденту можно было ответить «что случилось с заказом 42».

основная глава

Три столпа и на какой вопрос отвечает каждый

Что этоВопросСтоимость
Логизаписи о событиях: «что произошло» с контекстом«почему у этого заказа ошибка?»дорого по объёму — их надо хранить и индексировать
Метрикичисла во времени: RPS, задержка, ошибки, память«когда и насколько стало плохо?»дёшево (гл. 21)
Трейсыцепочка вызовов одного запроса по сервисам«где именно ушло время?»средне: сэмплирование обязательно

Они дополняют друг друга: метрика показывает что сломалось, трейс — где, лог — почему. Связывает их идентификатор запроса (см. ниже).

Структурные логи: сообщение — шаблон, а не строка

// ✘ интерполяция: строка уже склеена, полей для поиска нет
_logger.LogInformation($"Заказ {orderId} оплачен на {total}");

// ✔ шаблон: {OrderId} и {Total} сохраняются как отдельные поля
_logger.LogInformation("Заказ {OrderId} оплачен на {Total}", orderId, total);
  • Почему шаблон: в хранилище попадают поля OrderId=42, Total=1500 — по ним можно искать и строить графики, а не парсить текст регулярками.
  • Почему не интерполяция: строка собирается всегда, даже если уровень логирования выключен (лишние аллокации — гл. 7). Шаблон форматируется только при записи.
  • Исключение передавайте объектом: _logger.LogError(ex, "…") — тогда сохранится стек и innerException; ex.ToString() в сообщении этого не даст.

Уровни: когда какой

УровеньКогдаВ проде
Traceочень подробно, для отладки конкретной проблемывыключен
Debugдиагностика: вход/выход методов, параметрыобычно выключен, включается точечно

Категория — ILogger<OrderService>: имя типа попадает в лог, и можно включать подробности только для одного класса через конфигурацию:

{
  "Logging": {
    "LogLevel": {
      "Default": "Information",
      "Microsoft.AspNetCore": "Warning",          // не логировать каждый запрос Kestrel
      "Microsoft.EntityFrameworkCore.Database.Command": "Information",
      "Orders.Infrastructure.Payments": "Debug"  // только этот namespace — подробно
    }
  }
}

Что логировать и чего не логировать

НужноНельзя (или только с маскированием)
бизнес-события: «заказ 42 оплачен», «импорт завершён, 1200 строк»пароли, токены, номера карт, коды подтверждения
идентификаторы: OrderId, UserId, RequestId, TenantIdперсональные данные целиком (ФИО + адрес + телефон — это уже утечка)
ошибки с контекстом: что делали, с какими параметрами, что ответила зависимость тела запросов/ответов целиком (объём + PII)
начало/конец внешних вызовов — на уровне Debugлоги в цикле на каждую строку (объём растёт линейно)
Правило «одна запись — одно событие»

Не склеивайте в одно сообщение пять событий через запятую: по такому логу нельзя фильтровать. Лучше пять записей с общими полями (их свяжет RequestId) — и хранилище позволит построить по ним выборку.

Scope и корреляция: связать логи одного запроса

В логе должны быть поля, по которым записи одного запроса собираются вместе: RequestId / TraceId, а также TenantId, UserId, если они есть. В ASP.NET Core это делается один раз в middleware:

app.Use(async (ctx, next) =>
{
    // идентификатор запроса: уже есть (от прокси) или сгенерирован
    var requestId = ctx.Request.Headers["X-Request-Id"].FirstOrDefault() ?? ctx.TraceIdentifier;

    // всё, что залогировано внутри, получит эти поля автоматически
    using (_logger.BeginScope(new Dictionary<string, object>
    {
        ["RequestId"] = requestId,
        ["Path"]      = ctx.Request.Path.Value ?? ""
    }))
    {
        ctx.Response.Headers["X-Request-Id"] = requestId;   // вернуть клиенту для поддержки
        await next();
    }
});
  • Зачем возвращать X-Request-Id: клиент/поддержка присылают его в обращении, и вы находите все логи этого запроса одной строкой поиска.
  • Сквозная корреляция между сервисами идёт не через вашу переменную, а через стандарт W3C Trace Context (traceparent): его автоматически пробрасывают HttpClient/gRPC и читает OpenTelemetry. Поэтому TraceId одинаков у всех участников цепочки.
  • BeginScope не «приклеивает» поля к тексту: провайдер логирования сам добавляет их к каждой записи (у JSON-логов это отдельные свойства).

Куда писать: провайдеры

КудаКогдаОсобенность

Файл на дискеlegacy, не контейнерынужна ротация и место; в контейнере — антипаттерн

Формат — JSON (по строке на запись): его читают машины, и в нём сохраняются поля (OrderId, RequestId). Текстовый формат годится для локальной разработки.

Метрики: что считать

Метрики — числа, по которым строят графики и алерты. Подробно инструменты — в главе 21, здесь — что именно считать у сервиса:

  • RED для эндпоинтов: Rate (RPS), Errors (доля ошибок), Duration (гистограмма задержки — p95/p99, не среднее).
  • Насыщение: занятость пула соединений, длина очереди, число задач в пуле, память и CPU (в контейнере — относительно лимита, Docker-раздел).
  • Бизнес-метрики: заказов в минуту, отказов платежей, размер outbox-очереди. Они первыми показывают проблему, которую технические метрики ещё не видят.
// счётчик и гистограмма через System.Diagnostics.Metrics
private static readonly Meter Meter = new("Orders");

private static readonly Counter<long> OrdersPaid =
    Meter.CreateCounter<long>("orders.paid");

private static readonly Histogram<double> PayDuration =
    Meter.CreateHistogram<double>("orders.pay.duration", unit: "ms");

Трейсы: один запрос через все сервисы

Трейс — дерево спанов: «HTTP-запрос → SELECT в БД → вызов платёжного API». У каждого спана есть длительность и атрибуты, а у всего трейса — общий TraceId.

TraceId 4bf92f3577b34da6
├─ POST /api/orders               120 мс   ← наш эндпоинт
│  ├─ SELECT orders …              3 мс    ← EF Core (спан создаётся автоматически)
│  ├─ POST https://pay.internal   110 мс  ← внешний вызов (спан от HttpClient)
│  └─ INSERT order + outbox        5 мс
└─ (в другом сервисе) обработка события outbox   — тот же TraceId
  • Как включить: пакеты OpenTelemetry + инструментирование ASP.NET Core, HttpClient, EF Core/Npgsql. Свои спаны — через ActivitySource. Готовый код и реальный вывод трейса — в следующем разделе.
  • Сэмплирование обязательно: хранить все трейсы дорого; обычно 1–10 % + все «медленные» и все с ошибкой (tail-based sampling).
  • Зачем: именно трейс отвечает «где ушло время» — и часто показывает, что виноват не ваш код, а внешний сервис.

Включаем трейсинг: пакеты и код

Нужны пакеты OpenTelemetry: хост-интеграция, инструментирование того, что хотите видеть, и экспортёр. Ставятся как обычно — dotnet add package ИмяПакета; версии ниже — из реальной установки на .NET 8:

ПакетВерсияЗачем
OpenTelemetry.Extensions.Hosting1.20.1AddOpenTelemetry() в приложении
OpenTelemetry.Instrumentation.AspNetCore1.20.2спаны входящих запросов
OpenTelemetry.Instrumentation.Http1.20.2спаны исходящих HTTP-вызовов
OpenTelemetry.Exporter.Console1.20.1локально: спаны печатаются в консоль
OpenTelemetry.Exporter.OpenTelemetryProtocol1.20.1в проде: OTLP в коллектор

Вся настройка — один блок в Program.cs:

// using OpenTelemetry.Resources;
// using OpenTelemetry.Trace;

builder.Services.AddOpenTelemetry()
    .ConfigureResource(r => r.AddService("orders-api"))    // service.name попадёт в каждый спан
    .WithTracing(t => t
        .AddSource(OrderService.SourceName)                // свои спаны (см. ниже)
        .AddAspNetCoreInstrumentation()                    // входящие запросы → Server-спаны
        .AddHttpClientInstrumentation()                    // исходящие HTTP    → Client-спаны
        .SetSampler(new ParentBasedSampler(new TraceIdRatioBasedSampler(0.1)))  // 10 % трейсов
        .AddConsoleExporter());                            // локально; в проде — AddOtlpExporter()

builder.Services.AddHttpClient();
builder.Services.AddSingleton<OrderService>();

Свои спаны создаёт ActivitySource из System.Diagnostics — это часть BCL: без OpenTelemetry он просто ничего не делает. Источник делают static readonly, один на библиотеку или сервис:

public sealed class OrderService
{
    public const string SourceName = "Shop.Orders";
    private static readonly ActivitySource Source = new(SourceName);   // создаём один раз

    public List<Order> Build(int count)
    {
        using var span = Source.StartActivity("orders.build", ActivityKind.Internal);
        span?.SetTag("orders.count", count);                 // атрибуты спана

        var orders = Enumerable.Range(1, count).Select(i => new Order(i, i * 100m)).ToList();
        span?.SetTag("orders.total", (double)orders.Sum(o => o.Total));

        return orders;
    }   // using закроет спан и запишет длительность
}
Почему span? с вопросительным знаком

Если спан никто не слушает, StartActivity возвращает null — и это норма: при выключенном трейсинге код не платит за спаны. Проверено: без слушателя — null, после регистрации ActivityListener — спан. Поэтому пишут span?., а не падают.

Запрос GET /orders?count=3 (эндпоинт дополнительно вызывает /health через HttpClient) даёт четыре спана. Дерево собрано из реального вывода AddConsoleExporter(); вложенность задаёт ParentSpanId:

Что добавляет какая инструментация

Вызов / пакетСпаныЧто внутри
AddAspNetCoreInstrumentation()Server на каждый входящий запрос метод, путь и маршрут, статус, длительность
AddHttpClientInstrumentation()Client на каждый исходящий HTTP-вызов URL, статус; пробрасывает traceparent
AddSource("Shop.Orders")ваши спаныто, что вы сами назвали и разметили
AddEntityFrameworkCoreInstrumentation() — пакет OpenTelemetry.Instrumentation.EntityFrameworkCore, пока beta (1.20.2-beta.1)спан на каждую команду БДкоманда и параметры; SQL-текст сам не добавляется — если нужен, его кладут в EnrichWithIDbCommand (и думают про ПДн)
AddSource("Npgsql")спаны самого драйверакоманда и открытие соединения; источник действительно называется Npgsql (проверено)

Ещё две настройки, о которых стоит знать:

// EF Core: текст SQL попадёт в спан как тег (осторожно с ПДн в параметрах)
.AddEntityFrameworkCoreInstrumentation(o =>
    o.EnrichWithIDbCommand = (activity, command) => activity.SetTag("db.statement", command.CommandText));

// ошибка в трейсе: статус Error + описание (проверено — сохраняется)
span?.SetStatus(ActivityStatusCode.Error, ex.Message);
  • Локально — AddConsoleExporter(): спаны печатаются в консоль, как выше. Быстрая проверка, что инструментирование вообще работает.
  • В проде — AddOtlpExporter(o => o.Endpoint = new Uri("http://collector:4317")): один протокол на логи, метрики и трейсы; принимают Jaeger, Tempo, Seq, облачные сервисы.
  • Сэмплер — TraceIdRatioBasedSampler(0.1) берёт 10 % трейсов, а ParentBasedSampler уважает решение родителя, поэтому трейс не рвётся на полпути между сервисами.
  • HttpClient-спаны появляются у любых HttpClient (инструментация слушает System.Net.Http): проверено — Client-спан есть и у new HttpClient(). AddHttpClient() нужен по другой причине — пулы и настройка клиентов.

Чек-лист «сервис готов к разбору инцидента»

  1. Логи — в stdout, в JSON, с шаблонными полями и уровнями по смыслу.
  2. В каждой записи есть RequestId/TraceId; он возвращается клиенту.
  3. Ошибки логируются объектом исключения, один раз — на границе запроса.
  4. Есть метрики RED + насыщение (пул, очередь) + хотя бы одна бизнес-метрика.
  5. Трейсинг включён и пробрасывается через HTTP/gRPC; сэмплирование настроено.
  6. Секретов и ПДн в логах нет — проверяется на ревью и сканером.
  7. Есть алерты: доля ошибок, p95, насыщение пула; и они не шумят.
★ Что запомнить из главы
  • Логи отвечают «почему», метрики — «что и когда», трейсы — «где»; связывает их идентификатор запроса.
  • Логи структурные: шаблон + поля, а не склеенная строка.
  • Уровни по смыслу; Information — для бизнес-событий, а не для всего подряд.
  • Не логируйте секреты и ПДн; исключение передавайте объектом.
  • В контейнере — stdout + JSON, а не файлы; для трейсов — OpenTelemetry и traceparent.
  • Метрики: RED, насыщение и бизнес-показатели; инструменты — глава 21.
