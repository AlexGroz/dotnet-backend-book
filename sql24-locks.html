Глава 24. Блокировки, deadlock и retry

Строки, таблицы, DDL и почему ошибки надо повторять. Разберём, что и когда блокирует PostgreSQL, как найти виновника «зависшего» запроса, откуда берутся взаимные блокировки и как писать код так, чтобы их не было.

основная глава

Зачем блокировки, если есть MVCC

MVCC (глава 23) решает половину задачи: читатель не блокирует писателя, а писатель — читателя. Каждый видит свой снимок данных, поэтому SELECT спокойно работает, пока кто-то другой делает UPDATE.

Но остаётся вторая половина: два писателя не могут менять одну и ту же строку одновременно. Иначе получилось бы «потерянное обновление»: обе транзакции прочитали balance = 100, обе вычли по 30, и в итоге на счёте 70 вместо 40. Чтобы этого не было, PostgreSQL ставит на изменяемую строку блокировку, и вторая транзакция ждёт.

ОперацияЧто блокируетКого ждёт
SELECTничего (в MVCC)никого — читает из снимка
INSERTновую строку (её ещё никто не видит)никого, кроме уникальных индексов
UPDATE / DELETEизменяемую строкутого, кто изменил эту строку раньше и не закоммитил
ALTER TABLEвсю таблицувсех — включая читателей (см. ниже)
Главное правило ожидания

Ожидание блокировки — это не ошибка, а нормальный механизм. Плохо, когда ожидание становится долгим: соединение занято, пул исчерпывается, клиент получает таймаут. Поэтому кроме «кто кого ждёт» всегда есть второй вопрос — сколько он ждёт и почему так долго.

Два уровня: строка и таблица

  • Строчные блокировки (row-level) — то, что снимается при UPDATE/DELETE. В pg_locks их нет: «эта строка занята» хранится прямо в заголовке версии строки (поле xmax, глава 23). В pg_locks попадает только ожидание — запись с locktype = 'tuple' появляется у того, кто ждёт освобождения строки.
  • Табличные блокировки (table-level) — их берёт каждый запрос, даже обычный SELECT. Они не мешают друг другу, но именно они решают, может ли ALTER TABLE начать работу. Их восемь режимов — ниже.
  • Прочие объекты: страницы, индексы, последовательности, транзакции (pg_locks.locktype: relation, tuple, transactionid, virtualxid, page, advisory).

Восемь режимов табличных блокировок

Режим отвечает на вопрос «насколько сильно я занимаю таблицу». Чем он выше, тем меньше параллельной работы разрешено. Имена запоминать не нужно — важно понимать, что обычная работа (SELECT/INSERT/UPDATE/DELETE) друг другу не мешает, а вот обслуживание и DDL — мешают.

Режим (от слабого к сильному)Кто его берётС чем конфликтует
ACCESS SHARESELECTтолько с ACCESS EXCLUSIVE
ROW SHARESELECT … FOR UPDATE / FOR SHAREс EXCLUSIVE и ACCESS EXCLUSIVE
ROW EXCLUSIVEINSERT, UPDATE, DELETEс SHARE и сильнее (то есть с DDL и CREATE INDEX)
SHARE UPDATE EXCLUSIVEVACUUM (не FULL), ANALYZE, CREATE INDEX CONCURRENTLY, ALTER TABLE … SET (fillfactor = …)сам с собой и с более сильными
SHARECREATE INDEX (без CONCURRENTLY) с ROW EXCLUSIVE и сильнее → блокирует запись
SHARE ROW EXCLUSIVECREATE TRIGGER, некоторые формы ALTER TABLEсо всем, кроме ACCESS SHARE
EXCLUSIVEREFRESH MATERIALIZED VIEW CONCURRENTLYсо всем, кроме ACCESS SHARE (чтение ещё можно)
ACCESS EXCLUSIVEALTER TABLE, DROP TABLE, TRUNCATE, LOCK TABLE, REINDEX (не CONCURRENTLY), CLUSTER, VACUUM FULLсо всеми, включая SELECT

На практике достаточно запомнить три факта:

  1. SELECT + INSERT/UPDATE/DELETE совместимы. Обычная нагрузка не выстраивается в очередь — это и есть выигрыш MVCC.
  2. CREATE INDEX без CONCURRENTLY блокирует запись в таблицу на всё время построения (минуты на больших таблицах). Поэтому в проде — CREATE INDEX CONCURRENTLY: он берёт SHARE UPDATE EXCLUSIVE и не мешает INSERT/UPDATE.
  3. ALTER TABLE требует ACCESS EXCLUSIVE — то есть ждёт всех, кто сейчас читает или пишет таблицу, и на время своей работы блокирует всех.
Очередь блокировок: почему «быстрый ALTER» кладёт сервис

Блокировки выдаются в порядке очереди, без «обгона». Представьте: открыта долгая транзакция с SELECT на таблице; администратор запускает ALTER TABLE orders ADD COLUMN …. ALTER ждёт долгую транзакцию, но при этом уже занял место в очереди на ACCESS EXCLUSIVE. И теперь все новые SELECT/INSERT встают за ALTER, а не перед ним — хотя формально ALTER ещё ничего не делает. Через несколько секунд таблица полностью недоступна, и виноват не ALTER, а ожидание.

Поэтому DDL выполняют с коротким lock_timeout и повтором:

SET lock_timeout = '3s';          -- не ждать блокировку дольше 3 секунд
ALTER TABLE orders ADD COLUMN note text;
-- если не успели — ERROR: canceling statement due to lock timeout (55P03).
-- Тогда: подождать и повторить, а не «висеть» в очереди и блокировать всех.

Также полезно: ALTER TABLE … SET (fillfactor = 90) — это только параметр хранения, он берёт SHARE UPDATE EXCLUSIVE и чтение не блокирует. А ADD COLUMN … DEFAULT NULL не переписывает таблицу (только каталог), поэтому проходит мгновенно.

Строчные блокировки: FOR UPDATE и SKIP LOCKED

UPDATE сам блокирует строку — но только в момент записи. Если логика такая: «прочитать → принять решение → записать», между чтением и записью есть окно, в которое другая транзакция успевает изменить строку. Классический пример — снятие денег:

-- ✘ без блокировки: две сессии читают balance = 100 одновременно
BEGIN;
SELECT balance FROM accounts WHERE id = 1;          -- обе увидели 100
-- …проверка «хватает ли 100 на списание 100» в коде приложения…
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;
-- итог: баланс 0, а списаний два → ушли в минус, хотя каждая транзакция «проверила»

Лечится блокировкой на чтение: строка занимается сразу, и вторая сессия ждёт до того, как прочитает значение.

-- ✔ FOR UPDATE: строка заблокирована на время транзакции
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;   -- вторая сессия ждёт здесь
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;                                                 -- блокировка снята, ждущая читает уже 0
ВариантЧто делаетКогда нужен
FOR UPDATEполная блокировка строки: никто не изменит и не заблокирует её иначе«прочитать и изменить» — деньги, остатки, счётчики
FOR NO KEY UPDATEслабее: не мешает добавлять ссылки по внешнему ключу на эту строкуизменение неключевых полей (ставится автоматически обычным UPDATE)
FOR SHAREразрешает другим тоже читать с блокировкой, но запрещает менять«проверить, что строка не изменится, пока я работаю»
FOR KEY SHAREсамая слабая: защищает только ключпроверка ссылок по внешнему ключу (автоматически)

Модификаторы ожидания — то, что отличает «жду» от «падаю» и «беру следующую»:

-- (а) не ждать: если строка занята — сразу ошибка (SQLSTATE 55P03)
SELECT * FROM accounts WHERE id = 1 FOR UPDATE NOWAIT;

-- (б) не ждать, а взять другую строку — очередь задач на PostgreSQL
--     индекс по status нужен, иначе каждая воркер-сессия читает всю таблицу
SELECT id, payload
FROM   outbox
WHERE  status = 'pending'
ORDER  BY created_at
LIMIT  10
FOR UPDATE SKIP LOCKED;      -- занятые другими воркерами строки просто пропускаем

-- дальше — UPDATE ... SET status = 'in_progress' и COMMIT: строки освободятся
-- для остальных, но уже со статусом in_progress
Почему SKIP LOCKED — «правильная» очередь

Без него несколько воркеров встают в очередь за одними и теми же первыми строками: один работает, остальные ждут — параллелизм нулевой. С SKIP LOCKED каждый воркер берёт свободные строки, и они не мешают друг другу. Это ровно тот приём, которым устроены очереди в PostgreSQL (и воркер outbox в .NET-разделе).

Ограничения: SKIP LOCKED нельзя использовать для «прочитать все данные» — вы осознанно теряете занятые строки в этом запросе. И он бесполезен без индекса по условию выборки.

Диагностика: кто кого ждёт

Первое, что нужно при «запрос висит», — найти ожидание, а не гадать по логам приложения. Всё есть в системных представлениях, и лучший инструмент — функция pg_blocking_pids(pid): она сразу возвращает список тех, кто держит блокировку.

-- кто кого блокирует и сколько это уже длится
SELECT pid,
       usename,
       state,
       now() - xact_start            AS xact_age,        -- сколько живёт транзакция
       now() - query_start           AS query_age,       -- сколько идёт текущий запрос
       pg_blocking_pids(pid)         AS blocked_by,      -- массив PID «виновников»
       left(query, 60)               AS query
FROM   pg_stat_activity
WHERE  cardinality(pg_blocking_pids(pid)) > 0            -- только те, кто ждёт
ORDER  BY xact_age DESC;

Пример вывода: один сеанс держит строку в открытой транзакции, второй ждёт.

pidstatexact_ageblocked_byquery
20431active00:00:42{20388} UPDATE accounts SET balance = …
20388idle in transaction00:02:10 {}SELECT … FOR UPDATE

Читается так: 20388 взял блокировку и ничего не делает (транзакция открыта, но запросов нет — классическая ошибка приложения), а 20431 ждёт уже 42 секунды. Лечится не «убить ждущего», а закрыть транзакцию у 20388.

-- то же через pg_locks: что именно не выдали и в каком режиме
SELECT l.pid,
       l.locktype,                    -- relation / tuple / transactionid / advisory …
       l.mode,                        -- AccessShareLock, RowExclusiveLock, …
       l.relation::regclass           -- какая таблица (NULL, если это не relation)
FROM   pg_locks l
WHERE  NOT l.granted                 -- ждущие, ещё не полученные блокировки
ORDER  BY l.pid;

-- «забытые» транзакции: открыты, но ничего не делают
SELECT pid, state, now() - xact_start AS xact_age, left(query, 50) AS last_query
FROM   pg_stat_activity
WHERE  state = 'idle in transaction'
ORDER  BY xact_age DESC;

-- аккуратно закрыть: сначала отменить запрос, только потом — соединение
SELECT pg_cancel_backend(20431);       -- отменяет текущий запрос (мягко)
SELECT pg_terminate_backend(20388);    -- рвёт соединение целиком (жёстко)
Не начинайте с pg_terminate_backend

Обрыв соединения откатывает транзакцию — это может быть чужая работа на 10 минут, которая сейчас закоммитится. Сначала pg_cancel_backend (отменить один запрос), сначала проверьте, что за запрос и чья сессия. И помните: убийство сеанса не «исправляет» приложение — оно лишь освобождает блокировку до следующего раза.

Таймауты вместо бесконечного ожидания

Приложение не должно ждать вечно: лучше получить ошибку за 3 секунды и повторить/показать понятное сообщение, чем занять соединение на минуты (и тем самым исчерпать пул — глава 23 .NET-раздела).

ПараметрЧто ограничиваетРазумное значение
lock_timeoutсколько ждать блокировку, прежде чем упасть (55P03)1–3 с для OLTP; 0 = ждать бесконечно
statement_timeoutсколько может идти сам запрос5–30 с для API, отдельно для отчётов и DDL
idle_in_transaction_session_timeoutсколько транзакция может «просто стоять» открытой10–60 с — защита от «забытых» транзакций
deadlock_timeoutчерез сколько проверять взаимные блокировки1 с (по умолчанию), менять не нужно
log_lock_waits = onписать в лог ожидания дольше deadlock_timeoutвключать в проде — это главный источник диагностики
 
-- (а) на уровне роли приложения: применяется ко всем её соединениям
ALTER ROLE app_user SET lock_timeout      = '3s';
ALTER ROLE app_user SET statement_timeout = '15s';
ALTER ROLE app_user SET idle_in_transaction_session_timeout = '30s';

-- (б) точечно для опасной операции (DDL в миграции)
SET LOCAL lock_timeout = '2s';      -- LOCAL — только до конца транзакции
ALTER TABLE orders ADD COLUMN note text;

В .NET эти же значения можно задать в строке подключения (Options=-c lock_timeout=3000) и применить командой command.CommandTimeout — но это клиентский таймаут, он не отменяет работу на сервере, а только перестаёт ждать ответ.

Дедлок: когда ждут друг друга

Взаимная блокировка (deadlock) — ситуация, в которой A держит то, что нужно B, а B держит то, что нужно A. Ни одна не может продолжить, и без вмешательства они ждали бы вечно. Разберём по шагам (две сессии работают параллельно):

ШагСессия AСессия BСостояние
1BEGIN; UPDATE accounts SET … WHERE id = 1;— A держит строку 1
2—BEGIN; UPDATE accounts SET … WHERE id = 2; B держит строку 2
3UPDATE … WHERE id = 2;—A ждёт B
4—UPDATE … WHERE id = 1;цикл: B ждёт A

PostgreSQL замечает цикл через deadlock_timeout (по умолчанию 1 секунда) и откатывает одну из транзакций — ту, которую дешевле перезапустить:

-- у «проигравшей» сессии:
-- ERROR:  deadlock detected
-- DETAIL:  Process 20431 waits for ShareLock on transaction 51234; blocked by process 20388.
--          Process 20388 waits for ShareLock on transaction 51233; blocked by process 20431.
-- HINT:  See server log for query details.
-- SQLSTATE: 40P01

-- в логе сервера (при log_lock_waits = on) — то же плюс тексты запросов
-- deadlock detected … Process 20431 waits for … blocked by process 20388

Важно: дедлок — не баг базы, а следствие порядка действий приложения. Поэтому лечится он в коде, а не настройками.

Как не допускать

  1. Один и тот же порядок захвата. Самая частая причина — «A сначала трогает счёт 1, потом 2, а B наоборот». Если все транзакции блокируют строки в одном порядке (например, по возрастанию id), цикл невозможен: 
    -- ✔ сначала взять блокировки в детерминированном порядке, потом менять
SELECT id FROM accounts
WHERE  id IN (1, 2)
ORDER  BY id            -- все транзакции идут в одном порядке → дедлока не будет
FOR UPDATE;

UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
  2. Короткие транзакции и мало строк. Чем меньше строк и времени, тем меньше окно для пересечения. Не держите транзакцию открытой во время HTTP-вызова (глава 23 .NET-раздела).
  3. Не блокируйте лишнего. FOR UPDATE — только там, где действительно нужно «прочитать и изменить». Массовый FOR UPDATE по 10 000 строк почти гарантирует столкновения.
  4. Очереди — на SKIP LOCKED. Тогда воркеры вообще не ждут друг друга.
  5. Массовые обновления — пачками и в одном порядке (например, по диапазонам id), а не «всё сразу».
  6. Retry — часть контракта. Даже идеальный код может получить 40P01 или 40001: это штатная ситуация, транзакцию повторяют целиком (глава 22).
// повтор транзакции на «конкурентных» ошибках — по SQLSTATE, а не по тексту
private static bool IsRetryable(PostgresException ex) =>
    ex.SqlState is "40001" or "40P01" or "55P03";   // serialization / deadlock / lock_timeout

for (var attempt = 1; attempt <= 3; attempt++)
{
    try
    {
        await using var tx = await db.Database.BeginTransactionAsync(ct);
        // … работа с БД …
        await tx.CommitAsync(ct);
        break;                                        // успех — выходим из цикла
    }
    catch (PostgresException ex) when (IsRetryable(ex) && attempt < 3)
    {
        await Task.Delay(TimeSpan.FromMilliseconds(50 * attempt), ct);   // 50, 100 мс
        // транзакция уже откатана сервером — начинаем заново
    }
}

Сколько дедлоков было — видно в статистике: SELECT datname, deadlocks FROM pg_stat_database; Рост этого счётчика — сигнал, что где-то нарушен порядок захвата.

Advisory-блокировки: «свои» замки

Иногда блокировать нужно не строку и не таблицу, а логический ресурс: «ночная миграция», «импорт файла X», «только один воркер чистит каталог». Для этого есть advisory-блокировки: вы даёте PostgreSQL число (или пару чисел), и он блокирует его как обычный объект. За этим числом ничего не стоит — ни таблицы, ни строки.

-- (а) на время сессии: держится, пока её не снимут или сеанс не отключится
SELECT pg_try_advisory_lock(42);     -- true — взяли; false — уже занято (и мы НЕ ждём)
-- … работа …
SELECT pg_advisory_unlock(42);       -- снять вручную

-- (б) на время транзакции: снимается автоматически при COMMIT/ROLLBACK — безопаснее
BEGIN;
SELECT pg_try_advisory_xact_lock(42);
-- … работа …
COMMIT;                              -- замок снят сам

-- (в) без try: не «проверить», а подождать освобождения
SELECT pg_advisory_lock(42);
  • Зачем: «ровно один экземпляр задачи» без отдельной таблицы-флага: пересчёт отчёта, миграция, очистка. Работает между всеми инстансами приложения, потому что замок живёт в базе.
  • Ловушка пула: session-блокировка привязана к соединению. «Взять одним запросом, отпустить другим» не получится: в пуле запросы уходят в разные соединения. Берите xact-вариант (внутри той же транзакции) или держите один NpgsqlConnection явно.
  • Это не изоляция данных: advisory-замок ничего не знает о ваших строках и не мешает их менять. Это координация между процессами, а не защита строк.

Если запрос «висит»: порядок действий

  1. Убедиться, что это блокировка, а не медленный план: запрос в состоянии active и не растёт Buffers — скорее всего ждёт; pg_stat_activity покажет wait_event_type = 'Lock'.
  2. Найти виновника: pg_blocking_pids(pid) (или pg_locks с NOT granted). Смотрим state и xact_age у блокирующего.
  3. Проверить, не idle in transaction — тогда виновато приложение, а не запрос.
  4. Решить, что делать: закрыть транзакцию в приложении → pg_cancel_backend → только в крайнем случае pg_terminate_backend.
  5. Записать в журнал и починить причину: таймауты, CONCURRENTLY, вынос сети из транзакции, единый порядок захвата.
★ Что запомнить из главы
  • MVCC не отменяет блокировки: читатели не мешают писателям, но два писателя одну строку менять не могут — второй ждёт.
  • Каждый запрос берёт табличную блокировку (обычно ACCESS SHARE или ROW EXCLUSIVE); ALTER TABLE требует ACCESS EXCLUSIVE и блокирует даже SELECT.
  • Блокировки выдаются по очереди: «быстрый» ALTER TABLE может парализовать таблицу, потому что новые запросы встают за ним. Лечится lock_timeout + повтор.
  • «Прочитать и изменить» — SELECT … FOR UPDATE; очереди — FOR UPDATE SKIP LOCKED; «не ждать» — NOWAIT.
  • Дедлок — следствие разного порядка захвата; база откатывает одну транзакцию с 40P01, и это надо повторять. Одинаковый порядок (ORDER BY id) убирает причину.
  • Retry — по SQLSTATE (40001, 40P01, 55P03), а не по тексту ошибки.
  • Advisory-блокировки — «свои» замки для «один воркер на всю систему»; xact-вариант безопаснее в приложении с пулом.
  • Диагностика: pg_blocking_pids, pg_locks, pg_stat_activity, log_lock_waits, счётчик deadlocks.
