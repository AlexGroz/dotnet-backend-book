Глава 4. Consumer: группы, оффсеты, коммиты и rebalance

Как читать журнал со своего места, когда коммитить оффсет, что показывает LAG и почему партиции делятся между экземплярами

основная глава

Настройки consumer'а

var config = new ConsumerConfig
{
    BootstrapServers = "localhost:9092",          // точка входа в кластер
    GroupId          = "orders-workers",          // имя группы: по нему хранятся оффсеты
    AutoOffsetReset  = AutoOffsetReset.Earliest,  // с чего начинать, если коммита ещё нет
    EnableAutoCommit = false,                     // подтверждать оффсет вручную, после обработки
};
НастройкаЧто означает
GroupIdимя consumer group. Оффсеты хранятся на пару «группа + топик + партиция»; участники с одним GroupId делят партиции между собой
AutoOffsetResetчто делать, если для группы нет сохранённого оффсета: Earliest — с начала журнала, Latest — только новые сообщения. Значение по умолчанию — Latest
EnableAutoCommittrue — клиент коммитит оффсеты сам по таймеру, до обработки; false — коммит делает приложение через Commit
BootstrapServers, ClientIdадрес кластера и имя клиента — как у producer'а
EnableAutoCommit = true — источник потерь

Автокоммит отправляет оффсет по расписанию, не дожидаясь обработки. Процесс упал в середине обработки — оффсет уже сдвинут, сообщение не будет прочитано никем. Поэтому в рабочих сервисах автокоммит выключают и коммитят после обработки.

Код: читаем со своего места и коммитим

using Confluent.Kafka;                                   // ConsumerConfig, ConsumerBuilder, ConsumeResult

var config = new ConsumerConfig
{
    BootstrapServers = "localhost:9092",                 // адрес брокера
    GroupId          = "orders-workers",                 // группа: под ней будут храниться оффсеты
    AutoOffsetReset  = AutoOffsetReset.Earliest,         // нет коммита — читаем с начала
    EnableAutoCommit = false,                            // коммитить будем вручную
};

using var consumer = new ConsumerBuilder<string, string>(config).Build(); // ключ и значение — строки
consumer.Subscribe("orders");                            // подписка на топик целиком (все партиции)

var idleUntil = DateTime.UtcNow.AddSeconds(10);          // первая подписка ждёт ребаланс — даём до 10 с
while (DateTime.UtcNow < idleUntil)
{
    var cr = consumer.Consume(TimeSpan.FromMilliseconds(200)); // null, если за 200 мс ничего не пришло
    if (cr is null)
        continue;                                        // ждём дальше, пока не истечёт окно

    Console.WriteLine($"got key={cr.Message.Key} partition={cr.Partition.Value} offset={cr.Offset.Value}");
    consumer.Commit(cr);                                 // сдвинуть оффсет группы: сообщение обработано
    idleUntil = DateTime.UtcNow.AddSeconds(2);           // после сообщения ждём тишины 2 с
}

consumer.Close();                                        // выйти из группы и завершить сессию корректно
got key=order-3 partition=2 offset=0
got key=order-1 partition=1 offset=0
got key=order-2 partition=0 offset=0

Порядок строк — не порядок отправки: три партиции читаются параллельно, и consumer получает то, что пришло первым. Внутри партиции порядок сохраняется всегда.

Что лежит в результате чтения

ПолеЧто означает
cr.Message, cr.Key, cr.Valueсообщение и его ключ со значением — уже десериализованные клиентом
cr.Topic, cr.Partition, cr.Offsetоткуда прочитано: топик, партиция и оффсет записи
cr.TopicPartitionOffsetвсе три части одним значением — удобно передать в Commit или сохранить
cr.Timestampвремя записи (тип TimestampType говорит, чьё это время: producer'а или брокера)
cr.Headersзаголовки сообщения (например, trace-id)
cr.IsPartitionEOFtrue, если партиция дочитана до конца; сообщения в таком результате нет
Consume(timeout)вернёт null, если за timeout ничего не пришло. Это не ошибка — просто нет новых данных

Коммит: где именно хранится позиция

Commit(cr) записывает для группы оффсет следующего сообщения, то есть offset + 1. Поэтому после чтения оффсета 0 в партиции 2 в описании группы стоит CURRENT-OFFSET 1 — «следующее, которое надо прочитать».

# описание группы: что уже закоммичено и что осталось
docker exec kafka /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --describe --group orders-workers
# GROUP           TOPIC   PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG  CONSUMER-ID  HOST  CLIENT-ID
# orders-workers  orders  0          1               1               0    -            -     -
# orders-workers  orders  1          1               1               0    -            -     -
# orders-workers  orders  2          1               1               0    -            -     -

Оффсеты групп хранит не потребитель и не «память брокера», а служебный топик __consumer_offsets — обычный топик Kafka, который создаётся при первом коммите. Его параметры по умолчанию: 50 партиций и cleanup.policy=compact, то есть хранится последнее значение на ключ «группа + партиция».

# служебный топик появился после первого коммита
docker exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --list
# __consumer_offsets
# demo
# keys
# ... (остальные топики демо-кластера)

docker exec kafka /opt/kafka/bin/kafka-configs.sh --bootstrap-server localhost:9092 \
  --describe --entity-type brokers --entity-name 1 --all | grep offsets.topic.num.partitions
# offsets.topic.num.partitions=50   ... DEFAULT_CONFIG:offsets.topic.num.partitions=50

Гарантия: at-least-once

Схема «прочитал → обработал → закоммитил» даёт доставку как минимум один раз:

  • Упали до коммита — оффсет не сдвинулся, после перезапуска сообщение придёт снова. Работа не потеряна, но может выполниться дважды.
  • Упали после коммита — сообщение считается обработанным; если коммит был раньше обработки (автокоммит), работа потеряна.
Порядок действий важнее настроек

Коммит — это «я закончил». Пока он идёт после обработки, Kafka не теряет работу; дубли возможны, и обработчик должен быть идемпотентным: проверять Message.Key или уникальный идентификатор в БД, как в книге про RabbitMQ (глава 3).

LAG: насколько группа отстала

Главная метрика consumer'а — lag: сколько записей в партиции ещё не прочитано группой. Добавим в orders три сообщения и снова посмотрим описание:

# пишем ещё три сообщения в топик, который группа уже читала
printf 'order-4:{"id":4}\norder-5:{"id":5}\norder-6:{"id":6}\n' | docker exec -i kafka \
  /opt/kafka/bin/kafka-console-producer.sh --bootstrap-server localhost:9092 --topic orders \
  --property parse.key=true --property key.separator=:

docker exec kafka /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --describe --group orders-workers
# GROUP           TOPIC   PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG  CONSUMER-ID  HOST  CLIENT-ID
# orders-workers  orders  0          1               2               1    -            -     -
# orders-workers  orders  1          1               1               0    -            -     -
# orders-workers  orders  2          1               3               2    -            -     -
КолонкаЧто означает
CURRENT-OFFSETпоследний закоммиченный оффсет: следующее сообщение, которое группа прочитает
LOG-END-OFFSETсколько всего записей в партиции (следующий оффсет для записи)
LAGLOG-END-OFFSET − CURRENT-OFFSET: сколько ещё не прочитано. Сумма по партициям — общий lag группы
CONSUMER-ID, HOST, CLIENT-IDкто именно читает партицию; прочерки означают, что активных участников нет

Здесь суммарный lag — 3: ровно три новых сообщения. Если lag растёт монотонно, потребители не успевают; если он равен нулю, группа дочитала журнал.

Rebalance: как партиции делятся между экземплярами

Запустим два consumer'а с одним GroupId на топик из трёх партиций и попросим каждого напечатать своё назначение:

static ConsumerConfig Cfg() => new()                 // одинаковая конфигурация для обоих
{
    BootstrapServers = "localhost:9092",
    GroupId          = "assign-demo",                 // одна группа — значит делят партиции
    AutoOffsetReset  = AutoOffsetReset.Earliest,
    EnableAutoCommit = false,
};

using var c1 = new ConsumerBuilder<string, string>(Cfg()).Build();
using var c2 = new ConsumerBuilder<string, string>(Cfg()).Build();
c1.Subscribe("orders");
c2.Subscribe("orders");

using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(10)); // даём время на ребаланс
while (!cts.IsCancellationRequested)
{
    c1.Consume(100);                                  // опрос обязателен: он же держит участие в группе
    c2.Consume(100);
}

Console.WriteLine($"c1: {string.Join(",", c1.Assignment.Select(p => p.Partition.Value))}");
Console.WriteLine($"c2: {string.Join(",", c2.Assignment.Select(p => p.Partition.Value))}");
c1: 2
c2: 0,1
  • Партиции поделились, а не продублировались: каждая партиция досталась ровно одному участнику группы.
  • Максимум параллелизма — число партиций. Четвёртый consumer на топик из трёх партиций останется без работы.
  • Первая подписка ждёт group.initial.rebalance.delay.ms — в этом кластере 3000 мс (проверено в конфигурации брокера). «Первое сообщение не приходит мгновенно» — это нормально.
  • При добавлении участника партиции переезжают (rebalance): часть партиций освобождается и назначается новому consumer'у.
Почему нужен Consume в цикле

Участие в группе поддерживается опросом: heartbeats уходят во время Consume. Если перестать его вызывать, брокер решит, что участник умер, и запустит ребаланс.

AutoOffsetReset: где начинать

Настройка действует только тогда, когда у группы нет закоммиченного оффсета — например, при первом запуске новой группы:

ЗначениеПоведение
Earliestчитать журнал с самого начала (с earliest-оффсета). Так делает программа выше
Latest (по умолчанию)читать только новые сообщения, всё старое игнорируется

Если оффсет уже закоммичен, AutoOffsetReset не применяется: группа продолжит с сохранённого места. Сдвинуть её назад можно, удалив оффсеты группы — kafka-consumer-groups.sh --bootstrap-server localhost:9092 --delete --group orders-workers; команда работает, только когда в группе нет активных участников.

★ Что запомнить из главы
  • Оффсет группы хранится в Kafka — в служебном топике __consumer_offsets, а не в памяти потребителя.
  • Commit(cr) записывает offset + 1: «следующее, что надо прочитать».
  • Коммит после обработки = at-least-once: падение до коммита даёт повтор, а не потерю; обработчик должен быть идемпотентным.
  • LAG = LOG-END-OFFSET − CURRENT-OFFSET — главная метрика отставания группы.
  • Партиции делятся между участниками группы: максимум параллелизма — число партиций; лишние consumer'ы простаивают.
  • AutoOffsetReset работает только без коммита: Earliest читает с начала, Latest — только новое.
