Глава 9. Словари: Dictionary на практике

Полный разбор Dictionary: что бросает исключение, а что молча возвращает default (и чему он равен), из чего состоит элемент перебора, почему порядок перебора нельзя считать порядком вставки, почему изменяемый ключ теряет запись и как этого не допустить. Множества — глава 10, очереди и стеки — глава 11.

основная глава

Глава 6 объясняла, почему generic-коллекции лучше non-generic, и давала таблицу «что выбрать». Здесь — вторая половина: как этим пользоваться, не наступая на грабли. Каждый пример ниже прогнан на .NET 8, в блоках «вывод» — реальный результат, а не пересказ.

Dictionary построен на хеш-таблице: ключ превращается в хеш, хеш — в номер корзины, поэтому «положить», «найти» и «удалить по ключу» стоят в среднем O(1). Обратная сторона: коллекция ничего не обещает про порядок, а изменение ключа после вставки делает запись недостижимой. Обе темы — ниже, с реальным выводом.

Dictionary: положить, перезаписать, достать

Записать в словарь можно двумя способами: индексатором d[key] = value или методом d.Add(key, value). Ведут они себя по-разному, и в этом первая ловушка:

var byId = new Dictionary<int, string>();

byId[1] = "один";          // индексатор: вставит ИЛИ перезапишет — ошибки не будет
byId.Add(2, "два");        // Add: вставит, а если ключ уже есть — исключение
byId[1] = "ОДИН";          // ✔ тихо перезаписали значение
Console.WriteLine(byId[1]);          // ОДИН
Console.WriteLine(byId.Count);       // 2

byId.Add(2, "снова");      // ✘ ключ занят

Вывод: исключение на последней строке

Unhandled exception. System.ArgumentException: An item with the same key has already
been added. Key: 2

Отсюда правило: d[key] = value — это upsert («вставь или обнови»), d.Add(key, value) — «вставь строго новый». В прикладном коде почти всегда нужен первый: он же и быстрее (одно обращение вместо проверки + вставки).

А теперь обратная сторона: чтение индексатором ключа, которого нет, бросает исключение, а не возвращает null:

string v = byId[1];        // ✔ ОДИН
string x = byId[3];        // ✘ падение

Вывод

Unhandled exception. System.Collections.Generic.KeyNotFoundException:
The given key '3' was not present in the dictionary.

Это самая частая ошибка тех, кто пришёл из языков, где словарь на отсутствующем ключе отдаёт undefined/null. В C# null в словаре — это значение, которое кто-то положил; отличить его от «ключа нет» можно только методами ниже.

Чтение без исключений: TryGetValue, GetValueOrDefault

if (byId.TryGetValue(1, out var name))
    Console.WriteLine($"нашли: {name}");     // нашли: ОДИН
else
    Console.WriteLine("ключа нет");

// ✘ так делать не нужно: два поиска вместо одного
if (byId.ContainsKey(1))
{
    string value = byId[1];                   // второй проход по хеш-таблице
}

// «нет ключа» — нормальная ситуация: у метода две перегрузки
Console.WriteLine(byId.GetValueOrDefault(3) ?? "нет");      // перегрузка 1: вернулся default(string)
Console.WriteLine(byId.GetValueOrDefault(3, "нет"));        // перегрузка 2: вернулось заданное значение
Console.WriteLine(byId.GetValueOrDefault(1, "нет"));        // ключ есть — второе значение не нужно

TryGetValue экономит не только строки: он делает одно вычисление хеша и один проход по корзине. Связка ContainsKey + d[key] — два. На одном запросе это незаметно, в цикле на миллион элементов — вполне.

Чему равен default

У GetValueOrDefault в названии стоит default — это default(TValue), и он разный для разных типов. Не «null» и не «0», а именно «значение по умолчанию для TValue»:

TValueЧто вернётся, если ключа нет
int, long, double, decimal 0
boolfalse
char'\0'
string, int[], любой класс или интерфейсnull
int?, DateTime? — любой Nullable<T> null
DateTime01.01.0001 00:00:00 (DateTime.MinValue)
свой struct, Guid, TimeSpan структура, где все поля обнулены (Guid.Empty, TimeSpan.Zero) — это не null

Отсюда главное ограничение: если default для типа — «нормальное» значение, то ответ «ключа нет» неотличим от ответа «ключ есть, значение по умолчанию»:

var counters = new Dictionary<string, int> { ["есть"] = 0 };
var texts = new Dictionary<string, string> { ["есть"] = null };

Console.WriteLine(counters.GetValueOrDefault("есть"));            // 0 — ключ есть, значение 0
Console.WriteLine(counters.GetValueOrDefault("нет"));             // 0 — ключа нет: то же самое
Console.WriteLine(texts.GetValueOrDefault("есть") ?? "null");     // null — значение в словаре
Console.WriteLine(texts.GetValueOrDefault("нет") ?? "null");      // null — ключа нет

// различить два случая можно только отдельной проверкой
Console.WriteLine(counters.ContainsKey("есть") + " " + counters.ContainsKey("нет"));

Вывод

0
0
null
null
True False

Правило: GetValueOrDefault — когда «нет ключа» и «значение по умолчанию» обрабатываются одинаково (счётчик, накопитель, кэш). Если разница важна — TryGetValue. И ещё: ?? работает только с ссылочными и Nullable<T>-типами, поэтому counters.GetValueOrDefault("нет") ?? 0 для int не скомпилируется (error CS0019: Operator '??' cannot be applied to operands of type 'int' and 'int') — там нужна вторая перегрузка.

Перебор: KeyValuePair<TKey, TValue> и Deconstruct

Когда вы пишете foreach по словарю, каждый элемент — не «ключ» и не «значение», а пара: KeyValuePair<TKey, TValue>. Это маленькая структура с двумя свойствами, Key и Value (в примерах переменную обычно называют kvp — от key-value pair):

var hits = new Dictionary<string, int> { ["/a"] = 2 };

// 1. полная форма: тип элемента указан явно
foreach (KeyValuePair<string, int> kvp in hits)
    Console.WriteLine(kvp.Key + " = " + kvp.Value);

// 2. то же, но тип выведен — самая частая запись
foreach (var kvp in hits)
    Console.WriteLine(kvp.Key + " = " + kvp.Value);

// 3. Deconstruct: пара раскладывается на две переменные
foreach (var (url, count) in hits)
    Console.WriteLine(url + " = " + count);

Вывод: три одинаковые строки

/a = 2
/a = 2
/a = 2

Третий вариант — не «другой foreach», а вызов метода Deconstruct, который у KeyValuePair раскладывает пару на ключ и значение. Порядок не произвольный: первая переменная получает Key, вторая — Value. Работает это и вне цикла:

var pair = new KeyValuePair<string, int>("/b", 5);
var (key, value) = pair;

Console.WriteLine(key + " = " + value);      // /b = 5

Что брать: kvp.Key/kvp.Value — когда пара нужна целиком (передать в метод, положить в список); var (key, value) — когда в теле цикла нужны только имена.

Изменение: TryAdd, Remove и идиома счётчика

«Не бросать исключение» — общий стиль у Try*-методов: они возвращают bool и говорят, случилось ли изменение.

Console.WriteLine(byId.TryAdd(2, "x"));        // False — ключ занят, словарь не изменился
Console.WriteLine(byId.TryAdd(9, "девять"));   // True  — добавилось

Console.WriteLine(byId.Remove(9, out var removed));   // True, removed = "девять"
Console.WriteLine(byId.Remove(42));                   // False — и это не ошибка

byId.Clear();                                  // опустошить, ёмкость остаётся
Console.WriteLine(byId.Count);                 // 0

Remove(key, out var value) удобен, когда нужно и убрать, и забрать значение. Без второй перегрузки пришлось бы сначала читать TryGetValue, потом удалять — снова два прохода.

Классическая идиома на GetValueOrDefault — счётчик без ветвления:

var hits = new Dictionary<string, int>();

foreach (var url in new[] { "/a", "/b", "/a" })
    hits[url] = hits.GetValueOrDefault(url) + 1;   // «нет ключа» = 0, дальше просто +1

foreach (var (url, count) in hits)
    Console.WriteLine($"{url} = {count}");

Вывод

/a = 2
/b = 1

Второй аргумент GetValueOrDefault здесь не нужен: у int значение по умолчанию — 0. Для строк так писать нельзя: null + "x" случайно даст "x", а null.Length упадёт — там нужен второй аргумент с явным значением.

Порядок перебора — не порядок вставки

Контракт Dictionary не обещает никакого порядка. В текущей реализации он обычно совпадает с порядком добавления, но стоит что-то удалить — и совпадение заканчивается: освободившуюся ячейку переиспользует следующий добавленный элемент.

var d = new Dictionary<int, string>();
for (int i = 1; i <= 5; i++) d[i] = "v" + i;

d.Remove(1);
d[6] = "v6";

Console.WriteLine(string.Join(",", d.Keys));

Вывод (net8.0): шестёрка встала на место удалённой единицы

6,2,3,4,5

Три вывода из этого:

  • Не опирайтесь на порядок в тестах и в логике: сегодня «по вставке», завтра — другая реализация или другое число удалений.
  • Нужен порядок по ключу — SortedDictionary<TKey, TValue> (O(log n) на операцию) или SortedList<TKey, TValue> (то же на массиве: меньше памяти, дороже вставка в середину).
  • Нужен именно порядок вставки — это List<T> плюс Dictionary для поиска.

Порядок по ключу: SortedDictionary и SortedList

Оба держат ключи отсортированными не «когда-нибудь при переборе», а всегда, поэтому перебор идёт по возрастанию ключа, а поиск и вставка стоят O(log n) вместо O(1):

var dict = new Dictionary<int, string> { [3] = "c", [1] = "a", [2] = "b" };
var sortedDict = new SortedDictionary<int, string> { [3] = "c", [1] = "a", [2] = "b" };
var sortedList = new SortedList<int, string> { [3] = "c", [1] = "a", [2] = "b" };

Console.WriteLine(string.Join(",", dict.Keys));          // у Dictionary порядка нет
Console.WriteLine(string.Join(",", sortedDict.Keys));    // всегда по возрастанию ключа
Console.WriteLine(string.Join(",", sortedList.Keys));

// обратный порядок задаётся компаратором (глава 8)
var desc = new SortedDictionary<int, string>(Comparer<int>.Create((a, b) => b.CompareTo(a)));
desc[1] = "a"; desc[2] = "b"; desc[3] = "c";
Console.WriteLine(string.Join(",", desc.Keys));

// у SortedList есть доступ по номеру — он и есть массив
Console.WriteLine(sortedList.Keys[0] + " = " + sortedList.Values[0]);

Вывод

3,1,2
1,2,3
1,2,3
3,2,1
1 = a

Первая строка — ровно то, о чём предупреждение выше: у Dictionary совпало с порядком вставки, и строить логику на этом нельзя. Дальше — чем два сортированных типа отличаются:

SortedDictionary<TKey, TValue> SortedList<TKey, TValue>
Внутрикрасно-чёрное дереводва массива: ключи и значения
Поиск по ключуO(log n)O(log n) — бинарный поиск
Вставка и удалениеO(log n)O(n) — сдвиг хвоста массива
Доступ по номерунетесть: Keys[i], Values[i]
Память, скорость переборадороже: узлы деревадешевле и быстрее: массивы
Когда братьвставок и удалений многозаполнили один раз и в основном читаете или перебираете

Обоим нужны сравнимые ключи — IComparable<T> или компаратор в конструкторе (глава 8). Ключ без сравнения упадёт только на второй вставке, когда появится с чем сравнивать, причём разными исключениями: SortedDictionary — ArgumentException: At least one object must implement IComparable., SortedList — InvalidOperationException: Failed to compare two elements in the array.

Порядок вставки: List<T> + Dictionary

Готового generic-словаря с порядком вставки в .NET 8 нет: тип OrderedDictionary<TKey, TValue> на net8.0 не компилируется (error CS0246: The type or namespace name 'OrderedDictionary<,>' could not be found). Порядок хранят рядом — список для порядка, словарь для доступа:

var order = new List<string>();              // порядок вставки
var byKey = new Dictionary<string, int>();   // поиск за ~O(1)

void Set(string key, int value)
{
    if (!byKey.ContainsKey(key)) order.Add(key);   // новый ключ — в конец списка
    byKey[key] = value;                            // существующий — обновляем на месте
}

Set("a", 1); Set("b", 2); Set("c", 3); Set("a", 10);

Console.WriteLine(string.Join(" ", order.Select(k => k + "=" + byKey[k])));

order.Remove("b");
byKey.Remove("b");
Console.WriteLine(string.Join(" ", order.Select(k => k + "=" + byKey[k])) + " | " + byKey.Count);

Вывод

a=10 b=2 c=3
a=10 c=3 | 2

Ключ a остался на первом месте, хотя записан дважды, — ровно то, что нужно от «порядка вставки». Цена: перебор идёт по списку, значит order.Remove("b") — это O(n) (сдвиг элементов). Такую конструкцию берут, когда порядок нужен, а удаления редки или их нет вовсе. Если удалять нужно часто, а тип значения может быть object, есть старый non-generic System.Collections.Specialized.OrderedDictionary — порядок он сохраняет, но generics в нём нет, и перебор идёт через DictionaryEntry с приведением типов.

Ключ: хеш, мутация и IEqualityComparer

Словарь находит значение по хешу ключа (глава 3). Значит, ключ обязан быть таким, чтобы GetHashCode не менялся, пока он лежит в словаре. Нарушение — тихая потеря записи:

public record Key { public int Id { get; set; } }   // хеш считается по Id

var key = new Key { Id = 1 };
var map = new Dictionary<Key, string> { [key] = "a" };

key.Id = 2;                                        // хеш изменился — запись «уехала»

Console.WriteLine(map.Count);                      // 1 — запись никуда не делась
Console.WriteLine(map.TryGetValue(key, out _));    // False — найти её уже нельзя

Вывод

Count=1, TryGetValue=False

Когда именно это ломается. Только если GetHashCode зависит от изменяемого состояния: record с set-свойством, класс со своим Equals/ GetHashCode по полю. Обычный класс без переопределений устроен иначе — его хеш считается по ссылке и мутация поля ничего не портит, но и ключом «по значению» он не работает: два объекта с одинаковым Id — это два разных ключа.

public sealed class MutableKey { public int Id { get; set; } }   // без Equals/GetHashCode

var map = new Dictionary<MutableKey, string>();
var key = new MutableKey { Id = 1 };
map[key] = "a";

key.Id = 2;
Console.WriteLine(map.TryGetValue(key, out _));                       // True — хеш по ссылке
Console.WriteLine(map.ContainsKey(new MutableKey { Id = 2 }));        // False — «равный» не находится

Вывод

True
False

Как надо: три способа не потерять запись

1. Сделать ключ неизменяемым. Позиционный record (или init-свойства) — самый простой вариант: менять ключ физически нельзя, а «изменение» становится созданием нового ключа.

public sealed record OrderKey(int Id);        // Id — init-only

var map = new Dictionary<OrderKey, string>();
var key = new OrderKey(1);
map[key] = "a";

Console.WriteLine(map.TryGetValue(key, out var value) + " " + value);   // True a

// key.Id = 2;                                  // ✘ так уже нельзя
var changed = key with { Id = 2 };              // «изменить» = новый ключ

Console.WriteLine(map.TryGetValue(changed, out _));    // False — это другой ключ
Console.WriteLine(map[key]);                          // a — старый ключ на месте

Вывод

True a
False
a

Попытка всё-таки присвоить значение ловится компилятором, а не в рантайме:

error CS8852: Init-only property or indexer 'OrderKey.Id' can only be assigned in an
object initializer, or on 'this' or 'base' in an instance constructor or an 'init' accessor.

2. Не делать ключом сам объект — брать его идентификатор. Так работает код с сущностями: меняются поля (сумма, статус), ключ — Id — остаётся.

var byId = new Dictionary<int, Order>();
var order = new Order { Id = 7, Total = 100m };

byId[order.Id] = order;
order.Total = 200m;                 // объект меняется — ключ нет

Console.WriteLine(byId[7].Total);   // 200 — запись на месте

Вывод

200

3. Если ключ всё-таки должен меняться — менять его в словаре. То есть удалить запись до мутации и вставить заново под новым ключом. Уже испорченную запись удалить не получится: Remove ищет по тому же хешу, что и TryGetValue.

map.Remove(key);         // ✔ пока ключ ещё «старый»
key = key with { Id = 2 };
map[key] = "a";

Console.WriteLine(map.Count + " " + map.TryGetValue(key, out var v) + " " + v);   // 1 True a

Вывод

1 True a

Если же мутация уже случилась, у записи с «уехавшим» хешем остаётся только два выхода: пересоздать словарь или вызвать Clear(). Проверено на классе с равенством по Id: после мутации Count = 1, TryGetValue = False и Remove = False — запись есть в перечислении, но недостижима и неудаляема.

Второй инструмент — компаратор: он задаёт, какие ключи считать одинаковыми.

var byName = new Dictionary<string, int>(StringComparer.OrdinalIgnoreCase);
byName["Аня"] = 1;

Console.WriteLine(byName.TryGetValue("АНЯ", out var n) + " " + n);   // True 1

var plain = new Dictionary<string, int> { ["Аня"] = 1 };
Console.WriteLine(plain.ContainsKey("АНЯ"));                        // False

Вывод

True 1
False

Что брать: StringComparer.Ordinal — по умолчанию, и это правильно для идентификаторов, ключей, e-mail (быстро, без культур); OrdinalIgnoreCase — когда регистр не должен различать («Аня» и «АНЯ» — один пользователь); InvariantCulture* — только если так требует бизнес-правило. Тот же компаратор принимает и HashSet<T>.

LINQ → словарь: ToDictionary и ToLookup

Самый частый способ получить словарь — свернуть последовательность. Здесь спрятана ловушка: ToDictionary требует уникальных ключей и падает на дублях.

var orders = new[] { (Id: 1, Name: "a"), (Id: 2, Name: "b"), (Id: 1, Name: "c") };

var byKey = orders.ToDictionary(o => o.Id);          // ✘ Id = 1 встречается дважды
Console.WriteLine(byKey.Count);

Вывод: то же исключение, что у Add

Unhandled exception. System.ArgumentException: An item with the same key has already
been added. Key: 1

Три способа свернуть в словарь, когда дубли — не повод падать (1–3), и четвёртый — когда словарь вообще не нужен (4):

// 1. дубли — ошибка данных: пусть падает как можно раньше (ToDictionary без прикрас)
var byId = orders.ToDictionary(o => o.Id, o => o.Name);

// 2. дубли допустимы, но на ключ нужно ОДНО значение — правило выбираем сами
var last = orders.GroupBy(o => o.Id).ToDictionary(g => g.Key, g => g.Last().Name);
Console.WriteLine(last[1]);                          // c — «последний победил»

// 3. на ключ приходится несколько значений — GroupBy + ToDictionary
var grouped = orders.GroupBy(o => o.Id)
                    .ToDictionary(g => g.Key, g => g.Select(o => o.Name).ToList());
Console.WriteLine(string.Join(",", grouped[1]));     // a,c

// 4. читать «по ключу → много значений» — сразу ILookup, без промежуточного словаря
ILookup<int, string> lookup = orders.ToLookup(o => o.Id, o => o.Name);
Console.WriteLine(string.Join(",", lookup[1]));      // a,c
Console.WriteLine(lookup.Count);                     // 2 — число ключей, а не элементов
Console.WriteLine(lookup[99].Count());               // 0 — пустая последовательность, не null

Разница, которую стоит проговорить: Dictionary — «один ключ = одно значение», ILookup<TKey, TElement> — «один ключ = много значений», причём отсутствующий ключ возвращает пустую последовательность, а не исключение и не null. Перепутать их — типичная причина ArgumentException в отчётах.

Словарь и несколько потоков

Dictionary не потокобезопасен: одновременная запись (и даже запись при чтении) может испортить внутренние структуры — исключения не будет, будет «странное» поведение. Порядок такой:

  • Только чтение после заполнения — обычный Dictionary подходит: конкурентные чтения безопасны. Чтобы это было видно по типу, наружу отдают IReadOnlyDictionary<TKey, TValue> (глава 6).
  • Изменение из нескольких потоков — ConcurrentDictionary<TKey, TValue>: атомарные операции вместо «прочитать-изменить-записать».
  • Редкие изменения, много чтений — ImmutableDictionary (изменение создаёт новую версию) или FrozenDictionary (.NET 8): оптимизирован под чтение, создаётся один раз при старте.
var cache = new ConcurrentDictionary<int, int>();

Console.WriteLine(cache.GetOrAdd(1, _ => 1));                  // 1 — положил
Console.WriteLine(cache.GetOrAdd(1, _ => 999));                // 1 — уже есть, значение не меняется
Console.WriteLine(cache.AddOrUpdate(1, 10, (_, old) => old + 10));  // 11 — «прочитать и изменить» атомарно
Console.WriteLine(cache.TryRemove(1, out var rm) + " " + rm);   // True 11
Ловушка GetOrAdd

Делегат-фабрика при гонке может быть вызван несколько раз (победит один результат), а в сценариях с Lazy<T> это значит «создание объекта заказали дважды». Поэтому в фабрику не кладут тяжёлых side effect-ов; для дорогой инициализации берут GetOrAdd(key, k => new Lazy<T>(() => …)) и читают .Value.

Куда смотреть дальше: общий разбор «что хорошо / что дорого» и выбор интерфейса для сигнатуры (IReadOnlyDictionary, IReadOnlyList, IEnumerable) — глава 6; множества — глава 10; очереди и стеки — глава 11; связный список — глава 12, и там же, в конце главы 11, — сводная шпаргалка «операция → коллекция» по всей части II.

Чего не делать

  • Не читать d[key], не будучи уверенным, что ключ есть — это KeyNotFoundException, а не null. Сомневаетесь — TryGetValue.
  • Не проверять ContainsKey перед d[key], если нужно само значение: два прохода вместо одного.
  • Не делать ключом изменяемый объект — запись «потеряется» без единой ошибки.
  • Не полагаться на порядок перебора Dictionary и HashSet.
  • Не звать ToDictionary на данных с дублями — ToLookup или GroupBy.
  • Не менять коллекцию во время foreach — InvalidOperationException (глава 13).
  • Не передавать Dictionary между потоками без синхронизации.
★ Что запомнить из главы
  • d[k] = v — upsert, d.Add(k, v) — «только новый» (иначе ArgumentException); чтение отсутствующего ключа индексатором — KeyNotFoundException.
  • Обычный путь чтения — TryGetValue; «отсутствие — норма» — GetValueOrDefault; ContainsKey — только если значение не нужно.
  • Второе слово в GetValueOrDefault — это default(TValue): 0, false, null или обнулённая структура. Поэтому для int и string ответ «ключа нет» неотличим от «есть значение по умолчанию» — там нужен TryGetValue или вторая перегрузка с явным значением.
  • Порядок по ключу — SortedDictionary/SortedList (O(log n) и сравнимые ключи); порядок вставки — List + Dictionary, готового generic-словаря с порядком вставки в .NET 8 нет.
  • Порядок перебора не гарантирован: после удаления элемента порядок вставки уже не соблюдается.
  • Ключ должен быть неизменяемым: мутация ломает GetHashCode, и запись становится недостижимой (и неудаляемой). Правильно — неизменяемый record, ключ-Id или удаление записи до мутации. Одинаковость ключей задаёт IEqualityComparer.
  • Множества и очереди — в следующих главах: HashSet/SortedSet — глава 10, Queue/Stack/PriorityQueue — глава 11.
  • Дубли ключей — ToLookup/GroupBy, а не ToDictionary; запись из нескольких потоков — ConcurrentDictionary, «только чтение» — FrozenDictionary.
