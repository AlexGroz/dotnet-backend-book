SQL · Часть VIII · Миграция из Oracle

Глава 30. Конвертация PL/SQL: пакеты, автономные транзакции, NULL

Три самые болезненные вещи при переносе кода из Oracle. Именно о них спрашивают в интервью.

1. NULL и пустая строка

В Oracle пустая строка '' и NULL — это одно и то же. В PostgreSQL '' — обычная пустая строка, не NULL. Это ломает логику:

  • проверки IS NULL перестают срабатывать для пустых строк;
  • ограничение NOT NULL в PostgreSQL пропустит пустую строку;
  • уникальность: в Oracle '' = NULL, а NULL-ы в уникальном индексе допустимы; в PostgreSQL NULL-ы по умолчанию различны (можно изменить через NULLS NOT DISTINCT, PG15+);
  • конкатенация: NULL || 'x' в Oracle даёт 'x', в PostgreSQL — NULL.
Что делали

Приводили данные при миграции (пустые строки → NULL там, где так было в Oracle), добавляли CHECK (col <> '') или NULLIF(col,'') и переписывали проверки в коде. Ошибки тут «тихие» — проявляются не сразу, поэтому это проверяют тестами эквивалентности (глава 31).

2. PACKAGE — прямого аналога нет

В Oracle пакет — это группа процедур/функций плюс состояние сессии (package variables). В PostgreSQL пакетов нет. Варианты:

  • Схема как пространство имён — группировали функции в схему (pkg_orders.calculate_total(...)).
  • Префиксы в именах функций/процедур, если схема не подходила.
  • Состояние сессии (package variables) эмулировали через временные таблицы или set_config/GUC — либо (правильнее) убирали глобальное состояние.
  • В PostgreSQL 11+ появились настоящие процедуры (CREATE PROCEDURE) с управлением транзакциями — это помогло там, где раньше были только функции.
Честная формулировка для интервью

«Полноценных пакетов в PostgreSQL нет: функции группировали в схемы, а состояние сессии — либо эмулировали, либо избавлялись от него при рефакторинге».

3. PRAGMA AUTONOMOUS_TRANSACTION

Автономная транзакция нужна, когда операция (например, запись в аудит/лог) должна зафиксироваться независимо от основной транзакции — в том числе если основная откатится. В PostgreSQL функции не управляют транзакциями так, как это делал Oracle.

  • Обходной путь: писать через отдельное соединение — расширение dblink (или background worker): это отдельная сессия, значит своя транзакция.
  • Архитектурно лучше: вынести аудит/логирование из транзакции — писать события в очередь (таблица-очередь + фоновый воркер) или в отдельную лог-систему.
  • Формулировка: «точного аналога нет; где-то использовали dblink, где-то меняли архитектуру, чтобы лог не зависел от основной транзакции».
★ Что запомнить

Три «боли» из вопроса: '' ≠ NULL, нет PACKAGE, нет AUTONOMOUS_TRANSACTION. Каждая имеет обходной путь — но об этом надо честно рассказать, а не делать вид, что «переносится один в один».
