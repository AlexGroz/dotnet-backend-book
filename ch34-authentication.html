Глава 34. Аутентификация: JWT, OAuth 2.0 и OpenID Connect

Кто ты: токен, его подпись, срок жизни и ключи — и как это выглядит в ASP.NET Core. Все ответы, заголовки и тексты ошибок в главе получены запуском minimal API на .NET 8.

Путаница между 401 и 403 — самая частая мелочь на ревью: 401 без WWW-Authenticate ломает клиентов, а 403 вместо 401 (и наоборот) сбивает с толку и мониторинг, и фронтенд. Порядок вызовов тоже важен: UseAuthentication обязан идти до UseAuthorization, иначе политики увидят анонимного пользователя.

Payload читается кем угодно

Любой, у кого есть токен, декодирует payload одной строкой (в главе он так и получен). Подпись гарантирует неизменность, но не секретность: пароли, номера карт, ИНН и «внутренние» флаги в claims класть нельзя. Если данные нужны клиенту и не должны читаться посторонними — это уже не JWT, а зашифрованный токен (JWE) или обычный серверный сеанс.

Подключение в ASP.NET Core

Минимум, который нужен API, чтобы принимать токены от известного издателя:

builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(o =>
    {
        o.MapInboundClaims = false;              // имена claims остаются как в JWT
        o.TokenValidationParameters = new TokenValidationParameters
        {
            ValidIssuer = "https://issuer.example",
            ValidAudience = "orders-api",
            IssuerSigningKey = new SymmetricSecurityKey(key),
            ValidateIssuerSigningKey = true,
            NameClaimType = "sub",
            RoleClaimType = "role",
            ClockSkew = TimeSpan.Zero            // по умолчанию 5 минут «запаса»
        };
    });

var app = builder.Build();
app.UseAuthentication();                         // кто ты
app.UseAuthorization();                          // что можно

app.MapGet("/me", (ClaimsPrincipal user) => new
{
    name = user.Identity?.Name,
    sub = user.FindFirst("sub")?.Value,
    role = user.FindFirst("role")?.Value,
    isAdmin = user.IsInRole("admin")
}).RequireAuthorization();

Рабочий ответ этого эндпоинта с валидным токеном:

{"name":"alice","sub":"alice","role":"user","scope":"orders.read","isAdmin":false,
 "authType":"AuthenticationTypes.Federation"}

Что именно проверяется и как это выглядит при отказе

Каждая строка таблицы — реальный ответ стенда: запрос с «неправильным» токеном и заголовок WWW-Authenticate, по которому клиент понимает причину.

СитуацияКодWWW-Authenticate

Подпись чужим ключом401 Bearer error="invalid_token", error_description="The signature key was not found"
Чужая audience401 ... "The audience 'other-api' is invalid"
Истёк срок401 ... "The token expired at '11/26/2026 16:48:25'"
Ещё не действует (nbf)401 ... "The token is not valid before '11/26/2026 18:18:25'"
ClockSkew — тихая настройка на 5 минут

По умолчанию TokenValidationParameters.ClockSkew равно пяти минутам: токен, истёкший минуту назад, всё ещё принимается — это компенсация расхождения часов между серверами. Для тестов и для «строгой» безопасности ставят TimeSpan.Zero, иначе проверка «токен просрочен» на стенде проходит не так, как ожидается. Обратная сторона: без запаса любой дрейф часов у издателя начинает валить легитимные запросы.

Claims и ловушка с их именами

По умолчанию JwtSecurityTokenHandler переименовывает claims в длинные имена .NET: sub → ClaimTypes.NameIdentifier, role → ClaimTypes.Role. Из-за этого код user.FindFirst("sub") возвращает null, хотя claim в токене есть — мы это увидели на стенде: до установки MapInboundClaims = false вывод был sub = (пусто), после — sub = alice.

НастройкаЧто делаетКогда нужна
MapInboundClaims = falseоставляет имена как в токенекод читает "sub", "role", "scope" напрямую
NameClaimTypeкакой claim считать именем пользователя (Identity.Name)обычно sub или preferred_username
RoleClaimTypeкакой claim использовать в IsInRole и RequireRoleесли роль лежит не в ClaimTypes.Role, а в role/roles

Если этого не сделать, «не работает IsInRole» и «claim есть, а FindFirst его не находит» — одна и та же причина. Правило простое: посмотрите, что реально лежит в User.Claims, прежде чем искать баг в политике.

HS256 против RS256: у кого есть право выпускать токены

Симметричная подпись (HS256) означает: один и тот же секрет и подписывает, и проверяет. Значит, любой сервис, который умеет проверять токен, умеет и выпустить себе любой токен — включая role: admin. Проверено на стенде: проверяющая сторона, зная секрет, выпустила себе администраторский токен и успешно его провалидировала.

HS256: проверяющая сторона знает секрет и может выпустить свой токен, role = admin

Асимметричная подпись (RS256) делит роли: приватный ключ есть только у издателя, публичный — у всех, кто проверяет. Приватный ключ нельзя «вычитать» из публичного, поэтому проверяющая сторона не может подделать токен.

using var rsa = RSA.Create(2048);
var privateKey = new RsaSecurityKey(rsa) { KeyId = "kid-2026-11" };   // у издателя
var publicKey  = new RsaSecurityKey(rsa.ExportParameters(false)) { KeyId = "kid-2026-11" }; // у API

var token = new JwtSecurityTokenHandler().WriteToken(new JwtSecurityToken(
    issuer: "https://issuer.example",
    audience: "orders-api",
    claims: new[] { new Claim("sub", "alice"), new Claim("role", "user") },
    expires: DateTime.UtcNow.AddMinutes(5),
    signingCredentials: new SigningCredentials(privateKey, SecurityAlgorithms.RsaSha256)));

Для «взрослой» схемы ключи не хранят в коде: API берёт их из jwks_uri провайдера, кэширует и выбирает по kid из заголовка — именно поэтому kid в примере выставлен. Ротация тогда выглядит так: издатель добавляет новый ключ в JWKS, старые токены живут до exp, потом старый ключ убирают. Без kid смена ключа означает, что все выданные токены разом невалидны.

OAuth 2.0 и OpenID Connect: кто есть кто

Authorization serverвыдаёт токены, проверяет пользователяKeycloak, Entra ID, Duende, Auth0

OAuth 2.0 — про делегированный доступ (access token: «этому клиенту можно читать заказы»). OpenID Connect — надстройка над OAuth, которая добавляет аутентификацию: id_token (JWT с данными о пользователе), эндпоинт /userinfo и документ обнаружения /.well-known/openid-configuration, где перечислены все адреса, включая jwks_uri.

В .NET против реального провайдера конфигурация короче, чем в учебном примере: вместо самодельного ключа указывают Authority, и компонент сам скачивает метаданные и ключи, кэширует их и обновляет по kid:

builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(o =>
    {
        o.Authority = "https://login.example.com/realms/orders";  // OIDC-провайдер
        o.Audience = "orders-api";                                // ожидаемая aud
        o.TokenValidationParameters.ValidAudience = "orders-api";
    });
Как JWT мешает «разлогинить» пользователя

Access token валиден, пока не истёк exp: отозвать его нельзя — API проверяет только подпись и срок. Отсюда три рабочих приёма: короткий TTL (5–15 минут) плюс refresh-токен с ротацией; список отозванных jti в Redis с TTL до exp (глава про Redis и Lua); версия сессии/пользователя в claim, которую API сверяет с БД или кэшем. Если требуется мгновенный logout «как в монолите» — JWT не тот инструмент, нужен серверный сеанс.

★ Чек-лист аутентификации для API
  1. Токен проверяется по iss, aud, подписи и сроку — все четыре проверки включены, ни одна не отключена «чтобы работало».
  2. Ключи — из JWKS провайдера, с kid и ротацией; приватный ключ не лежит в репозитории и не попадает в образ.
  3. Секреты — user-secrets локально, переменные окружения или vault в проде (глава 36).
  4. Access token — 5–15 минут; refresh — с ротацией и отзывом.
  5. 401 отдаётся с WWW-Authenticate, 403 — только после успешной аутентификации.
  6. В логах нет токенов, в URL нет токенов (query string попадает в логи прокси и в историю).
  7. ClockSkew выбран осознанно; в тестах — Zero.
★ Что спросят и как отвечать
  1. «JWT — это шифрование?» — нет, подпись и base64url: payload читается кем угодно, меняться не может. Секреты и PII в claims не кладут.
  2. «Чем access token отличается от id token?» — access нужен API и содержит права (scope), id нужен клиенту и говорит, кто пользователь; отправлять id token в API — ошибка.
  3. «Почему не HS256 между сервисами?» — потому что каждый проверяющий получает право выпускать токены; для нескольких сервисов — RS256/ES256 и публичные ключи.
  4. «Как отозвать JWT?» — никак, если он уже выдан: короткий TTL, refresh с ротацией, blacklist по jti или версия сессии.
  5. «Что проверяет ValidateAudience и зачем?» — что токен выписан именно этому API; без проверки токен, украденный у соседнего сервиса, подходит и к вашему.
