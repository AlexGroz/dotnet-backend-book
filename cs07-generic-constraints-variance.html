Глава 7. Generic глубже: ограничения, вариантность и generic math

Что именно компилятор знает о T, как расширить этот список через where, почему List<string> нельзя отдать туда, где ждут List<object>, и как складывать «числа неизвестного типа».

основная глава

В главе 6 была механика: параметр типа, подстановка, открытый и закрытый тип. Здесь — то, что из этой механики следует на практике. Главная мысль главы в одном предложении: ограничения (where) — единственный способ сообщить компилятору, что у T есть что-то, чего нет у всех типов. Больше о T он не знает ничего.

Отсюда растут три темы, которые обычно спрашивают вместе:

  • Ограничения — что можно пообещать (new(), class, struct, notnull, unmanaged, базовый класс, интерфейс, Enum/Delegate) и что каждое из них разрешает вызвать.
  • Вариантность (in/out) — когда IEnumerable<A> можно подставить вместо IEnumerable<B>, а когда нельзя, и почему.
  • Generic math (C# 11+) — как + и * заработали для параметра типа.

Виды ограничений

Ограничение записывается после параметров типа; их можно комбинировать (правила порядка — в следующем разделе). Сводка — с тем, что каждое разрешает делать внутри generic-кода:

where T : structЗначимый типnew T() (у структур конструктор без параметров есть всегда), T? = Nullable<T>

Проверяются они в момент подстановки: неверный тип-аргумент — ошибка компиляции, а не сюрприз в рантайме. Поэтому ограничение ещё и документация: по сигнатуре IRepository<T> where T : Entity сразу видно, что положат в репозиторий.

Правила записи: порядок и взаимоисключения

У списка ограничений есть жёсткий порядок: сначала «первичное» (class, struct, unmanaged, notnull), затем базовый класс или интерфейсы, и только в конце new(). Нарушения ловятся компилятором:

public class A<T> where T : class, struct { }   // ✘ взаимоисключающие
public class B<T> where T : new(), class { }   // ✘ new() должен быть последним

Вывод компилятора

error CS0449: The 'class', 'struct', 'unmanaged', 'notnull', and 'default' constraints
cannot be combined or duplicated, and must be specified first in the constraints list.
error CS0401: The new() constraint must be the last constraint specified

Правильно так: where T : class, IEntity, new() — первичное, интерфейсы, new(). А ещё ограничение может быть самоссылочным, и это не опечатка:

public static T Max<T>(T a, T b) where T : IComparable<T>   // «T сравним сам с собой»
    => a.CompareTo(b) >= 0 ? a : b;

IComparable<T> вместо IComparable — важно: второй принимает object и требует приведения, а вместе с ним и упаковки для значимых типов (глава 4).

new(), class, struct: что можно вызвать

new() — обещание «есть открытый конструктор без параметров». Почему без него не работает new T() и что говорит CS0304 — разобрано в главе 6; здесь важны три следствия, которые всплывают в реальном коде.

  • Абстрактные классы не проходят. Даже с new() подставить абстрактный тип нельзя — создать объект невозможно, и текст ошибки это прямо называет: 'Shape' must be a non-abstract type with a public parameterless constructor (CS0310).
  • struct уже включает new(). У структур конструктор без параметров есть по определению, поэтому where T : struct разрешает new T() без дополнительного new(), а писать оба сразу бессмысленно (и запрещено).
  • Для value-типов new T() — это нули. Не «созданный объект с логикой», а default по всем полям: new Guid() — пустой GUID, new decimal() — 0. Если конструктор должен что-то заполнять, ограничение new() этого не гарантирует — нужен интерфейс-фабрика.
static T Make<T>() where T : new() => new T();

Console.WriteLine(Make<int>());                 // 0
Console.WriteLine(Make<Guid>());                // 00000000-0000-0000-0000-000000000000
Console.WriteLine(Make<List<int>>().Count);      // 0 — пустой список

Если логика создания обязательна, ограничение заменяют фабрикой: where T : IFactory<T> с методом static abstract T Create() (C# 11) — тогда компилятор требует не «какой-нибудь конструктор», а именно тот, который вы описали.

class против struct — это не «взаимоисключающие украшения», а переключатель того, чем T является внутри generic-кода:

where T : classwhere T : struct
T? означает«может быть null» (ссылка) Nullable<T>
default(T)nullнули
Упаковка при передаче в objectнетесть (глава 4)
new T()только с new()разрешено всегда
Типичный примерIRepository<T> where T : class Nullable<T>, числовые утилиты

notnull — ограничение «только для анализа nullability»: оно ничего не добавляет к возможностям, но запрещает подставлять nullable-типы. Ошибка при этом — предупреждение, а не ошибка сборки:

static void Add<T>(Dictionary<string, T> d, string key, T value) where T : notnull
    => d[key] = value;

var byId = new Dictionary<string, string?>();
Add<string?>(byId, "a", null);        // ⚠ T = string? не подходит

Вывод компилятора (CS8714 — предупреждение)

warning CS8714: The type 'string?' cannot be used as type parameter 'T' in the generic
type or method 'Add<T>(Dictionary<string, T>, string, T)'. Nullability of type
argument 'string?' doesn't match 'notnull' constraint.

Именно notnull стоит в объявлении Dictionary<TKey, TValue> — на ключе: словарь не предназначен для null-ключей, и попытка подставить string? даёт тот же CS8714 уже от имени TKey.

Enum, Delegate, IParsable: ограничение как «умение вызывать»

Три примера, где ограничение даёт не поля и методы экземпляра, а статические члены — именно ради них эти ограничения и существуют.

// 1. Перечисление: структура + Enum. Порядок обязателен: struct первым
static bool IsKnown<T>(T value) where T : struct, Enum => Enum.IsDefined(value);

// 2. Любой делегат: можно разобрать список подписчиков
static int HandlerCount<T>(T handler) where T : Delegate
    => handler.GetInvocationList().Length;

// 3. Всё, что умеет Parse: int, double, DateOnly, Guid, свои типы
static T ParseIt<T>(string text) where T : IParsable<T> => T.Parse(text, null);

Console.WriteLine(IsKnown(Color.Green));       // True
Console.WriteLine(HandlerCount(f));            // 2 — после f += второй подписчик
Console.WriteLine(ParseIt<int>("42"));        // 42
Console.WriteLine(ParseIt<Guid>("00000000-0000-0000-0000-000000000001"));

Как это устроено внутри: Enum, Delegate, IParsable<T> — обычные ограничения на интерфейсы и классы. Работают они потому, что с C# 11 у интерфейсов появились статические абстрактные члены: IParsable<T> требует от типа метод static T Parse(string, IFormatProvider?), и компилятор знает, что его можно вызвать для любого T, подошедшего под ограничение.

Зачем это, если можно передать Func<string, T>

Функцию-парсер можно передать параметром — и до C# 11 так и делали. Ограничение удобнее тем, что не требует лишней лямбды на каждом вызове, работает через JIT без делегата и само появляется в подсказке IDE: ParseIt<Order>(…) не скомпилируется, пока у Order нет static Parse.

Generic math: арифметика на неизвестном типе

До C# 11 «сложить два T» было невозможно: у параметра типа нет операторов. Обходили либо приведением к dynamic (медленно, ошибки в рантайме), либо отдельными методами под каждый числовой тип. Сейчас нужное поведение описывается интерфейсом INumber<T>:

using System.Numerics;

static T Sum<T>(T a, T b) where T : INumber<T> => a + b;
static T Avg<T>(IEnumerable<T> xs) where T : INumber<T>
{
    T sum = T.Zero, count = T.Zero;
    foreach (var x in xs) { sum += x; count++; }
    return sum / count;
}

Console.WriteLine(Sum(1, 2));              // 3      — int
Console.WriteLine(Sum(1.5, 2.5));          // 4      — double
Console.WriteLine(Avg(new[] { 1, 2, 3 })); // 2      — int
Console.WriteLine(Avg(new[] { 1.0, 2.0 }));// 1.5    — double

INumber<T> — «сборная» интерфейсов: в нём и +, и -, и *, и /, и сравнение, и T.Zero/T.One. Если нужна только часть, берут узкое ограничение:

ОграничениеЧто даёт
IAdditionOperators<T,T,T>Только +
IComparisonOperators<T,T,bool><, >, <=, >=
IParsable<T> / ISpanParsable<T> Parse из строки и из Span
INumber<T>Всё вышеперечисленное плюс Zero/One, Abs, Clamp
IBinaryInteger<T> / IFloatingPoint<T> Целочисленное / плавающее подмножество

Кто подходит под INumber<T>: числа — byte…decimal, Half, Int128, BigInteger и, что неожиданно, char (он реализует IBinaryInteger<char>, поэтому Sum('a', 'b') вернёт Ã). Не подходят string, bool, DateTime, Guid. Диагностика зависит от вида типа: для структуры это CS0315 («нет упаковочного преобразования»), для класса — CS0311 («нет ссылочного»), а Sum(1, "a") вообще не даёт вывести T (CS0411). Все три вывода компилятора — в главе 6.

Вариантность: когда IEnumerable<A> можно заменить на IEnumerable<B>

Представьте метод, которому нужен «любой список объектов». Логично отдать ему List<string> — строка ведь объект. Компилятор это запрещает, и вот почему:

List<string> strings = new();
List<object> objects = strings;      // ✘

Вывод компилятора

error CS0266: Cannot implicitly convert type 'System.Collections.Generic.List<string>'
to 'System.Collections.Generic.List<object>'. An explicit conversion exists
(are you missing a cast?)

Запрет правильный: List<object> умеет Add(object). Разреши мы такое приведение, через «список объектов» в действительности строк можно было бы положить число — и получить испорченную коллекцию. Поэтому List<T> инвариантен: подставлять можно только тот же самый T.

Но там, где элемент только читают (или только пишут), направление можно разрешить. Это и есть вариантность, объявленная у интерфейса через out/in:

МодификаторНаправлениеРазрешеноПримеры из BCL
out Tковариантность: T только возвращается IEnumerable<string> → IEnumerable<object> IEnumerable<out T>, IReadOnlyList<out T>, IReadOnlyCollection<out T>, Func<out TResult>
in Tконтравариантность: T только принимается IComparer<object> → IComparer<string> Action<in T>, IComparer<in T>, IEqualityComparer<in T>
нетинвариантность: и принимается, и возвращаетсятолько точное совпадениеList<T>, IList<T>, Dictionary<TKey, TValue>
 
IEnumerable<string> strings = new List<string> { "a" };
IEnumerable<object> objects = strings;                    // ✔ ковариантность

IComparer<object> byObject = Comparer<object>.Default;
IComparer<string> byString = byObject;                    // ✔ контравариантность

Func<string> getString = () => "s";
Func<object> getObject = getString;                       // ✔ результат «расширяется»

Action<object> actObject = o => Console.WriteLine(o);
Action<string> actString = actObject;                     // ✔ параметр «сужается»
actString("ok");                                          // ok

Логика одной фразой: если коллекция только отдаёт элементы, её можно считать коллекцией более общих типов; если только принимает — более узких. Отсюда и правило проектирования из главы 6: возвращайте IEnumerable<T>/IReadOnlyList<T> (они ковариантны), а не List<T>.

Почему Task<T> не вариантна

Task<string> нельзя отдать туда, где ждут Task<object> — это ошибка CS0029. Причина в том, что вариантность объявляют только у интерфейсов и делегатов, а Task<T> — класс. Практический выход: await и приведение результата, либо Task<object> в сигнатуре с самого начала.

Объявить вариантность можно только у интерфейсов и делегатов — у класса это ошибка:

public class MyList<out T> { }              // ✘ класс
public interface IBad<out T> { void Add(T item); }   // ✘ out, но T в параметре

Вывод компилятора

error CS1960: Invalid variance modifier. Only interface and delegate type parameters can be
specified as variant.
error CS1961: Invalid variance: The type parameter 'T' must be contravariantly valid on
'IBad<T>.Add(T)'. 'T' is covariant.
Ковариантность массивов — исключение и ловушка

Массивы в C# ковариантны по ссылочным типам: object[] a = new string[1]; компилируется. Проверка переносится в рантайм, и запись «не того» типа падает:

object[] arr = new string[1];
arr[0] = 42;          // ✘ падение при выполнении

Вывод

Unhandled exception. System.ArrayTypeMismatchException: Attempted to access an element
as a type incompatible with the array.

Именно из-за этого generic-коллекции сделали инвариантными: лучше ошибка компиляции, чем проверка типа на каждой записи.

Ограничения не наследуются сами

Две ошибки, на которые натыкаются при наследовании и переопределении, — и обе про то, что ограничение приходится повторять или, наоборот, не повторять.

Наследник generic-класса обязан повторить ограничения — иначе компилятор не может доказать, что T подходит родителю:

public class Repo<T> where T : Shape { }
public class CircleRepo<T> : Repo<T> { }        // ✘ ограничение потеряли

Вывод компилятора (CS0314)

error CS0314: The type 'T' cannot be used as type parameter 'T' in the generic type or
method 'Repo<T>'. There is no boxing conversion or type parameter conversion from 'T'
to 'Shape'.
public class CircleRepo<T> : Repo<T> where T : Shape { }   // ✔ повторили

А в override и явной реализации интерфейса — наоборот: ограничения наследуются от базового метода, и указывать их заново нельзя (исключение — class/ struct, их разрешено уточнять):

public class Base
{
    public virtual void Run<T>(T x) where T : IComparable<T> { }
}

public class Derived : Base
{
    public override void Run<T>(T x) where T : IComparable<T> { }   // ✘ повтор
}

Вывод компилятора (CS0460)

error CS0460: Constraints for override and explicit interface implementation methods are
inherited from the base method, so they cannot be specified directly, except for either a
'class', or a 'struct' constraint.

В C# 9 к этому добавили where T : default — пометку «здесь ограничение не задаётся», чтобы такие методы можно было писать явно.

Ловушки

  • where T : Enum без struct компилируется, но бесполезен. Ограничение на класс Enum пропускает и System.Enum с его наследниками, но «значимости» не гарантирует — и первый же Enum.IsDefined(value) не собирается:
static bool IsKnown<T>(T value) where T : Enum => Enum.IsDefined(value);   // ✘

Вывод компилятора (CS0453)

error CS0453: The type 'T' must be a non-nullable value type in order to use it as
parameter 'TEnum' in the generic type or method 'Enum.IsDefined<TEnum>(TEnum)'

Правильно — where T : struct, Enum (и именно в таком порядке, struct первым).

  • new() не означает «с настроенным объектом». Для значимых типов new T() — это нули, для классов — результат конструктора по умолчанию. Проверок инвариантов он не даёт.
  • notnull — предупреждение, а не запрет. Код скомпилируется, если отключить предупреждения; на валидацию данных это ограничение не заменяет.
  • Ограничение-интерфейс не гарантирует отсутствие упаковки. Вызов a.CompareTo(b) внутри generic-метода идёт без бокса, но (object)a или необобщённый IComparable — уже упаковка (глава 4).
  • Вариантность не «разрешает всё». IEnumerable<string> → IEnumerable<object> можно, List<string> → List<object> нельзя, а массивы хоть и ковариантны, но падают в рантайме.
  • Ограничения проверяются при подстановке, а не при объявлении. Ошибка появится в месте вызова Max<object>(…), а не в объявлении Max.
★ Что запомнить из главы
  • Ограничение — это обещание компилятору, что у T есть нужное. Без ограничений о T известно только «совместим с object»: работает default(T), Equals, хранение и передача.
  • new() даёт new T(); struct подразумевает его; абстрактный тип не подставить (CS0310); для структур new T() — нули.
  • class/struct решают, чем будет T?: ссылкой или Nullable<T>. notnull — про анализ nullability (предупреждение CS8714).
  • Порядок в списке: первичное (class, struct, unmanaged, notnull) → базовый класс/интерфейсы → new() последним (CS0449, CS0401).
  • Enum — только вместе с struct, иначе Enum.IsDefined не собирается (CS0453).
  • Generic math — INumber<T> (C# 11): + - * /, сравнение, T.Zero. Узкие интерфейсы (IAdditionOperators, IParsable) — когда нужна одна операция.
  • Вариантность: out — «только отдаёт» (ковариантность), in — «только принимает» (контравариантность); только у интерфейсов и делегатов (CS1960), направление нарушить нельзя (CS1961). List<T> инвариантен.
  • Ограничения не наследуются: наследник generic-класса их повторяет (CS0314), а override и явная реализация — нет (CS0460).
