Глава 25. Кэширование

Кэш — самый быстрый способ ускорить сервис и самый быстрый способ отдать неправильные данные. Разберём уровни, паттерны, инвалидацию и главную аварию — «cache stampede».

основная глава

Зачем кэш и когда он не нужен

Кэш обменивает свежесть данных на скорость. Он уместен, когда:

  • данные читают часто, а меняют редко (справочники, тарифы, конфигурация);
  • вычисление дорого: тяжёлый агрегат, несколько соединений, вызов внешнего API;
  • источник плохо масштабируется: одна база на десять реплик сервиса.

И не нужен, когда:

  • данные обязаны быть точными в момент чтения (баланс, остаток, статус платежа) — здесь кэш только добавит ошибок;
  • источник и так быстрый (индексный запрос за 1 мс) — кэш будет медленнее: сеть до Redis, сериализация;
  • нет способа корректно инвалидировать: «мёртвые» данные хуже медленных.
Правило, которое экономит нервы

Кэш никогда не должен быть единственным источником данных. Если Redis очистили, сервис обязан продолжить работать (медленнее), а не отдать 500.

Уровни: где именно живёт кэш

УровеньГдеСкорость / объёмОсобенность
L1 — в процессе (IMemoryCache)память вашего сервиса наносекунды, мегабайтыу каждой реплики свой кэш: инвалидация не доходит до других (гл. 28)
L2 — общий (Redis, Memcached)отдельный сервисдоли миллисекунды, гигабайтыобщий для всех реплик; сеть и сериализация — плата
HTTP-кэш (CDN, прокси)между клиентом и сервисом очень быстро для клиентауправляется заголовками: Cache-Control, ETag, Vary
Кэш в БДматериализованные представления, кэш планов быстро, но это БДобновляется по расписанию (REFRESH) — SQL-раздел

Типичная схема «на вырост»: L1 перед L2, оба с коротким TTL. L1 снимает нагрузку с Redis, L2 делает данные общими для реплик.

Три паттерна работы с кэшем

ПаттернКак работаетКогда брать
Cache-aside (самый частый)код сначала спрашивает кэш; промах → читаем источник и кладём в кэшчтение с БД/внешнего API; вы контролируете и чтение, и запись
Read-throughкэш сам ходит в источник при промахе (библиотека/прокси) когда источник инкапсулирован в кэш-слое
Write-through / write-behindпишем в кэш и в источник (или сначала в кэш, потом асинхронно в источник)нужна запись через кэш; write-behind рискован — можно потерять данные
// cache-aside: классическая схема «прочитай кэш → промах → источник → положи»
public async Task<Tariff> GetTariffAsync(int id, CancellationToken ct)
{
    var key = $"tariff:v3:{id}";                       // v3 — версия формата ключа (см. ниже)

    if (_cache.TryGetValue(key, out Tariff? cached))    // 1) пробуем кэш
        return cached!;

    var tariff = await _db.Tariffs.AsNoTracking()       // 2) промах: читаем источник
        .FirstAsync(t => t.Id == id, ct);

    _cache.Set(key, tariff, TimeSpan.FromMinutes(5));   // 3) кладём с TTL
    return tariff;
}

Код: IMemoryCache и IDistributedCache

// L1: в памяти процесса. Регистрируется как singleton
builder.Services.AddMemoryCache();

public sealed class TariffCache(IMemoryCache cache)
{
    public Tariff? Get(int id) =>
        cache.TryGetValue($"tariff:v3:{id}", out Tariff? t) ? t : null;

    public void Put(int id, Tariff tariff)
    {
        // AbsoluteExpirationRelativeToNow — умрёт через 5 минут
        // SlidingExpiration — умрёт через 2 минуты ПОСЛЕ последнего обращения
        // Size + SizeLimit — чтобы кэш не съел всю память процесса
        cache.Set($"tariff:v3:{id}", tariff, new MemoryCacheEntryOptions
        {
            AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5),
            SlidingExpiration = TimeSpan.FromMinutes(2),
            Size = 1
        });
    }
}
// L2: Redis через IDistributedCache (пакет Microsoft.Extensions.Caching.StackExchangeRedis)
builder.Services.AddStackExchangeRedisCache(o =>
{
    o.Configuration = "redis:6379";            // адрес Redis (в compose/k8s — имя сервиса)
    o.InstanceName = "orders:";                 // префикс ключей: один Redis на несколько сервисов
});

public sealed class TariffStore(IDistributedCache cache)
{
    public async Task<Tariff?> GetAsync(int id, CancellationToken ct)
    {
        var json = await cache.GetStringAsync($"tariff:v3:{id}", ct);   // байты → строка
        return json is null ? null : JsonSerializer.Deserialize<Tariff>(json);
    }

    public Task SetAsync(int id, Tariff tariff, CancellationToken ct) =>
        cache.SetStringAsync($"tariff:v3:{id}", JsonSerializer.Serialize(tariff), ct,
            new DistributedCacheEntryOptions
            {
                AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5)
            });
}
L1 перед L2: как не удвоить сложность

Если кэшей два, порядок всегда один и тот же: L1 → L2 → источник, а запись — в оба. Проблема: у каждой реплики свой L1, поэтому инвалидация должна либо рассылаться (pub/sub в Redis), либо быть не нужной — за счёт очень короткого TTL в L1 (5–30 секунд). Второй вариант проще и почти всегда достаточен.

Инвалидация: три способа не отдавать вчерашние данные

  1. TTL (время жизни). Самый простой и надёжный: данные «просрочились» — перечитали. Плата — до TTL вы можете отдавать старое значение. Для справочников это нормально; для остатков — нет.
  2. Версия в ключе. Меняется формат/логика — меняйте v3 на v4: старые ключи просто перестанут читаться и умрут по TTL. Это спасает от «после деплоя в кэше лежит объект старой структуры».
  3. Событийная инвалидация. При записи в БД удаляем/обновляем ключ (в той же транзакции — нельзя: кэш не транзакционный; поэтому делают после коммита или через outbox, гл. 31).
// запись: сначала БД, потом кэш (и только после успешного коммита)
await _db.SaveChangesAsync(ct);
await _cache.RemoveAsync($"tariff:v3:{tariff.Id}", ct);   // или PutAsync с новым значением
Порядок «кэш → БД» — источник расхождений

Если удалить кэш до коммита, параллельное чтение успеет положить туда старое значение, и оно останется до TTL. Поэтому: сначала БД, затем сброс кэша. А между этими шагами всё равно есть окно — поэтому TTL обязателен даже при событийной инвалидации.

Cache stampede: когда кэш «кончился» у всех одновременно

Классический сценарий: популярный ключ истёк, и все запросы одновременно пошли в базу. Тысяча запросов вместо одного — база ложится именно в тот момент, когда кэш должен был её спасать.

// «single flight»: источник читает ТОЛЬКО первый запрос, остальные ждут его результата
private static readonly ConcurrentDictionary<string, SemaphoreSlim> Locks = new();

public async Task<Tariff> GetAsync(int id, CancellationToken ct)
{
    var key = $"tariff:v3:{id}";
    if (_memory.TryGetValue(key, out Tariff? hit)) return hit!;

    var gate = Locks.GetOrAdd(key, _ => new SemaphoreSlim(1, 1));
    await gate.WaitAsync(ct);
    try
    {
        if (_memory.TryGetValue(key, out hit)) return hit!;      // второй раз: мог положить «первый»

        var tariff = await LoadFromDbAsync(id, ct);              // в базу идёт один запрос
        _memory.Set(key, tariff, TimeSpan.FromMinutes(5));
        return tariff;
    }
    finally
    {
        gate.Release();
        Locks.TryRemove(key, out _);                             // не копим семафоры по ключам
    }
}
  • Jitter в TTL (5 мин ± 30 с) — ключи не истекают синхронно.
  • Stale-while-revalidate: отдаём старое значение, пока в фоне обновляем. Свежесть «догоняет» без всплеска.
  • Прогрев после деплоя: заранее положить горячие ключи (гл. 28 — прогрев реплики).

Что кэшировать и что нельзя

КэшируемНе кэшируем (или только с оговорками)
справочники, тарифы, конфигурация, категориибаланс, остаток на складе, статус платежа — нужны точные данные
результаты тяжёлых агрегатов (отчёты за день)персональные данные без изоляции ключа по пользователю/тенанту
ответы внешних API с известным TTLсекреты, токены, содержимое, которое нельзя терять
«горячие» товары/страницы — общие для всехрезультаты, зависящие от прав доступа, если ключ не учитывает пользователя
Кэш — не хранилище

Всё, что лежит в кэше, должно восстанавливаться из источника. Если данные существуют только в Redis, то очистка Redis (или вытеснение по памяти) — это потеря данных, а не «замедление».

Ключи, сериализация, размер

  • Ключ — стабильный и полный: tariff:v3:{id}, а не "tariff" + id в разных местах по-разному. Всё, что влияет на результат (язык, tenant, валюта), должно быть в ключе.
  • Версия в ключе (v3) — бесплатная защита от несовместимого формата после деплоя.
  • Сериализация: JSON — читаемо и совместимо; для больших значений — сжатие (gzip/brotli) или более компактный формат. Помните: сериализация тоже стоит CPU.
  • Размер значения: кэшируйте проекцию (нужные поля), а не всю сущность с навигациями — иначе получите мегабайты на ключ и медленный десериализатор.
  • Кэширование «пусто»: если результата нет, кэшируйте маркер (например, null как "__none__"), иначе промахи будут бить в базу каждый раз.

Как понять, что кэш работает

  • Hit ratio — доля попаданий. 0,9 для справочника — норма; 0,3 значит, что вы кэшируете то, что почти всегда разное.
  • Задержка p95 с кэшем и без (гл. 21): если «с кэшем» не быстрее — кэш не нужен или неправильно выбран уровень.
  • Нагрузка на источник (QPS к БД, к внешнему API): упала в разы — работает.
  • Ошибки Redis и время ответа: кэш, который тормозит, хуже отсутствия кэша — поэтому у него тоже нужны таймауты (гл. 27).

★ Что запомнить из главы
  • Кэш меняет свежесть на скорость; он не нужен для точных в момент чтения данных и для быстрых источников.
  • Уровни: L1 (память процесса, свой у каждой реплики), L2 (Redis, общий), HTTP/CDN, кэш в БД.
  • Cache-aside — базовая схема: кэш → промах → источник → кэш.
  • Инвалидация: TTL обязателен, версия в ключе — дёшево, событийная — после коммита.
  • Cache stampede лечится single-flight, jitter и stale-while-revalidate.
  • Кэш никогда не единственный источник; hit ratio и p95 показывают, полезен ли он.
