A02. Криптография: пароли, целостность, ключи

Пароли не шифруют и не хешируют «просто SHA256»: нужна медленная функция с солью. В .NET это PBKDF2 (Rfc2898DeriveBytes.Pbkdf2) — встроенный, без пакетов. Замер на этой машине:

var salt = RandomNumberGenerator.GetBytes(16);                  // соль на пользователя

var hash = Rfc2898DeriveBytes.Pbkdf2(
    password: "correct horse battery staple",
    salt: salt,
    iterations: 210_000,                                        // рекомендация OWASP для SHA256
    hashAlgorithm: HashAlgorithmName.SHA256,
    outputLength: 32);

// проверка — за постоянное время, без короткого замыкания
var ok = CryptographicOperations.FixedTimeEquals(stored, candidate);
PBKDF2-SHA256,  100000 итераций:   19 мс, хеш 93D89F64A2C7FA30…
PBKDF2-SHA256,  210000 итераций:   39 мс, хеш D7D9B21ED7180D41…
PBKDF2-SHA256,  600000 итераций:  112 мс, хеш B46175684E906067…
FixedTimeEquals (верный пароль): True
FixedTimeEquals (неверный пароль): False

39 мс на проверку — незаметно для пользователя и смертельно для перебора: миллион попыток это больше десяти часов на одном ядре. Число итераций хранят рядом с хешем (например, pbkdf2$210000$salt$hash), чтобы его можно было поднять без сброса всех паролей. Ещё лучше — Argon2id (пакет Konscious.Security.Cryptography.Argon2), если он доступен.

Для данных, которые надо именно шифровать, берут аутентифицированное шифрование — AES-GCM: оно ловит и подмену байта шифротекста, и подмену тега.

using var aes = new AesGcm(key, tagSizeInBytes: 16);
aes.Encrypt(nonce, plaintext, cipher, tag);

// попытка расшифровать изменённый шифротекст
aes.Decrypt(nonce, tampered, tag, restored);
AES-GCM: шифротекст 41 байт, тег 4024F04602C599E7…
AES-GCM с изменённым байтом: AuthenticationTagMismatchException
Чего не делать никогда
  • MD5/SHA1/SHA256 без соли и растяжения — для паролей.
  • Свой «шифр» из XOR/Base64: Base64 — это кодирование, а не защита.
  • Один AES-ключ на всё приложение, без KMS/vault и ротации.
  • Сравнение секретов через == — только FixedTimeEquals.
  • HTTP внутри периметра: TLS везде, включая сервис-сервис.

A03. Инъекции: SQL

Стенд: PostgreSQL 16 в контейнере, таблица app_users из трёх строк (alice, bob, root с ролью admin). Запрос собирается склейкой строк — так, как это обычно и появляется в коде «для отчёта».

var injected = "' OR '1'='1' --";
var sql = $"SELECT id, email, role FROM app_users WHERE email = '{injected}'";
SQL: SELECT id, email, role FROM app_users WHERE email = '' OR '1'='1' --'
склейка + вредоносный ввод: 3 строк
   id=1 email=alice@example.com role=user
   id=2 email=bob@example.com role=user
   id=3 email=root@example.com role=admin
склейка + обычный ввод: 1 строк
   id=1 email=alice@example.com role=user
склейка + апостроф в данных: 42601 syntax error at or near "brien"
параметр + вредоносный ввод: 0 строк

Четыре вывода из одного запуска:

  • Инъекция вернула все строки, включая администратора, — типичная утечка через авторизацию/логин.
  • Тот же код с нормальным e-mail работает «правильно» — поэтому баг и живёт незамеченным.
  • Обычный апостроф в данных (o'brien@example.com) ломает запрос с ошибкой 42601: если приложение показывает текст ошибки, оно ещё и рассказывает структуру запроса.
  • Параметризованный запрос с тем же вредоносным вводом вернул 0 строк: значение ушло отдельно от текста SQL.
// EF Core: интерполяция в FromSqlRaw — это склейка, а не параметр
var bad = db.Users.FromSqlRaw($"SELECT id, email, role FROM app_users WHERE email = '{injected}'").ToList();

// FromSqlInterpolated превращает интерполяцию в параметры
var good = db.Users.FromSqlInterpolated($"SELECT id, email, role FROM app_users WHERE email = {injected}").ToList();
EF FromSqlRaw со склейкой: 3 строк
   id=1 email=alice@example.com role=user
   id=2 email=bob@example.com role=user
   id=3 email=root@example.com role=admin
EF FromSqlInterpolated: 0 строк
Почему анализатор ругается на FromSqlRaw

FromSqlRaw принимает строку — если в неё попала интерполяция, она уже склеена до вызова, и EF не может ничего параметризовать. Отсюда предупреждение EF1002 («possible SQL injection») и правило: либо FromSqlInterpolated/FromSql, либо FromSqlRaw с явными NpgsqlParameter. Динамические части — имена таблиц, направление сортировки, список колонок — параметрами не передать: их сверяют с белым списком.

A03. Инъекции: HTML и XSS

Razor и HtmlEncoder экранируют по умолчанию — уязвимость появляется там, где экранирование обошли руками (Html.Raw, @((MarkupString)…), конкатенация HTML в ContentResult). Вывод стенда с одной и той же строкой <script>alert(1)</script>:

### B2: сырой HTML (уязвимо)
<p>Привет, <script>alert(1)</script></p>
### B3: HTML-кодирование
<p>Привет, &lt;script&gt;alert(1)&lt;/script&gt;</p>
### B4: JSON (экранирование внутри JSON)
{"message":"<script>alert(1)</script>"}

JSON-ответ вернул строку как есть: System.Text.Json по умолчанию экранирует только то, что обязательно для JSON (кавычки, управляющие символы), но не <. Это нормально и правильно — экранировать должен тот, кто вставляет данные в HTML; React это делает сам, а dangerouslySetInnerHTML — нет. Отдельный риск — CSP и заголовки (ниже), которые ловят XSS, если экранирование где-то пропустили.

CSRF: почему cookie-аутентификации нужен токен

Cookie браузер прикладывает к запросу автоматически, в том числе к запросу с чужого сайта. Защита — antiforgery: сервер выдаёт cookie и требует тот же токен в заголовке (двойная отправка). Проверка на стенде с эндпоинтом перевода:

builder.Services.AddAntiforgery(o => o.HeaderName = "X-CSRF-TOKEN");
app.UseAntiforgery();

app.MapPost("/transfer", (HttpContext ctx) => "перевод выполнен").RequireAntiforgery();
### B5: POST без CSRF-токена, но с cookie
"CSRF: The required antiforgery header value \"X-CSRF-TOKEN\" is not present."  [400]
### B6: POST с заголовком X-CSRF-TOKEN
"перевод выполнен"  [200]
### B7: POST с чужим токеном
"CSRF: The antiforgery token could not be decrypted."  [400]

Cookie сама по себе запрос не пропускает (B5), подделанный токен не расшифровывается (B7) — чужой сайт не может прочитать токен из вашего домена. Если API аутентифицирует по Authorization: Bearer, CSRF ему не страшен: браузер не добавляет заголовок автоматически. Именно поэтому «JWT в заголовке» и «antiforgery» — альтернативы, а не «оба на всякий случай».

A05. Неверная конфигурация: заголовки и секреты

Минимальный набор заголовков, который отдавал стенд после добавления middleware:

app.Use(async (ctx, next) =>
{
    var h = ctx.Response.Headers;
    h["X-Content-Type-Options"] = "nosniff";            // не угадывать MIME
    h["X-Frame-Options"] = "DENY";                      // запрет встраивания в iframe
    h["Referrer-Policy"] = "no-referrer";               // не утекает URL с токеном
    h["Content-Security-Policy"] = "default-src 'none'; frame-ancestors 'none'";
    await next();
});
### B1: заголовки безопасности
X-Content-Type-Options: nosniff
X-Frame-Options: DENY
Referrer-Policy: no-referrer
Content-Security-Policy: default-src 'none'; frame-ancestors 'none'

CSP default-src 'none' — это заголовок для API (HTML тут не отдаётся). Для страниц политика мягче и подбирается под фронтенд: script-src 'self', без 'unsafe-inline'. Часть заголовков умеет ставить app.UseHsts() и UseHttpsRedirection(), но CSP и X-Frame-Options обычно добавляют явно или на прокси.

Секреты. На стенде в appsettings.json ключа Jwt не было вовсе; проверялись два штатных источника:

$ grep -c 'Jwt' appsettings.json
0
$ dotnet user-secrets init
Set UserSecretsId to '81501c06-b9d3-4a8d-92e2-7d1b7691a915' for MSBuild project 'web.csproj'.
$ dotnet user-secrets set 'Jwt:Key' 'super-secret-from-user-secrets-123456'
Successfully saved Jwt:Key = super-secret-from-user-secrets-123456 to the secret store.

$ grep -n 'UserSecretsId' web.csproj
7:    <UserSecretsId>81501c06-b9d3-4a8d-92e2-7d1b7691a915</UserSecretsId>

$ curl -s http://127.0.0.1:5082/secret
env=Development; Jwt:Key=super-secret…

Файл секретов лежит вне репозитория (~/.microsoft/usersecrets/<id>/secrets.json) и подключается только в Development. В контейнере тот же ключ приходит переменной окружения с двойным подчёркиванием вместо двоеточия:

$ Jwt__Key=from-environment-variable-abcdef dotnet run --no-build
$ curl -s http://127.0.0.1:5082/secret
env=Development; Jwt:Key=from-environ…
Секрет в appsettings.json — это уже утечка

Файл попадает в git, в образ, в логи сборки и в бэкапы. Правило: в appsettings.json — только несекретные значения и пустые заготовки; локально — user-secrets; в Kubernetes/проде — переменные окружения из Secret’ов или внешний vault. И помните про порядок источников конфигурации: переменная окружения перекрывает appsettings.json, поэтому «почему в проде не тот ключ» обычно объясняется именно этим.

A08. Небезопасная десериализация

Классика — TypeNameHandling.All в Newtonsoft.Json: JSON может указать, какой тип создать, и сериализатор создаст его вместе с конструктором. На стенде «полезная нагрузка» указывала на класс с побочным эффектом в конструкторе:

var settings = new JsonSerializerSettings { TypeNameHandling = TypeNameHandling.All };
var money = JsonConvert.DeserializeObject<Money>(attackerJson, settings);
файл до разбора: False
TypeNameHandling.All: создан SideEffect
файл после разбора: True
без TypeNameHandling: Money, amount = 0
System.Text.Json: Money, amount = 0
--- содержимое файла ---
конструктор выполнен

Один разбор JSON — и выполнился чужой конструктор; в реальной атаке там оказывается цепочка известных типов, приводящая к запуску процесса. Те же данные без TypeNameHandling и в System.Text.Json остались безобидным объектом: $type игнорируется, потому что полиморфизм по имени типа там не включён по умолчанию.

Правила для десериализации
  • TypeNameHandling.All/Auto/Objects — запрещены для данных извне; если очень нужно — SerializationBinder с белым списком типов.
  • System.Text.Json + [JsonPolymorphic] с явными [JsonDerivedType] — полиморфизм только по разрешённым типам (глава 24).
  • Ограничивайте размер тела запроса и глубину вложенности: «JSON-бомба» роняет процесс по памяти.
  • Не десериализуйте в типы с побочными эффектами в конструкторах и сеттерах.

A06, A09, A10: зависимости, логи, SSRF

A06. Уязвимые зависимости ищут командой, а не глазами:

$ dotnet list package --vulnerable --include-transitive
The following sources were used:
   https://api.nuget.org/v3/index.json

The given project `api` has no vulnerable packages given the current sources.

На стенде — пусто. Команда смотрит в те же фиды, откуда ставятся пакеты (приватный фид добавляют флагом --source), и её стоит запускать в CI, а не «раз в год»: она же проверяет транзитивные зависимости, которые вы сами не выбирали.

A09. Логи — тоже канал утечки. Токен в строке запроса попадает в логи прокси, историю браузера и Referer; тело запроса с паролем — в трейс исключения. Что делать: токены только в заголовке, в логах — идентификаторы (sub, jti) вместо значений, редактор для чувствительных полей, отдельный аудит-лог на доступ к чужим данным (кто, что, когда, с какого IP).

A10. SSRF — когда сервер сам идёт по URL из запроса: «загрузите аватар по ссылке». Минимум защиты:

var uri = new Uri(requestedUrl);
if (uri.Scheme is not ("http" or "https")) return Results.BadRequest();
if (!allowedHosts.Contains(uri.Host)) return Results.BadRequest();          // белый список

var ip = (await Dns.GetHostAddressesAsync(uri.Host)).First();
if (IPAddress.IsLoopback(ip) || ip.IsIPv6LinkLocal) return Results.BadRequest();
// плюс запрет 10/8, 172.16/12, 192.168/16, 169.254.169.254 (cloud metadata)

Проверка «по строке» недостаточна: DNS может вернуть внутренний адрес, а редирект — увести на 169.254.169.254. Надёжнее — резолвить имя и проверять адрес, запрещать редиректы (AllowAutoRedirect = false) и ходить через прокси с политикой egress.

★ Чек-лист: 10 пунктов на ревью
  1. Все SQL-запросы параметризованы; FromSqlRaw — только с явными параметрами; динамические имена — по белому списку.
  2. Пароли — PBKDF2 (≥210 000 итераций) или Argon2id; сравнение — FixedTimeEquals.
  3. Для шифрования — AES-GCM; ключи в vault/KMS, с ротацией.
  4. HTML собирается шаблонизатором; Html.Raw/dangerouslySetInnerHTML — под ревью и только с санитайзером.
  5. Cookie-аутентификация — с antiforgery; Bearer-аутентификация — без CSRF, но с CSP.
  6. Заголовки nosniff, X-Frame-Options, Referrer-Policy, CSP включены.
  7. Секретов нет в appsettings.json и в git; локально — user-secrets, в проде — env/Secrets.
  8. dotnet list package --vulnerable --include-transitive в CI; обновления не реже раза в месяц.
  9. Десериализация — System.Text.Json; TypeNameHandling запрещён, размер тела ограничен.
  10. Исходящие запросы по пользовательскому URL — белый список хостов, проверка IP, без авторедиректов.
★ Что спросят и как отвечать
  1. «Как защититься от SQL-инъекций?» — параметры вместо склейки; в EF — FromSqlInterpolated/LINQ; плюс минимальные права пользователя БД.
  2. «XSS: где экранировать?» — на выходе, в контексте HTML; Razor/React делают это по умолчанию, ломают — Raw/dangerouslySetInnerHTML; CSP — вторая линия.
  3. «Зачем antiforgery, если есть JWT?» — при Bearer-токене не нужен; нужен при cookie, потому что браузер прикладывает cookie к чужим запросам.
  4. «Чем опасен TypeNameHandling.All?» — JSON выбирает тип, создаётся объект с побочными эффектами в конструкторе → RCE; на стенде файл создался при разборе.
  5. «Как хранить секреты?» — user-secrets локально, переменные окружения/Secrets в проде, vault для критичных; appsettings.json — только несекретное.
  6. «Как понять, что зависимость уязвима?» — dotnet list package --vulnerable --include-transitive и автоматические PR от Dependabot/Renovate.
