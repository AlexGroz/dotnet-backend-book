Глава 6. Декоратор: добавить поведение, не меняя класс

Кэш, логи, метрики и ретраи поверх готового сервиса — без правки этого сервиса и без «класса на каждую комбинацию».

основная глава

Разминка: идея на десяти строках

Нужно добавить к готовому сервису логирование, не меняя сервис. Обёртка того же интерфейса:

public interface IGreeter { string Greet(string name); }

public sealed class Greeter : IGreeter                  // «настоящая» работа
{
    public string Greet(string name) => $"Привет, {name}!";
}

public sealed class TimedGreeter : IGreeter             // обёртка: тот же интерфейс
{
    private readonly IGreeter _inner;                   // кого оборачиваем
    public TimedGreeter(IGreeter inner) => _inner = inner;

    public string Greet(string name)
    {
        var started = DateTime.UtcNow;                      // до
        var result = _inner.Greet(name);                    // делегировали работу
        Console.WriteLine($"заняло {DateTime.UtcNow - started}");
        return result;                                      // после
    }
}

IGreeter greeter = new TimedGreeter(new Greeter());
Console.WriteLine(greeter.Greet("Алексей"));

Что окажется на консоли

заняло 00:00:00.0001234     ← печатает обёртка (время, конечно, будет своё)
Привет, Алексей!            ← печатает внешний Console.WriteLine

Снаружи ничего не изменилось: тип тот же (IGreeter), а поведение дополнилось. Дальше — кэш поверх репозитория и HTTP-handler'ы, где этот приём работает в .NET.

Проблема: комбинации разрастаются

Есть репозиторий, и со временем к нему хочется добавить кэш, логирование и метрики. Через наследование получается так:

Это не код и не using — это просто список классов, которые пришлось бы написать

EfProductRepository
CachedProductRepository
LoggingProductRepository
CachedLoggingProductRepository
CachedAndMetricsProductRepository
…                        ← каждая новая «добавка» удваивает число классов

Читается так: сначала класс про EF, потом его копия с кэшем, потом копия с логами, потом копия, где и кэш, и логи… Каждая новая «добавка» требует новой копии класса — вот почему наследование здесь не масштабируется.

Хуже того: логика кэша дублируется в каждом таком классе, а бизнес-код начинает зависеть от конкретного типа, а не от интерфейса.

Решение: обёртка того же интерфейса

Декоратор реализует тот же интерфейс, что и оборачиваемый объект, и вызывает его внутри. Внешний код не знает, что получил обёртку.

public interface IProductRepository
{
    Task<Product?> GetAsync(Guid id, CancellationToken ct);
    Task SaveAsync(Product product, CancellationToken ct);
}

// «Настоящая» реализация — про БД, и только про БД
public sealed class EfProductRepository(AppDbContext db) : IProductRepository
{
    public Task<Product?> GetAsync(Guid id, CancellationToken ct) =>
        db.Products.AsNoTracking().FirstOrDefaultAsync(p => p.Id == id, ct);

    public async Task SaveAsync(Product product, CancellationToken ct)
    {
        db.Products.Update(product);
        await db.SaveChangesAsync(ct);
    }
}

// Декоратор: кэш, который ничего не знает про EF
public sealed class CachedProductRepository(
    IProductRepository inner,
    IMemoryCache cache) : IProductRepository
{
    public async Task<Product?> GetAsync(Guid id, CancellationToken ct)
    {
        var key = $"product:{id}";
        if (cache.TryGetValue<Product>(key, out var cached))
            return cached;                       // попадание в кэш

        var product = await inner.GetAsync(id, ct);   // промах → идём внутрь
        if (product is not null)
            cache.Set(key, product, TimeSpan.FromMinutes(5));
        return product;
    }

    public async Task SaveAsync(Product product, CancellationToken ct)
    {
        await inner.SaveAsync(product, ct);      // сначала пишем в БД
        cache.Remove($"product:{product.Id}");   // и инвалидируем кэш
    }
}

Сборка «слоёного» сервиса — простое оборачивание: сначала настоящий, потом кэш.

// 1) «настоящая» реализация: только про базу
builder.Services.AddScoped<EfProductRepository>();

// 2) декоратор — тоже обычный класс, его можно зарегистрировать
builder.Services.AddScoped<CachedProductRepository>();

// 3) сборка цепочки: кто просит IProductRepository, получит кэш поверх базы
builder.Services.AddScoped<IProductRepository>(sp =>
    new CachedProductRepository(
        sp.GetRequiredService<EfProductRepository>(),   // ← кого оборачиваем
        sp.GetRequiredService<IMemoryCache>()));         // ← зависимость декоратора

Читается так: «на IProductRepository отдаём CachedProductRepository, а внутри у него — EfProductRepository». Добавить логи — ещё одна обёртка в этой же строке, остальной код не меняется.

Почему это лучше
  • Нет комбинаций: добавили логи — обернули ещё раз, порядок слоёв виден в коде.
  • Каждый слой про одно: репозиторий — про БД, декоратор — про кэш.
  • Тесты: подменяем декоратор «пустым» (или тестовым) и проверяем бизнес-логику без базы.

Декоратор, который .NET даёт «из коробки»: HttpMessageHandler

Конвейер HttpClient — это цепочка декораторов: каждый обработчик получает следующий и может добавить поведение. Логирование, заголовки, ретраи — типовые декораторы.

public sealed class RequestLoggingHandler(ILogger<RequestLoggingHandler> logger)
    : DelegatingHandler
{
    protected override async Task<HttpResponseMessage> SendAsync(
        HttpRequestMessage request, CancellationToken ct)
    {
        var sw = Stopwatch.StartNew();
        try
        {
            return await base.SendAsync(request, ct);        // внутрь цепочки
        }
        finally
        {
            logger.LogInformation("{Method} {Uri} — {Elapsed} мс",
                request.Method, request.RequestUri, sw.ElapsedMilliseconds);
        }
    }
}

builder.Services.AddHttpClient("payments")
    .AddHttpMessageHandler<RequestLoggingHandler>();        // обернули клиент

Где ещё это работает в .NET

СлойДекораторыЧто добавляют

HttpClientDelegatingHandlerЗаголовки, логи, ретраи, трейсинг
TextReader/StreamReaderобёртки над потокомКодировку, чтение строками
Ваш сервискэш, метрики, аудитВсё, что не относится к основной задаче

Проверяемый факт: в System.IO именно так и устроена работа с потоками: new GZipStream(new BufferedStream(new FileStream(...))) — вы декорировали поток дважды и не написали ни одного класса.

Как не путать с адаптером, прокси и фасадом

Структура у них похожа (обёртка + делегирование), но цель разная — об этом спрашивают на интервью.

ПаттернИнтерфейсЦельПример
ДекораторТот жеДобавить поведениеКэш поверх репозитория
АдаптерДругойПеревести один интерфейс в другойОбёртка над чужим SDK
ПроксиТот жеКонтролировать доступ: ленивая загрузка, права, сетьЛенивый прокси сущности
ФасадПрощеУпростить подсистемуOrderFacade над пятью сервисами
Статистика: насколько часто

Оценка: ~60 % проектов и ~15 % от всех применений паттернов.

  • Факт: каждый, кто работал с файлами или сжатием, использовал декоратор — GZipStream и CryptoStream устроены именно так.
  • Почему ниже стратегии и фабрики: свой декоратор пишут реже: он нужен, когда появляется сквозная задача (кэш, логи) поверх готового интерфейса. Плюс мешает «толстый» интерфейс — тогда сначала нужен ISP (разделение интерфейсов).
  • Оговорка: оценка пропорции, а не измерение (глава 1).

Когда декоратор не нужен

  • Поведение нужно в одном месте и один раз — проще написать его прямо в вызывающем коде.
  • Интерфейс слишком большой: обёртывать 30 методов ради одного — сигнал, что интерфейс надо разделить.
  • Порядок слоёв критичен и неочевиден: если «кэш до валидации» ломает логику, а порядок задаётся в DI-регистрации, это станет источником ошибок. Иногда честнее явный сервис-оркестратор.
★ Что запомнить из главы
  • Декоратор — обёртка с тем же интерфейсом, добавляющая поведение через делегирование.
  • Он убирает «комбинаторный взрыв» наследников и оставляет каждый слой про одну задачу.
  • В .NET декоратор — это Stream и DelegatingHandler; вы пользуетесь им, даже не замечая.
  • Отличие от адаптера/прокси/фасада — в цели, а не в структуре.
  • Оценка: ~60 % проектов, ~15 % от всех использований паттернов.
