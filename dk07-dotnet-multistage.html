Глава 7. Multi-stage: сборка .NET-образа построчно

SDK-стадия, publish, runtime-стадия и non-root — полный рабочий Dockerfile

основная глава

Из главы 5 остался образ на 1.02 ГБ. Здесь он станет 218 МБ

Dockerfile из главы 5 собирал приложение на том же образе, в котором оно потом работало: SDK, MSBuild, NuGet, исходники и готовые dll — всё в одном месте. Получается 1.02 ГБ, из которых приложению нужны полтора десятка мегабайт.

Multi-stage («многостадийная сборка») — возможность описать в одном файле несколько образов и взять из «строительного» только результат. Компилятор остаётся на первой стадии и в финальный образ не попадает вообще.

Что не так с одной стадией

Что лежит в образеНужно приложению?Цена
рантайм .NET (aspnet)да — на нём всё работает~218 МБ
SDK: компилятор, MSBuild, NuGet, шаблонынет: код уже скомпилирован +700 МБ
исходники: .cs, .csproj, .gitнет +размер и утечка кода
промежуточные obj и bin/Debugнет+мусор

Три следствия, и все три видны не сразу:

  • Образ качается при каждом деплое. Его тянут на каждую машину и в каждую реплику: 1 ГБ вместо 218 МБ — это минуты вместо секунд и лишний трафик.
  • Больше поверхностей атаки. Компилятор, NuGet и утилиты умеют скачивать и исполнять код. В работающем контейнере это не нужно, а уязвимости в них считаются так же, как в рантайме (глава 14).
  • Исходники уезжают вместе с образом. Кто получил образ — получил и ваш код. Для закрытого продукта это уже инцидент.

Схема того, что делает multi-stage:

СТАДИЯ 1 (build)                        СТАДИЯ 2 (final)
FROM sdk:8.0                            FROM aspnet:8.0
  ├ компилятор, MSBuild, NuGet            ├ только рантайм .NET
  ├ исходники                             ├
  ├ dotnet restore                        │
  ├ dotnet publish -c Release -o /app     │
  └ /app — готовые dll   ───────────────► └ COPY --from=build /app .
                                               │
                                               ▼
                                   ОБРАЗ 218 МБ: без SDK, без исходников

Стадия 1 целиком остаётся в кэше сборки (глава 6) — в результат она не входит.

Полный Dockerfile

Вот файл целиком — в нём всё, что нужно боевому .NET-API. Дальше разбираем каждую строку.

Dockerfile (рядом с ним — .dockerignore из главы 6)

# syntax=docker/dockerfile:1

# ---------- стадия 1: сборка ----------
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src

# restore зависит только от .csproj/.sln — копируем их первыми (глава 6)
COPY Orders.sln ./
COPY Orders.Api/Orders.Api.csproj Orders.Api/
COPY Orders.Domain/Orders.Domain.csproj Orders.Domain/
RUN --mount=type=cache,target=/root/.nuget/packages,sharing=locked \
    dotnet restore

# теперь весь остальной код и публикация в папку /app
COPY . .
RUN dotnet publish Orders.Api/Orders.Api.csproj \
      -c Release \
      -o /app \
      --no-restore

# ---------- стадия 2: то, что поедет в прод ----------
FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS final
WORKDIR /app

# берём готовый результат первой стадии — и только его
COPY --from=build /app .

# не root: пользователь app уже есть в образе (APP_UID=1654)
USER $APP_UID

# документация: приложение слушает 8080 (ASPNETCORE_HTTP_PORTS из образа)
EXPOSE 8080

# exec-форма: PID 1 = dotnet, сигналы доходят до приложения
ENTRYPOINT ["dotnet", "Orders.Api.dll"]

Что важно увидеть сразу:

  • Два FROM — это два независимых образа. Имена после AS (build, final) нужны, чтобы на стадию можно было сослаться: --from=build.
  • Между стадиями ничего не перетекает само. Всё, что нужно взять, перечислено в COPY --from=….
  • Вторая стадия ничего не знает о первой: ни про WORKDIR /src, ни про установленные пакеты, ни про исходники. Каждая стадия начинается с чистого базового образа — в этом и смысл.
  • В образ попадает только последняя стадия. Первая остаётся в кэше сборки (глава 6), поэтому docker images покажет 218 МБ, а не 1 ГБ.

Разбор по строкам

1. FROM … sdk:8.0 AS build

Первая стадия — строительная площадка. Здесь нужен полный SDK: компилятор, MSBuild, NuGet, шаблоны проектов. Имя стадии можно взять любое (AS compile, AS builder) — важно, что потом на него ссылаются.

ОбразЧто внутриРазмерКуда
sdk:8.0компилятор, MSBuild, NuGet, рантайм~780 МБ стадия сборки
aspnet:8.0рантайм .NET + ASP.NET Core (веб-сервер Kestrel) ~218 МБвеб-API в проде
runtime:8.0только рантайм .NET, без ASP.NET Core~190 МБ консольные приложения, worker-сервисы

Выбор образа для второй стадии — это выбор того, что вообще будет установлено в контейнере. Для API берут aspnet (там уже есть Kestrel), для фонового обработчика очередей — runtime.

2. COPY файлов проектов и dotnet restore

Копируем не весь код, а только .sln и .csproj — то, от чего зависит восстановление пакетов. Это приём из главы 6: правка Program.cs не должна заставлять заново качать пакеты.

--mount=type=cache,target=/root/.nuget/packages — пакеты складываются в кэш демона, который переживает между сборками и не попадает в образ. Если синтаксис незнаком — вернитесь к главе 6: там разобрано и монтирование, и почему publish потом идёт с --no-restore.

3. RUN dotnet publish … -c Release -o /app --no-restore

Главная инструкция стадии. Каждый флаг по делу:

  • dotnet publish, а не build: build только компилирует в bin/Debug/net8.0, а publish ещё и раскладывает результат в папку, готовую к запуску, — с зависимостями и конфигами.
  • -c Release — конфигурация Release: включены оптимизации, нет отладочных проверок. Без этого флага в прод уедет Debug-сборка — медленнее и болтливее, чем нужно.
  • -o /app — «положи результат сюда» (-o = output). Так путь известен точно, и вторая стадия копирует ровно его. Без -o publish кладёт файлы в bin/Release/net8.0/publish — работает, но путь длиннее и легче ошибиться.
  • --no-restore — «пакеты уже восстановлены, в сеть не ходи». Пара к предыдущему RUN dotnet restore: иначе restore выполнится второй раз, уже без кэша пакетов.
  • Orders.Api/Orders.Api.csproj — публикуется конкретный проект, а не solution: в solution обычно есть тесты и утилиты, в образе они не нужны.

4. FROM … aspnet:8.0 AS final

Вторая стадия начинается с нуля — из чистого aspnet. Здесь нет ни исходников, ни SDK: только рантайм .NET и ASP.NET Core с веб-сервером Kestrel. Именно этот образ и станет результатом сборки, потому что он последний.

AS final — просто имя. Оно понадобится, если вы захотите собрать образ только до определённой стадии: docker build --target build -t orders-api:debug . остановится на первой стадии и даст образ с SDK и исходниками — удобно, когда нужно зайти внутрь и что-то посмотреть.

5. COPY --from=build /app .

Одна строка, которая связывает стадии. Читается так: «возьми /app из стадии build и положи в текущую папку текущей стадии».

COPY --from=build /app .
     └── откуда ──┘ └источник┘ └куда: WORKDIR текущей стадии = /app
  • --from=build — имя стадии из AS build. Можно указать номер (--from=0) или даже чужой образ: COPY --from=nginx:latest /etc/nginx/nginx.conf /etc/nginx/ — так берут конфиги из готовых образов.
  • /app — путь внутри стадии build. Он существует потому, что publish писал именно туда (-o /app).
  • . — путь в текущей стадии, то есть /app (его задал WORKDIR /app строкой выше). Точка вместо абсолютного пути — чтобы работало и при смене WORKDIR.
  • Два аргумента обязательны: COPY --from=build /app без второго — ошибка COPY requires at least two arguments.
Что именно скопировалось

Не «проект», не «исходники» и не «всё из стадии build» — только содержимое папки /app: готовые dll, файл зависимостей, конфигурация. Всё остальное из первой стадии (SDK, .cs, obj, кэш NuGet) в финальный образ не попадает физически, потому что о нём никто не просил.

6. USER $APP_UID

Строка переключает пользователя: с этого места все инструкции RUN этой стадии и сам запуск контейнера идут не от root, а от пользователя app. В нашем файле после USER ни одного RUN нет, так что влияет он только на запуск. Пользователь app в образах .NET 8 уже создан, а его идентификатор лежит в переменной APP_UID=1654 (мы видели её в главе 3, когда смотрели Config.Env). Поэтому USER $APP_UID и USER app — одно и то же; первый вариант удобнее, потому что не зависит от имени.

Зачем это нужно и что ломается:

  • Зачем: если в приложении найдут уязвимость и выполнят свой код, он получит права app, а не root. Внутри контейнера root — это не «root на хосте», но достаточно, чтобы навредить соседним процессам и смонтированным папкам (глава 14).
  • Порт ниже 1024 недоступен. Поэтому приложение слушает 8080, а не 80: порты <1024 — привилегированные, их может открыть только root. Как это связано с -p 8080:8080 и почему снаружи может быть 80 — глава 8.
  • Писать в /app нельзя. Файлы туда положил COPY от root, а у app прав на запись нет. Если приложению нужно что-то писать — это либо COPY --chown=$APP_UID /app ., либо (правильнее) том или временная папка (глава 9).
  • Логи — только в stdout. Файл /var/log/app.log создать не выйдет; впрочем, в контейнере так и надо: docker logs читает stdout (глава 4).

7. EXPOSE 8080 и ENTRYPOINT

EXPOSE 8080 ничего не открывает — это документация для людей и подсказка для инструментов: «приложение слушает 8080». Публикация порта наружу делается флагом -p при запуске (глава 8).

ENTRYPOINT записывает в конфиг образа программу, которая станет процессом контейнера. Форма записи здесь принципиальна:

ФормаЧто станет PID 1Сигналы и переменные
ENTRYPOINT ["dotnet", "Orders.Api.dll"]
(exec, в квадратных скобках)		 dotnet сигнал SIGTERM от docker stop доходит до приложения → оно успевает корректно завершиться; переменные $VAR не раскрываются (их раскрывает только оболочка)
ENTRYPOINT dotnet Orders.Api.dll
(shell, строкой)		 /bin/sh оболочка раскрывает $VAR, но сигналы часто не передаёт дальше: docker stop ждёт 10 секунд, потом убивает контейнер SIGKILL — запросы рвутся

Правило для .NET-сервисов: exec-форма. Что происходит при остановке контейнера и как настроить graceful shutdown — глава 13; как передать приложению аргументы в обход ENTRYPOINT — глава 5.

Что именно попадает в /app

Полезно один раз увидеть это глазами. Запускаем одноразовый контейнер, но вместо приложения — ls:

Содержимое финального образа (сокращённо)

$ docker run --rm --entrypoint ls orders-api:1.4.2 -la /app
total 15M
drwxr-xr-x 1 root root 4.0K Nov  2 12:41 .
-rw-r--r-- 1 root root  412 Nov  2 12:41 Orders.Api.deps.json
-rw-r--r-- 1 root root  18K Nov  2 12:41 Orders.Api.dll
-rw-r--r-- 1 root root  128 Nov  2 12:41 Orders.Api.runtimeconfig.json
-rw-r--r-- 1 root root 1.1K Nov  2 12:41 appsettings.json
-rw-r--r-- 1 root root 1.4M Nov  2 12:41 Orders.Domain.dll
-rw-r--r-- 1 root root 1.2M Nov  2 12:41 Swashbuckle.AspNetCore.SwaggerUI.dll
  • --entrypoint ls — «запусти вместо приложения ls», а всё после имени образа станет его аргументами (глава 5).
  • Orders.Api.dll — ваш скомпилированный код. Имя файла = AssemblyName, по умолчанию совпадает с именем проекта; ровно оно стоит в ENTRYPOINT.
  • Orders.Api.deps.json — «карта зависимостей»: какие сборки и каких версий нужны рантайму и где их искать.
  • Orders.Api.runtimeconfig.json — как запускать: версия рантайма, режим сборки мусора и прочие настройки CLR (что там можно менять — глава 12).
  • appsettings.json — конфигурация. Секреты сюда не кладут: они приезжают переменными окружения (глава 10).
  • Остальные dll — ваши проекты и NuGet-пакеты.
  • Владелец всех файлов — root: их положил COPY, выполнявшийся от root. Это ровно та причина, по которой процессу от app нельзя писать в /app (см. пункт 6 выше).

Ни одного .cs, .csproj, obj и никакого SDK: это и есть работа второй стадии.

Сборка и проверка результата

Собираем той же командой, что и раньше, — разница только в выводе: шаги теперь подписаны именами стадий.

docker build: видно, какие шаги к какой стадии относятся

$ docker build -t orders-api:1.4.2 .
[+] Building 38.4s (13/13) FINISHED
 => [internal] load build definition from Dockerfile
 => [internal] load .dockerignore
 => [internal] load metadata for mcr.microsoft.com/dotnet/aspnet:8.0
 => [internal] load metadata for mcr.microsoft.com/dotnet/sdk:8.0
 => [build 1/8] FROM mcr.microsoft.com/dotnet/sdk:8.0
 => [build 2/8] WORKDIR /src
 => [build 3/8] COPY Orders.sln ./
 => [build 4/8] COPY Orders.Api/Orders.Api.csproj Orders.Api/
 => [build 5/8] COPY Orders.Domain/Orders.Domain.csproj Orders.Domain/
 => [build 6/8] RUN --mount=type=cache,... dotnet restore
 => [build 7/8] COPY . .

Две вещи в этом выводе стоят внимания: шаги идут параллельно (поэтому в живом терминале порядок строк перемешивается — это нормально), а [final 5/6] и [final 6/6] выполняются мгновенно: EXPOSE и ENTRYPOINT файлов не создают, только пишут настройки в конфиг образа (глава 5).

Размер — то, ради чего всё делалось:

$ docker images orders-api
REPOSITORY    TAG     IMAGE ID       CREATED          SIZE
orders-api    1.4.2   7c1e9b3d4a52   20 seconds ago   218MB

Было 1.02 ГБ (глава 5), стало 218 МБ — и почти всё это сам рантайм .NET. Что именно лежит в слоях:

Слои образа, сверху — самые новые (сокращённо)

$ docker history orders-api:1.4.2
IMAGE          CREATED         CREATED BY                              SIZE
7c1e9b3d4a52   20 seconds ago  ENTRYPOINT ["dotnet" "Orders.Api.dll"]  0B
<missing>      20 seconds ago  EXPOSE map[8080/tcp:{}]                 0B
<missing>      20 seconds ago  USER app                                0B
<missing>      20 seconds ago  COPY /app . # buildkit                  14.2MB
<missing>      20 seconds ago  WORKDIR /app                            0B
<missing>      3 weeks ago     #(nop)  CMD ["bash"]                    0B
  • docker history — «из чего собран образ»: инструкция и размер каждого слоя.
  • 0B у USER, EXPOSE, ENTRYPOINT — те самые инструкции-настройки: файлов не добавляют.
  • 14.2MB у COPY /app . — ваш код и зависимости. Это единственное, что добавила вторая стадия.
  • BuildKit не пишет в истории --from=build — видно просто COPY /app .. Не пугайтесь: источник всё равно указан в Dockerfile.
  • <missing> — слои, которые пришли из базового образа: они лежат отдельно и в строке не расписаны.

И наконец — запуск. Заодно проверяем, что приложение действительно отвечает:

$ docker run -d --name api -p 8080:8080 orders-api:1.4.2
9a4f2c1e7b33d5a8...

$ docker ps
CONTAINER ID   IMAGE               STATUS
9a4f2c1e7b33   orders-api:1.4.2    Up 12 seconds

$ curl -s http://localhost:8080/health
{"status":"Healthy"}

$ docker logs api
info: Microsoft.Hosting.Lifetime[14]
      Now listening on: http://[::]:8080
  • -d — «в фоне» (detached): команда вернёт ID и отпустит терминал. Без -d вывод приложения пошёл бы прямо в терминал.
  • --name api — имя контейнера, чтобы потом писать docker logs api вместо ID.
  • -p 8080:8080 — опубликовать порт: слева порт на вашей машине, справа порт в контейнере. Подробно — глава 8.
  • Now listening on: http://[::]:8080 — доказательство, что EXPOSE 8080 совпадает с реальностью. Если бы приложение слушало другой порт, curl молчал бы.
Если контейнер сразу завершился

Самая частая причина — ENTRYPOINT указывает на несуществующий файл: имя dll не совпало с AssemblyName или WORKDIR не та папка. Смотреть так: docker ps -a (увидеть Exited (…)) → docker logs api (сообщение вида Could not execute because the specified command or file was not found) → docker run --rm -it --entrypoint ls orders-api:1.4.2 -la /app (что вообще лежит в папке). Полный алгоритм разбора — глава 16.

Варианты, которые встречаются на работе

Фоновый сервис вместо API

Если приложение не принимает HTTP (обработчик очереди, планировщик), ASP.NET Core не нужен — берут runtime и меняют точку входа:

FROM mcr.microsoft.com/dotnet/runtime:8.0 AS final
WORKDIR /app
COPY --from=build /app .
USER $APP_UID
ENTRYPOINT ["dotnet", "Orders.Worker.dll"]

EXPOSE здесь не нужен: портов нет. Всё остальное — то же самое.

Сборка только до нужной стадии

--target останавливает сборку на указанной стадии и отдаёт её как результат:

# образ с SDK и исходниками — чтобы зайти и посмотреть, что происходит при сборке
$ docker build --target build -t orders-api:build-debug .

# внутри: /src с кодом, /app с результатом publish
$ docker run --rm -it --entrypoint bash orders-api:build-debug

Так разбираются вопросы вида «а точно ли publish положил файлы туда, куда я думаю». В продакшене такой образ, разумеется, не нужен.

Несколько сервисов из одного решения

Один Dockerfile на каждый сервис — самый простой и предсказуемый вариант: Dockerfile для API, Worker.Dockerfile для обработчика. Внутри каждого — своя стадия build, и dotnet publish указывает на нужный .csproj.

Собираются они из одного контекста и делят кэш (глава 6), поэтому restore во втором файле обычно берётся из кэша первого:

$ docker build -f Dockerfile        -t orders-api:1.4.2    .
$ docker build -f Worker.Dockerfile -t orders-worker:1.4.2 .

-f — «взять этот файл вместо ./Dockerfile» (глава 5). Не забудьте .dockerignore в корне контекста — он один на всех (глава 6).

Сборка под чужую архитектуру

Ноутбук на Apple Silicon собирает arm64, а сервер ждёт amd64 — при запуске это даст exec format error (глава 3). Лечится явной платформой:

$ docker buildx build --platform linux/amd64 -t orders-api:1.4.2 --push .

--platform — под какую архитектуру собирать; одна сборка может сделать сразу несколько (--platform linux/amd64,linux/arm64), но такой результат нельзя «загрузить в локальный Docker» — только --push в реестр. Где это нужно в пайплайне — глава 15.

Ещё меньше и безопаснее

Дальше размер уменьшают 8.0-alpine (меньше базовый образ, но другая libc) и 8.0-noble-chiseled — «выщербленный» образ без оболочки и пакетного менеджера: в него не зайти через docker exec, зато и атакующему почти нечего делать. Подробности и цена — глава 14.

Пять ошибок, которые встречаются в реальных Dockerfile
  1. Нет -c Release. В прод уезжает Debug-сборка: медленнее, с отладочной информацией. Видно по docker run --rm --entrypoint ls … -la /app — рядом с dll лежат *.pdb.
  2. COPY . . в финальной стадии. Классика: «скопирую весь проект, чтобы точно всё работало». SDK там не появится, зато приедут исходники, тесты и obj — и весь смысл стадий потерян. В финальной стадии нужен только COPY --from=build /app ..
  3. Путь не совпадает. publish писал в /app, а COPY --from=build смотрит в /src/bin/Release/net8.0. Итог — пустая папка и падение на старте. Проверка: ls -la /app в обеих стадиях.
  4. Забыт --no-restore. restore выполняется второй раз, уже без cache-монтирования: сборка медленнее и снова лезет в сеть.
  5. Shell-форма ENTRYPOINT. Работает, но PID 1 — это /bin/sh: docker stop и Kubernetes будут ждать таймаут и убивать приложение жёстко (глава 13).
★ Что запомнить из главы
  • Стадия — отдельный образ внутри одного Dockerfile: FROM … AS имя. В результат попадает только последняя стадия.
  • Между стадиями ничего не перетекает: нужное забирают явно — COPY --from=build /app ..
  • Сборка: sdk → restore (по .csproj) → COPY . . → dotnet publish -c Release -o /app --no-restore.
  • Запуск: aspnet (или runtime для не-HTTP) → WORKDIR → COPY --from → USER $APP_UID → EXPOSE → ENTRYPOINT в exec-форме.
  • Итог: 218 МБ вместо 1.02 ГБ — без SDK, без исходников, не от root, сигналы доходят до приложения.
  • Проверка: docker images (размер), docker history (слои), curl …/health (работает), --entrypoint ls … -la /app (что внутри).
