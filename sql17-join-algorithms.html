Глава 17. Алгоритмы соединений: Nested Loop, Hash, Merge

Когда запрос соединяет несколько таблиц, СУБД выбирает способ соединения. Именно здесь часто кроется причина «тормозов» — и именно это спрашивают на интервью.

Что значит «соединить таблицы»

JOIN сопоставляет строки двух наборов по условию (обычно по равенству ключей: «заказы и их клиенты»). Способов это сделать несколько, и у каждого — своя цена в зависимости от объёмов данных. Планировщик выбирает способ по оценке числа строк (глава 14).

Дальше для каждого способа одинаковый порядок: как работает → как выглядит в плане (с выводом) → что делать, если план плохой. Правильный ответ на собеседовании — не «нужен Hash Join», а «вот сигнал в плане, вот причина, вот что я меняю и как проверяю».

Nested Loop (вложенный цикл)

Для каждой строки внешнего набора делается поиск во внутреннем.

Хороший план: внешняя строка одна, внутренний поиск по индексу

EXPLAIN (ANALYZE)
SELECT o.id, i.sku
FROM   orders o
JOIN   order_items i ON i.order_id = o.id
WHERE  o.id = 42;

Nested Loop  (actual time=0.031..0.094 rows=3 loops=1)
  ->  Index Scan using orders_pkey on orders o  (actual time=0.020..0.021 rows=1 loops=1)
        Index Cond: (id = 42)
  ->  Index Scan using order_items_order_id_idx on order_items i
        (actual time=0.008..0.015 rows=3 loops=3)      ← 3 цикла по 1 индексу ≈ 3×0.015 мс
        Index Cond: (order_id = 42)

-- ВЫВОД: внешних строк 1, циклов 3, время в микросекундах.
-- Это лучший возможный план: ровно то, для чего Nested Loop существует.

Плохой план: внешних строк полмиллиона, а внутренняя сторона — Seq Scan

Nested Loop  (actual time=812.4..48213.5 rows=480000 loops=1)   ← 48 секунд
  ->  Seq Scan on orders o  (actual time=0.02..120.4 rows=480000 loops=1)
        Filter: (status = 'NEW'::text)
  ->  Seq Scan on order_items i  (actual time=0.01..0.06 rows=4 loops=480000)
        Filter: (order_id = o.id)                              ← 480 000 полных сканов!

-- ВЫВОД: 480 000 × (полное чтение order_items) — это O(N×M).
-- «rows=4 loops=480000» = 1 920 000 строк, проверенных ради 480 000 результата.

Что делать, если Nested Loop плохой

  1. Проверить оценку внешнего узла: если rows=10, а actual rows=480000 — планировщик выбрал Nested Loop «по ошибке». Лечится ANALYZE orders; (или поднятием default_statistics_target, глава 13) — после этого план перестроится сам.
  2. Индекс на внутренней стороне по колонке соединения: CREATE INDEX ON order_items (order_id); — тогда каждый цикл станет дешёвым (и часто этого достаточно, даже при многих тысячах циклов).
  3. Уменьшить число внешних строк — чтобы фильтр стал индексным: CREATE INDEX ON orders (status, created_at DESC); Тогда внешних строк будет не 480 000, а сотни.
  4. Проверить, не лучше ли Hash (только для диагностики, не как постоянное решение): SET LOCAL enable_nestloop = off; и снова EXPLAIN. Если с Hash в разы быстрее — значит оценка кардинальности врёт, и правим статистику, а не план.
  5. Не «чинить» его там, где он хорош: при LIMIT 20 Nested Loop выигрывает у Hash, потому что умеет остановиться на двадцатой строке, а Hash обязан построить хеш целиком.

Hash Join (соединение по хешу)

Строится хеш-таблица по меньшему набору, затем по ней «пробивается» больший. Работает только по равенству: хеш отвечает на вопрос «есть ли такой ключ», а не «больше/меньше».

Хороший план: хеш целиком в памяти

EXPLAIN (ANALYZE, BUFFERS)
SELECT c.name, count(*)
FROM   orders o
JOIN   customers c ON c.id = o.customer_id
GROUP  BY c.name;

HashAggregate  (actual time=920.4..930.1 rows=200 loops=1)
  ->  Hash Join  (actual time=8.3..812.4 rows=480000 loops=1)
        Hash Cond: (o.customer_id = c.id)
        ->  Seq Scan on orders o        (rows=480000)     ← большая сторона «пробивается»
        ->  Hash  (actual time=8.1..8.1 rows=200 loops=1)  ← хеш по МЕНЬШЕЙ стороне
              Buckets: 1024  Batches: 1  Memory Usage: 1024kB   ← Batches=1 — всё в памяти
              ->  Seq Scan on customers c  (rows=200)

-- ВЫВОД: Batches = 1 → ни одного временного файла. Дёшево и предсказуемо.

Плохой план: хеш не влез в work_mem и пошёл на диск батчами

Hash Join  (actual time=1204.8..93412.6 rows=960000 loops=1)
  Hash Cond: (i.order_id = o.id)
  ->  Seq Scan on order_items i  (rows=960000)
  ->  Hash  (actual time=702.1..702.1 rows=480000 loops=1)
        Buckets: 524288  Batches: 8  Memory Usage: 4096kB   ← в памяти только 1/8 хеша
        Buffers: shared hit=12040, temp read=18422 written=18440   ← 144 МБ на диск

-- ВЫВОД: Batches = 8 значит «8 проходов»: хеш порезан на 8 частей, и order_items
-- перечитывается для каждой части. Время выросло в 100 раз из-за диска, а не из-за CPU.

Что делать, если Hash Join плохой

  1. Дать памяти этому запросу — самое прямое лечение, если Batches > 1: SET LOCAL work_mem = '256MB'; внутри транзакции (или в сессии отчёта), затем снова EXPLAIN — Batches должен стать 1. Глобально поднимать нельзя: work_mem выделяется на операцию сортировки/хеша, и при 200 соединениях это гигабайты.
  2. Уменьшить «строящуюся» сторону — хеш по меньшему набору. Часто помогает отфильтровать заранее: WHERE o.created_at >= :from вместо фильтра после соединения, или предварительная агрегация в подзапросе (LEFT JOIN (SELECT … GROUP BY …)).
  3. Убрать лишние колонки из SELECT: чем уже строки, тем меньше хеш (Memory Usage падает).
  4. Индекс вместо соединения, если строк на выходе мало: индекс на order_items (order_id) даёт Nested Loop с 20 циклами вместо хеширования 960 000 строк.
  5. Проверить статистику, если Hash выбран там, где данных мало: rows на узлах сильно больше actual rows → ANALYZE.

Merge Join (соединение слиянием)

Обе стороны должны быть отсортированы по ключу соединения, после чего они «сливаются» за один проход — как две колоды карт, которые раскладывают в одну.

Плохой план: сортировки «с нуля» ради самого слияния

EXPLAIN (ANALYZE, BUFFERS)
SELECT o.id, c.name
FROM   orders o
JOIN   customers c ON c.id = o.customer_id;

Merge Join  (actual time=812.4..1204.9 rows=480000 loops=1)
  Merge Cond: (o.customer_id = c.id)
  ->  Sort  (actual time=402.1..601.2 rows=480000 loops=1)      ← сортируем 480 000 строк
        Sort Key: o.customer_id
        Sort Method: external merge  Disk: 25120kB                ← и ещё на диск
        Buffers: shared hit=20114 read=5832, temp read=3140 written=3144
        ->  Seq Scan on orders o  (rows=480000)
  ->  Index Scan using customers_pkey on customers c  (rows=200)   ← эта сторона уже отсортирована

-- ВЫВОД: слияние тут дешевле не стало — мы заплатили за сортировку 480 000 строк (с выгрузкой на
-- диск). Индекс по customers дал порядок только по одной стороне; вторая сторона сортируется «с нуля».

Хороший план: обе стороны берут порядок из индексов

CREATE INDEX ON orders (customer_id);   -- теперь order по customer_id «бесплатен»

Merge Join  (actual time=0.043..812.5 rows=480000 loops=1)
  Merge Cond: (o.customer_id = c.id)
  ->  Index Only Scan using orders_customer_id_idx on orders o  (rows=480000)
        Heap Fetches: 0                          ← ни таблицы, ни сортировки
  ->  Index Scan using customers_pkey on customers c  (rows=200)

-- ВЫВОД: узлы Sort исчезли, temp read/written исчезли: слияние стало одним проходом
-- по двум отсортированным индексам. Вот это и есть «Merge Join в своей стихии».

Что делать, если Merge Join плохой

  1. Убрать сортировку, дав порядок индексу — главное лечение. Индекс по колонке соединения (или по (col1, col2) в нужном порядке) превращает Sort в Index Scan. После этого Merge Join становится дешёвым — либо планировщик сам выберет Nested Loop, и это тоже нормально.
  2. Проверить, нужна ли сортировка вообще: если в запросе есть ORDER BY по тому же ключу, что и соединение, — Merge Join «бесплатно» отдаёт нужный порядок. Если ORDER BY в запросе нет, merge join почти всегда лишний: Hash сделает то же без сортировки.
  3. Сократить набор до сортировки: фильтр (WHERE o.created_at >= :from) или LIMIT в подзапросе — сортировать 10 000 строк дешевле, чем 480 000.
  4. Проверить память: external merge Disk перед Merge Join — тот же симптом нехватки work_mem; SET LOCAL work_mem = '256MB'; уберёт диск.
  5. Диагностика переключателем: SET LOCAL enable_mergejoin = off; — если Hash-план заметно быстрее, значит merge выбран из-за завышенной оценки строк → ANALYZE. Оставлять переключатель включённым нельзя: он «ломает» другие запросы в этой сессии.

Сводка: сигнал → причина → решение

Переключатели enable_* — только для диагностики

SET LOCAL enable_hashjoin / enable_mergejoin / enable_nestloop = off не «запрещают» способ навсегда: PostgreSQL использует их как огромный штраф к стоимости. Это инструмент, чтобы увидеть альтернативный план и сравнить время. Если альтернатива лучше — значит виновата не «магия планировщика», а оценка строк или отсутствие индекса; правим это, а переключатель снимаем.

Если план плохой: порядок действий

  1. Найти узел соединения и посчитать его время: actual time × loops. Именно он, а не «весь запрос», съедает секунды (глава 19).
  2. Сравнить rows и actual rows на входах этого узла. Расхождение в разы → виновата статистика (ANALYZE), а не выбор алгоритма.
  3. Посмотреть, что лежит под узлом: Sort с диском или Seq Scan на большой таблице → лечится индексом; Index Scan на внутренней стороне с большим loops → индекса мало, нужен другой способ соединения.
  4. Проверить память: Batches, Disk:, temp read/written → work_mem.
  5. Менять по одному и каждый раз снимать новый EXPLAIN: иначе непонятно, что именно помогло (глава 20).
★ Ключевая мысль

«Плохой» — не тип соединения, а неверная оценка кардинальности. Если планировщик думает, что строк 10, он выберет Nested Loop; если на деле их 500 000 — это катастрофа. Поэтому сначала сравнивают rows и actual rows, и только потом смотрят на сам способ соединения (глава 19).
