Глава 17. Алгоритмы соединений: Nested Loop, Hash, Merge

Когда запрос соединяет несколько таблиц, СУБД выбирает способ соединения. Именно здесь часто кроется причина «тормозов» — и именно это спрашивают на интервью.

Что значит «соединить таблицы»

JOIN сопоставляет строки двух наборов по условию (обычно по равенству ключей: «заказы и их клиенты»). Способов это сделать несколько, и у каждого — своя цена в зависимости от объёмов данных. Планировщик выбирает способ по оценке числа строк (глава 14).

Nested Loop (вложенный цикл)

Для каждой строки внешнего набора делается поиск во внутреннем.

  • Хорош, когда: внешних строк мало, а внутренний поиск идёт по индексу (глава 10) — тогда он отзывчив и быстр, особенно при LIMIT.
  • Узкое место, когда: внешних строк много — получаем тысячи циклов и сложность порядка N×M. Частая причина — недооценка числа строк или отсутствие индекса на внутренней стороне.
  • Сигнал в плане: большое loops и/или rows на внешнем узле в разы меньше actual rows.

Hash Join (соединение по хешу)

Строится хеш-таблица по меньшему набору, затем по ней «пробивается» больший.

  • Хорош, когда: соединяются большие наборы по равенству — обычно лучший выбор для «тяжёлых» запросов.
  • Узкое место, когда: хеш не влезает в память — тогда он идёт на диск батчами. Работает только по равенству (не для диапазонов).
  • Сигнал в плане: Batches больше 1, рост Memory Usage и temp written → мало work_mem.

Merge Join (соединение слиянием)

Обе стороны сортируются и «сливаются» за один проход.

  • Хорош, когда: обе стороны уже отсортированы (например, индексами) — тогда очень эффективен и на больших наборах.
  • Узкое место, когда: сортировка больших наборов выполняется «с нуля» — дорого, а при нехватке памяти уходит на диск.
  • Сигнал в плане: узлы Sort с external merge Disk перед Merge Join.
ТипЛучше всего подходитСтановится проблемой
Nested LoopВнешних строк мало, внутренний поиск по индексуМного внешних строк → тысячи циклов, O(N×M)
Hash JoinБольшие наборы, соединение по равенствуХеш не влезает в work_mem → батчи на диск
Merge JoinОбе стороны уже отсортированыНужна дорогая сортировка больших наборов
★ Ключевая мысль

«Плохой» — не тип соединения, а неверная оценка кардинальности. Если планировщик думает, что строк 10, он выберет Nested Loop; если на деле их 500 000 — это катастрофа. Поэтому сначала сравнивают rows и actual rows, и только потом смотрят на сам способ соединения (глава 19).
