Глава 7. Распределённые блокировки и Lua-скрипты

SET NX PX по словам, атомарное освобождение через Lua, что происходит, когда TTL истёк, а работа ещё идёт, и почему Redlock — не серебряная пуля. Все команды и выводы проверены на Redis 7 и StackExchange.Redis 2.8.

основная глава

Зачем нужна распределённая блокировка

lock и SemaphoreSlim (глава 10 C#-книги) работают внутри процесса: они разводят потоки одной реплики. Но в проде реплик несколько, и два экземпляра сервиса ничего не знают о блокировках друг друга — оба начнут «единственную» операцию. Примеры: ночной пересчёт, отправка отчёта, взятие задачи из очереди, миграция данных.

Идея простая: общий для всех реплик флаг в Redis. Взять можно только тогда, когда флага нет, и он сам исчезнет, если процесс упал. В Redis это одна команда:

# SET ключ значение NX PX миллисекунды
docker exec rds redis-cli SET lock:42 ownerA NX PX 3000
# OK                     ← блокировка взята, TTL 3000 мс

docker exec rds redis-cli SET lock:42 ownerB NX PX 3000
# (nil)                  ← уже занято, не наша

docker exec rds redis-cli GET lock:42
# "ownerA"               ← значение — это токен владельца
docker exec rds redis-cli TTL lock:42
# 3                      ← осталось секунд (PTTL — в миллисекундах)

Каждое слово важно:

ЭлементЧто делаетПочему именно так
SETЗаписать значение по ключуАтомарная команда; в отличие от «GET + SET», не даёт двоим пройти одновременно
lock:42Ключ блокировкиГранулярность: лок на конкретный заказ, а не на всю систему
ownerAЗначение — токен владельцаПо нему видно, кто держит лок; без него нельзя безопасно освободить
NXNot eXists: писать только если ключа нетЭто и есть «взять блокировку»; иначе команда просто перезапишет чужую
PX 3000Срок жизни в миллисекундахСтраховка от вечной блокировки: процесс упал — ключ исчезнет сам

Родственные опции: EX — то же, но в секундах; XX — писать только если ключ уже есть; GET — вернуть старое значение; KEEPTTL — сохранить прежний TTL при перезаписи.

Освобождение: почему DEL — ошибка

Первое, что хочется написать в finally, — DEL lock:42. И это удаляет любую блокировку по этому ключу, даже чужую. Проверка: владелец ownerA взял лок, а «уборщик» другой реплики вызвал DEL.

docker exec rds redis-cli SET lock:42 ownerA NX PX 3000   # OK — ownerA взял
docker exec rds redis-cli DEL lock:42                     # 1  — удалено чужой рукой
docker exec rds redis-cli GET lock:42                     # (nil) — лока нет, хотя ownerA работает

Правильно — удалять только своё: сравнить значение с токеном и удалить, причём одной атомарной операцией. Иначе между GET и DEL снова влезет другой процесс. Для этого в Redis есть серверные скрипты на Lua:

-- KEYS[1] — ключ блокировки, ARGV[1] — наш токен
if redis.call('get', KEYS[1]) == ARGV[1] then   -- значение совпало с нашим?
    return redis.call('del', KEYS[1])           -- да: удаляем и сообщаем 1
end
return 0                                        -- нет: чужая блокировка, ничего не делаем
# EVAL скрипт количество_ключей ключ аргументы
docker exec rds redis-cli EVAL "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end" 1 lock:42 ownerB
# 0                      ← чужой токен: не удалили
docker exec rds redis-cli EXISTS lock:42
# 1                      ← блокировка на месте

docker exec rds redis-cli EVAL "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end" 1 lock:42 ownerA
# 1                      ← свой токен: удалили
docker exec rds redis-cli EXISTS lock:42
# 0

Почему Lua атомарен: Redis исполняет скрипт целиком, без переключения на другие команды — внутри скрипта не может вклиниться другой клиент. Ровно того и не хватает паре GET + DEL.

EVAL и EVALSHA: не гоняйте текст скрипта каждый раз

Текст скрипта можно один раз загрузить на сервер (SCRIPT LOAD) и дальше вызывать по SHA1-хешу — это быстрее и меньше трафика. Проверено:

# Загрузить скрипт: сервер вернёт его SHA1
docker exec rds redis-cli SCRIPT LOAD "return redis.call('incr', KEYS[1])"
# 2bab3b661081db58bd2341920e0ba7cf5dc77b25

# Вызвать по хешу: 1 — количество ключей
docker exec rds redis-cli EVALSHA 2bab3b661081db58bd2341920e0ba7cf5dc77b25 1 cnt:x
# 1

# Если кеш скриптов очистить, тот же EVALSHA падает — и это надо обрабатывать
docker exec rds redis-cli SCRIPT FLUSH
docker exec rds redis-cli EVALSHA 2bab3b661081db58bd2341920e0ba7cf5dc77b25 1 cnt:x
# NOSCRIPT No matching script. Please use EVAL.

Правильная стратегия в коде: попробовать EVALSHA, при ошибке NOSCRIPT — загрузить скрипт и повторить. В StackExchange.Redis это делает ScriptEvaluateAsync сам.

Что происходит, когда TTL истёк, а работа идёт

TTL — это компромисс: слишком маленький — блокировка исчезнет под работающим процессом, слишком большой — после падения процесса другие будут ждать. Проверка «слишком маленького»:

docker exec rds redis-cli SET lock:1 ownerA NX PX 150    # ownerA взял лок на 150 мс
sleep 0.3                                                 # ownerA всё ещё работает
docker exec rds redis-cli GET lock:1                      # (nil) — лок исчез
docker exec rds redis-cli SET lock:1 ownerB NX PX 150     # OK — ownerB взял тот же лок

Теперь два процесса одновременно считают, что держат блокировку. Никакой TTL этого не решает: он лишь ограничивает время ожидания. Что делать:

  • Продлевать TTL, пока работа идёт (watchdog: раз в TTL/3 выполнять PEXPIRE тем же Lua-скриптом с проверкой токена).
  • Fencing token: каждому взятию блокировки выдавать монотонно растущий номер (INCR lock:42:fence) и передавать его в операцию; ресурс отвергает запись с меньшим номером. Это защита на стороне ресурса, а не «на честном слове» блокировки.
  • Идемпотентность: операция, которую можно безопасно повторить, снимает большую часть проблемы (глава 31 .NET-раздела).

То же самое в .NET

Ниже — рабочий сценарий на StackExchange.Redis: десять задач одновременно пытаются взять один лок, затем освобождение «своим» и «чужим» токеном. Код проверен прогоном, в комментариях — результат.

// Одно соединение на процесс: ConnectionMultiplexer потокобезопасен и переподключается сам
await using var redis = await ConnectionMultiplexer.ConnectAsync("localhost:6379");
var db = redis.GetDatabase();                    // логическая база 0

// Десять задач пытаются взять ОДНУ блокировку
var winners = 0;
var attempts = Enumerable.Range(0, 10).Select(i => Task.Run(async () =>
{
    var token = $"worker-{i}";                   // уникальный токен владельца
    // StringSetAsync(key, value, expiry, when): when = NotExists — это NX
    var taken = await db.StringSetAsync("lock:42", token, TimeSpan.FromSeconds(5), When.NotExists);
    if (taken) Interlocked.Increment(ref winners);   // прошёл только один
}));
await Task.WhenAll(attempts);
// A) взяли блокировку 1, значение worker-9  ← победитель зависит от гонки

// Освобождение: сравнить токен и удалить — одним скриптом
const string ReleaseScript = """
    if redis.call('get', KEYS[1]) == ARGV[1] then
        return redis.call('del', KEYS[1])
    end
    return 0
    """;

var asStranger = await db.ScriptEvaluateAsync(ReleaseScript, ["lock:42"], ["worker-99"]);
// B) чужой токен: результат 0, ключ существует True

var owner = await db.StringGetAsync("lock:42");   // реальный владелец (worker-9 в прогоне)
var asOwner = await db.ScriptEvaluateAsync(ReleaseScript, ["lock:42"], [owner]);
// C) свой токен: результат 1, ключ существует False

Разбор вызовов: ConnectAsync — установить соединение (host:port); GetDatabase() — выбрать базу; StringSetAsync — обёртка над SET с опциями, где When.NotExists — это NX, а TimeSpan превращается в PX; ScriptEvaluateAsync — выполнить Lua: первым аргументом ключи (KEYS), вторым — аргументы (ARGV).

Lua не только для блокировок: rate limiter

Второй частый сценарий — «не больше N операций в окно». Проблема наивного кода: INCR и EXPIRE — две команды, и между ними процесс может упасть, оставив ключ навсегда. Проверка:

docker exec rds redis-cli INCR rl:bad      # 1
docker exec rds redis-cli TTL rl:bad       # -1 — TTL нет, ключ будет жить вечно

Один скрипт решает обе задачи атомарно — счётчик и срок выставляются вместе (проверено: счётчики 1, 2, 3 и PTTL около 997 мс):

local c = redis.call('incr', KEYS[1])                    -- +1 к счётчику окна
if c == 1 then                                           -- первый запрос в окне?
    redis.call('pexpire', KEYS[1], ARGV[1])              -- тогда задаём срок жизни окна
end
return c                                                 -- вызывающий сравнивает с лимитом
const string RateScript = """
    local c = redis.call('incr', KEYS[1])
    if c == 1 then redis.call('pexpire', KEYS[1], ARGV[1]) end
    return c
    """;

for (var i = 0; i < 3; i++)
{
    var count = await db.ScriptEvaluateAsync(RateScript, ["rl:user"], [1000]);   // окно 1000 мс
    Console.WriteLine($"запрос {i + 1}: счётчик {count}");                        // 1, 2, 3
}
Console.WriteLine(await db.KeyTimeToLiveAsync("rl:user"));                        // 00:00:00.9970000

Границы: один Redis, Sentinel и Redlock

  • Один Redis — точка отказа. Упал сервер — блокировки исчезли (если не было персистентности) или недоступны. Для продакшена — репликация и Sentinel/Cluster (глава 6), но и там есть окно, когда мастер уже упал, а реплика ещё не знает о блокировке.
  • Redlock — попытка решить это кворумом: N независимых Redis (обычно 5), блокировка берётся на большинстве (N/2+1) с ограничением по времени. Даже он не даёт гарантий при долгих паузах процесса (GC, пауза виртуалки): блокировка истекает, а работа продолжается. Поэтому Redlock годится для «не делать дважды по возможности», но не для денег и не для инвариантов.
  • Когда блокировка не нужна: если операцию можно сделать идемпотентной (INSERT ... ON CONFLICT, уникальный индекс, outbox — глава 31 .NET-раздела) или взять данные под SELECT ... FOR UPDATE в PostgreSQL (глава 24 SQL-раздела). Тогда корректность держит сама БД, а не договорённость между процессами.
  • Не держите лок дольше TTL. Работа, которая может идти минуты, требует либо продления TTL, либо fencing-токена, либо переноса в очередь с одним воркером.
★ Что запомнить
  • Блокировка = SET key token NX PX ttl: NX — «только если нет», PX — срок жизни, токен — «чей лок».
  • Освобождать только своё: сравнение токена и удаление одним Lua-скриптом; DEL удаляет чужую блокировку (проверено).
  • Lua исполняется атомарно; EVALSHA — по SHA1 из SCRIPT LOAD, при NOSCRIPT скрипт надо загрузить заново.
  • TTL не спасает от двух владельцев: истёк — второй взял лок, пока первый работает (проверено GET → nil и SET → OK через 150 мс). Нужны продление TTL, fencing-токен или идемпотентность.
  • Один Redis — точка отказа; Redlock с кворумом уменьшает риск, но не даёт строгих гарантий; для инвариантов — блокировка в БД или уникальные ограничения.
  • Тот же Lua закрывает rate limiter: INCR + PEXPIRE одной операцией (без скрипта ключ может остаться без TTL — TTL -1).
