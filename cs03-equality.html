Глава 3. Равенство и хеш: Equals, GetHashCode, IEquatable, with

Почему два объекта с одинаковыми данными не равны, зачем нужен GetHashCode, что даёт IEquatable<T> и при чём здесь record, with, init и required.

подводящая глава

Задача: «одинаковые данные» и «одинаковый объект» — не одно и то же

public class Money          // обычный класс
{
    public long Kopeks { get; init; }
}

var a = new Money { Kopeks = 1000 };
var b = new Money { Kopeks = 1000 };

Console.WriteLine(a == b);            // False
Console.WriteLine(a.Equals(b));       // False
Console.WriteLine(ReferenceEquals(a, b)); // False

Данные одинаковые, а результат — False, потому что для класса по умолчанию сравниваются ссылки (где объект лежит), а не содержимое. Это называется ссылочной семантикой. Чтобы «1000 копеек» и «1000 копеек» считались равными, нужно объяснить компилятору, что в этом типе считать значением.

Три разных «равно»

ЧтоЧто сравниваетКогда используется
ReferenceEquals(a, b)Один и тот же объект в памятиПроверить «это тот же экземпляр» (например, в пуле или кэше)
a == bТо, что определяет оператор ==: для класса — ссылки, для string — символы, для своих типов — что вы написалиОбычное сравнение в коде
a.Equals(b)То, что определяет метод Equals Сравнение «по значению»; его вызывают коллекции

В Dictionary, HashSet, List.Contains, Enumerable.Distinct используется именно Equals + GetHashCode, а не ==. Поэтому «перегрузил ==, и всё заработало» — не работает.

Зачем нужен GetHashCode

Хеш-коллекции (словарь, множество) устроены так: по хешу вычисляют корзину, в которой искать значение, — и уже внутри корзины сравнивают через Equals. Отсюда контракт:

  • если a.Equals(b) истинно, то a.GetHashCode() == b.GetHashCode() обязательно;
  • обратное неверно: одинаковый хеш не означает равенство (бывают коллизии).
// ✘ нарушен контракт: Equals «по значению», а хеш — по ссылке (по умолчанию)
public class Money
{
    public long Kopeks { get; init; }
    public override bool Equals(object? obj) => obj is Money m && Kopeks == m.Kopeks;
    // GetHashCode не переопределён → у двух равных объектов разные хеши
}

var set = new HashSet<Money> { new() { Kopeks = 1000 } };
Console.WriteLine(set.Contains(new Money { Kopeks = 1000 }));   // False  ← «равный» объект не найден

Причина: словарь ищет в корзине по хешу, а объект попал в другую корзину. Поэтому Equals и GetHashCode переопределяют парой.

Как правильно: IEquatable<T> + Equals + GetHashCode

Что такое IEquatable<T>: интерфейс из одного метода — bool Equals(T other). Зачем он, если уже есть Equals(object)? Потому что Equals(object) принимает object, и для struct каждое сравнение означает упаковку (бокс): значение копируется в кучу, чтобы стать объектом. Типизированный вариант сравнивает напрямую, без копий и без приведения типов.

public readonly struct Money : IEquatable<Money>
{
    public long Kopeks { get; }
    public string Currency { get; }

    public Money(long kopeks, string currency) => (Kopeks, Currency) = (kopeks, currency);

    // 1) типизированное сравнение — его вызывают List, Dictionary, LINQ;
    //    работает без бокса, потому что параметр — Money, а не object
    public bool Equals(Money other) => Kopeks == other.Kopeks && Currency == other.Currency;

    // 2) версия для object — нужна там, где тип известен только как object
    public override bool Equals(object? obj) => obj is Money m && Equals(m);

    // 3) хеш: у равных объектов обязан быть одинаковым.
    //    HashCode.Combine — стандартный помощник, смешивает хеши полей
    public override int GetHashCode() => HashCode.Combine(Kopeks, Currency);

    // 4) операторы — чтобы == в обычном коде вёл себя так же, как Equals
    public static bool operator ==(Money a, Money b) => a.Equals(b);
    public static bool operator !=(Money a, Money b) => !a.Equals(b);

    // 5) человекочитаемый вид: удобно в логах и отладчике
    public override string ToString() => $"{Kopeks / 100m} {Currency}";
}
var a = new Money(1000, "RUB");
var b = new Money(1000, "RUB");

Console.WriteLine(a == b);                 // True  — оператор вызвал Equals
Console.WriteLine(a.Equals(b));            // True
Console.WriteLine(a.Equals((object)b));    // True  — версия для object
Console.WriteLine(a.GetHashCode() == b.GetHashCode()); // True

Зачем пункты 2 и 4, если есть пункт 1: коллекции и object-API вызывают Equals(object), а ваш код — ==. Без них «равенство» зависело бы от того, каким способом его спросили.

record: то же самое, но за вас

Всё, что выше, компилятор умеет писать сам. record — это тип, для которого «равенство = равенство данных»: он автоматически получает Equals, GetHashCode, ==, ToString и with.

public record Order(Guid Id, decimal Total);      // record class (ссылочный тип)

var a = new Order(Guid.Parse("…"), 100m);
var b = new Order(a.Id, 100m);

Console.WriteLine(a == b);      // True  — сравнение по значениям, а не по ссылке
Console.WriteLine(a);           // Order { Id = …, Total = 100 }   ← ToString сгенерирован

public readonly record struct Point(int X, int Y); // record struct (значимый тип)
Что генерируетсяЗачем
Equals / GetHashCode по всем полямРавенство «по данным» и корректная работа в словаре/множестве
== и !=Сравнение в коде ведёт себя так же, как Equals
ToString()Читаемые логи без ручного кода
withКопия с изменённым полем (ниже)
Deconstruct (у позиционного)Распаковка: var (id, total) = order;
Разница между class, record class и record struct

class — ссылка, равенство по ссылке. record class — тоже ссылка (в куче), но равенство по значениям. record struct — значение (как struct), равенство по значениям. Для DTO и событий домена почти всегда подходит record.

with: копия с изменением

Что делает: берёт объект (или значение), копирует все поля и заменяет те, что указаны в фигурных скобках. Исходный остаётся нетронутым:

var a = new Order(id, 100m);
var b = a with { Total = 200m };      // копия a, но с новым Total

Console.WriteLine(a.Total);           // 100 — исходный не изменился
Console.WriteLine(b.Total);           // 200
Console.WriteLine(a == b);            // False — данные разные
Console.WriteLine(ReferenceEquals(a, b)); // False — это два разных объекта
  • Где работает: record, record struct и любой struct (C# 10+). Для обычного class — нельзя.
  • Зачем: способ «изменить» неизменяемый объект — не мутировать, а создать новый с другим полем. Безопаснее в многопоточности: никто не увидит объект в промежуточном состоянии.
  • Почему работает: with может задавать свойства, объявленные init.

init: задать при создании, дальше — нельзя

Инициализатор — это фигурные скобки после new: new Order { Id = id, Total = 100 }. init разрешает присвоить свойство только в конструкторе, в инициализаторе и в with:

public sealed class Order
{
    public required Guid Id { get; init; }     // обязательно задать, потом нельзя менять
    public decimal Total { get; init; }        // можно не задавать → останется 0
}

var o = new Order { Id = id, Total = 100 };    // ✔ создание через инициализатор
// o.Total = 200;                              // ✘ ошибка компиляции: свойство только init

Чем init лучше set: объект нельзя случайно изменить после создания — ни в методе, ни в другом потоке. Именно поэтому with имеет смысл: «изменить» можно только создав копию.

required: компилятор проверит, что поле задано

Без required свойство можно забыть — и получить null или 0 в самом неудобном месте. required превращает это в ошибку компиляции:

var bad = new Order { Total = 100 };              // ✘ CS9035: требуется Id
var ok  = new Order { Id = id, Total = 100 };     // ✔

// в позиционном record required не нужен: параметры конструктора уже обязательны
public record Order(Guid Id, decimal Total);
МодификаторКогда можно задатьЧто гарантирует
setвсегданичего — можно менять в любой момент (и сломать инварианты)
initпри создании, в конструкторе и в with после создания значение не изменится
requiredвместе с init (или set) компилятор не даст создать объект, не задав поле

Три ловушки, на которых спотыкаются

  • Ключ в словаре изменился. Объект положили в Dictionary или HashSet, а потом поменяли поле, участвующее в GetHashCode: хеш стал другим, и объект «потерялся». Поэтому ключи делают неизменяемыми.
  • Внутри record — массив. Сгенерированный Equals сравнит поля, а для массива это сравнение ссылок: два record с одинаковым содержимым массивов будут не равны. Нужен свой Equals с SequenceEqual.
  • GetHashCode «на глаз». Если вернуть константу, всё скомпилируется, но все объекты попадут в одну корзину, и словарь выродится в список. Используйте HashCode.Combine.
★ Что запомнить
  • Equals — «равны ли по значению», GetHashCode — «в какую корзину положить»; переопределяют парой.
  • Коллекции (Dictionary, HashSet, LINQ) используют Equals/GetHashCode, а не ==.
  • IEquatable<T> — типизированный Equals, без бокса для struct.
  • record генерирует Equals, GetHashCode, ==, ToString, with — писать руками не нужно.
  • with — копия с изменением; init — «задать при создании»; required — «нельзя забыть».
  • Менять поле, участвующее в хеше, после вставки в словарь — значит потерять объект.
