Глава 22. Транзакции и уровни изоляции

ACID, READ COMMITTED, REPEATABLE READ, SERIALIZABLE

подводящая глава

Что такое транзакция

Транзакция — это набор операторов, который база выполняет как одно целое: либо все изменения применяются, либо ни одно. Границы задаются явно:

BEGIN;                                  -- начали транзакцию

UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;

COMMIT;                                 -- зафиксировали: оба изменения видны навсегда

-- или
ROLLBACK;                               -- отменили: как будто ничего не было

Без BEGIN каждый оператор — сам себе транзакция (авто-коммит): выполнился и зафиксировался.

Главная мысль

Транзакция нужна там, где несколько изменений должны примениться вместе. Один UPDATE атомарен и без неё.

Зачем это помнить на собеседовании

ACID — не «свойство базы вообще», а набор гарантий, каждая из которых имеет цену. Изоляцию можно ослабить (и получить больше параллельности), надёжность — ускорить (synchronous_commit = off, теряя последние коммиты при сбое). Выбор всегда компромисс.

Долгая транзакция — это дорого

Пока транзакция открыта, база держит для неё:

  • снимок → VACUUM не может удалить версии, которые ещё «видны» → растёт bloat (глава 25);
  • блокировки изменённых строк → другие транзакции ждут (глава 24);
  • в приложении — соединение из пула → оно недоступно другим запросам (глава 23 .NET-раздела).
-- кто держит транзакции дольше всего
SELECT pid,
       state,
       now() - xact_start AS xact_age,
       left(query, 50)    AS last_query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_age DESC
LIMIT 10;

Вот как это выглядит на живой базе: одна сессия сделала UPDATE и «забыла» закрыть транзакцию, вторая выполняет долгий запрос, а третья — сам этот диагностический запрос:

  pid |        state        |    xact_age     |                     last_query
------+---------------------+-----------------+----------------------------------------------------
  235 | idle in transaction | 00:00:02.984549 | UPDATE accounts SET balance = balance - 1 WHERE id
  242 | active              | 00:00:02.006254 | SELECT pg_sleep(16);
  249 | active              | 00:00:00        | SELECT pid,                                       +
      |                     |                 |        state,                                     +
      |                     |                 |        now() - xact_star
(3 rows)

Что здесь читать:

  • xact_age — сколько живёт транзакция. Первые строки списка — подозреваемые. Миллисекунды и пара секунд — норма (обычный запрос), минуты — уже повод смотреть, кто это и зачем.
  • state — самое важное поле. idle in transaction значит: транзакция открыта, но сессия ничего не делает. Это почти всегда ошибка в коде (BEGIN без COMMIT, забытый using/Dispose, ожидание HTTP-ответа внутри транзакции), а не «тяжёлый запрос».
  • last_query — последний запрос сессии (обрезан до 50 символов). По нему видно, какой именно код оставил транзакцию, и дальше искать уже в приложении.
  • Последняя строка — сам диагностический запрос. Он тоже выполняется в транзакции, поэтому попадает в собственный вывод с возрастом 00:00:00. Это нормально.
stateЧто означаетОпасность
activeВыполняется запрос — или сессия ждёт блокировку (см. ниже) Зависит от длительности: секунды — норма, минуты — проблема

Осторожно: active не всегда значит «работает». Сессия, которая просто ждёт чужую блокировку, тоже в состоянии active — отличает её поле wait_event:

SELECT pid, state, wait_event_type, wait_event,
       now() - query_start AS query_age, left(query, 40) AS last_query
FROM   pg_stat_activity
WHERE  backend_type = 'client backend'
ORDER  BY pid;

--  pid |        state        | wait_event_type |  wait_event   |  query_age   | last_query
-- -----+---------------------+-----------------+---------------+--------------+----------------------
--  548 | idle in transaction | Client          | ClientRead    | 00:00:03.517 | UPDATE accounts SET …
--  556 | active              | Lock            | transactionid | 00:00:02.009 | UPDATE accounts SET …
--  562 | active              |                 |               | 00:00:00     | SELECT pid, …

Сессия 556 «активна» уже две секунды, но не работает: wait_event = transactionid значит «ждёт, пока закончится транзакция, которая держит эту строку». Держит её 548 — та самая, что висит в idle in transaction. Так выглядят блокировки, которые потом превращаются в дедлоки (глава 24).

Чего этот запрос не покажет

Фильтр WHERE xact_start IS NOT NULL отсекает две категории сессий. Первая — обычные idle-соединения (это хорошо). Вторая — прерванные незакрытые транзакции (idle in transaction (aborted)): у них xact_start пустой, хотя транзакция формально открыта. Проверено: такая сессия в вывод не попадает, но блокировок она уже не держит (pg_locks для неё пуст — при ошибке PostgreSQL их освободил). Опасность в другом: она занимает соединение из пула и держит блок транзакции.

Если хотите видеть и такие сессии, фильтруйте по state:

SELECT pid, state, now() - xact_start AS xact_age, left(query, 50) AS last_query
FROM   pg_stat_activity
WHERE  state <> 'idle'            -- всё, что не «просто соединение»
ORDER  BY xact_start DESC NULLS LAST
LIMIT  10;

--  pid |             state             | xact_age |     last_query
-- -----+-------------------------------+----------+--------------------
--  508 | active                        | 00:00:00 | SELECT pid, …
--  498 | idle in transaction           | 00:00:02 | UPDATE accounts …
--  496 | active                        | 00:00:02 | SELECT pg_sleep(16);
--  495 | idle in transaction (aborted) |          | SELECT 1/0 AS boom;

Что делать с найденной сессией. Сначала понять, чей это код (last_query плюс application_name, client_addr, usename — они есть в той же pg_stat_activity). Если ждать нельзя — две команды, и они делают разное (проверено):

КомандаЧто делаетЧто увидит сессия-жертва
pg_cancel_backend(pid)Отменяет текущий запрос; соединение и транзакция остаютсяERROR: canceling statement due to user request (код 57014)
pg_terminate_backend(pid)Обрывает соединение целиком FATAL: terminating connection due to administrator command
Особый случай: idle in transaction

Транзакция открыта, но запросов нет — приложение «забыло» её закрыть (например, ждёт ответа внешнего сервиса или пользователя). Лечится короткими транзакциями и настройкой сервера: idle_in_transaction_session_timeout сама прибьёт такую сессию — она получит FATAL: terminating connection due to idle-in-transaction timeout (проверено).

Правила работы с транзакциями

  1. Транзакция — только вокруг работы с БД. Сеть, расчёты, ожидание ответа — до или после.
  2. Короткая. Ориентир — миллисекунды, а не секунды.
  3. Защитные таймауты — чтобы «залипшая» транзакция не держала ресурсы вечно.
  4. Retry на 40001/40P01 — это штатная ситуация (40001 — конфликт сериализации, 40P01 — дедлок; что это за коды — ниже).
  5. Уровень изоляции — по сценарию, а не «чем выше, тем лучше».
BEGIN;
SET LOCAL lock_timeout      = '2s';   -- не ждать блокировку дольше 2 секунд
SET LOCAL statement_timeout = '5s';   -- не выполнять запрос дольше 5 секунд

-- … работа с БД …

COMMIT;

Где и как долго они действуют. Разница — в слове LOCAL. Граница проходит не по функции и не по «блоку кода», а по транзакции:

Как заданоДо какого момента действуетПроверено
SET LOCAL имя = …До конца транзакции (COMMIT/ROLLBACK); вне транзакции не работает вовсе BEGIN; SET LOCAL statement_timeout = '1s'; … COMMIT; → SHOW statement_timeout снова 0
SET имя = … (без LOCAL)До конца соединения (или RESET)после SET statement_timeout = '1s' значение 1s остаётся и после запросов, и после COMMIT
SET в шапке функцииТолько на время выполнения функции после SELECT f(); → SHOW statement_timeout = 0

Мелочь, которую полезно знать: SET LOCAL вне транзакции не сработает — сервер вернёт WARNING: SET LOCAL can only be used in transaction blocks, а значение останется прежним. Поэтому SET LOCAL и пишут сразу после BEGIN.

А если SET LOCAL стоит внутри функции? Тогда ответ зависит от того, закончилась ли транзакция. Четыре случая, все проверены:

CREATE FUNCTION f_local() RETURNS text LANGUAGE plpgsql AS $$
BEGIN
    SET LOCAL statement_timeout = '7s';      -- «на текущую транзакцию»
    RETURN 'done';
END $$;
CREATE FUNCTION f_session() RETURNS text LANGUAGE plpgsql AS $$
BEGIN
    SET statement_timeout = '3s';            -- «на текущее соединение»
    RETURN 'done';
END $$;
CREATE FUNCTION f_clause() RETURNS text LANGUAGE plpgsql
SET statement_timeout = '4s' AS $$           -- «только пока выполняется функция»
BEGIN
    RETURN 'done';
END $$;

-- 1) f_local внутри BEGIN…COMMIT: установка ПЕРЕЖИВАЕТ выход из функции
BEGIN;
SELECT f_local();        -- done
SHOW statement_timeout;  -- 7s   ← действует на всю транзакцию, а не только на функцию
COMMIT;
SHOW statement_timeout;  -- 0    ← транзакция кончилась, настройка ушла

-- 2) f_local одним оператором (без BEGIN): «транзакция» = этот оператор
SELECT f_local();        -- done
SHOW statement_timeout;  -- 0    ← ушло вместе с оператором

-- 3) f_session: SET без LOCAL «протекает» наружу
SELECT f_session();      -- done
SHOW statement_timeout;  -- 3s   ← осталось после функции, до конца соединения
RESET statement_timeout;
SHOW statement_timeout;  -- 0

-- 4) f_clause: SET в шапке функции восстанавливается на выходе
SELECT f_clause();       -- done
SHOW statement_timeout;  -- 0

Правило короткое: SET LOCAL живёт до конца транзакции, SET — до конца соединения. Функция тут ничего не меняет: «на одну функцию» настройку задаёт только SET в шапке функции. И именно поэтому в пуле соединений опасен SET без LOCAL: соединение вернётся в пул с чужим таймаутом, и следующий запрос другого клиента неожиданно упадёт. SET LOCAL так не «протекает» — он исчезает вместе с COMMIT.

Что именно ограничивает каждый таймаут. lock_timeout — только ожидание блокировки; statement_timeout — весь оператор целиком (включая это ожидание). Одна и та же ситуация: вторая сессия держит строку, первая её ждёт:

-- ограничили ожидание блокировки
SET LOCAL lock_timeout = '1s';
UPDATE accounts SET balance = balance - 1 WHERE id = 1;
-- ERROR:  55P03: canceling statement due to lock timeout
-- CONTEXT:  while updating tuple (0,1) in relation "accounts"

-- то же место, но ограничение на весь оператор
SET LOCAL statement_timeout = '1s';
UPDATE accounts SET balance = balance - 1 WHERE id = 1;
-- ERROR:  57014: canceling statement due to statement timeout
-- CONTEXT:  while updating tuple (0,1) in relation "accounts"

Смысл разницы: lock_timeout говорит «не жди чужую транзакцию дольше N» — приложение успеет вернуть 503 и повторить; statement_timeout — «не работай дольше N вообще» (чтобы тяжёлый отчёт не съел соединение на минуты). Оба кода, 55P03 и 57014, — в таблице «Ошибки, которые надо повторять» ниже.

Уровни изоляции

Уровень изоляции отвечает на вопрос: что транзакция видит из изменений других транзакций. По умолчанию в PostgreSQL — read committed. Задаётся он до начала работы, и от места зависит, на что распространяется — на одну транзакцию или на все следующие:

Где задатьНа что действуетПроверено
BEGIN ISOLATION LEVEL REPEATABLE READ;только на эту транзакциювнутри SHOW transaction_isolation → repeatable read; после COMMIT → снова read committed
BEGIN; SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;на эту транзакцию, но только до первого запросапосле любого SELECT: ERROR: SET TRANSACTION ISOLATION LEVEL must be called before any query
SET SESSION CHARACTERISTICS AS TRANSACTION ISOLATION LEVEL REPEATABLE READ; на все последующие транзакции этого соединения SHOW default_transaction_isolation → repeatable read, и каждая новая BEGIN начинается с него
ALTER DATABASE shop SET default_transaction_isolation = 'repeatable read'; (или ALTER ROLE …)на все новые соединения к базе (роли) действует постоянно и переживает перезапуск; RESET в сессии его не отменяет
В коде приложения: уровень передают при открытии транзакции (BeginTransactionAsync(IsolationLevel.RepeatableRead, …))на транзакцию, которую открыл кодпример на C# — глава 23
 
SHOW default_transaction_isolation;      -- read committed

BEGIN ISOLATION LEVEL REPEATABLE READ;
SHOW transaction_isolation;              -- repeatable read   ← действует
COMMIT;
SHOW transaction_isolation;              -- read committed    ← и уже не действует

BEGIN;
SELECT 1;                                -- любой запрос уже начал транзакцию

-- ERROR:  SET TRANSACTION ISOLATION LEVEL must be called before any query

BEGIN;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
SHOW transaction_isolation;              -- serializable      ← успели до первого запроса
COMMIT;

-- «на всю сессию», а не на одну транзакцию:
SET SESSION CHARACTERISTICS AS TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SHOW default_transaction_isolation;      -- repeatable read
BEGIN;
SHOW transaction_isolation;              -- repeatable read   ← каждая следующая тоже
COMMIT;
RESET default_transaction_isolation;     -- вернули как было

Зачем всё это на практике. Две сессии, одна и та же последовательность: A открывает транзакцию и читает баланс, B в этот момент его меняет, A читает ещё раз.

-- сессия A: READ COMMITTED (по умолчанию)
BEGIN ISOLATION LEVEL READ COMMITTED;
SELECT balance FROM accounts WHERE id = 1;   -- 1000.00
SELECT pg_sleep(4);                          -- пауза, в это время работает сессия B
SELECT balance FROM accounts WHERE id = 1;   -- 1500.00  ← значение изменилось «под ногами»
COMMIT;

-- сессия B в паузе: UPDATE accounts SET balance = balance + 500 WHERE id = 1;

Те же действия с REPEATABLE READ:

BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT balance FROM accounts WHERE id = 1;   -- 1000.00
SELECT pg_sleep(4);
SELECT balance FROM accounts WHERE id = 1;   -- 1000.00  ← тот же снимок, данные «не поехали»
COMMIT;

Это и есть разница «снимок на каждый оператор» против «снимок на всю транзакцию»: в RC один и тот же запрос внутри одной транзакции может вернуть разные значения, в RR — нет.

Цена RR. Другая последовательность: A (в REPEATABLE READ) прочитала строку, B эту строку изменила и зафиксировала, а затем A пытается изменить её сама:

-- сессия A, та же транзакция из примера выше:
UPDATE accounts SET balance = balance - 10 WHERE id = 1;
-- ERROR:  40001: could not serialize access due to concurrent update
ROLLBACK;

PostgreSQL не может «применить изменение поверх того, чего транзакция не видела», и откатывает её. Это не сбой, а сигнал «повтори транзакцию целиком»: при повторе она увидит новое состояние, и конфликта не будет. Отсюда и правило выбора — уровни не «лучше/хуже», а под задачу (см. врезку ниже).

«Сериализация» в «конфликте сериализации» — это не про JSON

Сериализация транзакций (от series — «ряд, последовательность») — это режим, в котором база гарантирует: результат параллельных транзакций такой же, как если бы они выполнялись строго по очереди, одна за другой. Транзакции при этом идут одновременно — «очередь» существует только в смысле результата.

Чтобы так вышло, PostgreSQL (механизм SSI) запоминает, кто что прочитал и кто что записал, и ищет циклы зависимостей: «A прочитала данные, которые изменила B, а B — данные, которые изменила A». При таком цикле никакой последовательный порядок не даёт правильного результата. Это и есть сериализационный конфликт (аномалия сериализации).

Разрешить его «на лету» нельзя, поэтому одна из транзакций откатывается с кодом 40001 (serialization_failure). Это не сбой: база защитила данные, а приложение должно повторить транзакцию целиком — при повторе она увидит уже новое состояние, и цикла не будет.

И не путайте с сериализацией данных (объект → JSON/XML/байты): слово то же, смысл совсем другой.

Что выбирать
  • Read Committed — для обычных CRUD-операций: дёшево и достаточно.
  • Repeatable Read — для отчёта из нескольких запросов: все чтения из одного снимка.
  • Serializable — для правил «проверить и записать» (лимиты, остатки), обязательно с retry.

SAVEPOINT: откатить часть транзакции

Зачем это нужно. Транзакция — «всё или ничего» для всей группы операторов. Но бывает, что один шаг внутри неё рискованный, и при его неудаче терять всё остальное не хочется. Пример из этой главы: деньги со счёта уже списаны, а запись платежа может упасть из-за дубликата external_ref. Без SAVEPOINT такая ошибка отменяет всю транзакцию — вместе со списанием.

Что делает SAVEPOINT. Ставит внутри транзакции «закладку». После этого:

  • ROLLBACK TO SAVEPOINT sp — отменяет всё, что сделано после закладки; более ранние изменения (списание) остаются;
  • RELEASE SAVEPOINT sp — убирает закладку, ничего не отменяя;
  • транзакция остаётся живой: после отката к закладке работу можно продолжать и в конце сделать COMMIT.

Шаг 1. Что происходит без закладки. Две таблицы: accounts (балансы) и payments (платежи, у external_ref — UNIQUE). Списываем деньги и пишем платёж с номером, который уже занят другой строкой:

BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;          -- UPDATE 1
UPDATE payments SET external_ref = 'pay_999', status = 'sent' WHERE id = 42;
-- ERROR:  duplicate key value violates unique constraint "payments_external_ref_key"
-- DETAIL:  Key (external_ref)=(pay_999) already exists.
SELECT 1;
-- ERROR:  current transaction is aborted, commands ignored until end of transaction block
ROLLBACK;          -- выбора уже нет: COMMIT тоже не сработает

SELECT balance FROM accounts WHERE id = 1;
--  1000.00     ← списание отменилось вместе со всем остальным

Итог: не выполнено ничего. Одна ошибка «убила» всю транзакцию — в том числе удачное списание, которое к ошибке отношения не имело.

Шаг 2. Тот же случай, но с закладкой. Ставим SAVEPOINT прямо перед рискованным шагом:

BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;   -- UPDATE 1  (списание)
SAVEPOINT sp;                                              -- SAVEPOINT (закладка)

UPDATE payments SET external_ref = 'pay_999', status = 'sent' WHERE id = 42;
-- ERROR:  duplicate key value violates unique constraint "payments_external_ref_key"
-- DETAIL:  Key (external_ref)=(pay_999) already exists.
SELECT 1;
-- ERROR:  current transaction is aborted, commands ignored until end of transaction block
--   ↑ транзакция «мёртвая»: без отката к закладке дальше ничего не выполнится

ROLLBACK TO SAVEPOINT sp;                                  -- ROLLBACK (отмотали только упавший шаг)
UPDATE payments SET external_ref = 'pay_998', status = 'retry' WHERE id = 42;
-- UPDATE 1  (вторая попытка — уже проходит)
COMMIT;                                                    -- COMMIT

SELECT id, balance FROM accounts ORDER BY id;              -- 1 → 900.00  (списание сохранилось)
SELECT id, external_ref, status FROM payments ORDER BY id;
--  42 | pay_998 | retry     ← упавший шаг отменён, удачная попытка сохранена
--  43 | pay_999 | new

Итог: списание + удачная попытка, а неудачная попытка отменена. Ради этого SAVEPOINT и нужен.

Шаг 3. Если рискованный шаг прошёл. Продолжаем в той же базе: после шага 2 на счёте 900.00, у платежа 42 — pay_998/retry. Теперь номер свободен, шаг проходит — и закладка не нужна, её просто убирают:

BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;   -- UPDATE 1  (списание)
SAVEPOINT sp;                                              -- SAVEPOINT

UPDATE payments SET external_ref = 'pay_700', status = 'sent' WHERE id = 42;
-- UPDATE 1  (ошибки нет)

RELEASE SAVEPOINT sp;                                      -- RELEASE — закладка больше не нужна
COMMIT;                                                    -- COMMIT

SELECT balance FROM accounts WHERE id = 1;                 -- 800.00
SELECT id, external_ref, status FROM payments WHERE id = 42;
--  42 | pay_700 | sent     ← сохранён sent, а не retry

Итог: сохранён sent, ветка retry не выполнялась — её и не должно быть, ошибки ведь не было.

Почему нельзя «просто дописать ROLLBACK TO SAVEPOINT»

Соблазн: написать команды подряд, «на всякий случай» — пусть откат будет всегда, а вдруг ошибка. В чистом SQL так нельзя: ROLLBACK TO SAVEPOINT — это команда, а не конструкция «если ошибка». В такой записи итог одинаков при любом исходе:

BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
SAVEPOINT sp;
UPDATE payments SET status = 'sent' WHERE id = 42;   -- прошло успешно
ROLLBACK TO SAVEPOINT sp;                            -- ✘ всё равно отменяет шаг выше
UPDATE payments SET status = 'retry' WHERE id = 42;  -- и применяет «аварийную» ветку
COMMIT;

Результат — retry вместо sent, хотя ошибки не было. Откат «по факту неудачи» требует ветвления, а ветвления в чистом SQL нет: нужен PL/pgSQL (ниже) или код приложения.

Ошибка внутри транзакции «отравляет» её

После любой ошибки PostgreSQL помечает транзакцию как прерванную: следующие команды падают с current transaction is aborted. Помогает либо ROLLBACK целиком, либо откат к SAVEPOINT, если он был поставлен заранее. Именно поэтому savepoint — не «удобство», а единственный способ продолжить работу после ошибки внутри транзакции.

Прямые ответы на главный вопрос. Сравните «безусловную» запись из врезки выше и правильную схему:

Что произошло с шагом sentВыполнится ли retry? Как должно быть
Ошибка (шаг откатился)да — сразу после ROLLBACK TO SAVEPOINTда: это и есть обработка неудачи, после неё — COMMIT
Успех (шаг не откатился)в безусловной записи — да, и это ошибка: успешный sent будет стёртнет: нужен RELEASE SAVEPOINT и COMMIT, ветки retry не должно быть вовсе
Ошибка, а savepoint не ставилине выполнится ничего: транзакция уже прерванаостаётся ROLLBACK всей транзакции — списание тоже пропадёт

Короткая формула: retry — это ветка «если упало», а не следующий шаг. Значит нужен код с ветвлением — PL/pgSQL или C#.

Ветвление в PL/pgSQL: блок с EXCEPTION

Функция — это и есть «ветвление»: обычный код в BEGIN … END выполняется, пока не упадёт, а EXCEPTION — ветка «если упало».

CREATE OR REPLACE FUNCTION pay(p_id bigint, p_ref text)
RETURNS text
LANGUAGE plpgsql AS $$
BEGIN
    -- ↓↓↓ «тело блока»: операторы между BEGIN и EXCEPTION
    UPDATE payments SET external_ref = p_ref, status = 'sent' WHERE id = p_id;
    RETURN 'sent';                                  -- ошибки не было → выходим здесь
EXCEPTION
    WHEN unique_violation THEN                      -- сработал unique-индекс по external_ref
        -- сюда управление приходит уже ПОСЛЕ автоматического отката тела блока:
        -- для блоков с обработчиком PostgreSQL сам ставит savepoint на входе
        UPDATE payments SET status = 'retry' WHERE id = p_id;   -- ветка «если упало»
        RETURN 'retry';
END $$;

Где здесь «тело блока» и где «внешняя транзакция». Это две разные вещи, и путаница обычно из-за того, что обе выглядят как «код с BEGIN»:

  • Тело блока — операторы внутри функции, между её BEGIN и EXCEPTION: тот самый UPDATE … status = 'sent'. Именно он откатывается при ошибке.
  • Внешняя транзакция — транзакция вызывающей стороны, то есть того, кто вызвал функцию: BEGIN; UPDATE accounts …; SELECT pay(…); COMMIT;. Её изменения (списание денег) к телу блока не относятся и при ошибке внутри блока остаются.

Вот вызывающая сторона целиком — «внешняя транзакция» — и что получилось (проверено):

BEGIN;                                              -- ← внешняя транзакция начинается здесь
UPDATE accounts SET balance = balance - 100 WHERE id = 1;   -- списание, 1000.00 → 900.00

SELECT pay(42, 'pay_999') AS step;
--  step
-- -------
--  retry      ← внутри функции был дубликат, тело блока откатилось, сработал обработчик

INSERT INTO payments (id, external_ref, status) VALUES (44, 'pay_044', 'new');
-- INSERT 0 1  ← внешняя транзакция жива и продолжает работать
COMMIT;

SELECT id, balance FROM accounts ORDER BY id;
--  1 |  900.00   ← списание СОХРАНИЛОСЬ, хотя внутри блока была ошибка
--  2 | 1000.00

SELECT id, external_ref, status FROM payments ORDER BY id;
--  42 | pay_001 | retry    ← status изменён обработчиком, а external_ref остался старым:
--                            именно это и означает «откатилось только тело блока»
--  43 | pay_999 | new
--  44 | pay_044 | new      ← строка из внешней транзакции тоже сохранилась

Механизм, если коротко. Блок BEGIN … EXCEPTION … END — это неявный SAVEPOINT: PostgreSQL ставит закладку на входе в блок. Ошибка откатывает транзакцию до этой закладки — то есть только то, что успел сделать блок, — а дальше управление переходит в обработчик. Внешняя транзакция остаётся открытой.

А если обработчика нет? Тогда и закладки нет — ошибка откатывает всю транзакцию целиком, вместе со списанием. Проверено, та же функция без EXCEPTION:

BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;   -- UPDATE 1
SELECT pay_bad(42, 'pay_999');                              -- функция без EXCEPTION
-- ERROR:  duplicate key value violates unique constraint "payments_external_ref_key"
-- CONTEXT:  SQL statement "UPDATE payments SET external_ref = p_ref, status = 'sent' WHERE id = p_id"
-- PL/pgSQL function pay_bad(bigint,text) line 3 at SQL statement
INSERT INTO payments (id, external_ref, status) VALUES (45, 'pay_045', 'new');
-- ERROR:  current transaction is aborted, commands ignored until end of transaction block
COMMIT;                              -- psql ответит ROLLBACK: коммитить уже нечего

SELECT balance FROM accounts WHERE id = 1;                  -- 900.00 — как было, списание отменено
SELECT count(*) FROM payments WHERE id = 45;                -- 0 — строки нет

Разница между двумя вариантами — ровно в обработчике: с ним откатывается только тело блока, без него — вся транзакция вызывающей стороны.

  • Ловушка: обработчик ловит любую ошибку указанного класса. Проверяйте SQLSTATE/условие (WHEN unique_violation, а не WHEN others), иначе «проглотите» и настоящую аварию — и транзакция даже не заметит, что что-то пошло не так.
  • Практика: обработчик ставят вокруг рискованного шага (внешний вызов, вставка с UNIQUE, необязательная часть операции), а не на каждую функцию «на всякий случай» — иначе настоящие ошибки перестают быть видны.
  • В C# то же самое делается явно: SaveAsync("sp") → try { … } catch { await tx.RollbackAsync("sp"); … } (пример — в .NET-разделе, глава про транзакции и HTTP-вызовы).
  • Мелочи, которые спрашивают: после ROLLBACK TO SAVEPOINT сама закладка остаётся (к ней можно откатиться снова), RELEASE SAVEPOINT её удаляет, а COMMIT/ROLLBACK убирают все закладки.

Ошибки, которые надо повторять

Что такое 40001 и 40P01: это SQLSTATE — пятисимвольный код ошибки по стандарту SQL, который сервер возвращает вместе с сообщением. Первые два символа — класс ошибки: 40 = «откат транзакции из-за конкуренции». Дальше идёт конкретный код: 40001 — serialization_failure (конфликт при Repeatable Read/Serializable), 40P01 — deadlock_detected (две транзакции ждали друг друга), 55P03 — lock_not_available (истёк lock_timeout).

Где их видно: в psql — \errverbose после ошибки; в .NET — PostgresException.SqlState; в PL/pgSQL — EXCEPTION WHEN SQLSTATE '40001'. Именно по коду, а не по тексту сообщения, строят логику повтора: текст зависит от локали и версии.

КодИмяКогда возникаетЧто делать
40001serialization_failureКонфликт при Repeatable Read/SerializableПовторить транзакцию целиком
40P01deadlock_detectedДве транзакции ждут друг друга (глава 24)Повторить, порядок захвата — исправить
55P03lock_not_availablelock_timeout истёкПовторить позже

Поэтому retry — часть контракта транзакции, а не «костыль». Пример на C# — C#-книга, глава 21 и глава 23 .NET-раздела.

★ Что запомнить из главы
  • Транзакция — «всё или ничего»: BEGIN, изменения, COMMIT или ROLLBACK.
  • ACID — четыре гарантии: атомарность, согласованность, изоляция, надёжность; у каждой есть цена.
  • Уровень изоляции определяет, что видно из чужих изменений: RC (по умолчанию), RR (снимок на транзакцию), Serializable (конфликты → 40001).
  • SAVEPOINT — откат части транзакции; ошибка внутри транзакции «отравляет» её до ROLLBACK.
  • Retry — часть контракта, а не костыль.
  • Долгая транзакция держит снимок, блокировки и соединение — это причина bloat, deadlock’ов и таймаутов.
