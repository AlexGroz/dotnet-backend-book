Строка подключения: каждый ключ

Строка — это набор пар Ключ=Значение, разделённых точкой с запятой. Регистр ключей не важен, пробелы вокруг = допускаются. Ниже — рабочий набор с объяснением, что делает каждая пара:

Host=db.internal          -- имя хоста или IP сервера PostgreSQL
Port=5432                 -- порт; по умолчанию 5432
Database=app              -- имя базы (не схемы!), к которой подключаемся
Username=app_user         -- роль PostgreSQL
Password=***              -- пароль роли
SSL Mode=Require          -- Require проверяет шифрование и требует доверенный сертификат
Application Name=orders-api -- имя, которое видно в pg_stat_activity.application_name
Search Path=app,public    -- какие схемы искать, если схема не указана в имени таблицы
Pooling=true              -- включить пул соединений (по умолчанию true)
Minimum Pool Size=2       -- сколько соединений держать открытыми даже без нагрузки
Maximum Pool Size=50      -- предел одновременных соединений этого процесса
Timeout=5                 -- сколько секунд ждать свободное соединение из пула
Command Timeout=30        -- предел выполнения одной команды, секунды
Keepalive=30              -- TCP keepalive, чтобы мёртвое соединение не висело вечно
Include Error Detail=true -- вернуть Detail/Where из сервера (по умолчанию они скрыты)
Max Auto Prepare=10       -- сколько разных запросов готовить на сервере автоматически
Две пары, которые путают чаще всего
  • Timeout и Command Timeout — разные вещи. Timeout — сколько ждать свободное соединение из пула; Command Timeout — сколько ждать ответа на уже отправленную команду. В прогоне Command Timeout=1 на SELECT pg_sleep(3) дал NpgsqlException: Exception while reading from stream с внутренним TimeoutException: Timeout during reading attempt — то есть ошибка приходит обёрнутой, а не «сама по себе».
  • Database — это база, а не схема. Схема (public, app) задаётся Search Path или полным именем таблицы app.orders.

Проверка «кто я и откуда» — тот же application_name виден на сервере:

-- application_name и адрес клиента для всех соединений
SELECT application_name, client_addr, state
FROM pg_stat_activity
WHERE datname = current_database();

Один запрос целиком, строка за строкой

// 1) Источник соединений. Создаётся ОДИН раз на процесс: внутри него живёт пул.
await using var dataSource = new NpgsqlDataSourceBuilder(connectionString).Build();

// 2) Соединение берётся из пула. await using вернёт его в пул при выходе из области.
await using var conn = await dataSource.OpenConnectionAsync(ct);

// 3) Команда: SQL с позиционными параметрами $1, $2 (нумерация начинается с единицы).
await using var cmd = new NpgsqlCommand(
    "SELECT id, total FROM orders WHERE customer_id = $1 AND status = $2", conn);

// 4) Параметры: тип задаётся кодом, а не выводится «как получится».
cmd.Parameters.Add(new NpgsqlParameter<Guid> { TypedValue = customerId });   // $1 → uuid
cmd.Parameters.Add(new NpgsqlParameter<string> { TypedValue = "new" });      // $2 → text

// 5) Чтение: reader отдаёт строки по одной и не тянет весь результат в память.
await using var reader = await cmd.ExecuteReaderAsync(ct);
while (await reader.ReadAsync(ct))          // true — строка есть, false — набор закончился
{
    var id = reader.GetGuid(0);             // колонка 0: uuid → Guid
    var total = reader.GetDecimal(1);       // колонка 1: numeric → decimal
    Console.WriteLine($"{id}: {total}");
}

Разбор каждого элемента:

  • NpgsqlDataSourceBuilder — конструктор источника: принимает строку подключения и позволяет донастроить типы/логирование; Build() создаёт NpgsqlDataSource — неизменяемый объект с пулом внутри. Держать его в static/singleton — норма; создавать на каждый запрос — ошибка (новый пул на каждый вызов).
  • OpenConnectionAsync(ct) — взять соединение из пула; ct отменяет ожидание (если пул исчерпан, ожидание закончится токеном или Timeout).
  • await using — вернуть соединение в пул даже при исключении (глава 23 C#-книги); физически TCP-соединение при этом не закрывается.
  • $1, $2 — позиционные параметры PostgreSQL. Именованный вид @status Npgsql тоже поддерживает, но на сервер всё равно уходят позиционные — не смешивайте стили в одном запросе.
  • NpgsqlParameter<T> с TypedValue — параметр с известным типом: Npgsql отправляет его как uuid/text, и серверу не нужно угадывать.
  • ExecuteReaderAsync + ReadAsync — потоковое чтение. Для «одного значения» короче ExecuteScalarAsync, для «сколько строк изменено» — ExecuteNonQueryAsync.
  • GetGuid(0)/GetDecimal(1) — типизированные геттеры по номеру колонки; надёжнее номера — GetOrdinal("total"), если порядок колонок может измениться.

Параметры: почему строка вместо Guid — не «мелочь»

Классическая ошибка — положить в параметр строку, потому что «в базе uuid выглядит как строка». Результат в прогоне:

A) строковый параметр: 42883 — operator does not exist: uuid = text

42883 — SQLSTATE «undefined_function»: у PostgreSQL нет оператора сравнения uuid = text, и неявного приведения тут тоже нет. В psql такой же запрос работает, потому что литерал '86b6e5fa-…' имеет «неизвестный» тип и сервер сам решает, что это uuid. Параметр из приложения приходит с уже объявленным типом text — и сравнение невозможно.

С правильным типом индекс используется (тот же запрос, параметр Guid):

Bitmap Heap Scan on np_orders  (cost=14.74..734.08 rows=300 …)
  Recheck Cond: (customer_id = '86b6e5fa-bb80-443f-909b-7ee713e8ef83'::uuid)
  ->  Bitmap Index Scan on np_orders_customer_idx
        Index Cond: (customer_id = '86b6e5fa-…'::uuid)

Три правила про параметры:

  • Не склеивайте SQL строками. Это и путь к SQL-инъекции, и удар по плану: каждый текст — новый запрос, подготовка не работает.
  • Не полагайтесь на AddWithValue. Он выводит тип из .NET-значения: для string получится text, для DateTime — timestamp (без зоны). Явный NpgsqlParameter<T> или NpgsqlDbType снимает неоднозначность.
  • Приведение в SQL — не решение. WHERE customer_id = $1::text или ::uuid вокруг колонки отключает индекс (подробно — глава 24 .NET-раздела про неявные приведения).

Что приходит из базы в .NET

Типы Npgsql сопоставляет сам, но знать соответствия нужно: именно здесь появляются «неожиданные» DateTime вместо даты и string вместо объекта. Замер: один запрос возвращает значения разных типов, справа — что вернул GetValue:

timestamptzSystem.DateTime с Kind=Utc GetFieldValue<DateTimeOffset>(i) — если нужна зона
numericSystem.DecimalGetDecimal(i)
jsonbSystem.String (текст JSON) GetFieldValue<Meta>(i) — если включён динамический JSON
int[]System.Int32[]GetFieldValue<int[]>(i)
intervalSystem.TimeSpanGetFieldValue<TimeSpan>(i)
dateSystem.DateTimeGetFieldValue<DateOnly>(i)

Почему date — это DateTime

Так сложилось исторически: Npgsql отдаёт date как DateTime с временем 00:00:00, чтобы не ломать старый код. Явный GetFieldValue<DateOnly> в прогоне вернул 1/1/2024 — современный тип доступен, но его нужно попросить. С timestamptz наоборот: DateTime уже помечен Kind=Utc (2026-11-20T11:03:29.3534130Z), а DateTimeOffset сохраняет смещение.

jsonb по умолчанию — просто строка. Чтобы читать и писать объекты, у источника включают динамический JSON (проверено: POCO ушёл в jsonb и вернулся объектом):

// 1) Источник с поддержкой POCO ↔ jsonb
var builder = new NpgsqlDataSourceBuilder(connectionString);
builder.EnableDynamicJson();                 // разрешает сериализовать объекты в jsonb и обратно
await using var dataSource = builder.Build();

// 2) Запись: параметр-объект отправляется как jsonb
await using var insert = dataSource.CreateCommand("INSERT INTO meta (id, data) VALUES ($1, $2)");
insert.Parameters.Add(new NpgsqlParameter<int> { TypedValue = 1 });                    // $1 → int4
var json = insert.Parameters.Add(new NpgsqlParameter<Meta> { TypedValue = new Meta("gold", 3) });
json.NpgsqlDbType = NpgsqlDbType.Jsonb;      // без этого объект уйдёт как составной тип, а не JSON
await insert.ExecuteNonQueryAsync();

// 3) Чтение: строка JSON или сразу объект
await using var read = dataSource.CreateCommand("SELECT data FROM meta WHERE id = 1");
await using var reader = await read.ExecuteReaderAsync();
await reader.ReadAsync();
Console.WriteLine(reader.GetValue(0));              // String = {"Level": "gold", "Points": 3}
Console.WriteLine(reader.GetFieldValue<Meta>(0));  // Meta  = gold/3

Много строк: batch, COPY и одна транзакция

Три способа записать много строк и цена каждого — замер на одном и том же наборе:

10 000 INSERT по одному, каждый в своей транзакции   4736 мс
10 000 INSERT по одному, но в ОДНОЙ транзакции       1577 мс
10 000 INSERT через NpgsqlBatch                       378 мс
100 000 строк через COPY BINARY                       802 мс  (≈8 мкс на строку)

Откуда разница. «По одному» без транзакции — это 10 000 отдельных транзакций, и каждая завершается COMMIT с записью журнала на диск (fsync): отсюда 4.7 с. Те же вставки в одной транзакции убирают цену коммита — 1.6 с, но остаются накладные расходы на круг «запрос → ответ» (около 0.15 мс каждый). NpgsqlBatch отправляет все команды одним пакетом — 0.38 с. COPY — потоковый протокол загрузки без разбора SQL на каждую строку — 0.8 с на 100 000.

// NpgsqlBatch: команды копятся в объекте и уходят на сервер одним пакетом
await using var batch = new NpgsqlBatch(conn);                       // пакет привязан к соединению
foreach (var row in rows)
{
    var item = new NpgsqlBatchCommand(                              // одна команда внутри пакета
        "INSERT INTO orders (id, customer_id, total, status) VALUES ($1, $2, $3, 'batch')");
    item.Parameters.Add(new NpgsqlParameter<Guid> { TypedValue = row.Id });        // $1
    item.Parameters.Add(new NpgsqlParameter<Guid> { TypedValue = row.Customer });  // $2
    item.Parameters.Add(new NpgsqlParameter<decimal> { TypedValue = row.Total });  // $3
    batch.BatchCommands.Add(item);                                  // положили в пакет, на сервер пока нет
}
await batch.ExecuteNonQueryAsync();                                 // один round-trip на всё
// COPY: строки идут потоком, формат BINARY — без текстового разбора
await using var importer = await conn.BeginBinaryImportAsync(
    "COPY orders (id, customer_id, total, status) FROM STDIN (FORMAT BINARY)");   // открыть поток
for (var i = 0; i < 100_000; i++)
{
    await importer.StartRowAsync();                                 // отметить начало строки
    await importer.WriteAsync(Guid.NewGuid(), NpgsqlDbType.Uuid);   // колонка 1 → uuid
    await importer.WriteAsync(Guid.NewGuid(), NpgsqlDbType.Uuid);   // колонка 2 → uuid
    await importer.WriteAsync(10m + i, NpgsqlDbType.Numeric);       // колонка 3 → numeric
    await importer.WriteAsync("copy", NpgsqlDbType.Text);           // колонка 4 → text
}
await importer.CompleteAsync();                                     // закрыть поток и зафиксировать

Когда что: одиночные операции — обычные INSERT/UPDATE в своих транзакциях; пачка десятков-сотен — NpgsqlBatch; загрузка тысяч и миллионов — COPY (это же самый быстрый способ наполнить таблицу для тестов). Важное ограничение: COPY не умеет INSERT ... ON CONFLICT — конфликты он не разрешает, поэтому для «вставь или обнови» он не подходит.

Подготовленные запросы

Подготовка — это когда сервер один раз разбирает и планирует запрос, а дальше получает только параметры. В Npgsql она автоматическая: при Max Auto Prepare=N запрос готовится после третьего выполнения (по умолчанию Auto Prepare Min Usages=3) — проверено подсчётом pg_prepared_statements:

выполнений 1 → подготовлено 0
выполнений 2 → подготовлено 0
выполнений 3 → подготовлено 1
выполнений 5 → подготовлено 1

Сколько это даёт: на запросе, который сам выполняется 6 мс (count(*) по 130 тысячам строк), тысяча вызовов заняла 6541 мс без подготовки и 6162 мс с ней — около 6 %. Выгода мала, потому что время уходит на выполнение, а не на планирование. На сложных запросах с дорогим планом и на коротких повторяемых запросах (точечный SELECT по индексу) доля планирования выше — там эффект заметнее. Настройки:

Max Auto Prepare=10            -- держать до 10 подготовленных запросов на соединение (0 = выключено)
Auto Prepare Min Usages=3      -- после скольких выполнений готовить (ключ проверен: принимается)
-- что реально подготовлено на этом соединении
SELECT name,        -- имя, которое выдал сервер (у Npgsql — вида _p1)
       statement,   -- нормализованный текст запроса
       prepare_time -- когда подготовлен
FROM pg_prepared_statements;

Ловушка: подготовленный план зависит от параметров. Если данные распределены неравномерно (95 % заказов в статусе new), план «через индекс» может оказаться хуже для частого значения — это та же история, что с generic-планами, и лечится Auto Prepare Min Usages=0 для таких запросов или переписыванием запроса.

Ошибки: что именно читать

Ошибки БД приходят двумя разными типами, и путать их нельзя:

  • PostgresException — сервер вернул ошибку (ErrorResponse). У неё есть SqlState, ConstraintName, TableName, Detail, Hint.
  • NpgsqlException — проблема на стороне клиента или сети: таймаут, разорванное соединение, исчерпанный пул. Внутри обычно лежит настоящее исключение.
try
{
    await cmd.ExecuteNonQueryAsync(ct);                 // любая команда может нарушить ограничение
}
catch (PostgresException ex)                            // сервер ответил ошибкой
{
    Console.WriteLine($"SQLSTATE={ex.SqlState}");        // код по стандарту SQL, например 23505
    Console.WriteLine($"constraint={ex.ConstraintName}");// имя нарушенного ограничения: np_orders_pkey
    Console.WriteLine($"detail={ex.Detail}");            // подробности; по умолчанию скрыты, см. ниже
    Console.WriteLine($"transient={ex.IsTransient}");    // «стоит ли повторить»: для 23505 false
}
catch (NpgsqlException ex)                              // сеть, пул, таймаут
{
    Console.WriteLine($"{ex.GetType().Name}: {ex.Message}; inner={ex.InnerException?.Message}");
}

В прогоне без настройки сообщение содержало: Detail redacted as it may contain sensitive data. Specify 'Include Error Detail' in the connection string to include this information. С Include Error Detail=true пришло настоящее: Key (id)=(5550b1f-…) already exists. Сделано специально: подробности могут содержать значения из строк. Включайте осознанно — в разработке полезно, в проде это утечка данных в логи.

Ретраи: повторяют только «конкурентные» коды (40001, 40P01, 55P03) и сетевые сбои, и только если операция идемпотентна или транзакция целиком повторяема. Нарушение уникальности (23505) не ретраят никогда — повтор даст ту же ошибку.

Пул соединений: правила и как проверить

Соединение в PostgreSQL — это отдельный серверный процесс, и их число ограничено max_connections. Поэтому Npgsql держит пул: OpenAsync не создаёт новое TCP-соединение каждый раз, а берёт готовое; Dispose возвращает его обратно. Если свободных нет, начинается ожидание до Timeout, после чего приходит понятная ошибка (проверено на пуле из одного соединения):

The connection pool has been exhausted, either raise 'Max Pool Size' (currently 1)
or 'Timeout' (currently 1 seconds) in your connection string.
  • Один источник на процесс. NpgsqlDataSource создаётся один раз и живёт всё время работы приложения; новый экземпляр — это новый пул, то есть соединения сверх бюджета.
  • Открывайте поздно, закрывайте рано. Не держите соединение, пока идёт расчёт или HTTP-вызов: пул считает именно открытые соединения (глава 23 .NET-раздела).
  • Бюджет. Maximum Pool Size × число инстансов ≤ max_connections − запас. При трёх инстансах и пуле 100 на сервере с max_connections=200 вы упрётесь в лимит сервера, а не в свой.
-- сколько соединений занято приложением и что они делают
SELECT application_name,                -- имя из строки подключения
       state,                           -- active / idle / idle in transaction
       count(*) AS connections          -- сколько таких
FROM pg_stat_activity
WHERE datname = current_database()      -- только текущая база
GROUP BY application_name, state
ORDER BY connections DESC;

-- «забытые» транзакции: соединение держится, но ничего не делает
SELECT pid, application_name, state, now() - state_change AS how_long
FROM pg_stat_activity
WHERE state = 'idle in transaction'     -- открыли транзакцию и не закрыли
ORDER BY how_long DESC;

idle in transaction — самый частый источник проблем: транзакция не закрыта, снимок держится, VACUUM не может убрать мёртвые версии (глава 25). Причина обычно одна: транзакцию открыли и ушли в HTTP-вызов.

DI и EF Core

В приложении источник регистрируется как singleton, а соединения открываются на операцию:

// Источник соединений — один на приложение; контейнер вызовет Dispose при остановке
builder.Services.AddSingleton(_ => new NpgsqlDataSourceBuilder(connectionString).Build());

// Источник внедряется туда, где нужен ручной SQL
public sealed class ReportStore(NpgsqlDataSource dataSource)      // зависимость из DI
{
    public async Task<int> CountAsync(CancellationToken ct)       // токен запроса
    {
        await using var conn = await dataSource.OpenConnectionAsync(ct);  // взяли из пула
        await using var cmd = conn.CreateCommand();               // команда на этом соединении
        cmd.CommandText = "SELECT count(*) FROM orders";          // текст SQL
        return Convert.ToInt32(await cmd.ExecuteScalarAsync(ct)); // при выходе вернётся в пул
    }
}
// EF Core: тот же Npgsql работает под провайдером
builder.Services.AddDbContext<AppDbContext>(o =>
    o.UseNpgsql(connectionString));        // пакет Npgsql.EntityFrameworkCore.PostgreSQL

// Миграции — из командной строки, с тем же провайдером:
// dotnet ef migrations add Initial     -- создать миграцию
// dotnet ef database update            -- применить её к базе

Практическое разделение: EF Core — сущности и обычные запросы (глава 24 .NET-раздела); ручной Npgsql — массовые операции (COPY, NpgsqlBatch), сложные отчёты и места, где нужен полный контроль над SQL. Оба варианта должны смотреть на один NpgsqlDataSource/строку подключения, иначе пулы и бюджеты соединений считаются отдельно.

★ Что запомнить
  • Строка подключения: Timeout — ожидание соединения из пула, Command Timeout — предел выполнения команды; Database — база, а не схема.
  • Параметры — типизированные (NpgsqlParameter<T>/NpgsqlDbType). Строка вместо Guid даёт 42883 operator does not exist: uuid = text; с правильным типом запрос идёт по индексу.
  • jsonb по умолчанию — string; POCO включается EnableDynamicJson(). date приходит как DateTime, но GetFieldValue<DateOnly> работает.
  • Массовая запись: 10 000 по одному — 4736 мс, в одной транзакции — 1577 мс, NpgsqlBatch — 378 мс, COPY на 100 000 — 802 мс.
  • Автоподготовка включается после третьего выполнения (Max Auto Prepare, Auto Prepare Min Usages); на «тяжёлых» запросах выигрыш мал, на коротких повторяемых — заметнее.
  • Ошибки: PostgresException.SqlState — код, ConstraintName — ограничение, Detail скрыт без Include Error Detail=true; ретраят только 40001/40P01/55P03.
  • Пул: один NpgsqlDataSource на процесс, соединение открывается на операцию, бюджет считается по max_connections; idle in transaction — красный флаг.
