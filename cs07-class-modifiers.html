Глава 7. Модификаторы типов: sealed, abstract, static, record

Почему в коде пишут public sealed class, чем abstract отличается от интерфейса, зачем нужен partial и когда брать record.

основная глава

Карта модификаторов

МодификаторЧто означаетТипичный пример
sealedОт типа нельзя наследоватьсяpublic sealed class UserDto
abstractНельзя создать экземпляр, нужен наследникabstract class PaymentHandler

readonlyПоля задаются только в конструктореreadonly struct Money

Модификаторы комбинируются: public sealed record OrderDto, internal static partial class Generated. Порядок слов фиксирован правилами языка, но читается он именно так: доступ → «вид» типа → остальное.

sealed: запрет наследования

public sealed class UserDto            // от UserDto нельзя наследоваться
{
    public int Id { get; init; }
    public string Name { get; init; } = "";
}

// class AdminDto : UserDto { }        // ошибка компиляции

Зачем это нужно на практике:

  • Контракт защищён. Никто (включая вас через год) не «дополнит» DTO наследником и не сломает сериализацию или логику сравнения.
  • Понятнее код. Читатель видит: это конечный тип, искать наследников не нужно.
  • Производительность. Для sealed-методов JIT может не проверять таблицу виртуальных вызовов и делать вызов напрямую (девиртуализация) — важно на горячем пути.
  • Безопасность. Чужой код не сможет подменить поведение наследником.
public class Repository
{
    public virtual void Save() { … }
}

public sealed class OrderRepository : Repository
{
    public sealed override void Save() { … }   // «дальше уже нельзя переопределять»
}

Классический пример из .NET: string объявлен sealed — иначе можно было бы создать «строку с другим поведением» и сломать все гарантии неизменяемости (глава 1).

abstract против интерфейса

public abstract class NotificationSender
{
    protected NotificationSender(ILogger logger) => Logger = logger;   // общее состояние
    protected ILogger Logger { get; }

    public abstract Task SendAsync(string to, string text, CancellationToken ct);   // обязано быть реализовано

    protected void Log(string message) => Logger.LogInformation(message);            // готовая логика
}

public sealed class EmailSender : NotificationSender
{
    public EmailSender(ILogger logger) : base(logger) { }
    public override Task SendAsync(string to, string text, CancellationToken ct) { … }
}

В прикладном коде правило простое: интерфейс — когда нужен контракт и подмена (репозиторий, клиент внешнего сервиса), абстрактный класс — когда есть общая реализация и состояние (базовый обработчик с общими шагами).

А если abstract не писать?

Тогда метод должен иметь тело, иначе код не скомпилируется. Три варианта:

  • public abstract Task SendAsync(...); — без тела; каждый наследник обязан реализовать.
  • public Task SendAsync(...) { … } — обычный метод с реализацией; наследник не может его переопределить.
  • public virtual Task SendAsync(...) { … } — есть реализация по умолчанию, наследник может переопределить.

И ещё: у abstract-класса нельзя создать экземпляр — new NotificationSender(...) не скомпилируется. Создаются только наследники.

static: класс без экземпляров

public static class OrderMapper
{
    public static OrderDto ToDto(Order order) => new() { Id = order.Id, Total = order.Total };
}
// вызов: OrderMapper.ToDto(order); — экземпляр не нужен
  • Статические поля живут всё время работы процесса и общие для всех потоков. Изменяемое статическое состояние — источник гонок (глава 10 .NET-раздела) и утечек.
  • Статический конструктор выполняется один раз, лениво, при первом обращении к типу.
  • const против static readonly: const подставляется в код на этапе компиляции (менять нельзя без пересборки потребителей), static readonly — значение, вычисленное один раз в рантайме.
  • От static-класса нельзя наследоваться (ошибка компиляции CS0709), и сам он не может наследовать класс: у него нет экземпляров. Реализовывать интерфейсы статический класс тоже не может.
  • Минус: статический класс нельзя подменить в тестах и он скрывает зависимости. Поэтому «помощники» делают статическими, а сервисы с зависимостями — обычными классами с DI (глава 15).

partial: одно определение — несколько файлов

// OrderService.cs — пишет человек
public partial class OrderService
{
    public Task CreateAsync(Order order, CancellationToken ct) { … }
}

// OrderService.Generated.cs — генерируется инструментом
public partial class OrderService
{
    public Task CancelAsync(Guid id, CancellationToken ct) { … }
}

Нужен, когда часть кода создаётся автоматически (source generators, дизайнеры, EF Core-миграции) или когда класс физически огромен. Компилятор просто склеивает части в один тип — на поведение это не влияет. partial-методы позволяют объявить «точку расширения», которую генератор может реализовать.

record: равенство по значениям

У record компилятор сам генерирует Equals, GetHashCode, ToString и with — и всё это по значениям полей. Сравните с обычным классом:

public sealed class OrderClass
{
    public Guid Id { get; init; }
    public decimal Total { get; init; }
}

public sealed record OrderRecord(Guid Id, decimal Total);

var c1 = new OrderClass  { Id = id, Total = 100m };
var c2 = new OrderClass  { Id = id, Total = 100m };

var r1 = new OrderRecord(id, 100m);
var r2 = new OrderRecord(id, 100m);

Console.WriteLine(c1 == c2);                              // False — разные объекты
Console.WriteLine(r1 == r2);                              // True  — одинаковые данные
Console.WriteLine(r1.GetHashCode() == r2.GetHashCode());  // True  — работает в Dictionary/HashSet
Console.WriteLine(c1);                                    // OrderClass
Console.WriteLine(r1);                                    // OrderRecord { Id = …, Total = 100 }

Поэтому record удобен для DTO, событий, сообщений, ключей кэша: два одинаковых сообщения — «одно и то же», их можно сравнивать и складывать в коллекции.

public record OrderCreated(Guid Id, decimal Total);      // позиционный record

var a = new OrderCreated(id, 100m);
var b = new OrderCreated(id, 100m);

Console.WriteLine(a == b);              // True: сравниваются значения полей
Console.WriteLine(a);                   // OrderCreated { Id = …, Total = 100 }
var c = a with { Total = 200m };        // копия с изменением — исходный не тронут

record struct и неизменяемость в DTO

Если DTO маленький и нужен без ссылочной семантики — record struct. Чтобы объект нельзя было изменить после создания, свойства объявляют init (задать можно только в инициализаторе) или required (обязательно задать при создании):

public sealed record UserDto
{
    public required int Id { get; init; }        // обязательно указать
    public required string Name { get; init; }
}

Доступ и наследование: что ещё стоит знать рядом

МодификаторКто видит
publicВсе
internalТолько текущая сборка (по умолчанию для типов)
protectedНаследники
privateТолько внутри типа (по умолчанию для членов)
protected internalНаследники или своя сборка
private protectedНаследники внутри своей сборки
 
public class Base
{
    public virtual void Run() { … }      // можно переопределить
    public void Fixed() { … }            // переопределить нельзя
}

public class Derived : Base
{
    public override void Run() { … }     // переопределение — вызывается через базовую ссылку
    public new void Fixed() { … }        // СКРЫТИЕ: вызывается только через Derived — обычно ошибка
}

virtual/override — это полиморфизм: Base b = new Derived(); b.Run() вызовет реализацию наследника. new лишь «прячет» член, и такое поведение почти всегда нежелательно: код, работающий с базовым типом, увидит одно, а с производным — другое.

Base b = new Derived();      // переменная базового типа
b.Run();                     // Derived.Run  ← сработал override (полиморфизм)
b.Fixed();                   // Base.Fixed   ← метод не виртуальный: выбор по типу ПЕРЕМЕННОЙ

Derived d = new Derived();
d.Fixed();                   // Derived.Fixed ← сработало «скрытие» (new)

Зачем этот пример на собеседовании: он проверяет, понимаете ли вы разницу между переопределением (выбор по фактическому типу объекта) и скрытием (выбор по типу переменной). Из-за скрытия один и тот же метод ведёт себя по-разному в зависимости от того, через какую ссылку его вызвали — источник трудноуловимых ошибок.

★ Что запомнить из главы
  • sealed запрещает наследование: защищает контракт и позволяет JIT вызывать методы напрямую. Для DTO и «конечных» реализаций — норма.
  • abstract — общая основа с состоянием и готовой логикой; interface — контракт, который можно реализовать многими способами.
  • static — удобно для чистых функций, опасно для состояния: поля живут всё время процесса и общие для потоков.
  • partial — для генераторов и больших файлов; на поведение не влияет.
  • record — равенство по значениям и with: идеален для DTO, событий и ответов API; class — для сущностей с идентичностью.
  • virtual/override — полиморфизм; new — скрытие, которого обычно избегают.
