Глава 2. Где живут значения: struct, стек, куча и бокс

«Значимые типы создаются без аллокации» — верно, но не всегда. Разберём правило, из которого следует всё остальное: значение живёт там, где живёт его контейнер.

подводящая глава

Два места и два времени жизни

  • Стек — область для кадров методов: параметры и локальные переменные. Живёт ровно столько, сколько выполняется метод, и освобождается автоматически.
  • Куча — область для объектов. Объект живёт, пока на него есть ссылки; освобождает его сборщик мусора (глава 6 .NET-раздела).

Ключевая мысль: стек и куча — это не «свойства типа», а места, куда попадает переменная или объект. Один и тот же struct может оказаться и на стеке, и в куче — зависит от контекста.

Правило: значение живёт там, где его контейнер

Пять примеров, чтобы это закрепить

1. Локальная переменная — стек, аллокации нет

struct Point { public int X, Y; }

void Draw()
{
    Point p = new Point { X = 3, Y = 5 };   // значение на стеке
    Console.WriteLine(p.X);
}   // вышли из метода — значение исчезло вместе с кадром

2. Поле класса — значение лежит внутри объекта в куче

class Shape
{
    public Point Origin;      // Point — часть объекта Shape
}

var s = new Shape();          // одна аллокация: место под объект целиком,
                              // включая поле Origin внутри него
s.Origin.X = 1;               // отдельной аллокации для Point НЕТ

3. Массив и список — значения внутри массива в куче

var points = new Point[100];        // одна аллокация массива на 100 значений
points[0].X = 7;                    // пишем прямо в массив

var list = new List<Point>();       // внутри — массив Point[]
list.Add(new Point());              // копирование значения в массив

4. Захват в лямбду — значение переезжает в кучу

Func<int> MakeCounter()
{
    int counter = 0;                 // локальная переменная
    return () => ++counter;          // но лямбда её «захватила»
}
// компилятор создаёт объект-замыкание в куче: counter живёт в его поле

5. Бокс — явная аллокация

int n = 42;
object boxed = n;        // ✘ упаковка: в куче создан объект со значением 42
int back = (int)boxed;   // распаковка: значение копируется обратно

// ✘ то же самое, но незаметно: интерфейс без generic-версии
IComparable c = n;       // упаковка, если у типа нет IComparable<int>
Ответ на вопрос «почему часто, а не всегда»

«Часто» — потому что большинство значений в обычном коде — локальные переменные и параметры, а они на стеке. «Не всегда» — потому что struct может быть полем класса, элементом массива, захваченным лямбдой, упакованным в object или пережившим await. Во всех этих случаях значение оказывается в куче.

Бокс: самая частая «невидимая» аллокация

Упаковка (boxing) — превращение значения в объект. Происходит всегда, когда значение требуется там, где ожидается ссылочный тип:

  • приведение к object или к интерфейсу, у которого нет generic-версии;
  • не-generic коллекции (ArrayList, Hashtable) — глава 3;
  • string.Format/интерполяция со значением в object-параметре;
  • сравнение структур через Equals(object) без IEquatable<T>.
// ✘ каждое добавление упаковывает int
var list = new ArrayList();
for (int i = 0; i < 1000; i++) list.Add(i);      // 1000 объектов в куче

// ✔ generic-коллекция хранит значения как значения
var list2 = new List<int>();
for (int i = 0; i < 1000; i++) list2.Add(i);     // ни одной упаковки

// ✔ свой struct со сравнением без упаковки
public readonly struct Money : IEquatable<Money>
{
    public long Kopeks { get; }
    public Money(long kopeks) => Kopeks = kopeks;

    public bool Equals(Money other) => Kopeks == other.Kopeks;
    public override bool Equals(object? obj) => obj is Money m && Equals(m);
    public override int GetHashCode() => Kopeks.GetHashCode();
}

Почему struct не «всегда быстрее»

  • Копирование. Присваивание, передача в метод и возврат копируют всё значение. Большой struct (сотни байт) копировать дороже, чем передать ссылку.
  • Упаковка. Если struct попадает в object или в не-generic API — аллокация всё равно будет.
  • Защитные копии (defensive copies): вызов не-readonly метода или обращение к свойству через in-параметр может создать копию.
  • default-значения. У struct всегда есть состояние «все поля нули», которое не всегда осмысленно (например, нулевая сумма).
  • Нет наследования и null-семантики — иногда это именно то, что нужно, а иногда мешает.

readonly struct и in: как не копировать зря

public readonly struct Range
{
    public int From { get; }
    public int To { get; }

    public Range(int from, int to) { From = from; To = to; }
    public bool Contains(int x) => x >= From && x <= To;
}

// in — передача по ссылке, но только для чтения: без копии и без изменения
static bool Check(in Range range, int value) => range.Contains(value);

readonly struct гарантирует, что состояние не изменится, поэтому компилятор не делает защитных копий при вызове методов. in полезен для структур побольше (условно от 24 байт); для int выгоды нет — копия стоит столько же, сколько ссылка.

Отдельный случай: ref struct

Span<T> и ReadOnlySpan<T> объявлены как ref struct: они гарантированно не могут попасть в кучу — их нельзя положить в поле класса, в List<>, «пережить» ими await. Это цена за скорость и безопасность: окно на память не должно пережить саму память (глава 7 .NET-раздела).

★ Что запомнить из главы
  • Значение живёт там, где его контейнер: локальная переменная — стек; поле класса, элемент массива, замыкание, state machine — куча.
  • «Struct всегда в стеке» — неверное упрощение. Верно: локальные значения обычно не требуют аллокации.
  • Бокс — самая частая незаметная аллокация; лечится generic-коллекциями и IEquatable<T>.
  • Struct не всегда быстрее: копирование, бокс и защитные копии могут съесть всю выгоду.
  • readonly struct и in убирают лишние копии; ref struct принципиально живёт только на стеке.
