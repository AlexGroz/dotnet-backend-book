Глава 33. Миграция legacy: .NET Framework → .NET Core

Переезд — это не «поменять target framework», а замена целых подсистем: DI, конфигурации, HTTP-конвейера и работы с потоками. Разберём, что именно болит и чем это лечится — на сообщениях, которые реально печатает .NET 8.

основная глава

Почему «просто пересобрать» не получается

.NET Framework и современный .NET — разные платформы, а не две версии одной. Часть API из Framework в .NET Core не попала вообще: нельзя «включить обратно» System.Web или сборку, собранную под net48. Поэтому миграция всегда идёт по подсистемам:

Что было в .NET FrameworkПочему не переноситсяЧем заменяется
System.Web: HttpContext.Current, Global.asax, HTTP-модулиВ .NET Core System.Web нет middleware (глава 19), IHttpContextAccessor
Встроенного DI-контейнера нет — только сторонние (Autofac, Unity, Ninject)Контейнер стал частью платформы Microsoft.Extensions.DependencyInjection (глава 15)
web.config / app.config, transform-файлы System.Configuration остался в Framework appsettings*.json + IConfiguration / IOptions (глава 17)
WCF (service references, svcutil)WCF-сервер в .NET Core не входит gRPC (глава 29), CoreWCF, обычный HTTP API
Web FormsТехнология не переносиласьMVC, Razor Pages, Blazor

[ThreadStatic], CallContext.LogicalSetData При await значение теряется или не течёт в дочерние задачи AsyncLocal<T>

Отдельно стоит .NET Standard 2.0: это не платформа, а «контракт API». Библиотека, собранная под netstandard2.0, подключается и к net48, и к net8.0. Именно поэтому путь миграции обычно такой: сначала вынести общий код в netstandard2.0-библиотеки (их видят оба мира), потом переписать хост на .NET 8. Сборку под net48 подключить к .NET 8 нельзя — только пересобрать из исходников.

DI: как это было в .NET Framework

В .NET Framework контейнера «из коробки» не было. ASP.NET MVC 5 оставлял одну точку подключения — DependencyResolver, и в неё вставляли сторонний контейнер. Выглядело это так (пример исторический — на .NET 8 он не запускается, System.Web там нет):

Global.asax, MVC 5 + Autofac — типичный код 2015 года

// Application_Start() в Global.asax
var builder = new ContainerBuilder();
builder.RegisterType<OrderRepository>().As<IOrderRepository>().InstancePerRequest();
builder.RegisterType<ReportService>().SingleInstance();          // «живёт всё приложение»
builder.RegisterControllers(typeof(MvcApplication).Assembly);

var container = builder.Build();
DependencyResolver.SetResolver(new AutofacDependencyResolver(container));   // статическая точка входа
  • Жизненные циклы задавались методами контейнера, а не атрибутом регистрации: InstancePerDependency (каждый раз новый), InstancePerRequest (на HTTP-запрос), SingleInstance (один на приложение).
  • Per-request lifetime работал только внутри ASP.NET-конвейера. В консольном приложении или в WPF того же контейнера InstancePerRequest уже не «на запрос»: там нет запроса, и поведение зависит от контейнера.
  • В WPF контейнер строили один раз в App.xaml.cs, и почти всё регистрировалось как SingleInstance: «на запрос» делить нечего, окно живёт долго. Отсюда привычка «сервис = синглтон», которая в ASP.NET Core ломается (см. Captive Dependency).
  • Состояние запроса брали из статики: HttpContext.Current (в MVC), DependencyResolver.Current.GetService<T>() в любом месте кода. Это и есть Service Locator: зависимость не видна в конструкторе, а тест требует поднять «весь мир».
Почему старый код «просто работал»

Потому что у старых приложений было одно состояние на поток процесса и одна БД. Проблемы начинались позже: DbContext в синглтоне, «второй запрос на том же контексте», данные одного арендатора в другом запросе. В .NET Framework этого никто не проверял на старте — валидации графа не было.

Autofac (legacy)Microsoft.Extensions.DependencyInjection
InstancePerDependency()AddTransient<I, T>()
InstancePerRequest() / InstancePerLifetimeScope() AddScoped<I, T>()
SingleInstance()AddSingleton<I, T>()
RegisterGeneric(typeof(Repo<>)) AddScoped(typeof(IRepo<>), typeof(Repo<>))
RegisterDecorator<T>() Встроенного нет: пакет Scrutor, services.Decorate<I, Decorator>() (глава про декоратор)
DependencyResolver.SetResolver(...) Регистрации в builder.Services, ничего «подключать» не нужно (глава 15)
Property injection, Resolve<T>() в коде Только конструктор; IServiceProvider — лишь внутри фабрики

DI: как это стало — и что ловит контейнер

В .NET Core контейнер встроен, а все жизненные циклы — это три метода: AddTransient, AddScoped, AddSingleton (глава 15). Главное новшество для мигранта — не синтаксис, а валидация графа: контейнер умеет проверять, что Singleton не тянет Scoped. Именно этой проверки не было в legacy, и именно она ловит те самые баги, которые раньше «всплывали в проде».

Program.cs: Singleton, которому нужен Scoped

builder.Host.UseDefaultServiceProvider(o =>
{
    o.ValidateScopes = true;     // запрещает Singleton -> Scoped и резолв Scoped из корня
    o.ValidateOnBuild = true;    // проверяет ВЕСЬ граф на старте, а не при первом запросе
});

builder.Services.AddSingleton<ReportService>();    // живёт всё приложение
builder.Services.AddScoped<AppDbContext>();       // AddDbContext тоже даёт Scoped (проверено)

public sealed class ReportService(AppDbContext db); // Scoped попал в Singleton

Development и Production ведут себя по-разному

Проверено на .NET 8: с тем же кодом приложение в Development падает на старте (сообщение выше), а в Production стартует нормально — captive создаётся молча. Ошибка вылезает позже, когда два запроса одновременно работают с одним и тем же DbContext (два параллельных GET /report на боевом окружении):

req1: 500   req2: 200

System.InvalidOperationException: An attempt was made to use the context instance
while it is being configured. A DbContext instance cannot be used inside 'OnConfiguring'
since it is still being configured at this point. This can happen if a second operation
is started on this context instance before a previous operation completed.
Any instance members are not guaranteed to be thread safe.

Причина: WebApplicationBuilder включает ValidateScopes и ValidateOnBuild только в Development. Вывод для миграции: включайте UseDefaultServiceProvider явно и во всех окружениях — иначе прод останется без проверки.

Вторая половина проверки — резолв «короткоживущего» сервиса из корневого провайдера. Это ровно то, что делал legacy-код через DependencyResolver.Current:

Что печатает проверка (консольная программа на .NET 8)

1) ValidateOnBuild: Singleton -> Scoped
   AggregateException: Some services are not able to be constructed (Error while validating
   the service descriptor 'ServiceType: ReportService Lifetime: Singleton ...':
   Cannot consume scoped service 'AppDbContext' from singleton 'ReportService'.)
2) GetRequiredService<AppDbContext>() из корневого провайдера
   InvalidOperationException: Cannot resolve scoped service 'AppDbContext' from root provider.
3) Singleton держит IServiceProvider и резолвит Scoped
   запрос-1 получил запрос-1 -> RequestContext#1 (tenant=tenant-A)
   запрос-2 получил запрос-2 -> RequestContext#1 (tenant=tenant-A)
   один и тот же экземпляр: True
3b) ValidateOnBuild: зависимость не зарегистрирована
   AggregateException: ... Unable to resolve service for type 'AppDbContext'
   while attempting to activate 'ReportService'.
4) IServiceScopeFactory: свой scope на операцию
   операция-1 получила операция-1 -> RequestContext#2 (tenant=tenant-A)
   операция-2 получила операция-2 -> RequestContext#3 (tenant=tenant-A)

Сценарий 3 — тот самый Service Locator из legacy-кода: Singleton получил IServiceProvider и резолвит Scoped-сервис. Провайдер собран без валидации, и оба «запроса» получают один и тот же RequestContext#1. Если в этом объекте арендатор, имя пользователя или DbContext — данные первого запроса утекут во второй. Именно так выглядит баг «иногда показываются чужие заказы».

Сценарий 4 — правильный: Singleton зависит не от сервиса, а от фабрики scope'ов и создаёт свой scope на операцию (глава 15, раздел про Captive Dependency).

Код сценариев 3 и 4 (сокращённо)

public sealed class LegacyService(IServiceProvider sp)      // ✘ сервис-локатор в синглтоне
{
    public string Handle(string name) => $"{name} -> {sp.GetRequiredService<RequestContext>}";
}

public sealed class FixedService(IServiceScopeFactory factory)   // ✔ свой scope на операцию
{
    public string Handle(string name)
    {
        using var scope = factory.CreateScope();
        return $"{name} -> {scope.ServiceProvider.GetRequiredService<RequestContext>}";
    }
}
Чек-лист миграции DI
  1. Каждую регистрацию legacy-контейнера переписать в один из трёх методов: «на запрос» — AddScoped, «на всё приложение» — AddSingleton.
  2. Все Resolve<T>() / DependencyResolver.Current заменить на параметры конструктора. Если без провайдера не обойтись — только IServiceScopeFactory.
  3. Включить ValidateScopes + ValidateOnBuild во всех окружениях.
  4. Добавить тест-сторож: собрать провайдер из реальных регистраций и получить каждый сервис внутри scope (глава 15).
  5. Проверить, что DbContext нигде не Singleton — в EF Core его время жизни Scoped.

HttpContext.Current → IHttpContextAccessor

В MVC 5 контекст запроса был глобальной статикой: HttpContext.Current (и Thread.CurrentPrincipal рядом). В .NET Core такой статики нет — есть сервис IHttpContextAccessor. Первая ловушка: он не зарегистрирован по умолчанию. Если внедрить его в конструктор и забыть AddHttpContextAccessor(), контейнер скажет:

Что печатает приложение (Development)

Unhandled exception. System.AggregateException: Some services are not able to be constructed
(Error while validating the service descriptor 'ServiceType: Probe Lifetime: Singleton
ImplementationType: Probe': Unable to resolve service for type
'Microsoft.AspNetCore.Http.IHttpContextAccessor' while attempting to activate 'Probe'.)

Проверка «а он вообще есть?» делается одной строкой, если сомневаетесь:

builder.Services.AddHttpContextAccessor();   // без этой строки IHttpContextAccessor = null/ошибка
var app = builder.Build();
Console.WriteLine(app.Services.GetService<IHttpContextAccessor>() is not null);   // False → True после Add

Дальше — как этим пользоваться правильно. Singleton может зависеть от аксессора: аксессор отдаёт контекст текущего запроса, поэтому один и тот же Singleton видит разные запросы:

public sealed class CtxProbe(IHttpContextAccessor acc)      // Singleton — можно
{
    public string Describe() =>
        $"path={acc.HttpContext?.Request.Path}";             // ← контекст ТЕКУЩЕГО запроса
}

app.MapGet("/orders",   (CtxProbe p) => p.Describe());
app.MapGet("/invoices", (CtxProbe p) => p.Describe());

Что вернули два запроса

path=/orders
path=/invoices

А теперь классическая ошибка мигранта: сохранить HttpContext в поле «чтобы не дёргать аксессор». Контекст живёт один запрос; после его завершения объект уничтожается:

public sealed class StaleHolder(IHttpContextAccessor acc)
{
    private HttpContext? _saved;                   // ✘ так делать нельзя
    public string Describe(string path)
    {
        _saved ??= acc.HttpContext;                // запомнили контекст ПЕРВОГО запроса
        return $"пришёл {path}, в поле лежит {_saved?.Request.Path}";
    }
}

Что происходит со вторым запросом

GET /orders    200   пришёл /orders, в поле лежит /orders
GET /invoices  500   System.ObjectDisposedException: IFeatureCollection has been disposed.
                     Object name: 'Collection'.
Правило вместо HttpContext.Current

Внутри запроса берите HttpContext из параметра обработчика (он приходит сам), в сервисах — IHttpContextAccessor.HttpContext в момент вызова. Хранить контекст, Request, Response, HttpContext.User в полях Singleton'а нельзя: после запроса это уже мусор. Всё, что нужно «после», копируйте в свои объекты (например, tenantId строкой).

Конфигурация: web.config → appsettings.json

Второй по частоте источник боли: в Framework настройки читали через ConfigurationManager.AppSettings[...] и <connectionStrings>, а файл web.config ещё и содержал модули, handlers и трансформации для сборок. В .NET Core конфигурация — это набор источников «ключ-значение» (глава 17):

БылоСтало
<appSettings><add key="Rate" value="5"/> appsettings.json → builder.Configuration["Rate"]
<connectionStrings><add name="Main" .../> ConnectionStrings:Main и builder.Configuration.GetConnectionString("Main")
Трансформации Web.Release.config appsettings.{Environment}.json поверх основного файла
machine.config, реестр, IIS-настройки Переменные окружения и аргументы командной строки (последние в цепочке — главные)
Своя секция ConfigurationSection Класс настроек + IOptions<T> + валидация на старте

HTTP-модули и handlers из web.config заменяются middleware в Program.cs (глава 19), а Global.asax — обычным кодом до app.Run(): регистрации, прогрев, app.Use....

Потоки и асинхронность: что изменилось

В ASP.NET (System.Web) у запроса был SynchronizationContext: продолжение после await возвращалось в него, а HttpContext.Current был привязан к потоку. В ASP.NET Core контекста нет — это проверяется одной строкой в обработчике:

app.MapGet("/sync", () => $"SynchronizationContext = {(SynchronizationContext.Current is null ? "null" : SynchronizationContext.Current.GetType().Name)}");

Ответ эндпоинта

SynchronizationContext = null

Из этого следуют два практических вывода. Первый: ConfigureAwait(false) в ASP.NET Core почти ни на что не влияет (контекста нет), но в библиотеках его всё равно пишут — библиотека не знает, куда её подключат (глава 18 C#-книги). Второй: «поток запроса» больше не существует как понятие, поэтому любое состояние, привязанное к потоку, ломается при первом же await.

Проверка на .NET 8: [ThreadStatic] против AsyncLocal

[ThreadStatic] static string? _threadValue;                  // legacy-подход
static readonly AsyncLocal<string?> _asyncValue = new();    // современный

_threadValue = "tenant-A";
_asyncValue.Value = "tenant-A";
await Task.Delay(50).ConfigureAwait(false);                 // продолжение на другом потоке

Вывод

до await:     ThreadStatic=tenant-A, AsyncLocal=tenant-A
после await:  ThreadStatic=null,     AsyncLocal=tenant-A
поток: 5
после Task.Run: AsyncLocal=tenant-A
  • [ThreadStatic] теряет значение после await: продолжение выполнилось на другом потоке, а поле принадлежит потоку.
  • AsyncLocal<T> течёт по цепочке вызовов — значение видно и после await, и внутри вложенных асинхронных методов.
  • Но не в обратную сторону: изменение внутри Task.Run не вернулось в родителя — после него всё ещё tenant-A. Это «копия на ветку», а не общая переменная.

Именно поэтому CallContext.LogicalSetData/[ThreadStatic] из legacy-кода (контекст арендатора, корреляционный id, «текущий пользователь») при переезде заменяют на AsyncLocal — или, что честнее, передают параметром. Тот же механизм лежит в основе HttpContextAccessor и Activity.Current (трассировка, глава 20).

Чего в .NET 8 нет вообще
  • Второй AppDomain. AppDomain.CreateDomain("second") → PlatformNotSupportedException: Secondary AppDomains are not supported on this platform. Плагины, которые грузили в отдельный AppDomain «чтобы выгрузить», переписывают на AssemblyLoadContext (он выгружаемый) или на отдельный процесс.
  • BinaryFormatter. В .NET 8 это ошибка компиляции SYSLIB0011, а если её подавить — NotSupportedException: BinaryFormatter serialization and deserialization are disabled within this application. Данные, которые лежали в кэше/очереди в виде BinaryFormatter, придётся перечитать старым кодом и переложить в JSON/Protobuf.
  • WCF-сервер, Web Forms, System.Web, .NET Remoting. Только замена: gRPC (глава 29), MVC/Razor Pages/Blazor, HTTP API.

Порядок миграции, который работает

  1. Инвентаризация. Список проектов и их target framework; зависимости, которые нельзя пересобрать (COM, GAC-сборки, сторонние net48-библиотеки); места, где используется System.Web, HttpContext.Current, web.config, WCF, BinaryFormatter, AppDomain. Это и есть объём работ, а не «количество файлов».
  2. Вынести общий код в netstandard2.0. Модели, бизнес-логику, клиентов внешних систем. Такие библиотеки собираются и для net48, и для net8.0 — старый хост продолжает работать, новый уже использует тот же код.
  3. Переписать хост. Program.cs: DI (глава 15), конфигурация (глава 17), middleware вместо модулей (глава 19), IHttpContextAccessor вместо статики. Сразу включить ValidateScopes/ValidateOnBuild.
  4. Данные. Схему ведёт одна сторона: пока пишет EF6 — EF Core подключается к той же базе без своих миграций (и наоборот). Массовые операции и проекции — по правилам главы 24.
  5. Сосуществование. Классический приём — strangler: ставим перед старым приложением reverse proxy (например, YARP) и постепенно переводим маршруты на новое. Тогда откат — это изменение одного маршрута, а не выкатка целиком.
  6. Проверка эквивалентности. Одни и те же запросы к старой и новой системе, сравнение JSON (с точностью до порядка полей), сравнение планов SQL для тяжёлых запросов (SQL-книга, глава 21). Только после этого — теневой трафик и канареечный выкат.
Две вещи, которые забывают
  • Аутентификация. Cookie, выданная старым приложением, не «просто работает» в новом: нужны те же имя и схема cookie, общие ключи защиты данных и одинаковые claim'ы. Иначе пользователи получат разлогин на каждом переключении маршрута.
  • Фоновые задачи. В Framework это часто Windows-служба или HostingEnvironment.QueueBackgroundWorkItem; в .NET Core — BackgroundService (глава 16) с корректной остановкой (глава 28). Две копии обработчика на одной таблице-очереди без блокировки — это двойная обработка (глава 31, идемпотентность).

Что спросят на интервью

  • «Что было самым сложным при переезде?» — не смена target framework, а неявные контракты: времена жизни в DI, статика HttpContext.Current, конфигурация, сериализация и фоновые задачи. Каждую из этих подсистем пришлось заменять целиком.
  • «Как ловили Captive Dependency?» — ValidateScopes + ValidateOnBuild во всех окружениях (в Development они включены сами, в Production — нет), тест-сторож по графу, код-ревью на DbContext/IServiceProvider в Singleton. Текст ошибки конкретный: Cannot consume scoped service 'AppDbContext' from singleton 'ReportService'.
  • «Куда девать HttpContext.Current?» — IHttpContextAccessor, который надо зарегистрировать руками, и брать контекст в момент вызова. Сохранённый в поле контекст после запроса — ObjectDisposedException.
  • «Как перевозили данные?» — общий код в netstandard2.0, EF Core рядом с EF6 на одной схеме, у схемы один хозяин, тесты эквивалентности выборок.
  • «Как выкатывали?» — strangler через reverse proxy: маршрут за маршрутом, теневой трафик, канарейка, откат переключением маршрута.
★ Что запомнить

Миграция — это замена подсистем, а не смена версии: DI (три времени жизни + валидация графа), конфигурация (источники вместо web.config), контекст запроса (IHttpContextAccessor вместо статики), состояние потока (AsyncLocal вместо [ThreadStatic]). Всё, чего в .NET нет (AppDomain, BinaryFormatter, WCF, Web Forms), заменяется, а не «включается обратно».
