Глава 1. Зачем Kafka: журнал, партиции и оффсеты

Сообщение из Kafka не «забирают» — его читают со своего места: чем журнал отличается от очереди и из чего он состоит

подводящая глава

Задача: одно событие — много читателей

Очередь (RabbitMQ, книга про AMQP) отвечает на вопрос «кто-то один должен сделать работу». Она хорошо подходит для команд: «списать деньги», «отправить письмо». Но есть другой класс задач — события: «заказ создан», «платёж прошёл», «цена изменилась». Такое событие нужно сразу нескольким системам: биллингу, складу, аналитике, поисковому индексу. И каждой из них может понадобиться перечитать события заново — например, чтобы пересчитать витрину после исправления бага.

Если строить это на очереди, придётся заводить по копии сообщения на каждого читателя: producer не знает, кто ещё захочет это событие, а после подтверждения сообщение из очереди исчезает. Добавили нового потребителя — он не увидит ни одного события из прошлого.

Идея Kafka

Сообщения не удаляются после чтения. Они складываются в журнал (log) и лежат там, пока не истечёт срок хранения. Каждый потребитель хранит не «где сообщение», а свою позицию в журнале — и читает с любого места столько раз, сколько нужно.

Журнал, а не очередь

Слово «очередь» в Kafka осталось только в названии команды. Семантика другая:

Очередь (RabbitMQ)Журнал (Kafka)
После чтенияСообщение подтверждают — и оно удаляется Ничего: запись остаётся в партиции до истечения retention
Кто получаетОдно сообщение — одному потребителю (копия — на каждую очередь) Каждая consumer group читает весь журнал независимо от других
Повторное чтениеНет: подтверждённое сообщение исчезло Есть: группа может сдвинуть оффсет назад и перечитать
ПорядокВ пределах одной очередиВ пределах одной партиции; между партициями порядка нет
«Где я остановился»Хранит брокер (доставленные и неподтверждённые) Хранит потребитель: коммит оффсета в служебный топик __consumer_offsets

Отсюда главное практическое следствие: Kafka — это события, которые читают многие и, возможно, несколько раз. Команда «сделай это один раз» лучше ложится на очередь.

Из чего состоит Kafka

  • Брокер (broker) — процесс Kafka, который хранит партиции на диске и обслуживает клиентов. Кластер — несколько брокеров (в этой книге — один).
  • Топик (topic) — именованный поток событий: orders, payments. Топик режут на партиции.
  • Партиция (partition) — независимый журнал: записи только добавляются в конец, у каждой есть номер. Партиция — единица параллелизма и порядка.
  • Оффсет (offset) — номер записи внутри партиции: 0, 1, 2, … Он не «тратится» после чтения, а указывает место.
  • Реплики (replicas) — копии партиции на других брокерах; одна из них лидер, остальные догоняют. Репликация защищает от потери узла (глава 5).
  • Producer — пишет в конец партиции; какую именно выбрать, решает ключ сообщения (глава 2).
  • Consumer group — читатели, которые делят партиции между собой: в каждый момент партицию читает один участник группы (глава 4).
producer ──▶ topic "orders"
                ├─ partition 0:  [0][1][2][3]   <- оффсеты; записи только добавляются справа
                ├─ partition 1:  [0][1]
                └─ partition 2:  [0][1][2]

consumer group "billing":    оффсет 3 в p0, 1 в p1, 2 в p2   <- своя позиция
consumer group "analytics":  оффсет 0 во всех партициях      <- читает с начала

Две группы не мешают друг другу: каждая двигает свои оффсеты. Внутри группы партиции распределяются между участниками — поэтому «больше потребителей, чем партиций» чтение не ускоряет (глава 4).

Запуск брокера

Официальный образ Apache Kafka 3.9 работает в режиме KRaft: метаданные хранит сам брокер, отдельный ZooKeeper не нужен. Для локальных опытов достаточно одной команды:

# -d — в фоне; --name kafka — имя контейнера для docker exec
# -p 9092:9092 — порт, на который будут подключаться клиенты с хоста
docker run -d --name kafka -p 9092:9092 apache/kafka:3.9.1

# готовность: брокер принимает запросы, когда утилита может получить список топиков
# (на тёплом образе это ~5 секунд; команду можно повторять, пока не ответит)
docker exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --list

# версия Kafka внутри контейнера
docker exec kafka /opt/kafka/bin/kafka-topics.sh --version
# 3.9.1

Один брокер — только для опытов

В контейнере нет тома: остановили и удалили — данные пропали. А replication-factor 1 означает единственную копию партиции: потеря брокера — потеря данных. Для продакшена нужны минимум три брокера и фактор репликации 3 (глава 5).

Первый топик и первые сообщения

Создадим топик из трёх партиций и одной реплики — кластер у нас один:

# --create        создать топик
# --topic demo    его имя
# --partitions 3  три независимых журнала внутри топика
# --replication-factor 1  одна копия каждой партиции (при одном брокере иначе нельзя)
docker exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic demo --partitions 3 --replication-factor 1
# Created topic demo.

Посмотрим, что получилось:

# --describe --topic demo  показать топик и каждую его партицию
docker exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic demo
# Topic: demo  TopicId: lr8veZlzSbOdrNUUlPrMLw  PartitionCount: 3  ReplicationFactor: 1
#              Configs: segment.bytes=1073741824
#   Topic: demo  Partition: 0  Leader: 1  Replicas: 1  Isr: 1  Elr:  LastKnownElr:
#   Topic: demo  Partition: 1  Leader: 1  Replicas: 1  Isr: 1  Elr:  LastKnownElr:
#   Topic: demo  Partition: 2  Leader: 1  Replicas: 1  Isr: 1  Elr:  LastKnownElr:

Три партиции, у каждой лидер (брокер 1), список реплик и синхронных реплик (Isr). Пока реплика одна — всё это один и тот же брокер; в главе 5 столбцы станут разными, когда брокеров будет несколько.

Кладём три сообщения с ключами. Консольный producer читает строки со stdin и отправляет их по одной:

# parse.key=true     считать первую часть строки ключом
# key.separator=:    разделитель ключа и значения в строке (по умолчанию табуляция)
printf 'k1:a\nk2:b\nk3:c\n' | docker exec -i kafka /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server localhost:9092 --topic demo \
  --property parse.key=true --property key.separator=:

Теперь прочитаем с начала и попросим печатать ключ, партицию и оффсет:

# --from-beginning   начать с самого старого доступного оффсета
# --max-messages 3   выйти после трёх сообщений (иначе утилита ждёт новых)
# print.key/print.partition/print.offset  что печатать перед значением
docker exec kafka /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 \
  --topic demo --from-beginning --max-messages 3 \
  --property print.key=true --property print.partition=true --property print.offset=true
# Partition:0  Offset:0  k2  b
# Partition:1  Offset:0  k3  c
# Partition:2  Offset:0  k1  a
# Processed a total of 3 messages

Обратите внимание: ключи разошлись по разным партициям, и в каждой записи достался оффсет 0 — свои оффсеты у каждой партиции. Ключ k1 попал в партицию 2, k2 — в 0, k3 — в 1: это не порядок отправки, а результат хеширования ключа (глава 2).

Теперь главное отличие от очереди — прочитаем ещё раз, новой группой:

docker exec kafka /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 \
  --topic demo --from-beginning --max-messages 3 \
  --property print.key=true --property print.partition=true --property print.offset=true
# Partition:0  Offset:0  k2  b
# Partition:1  Offset:0  k3  c
# Partition:2  Offset:0  k1  a
# Processed a total of 3 messages

Сообщения на месте: чтение ничего не удалило. Консольная утилита каждый раз создаёт новую consumer group, поэтому начинает с начала — своим оффсетом.

Оффсеты: где начало и где конец журнала

Утилита kafka-get-offsets.sh показывает границы журнала для каждой партиции:

# --time -2  самый старый доступный оффсет (earliest)
docker exec kafka /opt/kafka/bin/kafka-get-offsets.sh --bootstrap-server localhost:9092 --topic demo --time -2
# demo:0:0
# demo:1:0
# demo:2:0

# без --time (то же, что --time -1)  следующий оффсет, куда запишется новое сообщение (latest)
docker exec kafka /opt/kafka/bin/kafka-get-offsets.sh --bootstrap-server localhost:9092 --topic demo
# demo:0:1
# demo:1:1
# demo:2:1

Формат ответа — топик:партиция:оффсет. Разница между latest и earliest — сколько записей сейчас лежит в партиции; здесь по одной. Новое сообщение получит оффсет 1, и latest станет 2.

Флаги и свойства, которые встретились в главе:

ФлагЧто означает

Что мы увидели

  • Запись осталась после чтения. Второй consumer прочитал те же три сообщения: журнал не «отдаёт» их, а позволяет читать с любого оффсета.
  • Оффсеты у каждой партиции свои. Три сообщения получили оффсет 0 в трёх разных партициях — это нормально.
  • Ключ определяет партицию. k1, k2, k3 разошлись по партициям 2, 0 и 1 — по хешу, а не по порядку (глава 2).
  • Порядок гарантирован только внутри партиции. Между партициями общего порядка нет — поэтому и говорят «порядок на ключ», а не «порядок в топике».
★ Что запомнить из главы
  • Kafka — распределённый журнал, а не очередь: сообщения хранятся после чтения, пока действует retention.
  • Топик = набор партиций. Партиция — единица параллелизма и порядка; оффсет — номер записи внутри партиции.
  • Каждая consumer group читает независимо и хранит свою позицию (коммит оффсета), а не «забирает» сообщения у других.
  • Порядок — только внутри партиции. Ключ сообщения определяет, в какую партицию оно попадёт, и тем самым — по какому «потоку» сохранится порядок.
  • Клиент и CLI говорят одним протоколом: --bootstrap-server — та же точка входа, что BootstrapServers в .NET.
