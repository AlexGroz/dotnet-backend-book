Глава 4. struct: что это и когда применять

Целый тип, объявленный одним словом struct: что в нём можно хранить, чем он отличается от класса и почему с ним так легко выстрелить себе в ногу.

основная глава

Что такое struct: значение целиком, без отдельной ссылки

struct — способ объявить свой значимый тип. Разница с классом видна, если посмотреть на переменную: у переменной-класса в стеке лежит адрес объекта в куче, а у переменной-структуры — сами данные, все поля подряд. Отдельной «ссылки на структуру» нет.

Где именно лежат поля структуры — зависит от того, где объявлена переменная:

Где объявленаГде лежат её поля
Локальная переменная в методеВ стеке этого метода (в его «кадре»)

Как программа узнаёт, где данные. Никакого поиска в рантайме нет: тип переменной известен компилятору, а вместе с типом известны размер и состав значения. Для Point это «два int = 8 байт», и компилятор просто резервирует эти 8 байт там, где объявлена переменная. Для класса он резервирует 8 байт под ссылку, а объект создаётся отдельно в куче.

А ссылка у структуры всё-таки бывает?

Только в двух случаях: (1) когда структуру кладут в object или интерфейс — это упаковка (бокс): значение копируется в кучу, и появляется ссылка на копию; (2) когда структура — поле класса: тогда к ней ходят через ссылку на объект-владелец. Сама по себе структура ссылки не имеет — поэтому не может быть null.

public struct Point        // значимый тип: 8 байт данных
{
    public int X;
    public int Y;
}

var a = new Point { X = 1, Y = 2 };
var b = a;                 // скопировались ВСЕ 8 байт значения
b.X = 99;

Console.WriteLine(a.X);    // 1  — у a своя копия данных
Console.WriteLine(b.X);    // 99

int, double, DateTime — тоже struct. Как это увидеть

int — не «встроенное ключевое слово», а короткое имя типа System.Int32, который объявлен структурой в базовой библиотеке. Проверяется обычным кодом:

Console.WriteLine(typeof(int).FullName);            // System.Int32
Console.WriteLine(typeof(int).IsValueType);         // True  ← это значение, не ссылка
Console.WriteLine(typeof(int).BaseType);            // System.ValueType
Console.WriteLine(typeof(int) == typeof(Int32));    // True  ← int и Int32 — один тип
Console.WriteLine(typeof(List<int>).IsValueType);   // False ← а это класс

Что окажется на консоли

System.Int32
True

То же самое верно для double (System.Double), bool, long, DateTime, Guid, decimal. В исходниках .NET они объявлены примерно так: public readonly struct Int32 : …. А int? — это Nullable<int>, тоже структура (глава 10).

Вывод: «struct» — не экзотика, а способ сделать свой такой тип. Вопрос только в том, стоит ли: ниже — когда да, а когда нет.

Три следствия, которые надо принять сразу
  • Копирование. Присваивание, передача в метод и возврат копируют всё значение.
  • Нет null. Переменная struct всегда существует. «Пустое» состояние — это default (все поля = 0/null).
  • Нет наследования. От struct нельзя наследоваться, и он не может наследовать класс.

public struct Money : IEquatable<Money>     // интерфейсы — можно
{
    public long Kopeks { get; }                // свойство
    public string Currency { get; }            // ССЫЛОЧНОЕ поле — можно!

    public Money(long kopeks, string currency) // конструктор
    {
        Kopeks = kopeks;
        Currency = currency;
    }

    public Money Add(Money other) =>          // метод
        new(Kopeks + other.Kopeks, Currency);

    public bool Equals(Money other) => Kopeks == other.Kopeks && Currency == other.Currency;
    public override bool Equals(object? obj) => obj is Money m && Equals(m);
    public override int GetHashCode() => HashCode.Combine(Kopeks, Currency);
}

Да, внутри struct могут быть методы и ссылочные поля — это обычный тип, просто со «значимой» семантикой. Именно поэтому вопрос «структура или класс» — не про «есть ли методы», а про то, как тип должен вести себя при копировании.

Копирование: что именно копируется

Копируется всё значение целиком: поля значимых типов — по значению, поля ссылочных — как ссылка. Второе — самый частый источник ошибок.

public sealed class Customer { public string Name = ""; }

public struct OrderInfo
{
    public int Id;                 // значимое поле
    public Customer Customer;      // ссылочное поле
}

var customer = new Customer { Name = "Алексей" };
var a = new OrderInfo { Id = 1, Customer = customer };

var b = a;                         // копия структуры

b.Id = 99;                         // a.Id остаётся 1 — значения независимы
b.Customer.Name = "Иван";          // a.Customer.Name ТОЖЕ стало "Иван"!

// потому что скопировалась ссылка, а объект Customer — один и тот же
ПолеЧто происходит при копированииРезультат

Customer CustomerКопируется ссылкаОба struct смотрят на один объект

Если внутри структуры лежит ссылка на изменяемый объект, копия структуры не копирует этот объект. Нужна настоящая независимость — придётся реализовать копирование вручную (и лучше не проектировать структуру с изменяемыми ссылочными полями вовсе).

Изменяемость и «ловушка копии»

Метод структуры может менять её поля — и это работает, пока вы вызываете его на переменной.

public struct Counter
{
    public int Value;
    public void Inc() => Value++;      // меняет поле ЭТОГО значения
}

var c = new Counter();
c.Inc();
Console.WriteLine(c.Value);            // 1 — всё ожидаемо

// а теперь та же структура внутри класса:
public sealed class Holder { public Counter C { get; set; } }

var h = new Holder();
h.C.Inc();                             // ⚠ вызов на КОПИИ, которую вернуло свойство
Console.WriteLine(h.C.Value);          // 0 — изменение потеряно, без единой ошибки компиляции
Почему напечаталось 0 — по шагам
  1. h.C — это свойство. Оно возвращает значение поля, а не «ссылку на него», то есть копию структуры Counter с Value = 0.
  2. h.C.Inc() вызывает метод на этой копии: у копии Value становится 1.
  3. Копия временная — после строки она никому не нужна и выбрасывается.
  4. h.C.Value в следующей строке снова возвращает копию исходного поля, где Value так и осталось 0. Отсюда 0.

Компилятор не ошибся: код синтаксически корректен. Ошибка смысловая — изменение ушло в никуда. Именно поэтому изменяемые структуры (с методами, меняющими поля) считаются плохой практикой: решение — readonly struct (ниже) или класс вместо структуры.

Правило, которое снимает половину проблем

Объявляйте структуры readonly struct, а методы делайте возвращающими новое значение:

public readonly struct Point
{
    public int X { get; }
    public int Y { get; }

    public Point(int x, int y) { X = x; Y = y; }

    public Point Move(int dx, int dy) => new(X + dx, Y + dy);   // новое значение
}

var p = new Point(1, 2);
p = p.Move(1, 1);        // явно присваиваем результат — «ловушки копии» нет

in: что было бы без него

Параметр-структура по умолчанию копируется при каждом вызове. Для int это незаметно, для структуры из десяти полей — уже нет.

// без in: p — копия, метод не может испортить оригинал, но копирует всё значение
static double Length(Point p) => Math.Sqrt(p.X * p.X + p.Y * p.Y);

// с in: p передаётся по ссылке, но менять его компилятор запрещает
static double Length(in Point p) => Math.Sqrt(p.X * p.X + p.Y * p.Y);
  • Без in — копия (безопасно, но для больших структур дорого).
  • С in — ссылка только для чтения: копии нет, изменить нельзя.
  • Для маленьких типов (int, Guid, Point из двух int) выгоды нет: копия стоит столько же, сколько ссылка.
  • Важно: если метод структуры не помечен readonly, компилятор может сделать защитную копию даже при in — и выгода исчезает. Поэтому in имеет смысл вместе с readonly struct.

Равенство: почему «по умолчанию» дорого

var p1 = new Point(1, 2);
var p2 = new Point(1, 2);

// Console.WriteLine(p1 == p2);      // ✘ для своего struct оператор == не определён
Console.WriteLine(p1.Equals(p2));    // True — но работает через Equals(object)

Что происходит за кулисами p1.Equals(p2):

  1. значение p1 упаковывается в object (аллокация в куче);
  2. ValueType.Equals сравнивает поля через рефлексию.

Поэтому в HashSet<Point>, Dictionary<Point, …> и List.Contains структура без IEquatable<T> работает заметно медленнее ожидаемого.

public readonly struct Money : IEquatable<Money>
{
    public long Kopeks { get; }
    public Money(long kopeks) => Kopeks = kopeks;

    public bool Equals(Money other) => Kopeks == other.Kopeks;      // без бокса, по значению
    public override bool Equals(object? obj) => obj is Money m && Equals(m);
    public override int GetHashCode() => Kopeks.GetHashCode();

    public static bool operator ==(Money a, Money b) => a.Equals(b);
    public static bool operator !=(Money a, Money b) => !a.Equals(b);
}

Реализовав IEquatable<T>, вы получаете быстрое сравнение, нормальную работу в коллекциях и возможность определить ==.

Бокс: когда значение всё-таки уезжает в кучу

var p = new Point(1, 2);

object boxed = p;          // ✘ аллокация в куче + копия значения
IComparable c = p;         // ✘ то же, если у типа нет generic-интерфейса

var list = new List<Point>();   // ✔ generic-коллекция: значения как значения
list.Add(p);

Бокс «невидим» там, где API ждёт object: не-generic коллекции, старый string.Format, сравнение через Equals(object). Лечится generic-типами и IEquatable<T> (подробно — глава 3).

Частая ошибка: «сделаю struct, будет быстрее»

Для сущности с десятком полей и изменяемым состоянием структура делает хуже: каждое присваивание копирует всё значение, а изменение через свойство теряется. Struct — это про семантику значения, а не про «оптимизацию на всякий случай».

Особый подвид — ref struct (например, Span<T>): такие типы принципиально живут только на стеке. Это отдельная тема — глава 5.

★ Что запомнить из главы
  • struct — значимый тип: переменная хранит значение, присваивание копирует.
  • Внутри можно объявлять методы, свойства, интерфейсы и ссылочные поля; нельзя — наследование, virtual/abstract, финализатор.
  • Копия структуры не глубокая: ссылочные поля указывают на тот же объект.
  • Изменяемые структуры опасны: метод, вызванный на копии (например, через свойство), меняет копию.
  • readonly struct + IEquatable<T> убирают защитные копии, бокс и медленное сравнение.
  • in — про отсутствие копии при передаче; для маленьких типов смысла нет.
