Глава 4. Фабрика: почему new HttpClient() — ловушка

Фабрика нужна не для красоты, а чтобы спрятать создание и время жизни объектов. В .NET это видно на двух классических авариях.

основная глава

Разминка: идея на десяти строках

Задача: в разных местах нужно уведомление, но создаётся оно по-разному. Фабрика — это «кто-то, кто знает, как создать».

public interface INotification { void Show(); }

public sealed class EmailNote : INotification { public void Show() => Console.WriteLine("email"); }
public sealed class SmsNote   : INotification { public void Show() => Console.WriteLine("sms"); }

// Единственное место, где решается «что создать»
public static class NotificationFactory
{
    public static INotification Create(string channel) => channel switch
    {
        "email" => new EmailNote(),
        "sms"   => new SmsNote(),
        _       => throw new ArgumentOutOfRangeException(nameof(channel))
    };
}

// Потребитель не знает про EmailNote и SmsNote вообще
INotification note = NotificationFactory.Create("sms");
note.Show();

Идея: создание вынесено в одно место. В реальном проекте за этим «одним местом» стоят ещё настройка, время жизни объекта и пулы — об этом дальше.

Авария №1: HttpClient и исчерпанные сокеты

Выглядит правильно — «создал, использовал, освободил»:

// ✘ так делать нельзя
public async Task<string> GetAsync(string url, CancellationToken ct)
{
    using var client = new HttpClient();       // новый сокет на каждый вызов
    return await client.GetStringAsync(url, ct);
}

Почему это ломается под нагрузкой:

  • HttpClient — это обёртка над сокетом; Dispose закрывает соединение.
  • Закрытый TCP-сокет уходит в состояние TIME_WAIT на десятки секунд. При тысяче вызовов в секунду порт-лимит заканчивается — начинаются ошибки вида «не удалось выделить сокет».
  • Один статический HttpClient тоже не универсален: он держит соединения (и DNS), которые могут «протухнуть».
Фабрика, которая решает всё три проблемы

IHttpClientFactory пулирует обработчики (handlers): сокеты переиспользуются, но их жизнью управляет платформа, а настройки (базовый адрес, таймауты, ретраи, заголовки) задаются один раз и по имени.

// ── Шаг 1. Регистрация: один раз при старте приложения ─────────────────────
builder.Services.AddHttpClient("payments", c =>
{
    c.BaseAddress = new Uri("https://payments.example.com");   // 1) куда ходим
    c.Timeout = TimeSpan.FromSeconds(5);                       // 2) сколько ждём
})
.AddStandardResilienceHandler();                               // 3) ретраи + circuit breaker

// ── Шаг 2. Использование: клиент приходит от фабрики, а не от new ──────────
public sealed class PaymentClient(IHttpClientFactory factory)  // 4) фабрику внедрили
{
    public async Task<PaymentStatus> GetAsync(Guid id, CancellationToken ct)
    {
        using var client = factory.CreateClient("payments");   // 5) клиент на этот вызов

        return await client.GetFromJsonAsync<PaymentStatus>($"/payments/{id}", ct)!;  // 6) запрос
    }
}
Что происходит по шагам
  • 5) CreateClient не создаёт новый сокет: он берёт общий handler из пула и оборачивает его в лёгкий HttpClient.
  • После вызова using освобождает именно HttpClient, а соединение возвращается в пул — TIME_WAIT больше не накапливается.
  • Настройки (адрес, таймаут, ретраи) заданы в одном месте — в шаге 1.

Авария №2: scoped-объект в singleton

Фоновый сервис (IHostedService) живёт всё время процесса. DbContext — scoped (живёт в рамках запроса). Если попытаться внедрить одно в другое, приложение упадёт с «Cannot consume scoped service from singleton».

// ✘ так не скомпилируется как задумано: DbContext — scoped, воркер — singleton
public sealed class OutboxWorker(AppDbContext db) : BackgroundService { … }

Правильный ответ — фабрика контекста: она создаёт новый контекст на одну операцию и освобождает его после.

// 1) регистрируем ФАБРИКУ контекста, а не сам контекст
builder.Services.AddDbContextFactory<AppDbContext>(o => o.UseNpgsql(cs));

// 2) воркер живёт всё время процесса (singleton) — поэтому получает фабрику
public sealed class OutboxWorker(IDbContextFactory<AppDbContext> factory) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            // 3) на каждую итерацию — свежий контекст: свой ChangeTracker, свежие данные
            await using var db = await factory.CreateDbContextAsync(ct);

            var batch = await db.Outbox
                .Where(x => x.Status == "new")
                .Take(100)
                .ToListAsync(ct);
            …

            await db.SaveChangesAsync(ct);
            // 4) await using освободит контекст: соединение вернётся в пул
            await Task.Delay(TimeSpan.FromSeconds(1), ct);
        }
    }
}

Три вида фабрик — и в чём разница

ВидСутьПример в .NET
Простая фабрикаОдин метод/класс решает, какой тип создатьВаш NotificationFactory.Create(type)
Фабричный методСоздание вынесено в метод, который наследники могут переопределитьILoggerFactory.CreateLogger()
Абстрактная фабрикаСоздаёт семейство согласованных объектовDbProviderFactory (набор объектов для конкретной СУБД)
Фабрика как сервис DIКонтейнер сам управляет созданием и временем жизниIServiceProvider, AddHttpClient, AddDbContextFactory
Важное следствие для .NET

В приложении с DI контейнер уже является фабрикой. Поэтому «своя» фабрика нужна не для того, чтобы «создавать объекты», а чтобы управлять тем, что контейнер не умеет: пулом обработчиков, временем жизни scoped-объектов в фоне, выбором реализации по данным.

Ещё одна жизненная задача: выбор реализации по входным данным

public interface INotificationSender
{
    Task SendAsync(string to, string text, CancellationToken ct);
}

public sealed class NotificationFactory(IEnumerable<INotificationSender> senders)
{
    public INotificationSender For(Channel channel) => channel switch
    {
        Channel.Email => senders.OfType<EmailSender>().Single(),
        Channel.Sms   => senders.OfType<SmsSender>().Single(),
        _             => throw new ArgumentOutOfRangeException(nameof(channel))
    };
}

Здесь фабрика — тонкая: она лишь выбирает из уже собранных контейнером реализаций. Логика отправки остаётся в стратегиях (глава 2) — и это нормальное сочетание паттернов.

Статистика: насколько часто

Оценка: ~85 % проектов и ~25 % от всех применений паттернов.

  • Факт: ILoggerFactory и IHttpClientFactory входят в стандартный набор ASP.NET Core — фабрика используется в любом проекте с логгированием и HTTP-вызовами, то есть почти везде.
  • Почему не 100 %: часть проектов обходится голым IServiceProvider или вообще без DI (консольные утилиты).
  • Оговорка: оценка пропорции, а не измерение (глава 1).

Когда фабрика не нужна

  • Объект без зависимостей и настройки: new Point(3, 5) — фабрика только добавит слой.
  • Контейнер уже всё умеет: если нужен просто IOrderService, его внедряют, а не «достают через фабрику» (иначе получится Service Locator — антипаттерн, глава 6).
  • «Фабрика на будущее»: если вариант один и не планируется второй, это лишний код.
★ Что запомнить из главы
  • Фабрика прячет создание и время жизни объектов, а не «делает красиво».
  • new HttpClient() на каждый вызов → исчерпание сокетов; решение — IHttpClientFactory.
  • Scoped-объект в singleton-сервисе → IDbContextFactory/IServiceScopeFactory.
  • В DI контейнер сам является фабрикой: своя фабрика нужна только там, где контейнер бессилен.
  • Оценка: ~85 % проектов, ~25 % от всех использований паттернов.
