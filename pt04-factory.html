Глава 4. Фабрика: почему new HttpClient() — ловушка

«Спрятать создание и время жизни» — это два конкретных решения, которые потребитель перестаёт принимать сам: что именно создать и как долго объект живёт. В .NET цена ошибки в каждом из них видна на двух классических авариях.

основная глава

Что значит «создание» и «время жизни»

Оба слова звучат абстрактно, пока не разложить их на вопросы, которые код задаёт себе при каждом использовании объекта.

СозданиеВремя жизни
Какой тип создать (EmailNote или SmsNote?) Сколько объектов нужно: на каждый вызов, на запрос, один на процесс?
С какими параметрами (адрес, таймаут, строка подключения, флаги)? Кто освобождает ресурс и когда (Dispose, возврат в пул)?
Какие зависимости передать в конструктор? Кто переиспользует объект и можно ли его вообще переиспользовать?
Что делать, если создать нельзя (неизвестный тип, нет настройки)? Что будет, если объектов станет больше лимита (сокеты, соединения, память)?

«Спрятать» значит, что эти решения принимаются не в месте использования. Потребителю не нужно знать ни класс, ни параметры, ни то, когда вызывать Dispose: он просит «дай мне INotification» или «дай мне клиента для платежей», а фабрика отвечает за всё остальное.

// ✘ решение о создании размазано по коду: три места — три одинаковых new
var mail1 = new SmtpClient("smtp.example.com", 587);    // адрес и порт знает каждый вызывающий
var mail2 = new SmtpClient("smtp.example.com", 587);
var client = new HttpClient();                          // и ещё одно решение — «живёт один вызов»

// ✔ решение принято один раз, в фабрике; потребитель видит только контракт
INotification note = NotificationFactory.Create("email");
using var http = _httpClientFactory.CreateClient("payments");

Зачем прятать — четыре причины, и каждая проверяема на практике:

  1. Одно место изменения. Сменился адрес платёжного сервиса, таймаут или тип уведомления — правится одна регистрация, а не двадцать вызовов new.
  2. Нельзя забыть про ресурс. Если создание спрятано, вызывающий код физически не может «забыть Dispose» или создать HttpClient на каждый вызов: политика освобождения живёт там же, где создание.
  3. Тесты. Подменить реализацию можно в одном месте (в контейнере), не трогая потребителей.
  4. Политика и лимиты. Пул соединений, максимальное число сокетов, повторные попытки, таймауты — это свойства создания, и настраивать их надо централизованно.
Почему в .NET это особенно заметно

Здесь есть объекты, у которых «создание» и «время жизни» стоят денег: HttpClient держит сокет, DbContext — соединение и ChangeTracker, ILoggerFactory — подписки на провайдеры. Ошибка в любом из двух решений проявляется не сразу, а под нагрузкой: исчерпанные порты, «второй запрос на том же контексте», утечка памяти.

Разминка: идея на десяти строках

Задача: в разных местах нужно уведомление, но создаётся оно по-разному. Фабрика — это «кто-то, кто знает, как создать».

public interface INotification { void Show(); }

public sealed class EmailNote : INotification { public void Show() => Console.WriteLine("email"); }
public sealed class SmsNote   : INotification { public void Show() => Console.WriteLine("sms"); }

// Единственное место, где решается «что создать»
public static class NotificationFactory
{
    public static INotification Create(string channel) => channel switch
    {
        "email" => new EmailNote(),
        "sms"   => new SmsNote(),
        _       => throw new ArgumentOutOfRangeException(nameof(channel))
    };
}

// Потребитель не знает про EmailNote и SmsNote вообще
INotification note = NotificationFactory.Create("sms");
note.Show();

Идея: создание вынесено в одно место. В реальном проекте за этим «одним местом» стоят ещё настройка, время жизни объекта и пулы — об этом дальше.

Авария №1: HttpClient и исчерпанные сокеты

Выглядит правильно — «создал, использовал, освободил»:

// ✘ так делать нельзя
public async Task<string> GetAsync(string url, CancellationToken ct)
{
    using var client = new HttpClient();       // новый сокет на каждый вызов
    return await client.GetStringAsync(url, ct);
}

Почему это ломается под нагрузкой:

  • HttpClient — это обёртка над сокетом; Dispose закрывает соединение.
  • Закрытый TCP-сокет уходит в состояние TIME_WAIT на десятки секунд. При тысяче вызовов в секунду порт-лимит заканчивается — начинаются ошибки вида «не удалось выделить сокет».
  • Один статический HttpClient тоже не универсален: он держит соединения (и DNS), которые могут «протухнуть».
Фабрика, которая решает всё три проблемы

IHttpClientFactory пулирует обработчики (handlers): сокеты переиспользуются, но их жизнью управляет платформа, а настройки (базовый адрес, таймауты, ретраи, заголовки) задаются один раз и по имени.

// ── Шаг 1. Регистрация: один раз при старте приложения ─────────────────────
builder.Services.AddHttpClient("payments", c =>
{
    c.BaseAddress = new Uri("https://payments.example.com");   // 1) куда ходим
    c.Timeout = TimeSpan.FromSeconds(5);                       // 2) сколько ждём
})
.AddStandardResilienceHandler();                               // 3) ретраи + circuit breaker

// ── Шаг 2. Использование: клиент приходит от фабрики, а не от new ──────────
public sealed class PaymentClient(IHttpClientFactory factory)  // 4) фабрику внедрили
{
    public async Task<PaymentStatus> GetAsync(Guid id, CancellationToken ct)
    {
        using var client = factory.CreateClient("payments");   // 5) клиент на этот вызов

        return await client.GetFromJsonAsync<PaymentStatus>($"/payments/{id}", ct)!;  // 6) запрос
    }
}
Что такое «ретраи» и «circuit breaker» в строке 3

AddStandardResilienceHandler() добавляет к клиенту готовый набор политик (пакет Microsoft.Extensions.Http.Resilience, .NET 8). Две из них — самые важные:

  • Ретрай (retry, повтор) — если вызов упал временно (таймаут, обрыв соединения, ответ 5xx), тот же запрос повторяется ещё несколько раз с паузой. «Временно» — ключевое слово: 4xx повторять бессмысленно (запрос неверен), а POST, который создаёт платёж, — опасно (можно создать дважды), поэтому повторяют только идемпотентные операции или с ключом идемпотентности. Пауза растёт экспоненциально плюс случайная добавка (jitter), чтобы клиенты не били по серверу одновременно.
  • Предохранитель (circuit breaker) — счётчик неудач с окном. Когда доля ошибок превышает порог (и запросов было достаточно), «пробка выбивает»: все вызовы сразу падают, не доходя до сервиса. Через заданное время предохранитель пропускает один пробный запрос (half-open): успех — цепь закрывается, ошибка — снова открывается. Смысл: не тратить свои потоки и таймауты на зависимость, которая и так лежит, и дать ей время восстановиться.

Значения по умолчанию у стандартного пайплайна (получены из new HttpStandardResilienceOptions(), .NET 8):

Проверено на локальном сервере (в демонстрации MaxRetryAttempts = 1 и MinimumThroughput = 2 — с настройками по умолчанию ждать пришлось бы дольше): эндпоинт отвечал 503 два раза, потом 200 — клиент сделал три запроса и вернул 200 за 536 мс (паузы между повторами). Второй эндпоинт отвечал 500 всегда; после двух запросов к нему (первый вызов: попытка + ретрай) предохранитель открылся, и следующие вызовы падали мгновенно, не доходя до сервера:

1) /flaky -> 200 за 536 мс (ретраи внутри)      ← сервер получил 3 запроса
2) /fail: три вызова подряд
   вызов 1: 500 за 149 мс                       ← 2 запроса к серверу (1 попытка + 1 ретрай)
   вызов 2: BrokenCircuitException за 3 мс: The circuit is now open and is not allowing calls.
   вызов 3: BrokenCircuitException за 0 мс: The circuit is now open and is not allowing calls.

Подробно политики, таймауты и метрики разобраны в главе 27 «Устойчивость внешних вызовов».

Что происходит по шагам
  • 5) CreateClient не создаёт новый сокет: он берёт общий handler из пула и оборачивает его в лёгкий HttpClient.
  • После вызова using освобождает именно HttpClient, а соединение возвращается в пул — TIME_WAIT больше не накапливается.
  • Настройки (адрес, таймаут, ретраи) заданы в одном месте — в шаге 1.

Откуда взялся IHttpClientFactory

Резонный вопрос: это интерфейс, но кто его реализует и когда появляется объект? Ответ: его регистрирует сам AddHttpClient() — вы не пишете ни класс, ни регистрацию фабрики. Проверено на пустом ServiceCollection:

после AddHttpClient() в контейнере:
   IHttpClientFactory   Lifetime=Singleton   Impl=(factory)
   HttpClient           Lifetime=Transient   Impl=(factory)

GetRequiredService<IHttpClientFactory>() -> Microsoft.Extensions.Http.DefaultHttpClientFactory
AddHttpClient<PaymentClient>()             -> PaymentClient Lifetime=Transient
без AddHttpClient()                       -> InvalidOperationException:
   No service for type 'System.Net.Http.IHttpClientFactory' has been registered.

То есть последовательность такая:

  1. В Program.cs вызывается AddHttpClient() (без имени — только фабрика, либо с именем — фабрика + описание клиента, либо с типом — фабрика + типизированный клиент).
  2. Метод кладёт в DI-контейнер IHttpClientFactory (Singleton) и HttpClient (Transient). Реализация — DefaultHttpClientFactory из Microsoft.Extensions.Http (входит в ASP.NET Core, отдельный пакет нужен только консольным приложениям).
  3. Дальше фабрика внедряется как любой сервис: PaymentClient(IHttpClientFactory factory). «Внедрить» её можно только после шага 1 — порядок регистраций в Program.cs при этом не важен, важен сам факт вызова до Build().
// шаг 1: имя + настройки. Имя — это ключ, по которому потом выдадут клиента
builder.Services.AddHttpClient("payments", c =>
{
    c.BaseAddress = new Uri("https://payments.example.com");
    c.Timeout = TimeSpan.FromSeconds(5);
});

// шаг 3: фабрика пришла из контейнера, имя — то же самое
public sealed class PaymentClient(IHttpClientFactory factory)
{
    public Task<HttpResponseMessage> GetAsync(Guid id, CancellationToken ct)
    {
        using var client = factory.CreateClient("payments");   // BaseAddress уже настроен
        return client.GetAsync($"/payments/{id}", ct);
    }
}
Что важно знать про имена
  • Имя — обычная строка. Опечатались в CreateClient("payment") — получите клиента без настроек: BaseAddress = null, без таймаута из регистрации. Исключения не будет (проверено), ошибка вылезет позже — на относительном URL.
  • Типизированный клиент короче: AddHttpClient<PaymentClient>() регистрирует PaymentClient как Transient и сам передаёт ему настроенный HttpClient — тогда IHttpClientFactory в конструкторе не нужен.
  • Пул общий. Все клиенты с одним именем используют один и тот же пул handlers, поэтому using вокруг CreateClient освобождает только лёгкую обёртку, а не соединения (глава 27 «Устойчивость внешних вызовов»).

Авария №2: scoped-объект в singleton

Фоновый сервис (IHostedService) живёт всё время процесса. DbContext — scoped (живёт в рамках запроса). Если попытаться внедрить одно в другое, приложение упадёт с «Cannot consume scoped service from singleton».

// ✘ так не скомпилируется как задумано: DbContext — scoped, воркер — singleton
public sealed class OutboxWorker(AppDbContext db) : BackgroundService { … }

Правильный ответ — фабрика контекста: она создаёт новый контекст на одну операцию и освобождает его после.

// 1) регистрируем ФАБРИКУ контекста, а не сам контекст
builder.Services.AddDbContextFactory<AppDbContext>(o => o.UseNpgsql(cs));

// 2) воркер живёт всё время процесса (singleton) — поэтому получает фабрику
public sealed class OutboxWorker(IDbContextFactory<AppDbContext> factory) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            // 3) на каждую итерацию — свежий контекст: свой ChangeTracker, свежие данные
            await using var db = await factory.CreateDbContextAsync(ct);

            var batch = await db.Outbox
                .Where(x => x.Status == "new")
                .Take(100)
                .ToListAsync(ct);
            …

            await db.SaveChangesAsync(ct);
            // 4) await using освободит контекст: соединение вернётся в пул
            await Task.Delay(TimeSpan.FromSeconds(1), ct);
        }
    }
}
Где именно заканчивается await using var db

В коде выше await using var db = ... стоит в начале тела while, поэтому контекст освобождается в конце тела цикла — то есть после await Task.Delay(1000, ct), а не сразу после SaveChangesAsync. Проверено на эквивалентном коде с метками времени: Dispose случился через 100 мс сна, а не в момент объявления.

Если контекст должен жить только работу, сузьте область — скобками:

while (!ct.IsCancellationRequested)
{
    await using (var db = await factory.CreateDbContextAsync(ct))
    {
        var batch = await db.Outbox.Where(x => x.Status == "new").Take(100).ToListAsync(ct);
        …
        await db.SaveChangesAsync(ct);
    }                                        // ← контекст освобождён здесь
    await Task.Delay(TimeSpan.FromSeconds(1), ct);   // пауза уже без контекста
}

Подробно про область жизни using var, порядок Dispose и await using — в C#-книге, глава 23.

Почему это не «scoped внутри singleton»

Резонный вопрос: воркер — singleton, а AppDbContext — scoped. Не то же ли это самое нарушение? Нет: разница в том, что именно попало в singleton.

  • Плохо — в singleton попадает сам scoped-объект. Тогда он живёт всё время процесса: DbContext не освобождается, его ChangeTracker копит отслеживаемые сущности, соединение держится. Плюс при проверке scope контейнер бросает «Cannot consume scoped service from singleton».
  • Хорошо — в singleton попадает фабрика. IDbContextFactory<AppDbContext> регистрируется как singleton и не хранит контекст: каждый CreateDbContextAsync() создаёт новый экземпляр, а await using его освобождает (шаги 3–4 в коде). В поле воркера лежит только фабрика — ни одного scoped-объекта.

Если scoped-сервис — не DbContext: scope

«То же» — это та же проблема: singleton (фоновый воркер) хочет работать с сервисом, зарегистрированным как Scoped. Для DbContext есть отдельная фабрика IDbContextFactory<T>, а для любого другого scoped-сервиса (репозиторий, Unit of Work, сервис с состоянием запроса) универсальный способ — создать scope вручную. Пример: IOrdersRepository зарегистрирован как Scoped.

builder.Services.AddScoped<IOrdersRepository, OrdersRepository>();

public sealed class PollingWorker(IServiceScopeFactory scopeFactory) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            using (var scope = scopeFactory.CreateScope())          // 1) граница владения
            {
                var repo = scope.ServiceProvider                     // 2) scoped из ЭТОГО scope
                    .GetRequiredService<IOrdersRepository>();

                await repo.DoWorkAsync(ct);                          // 3) работа
            }                                                        // 4) Dispose(scope) здесь

            await Task.Delay(1000, ct);                              // пауза уже без scope
        }
    }
}

По шагам:

  1. CreateScope() создаёт не сервис, а границу владения: у scope свой ServiceProvider и свой набор scoped-экземпляров.
  2. Резолв внутри scope отдаёт объект, принадлежащий именно этому scope. Два разных scope — два разных экземпляра (проверено: «два scope → два экземпляра: True»).
  3. Работа — всё, что должно жить в одной единице работы.
  4. Конец блока — Dispose scope; контейнер сам вызовет Dispose у всех scoped-сервисов, созданных внутри (проверено: два scope — «освобождено 2»). Ручной using на самом репозитории не нужен: владелец — контейнер, а второй Dispose (пусть обычно и безвредный) означает, что владение определено неверно.

Чего этот способ не делает:

  • не превращает репозиторий в singleton и не делит его между итерациями — каждая итерация получает свежий экземпляр;
  • не отменяет правило «долгоживущий не зависит от короткоживущего»: в поле воркера лежит только фабрика scope, а не scoped-объект;
  • не делает транзакцию на несколько итераций: scope — это время жизни объектов, а не транзакция;
  • не освобождает объекты, созданные вами вручную вне scope, и не защищает от конкурентности: DbContext и большинство scoped-сервисов не потокобезопасны, поэтому один scope — одна последовательная единица работы.

Два практических нюанса
  • CreateScope() против CreateAsyncScope(). Если среди scoped-сервисов есть реализующий только IAsyncDisposable, обычный CreateScope() при закрытии упадёт: InvalidOperationException: 'AsyncThing' type only implements IAsyncDisposable. Use DisposeAsync to dispose the container. Тогда — await using var scope = factory.CreateAsyncScope(); (проверено: работает).
  • Не храните scope в поле. Он живёт ровно одну единицу работы; повторное использование того же scope между операциями — это тот же captive dependency, только замаскированный.

Четыре вида фабрик — и в чём разница

В таблице ниже четыре строки, и это не «четыре паттерна GoF». Два из них — действительно паттерны из книги «Банды четырёх» (Factory Method и Abstract Factory); «простая фабрика» — распространённая идиома, которой в GoF нет; «фабрика как сервис DI» — вообще механизм платформы, а не паттерн. В одной таблице они стоят потому, что отвечают на один и тот же вопрос («кто решает, что создать и как долго это живёт»), но разными механизмами. Поэтому дальше — по строке на каждый, с кодом и тем, что происходит под капотом.

1. Простая фабрика: один метод со switch

Это то, с чего начиналась глава (NotificationFactory.Create(channel)). Под капотом — обычный статический метод: решение принимается здесь и сейчас, по значению параметра; наследников нет, переопределить нечего. Меняется набор типов — правится один switch. Это идиома, а не паттерн GoF: у неё нет ни полиморфизма, ни инверсии управления.

2. Фабричный метод: решение принимает наследник

Здесь создание вынесено в виртуальный метод базового класса, а конкретный тип выбирает наследник. Базовая логика при этом общая (типы Report и IWriter — условные, важен только контракт):

public abstract class ReportExporter
{
    protected abstract IWriter CreateWriter();      // ← фабричный метод: решает наследник

    public void Export(Report report)               // общий алгоритм для всех наследников
    {
        using var writer = CreateWriter();
        writer.Write(report);
    }
}

public sealed class CsvExporter : ReportExporter
{
    protected override IWriter CreateWriter() => new CsvWriter();
}

Под капотом — виртуальный вызов: Export не знает, какой писатель появится, но контракт гарантирует, что он будет. В .NET этот приём встречается в обёртке над «создать по интерфейсу»: ILoggerFactory.CreateLogger(string) возвращает ILogger (проверено: тип возврата — ILogger), а какая реализация логгера получится, решает конкретная фабрика.

3. Абстрактная фабрика: семейство согласованных объектов

Отличие от фабричного метода: создаётся не один объект, а набор объектов одного семейства, которые должны подходить друг другу. Классический пример в .NET — DbProviderFactory: одна фабрика для конкретной СУБД создаёт соединение, команду, параметр, адаптер и построитель строки подключения. Проверено рефлексией, что она создаёт именно семейство:

DbProviderFactory создаёт: CreateBatch, CreateBatchCommand, CreateCommand,
CreateCommandBuilder, CreateConnection, CreateConnectionStringBuilder,
CreateDataAdapter, CreateDataSource, CreateDataSourceEnumerator, CreateParameter

Смысл: нельзя случайно смешать SqlConnection с NpgsqlCommand — все объекты приходят из одного семейства и гарантированно совместимы.

4. Фабрика как сервис DI: создание и время жизни — у контейнера

Это уже не паттерн, а механизм: контейнер сам решает, когда создать объект и сколько он живёт. Фабрика здесь — объект, который умеет выдать сервис, и его регистрирует платформа. Проверено: AddHttpClient() кладёт IHttpClientFactory как Singleton, а реализация — Microsoft.Extensions.Http.DefaultHttpClientFactory; типизированный клиент регистрируется как Transient. Разница с первыми тремя: там вы вызываете метод и получаете объект сейчас, а здесь вы просите «дай мне IHttpClientFactory» — и контейнер решает, что вернуть, создать ли новый экземпляр и когда его освободить.

Важное следствие для .NET

В приложении с DI контейнер уже является фабрикой. Поэтому «своя» фабрика нужна не для того, чтобы «создавать объекты», а чтобы управлять тем, что контейнер не умеет: пулом обработчиков, временем жизни scoped-объектов в фоне, выбором реализации по данным.

Ещё одна жизненная задача: выбор реализации по входным данным

public interface INotificationSender
{
    Task SendAsync(string to, string text, CancellationToken ct);
}

public sealed class NotificationFactory(IEnumerable<INotificationSender> senders)
{
    public INotificationSender For(Channel channel) => channel switch
    {
        Channel.Email => senders.OfType<EmailSender>().Single(),
        Channel.Sms   => senders.OfType<SmsSender>().Single(),
        _             => throw new ArgumentOutOfRangeException(nameof(channel))
    };
}

Здесь фабрика — тонкая: она лишь выбирает из уже собранных контейнером реализаций. Логика отправки остаётся в стратегиях (глава 2) — и это нормальное сочетание паттернов.

Статистика: насколько часто

Оценка: ~85 % проектов и ~25 % от всех применений паттернов.

  • Факт: ILoggerFactory и IHttpClientFactory входят в стандартный набор ASP.NET Core — фабрика используется в любом проекте с логгированием и HTTP-вызовами, то есть почти везде.
  • Почему не 100 %: часть проектов обходится голым IServiceProvider или вообще без DI (консольные утилиты).
  • Оговорка: оценка пропорции, а не измерение (глава 1).

Когда фабрика не нужна

  • Объект без зависимостей и настройки: new Point(3, 5) — фабрика только добавит слой.
  • Контейнер уже всё умеет: если нужен просто IOrderService, его внедряют, а не «достают через фабрику» (иначе получится Service Locator — антипаттерн, глава 6).
  • «Фабрика на будущее»: если вариант один и не планируется второй, это лишний код.
★ Что запомнить из главы
  • Фабрика прячет создание и время жизни объектов, а не «делает красиво».
  • new HttpClient() на каждый вызов → исчерпание сокетов; решение — IHttpClientFactory.
  • Scoped-объект в singleton-сервисе → IDbContextFactory/IServiceScopeFactory.
  • В DI контейнер сам является фабрикой: своя фабрика нужна только там, где контейнер бессилен.
  • Оценка: ~85 % проектов, ~25 % от всех использований паттернов.
