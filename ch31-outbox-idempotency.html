Глава 31. Надёжные интеграции: Transactional Outbox, идемпотентность и саги

Что делать, когда данные нужно записать в свою базу и передать в чужой сервис — и нельзя ни потерять, ни продублировать.

основная глава

Проблема: две системы и одна транзакция

Разберём типичный код: сохранить заказ и отправить событие «заказ создан» в брокер (глава 29). Выглядит логично, но между этими действиями нет и не может быть общей транзакции — это две разные системы. Такая ситуация называется dual write («двойная запись»).

// ✘ коммит и отправка — не одно действие
await db.SaveChangesAsync(ct);              // 1) база
await _bus.PublishAsync(new OrderCreated(id), ct);   // 2) брокер

Между шагами 1 и 2 всегда есть окно, и в нём возможны три исхода:

Что произошлоРезультат для системы
База сохранилась, отправка упала (сеть, брокер недоступен)Событие потеряно: заказ есть, а склад и биллинг о нём не знают. Тихая ошибка — никто не узнает
Отправка прошла, коммит упал (ошибка БД)Событие-фантом: соседи обрабатывают то, чего в базе нет
Отправка «зависла» по таймаутуНеизвестность: дошло или нет? Повтор даёт дубликаты, отсутствие повтора — потерю
Почему не одна общая транзакция на две системы

Технически это двухфазный коммит (2PC): координатор, который сначала «подготавливает» всех участников, а потом подтверждает. На практике это не работает: нужна поддержка XA каждой стороной, в контейнерах и облаке координатор (MSDTC) обычно недоступен, а подготовленные транзакции в PostgreSQL мешают очистке (VACUUM) и превращаются в источник инцидентов. Поэтому надёжность строят не на «общей транзакции», а на гарантиях через базу.

Transactional Outbox: событие как часть транзакции

Идея проста и надёжна: сделать намерение отправить событие частью транзакции в базе. Рядом с бизнес-данными появляется таблица outbox, и сообщение пишется в неё в той же самой транзакции, что и заказ. Отправляет сообщение отдельный воркер — уже после коммита.

Поток целиком

Запрос клиента
   │
   ├─ BEGIN
   │    INSERT INTO orders  …                                  ← бизнес-данные
   │    INSERT INTO outbox  (type='order.created', payload=…)  ← намерение отправить
   ├─ COMMIT                    ← атомарно: либо есть оба, либо ни одного
   │
   └─ воркер:  SELECT … FOR UPDATE SKIP LOCKED → publish → UPDATE status='sent'
-- таблица-очередь внутри вашей же базы
CREATE TABLE outbox (
    id           bigint      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    occurred_at  timestamptz NOT NULL DEFAULT now(),
    type         text        NOT NULL,
    payload      jsonb       NOT NULL,
    status       text        NOT NULL DEFAULT 'new',      -- new | sent | failed
    attempts     int         NOT NULL DEFAULT 0,
    next_attempt timestamptz NOT NULL DEFAULT now(),      -- время следующей попытки
    sent_at      timestamptz
);

-- частичный индекс: ищем только «ожидающие» сообщения
CREATE INDEX outbox_pending_idx ON outbox (next_attempt) WHERE status = 'new';

Продюсер (обычный код обработки запроса):

await using var tx = await db.Database.BeginTransactionAsync(ct);

db.Orders.Add(order);
db.Outbox.Add(new OutboxMessage
{
    Type    = "order.created",
    Payload = JsonSerializer.SerializeToDocument(new { order.Id, order.Total })
});

await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);      // заказ и событие — одной транзакцией
Что именно даёт outbox
  • Атомарность «мои данные + намерение отправить». Нет заказа — нет события; нет события — нет заказа. Фантомы исчезают.
  • Потерь нет. Даже если брокер лежит час, сообщения лежат в базе и уедут, когда он вернётся.
  • Можно переиграть. Сбойный обработчик чинится, а сообщения отправляются заново — без ручных вылазок в прод.
  • Видно состояние. Количество неотправленных сообщений — это метрика, по которой видно проблему до того, как её заметят данные.

Воркер: как сообщения уезжают

Воркер — обычный BackgroundService (глава 26): забирает пачку сообщений, публикует и помечает. Ключевая деталь — FOR UPDATE SKIP LOCKED: строки блокируются на время обработки, но воркеры не мешают друг другу — каждый берёт свою пачку, а не ждёт чужую блокировку.

protected override async Task ExecuteAsync(CancellationToken ct)
{
    while (!ct.IsCancellationRequested)
    {
        var batch = await db.Outbox.FromSqlRaw("""
            SELECT * FROM outbox
            WHERE status = 'new' AND next_attempt <= now()
            ORDER BY id
            LIMIT 100
            FOR UPDATE SKIP LOCKED          -- берём только «свободные» строки
            """).ToListAsync(ct);

        foreach (var msg in batch)
        {
            try
            {
                await _bus.PublishAsync(msg, ct);
                msg.Status = "sent";
                msg.SentAt = DateTime.UtcNow;
            }
            catch (Exception)
            {
                msg.Attempts++;
                msg.NextAttempt = DateTime.UtcNow.AddSeconds(Math.Pow(2, msg.Attempts)); // 2, 4, 8… с
                if (msg.Attempts >= 10)
                    msg.Status = "failed";            // dead-letter + метрика и алерт
            }
        }
        await db.SaveChangesAsync(ct);

        if (batch.Count == 0)
            await Task.Delay(TimeSpan.FromSeconds(1), ct);   // не «крутить» пустой цикл
    }
}
  • Пачка, а не всё сразу. Размер пачки (например, 100) ограничивает и память, и время удержания блокировок.
  • Backoff с потолком. Растущая пауза не даёт «долбить» упавший брокер, а потолок (например, пять минут) не даёт задержке стать бесконечной.
  • Dead-letter и алерт. Сообщение, не ушедшее за 10 попыток, — это инцидент, а не «пусть лежит». Его должно быть видно: метрика, алерт, дашборд.
  • Порядок. Параллельная отправка может переставить сообщения. Если порядок важен, воркер обрабатывает строго по id (одна пачка — один поток) или отправляет события одного ключа в одну партицию брокера.
  • Очистка. Отправленные сообщения удаляются заданием по расписанию (например, старше суток). Иначе таблица outbox сама станет источником bloat — как любая «горячая» таблица с частыми DELETE (глава 23 SQL-раздела).
  • Короткие транзакции. Воркер не держит соединение и блокировки, пока «думает»: публикация идёт между короткими обращениями к базе (глава 23).

Идемпотентность: почему доставка «минимум один раз»

Outbox даёт гарантию at-least-once — «минимум один раз». Почему не «ровно один»: воркер мог успеть отправить сообщение, но упасть до того, как отметил его отправленным. Тогда после перезапуска он отправит его снова. Это не дефект реализации, а свойство распределённых систем — «exactly-once» доставки «из коробки» не существует.

Вывод: потребитель должен быть идемпотентным — повторная обработка того же сообщения не должна менять результат.

// ✘ повтор = второе списание
await db.Accounts.Where(a => a.Id == id).ExecuteUpdateAsync(
    s => s.SetProperty(a => a.Balance, a => a.Balance - amount), ct);

// ✔ «входящая» таблица + уникальный ключ сообщения: повтор отсекается
var inserted = await db.Inbox.AnyAsync(x => x.MessageId == messageId, ct);
if (inserted) return;                                   // уже обрабатывали — выходим

db.Inbox.Add(new InboxMessage { MessageId = messageId });
await db.Accounts.Where(a => a.Id == id).ExecuteUpdateAsync(
    s => s.SetProperty(a => a.Balance, a => a.Balance - amount), ct);
await db.SaveChangesAsync(ct);                          // запись в inbox и сам эффект — одной транзакцией
CREATE TABLE inbox (
    message_id  uuid PRIMARY KEY,        -- ключ сообщения от продюсера
    processed_at timestamptz NOT NULL DEFAULT now()
);
  • Ключ сообщения генерирует продюсер (например, Guid или order-id + тип события) и кладёт его в payload. Так повтор «того же» события распознаётся на приёмнике.
  • Альтернативы для простых случаев: INSERT … ON CONFLICT DO NOTHING, уникальный индекс по бизнес-ключу, «естественная» идемпотентность операции (SET status = 'paid' вместо balance = balance + amount).
  • Идемпотентность нужна и на входе API: Idempotency-Key в заголовке, ответ сохраняется и повторяется при том же ключе — это спасает от повторных запросов клиента.

Когда процессов несколько: саги и компенсации

Outbox закрывает передачу своего события. Но бизнес-процесс часто длиннее: создать заказ → списать деньги → зарезервировать товар → отгрузить. Это работа нескольких сервисов, и одной транзакции на них нет и быть не может.

Вместо «всё или ничего» используют сагу: последовательность локальных транзакций, у каждой из которых есть компенсация — действие, отменяющее её результат.

Шаг сагиКомпенсация при сбое дальше по цепочке
Заказ создан (статус «новый»)Отменить заказ
Деньги списаныВернуть деньги
Товар зарезервированСнять резерв
Отгрузка оформленаОтменить отгрузку
  • Оркестрация — есть координатор (процесс-менеджер), который знает шаги и запускает компенсации. Проще отлаживать.
  • Хореография — сервисы слушают события друг друга и сами решают, что делать. Меньше связности, но логика процесса «размазана» и её труднее увидеть целиком.
  • Итоговая согласованность — данные становятся согласованными не «в момент», а через некоторое время. Это осознанный обмен: мы отказываемся от мгновенной строгой согласованности ради доступности и масштабируемости.

Альтернативы и когда outbox не нужен

ПодходКак работаетКогда выбирать
Outbox в своей БДСобытие пишется в транзакции, воркер публикуетДанные уже в БД, нужна гарантия «не потеряется». Универсальный выбор
CDC (Debezium, логическая репликация)Внешний процесс читает журнал изменений (WAL) и публикует событияНе хочется писать в outbox из приложения; нужны события по любым изменениям таблицы
Периодическая сверка (reconciliation)Задание сравнивает состояние систем и догоняет расхожденияКак дополнение к любому подходу: страховка от «зависших» событий
Отправка после коммита с ретраямиПросто повторить публикацию при сбоеПотеря события допустима (аналитика, «мягкие» уведомления) — самое дешёвое решение
Цена, о которой надо сказать честно
  • Задержка. Событие уходит через цикл воркера — десятки-сотни миллисекунд, а не мгновенно.
  • Дополнительная нагрузка на БД. Вставка в outbox и её последующая очистка — это ещё запись и ещё мёртвые версии (глава 23 SQL-раздела).
  • Сложнее код и код-ревью. Появляются воркер, повторы, dead-letter, дедупликация.

Поэтому outbox берут там, где потеря события действительно дорога: платежи, заказы, склад, биллинг. Для телеметрии и «мягких» уведомлений достаточно отправки с ретраями.

Что смотреть в эксплуатации

  • Время до отправки (lag): сколько живёт самое старое неотправленное сообщение. Рост — первый признак, что воркер не справляется или брокер «тормозит».
  • Количество new и failed. failed — всегда алерт: кто-то не получил свои данные.
  • Число повторов. Много повторов = нестабильный брокер или ошибка в отправке.
  • Размер таблицы outbox. Если очистка не работает, таблица растёт (и это bloat).
  • Дубликаты на приёмнике. Если их много — повод проверить идемпотентность обработчиков.
★ Что запомнить из главы
  • Запись в БД и отправка события — две системы: без специального приёма возможны и потеря, и фантом.
  • Transactional Outbox: пишем намерение отправить в ту же транзакцию, что и данные, а публикует отдельный воркер.
  • Доставка получается at-least-once → потребитель обязан быть идемпотентным (таблица inbox, уникальные ключи, ON CONFLICT).
  • Обязательные детали: FOR UPDATE SKIP LOCKED, backoff, dead-letter с алертом, очистка, метрика «лаг отправки».
  • Процесс из нескольких сервисов закрывается сагами с компенсациями, а не попыткой сделать одну распределённую транзакцию.
