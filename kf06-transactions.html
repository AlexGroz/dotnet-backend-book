Глава 6. Транзакции и exactly-once: атомарная запись и коммит оффсетов

Почему at-least-once даёт дубли, что именно делает транзакция Kafka, как читать маркеры COMMIT/ABORT в сыром логе и почему lag у EOS-группы никогда не станет нулём

основная глава

Откуда берутся дубли

В главе 4 мы коммитили оффсет вручную и получали at-least-once: потребитель может обработать запись, упасть до коммита и обработать её снова. Есть и второй источник дублей — продюсер: если брокер записал сообщение, а подтверждение потерялось, клиент повторит отправку.

Идемпотентный продюсер (глава 3, EnableIdempotence=true) убирает второй источник: брокер помнит (producerId, epoch, sequence) и отбрасывает повтор. Но остаётся главная проблема — запись в Kafka и коммит оффсета не атомарны:

// «наивный» EOS: два независимых действия
producer.Produce("orders-out", result);            // 1) записали результат
consumer.Commit(record);                           // 2) сдвинули оффсет
// упали между 1 и 2 → после рестарта запись обработается снова → дубль в orders-out
// упали после 2, но запись не долетела → потеря результата

Транзакция Kafka склеивает эти два действия в одно: либо в журнал попадут и записи, и новый оффсет, либо ничего. Дальше — как это устроено и как проверяется.

Отдельные листенеры — не придирка: клиент с хоста не сможет подключиться к kfk:9092 (такого имени в DNS хоста нет), а утилиты внутри контейнера — к localhost:19092. Отсюда два адреса в одном стенде: продюсер в C# ходит на localhost:19092, CLI — на kfk:9092.

Настройки продюсера: три обязательных пункта

using Confluent.Kafka;                              // клиент Kafka для .NET

const string Bootstrap = "localhost:19092";         // EXTERNAL-листенер: приложение запущено на хосте

static IProducer<string, string> MakeProducer(string txId, bool idempotence = true) =>
    new ProducerBuilder<string, string>(new ProducerConfig
    {
        BootstrapServers = Bootstrap,               // адрес брокера
        TransactionalId = txId,                     // включает транзакционный продюсер
        EnableIdempotence = idempotence,            // для транзакций обязателен
        Acks = Acks.All                             // ждём подтверждения всех синхронных реплик
    }).Build();

Разбор. TransactionalId — не «настройка на всякий случай», а ключ состояния транзакции на брокере: под этим именем в служебном топике __transaction_state хранится, какой продюсер (producerId + epoch) сейчас владеет правом писать. Имя должно быть стабильным между рестартами сервиса — тогда новая инкарнация «фенсит» старую и двух живых писателей не будет (сценарий E). EnableIdempotence=true — фундамент: транзакция добавляет к идемпотентной отправке двухфазный коммит. Acks.All — без подтверждения всех синхронных реплик CommitTransaction не может обещать, что данные переживут падение лидера.

Без идемпотентности транзакции не включаются

Клиент не «тихо отключит» одно ради другого — он упадёт на InitTransactions (проверено, сценарий D):

InvalidOperationException: `transactional.id` requires `enable.idempotence=true`

Сообщение точное: искать причину в коде не придётся.

Сценарий A: закоммиченная транзакция

// A) закоммиченная транзакция
using (var p = MakeProducer("tx-1"))                 // transactional.id = "tx-1"
{
    p.InitTransactions(TimeSpan.FromSeconds(10));   // регистрирует transactional.id на брокере
    p.BeginTransaction();                           // BEGIN: дальше записи идут «внутри транзакции»
    p.Produce("tx-in", new Message<string, string> { Key = "k1", Value = "committed-1" });
    p.Produce("tx-in", new Message<string, string> { Key = "k2", Value = "committed-2" });
    p.CommitTransaction(TimeSpan.FromSeconds(10));  // COMMIT: записи становятся видимыми
}
Console.WriteLine($"A) read_committed={Count("tx-in", IsolationLevel.ReadCommitted, "g-rc-a")}, " +
                  $"read_uncommitted={Count("tx-in", IsolationLevel.ReadUncommitted, "g-ru-a")}");

Разбор построчно.

  • MakeProducer("tx-1") — продюсер с TransactionalId=tx-1; до InitTransactions он ещё не имеет права писать в транзакции.
  • InitTransactions(10 c) — регистрация у координатора транзакций: брокер выдаёт producerId и epoch и закрывает старые эпохи с тем же id. Таймаут — сколько ждать ответа.
  • BeginTransaction() — локальный BEGIN. Записи уходят на брокер сразу и получают оффсеты, но читатели с read_committed их пока не видят.
  • Produce(...) — две записи в одну партицию: брокер запоминает их batch как часть транзакции (флаг isTransactional в сыром логе, см. ниже).
  • CommitTransaction(10 c) — двухфазный коммит: клиент просит координатора завершить транзакцию, координатор пишет COMMIT-маркер во все затронутые партиции. Только после маркера записи видны read_committed-потребителям.

Как считаются записи — вспомогательная функция, ею пользуются все сценарии:

static int Count(string topic, IsolationLevel level, string group)
{
    using var c = new ConsumerBuilder<string, string>(new ConsumerConfig
    {
        BootstrapServers = Bootstrap,               // адрес брокера
        GroupId = group,                            // своя группа на каждый замер, чтобы не мешать другим
        AutoOffsetReset = AutoOffsetReset.Earliest, // если оффсета нет — читать с начала
        EnableAutoCommit = false,                   // коммиты не нужны: только считаем
        IsolationLevel = level                      // ReadCommitted / ReadUncommitted
    }).Build();

    c.Assign(new TopicPartitionOffset(topic, 0, Offset.Beginning));  // партиция 0 с начала, без ребаланса
    var n = 0;
    var deadline = DateTime.UtcNow.AddSeconds(2);   // «тишина» 2 с = данные кончились
    while (DateTime.UtcNow < deadline)
    {
        var r = c.Consume(300);                     // ждём запись максимум 300 мс
        if (r is null) continue;                    // пока тихо — просто ждём
        n++;                                        // запись пришла — считаем
        deadline = DateTime.UtcNow.AddSeconds(2);   // и продлеваем окно тишины
    }
    return n;
}

Разбор. Assign вместо Subscribe — чтобы не ждать ребаланса: партиция одна, распределять нечего. IsolationLevel — то самое единственное отличие двух замеров. Критерий остановки «2 секунды тишины» вместо «до конца партиции»: конец партиции узнать нельзя, а ждать вечно в учебном примере незачем.

Сценарий B: отменённая транзакция

// B) отменённая транзакция
using (var p = MakeProducer("tx-1"))                 // тот же transactional.id, новая инкарнация
{
    p.InitTransactions(TimeSpan.FromSeconds(10));
    p.BeginTransaction();
    p.Produce("tx-in", new Message<string, string> { Key = "k3", Value = "aborted-1" });
    p.Produce("tx-in", new Message<string, string> { Key = "k4", Value = "aborted-2" });
    p.Flush(TimeSpan.FromSeconds(5));               // отправить записи (иначе abort их выбросит)
    p.AbortTransaction(TimeSpan.FromSeconds(10));   // ROLLBACK: записи останутся в логе, но скрыты
}
Console.WriteLine($"B) read_committed={Count("tx-in", IsolationLevel.ReadCommitted, "g-rc-b")}, " +
                  $"read_uncommitted={Count("tx-in", IsolationLevel.ReadUncommitted, "g-ru-b")}");

Разбор. Flush перед AbortTransaction — не формальность: если отменить транзакцию, пока записи ещё в очереди клиента, они вообще не долетят до брокера, и проверять фильтрацию будет не на чем. В первом прогоне без Flush и read_committed, и read_uncommitted показали ровно 2 — отменённых записей в логе просто не было.

AbortTransaction ничего не удаляет: брокер дописывает в партицию управляющий ABORT-маркер, а записи транзакции остаются в логе до истечения retention. Фильтрация — работа потребителя.

A) read_committed=2, read_uncommitted=2
B) read_committed=2, read_uncommitted=4
C) обработано 2, в tx-out=2
C) закоммиченный offset группы eos-group: 2
D) без идемпотентности: InvalidOperationException: `transactional.id` requires `enable.idempotence=true`
E) старый продюсер: KafkaException: Failed to add partitions to transaction: Local: This instance has been fenced by a newer instance

Читаем результат: после A видно 2 записи при любом уровне изоляции; после B read_committed по-прежнему 2 (отменённые скрыты), а read_uncommitted — 4 (видит всё, что физически лежит в логе). То же самое из консольной утилиты — с ключом --isolation-level:

# kafka-console-consumer.sh — читает топик и печатает значения в stdout
# --bootstrap-server kfk:9092 — адрес брокера (изнутри контейнера это INTERNAL-листенер)
# --topic tx-in --from-beginning — читать партицию с самого начала
# --isolation-level read_committed — не показывать записи отменённых и незавершённых транзакций
# --timeout-ms 5000 — выйти, если 5 секунд нет новых данных (иначе утилита ждёт вечно)
docker exec kfk /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server kfk:9092 \
  --topic tx-in --from-beginning --isolation-level read_committed --timeout-ms 5000
# committed-1
# committed-2                                  ← всего 2 строки

# то же, но --isolation-level read_uncommitted — показывать всё, включая отменённое
docker exec kfk /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server kfk:9092 \
  --topic tx-in --from-beginning --isolation-level read_uncommitted --timeout-ms 5000
# committed-1
# committed-2
# aborted-1
# aborted-2                                    ← уже 4 строки
Изоляция — на стороне потребителя

read_committed — настройка читателя (IsolationLevel в ConsumerConfig, --isolation-level в CLI). Продюсер ничего не «прячет»: записи отменённой транзакции лежат в логе и доступны каждому, кто читает с read_uncommitted — а это значение по умолчанию в Kafka. Поэтому в EOS-системе уровень изоляции задаётся у каждого потребителя, а не «где-то в кластере».

Что на самом деле лежит в партиции

Слова «маркер» и «скрыто» легко принять на веру — посмотрим на байты. Утилита kafka-dump-log.sh читает файл сегмента партиции напрямую:

# kafka-dump-log.sh — разбирает файлы сегментов партиции и печатает batch'и
# --files …00000000000000000000.log — первый сегмент партиции (начинается с оффсета 0)
# --print-data-log — дополнительно показать содержимое записей (payload)
# /tmp/kafka-logs/tx-in-0 — каталог партиции 0 топика tx-in в образе apache/kafka
docker exec kfk /opt/kafka/bin/kafka-dump-log.sh \
  --files /tmp/kafka-logs/tx-in-0/00000000000000000000.log --print-data-log
# сокращено: оставлены только ключевые поля batch'ей
baseOffset: 0 lastOffset: 1 count: 2 baseSequence: 0 lastSequence: 1 producerId: 0 producerEpoch: 16
  isTransactional: true isControl: false
| offset: 0 ... key: k1 payload: committed-1
| offset: 1 ... key: k2 payload: committed-2
baseOffset: 2 lastOffset: 2 count: 1 baseSequence: -1 lastSequence: -1 producerId: 0 producerEpoch: 16
  isTransactional: true isControl: true
| offset: 2 ... endTxnMarker: COMMIT coordinatorEpoch: 2
baseOffset: 3 lastOffset: 4 count: 2 baseSequence: 0 lastSequence: 1 producerId: 0 producerEpoch: 17
  isTransactional: true isControl: false
| offset: 3 ... key: k3 payload: aborted-1
| offset: 4 ... key: k4 payload: aborted-2
baseOffset: 5 lastOffset: 5 count: 1 baseSequence: -1 lastSequence: -1 producerId: 0 producerEpoch: 17
  isTransactional: true isControl: true
| offset: 5 ... endTxnMarker: ABORT coordinatorEpoch: 2

Разбор полей.

  • baseOffset: 0 lastOffset: 1 count: 2 — один batch с двумя записями: оффсеты 0 и 1. Оффсет выдаётся записи, а не batch'у.
  • producerId: 0 producerEpoch: 16 — кто писал. producerId — номер, выданный при первом InitTransactions; producerEpoch растёт на каждом новом InitTransactions (у сценария B уже 17) и защищает от «зомби-продюсера».
  • baseSequence: 0 lastSequence: 1 — сквозные номера записей идемпотентного продюсера. Именно по ним брокер отбрасывает повторную отправку того же batch'а.
  • isTransactional: true — batch принадлежит транзакции; isControl: true — это не данные, а управляющая запись.
  • endTxnMarker: COMMIT … coordinatorEpoch: 2 — тот самый маркер: он занимает свой оффсет (2) и не содержит payload. Маркер ABORT для второй транзакции — оффсет 5.
  • Итог по партиции: оффсеты 0–5, следующий свободный — 6. Отсюда LOG-END-OFFSET = 6, хотя полезных записей всего 2 — эту цифру мы увидим в kafka-consumer-groups и разберём ниже.

Отменённые записи (aborted-1, aborted-2) физически лежат в логе рядом с закоммиченными. Потребитель с read_committed их пропускает, read_uncommitted — отдаёт как обычные.

Сценарий C: read-process-write одной транзакцией

Ради этого всё и делается: прочитать событие, записать результат в другой топик и сдвинуть оффсет — атомарно.

// C) read-process-write: чтение, запись в другой топик и коммит оффсета — одной транзакцией
using (var p = MakeProducer("tx-eos"))              // свой transactional.id для этого обработчика
using (var c = new ConsumerBuilder<string, string>(new ConsumerConfig
{
    BootstrapServers = Bootstrap,
    GroupId = "eos-group",                          // группа, чей оффсет будет коммититься
    AutoOffsetReset = AutoOffsetReset.Earliest,     // с начала, если оффсета нет
    EnableAutoCommit = false,                       // автокоммит запрещён: он ломает атомарность
    IsolationLevel = IsolationLevel.ReadCommitted    // не читать чужие незавершённые транзакции
}).Build())
{
    p.InitTransactions(TimeSpan.FromSeconds(10));   // один раз на жизнь продюсера
    c.Assign(new TopicPartitionOffset("tx-in", 0, Offset.Beginning));  // партиция 0 с начала
    p.BeginTransaction();                           // BEGIN
    var processed = 0;
    TopicPartitionOffset? last = null;              // последняя обработанная запись
    var idleUntil = DateTime.UtcNow.AddSeconds(3);  // окно ожидания данных
    while (DateTime.UtcNow < idleUntil)
    {
        var r = c.Consume(300);                     // читаем с таймаутом
        if (r is null) continue;                    // данных нет — ждём дальше
        p.Produce("tx-out", new Message<string, string>   // результат — в другой топик,
            { Key = r.Message.Key, Value = "out:" + r.Message.Value });  // в этой же транзакции
        last = r.TopicPartitionOffset;              // запоминаем оффсет записи
        processed++;                                // счётчик для отчёта
        idleUntil = DateTime.UtcNow.AddSeconds(3);  // продлеваем окно
    }
    // оффсет потребителя добавляется в ТУ ЖЕ транзакцию, что и записи в tx-out
    p.SendOffsetsToTransaction(
        new[] { new TopicPartitionOffset(last!.TopicPartition, last.Offset + 1) },  // оффсет последней + 1
        c.ConsumerGroupMetadata,      // поколение группы: защита от коммита «уже не нашим» членом
        TimeSpan.FromSeconds(10));
    p.CommitTransaction(TimeSpan.FromSeconds(10));  // одна точка фиксации на всё
    Console.WriteLine($"C) обработано {processed}, в tx-out={Count("tx-out", IsolationLevel.ReadCommitted, "g-out-c")}");

    var committed = c.Committed(new[] { new TopicPartition("tx-in", 0) }, TimeSpan.FromSeconds(5));
    Console.WriteLine($"C) закоммиченный offset группы eos-group: {committed[0].Offset}");
}

Разбор построчно.

  • EnableAutoCommit = false — обязательное условие: автокоммит идёт отдельным запросом к координатору группы, вне транзакции, и вся атомарность рассыпается.
  • Produce("tx-out", …) — запись в другую партицию, но в рамках текущей транзакции. Именно поэтому нужен TransactionalId: обе партиции связаны через координатора.
  • last = r.TopicPartitionOffset — запоминаем оффсет каждой записи, а не считаем «сколько обработано»: в логе есть отменённые записи и маркеры, поэтому количество записей и оффсет — разные числа.
  • last.Offset + 1 — коммитится следующий оффсет, т. е. «с какой записи продолжить». Для записи с оффсетом 1 это 2.
  • SendOffsetsToTransaction(offsets, ConsumerGroupMetadata, timeout) — не коммит, а добавление оффсета в транзакцию: брокер запишет его только вместе с COMMIT-маркером.
  • ConsumerGroupMetadata — поколение (generation) группы и её memberId. Если между чтением и коммитом прошёл ребаланс, брокер отклонит коммит — «угнать» партиции у нового члена не получится.
  • CommitTransaction — единственная точка фиксации: до неё не видны ни записи в tx-out, ни новый оффсет; после — видны оба.

Результат: обработано 2, в tx-out=2, закоммиченный оффсет группы — 2. Сбой в любой момент до CommitTransaction означает, что ни результата, ни сдвига оффсета не будет; повторная обработка начнётся с прежнего места, и дубля в tx-out не появится.

Почему lag EOS-группы не станет нулём

# kafka-consumer-groups.sh — утилита работы с группами потребителей
# --describe --group eos-group — показать оффсеты и lag конкретной группы
# --bootstrap-server kfk:9092 — адрес брокера
docker exec kfk /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server kfk:9092 \
  --describe --group eos-group
# GROUP      TOPIC  PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG
# eos-group  tx-in  0          2               6               4

Разбор. CURRENT-OFFSET 2 — закоммиченный оффсет: следующий раз группа начнёт с записи №2. LOG-END-OFFSET 6 — конец журнала: 2 записи + COMMIT-маркер + 2 отменённые записи + ABORT-маркер (ровно то, что мы видели в dump-log). LAG = 6 − 2 = 4.

При этом группа не отстала: все закоммиченные записи обработаны. Lag считает оффсеты, а не полезные сообщения, поэтому в топиках с отменёнными транзакциями остаток «висит» навсегда. Для read_committed-потребителя реальное отставание — это расстояние до LSO (last stable offset — оффсет, до которого все транзакции завершены), а не до конца журнала.

Алерт «lag > 0» на EOS-топике будет ложно срабатывать

Порог для lag имеет смысл только с поправкой на отменённые транзакции и контрольные записи: сравнивайте с LSO, а не с LOG-END-OFFSET, либо задавайте допуск. Иначе дежурный получает вечный «лаг 4» при полностью обработанном топике.

Состояние транзакций у координатора

# kafka-transactions.sh — утилита координатора транзакций
# --bootstrap-server kfk:9092 — адрес брокера
# list — перечислить известные transactional.id и их состояние
docker exec kfk /opt/kafka/bin/kafka-transactions.sh --bootstrap-server kfk:9092 list
# TransactionalId  Coordinator  ProducerId  TransactionState
# tx-1             1            0           CompleteAbort
# tx-fence         1            1000        Empty
# tx-eos           1            1           CompleteCommit

Разбор. Coordinator 1 — номер брокера-координатора (в стенде он один). Состояния: Empty — открытой транзакции нет; CompleteCommit — последняя транзакция закоммичена; CompleteAbort — отменена. tx-1 в CompleteAbort, потому что сценарий B был последним, кто им пользовался, а tx-eos — CompleteCommit после сценария C.

Обратите внимание на ProducerId 1000 у tx-fence: это уже второе поколение продюсера с тем же именем — как раз результат вытеснения из следующего сценария.

Сценарий E: fencing — второй продюсер вытесняет первый

Самая частая авария в проде — «зомби»: старый под завис на долгом GC, оркестратор поднял новый, а старый очнулся и продолжил писать. Kafka закрывает это на уровне протокола.

// E) fencing: второй продюсер с тем же transactional.id вытесняет первый
try
{
    using var p1 = MakeProducer("tx-fence");        // первая инкарнация
    p1.InitTransactions(TimeSpan.FromSeconds(10));  // получает producerId + epoch

    using var p2 = MakeProducer("tx-fence");        // тот же transactional.id
    p2.InitTransactions(TimeSpan.FromSeconds(10));  // брокер увеличивает epoch — p1 больше не владелец

    p1.BeginTransaction();                          // p1 пытается работать дальше
    p1.Produce("tx-in", new Message<string, string> { Key = "k5", Value = "zombie" });
    p1.CommitTransaction(TimeSpan.FromSeconds(10)); // здесь и выясняется, кто настоящий
    Console.WriteLine("E) старый продюсер смог закоммитить (неожидано)");
}
catch (Exception ex)
{
    Console.WriteLine($"E) старый продюсер: {ex.GetType().Name}: {ex.Message}");
}

Результат:

E) старый продюсер: KafkaException: Failed to add partitions to transaction: Local: This instance has been fenced by a newer instance

Разбор. InitTransactions второго продюсера увеличил epoch; первая инкарнация об этом не знает и получает отказ на первой же попытке что-то сделать в транзакции. Записи «зомби» в лог не попадут — даже если он успел их отправить. Отсюда практическое правило: TransactionalId должен быть стабильным и уникальным на обработчик (например, orders-enricher), а не случайным при каждом запуске. Случайный id означает, что после рестарта старый и новый продюсеры живут одновременно и оба считаются легальными.

Где exactly-once заканчивается

Транзакция Kafka покрывает только Kafka: записи в партиции и оффсеты потребителя. Всё, что обработчик сделал «наружу», в транзакцию не входит.

  • Внешние эффекты не откатываются. Если внутри транзакции вы вызвали платёжный API и затем сделали AbortTransaction, платёж останется. Для БД — идемпотентный приёмник (INSERT … ON CONFLICT, уникальный ключ события) или outbox-таблица, которую читает отдельный продюсер.
  • Все потребители должны читать с read_committed. Один потребитель с уровнем по умолчанию (read_uncommitted) увидит отменённые записи, и «ровно один раз» превратится в «иногда лишние».
  • Открытая транзакция задерживает читателей. read_committed-потребитель не увидит записи за LSO, пока транзакция не завершена. Долгая транзакция = рост задержки у всех ниже по потоку.
  • Таймауты. transaction.timeout.ms (по умолчанию 60 с) — сколько координатор ждёт завершения, после чего прерывает транзакцию. Обработка дольше этого порога (или дольше max.poll.interval.ms) — и CommitTransaction упадёт; размер порции надо подбирать под время обработки.
  • Один продюсер = одна транзакция за раз. Транзакции на одном IProducer не параллелятся: для параллельной обработки — несколько продюсеров с разными TransactionalId.
  • Эксплуатация. В проде __transaction_state должен иметь replication factor 3 и min.insync.replicas=2: потеря координатора иначе означает «зависшие» транзакции. В стенде выше стоит 1 — только потому что брокер один.
ГарантияКак получаетсяЦена
at-most-onceкоммит оффсета до обработки (или автокоммит) при сбое событие теряется
at-least-onceобработка, затем коммит; продюсер с ретраями дубли при сбое между обработкой и коммитом
exactly-once внутри KafkaTransactionalId + SendOffsetsToTransaction + read_committed round-trip к координатору, задержка до LSO, дисциплина у потребителей
exactly-once наружуидемпотентность на стороне приёмника или outbox своя логика дедупликации
★ Что запомнить
  • Транзакция склеивает запись в партиции и коммит оффсета: до CommitTransaction не видно ни того, ни другого.
  • Три обязательных настройки: TransactionalId, EnableIdempotence=true, Acks.All. Без идемпотентности — InvalidOperationException: `transactional.id` requires `enable.idempotence=true`.
  • AbortTransaction не удаляет данные: в партиции остаются записи и ABORT-маркер (endTxnMarker: ABORT). read_committed = 2 записи, read_uncommitted = 4 — проверено.
  • Маркер COMMIT/ABORT занимает собственный оффсет, поэтому LOG-END-OFFSET 6 при двух полезных записях, а lag EOS-группы навсегда равен 4. Сравнивайте с LSO, а не с концом журнала.
  • Коммитить оффсет — только через SendOffsetsToTransaction(last.Offset + 1, ConsumerGroupMetadata), при EnableAutoCommit=false.
  • Одинаковый TransactionalId у двух живых продюсеров — второй вытесняет первого: This instance has been fenced by a newer instance. Имя должно быть стабильным между рестартами.
  • Внешние эффекты (БД, HTTP) транзакция не откатывает: нужна идемпотентность или outbox.
