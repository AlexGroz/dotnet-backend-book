Глава 7. Цепочка обязанностей: как устроен конвейер ASP.NET Core

Последовательность обработчиков, где каждый решает: обработать самому, прервать или передать дальше. Именно так работает каждый запрос в ASP.NET Core.

основная глава

Разминка: идея на десяти строках

Проверки идут по очереди, и каждая может остановить следующие. Цепочка — это «следующий» внутри каждого звена.

abstract class Check
{
    private Check? _next;
    public Check Next(Check next) { _next = next; return next; }   // связали звенья

    public string? Run(int amount)
    {
        var error = Validate(amount);
        if (error is not null) return error;        // остановились
        return _next?.Run(amount);                  // передали дальше
    }

    protected abstract string? Validate(int amount);
}

sealed class Positive : Check { protected override string? Validate(int a) => a <= 0 ? "сумма ≤ 0" : null; }
sealed class Limit    : Check { protected override string? Validate(int a) => a > 1000 ? "больше лимита" : null; }

var chain = new Positive();
chain.Next(new Limit());

Console.WriteLine(chain.Run(-5));      // «сумма ≤ 0» — дальше не пошли
Console.WriteLine(chain.Run(5000));    // «больше лимита»
Console.WriteLine(chain.Run(100));     // пусто — все проверки пройдены

Кто кого останавливает

Run(-5)     Positive: «сумма ≤ 0»   → вернули ошибку, Limit НЕ вызывался
Run(5000)   Positive: null (ок)      → Limit: «больше лимита»
Run(100)    Positive: null (ок)      → Limit: null (ок) → _next == null → вернули null

Правило простое: звено вернуло ошибку — цепочка останавливается; вернуло null — управление уходит следующему звену. Последнее звено возвращает null, потому что _next у него нет.

Дальше — конвейер middleware в ASP.NET Core: там ровно эта идея, только звено называется RequestDelegate.

Проблема: один обработчик знает слишком много

Типичный «толстый» обработчик запроса собирает в себе всё сразу:

app.MapPost("/orders", async (HttpContext ctx, CreateOrderDto dto, AppDbContext db) =>
{
    if (!ctx.Request.Headers.TryGetValue("X-Api-Key", out var key) || !IsValid(key))
    {
        ctx.Response.StatusCode = 401; return;             // 1) аутентификация
    }

    if (!ctx.User.IsInRole("manager"))
    {
        ctx.Response.StatusCode = 403; return;             // 2) авторизация
    }

    if (!RateLimiter.TryAcquire(ctx.Connection.Id))
    {
        ctx.Response.StatusCode = 429; return;             // 3) лимит
    }

    if (!Validator.Validate(dto, out var errors))
    {
        ctx.Response.StatusCode = 400;                     // 4) валидация
        await ctx.Response.WriteAsJsonAsync(errors); return;
    }

    // … и только здесь — сама логика заказа
});

С каждым новым требованием (аудит, трейсинг, идемпотентность) этот блок растёт, а бизнес-логика отодвигается всё дальше.

Решение: цепочка, где каждый шаг — отдельный обработчик

Ключевая идея: обработчик получает ссылку на следующий и сам решает, вызывать его или остановиться. Реализация «руками» — это интерфейс и связанный список:

public abstract class OrderCheck
{
    private OrderCheck? _next;
    public OrderCheck SetNext(OrderCheck next) { _next = next; return next; }

    public async Task<CheckResult> HandleAsync(OrderRequest request, CancellationToken ct)
    {
        var result = await CheckAsync(request, ct);
        if (!result.Passed) return result;                  // прервали цепочку
        return _next is null
            ? CheckResult.Ok()
            : await _next.HandleAsync(request, ct);         // передали дальше
    }

    protected abstract Task<CheckResult> CheckAsync(OrderRequest request, CancellationToken ct);
}

// Звенья цепочки: каждое проверяет ровно одно
public sealed class LimitCheck(decimal max) : OrderCheck
{
    protected override Task<CheckResult> CheckAsync(OrderRequest r, CancellationToken ct) =>
        Task.FromResult(r.Sum <= max ? CheckResult.Ok() : CheckResult.Fail("Сумма превышает лимит"));
}

public sealed class FraudCheck(IFraudService fraud) : OrderCheck
{
    protected override async Task<CheckResult> CheckAsync(OrderRequest r, CancellationToken ct) =>
        await fraud.IsSuspiciousAsync(r, ct) ? CheckResult.Fail("Подозрительная операция") : CheckResult.Ok();
}

Program.cs — отдельное место сборки («композиционный корень»)

// 1) создаём звенья — по одному на проверку
var limit     = new LimitCheck(1_000_000m);    // сумма ≤ 1 млн
var fraud     = new FraudCheck(fraudService);  // нет ли признаков мошенничества
var duplicate = new DuplicateCheck(db);        // не было ли такого заказа раньше

// 2) связываем в цепочку: limit → fraud → duplicate → конец
limit.SetNext(fraud).SetNext(duplicate);

// 3) запускаем с первого звена
var result = await limit.HandleAsync(request, ct);
Почему сборка — отдельный блок

Классы-звенья (LimitCheck, FraudCheck) — это определения, каждое в своём файле. А строки выше — сборка: место, где приложение решает, из каких звеньев и в каком порядке составить цепочку. Такое место называют композиционным корнем — обычно это Program.cs или фабрика обработчика. Так же устроен и DI: классы отдельно, регистрации отдельно («Backend на .NET», глава 15).

Что происходит при вызове HandleAsync

limit.HandleAsync(request)
 └─ LimitCheck: сумма > 1 000 000?   ── да ──► «Сумма превышает лимит», дальше НЕ идём
                                    └─ нет ─► идём дальше
      └─ FraudCheck: подозрительно?  ── да ──► «Подозрительная операция»
                                    └─ нет ─► идём дальше
           └─ DuplicateCheck: уже есть? ──► вернули результат
                └─ _next == null ──► цепочка закончилась

Теперь новый шаг — это новый класс и одна строка сборки. Порядок проверок виден явно, каждую можно протестировать отдельно.

Главный пример: конвейер ASP.NET Core

Middleware — это та же цепочка, только звено называется RequestDelegate и получает HttpContext. Каждый компонент может выполнить свою часть, вызвать следующий и не вызывать его, если решил остановить запрос.

public sealed class CorrelationIdMiddleware(RequestDelegate next)
{
    public async Task InvokeAsync(HttpContext context)
    {
        var id = context.Request.Headers.TryGetValue("X-Correlation-Id", out var value)
            ? value.ToString()
            : Guid.NewGuid().ToString();

        context.Items["CorrelationId"] = id;
        context.Response.Headers["X-Correlation-Id"] = id;

        await next(context);            // передали следующему звену
    }
}

// регистрация — цепочка строится порядком строк
app.UseMiddleware<CorrelationIdMiddleware>();
app.UseAuthentication();
app.UseAuthorization();
app.UseRateLimiter();
app.MapGet("/orders/{id:int}", …);
Порядок — часть логики

Обработка ошибок должна стоять раньше остальных звеньев, иначе исключения из следующих компонентов она не увидит. Аутентификация — до авторизации. Это ровно то же свойство цепочки, что в «ручной» реализации: кто раньше — тот и decides, кому передавать запрос.

Чем цепочка отличается от декоратора

Структура похожа (обёртки), но смысл разный — это классический вопрос на интервью.

ДекораторЦепочка обязанностей
Главная идеяДобавить поведение к одному объектуВыбрать, кто обработает, и остановить при необходимости
Передача дальшеКак правило, всегда вызывает вложенный объектМожет не вызывать — это и есть «прерывание»
Кто «главный»Внешний код работает с последним слоемНикто не гарантирует, что запрос дойдёт до конца
ПримерКэш поверх репозиторияПроверки заказа, middleware
Статистика: насколько часто

Оценка: ~70 % проектов и ~20 % от всех применений паттернов.

  • Факт: в любом приложении ASP.NET Core есть конвейер middleware — то есть цепочка обязанностей используется в 100 % веб-приложений, даже если разработчик её не писал.
  • Почему оценка проектов ниже 100 %: в консольных утилитах, фоновых воркерах и библиотеках конвейера нет; там паттерн встречается только если его написали осознанно.
  • Оговорка: оценка пропорции, а не измерение (глава 1).

Когда цепочка не нужна

  • Шагов два-три и они не меняются: обычный последовательный код читается лучше.
  • Шаги обязаны выполниться все: это не цепочка обязанностей, а набор действий — например, `foreach` по обработчикам или события.
  • Критичен порядок и он неочевиден: цепочка, собранная в случайном порядке в DI, — источник трудноуловимых ошибок. Порядок должен быть виден в одном месте.
★ Что запомнить из главы
  • Цепочка обязанностей — последовательность обработчиков, каждый решает: обработать, прервать или передать дальше.
  • Middleware ASP.NET Core — это и есть цепочка; порядок регистрации = порядок выполнения.
  • Отличие от декоратора: декоратор добавляет поведение, цепочка выбирает обработчика и может остановить запрос.
  • Плюсы: каждый шаг отдельно тестируется, новый шаг не меняет существующие.
  • Оценка: ~70 % проектов, ~20 % от всех использований паттернов (в веб-приложениях — фактически 100 %).
