Глава 7. Аллокации на практике: строки, коллекции, пулы

Зная, что под нагрузкой дорог не объём памяти, а скорость создания объектов, посмотрим, как сократить мусор конкретными приёмами.

Упаковка (boxing)

Упаковка — это превращение значимого типа в объект в куче. Часто она «невидима».

// ✘ ArrayList упаковывает каждый int в объект → мусор
var list = new ArrayList();
list.Add(42);

// ✔ generic-коллекция: int хранится как int, без упаковки
var list2 = new List<int>();
list2.Add(42);

Похожая ловушка — сравнение структур через обычный Equals: упаковка происходит, если у типа нет IEquatable<T>. Поэтому значимые типы стоит делать readonly struct с реализацией IEquatable<T>.

Строки

Строки неизменяемы: каждая операция «изменения» создаёт новую строку. В цикле это превращается в лавину мусора.

// ✘ строка на каждой итерации
string s = "";
for (int i = 0; i < 1000; i++) s += i + ",";

// ✔ один буфер → одна итоговая строка
var sb = new StringBuilder(4096);
for (int i = 0; i < 1000; i++) sb.Append(i).Append(',');
string result = sb.ToString();
Почему StringBuilder быстрее

Не потому, что «строки лежат в стеке»: string — ссылочный тип, объект живёт в куче, а в переменной лишь ссылка. Причина в другом: StringBuilder меняет свой буфер — O(n) вместо O(n²) копирований. Пул интернированных литералов и остальные детали — «C#: язык и типы», глава 2.

Коллекции

  • Задавайте начальную ёмкость, если знаете размер: new List<T>(count) — меньше промежуточных расширений и копирований.
  • Предпочитайте generic-коллекции не-generic (нет упаковки, нет приведения типов) — подробный разбор в «C#: язык и типы», глава 5.
  • Не создавайте копии без нужды: лишний ToList() — это новый список.

Пулы (pools): переиспользование вместо создания

Пул — это «склад заранее созданных объектов». Вместо того чтобы каждый раз создавать новый объект (и потом выбрасывать его), объект берут из пула, используют и возвращают обратно. Так аллокаций становится сильно меньше.

Особенно это важно для крупных буферов: массивы от ~85 КБ попадают в LOH и дороги для GC (глава 6).

ArrayPool: переиспользование буферов-массивов

// Shared — встроенный ОБЩИЙ пул .NET (им пользуется всё приложение).
// Свой создавать не нужно — достаточно взять этот.
var pool = ArrayPool<byte>.Shared;

// Rent = «арендовать» массив у пула (минимум 4096 байт).
byte[] buffer = pool.Rent(4096);

try
{
    // Работаем не со всем массивом, а с его частью (0..4096)
    int read = await stream.ReadAsync(buffer.AsMemory(0, 4096), ct);
    Process(buffer.AsSpan(0, read));
}
finally
{
    pool.Return(buffer);   // вернуть массив в пул — обязательно
}
Пояснения к примеру
  • ArrayPool<byte>.Shared — «общий» пул, встроенный в .NET. Готовый и потокобезопасный, разделяемый всем приложением: не нужно создавать свой.
  • Rent(4096) — «арендовать» буфер размером минимум 4096 байт. Пул хранит память «корзинами» (8192, 16384, …), поэтому реально массив может оказаться больше запрошенного. Именно поэтому дальше мы работаем не со всем массивом, а с его частью — AsMemory(0, 4096).
  • Return(buffer) — вернуть массив в пул. Если не вернуть, пул начнёт создавать новые массивы, и весь смысл потеряется. Поэтому Return — в finally.
  • ct — это CancellationToken, «токен отмены». Важно: ct — просто имя параметра, так принято сокращать; это не ключевое слово и не «магическая» переменная. Токен приходит в метод параметром — его создаёт и передаёт вызывающий код (в ASP.NET Core это делает фреймворк на каждый запрос), а имя может быть любым: 
    // токен объявлен в параметрах метода — сюда его передаёт вызывающий
public async Task ProcessAsync(int id, CancellationToken ct)
{
    int read = await stream.ReadAsync(buffer.AsMemory(0, 4096), ct);
}

// если переименовать параметр, работать будет точно так же
public async Task ProcessAsync(int id, CancellationToken token)
{
    int read = await stream.ReadAsync(buffer.AsMemory(0, 4096), token);
}
    Зачем он нужен: если клиент отключился или истёк таймаут, операция прервётся и не будет зря занимать ресурсы. Подробнее — в главе 12.

Для дорогих в создании объектов (например, StringBuilder) есть ObjectPool<T> из пакета Microsoft.Extensions.ObjectPool — принцип тот же: взять, использовать, вернуть.

Span<T>: работать с памятью без аллокаций

Проблема, которую он решает

Обычные операции со строками и массивами создают новые объекты. Разрезали строку — получили массив новых строк; взяли её часть — получили ещё одну новую строку. На горячем пути это мусор для сборщика (глава 6).

string line = "10,20,30";

string[] parts = line.Split(',');     // аллокация массива + три новые строки
string sub = line.Substring(0, 2);    // ещё одна новая строка («10»)

Идея Span

Span<T> — это «окно» в уже существующую память: он не копирует данные, а только указывает на их часть. Взяли подстроку через Span — новой строки не появилось.

string line = "10,20,30";

ReadOnlySpan<char> span  = line.AsSpan();      // окно на всю строку — без копии
ReadOnlySpan<char> first = span.Slice(0, 2);   // окно на «10» — тоже без копии

// пройти по данным и посчитать запятые: ни одной аллокации
int commas = 0;
foreach (char c in span)
    if (c == ',') commas++;

Почему это дешевле

Обычный подходЧерез Span
Взятие частиНовый объект (строка или массив) — аллокация«Окно» — без аллокации
Что уходит в GCМусор на каждое обращениеНичего

Правила и границы

  • Span<T> — это ref struct: он живёт только на стеке. Его нельзя положить в поле класса, в List<> или «пережить» им await.
  • Точка входа обычно — AsSpan() у строки или массива.
  • ReadOnlySpan<char> — когда данные только читаем (строка всегда даёт такой).
  • Для своей памяти на стеке есть stackalloc (см. эту же главу выше).
Когда это не нужно

Span усложняет код. Держите его для горячих путей — парсинг, обработка протоколов, большие массивы, — и только если профилировщик показал там аллокации (глава 21). В обычном коде string и List<T> понятнее и достаточны.

Исключения — не для управления потоком

Бросок исключения — дорогая операция: создаётся объект исключения (аллокация!) и собирается трассировка стека. Если этим обрабатывать обычные ситуации, платим и временем, и мусором.

Плохо и хорошо — на конкретном примере

// ✘ исключение как «нормальный» ход событий
int ParseBad(string s)
{
    try
    {
        return int.Parse(s);      // на каждой неверной строке бросается FormatException
    }
    catch (FormatException)
    {
        return 0;                 // а это: аллокация объекта + сборка трассировки
    }
}

// ✔ метод-проверка: без исключений и без мусора
int ParseGood(string s)
{
    return int.TryParse(s, out var value) ? value : 0;
}
Правило

Исключения — для исключительных случаев (то, чего «не должно быть»: нет соединения, нарушен инвариант). Для ожидаемых исходов используйте методы-проверки (TryParse, TryGetValue) или обычные условия.

Правило хорошего тона

Всё это — только для горячих путей, и только по результатам измерений (глава 21). Преждевременно усложнять обычный код Span и пулами — вредно: теряется читаемость без заметной выгоды.

★ Что запомнить из главы

Меньше мусора — меньше работы GC. Основные приёмы: не упаковывать (generics, IEquatable), строить строки через StringBuilder, задавать ёмкость коллекций, брать крупные буферы из ArrayPool, работать со Span без копий. И всё это — по замерам.
