Глава 8. Наблюдатель: события, подписки и доменные события

Один объект изменился — об этом должны узнать другие, но он не должен знать, кто именно. Разберём `event` в C#, доменные события и главную ловушку: публикацию до `SaveChanges`.

основная глава

Разминка: идея на пятнадцати строках

Заказ оплачен — надо, чтобы об этом узнали все, кому интересно. Сам заказ не должен знать, кто именно слушает:

public sealed class Order
{
    public decimal Total { get; init; }

    // Событие: «кто хочет — подпишись». Тип EventHandler<decimal> значит
    // «обработчик получает отправителя и число (сумму)».
    public event EventHandler<decimal>? Paid;

    public void Pay()
    {
        // … тут списание денег …
        Paid?.Invoke(this, Total);   // ?. — если подписчиков нет, ничего не падает
    }
}
var order = new Order { Total = 1500m };

order.Paid += (sender, total) => Console.WriteLine($"[письмо] оплачен заказ на {total}");
order.Paid += (sender, total) => Console.WriteLine($"[склад] зарезервировать товары");
order.Paid += (sender, total) => Console.WriteLine($"[аналитика] +1 оплата");

order.Pay();

Что окажется на консоли

[письмо] оплачен заказ на 1500
[склад] зарезервировать товары
[аналитика] +1 оплата

Что произошло по сути: Order сообщил «я оплачен» и не знает, кто на это отреагировал. Добавить нового слушателя — это одна строка +=, а класс заказа при этом не меняется. Это и есть наблюдатель (Observer): «издатель» и любое число «подписчиков».

Чем event отличается от обычного делегата

Поле-делегат можно вызвать откуда угодно и присвоить целиком (handler = other), а event разрешает снаружи только += и -=. Вызвать (Invoke) может лишь сам класс-издатель. Это и есть инкапсуляция подписки: снаружи нельзя «перезаписать» всех слушателей или дёрнуть событие в обход владельца.

Проблема в реальном проекте

Сначала — как это выглядит, когда паттерна нет. Метод оплаты в сервисе заказов:

public async Task PayAsync(Guid orderId)
{
    var order = await _db.Orders.FindAsync(orderId);
    order.Status = OrderStatus.Paid;
    await _db.SaveChangesAsync();          // 1) сохранили заказ

    await _email.SendReceiptAsync(order);  // 2) письмо клиенту
    await _stock.ReserveAsync(order);      // 3) резерв на складе
    await _analytics.TrackAsync(order);    // 4) событие в аналитику
    await _bonus.AccrueAsync(order);       // 5) бонусы
}

Чем это плохо — по пунктам, а не «так не принято»:

  • Связанность. Сервис заказов знает про письма, склад, аналитику и бонусы. Смена почтового провайдера трогает код оплаты.
  • Каждая новая реакция — правка метода. «Ещё нужно пушить в 1С» → меняем PayAsync и все его тесты.
  • Ошибка одного шага ломает остальные. Упало письмо — заказ уже оплачен, но склад не зарезервирован; и наоборот: заказ откатился, а письмо ушло.
  • Тесты. Чтобы проверить оплату, нужно подделать пять зависимостей, хотя сама оплата — это «сменить статус и сохранить».

Решение: заказ объявляет факт («оплачен»), а реакции живут отдельно от него.

Решение: событие + обработчики

// 1) Событие домена — просто «факт, который произошёл». Никакой логики внутри.
public sealed record OrderPaid(Guid OrderId, decimal Total, DateTimeOffset At);

// 2) Контракт обработчика: одна реакция — один класс.
public interface IOrderPaidHandler
{
    Task HandleAsync(OrderPaid e, CancellationToken ct);
}

// 3) Сервис оплаты больше ничего не знает о подписчиках.
public sealed class OrderService(AppDbContext db, IEnumerable<IOrderPaidHandler> handlers)
{
    public async Task PayAsync(Guid orderId, CancellationToken ct)
    {
        var order = await db.Orders.FindAsync([orderId], ct);
        order!.Status = OrderStatus.Paid;

        await db.SaveChangesAsync(ct);          // СНАЧАЛА фиксируем в базе

        var e = new OrderPaid(order.Id, order.Total, DateTimeOffset.UtcNow);
        foreach (var handler in handlers)       // ПОТОМ сообщаем всем
            await handler.HandleAsync(e, ct);
    }
}
// 4) Реакции — отдельные классы, каждый со своей зависимостью.
public sealed class SendReceiptOnOrderPaid(IEmail email) : IOrderPaidHandler
{
    public Task HandleAsync(OrderPaid e, CancellationToken ct)
        => email.SendReceiptAsync(e.OrderId, e.Total, ct);
}

public sealed class ReserveStockOnOrderPaid(IStock stock) : IOrderPaidHandler
{
    public Task HandleAsync(OrderPaid e, CancellationToken ct)
        => stock.ReserveAsync(e.OrderId, ct);
}

// 5) Регистрация: порядок вызовов = порядок регистраций.
builder.Services.AddScoped<IOrderPaidHandler, SendReceiptOnOrderPaid>();
builder.Services.AddScoped<IOrderPaidHandler, ReserveStockOnOrderPaid>();

IEnumerable<IOrderPaidHandler> — это и есть «список подписчиков», который подставляет DI (механика — «Backend на .NET», глава 15). Новый подписчик = новый класс + одна строка регистрации; OrderService не меняется.

Почему в прикладном коде чаще берут интерфейс, а не event

event — синхронный, привязан к конкретному экземпляру и не умеет async, DI и подписку «по соглашению». Список обработчиков за тем же интерфейсом решает это и легко тестируется: в тесте подставляется фейковый обработчик и проверяется, что событие пришло. Именно так устроены INotificationHandler в MediatR и обработчики доменных событий в DDD.

Пять ловушек наблюдателя

ЛовушкаЧто происходитКак не попасть
Публикация до SaveChangesОбработчик прочитал ещё старые данные; транзакция откатилась, а письмо уже ушлоПубликовать после фиксации; для внешних эффектов — Outbox («Backend на .NET», глава 31)
Исключение в обработчикеПадает вся цепочка: остальные реакции не выполнились, запрос вернул 500Выбрать политику: «всё или ничего» (тогда обработчики в одной транзакции) или «каждый сам за себя» (try/catch + лог)
Утечка подписокПодписчик не собирается GC, пока жив издатель Отписываться (-=) в Dispose, слабые ссылки для долгоживущих издателей
Порядок вызовов«Письмо после резерва» не гарантировано Не полагаться на порядок; если зависимость есть — она внутри одного обработчика
Двойная доставкаRetry после ошибки → письмо ушло дважды Идемпотентность: идентификатор события + дедупликация (глава 31)

Утечка — самое частое на практике, потому что выглядит безобидно:

// ✘ подписка на долгоживущий объект: кэш (singleton) держит ссылку на подписчика вечно
_cache.Invalidated += OnInvalidated;

// ✔ подписка оформлена парой с отпиской
public sealed class PriceView : IDisposable
{
    private readonly PriceCache _cache;

    public PriceView(PriceCache cache)
    {
        _cache = cache;
        _cache.Invalidated += OnInvalidated;
    }

    public void Dispose() => _cache.Invalidated -= OnInvalidated;   // без этого — утечка

    private void OnInvalidated(object? sender, EventArgs e) { /* обновить отображение */ }
}

Не путать с соседями

ПаттернСхемаКто решает, что делать
Наблюдательодин → многоКаждый подписчик реагирует сам; издатель не в курсе
Цепочка обязанностей (глава 6)один → следующий → следующий Каждое звено решает, передавать ли дальше
Декоратор (глава 5)обёртка вокруг одногоВызов один, но с дополнительным поведением до/после
★ Что запомнить
  • Наблюдатель — это один ко многим: издатель объявляет факт, подписчики реагируют, издатель их не знает.
  • event — встроенный вариант в C#; снаружи только +=/-=, вызывает только владелец.
  • В прикладном коде чаще берут список обработчиков за интерфейсом: работает с DI, async и тестами.
  • Публикуйте после SaveChanges, а внешние эффекты отправляйте через Outbox — иначе письмо уйдёт об отменённом заказе.
  • Отписывайтесь; исключение в обработчике и двойная доставка — штатные проблемы, у них должны быть правила.
