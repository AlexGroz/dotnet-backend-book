Глава 35. Авторизация: роли, claims, политики и ресурсы

Аутентификация ответила «кто ты». Теперь — «что тебе можно»: от ролей до проверки прав на конкретный объект. Все коды ответов в главе — из запуска minimal API на .NET 8 с JWT.

основная глава

Четыре уровня, и все четыре нужны

УровеньВопросИнструмент
Аутентификациявалиден ли токенUseAuthentication, RequireAuthorization()
Роль / scopeэтот класс пользователей вообще ходит сюдаRequireRole, RequireClaim("scope", …)
Политиканабор условий из claimsAddPolicy, RequireAssertion
Ресурсможно ли этому пользователю этот заказ IAuthorizationService.AuthorizeAsync(user, resource, policy)

Типичная ошибка — остановиться на первом уровне: «эндпоинт закрыт, значит безопасно». Ниже мы на стенде получим 403 на чужой заказ и увидим, почему одной роли user для этого мало.

Роли

app.MapGet("/admin", () => "админка")
   .RequireAuthorization(p => p.RequireRole("admin"));
### A13: /admin с ролью user и с ролью admin
403 200

RequireRole читает claim, указанный в RoleClaimType (в нашем стенде — "role"). Если эту настройку забыть, роли «не работают»: claim лежит в role, а проверка ищет ClaimTypes.Role. Можно требовать несколько ролей сразу — RequireRole("admin", "manager") означает «любая из».

Политика из claims

Как только правило перестаёт быть «одна роль», его выносят в политику. Здесь доступ к отчёту требует одновременно: отдел finance и не гость.

builder.Services.AddAuthorization(o =>
{
    o.AddPolicy("finance", p => p
        .RequireClaim("department", "finance")
        .RequireAssertion(c => !c.User.IsInRole("guest")));
});

app.MapGet("/reports", () => "финансовый отчёт")
   .RequireAuthorization("finance");
### A10: /reports с department=finance
финансовый отчёт  [200]
### A11: /reports без finance
403
### A12: /reports с finance, но роль guest
403

Три вещи, которые показывают эти строки:

  • RequireClaim проверяет наличие claim с нужным значением; список допустимых значений задаётся вторым параметром (RequireClaim("department", "finance", "audit")).
  • RequireAssertion — «запасной выход» для правил, которые не выразить готовыми методами: здесь — запрет для гостя даже при правильном отделе (A12). Это лямбда, поэтому её легко превратить в нечитаемое условие — держите такие проверки маленькими и с именем политики.
  • Отказ политики — это 403, а не 401: пользователь аутентифицирован, ему просто нельзя.

Права на конкретный объект

Самое частое место уязвимостей: /orders/43 доступен любому аутентифицированному пользователю, если проверять только «залогинен ли он». Правильный шаблон — политика, которая получает ресурс:

class OrderOwnerRequirement : IAuthorizationRequirement { }

class OrderOwnerHandler : AuthorizationHandler<OrderOwnerRequirement, Order>
{
    protected override Task HandleRequirementAsync(AuthorizationHandlerContext context,
        OrderOwnerRequirement requirement, Order resource)
    {
        if (context.User.IsInRole("admin") ||
            context.User.FindFirst("sub")?.Value == resource.OwnerSub)
            context.Succeed(requirement);
        return Task.CompletedTask;
    }
}

builder.Services.AddSingleton<IAuthorizationHandler, OrderOwnerHandler>();
builder.Services.AddAuthorization(o =>
    o.AddPolicy("owner-or-admin", p => p.AddRequirements(new OrderOwnerRequirement())));

app.MapGet("/orders/{id:int}", async (int id, ClaimsPrincipal user, IAuthorizationService authz) =>
{
    if (!orders.TryGetValue(id, out var order)) return Results.NotFound();
    var result = await authz.AuthorizeAsync(user, order, "owner-or-admin");
    return result.Succeeded ? Results.Ok(order) : Results.Forbid();
});
### A4: /orders/42 — alice владелец
{"id":42,"amount":1500,"user":"alice"}  [200]
### A5: /orders/43 — alice не владелец
403
### A6: /orders/43 — bob владелец
{"id":43,"amount":900,"user":"bob"}  [200]
### A7: /orders/43 — admin не владелец, но админ
{"id":43,"amount":900,"user":"root"}  [200]
Почему handler, а не if в эндпоинте

Логику «владелец или админ» можно написать прямо в обработчике — и она разъедется по пяти эндпоинтам с разными вариациями. IAuthorizationHandler даёт: одно место правки, тестируемость без HTTP, повторное использование в [Authorize] через IAuthorizationService и явную семантику «политика + ресурс». Регистрировать handler нужно как Singleton (или Scoped, если он ходит в БД), и он не должен бросать исключения — только Succeed/ничего.

403 или 404: не рассказывать лишнего

403 на чужой объект сам по себе — утечка: он подтверждает, что заказ 43 существует (иначе был бы 404). Если существование объекта само по себе чувствительно (медкарта, чужой договор, счёт), принято «маскировать» отказ под 404:

app.MapGet("/orders/{id:int}/masked", async (int id, ClaimsPrincipal user, IAuthorizationService authz) =>
{
    if (!orders.TryGetValue(id, out var order)) return Results.NotFound();
    var result = await authz.AuthorizeAsync(user, order, "owner-or-admin");
    return result.Succeeded ? Results.Ok(order) : Results.NotFound();   // 404 вместо 403
});
### A8: /orders/43/masked — чужой заказ
404
### A9: /orders/99 — не существует
404

Клиент теперь не может отличить «нет такого» от «есть, но не твой». Цена — менее понятные ошибки для поддержки и логи, поэтому решение принимают для каждого ресурса отдельно: для публичного каталога 403 информативнее, для персональных данных — 404.

Безопасно по умолчанию: FallbackPolicy

Забытый RequireAuthorization() на новом эндпоинте — классическая дыра. FallbackPolicy переворачивает логику: всё требует аутентификации, а открытые эндпоинты помечаются явно.

builder.Services.AddAuthorization(o =>
    o.FallbackPolicy = new AuthorizationPolicyBuilder().RequireAuthenticatedUser().Build());

app.MapGet("/public", () => "открытый эндпоинт").AllowAnonymous();
### A1: /public без токена (AllowAnonymous при fallback-политике)
открытый эндпоинт  [200]
### A2: /profile без токена (fallback-политика закрыла всё по умолчанию)
401

На этом же стенде всплыла и обратная сторона: эндпоинт выдачи тестовых токенов /dev/token тоже попал под fallback и отвечал 401 — пока его не пометили AllowAnonymous(). Это ровно то поведение, которое нужно: новое «забытое» API закрыто, а не открыто.

Что ломается чаще всего
  • Проверка прав на клиенте. Скрытая кнопка в React — удобство, не защита: запрос можно отправить curl’ом. Права проверяются на сервере, всегда.
  • IDOR. «Взял id из URL и отдал объект» — ровно A5 выше. Каждый доступ к объекту по идентификатору обязан проверять владельца/арендатора, а не только факт логина.
  • Устаревшие роли в токене. Роль сняли в БД, а в токене она живёт до exp. Либо короткий TTL, либо проверка критичных прав по БД/кэшу на каждый запрос.
  • Права только в контроллере. Внутренний сервис, вызванный из другого места, уже не проходит через атрибут — критичные проверки дублируют в слое приложения.
  • Одна роль «admin» на всё. Она неизбежно выдаётся слишком широко; права лучше дробить по областям (orders.write, reports.finance).

Что выбрать: сравнение подходов

ПодходХорошоПлохоПример
Рольпросто, понятно бизнесу, есть в токенероли «толстеют», не выражают правила «свой объект»RequireRole("admin")
Claimгибко: отдел, регион, тарифзначения приходят извне — нужна валидация источникаRequireClaim("department", "finance")
Scope (OAuth)делегирование клиенту: что разрешил пользовательscope — про клиента, а не про конкретные данныеRequireClaim("scope", "orders.read")
Политикаодно место, комбинируем условия, тестируетсянужна дисциплина именованияAddPolicy("finance", …)
Политика + ресурсединственный корректный способ для «своих» объектовтребует загрузить объект до проверкиAuthorizeAsync(user, order, "owner-or-admin")

Практическое правило: роль — «может ли этот человек в принципе открыть раздел», политика — «условия доступа к функции», ресурс — «этот конкретный объект». Проверка прав на объект никогда не заменяется проверкой роли, и наоборот.

★ Чек-лист авторизации для API
  1. FallbackPolicy = требует аутентификации; открытые эндпоинты помечены AllowAnonymous осознанно.
  2. Каждый доступ к объекту по id проверяет владельца через IAuthorizationService, а не только факт логина.
  3. Отказ на «не своё» — 403 или замаскированный 404, выбрано для ресурса явно.
  4. Критичные правила живут в политиках/handler’ах, а не размазаны по эндпоинтам.
  5. Роли/права в токене не считаются «вечными»: TTL токена и/или проверка по БД для критичных операций.
  6. Есть тесты на отказ: без токена, чужая роль, чужой объект, несуществующий id — все четыре случая.
★ Что спросят и как отвечать
  1. «Чем 401 отличается от 403?» — 401: не аутентифицирован (нужен токен), 403: аутентифицирован, но политика не пропустила.
  2. «Как проверить, что пользователь не читает чужой заказ?» — загрузить заказ и вызвать AuthorizeAsync(user, order, policy); проверять sub против владельца или арендатора.
  3. «Зачем FallbackPolicy?» — чтобы новый эндпоинт по умолчанию был закрыт: забыть RequireAuthorization проще, чем забыть AllowAnonymous.
  4. «Почему 404 вместо 403?» — чтобы не подтверждать существование чужого объекта; выбирается для каждого ресурса.
  5. «Где хранить права: в токене или в БД?» — в токене быстрее, но устаревает; в БД актуальнее, но дороже. Обычно: в токене — роли/scope, в БД/кэше — права на объекты и критичные флаги.
