Глава 8. Сеть: порты, DNS и localhost

Почему localhost внутри контейнера — это не хост, зачем нужна своя сеть и как сервисы находят друг друга по имени. Все команды и выводы в главе проверены на Docker с образом nginx:alpine и alpine.

основная глава

Три направления трафика

Первое, что нужно держать в голове: у контейнера свой сетевой стек (namespaces из главы 2). Поэтому «localhost» и «порт» означают разное в зависимости от того, откуда смотреть:

Кто к комуЧто писатьПочему
Хост → контейнерhttp://localhost:18080 (если опубликован -p 18080:80)Порт опубликован на хосте и ведёт внутрь контейнера
Контейнер → хостIP шлюза (172.17.0.1) или host.docker.internal с --add-hostlocalhost внутри — это сам контейнер, а не хост
Контейнер → контейнеримя контейнера в пользовательской сети: http://webВ своей сети Docker поднимает встроенный DNS
 
# Поднимаем веб-сервер и публикуем порт: -d — в фоне, --name — имя, -p хост:контейнер
docker run -d --name web -p 18080:80 nginx:alpine

# С хоста: обращаемся к ОПУБЛИКОВАННОМУ порту 18080
curl -s -o /dev/null -w 'host->18080: %{http_code}\n' http://localhost:18080/
# host->18080: 200

# Внутри контейнера работает ЕГО порт 80 (тут слушает nginx), а 18080 внутри нет
docker exec web wget -qO- -T2 http://localhost:80 | head -1      # HTML nginx
docker exec web wget -qO- -T2 http://localhost:18080             # Connection refused

Разбор флагов: -d — запустить в фоне и вернуть управление; --name web — задать имя (по нему потом docker exec, logs, network connect); -p 18080:80 — слева порт хоста, справа порт контейнера; nginx:alpine — образ и тег.

Почему -p 8080:80 «не работает» с .NET 8

Официальный образ mcr.microsoft.com/dotnet/aspnet:8.0 задаёт переменную ASPNETCORE_HTTP_PORTS=8080 (проверено: docker run --rm mcr.microsoft.com/dotnet/aspnet:8.0-alpine sh -c 'echo $ASPNETCORE_HTTP_PORTS' печатает 8080). Приложение слушает 8080 внутри контейнера, поэтому правильная публикация — -p 8080:8080: левый порт можно менять, правый должен совпадать с тем, что слушает приложение. Подробнее — глава 13.

Публикация портов: -p, -P и EXPOSE

# 1) Конкретный порт хоста
docker run -d --name web -p 18080:80 nginx:alpine

# 2) Только на loopback хоста: снаружи (из другой машины) порт недоступен
docker run -d --name web4 -p 127.0.0.1:18082:80 nginx:alpine

# 3) Случайный свободный порт хоста: Docker выберет сам
docker run -d --name web7 -P nginx:alpine        # -P (большая) публикует все EXPOSE-порты образа

# 4) Посмотреть, что куда опубликовано
docker port web        # 80/tcp -> 0.0.0.0:18080  и  [::]:18080
docker port web7       # 80/tcp -> 0.0.0.0:32768  (случайный)

Что показали проверки:

  • -p 127.0.0.1:18082:80 — с хоста 200, а из другого контейнера через шлюз 172.17.0.1:18082 — Connection refused: порт привязан только к loopback хоста.
  • -P дал 32768, и запрос на него вернул 200. Полезно, когда параллельно запускают несколько копий одного сервиса.
  • EXPOSE в Dockerfile ничего не публикует — это только документация и значение по умолчанию для -P. Контейнер без -p: с хоста curl localhost:18081 не отвечает, а из другого контейнера по IP 172.17.0.x — отвечает.
  • Занятый порт даёт ошибку демона (проверено): Bind for 0.0.0.0:18080 failed: port is already allocated.

DNS: почему имя работает не всегда

У Docker есть три предустановленные сети (проверено docker network ls): bridge (по умолчанию), host и none. В дефолтной bridge имена контейнеров не резолвятся:

# Пробуем обратиться к контейнеру по имени из другого контейнера (оба в дефолтной bridge)
docker run --rm alpine wget -qO- -T2 http://web
# wget: bad address 'web'      ← DNS-имени нет

# А по IP — работает: узнаём адрес через inspect
IP=$(docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' web)
echo $IP                       # 172.17.0.3
docker run --rm alpine wget -qO- -T2 http://$IP | head -1     # HTML nginx

Разбор: docker inspect -f '{{…}}' — вывод по шаблону Go: .NetworkSettings.Networks — карта сетей, .IPAddress — адрес в каждой. Команда возвращает то, что нужно, без огромного JSON.

Своя сеть решает проблему: в пользовательской сети Docker поднимает встроенный DNS, и имя контейнера становится адресом.

# Создаём свою сеть (драйвер bridge по умолчанию)
docker network create appnet

# Подключаем уже запущенный контейнер в эту сеть (он остаётся и в старой)
docker network connect appnet web

# Теперь имя резолвится: клиент в той же сети ходит по имени
docker run --rm --network appnet alpine wget -qO- -T2 http://web | head -1    # HTML nginx

# Смотрим параметры сети: подсеть и шлюз
docker network inspect appnet --format '{{.Name}} sub={{range .IPAM.Config}}{{.Subnet}} gw={{.Gateway}}{{end}}'
# appnet sub=172.18.0.0/16 gw=172.18.0.1

# У контейнера теперь два адреса — по одному в каждой сети
docker inspect -f '{{range $k, $v := .NetworkSettings.Networks}}{{$k}}={{$v.IPAddress}} {{end}}' web
# appnet=172.18.0.2 bridge=172.17.0.3

Флаги и слова: docker network create — создать сеть; connect — подключить контейнер к ещё одной сети (можно и disconnect); --network appnet при docker run — сразу запустить в этой сети; --format — шаблон вывода; .IPAM.Config — настройки адресации (Subnet, Gateway).

Правило, которое экономит часы

Если сервисы должны видеть друг друга по имени — запускайте их в одной пользовательской сети. Именно это делает docker compose автоматически: создаёт сеть проекта и поднимает в ней все сервисы, поэтому в compose-файле хост базы — db, а не localhost (глава 11).

Из контейнера в хост

Обратное направление сложнее: localhost внутри контейнера — это сам контейнер. Вариантов три, и все проверены:

# 1) Шлюз сети — это хост со стороны контейнера
docker run --rm alpine sh -c 'ip route | grep default'
# default via 172.17.0.1 dev eth0        ← 172.17.0.1 и есть хост

# 2) host.docker.internal: на Linux имени нет по умолчанию
docker run --rm alpine wget -qO- -T2 http://host.docker.internal:18080
# wget: bad address 'host.docker.internal:18080'

# 2b) …пока не добавим запись в /etc/hosts контейнера
docker run --rm --add-host=host.docker.internal:host-gateway alpine \
  wget -qO- -T2 http://host.docker.internal:18080 | head -1     # HTML nginx

# 3) --network host: контейнер вообще без своей сети, порты — хостовые
docker run -d --name web5 --network host nginx:alpine
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:80/    # 200
  • --add-host имя:host-gateway — добавить запись в /etc/hosts контейнера; специальное значение host-gateway Docker заменяет на адрес шлюза. На Docker Desktop (macOS/Windows) host.docker.internal существует из коробки, на Linux — только так.
  • --network host — контейнер использует сетевой стек хоста: своего IP нет, порт 80 занят самим хостом. Удобно для отладки, но плохо для прода: два контейнера с одним портом конфликтуют, а изоляция сети исчезает.

Разбор «Connection refused» к базе

Самая частая жалоба: «приложение в контейнере не подключается к PostgreSQL». Причина всегда в одном из четырёх мест, и проверяются они по порядку:

ПроверкаКомандаЧто значит
Имя резолвится?docker exec app getent hosts dbПусто — контейнеры в разных сетях или в дефолтной bridge
Порт открыт?docker exec app nc -zv db 5432refused — процесс не слушает или слушает не там
На каком порту слушает сервер?docker port dbПоказывает публикацию; без -p пусто — и это нормально внутри сети
Что видит само приложение?docker logs app | tailСтрока подключения в логе — половина ответа
 
# Имя и адрес: getent смотрит те же источники, что и приложение (/etc/hosts, DNS)
docker exec app getent hosts db

# Доступность порта: -z — только проверить, -v — рассказать
docker exec app nc -zv db 5432

# Куда Docker опубликовал порты контейнера (пусто, если -p не задавали)
docker port db

# Внутри контейнера приложения: какой URL реально используется
docker exec app printenv | grep -i -E 'ConnectionStrings|POSTGRES|DB_'

Типичные комбинации ошибок:

  • bad address — имя не резолвится: разные сети (лечится docker network connect или общим compose-файлом).
  • Connection refused на localhost:5432 — приложение ищет базу внутри себя; в строке подключения должен быть db (имя сервиса), а не localhost.
  • Connection refused на db:5432 — база ещё не поднялась или слушает другой порт; проверьте docker logs db и nc -zv.
  • Таймаут вместо отказа — обычно файрвол или порт опубликован на другом интерфейсе (см. привязку к 127.0.0.1 выше).
Проверять изнутри того же контейнера

Все проверки выше делаются из контейнера приложения (docker exec app …), а не с хоста: с хоста видно опубликованные порты, а не сеть контейнеров. Разница ровно та, из-за которой «у меня curl работает, а приложение нет».

★ Что запомнить
  • -p хост:контейнер: слева порт на хосте, справа — внутри контейнера. EXPOSE ничего не публикует, -P публикует все EXPOSE-порты на случайные порты хоста.
  • localhost внутри контейнера — это сам контейнер. Хост — шлюз сети (172.17.0.1) или host.docker.internal с --add-host=host.docker.internal:host-gateway.
  • Имена контейнеров резолвятся только в пользовательской сети; в дефолтной bridge — bad address.
  • docker network create/connect/inspect, docker port, docker inspect -f — четыре команды, которые закрывают почти всю диагностику.
  • .NET 8 в контейнере слушает 8080 (ASPNETCORE_HTTP_PORTS=8080), поэтому публикация — -p 8080:8080, а не -p 8080:80.
  • При ошибке подключения к базе проверяйте по порядку: имя (getent hosts), порт (nc -zv), публикацию (docker port), строку подключения в логах.
