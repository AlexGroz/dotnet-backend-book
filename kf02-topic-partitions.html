Глава 2. Топики и партиции: где лежит сообщение и почему порядок не глобальный

Ключ сообщения, хеш партиции, границы роста топика и что означают Leader, Replicas и Isr в выводе describe

основная глава

Что задаёт топик

Топик — это не только имя. У него есть число партиций, фактор репликации и набор конфигураций. Посмотрим на demo из главы 1:

docker exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic demo
# Topic: demo  TopicId: lr8veZlzSbOdrNUUlPrMLw  PartitionCount: 3  ReplicationFactor: 1
#              Configs: segment.bytes=1073741824
#   Topic: demo  Partition: 0  Leader: 1  Replicas: 1  Isr: 1  Elr:  LastKnownElr:
#   Topic: demo  Partition: 1  Leader: 1  Replicas: 1  Isr: 1  Elr:  LastKnownElr:
#   Topic: demo  Partition: 2  Leader: 1  Replicas: 1  Isr: 1  Elr:  LastKnownElr:
ПолеЧто означает
TopicIdвнутренний идентификатор топика. Он не меняется при переименовании и отличает новый топик с тем же именем от старого
PartitionCountсколько партиций: столько независимых журналов и столько параллельных читателей максимум (внутри одной группы)
ReplicationFactorсколько копий каждой партиции хранится в кластере
Configsнастройки топика, отличающиеся от настроек брокера. Здесь только segment.bytes, унаследованный от брокера
Leaderброкер, который принимает записи и отдаёт чтение для этой партиции
Replicasвсе брокеры, на которых лежит копия партиции
Isrin-sync replicas: реплики, которые не отстали от лидера. Только они могут стать новым лидером без потери данных
Elreligible leader replicas — расширенный набор кандидатов в лидеры (появился в KRaft-кластерах)

Пока брокер один, все роли — 1: он и лидер, и реплика, и синхронная реплика. Смысл колонок становится виден в кластере из нескольких брокеров (глава 5).

Ключ решает, в какую партицию писать

В главе 1 ключи k1, k2, k3 разошлись по партициям 2, 0 и 1. Это не случайность и не порядок отправки: партиция вычисляется из ключа:

partition = hash(key) mod число_партиций

при 3 партициях:  k1 → 2,  k2 → 0,  k3 → 1
при 6 партициях:  тот же k1 может попасть в другую партицию

Из этого следуют три важных свойства:

  • Один ключ — всегда одна партиция. Пока число партиций не менялось, все сообщения с ключом k1 попадут в партицию 2.
  • Порядок есть только на ключ. В партиции 2 записи k1 получили оффсеты 0, 1, 2, 3 — по порядку отправки. Но между k1 и k2 никакого порядка нет: они в разных журналах.
  • Разные ключи могут делить партицию. В том же прогоне ключ k9 тоже попал в партицию 2 — хеши совпали по модулю. Это нормально: партиций меньше, чем ключей.
# отдельный топик на три партиции, чтобы отсчёт оффсетов начался с нуля
docker exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic keys --partitions 3 --replication-factor 1

# три сообщения с ключом k1 и одно с ключом k9
printf 'k1:x1\nk1:x2\nk1:x3\nk9:z\n' | docker exec -i kafka /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server localhost:9092 --topic keys --property parse.key=true --property key.separator=:

docker exec kafka /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 \
  --topic keys --from-beginning --max-messages 4 \
  --property print.key=true --property print.partition=true --property print.offset=true
# Partition:2  Offset:0  k1  x1
# Partition:2  Offset:1  k1  x2
# Partition:2  Offset:2  k1  x3
# Partition:2  Offset:3  k9  z
# Processed a total of 4 messages

Без ключа: sticky, а не «по кругу»

Если ключ не задан, партиция выбирается не хешем. Клиент применяет sticky-стратегию: пока набирается батч, все сообщения летят в одну партицию, затем выбирается следующая. На небольшой пачке это выглядит так, будто партиции вообще не используются:

# ключи не заданы: просто шесть строк
printf 'n1\nn2\nn3\nn4\nn5\nn6\n' | docker exec -i kafka /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server localhost:9092 --topic nokeys

docker exec kafka /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 \
  --topic nokeys --from-beginning --max-messages 6 \
  --property print.partition=true --property print.offset=true
# Partition:0  Offset:0  n1
# Partition:0  Offset:1  n2
# Partition:0  Offset:2  n3
# Partition:0  Offset:3  n4
# Partition:0  Offset:4  n5
# Partition:0  Offset:5  n6
# Processed a total of 6 messages

Причина — производительность: один батч в одну партицию означает меньше запросов и лучшее сжатие. Следствия важнее: без ключа Kafka не обещает порядок и не размазывает нагрузку по сообщениям. Нужен порядок на сущность — задайте ключ: id заказа, id пользователя, id устройства.

Ловушка: партиционер зависит от клиента

Хеш — это не «вообще хеш», а конкретная функция из библиотеки. Проверено на одном топике на 3 партиции и одном ключе k1: консольная утилита (Java-клиент) положила его в партицию 2, а Confluent.Kafka с настройками по умолчанию — в партицию 1.

# одно и то же сообщение с ключом k1, записанное разными клиентами в один топик
# console → partition 2, .NET (по умолчанию) → partition 1
docker exec kafka /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 \
  --topic same --from-beginning --max-messages 2 \
  --property print.key=true --property print.partition=true --property print.offset=true
# Partition:2  Offset:0  k1  from-console
# Partition:1  Offset:0  k1  from-dotnet
# Processed a total of 2 messages

Лечится настройкой партиционера — нужно выбрать тот же алгоритм, что у Java-клиента:

var cfg = new ProducerConfig
{
    BootstrapServers = "localhost:9092",       // адрес брокера
    Acks = Acks.All,                           // ждать подтверждения от всех синхронных реплик
    EnableIdempotence = true,                  // защита от дублей при ретраях (глава 3)
    Partitioner = Partitioner.Murmur2Random,   // murmur2, как у Java-клиента
};
using var p = new ProducerBuilder<string, string>(cfg).Build();
var dr = await p.ProduceAsync("same2", new Message<string, string> { Key = "k1", Value = "from-dotnet" });
Console.WriteLine($"dotnet murmur2 k1 -> partition {dr.Partition.Value}");
// dotnet murmur2 k1 -> partition 2   <- совпало с консолью
Клиент / настройкаАлгоритмПартиция для k1 (3 партиции)
Java-клиент, консольные утилитыmurmur2 по ключу2
Confluent.Kafka по умолчаниюconsistent_random (CRC32) 1
Partitioner.Murmur2Randommurmur2 по ключу2
Почему это критично в проде

Если часть producer'ов пишет из Java, часть из .NET, а партиционеры разные, один ключ окажется в двух партициях — и порядок по этому ключу исчезнет. Клиенты не узнают об этом: оба вызова успешны, просто события лежат в разных журналах. Договоритесь об алгоритме явно: в .NET — Partitioner.Murmur2Random, в Java — значение по умолчанию.

Число партиций можно только увеличивать

Партиции добавляют, когда читатели не успевают: больше партиций — больше параллельных потребителей в группе. Команда не печатает ничего при успехе и меняет только счётчик:

# увеличить число партиций с 3 до 6
docker exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --alter --topic keys --partitions 6
# (пусто, код возврата 0)

docker exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic keys
# Topic: keys  TopicId: kYUr7SVOS2G5RN-42m3Zjg  PartitionCount: 6  ReplicationFactor: 1
#              Configs: segment.bytes=1073741824
# ...шесть строк Partition: 0..5

# уменьшить нельзя
docker exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --alter --topic keys --partitions 4
# Error while executing topic command : The topic keys currently has 6 partition(s); 4 would not be an increase.
# ... InvalidPartitionsException: The topic keys currently has 6 partition(s); 4 would not be an increase.
Увеличение партиций ломает привязку ключа

Старые записи остаются в своих партициях, но для новых сообщений hash(key) mod 6 уже не то же, что hash(key) mod 3: ключ, который жил в партиции 2, может уехать в другую. Порядок по этому ключу разрывается. Поэтому число партиций планируют заранее «на вырост», а не увеличивают на работающем потоке.

Автосоздание топиков и значения по умолчанию

Kafka создаёт топик при первой записи, если его нет. Проверено на этом брокере:

# --entity-type brokers --entity-name 1 --all  показать все настройки брокера 1
docker exec kafka /opt/kafka/bin/kafka-configs.sh --bootstrap-server localhost:9092 \
  --describe --entity-type brokers --entity-name 1 --all | grep -E 'auto.create.topics.enable|num.partitions'
# auto.create.topics.enable=true   ... DEFAULT_CONFIG:auto.create.topics.enable=true
# num.partitions=1                 ... STATIC_BROKER_CONFIG:num.partitions=1, DEFAULT_CONFIG:num.partitions=1

Значит случайно созданный топик получит одну партицию и одну реплику — и «ускорить» его потом можно только добавлением партиций. В продакшене автосоздание отключают (auto.create.topics.enable=false) и создают топики явно, с нужным числом партиций и репликацией.

Реплики: что защищает от потери брокера

Сейчас у всех партиций ReplicationFactor: 1: копия одна, и её потеря — потеря данных. Для продакшена фактор репликации 3 означает три копии на разных брокерах; лидер принимает записи, остальные догоняют.

Две настройки определяют, когда запись считается надёжной:

docker exec kafka /opt/kafka/bin/kafka-configs.sh --bootstrap-server localhost:9092 \
  --describe --entity-type topics --entity-name orders --all | grep -E 'min.insync.replicas|unclean.leader'
# min.insync.replicas=1                  ... DEFAULT_CONFIG:min.insync.replicas=1
# unclean.leader.election.enable=false   ... DEFAULT_CONFIG:unclean.leader.election.enable=false
НастройкаЧто означает
min.insync.replicasсколько синхронных реплик должно подтвердить запись, чтобы producer с acks=all получил успех. Для RF=3 ставят 2: переживает потерю одного брокера
unclean.leader.election.enableразрешать ли выбирать лидером отставшую реплику. false — лучше остаться без записи, чем потерять уже подтверждённые данные
replication-factorсколько копий хранить. 3 — стандарт для продакшена; 1 — только для локальных опытов

Связка для «не терять подтверждённое»: replication-factor=3 + min.insync.replicas=2 + acks=all у producer (глава 3). Если acks=1, подтверждение придёт от лидера, а он может упасть до того, как реплики заберут запись.

★ Что запомнить из главы
  • Партиция выбирается по ключу: hash(key) mod partitionCount. Один ключ — одна партиция, и только внутри неё сохраняется порядок.
  • Без ключа — sticky-батчи: сообщения липнут к одной партиции, порядок между ними не обещан.
  • Партиционер зависит от клиента: Java — murmur2, Confluent.Kafka по умолчанию — CRC32. Для совместимости ставят Partitioner.Murmur2Random.
  • Партиций может стать больше, но не меньше; увеличение меняет отображение ключей и рвёт порядок на ключ.
  • Автосоздание даёт 1 партицию и 1 реплику; в проде топики создают явно.
  • Надёжность — это RF, ISR и acks: 3 копии, min.insync.replicas=2, acks=all.
