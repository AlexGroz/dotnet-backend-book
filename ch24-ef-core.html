Глава 24. ORM и EF Core эффективно

Tracking, проекции, N+1, массовые операции

основная глава

Что делает EF Core (и за что вы платите)

EF Core — это посредник между объектами C# и таблицами: он строит SQL из LINQ, отслеживает изменения (change tracker) и умеет применять миграции схемы. Плата — непрозрачность: не посмотрев на сгенерированный SQL, легко получить лишние запросы и лишний I/O.

Хорошая новость: у EF Core есть ровно один «фонарик», который всё показывает:

var query = db.Orders.Where(o => o.UserId == userId).OrderByDescending(o => o.CreatedAt).Take(20);

Console.WriteLine(query.ToQueryString());     // SQL, который уйдёт в базу — ДО выполнения
await query.ToListAsync(ct);

Четыре приёма, которые дают 90 % эффекта

  1. AsNoTracking() для чтения. Change tracker не нужен, если данные не будут меняться: меньше памяти и меньше работы на каждый объект.
  2. Проекции вместо сущностей. Выбирайте только нужные поля — это меньше данных и часто позволяет базе использовать покрывающий индекс (SQL-раздел о индексах).
  3. Никаких «N+1». Один запрос на список + по запросу на элемент — классика медленного API. Лечится Include, проекцией или отдельным запросом по списку ключей. Что это такое и как поймать — ниже, отдельный раздел.
  4. Пагинация по ключу. Skip/Take с глубоким OFFSET тормозит: OFFSET — это «пропусти N строк», и база честно читает и выбрасывает их (подробно — SQL-раздел, глава про OFFSET и keyset). Keyset-пагинация (where created_at < :last) работает по индексу независимо от глубины.
Два обозначения, которые встретятся ниже
  • OFFSET 10000 — «пропусти первые 10 000 строк». База читает их, сортирует и выбрасывает, поэтому время растёт с глубиной страницы.
  • :last — параметр: «сюда приложение подставит значение» (последний created_at с предыдущей страницы). Двоеточие — не SQL-синтаксис PostgreSQL, а запись «здесь параметр»; в Npgsql это будет @last, в psql — :'last'. Подробно — SQL-раздел, глава 4 «Параметры в SQL».
// ✘ N+1: один запрос за заказами + по запросу за клиентом каждого заказа
var orders = await db.Orders.Take(100).ToListAsync(ct);
foreach (var o in orders) Console.WriteLine(o.Customer.Name);

// ✔ один запрос с проекцией (и без лишних полей)
var rows = await db.Orders
    .AsNoTracking()
    .OrderByDescending(o => o.CreatedAt)
    .Take(100)
    .Select(o => new OrderRow(o.Id, o.Total, o.Customer.Name))
    .ToListAsync(ct);
Change tracker: что происходит с ним и без него

С трекингом (по умолчанию): EF Core запоминает каждый загруженный объект и его исходные значения в snapshot. При SaveChanges он сравнивает текущее состояние с исходным и генерирует UPDATE только для изменённых полей. Цена — память на снимки всех загруженных объектов и время на сравнение.

Без трекинга (AsNoTracking()): объекты создаются и сразу «забываются»: памяти меньше, чтение быстрее. Но изменения в этих объектах SaveChanges не увидит.

// чтение для отображения: меняться не будет → трекинг не нужен
var rows = await db.Orders.AsNoTracking().Where(o => o.Total > 100).ToListAsync(ct);

// чтение с последующим изменением: нужен трекинг, иначе SaveChanges ничего не сохранит
var order = await db.Orders.FirstAsync(o => o.Id == id, ct);
order.MarkAsPaid();
await db.SaveChangesAsync(ct);

«N+1»: главная болезнь ORM

«N+1» — это когда для списка из N элементов приложение делает 1 запрос за списком и ещё N запросов за связанными данными. Итого N+1 обращений к базе вместо одного-двух. На 20 заказах это незаметно, на 10 000 — превращается в секунды и забитый пул соединений.

Почему это происходит. Причина всегда одна: код ходит к навигационному свойству после того, как список уже получен. ORM видит «нужен o.Customer» и делает отдельный запрос — на каждый элемент. Если включена ленивая загрузка (lazy loading), это происходит даже без видимого вами запроса: достаточно обратиться к свойству в foreach.

// ✘ 1 запрос за заказами + N запросов за клиентами (по одному на заказ)
var orders = await db.Orders.Take(100).ToListAsync(ct);    // 1
foreach (var o in orders)
    Console.WriteLine(o.Customer.Name);                     // +100 запросов

// ✔ один запрос: связь загружается сразу
var orders2 = await db.Orders
    .Include(o => o.Customer)
    .Take(100)
    .ToListAsync(ct);

// ✔ ещё лучше: проекция — только нужные поля
var rows = await db.Orders
    .Select(o => new { o.Id, o.Total, Customer = o.Customer.Name })
    .Take(100)
    .ToListAsync(ct);

Как увидеть, что это оно. Три признака, по которым N+1 узнаётся сразу:

  • в логе EF Core (или PostgreSQL) много одинаковых запросов, отличающихся только параметром — WHERE id = 1, WHERE id = 2, …;
  • число SQL-запросов на один HTTP-запрос растёт вместе с числом элементов в списке;
  • время эндпоинта зависит от размера страницы почти линейно.

На реальных таблицах: 3 клиента, 3 заказа

CREATE TABLE customers (id int PRIMARY KEY, name text NOT NULL);
CREATE TABLE orders    (id int PRIMARY KEY, customer_id int REFERENCES customers(id), total numeric);

Что уходит в базу (лог EF Core): 1 + N запросов

-- 1) список заказов
SELECT id, customer_id, total FROM orders LIMIT 3;

-- 2) дальше — по одному запросу на КАЖДЫЙ заказ (это и есть «+N»)
SELECT id, name FROM customers WHERE id = 1;
SELECT id, name FROM customers WHERE id = 2;
SELECT id, name FROM customers WHERE id = 3;

-- Итого: 1 + 3 = 4 запроса. На 10 000 заказов — 10 001.

Исправление: один запрос с JOIN

SELECT o.id, o.total, c.name
FROM orders o
JOIN customers c ON c.id = o.customer_id
LIMIT 3;

Почему это дорого даже при быстрой базе: каждый запрос — отдельный round-trip по сети (даже 0,2 мс на 10 000 дают 2 секунды только на «туда-обратно»), плюс 10 000 раз разбирается и планируется один и тот же SQL. И каждое такое обращение занимает соединение из пула (глава 23).

  • Откуда берётся: ленивая загрузка (lazy loading) или обращение к навигационному свойству после того, как список уже получен.
  • Как заметить: счётчик SQL-запросов на один HTTP-запрос; в логах — одинаковые запросы, отличающиеся только параметром.
  • Как лечить: Include (нужна вся сущность), проекция (нужны несколько полей) или отдельный запрос по списку ключей (WHERE Id IN (…)) — два запроса вместо N+1.
  • Чего не делать: «выключить ленивую загрузку и надеяться». Лучше вообще её не включать и загружать связи явно — тогда N+1 просто негде взяться.

Include и AsSplitQuery: в чём разница

Include по умолчанию собирает всё одним SQL с JOIN. Если включить две коллекции сразу, строки начинают дублироваться: каждая комбинация «заказ × позиция × комментарий» — отдельная строка результата.

// один запрос с JOIN: 10 заказов × 5 позиций × 3 комментария = 150 строк
var orders = await db.Orders
    .Include(o => o.Items)
    .Include(o => o.Comments)
    .Take(10)
    .ToListAsync(ct);

// несколько запросов: без «декартова взрыва» и дублирующихся строк
var orders2 = await db.Orders
    .Include(o => o.Items)
    .Include(o => o.Comments)
    .AsSplitQuery()
    .Take(10)
    .ToListAsync(ct);

Что генерирует EF для обычного Include — ОДИН SQL

SELECT t.id, t.total, i.id, i.qty, c.id, c.text
FROM (SELECT id, total FROM orders ORDER BY id LIMIT 10) AS t      -- ваш Take(10): 10 заказов
LEFT JOIN order_items    AS i ON i.order_id = t.id                 -- EF добавил сам
LEFT JOIN order_comments AS c ON c.order_id = t.id;                -- EF добавил сам

Откуда здесь WHERE/JOIN, если в вашем коде их не было. Их добавил EF: вы попросили Include, и он сам собрал соединения по ключам связи. Ваш код лишь говорит что нужно, SQL строит провайдер. Поэтому «код почти одинаковый» — это нормально: разница будет в сгенерированном SQL, а не в LINQ.

Строк в ответе столько, сколько комбинаций «заказ × позиция × комментарий»: у заказа с 2 позициями и 2 комментариями — 4 строки. На 10 заказах × 5 позиций × 3 комментария — 150 строк, хотя заказов всего 10.

Тот же запрос с AsSplitQuery() — ТРИ SQL

-- 1) корневые заказы: ровно ваш запрос (фильтр, сортировка, Take — всё здесь)
SELECT id, total FROM orders ORDER BY id LIMIT 10;                     → 10 строк

-- 2) позиции ТОЛЬКО для этих заказов: фильтр по ключу придумал EF
SELECT id, order_id, qty FROM order_items    WHERE order_id IN (1, …, 10);  → 50 строк

-- 3) комментарии ТОЛЬКО для этих же заказов
SELECT id, order_id, text FROM order_comments WHERE order_id IN (1, …, 10); → 30 строк

-- Итого: 10 + 50 + 30 = 90 строк вместо 150, но три round-trip вместо одного

В чём выгода и в чём плата. Выгода — нет дублирования строк, поэтому по сети и в память едет меньше данных (и «декартов взрыв» исчезает). Плата — три обращения к базе вместо одного и разные снимки: между запросами данные могли измениться (в другом соединении/транзакции), поэтому объекты могут оказаться «несогласованными». Плюс Take сначала применяется к корню, а вторые два запроса используют ключи этих 10 заказов — именно поэтому в них появляется WHERE order_id IN (…).

Выбор делается по измерениям: смотрим SQL из логов, размер результата и время. «Всегда AsSplitQuery» и «всегда один запрос» — одинаково неверные стратегии.

Смена провайдера: Oracle → PostgreSQL

SQL пишет провайдер (Oracle.EntityFrameworkCore → Npgsql.EntityFrameworkCore.PostgreSQL). Поэтому при переезде меняется диалект, а «тот же LINQ» может дать другой — или неожиданно плохой — запрос.

ОбластьOraclePostgreSQL
ПагинацияROW_NUMBER / OFFSET … FETCHLIMIT … OFFSET
Логический типNUMBER(1)boolean
GUIDRAW(16)uuid
Пустая строка'' = NULL'' ≠ NULL
Дата-времяDATE содержит времяtimestamp ≠ timestamptz
 
// (1) Пагинация: один и тот же LINQ — разный SQL
var page = await db.Orders.OrderBy(o => o.Id).Skip(20_000).Take(20).ToListAsync(ct);
// PostgreSQL: ORDER BY o.id LIMIT @__p_1 OFFSET @__p_0      ← «страница по номеру» = OFFSET
// Oracle:     OFFSET 20000 ROWS FETCH NEXT 20 ROWS ONLY     (или ROW_NUMBER() OVER …)
// Следствие: на глубоких страницах OFFSET дорожает → keyset (см. ниже и SQL-раздел, гл. 20)

// (2) UUID: решаем, ГДЕ рождается значение
modelBuilder.Entity<Order>().Property(o => o.Id)
    .HasDefaultValueSql("gen_random_uuid()");   // значение создаёт PostgreSQL (PG13+ / pgcrypto)
// альтернатива — Guid.NewGuid() в приложении: id известен ДО вставки (удобно для outbox и ссылок)

// (3) Типы задаём явно, чтобы схема совпала с существующей после миграции
modelBuilder.Entity<Order>().Property(o => o.CreatedAt).HasColumnType("timestamptz");
modelBuilder.Entity<Order>().Property(o => o.Total).HasPrecision(18, 2);

Главная ловушка миграции — неявное приведение типов. Если колонка uuid, а параметр уходит строкой, PostgreSQL приводит колонку к тексту, и индекс по ней становится неприменим:

// ✘ параметр — строка, колонка — uuid
cmd.CommandText = "SELECT id FROM orders WHERE user_id = @uid";
cmd.Parameters.AddWithValue("uid", userId.ToString());
// SQL: WHERE user_id = ($1)::text   → сравнение по тексту → Seq Scan

// ✔ параметр того же типа, что колонка
cmd.Parameters.AddWithValue("uid", userId);              // Guid → uuid
// SQL: WHERE user_id = $1          → Index Scan using orders_user_id_idx

Планы: до и после

✘ WHERE user_id = ($1)::text
Seq Scan on orders  (actual time=0.03..612.4 rows=3 loops=1)
  Filter: ((user_id)::text = '2f1c…'::text)      ← приведение НАД КОЛОНКОЙ
  Rows Removed by Filter: 480000                 ← прочитали полмиллиона строк ради трёх

✔ WHERE user_id = $1
Index Scan using orders_user_id_idx on orders  (actual time=0.02..0.05 rows=3 loops=1)
  Index Cond: (user_id = '2f1c…'::uuid)          ← прямое сравнение того же типа
  • Проверяйте SQL, а не догадывайтесь: ToQueryString() и логирование EF показывают, что реально уходит в базу. Если выражение не перевелось — оно выполнится на клиенте (медленно и незаметно).
  • Типы задавайте явно: HasColumnType("uuid" | "timestamptz"), HasPrecision(18, 2), HasConversion<string>() — иначе провайдер выберет сам, и это может не совпасть с существующей схемой.
  • Приведения ломают индексы: если колонка uuid, а параметр приходит как text, в плане появляется Seq Scan. Передавайте Guid/DateTime, а не строки.
  • Время храните в UTC (DateTime.UtcNow) — иначе timestamptz «поедет» при смене таймзоны сервера.
  • Глубокую пагинацию переведите на keyset (см. выше) — иначе OFFSET 100000 будет читать и выбрасывать сто тысяч строк.

Массовые операции: не тяните данные в память

// ✔ один SQL на всю пачку, без загрузки сущностей и change tracker
await db.Orders
    .Where(o => o.Status == OrderStatus.New && o.CreatedAt < cutoff)
    .ExecuteUpdateAsync(s => s.SetProperty(o => o.Status, OrderStatus.Expired), ct);

await db.Orders.Where(o => o.CreatedAt < cutoff).ExecuteDeleteAsync(ct);
  • ExecuteUpdate/ExecuteDelete (EF Core 7+) выполняют изменение одной командой. Плюс: они меняют только указанные колонки — это важно для HOT-апдейтов в PostgreSQL (глава 25 SQL-раздела).
  • Массовые вставки: AddRange с разбивкой на батчи; для миллионов строк — COPY через NpgsqlBinaryImporter, а не по одной сущности.
  • Удаление старых данных лучше делать секциями (SQL-раздел про секционирование), а не миллионами DELETE, которые создают мёртвые версии.

Когда EF Core не хватает

  • Сложная аналитика и оконные функции — проще написать SQL, чем подбирать LINQ. Для таких мест берут Dapper или FromSql.
  • Параметры в raw SQL обязательны: FromSqlInterpolated (или FromSqlRaw с явными параметрами) — склейка значений строками даёт и проблемы с планом, и риск инъекции.
  • Хитрые bulk-операции (например, загрузка миллионов строк) — COPY, NpgsqlBinaryImporter или пакетные задания.
// ✔ параметр типизирован, база снова может использовать индекс
var last = await db.Orders
    .FromSqlInterpolated($"SELECT * FROM orders WHERE user_id = {userId} ORDER BY created_at DESC LIMIT 20")
    .AsNoTracking()
    .ToListAsync(ct);

Как проверять эффективность

  • Логирование запросов в dev: LogTo(Console.WriteLine), категория Microsoft.EntityFrameworkCore.Database.Command. Видно SQL, параметры и время. В продакшене — включать точечно, EnableSensitiveDataLogging — только в dev (в логах будут значения!).
  • Счётчик запросов на один HTTP-запрос. Резкий рост — почти всегда «N+1».
  • pg_stat_statements (SQL-раздел про мониторинг): топ запросов по суммарному времени — там видно, какой именно LINQ оказался дорогим.
  • EXPLAIN (ANALYZE, BUFFERS) для горячих запросов: проверяем, что индексы действительно применяются (глава 21 и SQL-раздел).
★ Что запомнить из главы
  • EF Core удобен, но непрозрачен: смотрите сгенерированный SQL (ToQueryString(), логи).
  • Базовый набор: AsNoTracking, проекции, никаких «N+1», пагинация по ключу.
  • SQL пишет провайдер: при переезде Oracle → PostgreSQL проверяйте диалект, типы и приведения (они убивают индексы).
  • Массовые изменения — ExecuteUpdate/ExecuteDelete и батчи, а не «загрузить всё в память».
  • Проверять эффективность нужно измерениями: логи, счётчик запросов, pg_stat_statements, EXPLAIN.
