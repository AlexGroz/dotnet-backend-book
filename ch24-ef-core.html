Глава 24. ORM и EF Core эффективно

Tracking, проекции, N+1, массовые операции

основная глава

Что делает EF Core (и за что вы платите)

EF Core — это посредник между объектами C# и таблицами: он строит SQL из LINQ, отслеживает изменения (change tracker) и умеет применять миграции схемы. Плата — непрозрачность: не посмотрев на сгенерированный SQL, легко получить лишние запросы и лишний I/O.

Хорошая новость: у EF Core есть ровно один «фонарик», который всё показывает:

var query = db.Orders.Where(o => o.UserId == userId).OrderByDescending(o => o.CreatedAt).Take(20);

Console.WriteLine(query.ToQueryString());     // SQL, который уйдёт в базу — ДО выполнения
await query.ToListAsync(ct);

Четыре приёма, которые дают 90 % эффекта

  1. AsNoTracking() для чтения. Change tracker не нужен, если данные не будут меняться: меньше памяти и меньше работы на каждый объект.
  2. Проекции вместо сущностей. Выбирайте только нужные поля — это меньше данных и часто позволяет базе использовать покрывающий индекс (SQL-раздел о индексах).
  3. Никаких «N+1». Один запрос на список + по запросу на элемент — классика медленного API. Лечится Include, проекцией или отдельным запросом по списку ключей.
  4. Пагинация по ключу. Skip/Take с глубоким OFFSET тормозит; keyset-пагинация (`where created_at < :last`) работает по индексу независимо от глубины.
// ✘ N+1: один запрос за заказами + по запросу за клиентом каждого заказа
var orders = await db.Orders.Take(100).ToListAsync(ct);
foreach (var o in orders) Console.WriteLine(o.Customer.Name);

// ✔ один запрос с проекцией (и без лишних полей)
var rows = await db.Orders
    .AsNoTracking()
    .OrderByDescending(o => o.CreatedAt)
    .Take(100)
    .Select(o => new OrderRow(o.Id, o.Total, o.Customer.Name))
    .ToListAsync(ct);
Include: осторожно с «декартовым взрывом»

Несколько Include подряд (две коллекции в одной сущности) дают один запрос с большим соединением и дублирующимися строками. Тогда используют AsSplitQuery() — несколько запросов вместо одного. Выбирать нужно по измерениям, а не по привычке.

Смена провайдера: Oracle → PostgreSQL

SQL пишет провайдер (Oracle.EntityFrameworkCore → Npgsql.EntityFrameworkCore.PostgreSQL). Поэтому при переезде меняется диалект, а «тот же LINQ» может дать другой — или неожиданно плохой — запрос.

  • Проверяйте SQL, а не догадывайтесь: ToQueryString() и логирование EF показывают, что реально уходит в базу. Если выражение не перевелось — оно выполнится на клиенте (медленно и незаметно).
  • Типы задавайте явно: HasColumnType("uuid" | "timestamptz"), HasPrecision(18, 2), HasConversion<string>() — иначе провайдер выберет сам, и это может не совпасть с существующей схемой.
  • Приведения ломают индексы: если колонка uuid, а параметр приходит как text, в плане появляется Seq Scan. Передавайте Guid/DateTime, а не строки.
  • Время храните в UTC (DateTime.UtcNow) — иначе timestamptz «поедет» при смене таймзоны сервера.
  • Глубокую пагинацию переведите на keyset (см. выше) — иначе OFFSET 100000 будет читать и выбрасывать сто тысяч строк.

Массовые операции: не тяните данные в память

// ✔ один SQL на всю пачку, без загрузки сущностей и change tracker
await db.Orders
    .Where(o => o.Status == OrderStatus.New && o.CreatedAt < cutoff)
    .ExecuteUpdateAsync(s => s.SetProperty(o => o.Status, OrderStatus.Expired), ct);

await db.Orders.Where(o => o.CreatedAt < cutoff).ExecuteDeleteAsync(ct);
  • ExecuteUpdate/ExecuteDelete (EF Core 7+) выполняют изменение одной командой. Плюс: они меняют только указанные колонки — это важно для HOT-апдейтов в PostgreSQL (глава 23 SQL-раздела).
  • Массовые вставки: AddRange с разбивкой на батчи; для миллионов строк — COPY через NpgsqlBinaryImporter, а не по одной сущности.
  • Удаление старых данных лучше делать секциями (SQL-раздел про секционирование), а не миллионами DELETE, которые создают мёртвые версии.

Когда EF Core не хватает

  • Сложная аналитика и оконные функции — проще написать SQL, чем подбирать LINQ. Для таких мест берут Dapper или FromSql.
  • Параметры в raw SQL обязательны: FromSqlInterpolated (или FromSqlRaw с явными параметрами) — склейка значений строками даёт и проблемы с планом, и риск инъекции.
  • Хитрые bulk-операции (например, загрузка миллионов строк) — COPY, NpgsqlBinaryImporter или пакетные задания.
// ✔ параметр типизирован, база снова может использовать индекс
var last = await db.Orders
    .FromSqlInterpolated($"SELECT * FROM orders WHERE user_id = {userId} ORDER BY created_at DESC LIMIT 20")
    .AsNoTracking()
    .ToListAsync(ct);

Как проверять эффективность

  • Логирование запросов в dev: LogTo(Console.WriteLine), категория Microsoft.EntityFrameworkCore.Database.Command. Видно SQL, параметры и время. В продакшене — включать точечно, EnableSensitiveDataLogging — только в dev (в логах будут значения!).
  • Счётчик запросов на один HTTP-запрос. Резкий рост — почти всегда «N+1».
  • pg_stat_statements (SQL-раздел про мониторинг): топ запросов по суммарному времени — там видно, какой именно LINQ оказался дорогим.
  • EXPLAIN (ANALYZE, BUFFERS) для горячих запросов: проверяем, что индексы действительно применяются (глава 21 и SQL-раздел).
★ Что запомнить из главы
  • EF Core удобен, но непрозрачен: смотрите сгенерированный SQL (ToQueryString(), логи).
  • Базовый набор: AsNoTracking, проекции, никаких «N+1», пагинация по ключу.
  • SQL пишет провайдер: при переезде Oracle → PostgreSQL проверяйте диалект, типы и приведения (они убивают индексы).
  • Массовые изменения — ExecuteUpdate/ExecuteDelete и батчи, а не «загрузить всё в память».
  • Проверять эффективность нужно измерениями: логи, счётчик запросов, pg_stat_statements, EXPLAIN.
